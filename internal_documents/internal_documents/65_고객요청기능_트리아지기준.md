# 고객 요청 기능 트리아지 기준
<!--meta: doc=PSY-03; doc_type=triage_rule; tier=1; topic=PROCESS; disclosure=internal; status=active-->

## 목적과 적용 범위
<!--meta: sec=s1; dept=CNS|AIAX|BE|SALES; level=주니어|시니어; ct_band=하; related=none-->
트리아지는 쌓인 요청을 분류하여 각 요청에 무엇이 일어날지 정하는 단계입니다.  
단순히 요청을 접수 순서대로 처리하거나 구현 가능 여부만 검토하는 활동은 트리아지에 해당하지 않습니다.

이 문서는 고객 요청을 일관된 기준으로 판정하고, 그 결과를 고객에게 회신하는 원칙을 정합니다.  
적용 대상은 다음과 같습니다.

| 구분 | 적용 대상 | 대표적인 발생 시점 |
|---|---|---|
| 수행 중 프로젝트 | 합의된 요구사항 외에 새로 제기된 기능·개선 요구 | 설계, 개발, 시험, 검수 준비 단계 |
| 운영 단계 | 사용 중 확인된 편의성·성능·관리 기능 개선 요청 | 운영 지원 또는 후속 협의 단계 |
| 사내 공통 자산 | 여러 사업에서 사용할 수 있는 기능 추가 요청 | 자산 적용 검토 또는 재사용 과정 |

다음 사항은 고객 요청 기능 트리아지에서 제외합니다.

- 서비스 중단, 오류 확산 등 장애 신고는 장애 대응 경로로 이관합니다.
- 계약상 하자에 해당할 가능성이 있는 신고는 하자 판정 경로로 이관합니다.
- 정보 유출, 비인가 접근, 취약점 악용 의심 등 보안 사고는 보안 사고 대응 경로로 즉시 이관합니다.
- 최초 접수 시 성격이 불명확하면 기능 요청으로 확정하지 않고 해당 대응 책임자에게 분류를 요청합니다.

이 문서는 다음 사항을 정합니다.

1. 요청을 비교·판정하기 위한 기준을 정합니다.
2. 처리 경로별로 필요한 기록을 정합니다.
3. 고객에게 결과를 전달할 때 사용할 회신 원칙을 정합니다.
4. 보류하거나 거절한 요청에 남겨야 할 근거를 정합니다.

다음 사항은 이 문서에서 정하지 않습니다.

- 회의에서 판정 결과를 다루는 방법은 PSY-02#s7을 참조합니다.
- 계약상 변경 절차는 PRP-04#s10을 참조합니다.
- 변경 범위의 견적과 가격 산정은 PRP-03을 참조합니다.

모든 요청은 수용을 전제로 하지 않습니다.  
계약 범위, 고객 영향, 전략 정합성, 가용 자원 또는 다른 요청과의 우선순위가 기준을 충족하지 않으면 거절할 수 있습니다.  
이 전제를 명시하는 이유는 접수 행위가 구현 약속으로 오해되는 것을 막고, 담당자가 근거 없이 일정이나 제공 여부를 확답하지 않도록 하기 위해서입니다.  
거절은 요청자에 대한 평가가 아니라 해당 시점의 조건에 따른 판정이며, 조건이 달라지면 정해진 기준으로 다시 검토합니다.

## 접수 창구 단일화와 등록 양식
<!--meta: sec=s2; dept=CNS|BE|SALES; level=주니어|시니어; ct_band=중; related=s1-->-->
담당자 개인 메신저, 현장 대화, 전화 또는 개별 메일에 요청이 흩어지면 동일 요청의 중복 여부를 확인할 수 없습니다.  
이 상태에서는 판정 근거, 미처리 건수, 반복 요구, 고객별 요청량도 집계할 수 없습니다.  
따라서 모든 요청은 팀이 지정한 하나의 요청 등록부에 모읍니다.

등록부 밖에서 받은 요청도 정식 접수로 간주할 수 있으나, 받은 사람이 등록 책임을 집니다.  
구두, 전화, 회의 또는 메신저로 요청을 받은 사람은 수신 시점부터 24시간 이내에 등록합니다.  
원래 요청자가 직접 등록하도록 되돌려 보내는 것만으로 등록 책임을 종료하지 않습니다.

등록부는 다음 열을 사용합니다.

| 열 | 기재 기준 |
|---|---|
| 요청 ID | 중복되지 않는 식별자를 부여합니다. |
| 접수 일시 | 최초로 요청을 받은 날짜와 시각을 기록합니다. |
| 접수 경로 | 메일, 회의, 전화, 메신저 등 최초 경로를 기록합니다. |
| 요청자(역할) | 개인 식별이 필요한 범위에서 요청자와 업무 역할을 적습니다. |
| 관련 사업 | 요청이 발생한 프로젝트, 운영 업무 또는 공통 자산을 적습니다. |
| 요청 원문 | 요청자가 사용한 표현을 의미가 바뀌지 않도록 기록합니다. |
| 요청자가 말한 이유 | 요청자가 설명한 불편, 목표 또는 발생 배경을 적습니다. |
| 요청자가 말한 희망 시점 | 요청자가 제시한 날짜나 시기를 적고, 없으면 ‘미제시’로 표시합니다. |
| 등록자 | 등록부에 입력한 담당자를 적습니다. |
| 1차 분류 상태 | 미분류, 확인 필요, 분류 완료 중 하나를 표시합니다. |

요청 원문에는 담당자의 해결책, 우선순위 판단 또는 구현 해석을 섞지 않습니다.  
해석이 필요하면 별도 메모에 작성하고 원문과 구분합니다.  
이 분리는 고객이 실제로 말한 내용과 내부에서 추론한 내용을 나중에 대조하기 위한 것입니다.

등록자는 다음 순서로 입력합니다.

1. 최초 수신 시점을 확인하고 요청 ID를 발급합니다.
2. 원문의 문장 또는 발언 요지를 가능한 한 그대로 옮깁니다.
3. 이유와 희망 시점이 없으면 임의로 추정하지 않고 ‘미확인’으로 적습니다.
4. 관련 사업을 선택하고 자신의 이름을 등록자 열에 남깁니다.
5. 판단에 필요한 정보가 부족하면 상태를 ‘확인 필요’로 지정합니다.

등록되지 않은 요청은 분석, 설계, 개발 또는 배포 대상으로 착수하지 않습니다.  
고객이 일정한 날짜를 언급했더라도 등록 전에는 제공 일정이 확정된 것으로 취급하지 않습니다.

예외는 요청 확인부터 완료 통지까지 총 작업시간이 5분 이내인 경우에만 허용합니다.  
5분을 넘길 가능성이 확인되는 즉시 작업을 중단하고 등록합니다.  
여러 작업을 각각 5분 이하로 나누어 예외를 반복 적용하지 않습니다.  
예외 처리 중 코드 변경, 배포, 데이터 수정 또는 접근 권한 변경이 필요해지면 소요시간과 관계없이 먼저 등록합니다.

## 문제 단위로 묶기
<!--meta: sec=s3; dept=CNS|AIAX|DATA; level=시니어; ct_band=상; related=s2|s5-->-->
요청을 한 건씩 독립적으로 처리하면 같은 근본 문제에 서로 다른 기능을 덧붙일 수 있습니다.  
그 결과 중복 개발, 상충하는 동작, 특정 요청자에게만 맞는 해법이 발생할 수 있습니다.  
분류 담당자는 개별 요청을 근본 문제 단위로 묶고, 드러난 주제를 고객 영향과 전략 정합성으로 비교합니다.

묶기 작업은 다음 순서로 수행합니다.

1. 요청 문장에서 요청자가 원하는 해법을 표시합니다.
2. 그 해법으로 해결하려는 불편, 손실 또는 목표를 별도로 적습니다.
3. 문제 서술을 특정 기능명 없이 한 문장으로 작성합니다.
4. 동일하거나 실질적으로 유사한 기존 문제 코드를 검색합니다.
5. 기존 문제가 있으면 해당 코드에 요청을 연결합니다.
6. 기존 문제로 설명할 수 없으면 신규 문제 코드를 생성합니다.

예를 들어 “화면에 다운로드 버튼을 추가해 달라”는 표현에서 버튼은 원하는 해법입니다.  
내부 분류자는 다운로드가 필요한 이유와 현재 완료하지 못하는 업무를 확인한 뒤 문제를 서술합니다.  
이 단계에서는 요청자가 제안한 화면이나 기능을 구현안으로 확정하지 않습니다.

묶음 등록부는 다음 항목으로 구성합니다.

| 항목 | 기록 방법 |
|---|---|
| 문제 코드 | 묶음별 고유 식별자를 부여합니다. |
| 문제 서술 | 영향을 받는 업무와 해결되지 않은 상태를 한 문장으로 적습니다. |
| 연결된 요청 수 | 해당 문제에 병합된 요청 건수를 집계합니다. |
| 영향 고객 수 | 동일 문제를 제기했거나 확인한 고객 수를 기록합니다. |
| 최초 접수일 | 연결된 요청 중 가장 이른 접수일을 사용합니다. |
| 상태 | 확인 중, 비교 대상, 분리 검토, 종료 중 하나로 표시합니다. |

문제를 확인할 때에는 다음 질문을 사용합니다.

- 이 기능이 없어서 현재 완료하지 못하는 업무는 무엇입니까?
- 그 업무를 수행하는 역할과 사용 빈도는 어떻게 됩니까?
- 현재 사용하는 우회 방법은 무엇이며 어떤 비용이나 지연이 발생합니까?
- 요청한 해법이 아니어도 해결되는 최소 조건은 무엇입니까?
- 동일한 문제를 겪는 다른 사용자 또는 조직이 있습니까?
- 문제가 해결되었다고 판단할 수 있는 관찰 가능한 결과는 무엇입니까?

각 문제 묶음에는 고객 영향의 근거와 사업·제품 방향과의 연결 근거를 각각 기록합니다.  
단순 요청 건수만으로 두 기준을 대신하지 않습니다.  
고객 영향에 대한 정량 비교는 s5를 참조하며, 전략 정합성 등 추가 요소는 s6을 참조합니다.

병합 후 서로 다른 원인이나 성공 조건이 확인되면 묶음을 분리합니다.  
분리 담당자는 새 문제 코드를 만들고 해당 요청의 연결을 옮깁니다.  
기존 문제에는 분리 일자, 새 문제 코드, 분리 사유를 남깁니다.  
이미 내려진 판정이 있으면 자동 승계하지 않고 분리된 각 문제를 다시 평가합니다.

## 계약 범위 내외 1차 판정
<!--meta: sec=s4; dept=CNS|SALES; level=시니어; ct_band=상; related=s2|s7-->
등록된 요청은 구현 가능성이나 예상 공수보다 계약상 의무 여부를 먼저 판정합니다.  
판정 책임자는 해당 프로젝트의 CNS 과장 이상 담당자입니다. SALES 담당자는 계약 문서, 견적 전제 및 승인 이력을 제공하고 상업 조건 해석을 지원합니다.

판정은 다음 순서를 바꾸지 않고 수행합니다.

1. 계약서와 과업범위에 기재된 산출물 명세에서 요청 결과가 명시되어 있는지 확인합니다.
2. 범위 외 항목 목록 및 인수인계 시 확인된 제외 조건과 대조합니다. 제외 조건의 원문은 `PSY-01#s7 참조`로 확인합니다.
3. 기존 합의 결과가 기준에 미달한 것인지, 새로운 결과를 추가하거나 기존 동작을 바꾸는 것인지 구분합니다.
4. 하자와 변경의 구분에는 `PRP-04#s5 참조`의 기준을 적용합니다.
5. 검토 근거와 함께 판정 결과를 네 값 중 하나로 기록합니다.

| 판정값 | 적용 조건 | 후속 경로 |
|---|---|---|
| 범위 내 | 계약 산출물 또는 합의된 요구사항에 요청 결과가 포함됩니다. | 점수 평가 대상으로 넘깁니다. |
| 범위 외 | 제외 항목에 해당하거나 새로운 산출물·연동·동작을 요구합니다. | `PSY-03#s12 참조` |
| 하자 | 합의된 수용 기준을 충족하지 못한 기존 결과의 시정을 요구합니다. | 하자 처리 절차로 넘기며 기능 점수 대상에서 제외합니다. |
| 판정 불가 | 계약 원문, 승인 이력, 수용 기준 또는 요청 사실 중 판정 필수 근거가 없습니다. | 누락 근거를 보완한 뒤 재판정합니다. |

판정 책임자는 접수 시점부터 2영업일 이내에 결과를 확정합니다.  
2영업일 안에 확정할 수 없으면 임의로 범위 내 또는 범위 외를 선택하지 않고 판정 불가로 기록합니다.

판정 불가 건에는 다음 항목을 함께 남깁니다.

- 확인되지 않은 문서 또는 사실
- 자료 제공 책임 부서와 담당자
- 고객 확인이 필요한 질문
- 재판정 예정일
- 근거 확보 전 작업 차단 여부

계약 문서가 누락된 경우 SALES 담당자가 원문과 승인 이력을 확인합니다.  
기술적 수용 기준이 불명확한 경우 CNS 판정 책임자가 영향받는 개발 부서에 사실 확인을 요청합니다.  
계약 해석에 법률 검토가 필요한지는 사안별 확인이 필요하며, 확인 완료 전 판정 불가 상태를 유지합니다.

범위 내 요청의 예상 공수가 크더라도 공수만을 이유로 범위 외로 바꾸지 않습니다.  
대신 계약 유형에 따라 다음 추가 확인을 수행합니다.

| 계약 유형 | 추가 확인 사항 | 확인 결과의 사용 |
|---|---|---|
| 고정가 | 최초 산정 전제, 잔여 예산, 일정 영향, 누락 산정 여부 | 원가·일정 위험을 내부 에스컬레이션하되 범위 판정과 분리합니다. |
| T&M | 잔여 투입 한도, 청구 가능 시간, 고객 승인 조건 | 한도 내 배치 여부를 확인하고 초과 예상 시 승인 경로로 넘깁니다. |

판정 책임자는 결과를 등록한 당일 요청자에게 계약 범위 판정 상태를 알립니다.  
고객에게 전달할 표현과 시점은 `PSY-03#s11 참조`로 적용합니다.  
판정 전에는 코드 수정, 설정 변경, 데이터 가공, 설계 확정 또는 납기 약속을 시작하지 않습니다.  
단, 별도 장애 대응으로 분리된 조치는 기능 요청의 선행 구현으로 간주하지 않습니다.

판정 번복은 다음 사유가 확인된 경우에만 허용합니다.

- 뒤늦게 발견된 계약 부속서 또는 승인 문서가 기존 근거와 충돌합니다.
- 고객과 회사가 사용한 용어의 정의가 수용 기준에서 다르게 확인됩니다.
- 하나의 요청에 하자 시정과 신규 변경이 섞여 있어 분리 판정이 필요합니다.
- 최초 접수 내용과 실제 재현 결과가 달라 요청의 성격이 변경됩니다.
- 정정된 계약 문서 또는 공식 합의가 판정 이후 유효하게 성립합니다.

번복 시 기존 판정값을 삭제하지 않고 변경 전 값, 변경 사유, 근거 문서, 변경자 및 변경 시각을 이력으로 남깁니다.

## 긴급도 × 영향도 점수 모델
<!--meta: sec=s5; dept=CNS|AIAX|BE; level=시니어; ct_band=상; related=s3|s6-->
범위 판정을 통과한 기능 요청은 긴급도와 영향도를 각각 1점부터 5점까지 평가합니다.  
기본 점수는 `긴급도 × 영향도`로 계산하며 최솟값은 1점, 최댓값은 25점입니다.

긴급도는 요청을 처리하지 않을 때 시간 경과에 따라 발생하는 제약을 평가합니다.

| 긴급도 | 판정 기준 |
|---:|---|
| 5 | 핵심 업무가 현재 중단되었고 사용 가능한 회피 수단이 없으며 즉시 대응하지 않으면 운영 손실이 계속됩니다. |
| 4 | 핵심 업무가 심각하게 제한되며 임시 회피 수단은 있으나 2영업일 이상 유지하기 어렵거나 확정된 외부 일정이 임박했습니다. |
| 3 | 업무는 계속할 수 있지만 반복 수작업 또는 제한된 우회 절차가 필요하며 외부 일정 전에 조치 여부를 정해야 합니다. |
| 2 | 특정 상황에서 불편이나 지연이 발생하지만 안정적인 회피 수단이 있고 확정된 외부 일정에 묶이지 않습니다. |
| 1 | 사용 편의 개선, 표현 변경 또는 선택 기능에 해당하며 현재 업무 수행에는 지장이 없습니다. |

외부 일정은 고객이 희망한 날짜만으로 인정하지 않습니다.  
검수일, 계약상 제출일, 이미 공지된 운영 전환일처럼 확인 가능한 근거가 있어야 합니다.

영향도는 영향을 받는 사용자 범위, 업무 단계의 중요도, 데이터 정확성 및 복구 가능성을 함께 평가합니다.

| 영향도 | 판정 기준 |
|---:|---|
| 5 | 전체 또는 다수 사용자의 핵심 업무에 영향을 주며 데이터 정확성 훼손 가능성이 있고 결과를 되돌리기 어렵습니다. |
| 4 | 여러 사용자 또는 복수 조직의 주요 업무 단계에 영향을 주며 잘못된 결과가 후속 업무로 전파될 수 있습니다. |
| 3 | 한 조직 또는 명확한 사용자 집단의 업무 흐름에 영향을 주지만 검증된 절차로 결과를 복구할 수 있습니다. |
| 2 | 소수 사용자의 보조 업무에 한정되며 데이터 정확성에는 영향을 주지 않고 즉시 되돌릴 수 있습니다. |
| 1 | 개인화, 표시 방식 또는 선택적 편의에 국한되며 다른 사용자와 후속 업무에 영향이 없습니다. |

서로 다른 영향도 조건이 동시에 확인되면 증거가 있는 가장 높은 등급을 적용합니다.  
가정만으로 데이터 훼손이나 전체 사용자 영향을 추정한 경우에는 해당 등급을 적용하지 않습니다.

| 기본 점수 | 기본 처리 구간 | 의미 |
|---:|---|---|
| 20~25 | 즉시 처리 | 단기 대응 필요성을 우선 검토합니다. 세부 상한은 `PSY-03#s8 참조`로 적용합니다. |
| 12~19 | 로드맵 우선 | 후보군의 상위 순서로 비교합니다. |
| 6~11 | 로드맵 후순위 | 선행 과제와 가용 역량을 확인한 뒤 배치합니다. |
| 1~5 | 거절 후보 | 유지 가치와 재검토 조건을 확인합니다. |

기본 처리 구간은 최종 약속이 아닙니다.  
추가 가중 요소를 적용한 최종 점수와 계약 경로를 확인한 뒤 판정 구분을 확정하며 세부 경로는 `PSY-03#s7 참조`로 처리합니다.

요청자가 표시한 긴급도는 참고 정보로만 보존합니다.  
담당자는 다음 확인 질문으로 긴급도를 다시 검증합니다.

1. 이 기능이 없어서 현재 중단된 업무는 무엇입니까?
2. 영향을 받기 시작한 시각과 가장 가까운 확정 일정은 언제입니까?
3. 사용할 수 있는 수작업, 대체 화면 또는 기존 절차가 있습니까?
4. 회피 수단을 사용할 수 있는 기간과 추가 소요 시간은 얼마입니까?
5. 처리하지 않을 경우 어떤 데이터나 후속 업무에 오류가 전파됩니까?
6. 영향받는 사용자는 몇 명이며 동일한 상황을 재현한 사용자는 몇 명입니까?
7. 잘못된 결과를 원상 복구할 수 있으며 복구에 어떤 승인이나 작업이 필요합니까?

답변이 없거나 수치가 확인되지 않으면 요청자의 최고 등급 주장을 그대로 반영하지 않습니다.  
담당자는 확인된 사실만으로 등급을 부여하고 미확인 항목을 점수 근거에 표시합니다.  
업무 중단 주장과 실제 재현 결과가 다르면 재현 결과를 우선하되, 재현 환경 차이는 별도 미확인 사항으로 남깁니다.

점수 기록에는 두 축의 값, 산식, 적용 문장, 증빙 위치, 평가자 및 평가 시각을 포함합니다.  
동일한 근본 문제로 묶인 요청은 대표 요청에 점수를 부여하고, 개별 요청별 점수를 합산하지 않습니다.

## 추가 가중 요소
<!--meta: sec=s6; dept=CNS|SALES|AIAX; level=시니어; ct_band=상; related=s5-->
기본 점수에는 고객 분포, 사업 시점, 선행 관계, 재사용성 및 구현 구조를 반영한 가중치를 더하거나 뺍니다.  
가중치는 요청자의 직급, 발언 횟수, 연락 빈도 또는 표현 강도와 무관하게 적용합니다.

| 가중 요소 | 확인 기준 | 조정 폭 |
|---|---|---:|
| 다수 고객 공통 요청 | 서로 다른 여러 사업에서 동일한 문제 코드가 반복되고 각 요청의 근거가 확인됩니다. | +3 |
| 계약 갱신·검수 시점 임박 | 갱신 또는 검수 일정이 확정되어 있고 요청 결과가 해당 판단 항목에 직접 연결됩니다. | +2 |
| 다른 요구사항의 선행 조건 | 미처리 시 이미 승인된 다른 요구사항을 착수하거나 완료할 수 없습니다. | +3 |
| 공통 자산 전환 가능 | 고객 고유 정보와 결합을 제거한 뒤 복수 사업에서 사용할 수 있다는 검토 결과가 있습니다. | +2 |
| 구현 비용이 매우 낮음 | 영향 분석과 테스트를 포함해 담당 개발자 1인이 4시간 이내에 완료할 수 있습니다. | +1 |
| 되돌리기 어려운 구조 변경 | 데이터 구조, 외부 연동 규격 또는 다수 모듈의 공개 인터페이스를 비가역적으로 바꿉니다. | -3 |
| 기술 부채 증가 | 임시 분기, 중복 구현 또는 검증 우회를 추가하며 상환 계획 없이는 유지비가 누적됩니다. | -2 |

공통 자산 전환 가능성의 상세 평가는 `PSY-05 참조`로 수행합니다.  
기술 부채 여부와 상환 조건은 `PSY-06 참조`로 판정합니다.

가중치는 확인된 항목별로 한 번만 적용합니다.  
같은 사실이 두 요소의 근거가 되면 조정 절댓값이 큰 한 항목만 선택합니다.  
양수 조정 합계와 음수 조정 합계는 각각 최대 5점으로 제한합니다.  
최종 점수는 `기본 점수 + 양수 가중치 - 음수 가중치`로 계산하며 1점 미만은 1점, 25점 초과는 25점으로 고정합니다.

각 조정에는 다음 근거를 기록합니다.

- 적용한 가중 요소명과 점수
- 근거가 되는 요청 번호, 계약 일정 또는 요구사항 번호
- 공통 문제 코드와 확인된 사업 수
- 비용 추정 담당자와 산정 시각
- 구조 변경 또는 기술 부채에 대한 개발 부서 의견
- 적용자와 승인 시각

근거를 기록하지 않은 가중 조정은 무효이며 기본 점수로 되돌립니다.  
예상 갱신 가능성, 비공식 검수 일정 또는 담당자의 경험만으로는 가점을 부여하지 않습니다.  
구현 비용이 낮다는 판단은 코딩 시간만으로 계산하지 않고 영향 분석, 테스트 및 배포 준비를 포함합니다.

요청 지지자 중 회사의 주 고객 유형에 해당하는 비중이 30% 미만이면 `고객 유형 재검토`로 표시합니다.  
비중의 분모는 동일한 근본 문제에 대해 지지 의사를 확인한 전체 고객 수이며, 동일 고객의 반복 요청은 한 건으로 계산합니다.  
고객 유형 재검토 표시는 자동 감점이 아니며 CNS와 SALES가 표본 편향, 신규 시장 가능성 및 기존 계약 분포를 다시 확인하게 하는 통제값입니다.  
재검토가 끝나기 전에는 해당 요청을 다수 고객 공통 요청으로 가점하지 않습니다.

특정 고객의 목소리 크기가 점수를 바꾸지 않도록 다음 통제를 적용합니다.

1. 동일 고객의 반복 연락은 지지 고객 수를 늘리지 않습니다.
2. 요청자의 직급이나 고객사 내 영향력은 가중 요소로 등록하지 않습니다.
3. 매출 또는 계약상 효과를 반영하려면 확인 가능한 계약 일정과 직접 연결 근거가 있어야 합니다.
4. 영업 관계상 긴급하다는 설명만으로 갱신·검수 가점을 적용하지 않습니다.
5. 점수를 수동 변경하려면 기존 산식, 변경값, 객관적 근거 및 승인자를 이력에 남깁니다.

가중 적용 후 점수 구간이 바뀌면 이전 구간과 최종 구간을 모두 보존합니다.  
점수 변경은 구현 확정이나 일정 약속을 의미하지 않으며, 최종 처리 경로는 `PSY-03#s7 참조`로 결정합니다.

## 판정 구분과 각 경로
<!--meta: sec=s7; dept=CNS|AIAX|BE|SALES; level=시니어; ct_band=상; related=s4|s5-->
최종 판정은 `즉시 처리`, `로드맵 반영`, `거절`, `유상 변경(CR)` 중 하나로 고정합니다. 판정 책임자는 계약 범위 결과, 최종 점수, 공수 추정치와 고객의 비용 부담 의사를 확인한 후 요청 등록부의 상태를 변경합니다.

| 판정 | 필수 전제 조건 | 경로 책임자 | 판정 후 시한 | 필수 산출물 |
|---|---|---|---|---|
| 즉시 처리 | 범위 내 요청이고 최종 점수가 20점 이상이며 PSY-03#s8의 건별·주별·동시 진행 상한을 모두 충족합니다. | 해당 작업을 수행하는 AIAX 또는 BE 시니어가 책임집니다. | 판정 후 1영업일 이내에 담당자와 검증 일정을 확정합니다. | 실행 작업 카드, 공수 추정치, 검증 방법, 배포 대상 버전을 남깁니다. |
| 로드맵 반영 | 즉시 처리 조건을 충족하지 않지만 고객 영향 또는 전략 정합성에 따라 후속 검토 가치가 확인됩니다. | CNS 시니어가 상태를 부여하고 AIAX 또는 BE 시니어가 기술 검토자를 맡습니다. | 판정 후 3영업일 이내에 Now·Next·Later 중 하나를 표시합니다. | 로드맵 항목, 문제 코드, 채택 근거, 다음 재검토 조건을 남깁니다. |
| 거절 | 요청이 판정 기준을 충족하지 못하거나, 실행 가능한 해결 경로가 없거나, 범위 외이면서 유상 전환 및 내부 투자 근거가 모두 없습니다. | CNS 시니어가 판정하고 고객 담당자가 회신합니다. | 판정 후 2영업일 이내에 회신 초안을 확정합니다. | 거절 이유와 재검토 조건을 기록합니다. 세부 기록은 PSY-03#s10을 따릅니다. |
| 유상 변경(CR) | 범위 외 요청이고 고객이 추가 비용을 부담할 의사를 명시했으며 사전 기술 검토에서 수행 불가 사유가 발견되지 않았습니다. | CNS 시니어가 변경 범위를 소유하고 SALES가 상업 조건 협의를 담당합니다. | 비용 부담 의사 확인 후 2영업일 이내에 변경 검토를 개시합니다. | CR 개시 기록, 범위 초안, 견적 요청, 고객 의사 확인 근거를 남깁니다. |

`범위 내·외`는 PSY-03#s4의 결과를 사용하며, 긴급도와 영향도 및 가중 요소를 판정 단계에서 임의로 다시 채점하지 않습니다. 유상 변경은 범위 외라는 이유만으로 선택하지 않으며, 고객의 비용 부담 의사가 확인되지 않으면 CR 상태를 부여할 수 없습니다.

판정 순서는 다음과 같습니다.

1. 범위 외 요청에 대해 고객의 비용 부담 의사와 기술 검토 가능 여부를 확인합니다.
2. CR 전제가 충족되면 유상 변경으로 판정하고 PSY-03#s12로 이관합니다.
3. 나머지 범위 내 요청 중 20점 이상인 건은 즉시 처리 상한을 확인합니다.
4. 즉시 처리 상한을 충족하지 못한 건은 로드맵 채택 조건을 검토합니다.
5. 앞선 어느 경로에도 해당하지 않는 건은 거절합니다.

한 요청에 두 판정을 동시에 표시하지 않습니다. 요청의 일부만 즉시 처리하고 나머지를 로드맵에서 검토해야 하면 다음과 같이 분할 등록합니다.

- 원 요청 ID 아래에 하위 요청 ID를 각각 생성합니다.
- 각 하위 요청에는 독립된 문제 설명, 범위 판정, 점수, 예상 공수와 최종 판정을 기록합니다.
- 공통 근거는 원 요청에 유지하고 하위 요청에서 해당 근거를 링크합니다.
- 고객 회신에서는 즉시 처리 부분과 미확정 부분을 구분하여 표시합니다.

상태 전이는 전제 조건이 달라졌을 때만 허용합니다.

| 기존 판정 | 변경 가능한 판정 | 전이 조건 |
|---|---|---|
| 즉시 처리 | 로드맵 반영 | 착수 전 상세 추정에서 상한 초과가 확인되거나 선행 의존성이 새로 발견됩니다. |
| 로드맵 반영 | 즉시 처리 | 재평가 점수가 20점 이상이고 즉시 처리 상한에 여유가 생겼습니다. |
| 로드맵 반영 | 유상 변경 | 범위 외 판정이 유지되는 상태에서 고객이 비용 부담 의사를 새로 명시합니다. |
| 유상 변경 | 거절 | 고객이 비용 부담 의사를 철회하거나 기술 검토에서 수행 불가 사유가 확정됩니다. |
| 거절 | 로드맵 반영 | 기존 거절 기준을 뒤집는 신규 고객 근거, 매출 근거 또는 전략 변경이 확인됩니다. |

거절 건을 되돌릴 때는 기존 기록을 삭제하지 않고 변경 근거와 재판정 일자를 추가합니다. 담당자의 교체, 고객의 반복 문의 또는 요청 표현의 강도만으로는 상태를 전이하지 않습니다. 판정 결과의 집계 및 보고 주기는 PSY-03#s15를 참조합니다.

## 즉시 처리 기준과 상한
<!--meta: sec=s8; dept=AIAX|BE; level=시니어; ct_band=중; related=s7-->
즉시 처리는 계획된 수행 업무를 대체하는 별도 작업 통로가 아닙니다. AIAX 또는 BE 시니어는 착수 전에 개발, 검토, 테스트와 배포 준비를 포함한 총공수를 산정하고 다음 상한을 모두 확인합니다.

| 구분 | 상한 | 적용 단위 | 초과 시 처리 |
|---|---:|---|---|
| 1건당 공수 | 8인시 | 하나의 하위 요청 ID 기준입니다. | 착수하지 않고 로드맵 반영 또는 유상 변경 검토로 전환합니다. |
| 주당 누적 공수 | 24인시 | 프로젝트 수행팀의 월요일부터 일요일까지 승인된 즉시 처리 공수 합계입니다. | 남은 요청을 다음 주로 자동 이월하지 않고 다시 판정합니다. |
| 동시 진행 건수 | 2건 | 프로젝트 수행팀에서 `진행 중`인 즉시 처리 요청 기준입니다. | 기존 건이 검증 완료될 때까지 신규 착수를 금지합니다. |

세 상한 중 하나라도 초과하면 즉시 처리 판정은 성립하지 않습니다. 범위 내 요청은 로드맵 경로로, 범위 외 요청은 고객의 비용 부담 의사가 확인된 경우에만 유상 변경 경로로 보냅니다.

공수 산정에는 다음 작업을 포함합니다.

1. 영향 범위 확인과 구현 작업을 포함합니다.
2. 코드 또는 설정 변경에 대한 동료 검토 시간을 포함합니다.
3. 테스트 데이터 준비, 검증 실행과 결과 기록 시간을 포함합니다.
4. 배포 준비와 릴리즈 노트 판단 시간을 포함합니다.
5. 고객 확인이나 외부 승인 대기시간은 인시에 포함하지 않되 일정 의존성으로 별도 기록합니다.

즉시 처리 요청에는 최소한 다음 기록을 남깁니다.

- 요청 ID와 PSY-03#s7의 최종 판정 일자를 기록합니다.
- 실제 변경 내용을 파일, API, 배치, 설정 또는 데이터 항목 단위로 적습니다.
- 정상 경로와 실패·경계 경로의 검증 방법 및 결과를 기록합니다.
- 릴리즈 노트 반영 여부와 제외 사유를 표시합니다. 작성 기준은 PSY-04#s3을 참조합니다.
- 예상 공수와 실제 공수를 각각 기록하여 주당 누적치를 갱신합니다.

변경을 운영 환경에 반영하기 전 최소 검증은 다음 기준을 충족해야 합니다.

| 검증 항목 | 통과 기준 |
|---|---|
| 정상 동작 | 요청에서 요구한 대표 입력 또는 업무 흐름 1건 이상이 기대 결과와 일치합니다. |
| 실패·경계 동작 | 오류 입력, 빈 값, 한계값 또는 연동 실패 중 영향받는 조건 1건 이상을 확인합니다. |
| 회귀 확인 | 변경과 직접 연결된 기존 기능의 대표 경로가 변경 전과 동일하게 동작합니다. |
| 동료 확인 | 구현자가 아닌 AIAX 또는 BE 구성원 1명이 변경 내용과 검증 결과를 확인합니다. |

테스트를 생략하고 즉시 배포하는 예외는 두지 않습니다. 자동화 테스트가 없는 영역은 수동 검증 절차, 입력값, 기대 결과와 실제 결과를 작업 카드에 남깁니다.

상한 소진 현황은 주간 싱크 전에 `사용 인시/24인시`, `진행 건수/2건`, `대기 요청 수` 형식으로 입력합니다. 18인시 이상 사용했거나 동시 진행 2건에 도달하면 상태를 `상한 임박`으로 표시하고 신규 즉시 처리 승인을 중지합니다.

예를 들어 6인시 요청 4건을 승인하면 주당 누적치는 24인시가 됩니다. 이후 들어온 4인시 요청은 건별 상한 안에 있더라도 주당 누적치가 28인시가 되므로 즉시 처리할 수 없습니다. 이를 작은 요청이라는 이유로 추가하면 계획 작업에서 12인시를 초과 사용하게 되는 전형적인 일정 훼손 경로가 됩니다.

## 로드맵 반영 표기와 약속 금지 표현
<!--meta: sec=s9; dept=CNS|SALES; level=시니어; ct_band=상; related=s7|s11-->
로드맵 반영 요청은 `Now`, `Next`, `Later`로 표시합니다. 이 표기는 처리 순서와 검토 위치를 전달하는 상태값이며, 그 자체로 제공 날짜나 계약상 이행 의무를 확정하지 않습니다.

| 구간 | 정의 | 사용할 수 있는 표현 | 사용할 수 없는 표현 |
|---|---|---|---|
| Now | 담당자와 작업 항목이 배정되어 현재 구현 또는 검증 중입니다. | “현재 구현 중이며 검증 결과가 확인되면 안내합니다.”라고 표현합니다. | “이번 주에 완료됩니다.”, “해당 날짜에 반드시 배포합니다.”라고 표현하지 않습니다. |
| Next | Now 작업 이후 우선 검토할 후보이며 착수 여부와 순서는 아직 확정되지 않았습니다. | “다음 검토 대상에 포함되어 있습니다.”라고 표현합니다. | “다음 분기에 제공됩니다.”, “Now가 끝나면 바로 개발합니다.”라고 표현하지 않습니다. |
| Later | 전략 정합성이나 고객 영향에 대한 추가 근거를 기다리며 장기 후보로 보관합니다. | “향후 검토 후보로 유지하며 근거가 추가되면 재평가합니다.”라고 표현합니다. | “추후 반드시 반영합니다.”, “일정만 미정이고 개발은 확정입니다.”라고 표현하지 않습니다. |

공개 로드맵은 이 상태 체계를 고객이 확인할 수 있게 만든 가시적 산출물입니다. 공개본에는 고객 식별 정보, 계약 금액, 내부 점수, 미확정 기술 구조와 다른 고객의 요청 근거를 포함하지 않습니다.

구간은 다음 조건으로 이동합니다.

| 이동 | 필수 조건 | 고객 통보 |
|---|---|---|
| Later → Next | 최신 근거로 재평가한 결과 우선 검토 후보에 포함되고 기술 검토자가 지정됩니다. | 정기 로드맵 안내 시 변경 상태를 알립니다. |
| Next → Now | 담당자, 작업 항목, 검증 방법과 착수 승인이 모두 확정됩니다. | 이동 후 2영업일 이내에 알립니다. |
| Now → Next 또는 Later | 의존성 미충족, 우선순위 변경 또는 기술 위험으로 현재 작업을 계속할 수 없습니다. | 이동 후 2영업일 이내에 사유와 다음 검토 조건을 알립니다. |
| Next → Later | 최신 고객 영향 또는 전략 정합성 근거가 다른 후보보다 낮아졌습니다. | 기존에 Next 상태를 안내한 고객에게 다음 정기 회신에서 알립니다. |
| Later → 보관 종료 | 두 번의 연속된 분기 검토 동안 신규 근거가 없고 재검토 조건도 충족되지 않았습니다. | 고객에게 상태를 개별 안내했던 항목이면 종료 사실을 알립니다. |

Now 상태는 단순한 내부 의향으로 부여하지 않습니다. 담당자가 정해지지 않았거나 작업 카드가 생성되지 않은 요청은 Next에 둡니다. 개발이 끝났더라도 검증이 완료되지 않은 항목은 완료로 표시하지 않습니다.

로드맵 요청에 특정 날짜를 약속할 수 있는 유일한 경로는 서명 또는 이에 준하는 승인 절차가 완료된 변경 계약입니다. 해당 절차는 PSY-03#s12를 참조합니다. 변경 계약이 체결되지 않은 상태에서는 CNS와 SALES 모두 다음 표현을 사용하지 않습니다.

- “요청하신 날짜까지 제공하겠습니다.”
- “다음 달 배포가 확정되었습니다.”
- “해당 분기 내 반영을 보장합니다.”
- “내부 일정만 남았으므로 변동이 없습니다.”
- “로드맵에 등록되었으므로 반드시 개발됩니다.”

고객이 목표 날짜를 제시한 경우에는 이를 `고객 희망일`로 기록하며 `확정 제공일`로 바꾸지 않습니다. 회신에서는 현재 구간, 확정되지 않은 항목과 다음 판정 시점을 구분하며 문안 작성 원칙은 PSY-03#s11을 참조합니다.

로드맵 방치 항목은 분기 전체 검토에서 정리합니다. 두 번의 연속된 분기 검토 동안 상태 이동, 신규 고객 근거, 매출 근거 또는 기술 검토가 없으면 보관 종료 후보로 표시합니다. 담당자는 종료 또는 유지 중 하나를 선택하고, 유지할 경우 다음 재검토에 필요한 구체 조건을 새로 기록합니다.

## 거절 시 필수 기록 두 항목
<!--meta: sec=s10; dept=CNS|AIAX|SALES; level=시니어; ct_band=상; related=s7|s11-->
거절 또는 보류한 요청에는 `거절 이유`와 `재검토 조건`을 반드시 함께 기록합니다.  
둘 중 하나라도 비어 있으면 판정을 완료 상태로 변경할 수 없습니다.  
기록 없이 요청을 종료하면 같은 요구가 다른 담당자나 창구를 통해 반복 접수되므로, 기존 요청 ID와 판단 근거를 검색할 수 있게 유지합니다.

| 사유 코드 | 거절 이유 | 기록할 구체 기준 |
|---|---|---|
| RJ-01 | 계약 범위 외·비용 미부담 | 계약 범위 밖이며 고객이 유상 변경을 선택하지 않았음을 적습니다. |
| RJ-02 | 점수 미달 | 충족하지 못한 점수 기준과 산정 시 확인한 사실을 적습니다. |
| RJ-03 | 소수 요청 | 동일 문제를 지지하는 고객 분포 또는 ICP 비중이 기준에 미달했음을 적습니다. |
| RJ-04 | 구조 충돌 | 현재 아키텍처, 데이터 모델 또는 인터페이스 원칙과 충돌하는 지점을 적습니다. |
| RJ-05 | 대체 수단 존재 | 사용할 수 있는 기존 기능이나 운영 절차와 남는 제약을 적습니다. |
| RJ-06 | 법·보안 제약 | 확인이 필요한 법률·보안 조건과 현재 충족되지 않은 통제 항목을 적습니다. 법률 판단은 사안별 확인이 필요합니다. |
| RJ-07 | 기술 부채 증가 | 중복 구현, 결합도 상승, 테스트 불가 영역 등 예상되는 부채를 적습니다. |

한 요청에 사유가 여러 개이면 주된 사유 하나를 대표 코드로 지정하고 나머지는 보조 코드로 연결합니다.  
“우선순위가 낮습니다”, “지금은 아닙니다”, “내부 사정으로 어렵습니다”만 적는 것은 허용하지 않습니다.  
거절 이유에는 요청자가 충족하지 못한 기준의 이름과 확인 결과를 포함합니다.

재검토 조건은 미래에 확인할 수 있는 사건이나 수치로 작성합니다.  
조건을 충족해도 자동 승인되는 것으로 표현하지 않으며, 재평가가 개시된다는 의미로 한정합니다.

| 미흡한 기록 | 허용되는 재검토 조건 예시 |
|---|---|
| 요청이 더 많아지면 봅니다. | 동일 문제 코드의 독립 고객 요청이 3건 이상 누적되면 다시 평가합니다. |
| 시장성이 생기면 검토합니다. | 요청 지지 고객 중 ICP 비중이 30% 이상으로 확인되면 다시 점수화합니다. |
| 구조가 개선되면 가능합니다. | 공통 권한 모듈이 운영 환경에 배포되고 연동 규격이 확정되면 구조 충돌 여부를 재검토합니다. |
| 예산이 있으면 진행합니다. | 고객이 유상 영향 분석과 변경 견적 수령 의사를 서면으로 확인하면 변경 후보로 전환합니다. |
| 보안 문제가 해결되면 봅니다. | 요구된 접근통제 항목과 데이터 처리 조건이 승인되면 제한 사항을 다시 확인합니다. |

재검토 조건에는 `변경되어야 할 항목`, `판정 기준값`, `확인 자료`, `재검토 책임자`를 기재합니다.  
기한 자체가 조건인 경우에는 해당 기한에 상황이 달라지는 이유도 함께 적습니다.  
근거 없이 특정 날짜만 지정하지 않습니다.

요청자에게는 요청 요약, 판정 상태, 대표 사유, 충족하지 못한 기준 및 재검토 조건을 공개합니다.  
다른 고객의 식별 정보, 내부 원가, 미공개 보안 취약점, 법률 검토 의견 원문은 공개 범위에서 제외합니다.  
공개할 수 없는 근거가 있으면 해당 내용을 삭제하는 대신 “내부 보안 기준 미충족”처럼 적용 기준을 식별할 수 있는 수준으로 기록합니다.  
고객에게 전달할 표현은 PSY-03#s11을 따릅니다.

기존 거절 요청이 다시 접수되면 신규 ID를 발급하되 이전 ID를 연결합니다.  
분류 담당자는 재검토 조건의 변화 여부만 확인하며, 변화가 없으면 기존 판정을 인용해 종결합니다.  
조건이 달라졌다면 과거 거절 기록을 수정하지 않고 새 판정 이력을 추가합니다.

## 고객 회신 문안 원칙
<!--meta: sec=s11; dept=CNS|SALES; level=시니어; ct_band=상; related=s9|s10-->
고객 회신은 요청의 접수 여부만 알리는 문장이 아니라 회사의 판정과 후속 행동을 고정하는 기록입니다.  
SALES 또는 해당 프로젝트의 CNS 수행 책임자가 공식 회신하며, 개발 담당자가 개인 메신저로 일정이나 제공 여부를 직접 확정하지 않습니다.

회신은 다음 순서를 유지합니다.

1. 고객 요청을 회사가 이해한 내용으로 재진술합니다.
2. 현재 판정 결과를 명시합니다.
3. 적용한 기준 이름과 확인 결과를 설명합니다.
4. 다음에 일어날 행동, 담당 주체 및 시점을 적습니다.
5. 고객이 선택할 수 있는 후속 경로를 제시합니다.

재진술에는 기능명이 아니라 해결하려는 문제, 적용 사용자, 기대 결과를 포함합니다.  
고객의 원래 의도와 다를 가능성이 있으면 “다음 내용으로 이해했습니다”라고 표시하고 확인을 요청합니다.  
판정 근거는 내부 감상이나 담당자의 선호가 아니라 계약 범위, 점수, 구조 제약, 재검토 조건 등 식별 가능한 기준으로 작성합니다.

| 금지 문구 | 금지 사유 | 대체 문안 |
|---|---|---|
| 검토해 보겠습니다. | 검토 대상과 회신 시점이 없습니다. | “영향 범위를 확인해 3영업일 이내에 판정 결과를 회신하겠습니다.”라고 씁니다. |
| 곧 반영 예정입니다. | 제공 시점을 확정한 것으로 해석될 수 있습니다. | “현재 로드맵의 `Next` 구간에 있으며 일정 확정 전입니다.”라고 씁니다. |
| 어렵습니다. | 거절 기준과 재검토 가능성을 알 수 없습니다. | “구조 충돌 기준에 해당하며, 공통 권한 모듈이 선행되기 전에는 반영하지 않습니다.”라고 씁니다. |
| 다음 버전에 넣겠습니다. | 승인되지 않은 버전 약속이 됩니다. | “변경 계약 없이는 제공 버전과 일정을 약속하지 않습니다.”라고 씁니다. |
| 내부적으로 우선순위를 조정하겠습니다. | 실제 후속 행동을 확인할 수 없습니다. | “월간 재점수 대상에 포함하며 결과는 해당 검토 종료 후 회신합니다.”라고 씁니다. |
| 최대한 빨리 처리하겠습니다. | 완료 기준과 시간 범위가 없습니다. | “담당자가 다음 영업일까지 영향 분석 착수 여부를 안내합니다.”라고 씁니다. |

공식 창구로 요청이 들어오면 회신 주체는 1영업일 이내에 접수 사실과 판정 예정일을 알립니다.  
즉시 판정할 수 있는 건은 3영업일 이내에 결과를 회신합니다.  
추가 자료가 필요하면 같은 기한 안에 필요한 자료 목록, 제출 주체 및 자료 수령 후 예상 회신일을 안내합니다.  
고객의 자료 제출을 기다리는 기간은 회사의 판정 지연으로 표현하지 않습니다.

다음 사항이 포함된 회신은 발송 전에 수행 책임자의 확인을 받습니다.

- 특정 날짜, 버전 또는 배포 회차를 언급합니다.
- 공수, 비용, 할인 또는 무상 제공 가능성을 언급합니다.
- 기존 산출물의 일정이나 수용 기준 변경을 전제로 합니다.
- 보안, 데이터 처리 또는 법률상 가능 여부를 단정합니다.
- 다른 고객이나 공통 기능의 개발 계획을 근거로 사용합니다.

수행 책임자는 확인 요청을 받은 뒤 1영업일 이내에 승인, 수정 요청 또는 에스컬레이션 중 하나를 남깁니다.  
SALES는 상업 조건을 포함한 문안을 발송하고, CNS는 수행 범위와 후속 행동의 정확성을 확인합니다.  
두 부서의 판단이 다르면 고객에게 중간 결론을 보내지 않고 PSY-03#s16에 따라 처리합니다.

회신에는 내부 점수 계산식 전체를 붙이지 않아도 되지만 적용한 기준명과 미충족 결과는 생략하지 않습니다.  
거절 회신에는 PSY-03#s10의 두 필수 기록을 반영합니다.  
로드맵 상태를 회신할 때 사용할 수 있는 표현은 PSY-03#s9를 따릅니다.  
발송된 회신 원문과 발송 시각은 요청 등록부에 연결합니다.

## 유상 변경 전환 경로
<!--meta: sec=s12; dept=SALES|CNS; level=시니어; ct_band=상; related=s7-->
유상 변경으로 판정된 요청은 구두 동의나 일반 견적 전달만으로 착수하지 않습니다.  
변경 후보 등록, 영향 분석, 견적, 고객 수락, 계약 반영 및 일정 재기준선화가 완료되어야 수행 항목으로 전환합니다.  
변경 조항의 내용은 PRP-04#s10을 따르며, 금액 산정은 PRP-03을 참조합니다.

| 단계 | 책임자 | 표준 소요일 | 완료 증빙 |
|---|---|---:|---|
| 변경 후보 표시 | CNS 수행 책임자 | 판정 후 1영업일 | 요청 ID, 변경 후보 상태, 요청 요약 |
| 영향 분석 요청 | CNS 수행 책임자 | 표시 후 1영업일 | 분석 범위, 답변 기한, 담당 부서 |
| 공수·일정 영향 분석 | AIAX·BE·DATA 중 영향 부서 담당자 | 요청 후 3영업일 | 공수 범위, 선행 조건, 영향받는 산출물 |
| 견적 요청 및 작성 | SALES | 분석 완료 후 2영업일 | 견적안과 상업 조건 검토 기록 |
| 고객 제시 | SALES | 내부 승인 후 1영업일 | 제시 문서와 발송 이력 |
| 계약 반영 | SALES·CNS | 고객 수락 후 진행 | 서명 또는 승인된 변경 문서 |
| 일정 재기준선화 | CNS 수행 책임자 | 계약 반영 후 2영업일 | 변경 일정, 의존성, 기준선 승인 기록 |
| 미수락 종결 | SALES | 거절 확인 후 1영업일 | 미수락 사유와 종결 상태 |

표준 소요일 안에 분석할 수 없는 요청은 담당자가 만료 전에 지연 사유와 새 완료 예정일을 기록합니다.  
고객 검토 기간과 서명 기간은 회사의 표준 소요일에 포함하지 않습니다.  
고객의 조건부 수락은 계약 반영 완료로 간주하지 않습니다.

영향 분석에는 요청 기능 자체의 공수 외에 테스트, 배포, 데이터 변경, 연동 수정 및 기존 산출물 일정 영향을 포함합니다.  
분석 결과가 범위형 추정치이면 상한과 하한의 전제 차이를 적습니다.  
상세 조항 설명이나 가격 계산을 영향 분석 문서에 중복 작성하지 않습니다.

수주 가능성이 확인되지 않은 상태에서 무상 분석이 반복되는 것을 막기 위해 변경 후보 1건당 사전 영향 분석은 최대 4인시로 제한합니다.  
4인시 안에는 구현안 확정이 아니라 견적 가능한 공수 범위와 주요 위험까지만 제시합니다.  
이를 초과하는 검증, 시제품, 데이터 표본 분석 또는 상세 설계가 필요하면 SALES가 고객의 유상 사전 분석 의사를 먼저 확인합니다.  
고객이 이를 수락하지 않으면 제한된 정보로 범위형 견적을 제시하거나 변경 후보를 종결합니다.

무상 흡수 한도가 남아 있더라도 담당자가 임의로 유상 변경을 무상 작업으로 바꿀 수 없습니다.  
무상 전환 승인 권한과 가격 바닥선은 PRP-03을 따릅니다.  
승인된 경우 요청 등록부에 승인자, 승인 사유, 사용 인시, 적용 기간 및 잔여 한도를 기록합니다.  
한도 소진 후 발생한 추가 작업은 별도 변경 후보로 다시 등록합니다.

고객이 변경 계약 없이 수행을 요구하면 SALES는 기존 계약 문서에 해당 결과가 포함되지 않았다는 판정 근거를 제시합니다.  
CNS는 미승인 작업을 일정표나 개발 작업으로 배정하지 않습니다.  
고객이 검수 보류, 대금 지급 보류 또는 기존 일정 준수를 조건으로 요구하면 수행 책임자는 같은 영업일 안에 SALES 부장에게 에스컬레이션합니다.  
계약 해석상 이견이 남으면 사안별 확인이 필요하며, 확인 전에는 제공 일정이나 무상 수행을 약속하지 않습니다.

## 운영 주기
<!--meta: sec=s13; dept=CNS|AIAX|BE; level=주니어|시니어; ct_band=중; related=s5|s7-->
요청 등록부는 주간·월간·분기 단위로 검토합니다. 각 주기는 신규 요청 처리, 우선순위 갱신, 장기 적체 정리라는 서로 다른 목적으로 운영하며 한 회의에서 합치지 않습니다.

| 주기 | 참석 범위 | 필수 입력 | 산출물 | 소요 시간 |
|---|---|---|---|---:|
| 주간 트리아지 | CNS 요청 담당자와 영향받는 AIAX·BE 시니어가 참석합니다. | 직전 회의 이후 접수된 요청, 미분류 요청, 보완 자료와 현재 점수를 사용합니다. | 신규 태그, 문제 코드, 담당자, 1차 판정 및 추가 확인 항목을 확정합니다. | 45분 이내로 운영합니다. |
| 월간 재점수 | CNS 수행 책임자와 해당 요청의 AIAX·BE 시니어가 참석합니다. | 최신 계약 상태, 검수·갱신 시점, 고객 분포, 사업 데이터와 선행 작업 변동을 사용합니다. | 상위 요청의 변경 점수, 변경 사유, 판정 유지·전환 결과를 남깁니다. | 60분 이내로 운영합니다. |
| 분기 전체 리뷰 | CNS 과장 이상 책임자와 AIAX·BE 과장 이상 담당자가 참석합니다. | 전체 요청 등록부, 로드맵 상태, 완료·거절 이력과 장기 체류 목록을 사용합니다. | 다음 분기 검토 대상, Later 정리 결과와 로드맵 동기화 내역을 확정합니다. | 90분 이내로 운영합니다. |

주간 트리아지는 매주 같은 요일에 열고, 참석자는 회의 시작 4업무시간 전까지 본인 담당 요청의 누락 필드를 보완합니다. 의사결정에 필요한 정보가 없으면 임의 점수를 부여하지 않고 보완 책임자와 기한을 기록합니다.

다음 시한은 내부 응답 기준입니다. 계약서에 별도 SLA가 있으면 계약 기준을 우선하며, 법적 의미의 의무 여부는 사안별 확인이 필요합니다.

| 요청 유형 | 접수 확인 | 1차 판정 | 공식 회신 |
|---|---:|---:|---:|
| 일반 기능 요청 | 1영업일 이내에 합니다. | 접수 후 3영업일 이내에 합니다. | 접수 후 5영업일 이내에 합니다. |
| 운영 중단 가능성이 표시된 요청 | 1업무시간 이내에 합니다. | 접수 후 4업무시간 이내에 합니다. | 접수 후 8업무시간 이내에 합니다. |
| 유상 변경 후보 | 1영업일 이내에 합니다. | 접수 후 3영업일 이내에 합니다. | 접수 후 5영업일 이내에 경로 전환 여부를 회신합니다. |
| 필수 정보가 누락된 요청 | 1영업일 이내에 접수와 누락 항목을 알립니다. | 접수 후 2영업일 이내에 보완 필요 판정을 합니다. | 보완 자료 수신 후 3영업일 이내에 합니다. |

고객의 자료 보완을 기다리는 기간은 시한 계산에서 일시 정지합니다. 담당자는 정지 시작 시각, 요청한 자료와 재개 시각을 등록부에 기록합니다.

월간 재점수에서는 다음 사유가 확인될 때 기존 점수를 변경합니다.

- 계약 갱신일이나 검수 예정일이 확정되거나 변경된 경우입니다.
- 동일 문제 코드의 요청 고객 수 또는 최신 사업 데이터가 달라진 경우입니다.
- 선행 기능의 완료·지연으로 구현 가능 시점이 바뀐 경우입니다.
- 회피 수단이 새로 생기거나 기존 회피 수단을 사용할 수 없게 된 경우입니다.
- 고객 영향 범위가 실측 자료로 확대되거나 축소된 경우입니다.

점수를 변경한 담당자는 이전 점수, 변경 점수, 근거 자료 기준일을 함께 남깁니다. 판정 전환은 PSY-03#s5와 PSY-03#s7을 적용합니다.

분기 리뷰에서는 Later 항목을 마지막 갱신일이 오래된 순서로 검토합니다. 두 개 분기 동안 근거 갱신이 없고 담당자·재검토 조건·활성 고객 요청이 모두 없는 항목은 폐기 후보로 표시합니다. 후보 표시 후 5영업일 동안 CNS 수행 책임자의 이의가 없으면 폐기하며, 삭제하지 않고 `폐기` 상태와 사유를 보존합니다.

특정 고객에게 이전에 Later 상태를 공식 회신한 항목은 폐기 후 5영업일 이내에 변경 결과를 통보합니다. 내부 검토용으로만 생성되었거나 고객 회신 이력이 없는 항목은 별도 통보하지 않습니다.

## 재사용 가능성 평가와 공통 자산 연결
<!--meta: sec=s14; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=s6-->
동일한 문제 코드가 여러 사업에서 반복되면 담당 시니어는 프로젝트별 구현을 계속할지 공통 자산 후보로 전환할지 평가합니다. 기능 이름이 같다는 이유만으로 공통화하지 않으며, 입력·출력·운영 조건이 실제로 유사한지 확인합니다.

| 신호 | 평가 기준 | 임계값 | 임계값 미달 시 처리 |
|---|---|---:|---|
| 사업 반복성 | 서로 다른 사업에서 동일 문제 코드가 정식 접수되었는지 확인합니다. | 3개 이상 사업입니다. | 프로젝트별 구현으로 유지합니다. |
| 구현 유사도 | 핵심 처리 흐름, 데이터 입출력과 오류 처리 중 공통 부분의 비율을 산정합니다. | 70% 이상입니다. | 공통 인터페이스를 만들지 않습니다. |
| 유지 비용 | 향후 12개월의 중복 수정·시험 비용과 공통화 후 예상 비용을 비교합니다. | 중복 유지 비용이 공통화 구축비와 공통 유지비의 합보다 커야 합니다. | 기존 구현을 독립적으로 유지합니다. |
| 반복 변경 | 같은 원인의 수정이 각 사업 코드에 별도로 발생했는지 확인합니다. | 최근 6개월 동안 2회 이상입니다. | 변경 이력만 축적하고 다음 평가를 기다립니다. |

공통 자산 후보는 사업 반복성 임계값을 반드시 충족해야 합니다. 나머지 신호 중 구현 유사도와 유지 비용이 모두 기준을 충족할 때 정식 평가를 개시합니다.

평가자는 AIAX·BE·DATA 중 해당 구조를 가장 많이 소유하는 부서의 시니어로 지정합니다. 복수 부서가 영향을 받으면 인터페이스 변경 책임이 가장 큰 부서가 평가를 주관합니다.

| 평가 항목 | 통과 기준 | 탈락 판단 |
|---|---|---|
| 일반화 가능성 | 고객명을 제거해도 문제 정의와 핵심 동작을 설명할 수 있어야 합니다. | 특정 고객의 조직·업무 명칭이 로직 조건으로 남으면 탈락합니다. |
| 설정 흡수 가능성 | 고객별 차이를 설정값, 어댑터 또는 확장 지점으로 분리할 수 있어야 합니다. | 고객이 추가될 때마다 공통 핵심 로직을 분기해야 하면 탈락합니다. |
| 데이터 독립성 | 고객별 데이터 형식 차이를 경계 계층에서 변환할 수 있어야 합니다. | 원본 스키마가 공통 모듈 내부에 직접 결합되면 탈락합니다. |
| 소유자 지정 가능성 | 버전 결정, 결함 대응과 변경 승인 책임을 맡을 시니어 1인을 지정할 수 있어야 합니다. | 담당 부서와 소유자를 정하지 못하면 등록을 중단합니다. |
| 검증 가능성 | 최소 3개 사례를 같은 시험 기준으로 재현할 수 있어야 합니다. | 사례별 성공 조건이 서로 비교 불가능하면 공통화하지 않습니다. |

최소 3개 사업 사례가 모이기 전에는 미래 요구를 예상해 공통 모듈을 만들지 않습니다. 이 기간에는 검증된 구현을 각 프로젝트 저장 영역에 복사하여 사용하고, 고객별 변경은 해당 프로젝트 안에서 분리합니다.

복사된 구현 사이에 차이가 생기면 차이의 원인과 변경 부분만 기록합니다. 세 번째 사례가 확보되었을 때 누적된 차이를 비교하여 공통 핵심과 고객별 설정 경계를 결정합니다.

다음 징후가 있으면 과도한 추상화로 판정합니다.

- 실제 사례보다 확장 지점이나 설정 항목 수가 더 많습니다.
- 하나의 고객 요구를 수용하기 위해 두 단계 이상의 추상 계층을 새로 추가해야 합니다.
- 공통 모듈 변경 때 사용하지 않는 프로젝트까지 회귀시험해야 합니다.
- 고객별 분기가 공통 핵심 로직 전체에 흩어져 있습니다.
- 공통화 후 예상 유지 공수가 독립 구현의 합보다 줄지 않습니다.

과도한 추상화 판정 시 공통 자산 후보 상태를 해제하고 프로젝트별 구현으로 되돌립니다. 이미 연결된 프로젝트가 있으면 즉시 제거하지 않고 영향 분석 후 독립 버전으로 분리합니다.

공통 자산화 제안서의 기재 내용과 제출 경로는 PSY-05#s7을 참조합니다.

## 측정 지표와 보고
<!--meta: sec=s15; dept=CNS|SALES|AIAX; level=시니어; ct_band=중; related=s13-->
CNS는 요청 등록부의 상태 변경 이력을 기준으로 지표를 산출합니다. 수기 보정이 발생하면 원자료 값, 보정 값, 보정 사유와 승인자를 함께 보존합니다.

| 지표 | 산식·집계 기준 | 목표값 | 해석 시 주의사항 |
|---|---|---|---|
| 접수 후 1차 판정까지의 중위 시간 | 유효 접수 시각부터 최초 판정 시각까지의 업무시간을 정렬한 중앙값입니다. | 일반 요청 기준 3영업일 이하입니다. | 평균값만 보면 장기 지연 요청이 가려지므로 중위 시간과 최댓값을 함께 봅니다. |
| 회신 시한 준수율 | 시한 내 공식 회신 건수 ÷ 회신 대상 건수입니다. | 월 95% 이상입니다. | 고객 자료 대기 시간을 제외한 건과 포함한 건을 구분합니다. |
| 판정 분포 | 즉시 처리·로드맵·거절·유상 변경 건수를 전체 판정 건수로 나눕니다. | 네 구분의 합계가 100%여야 하며 전월 대비 15%포인트 이상 변동 시 분석합니다. | 특정 판정의 비율을 높이는 것을 성과로 보지 않습니다. |
| 거절 건 재접수율 | 거절 후 90일 이내 동일 고객·동일 문제 코드로 다시 접수된 건수 ÷ 거절 건수입니다. | 10% 이하입니다. | 재검토 조건이 실제로 충족된 재접수는 별도 표시합니다. |

| Later 구간 적체 건수 | 분기 말 현재 Later 상태이면서 두 개 분기를 초과해 체류한 건수입니다. | 0건입니다. | 단순 총건수보다 체류 기간과 근거 갱신 여부를 우선 확인합니다. |

거절률이 낮다고 해서 트리아지가 양호한 것은 아닙니다. 범위 외 요청을 로드맵에 남기거나 판단을 미룬 경우에도 거절률은 낮아질 수 있으므로 판정 분포, Later 적체와 유상 변경 전환율을 함께 봅니다.

보고는 다음 주기로 수행합니다.

1. CNS 담당자는 매주 트리아지 전에 시한 초과 건, 즉시 처리 공수와 신규 요청 수를 참석자에게 공유합니다.
2. CNS 과장 이상 책임자는 매월 전체 지표와 전월 변동 사유를 CNS·SALES·AIAX 부장에게 보고합니다.
3. 분기 보고에는 판정 분포 추세, 장기 Later 목록, 재접수 원인과 유상 변경 수락 결과를 포함합니다.
4. 프로젝트별 표본이 10건 미만이면 비율만 제시하지 않고 분자와 분모를 함께 표시합니다.

지표가 목표에서 벗어나면 다음 순서로 확인합니다.

1. 등록 시각, 상태 변경 시각, 문제 코드 또는 판정값의 누락과 중복을 먼저 확인합니다.
2. 고객 자료 대기, 휴일과 계약상 별도 시한이 계산에 올바르게 반영되었는지 확인합니다.
3. 특정 프로젝트, 지점, 요청 유형 또는 담당자에게 이상치가 집중되는지 분리합니다.
4. 판정 기준 적용 오류인지 실제 요청 구성 변화인지 원자료 표본으로 확인합니다.
5. 기준 적용 오류이면 담당자와 수정 기한을 지정하고, 실제 변화이면 다음 월간 재점수 입력에 반영합니다.

목표 미달이 2개월 연속 발생하면 CNS 부장은 원인, 조치 담당자, 완료 예정일과 재측정 시점을 월간 보고에 추가합니다.

## 분쟁과 이견 처리
<!--meta: sec=s16; dept=CNS|SALES; level=시니어; ct_band=상; related=s4|s11-->
판정에 이견이 제기되어도 기존 상태를 즉석에서 변경하지 않습니다. 요청 등록부에 `이견 검토 중` 표시를 추가하고, 재심 결과가 확정될 때까지 기존 판정과 작업 통제를 유지합니다.

| 이견 유형 | 1차 처리 | 2차 처리 | 최종 내부 결정권자 | 처리 기한 |
|---|---|---|---|---|
| SALES와 수행 부서 간 범위 이견 | 양측 담당자가 근거 문서를 대조합니다. | 주간 트리아지 회의의 별도 안건으로 상정합니다. | 해당 지점 책임자입니다. | 최초 제기일부터 5영업일 이내입니다. |
| 고객의 판정 이견 | CNS가 판정 근거표와 문서 위치를 제시합니다. | 고객이 제시한 반대 근거를 계약 문서와 다시 대조합니다. | 해당 지점 책임자입니다. | 유효한 재심 접수일부터 5영업일 이내입니다. |
| 고객의 상위 경로 직접 항의 | 접촉한 임직원이 항의 내용을 등록부로 이관합니다. | 통상 재심 절차로 전환합니다. | 해당 지점 책임자입니다. | 접수 사실을 1영업일 이내 회신합니다. |

내부 이견은 다음 순서로 처리합니다.

1. 이견 제기자는 요청 ID, 기존 판정, 반대 결론, 근거 문서 위치 및 원하는 조치를 1영업일 이내 등록합니다.
2. SALES와 CNS 담당자는 등록 후 2영업일 이내에 직접 협의하며, 구두 기억이나 제안 당시의 의도만으로 범위를 해석하지 않습니다.
3. 합의되지 않으면 어느 문구의 해석이 다른지와 각 해석의 비용·일정 영향을 한 페이지 이내로 정리하여 주간 트리아지에 상정합니다.
4. 회의에서도 미결이면 지점 책임자가 제출된 자료를 기준으로 결정하며, 추가 자료가 필요하면 자료명과 제출 기한을 지정합니다.
5. 최초 판정의 범위 기준을 다시 적용해야 하는 경우에는 PSY-03#s4를 참조합니다.

고객 이견에는 계약서, 과업범위, 승인 이력 등 해당 결론에 실제 사용한 문서의 명칭·조항·버전을 근거표로 제시합니다. 고객에게 내부 점수표 전체나 다른 고객의 사례를 제공하지 않습니다.

재심 요청은 다음 항목을 모두 포함해야 유효하게 접수합니다.

- 기존 요청 ID와 이견 대상 판정을 기재합니다.
- 잘못 적용되었다고 보는 기준 또는 새로 확인된 문서를 특정합니다.
- 원하는 정정 결과와 그 이유를 기재합니다.
- 대리 제기인 경우 고객 측 확인 권한 또는 내부 위임 관계를 확인할 수 있어야 합니다.

CNS는 재심 요청을 받은 뒤 2영업일 이내에 요건 충족 여부를 확인합니다. 동일 주장만 반복되고 새로운 근거나 기준 적용 오류가 없으면 재심을 다시 열지 않으며, 직전 결정 ID를 연결하여 종결합니다.

고객이 임원, 지점 책임자 또는 SALES 상위자에게 직접 항의하더라도 접촉자는 제공 여부·금액·일정을 현장에서 확정하지 않습니다. “기존 판정을 재심 절차로 접수하고 근거 확인 후 회신합니다.”라고 안내하며, 공식 회신 형식은 PSY-03#s11을 따릅니다.

재심 결과는 `유지`, `변경`, `일부 변경` 중 하나로 기록합니다. 기록에는 결정자, 결정 시각, 검토 문서, 쟁점별 판단, 후속 조치, 고객 회신 일시 및 최초 판정과 달라진 이유를 포함합니다. 처리 기한을 지키기 어려우면 만료 전에 사유와 새 회신일을 알리며, 연장은 1회 및 최대 3영업일로 제한합니다.

동일 쟁점이 한 분기 내 2회 이상 공식 이견으로 접수되거나 서로 다른 3개 사업에서 반복되면 CNS는 표준화 후보로 등록합니다. 단순 설명 부족은 범위 외 목록의 문구 보완 후보로, 계약 해석 차이는 차기 제안·계약 문안의 수정 후보로 구분합니다. SALES는 적용 대상과 예상 영향을 검토하며, 실제 계약 문안 반영과 법률적 효력은 사안별 확인이 필요합니다.
