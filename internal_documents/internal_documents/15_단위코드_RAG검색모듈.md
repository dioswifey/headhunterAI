# RAG 검색 모듈 단위코드 설명
<!--meta: doc=CODE-RAG-01; doc_type=unit_code; tier=1; topic=CC; disclosure=internal; status=active; related=PRJ-CC-DET-->

## 개요
<!--meta: sec=s1; dept=AIAX; level=주니어; ct_band=중; related=PRJ-CC-DET-->
콜센터 AI 상담 프로젝트에서 쓰이는 RAG 검색 모듈의 핵심 함수는 질의를 임베딩해 벡터DB에서 유사도 상위 문서를 가져오고, 유사도가 기준값 미만이면 빈 결과를 반환합니다.

이 모듈의 책임은 다음 세 단계로 제한됩니다.

- 사용자 질의를 검색 가능한 형태로 정규화합니다.
- 정규화된 질의를 임베딩 벡터로 변환하고 벡터DB에 검색을 요청합니다.
- 검색 결과를 유사도 기준값으로 필터링해 상위 로직이 사용할 수 있는 표준 결과 객체로 반환합니다.

이 모듈은 상담 답변을 직접 생성하지 않으며, 검색 문서를 프롬프트에 삽입하거나 LLM 호출 여부를 결정하지 않습니다. 검색 결과가 없으면 표준화된 빈 결과와 `"검색 결과 없음"` 신호를 반환하는 것으로 역할을 마칩니다.

주요 사용 주체는 응답 생성기, 검색 품질 평가 도구, 운영 점검 스크립트입니다. 상담 화면이나 외부 고객 채널이 이 모듈을 직접 호출하지 않도록 하며, 반드시 상위 애플리케이션 서비스를 통해 접근합니다.

## 핵심 로직
<!--meta: sec=s2; dept=AIAX; level=주니어|시니어; ct_band=상; related=PRJ-CC-DET-->
1. 사용자 질의를 임베딩 모델로 벡터화
2. 벡터DB에서 코사인 유사도 상위 5건 검색
3. 유사도가 기준값(0.6) 미만인 문서는 제외
4. 남은 문서가 0건이면 "검색 결과 없음" 신호를 상위 로직(LLM 호출 여부 결정)에 전달

핵심 로직은 검색 개수와 최종 반환 개수를 구분합니다. 벡터DB에는 상위 5건을 요청하지만, 기준값 필터링 이후 반환 건수는 0건부터 5건까지 달라질 수 있습니다. 따라서 호출자는 항상 5건이 반환된다고 가정해서는 안 됩니다.

처리 순서는 다음과 같습니다.

| 순서 | 처리 | 입력 | 출력 |
|---|---|---|---|
| 1 | 질의 검증 | 원문 문자열 | 검증된 문자열 또는 입력 오류 |
| 2 | 질의 정규화 | 검증된 문자열 | 정규화 문자열 |
| 3 | 임베딩 생성 | 정규화 문자열 | 고정 차원 실수 벡터 |
| 4 | 후보 검색 | 임베딩 벡터 | 상위 5건 후보 |
| 5 | 점수 표준화 | 벡터DB 원시 점수 | 코사인 유사도 기준 점수 |
| 6 | 임계값 필터링 | 후보와 점수 | 유사도 0.6 이상 문서 |
| 7 | 중복 제거 및 정렬 | 필터 통과 문서 | 안정적으로 정렬된 문서 목록 |
| 8 | 결과 조립 | 문서 목록 | 표준 검색 결과 객체 |

필터 비교는 `score >= 0.6`으로 처리합니다. 점수가 정확히 0.6인 문서는 포함합니다. 부동소수점 값을 표시용 문자열로 반올림한 뒤 비교하지 않으며, 벡터DB 어댑터가 반환한 표준화 실수 값을 그대로 비교합니다.

## 주의점
<!--meta: sec=s3; dept=AIAX; level=주니어|시니어; ct_band=상; related=INC-AI-01-->
INC-AI-01 장애 이후, 검색 결과가 비어 있을 때 LLM을 호출하지 않는 처리가 이 모듈 밖(응답 생성기)에 있다는 점에 유의합니다. 이 모듈 자체는 "결과 없음"만 알릴 뿐 답변 생성 여부를 판단하지 않습니다.

다음과 같은 구현은 금지합니다.

- 검색 결과가 없다는 이유로 이 모듈에서 임의의 안내 답변을 생성하는 처리
- 빈 결과일 때 일반 지식 답변을 얻기 위해 LLM을 직접 호출하는 처리
- 기준값 미만 문서를 강제로 한 건 선택해 반환하는 처리
- 검색 실패와 검색 결과 없음을 동일한 상태로 반환하는 처리
- 벡터DB 타임아웃을 빈 결과로 변환해 정상 응답처럼 숨기는 처리
- 운영 중 요청 단위로 임계값을 임의 하향하는 처리

`"검색 결과 없음"`은 정상적인 검색 결과 상태입니다. 반면 임베딩 모델 오류, 벡터DB 연결 오류, 점수 형식 오류는 기술적 실패입니다. 두 경우는 상위 로직의 처리 방식과 운영 경보 기준이 다르므로 반드시 구분해야 합니다.

## 모듈 책임과 비책임 범위
<!--meta: sec=s4; dept=AIAX; level=주니어; ct_band=하; related=CODE-RAG-01-->
검색 모듈이 담당하는 범위는 다음과 같습니다.

- 질의 문자열의 기본 유효성 검증
- 검색 목적의 최소 정규화
- 임베딩 어댑터 호출
- 벡터DB 어댑터 호출
- 코사인 유사도 기준 점수 필터링
- 문서 중복 제거
- 안정적인 결과 정렬
- 표준 결과 객체 생성
- 검색 단계별 지연 시간과 결과 건수 기록
- 검색 실패 유형 분류

검색 모듈이 담당하지 않는 범위는 다음과 같습니다.

- 상담 의도 분류
- 고객 인증 또는 상담 권한 판단
- 답변 문장 생성
- 프롬프트 템플릿 조립
- 대화 이력 요약
- 개인정보 마스킹 정책 결정
- 상담원 화면 렌더링
- LLM 호출 여부 최종 결정
- 답변 근거의 사용자 표시 형식 결정
- 문서 수집, 청킹, 임베딩 색인 생성

책임 범위를 분리하는 이유는 검색 품질 문제와 생성 품질 문제를 독립적으로 진단하기 위해서입니다. 검색 결과가 적절했지만 답변이 잘못된 경우와, 검색 자체가 부적절했던 경우가 하나의 함수에 섞이면 장애 원인과 개선 담당을 구분하기 어렵습니다.

## 논리 구성 요소
<!--meta: sec=s5; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
참조 구현은 다음 논리 구성 요소로 나뉩니다. 실제 파일명은 배포 환경에 따라 달라질 수 있으나 책임 분리는 유지합니다.

| 구성 요소 | 주요 책임 |
|---|---|
| `QueryValidator` | 빈 문자열, 길이, 문자 형식 검증 |
| `QueryNormalizer` | 공백과 제어문자 정리 |
| `EmbeddingPort` | 임베딩 모델 호출 인터페이스 |
| `VectorSearchPort` | 벡터DB 검색 인터페이스 |
| `ScoreNormalizer` | 원시 거리 또는 점수의 코사인 유사도 표준화 |
| `ResultFilter` | 기준값 0.6 적용 |
| `DocumentDeduplicator` | 동일 문서 또는 동일 청크 중복 제거 |
| `ResultAssembler` | 표준 결과 객체 구성 |
| `RetrievalMetrics` | 지연 시간, 후보 수, 필터 통과 수 기록 |
| `RetrievalService` | 전체 검색 흐름 조정 |

`RetrievalService`는 각 구성 요소를 직접 생성하지 않고 생성자 또는 팩토리를 통해 주입받습니다. 이 구조는 실제 임베딩 모델이나 벡터DB 없이 단위 테스트를 수행할 수 있게 합니다.

상위 서비스는 구체적인 벡터DB 클라이언트가 아니라 `VectorSearchPort`에 의존합니다. 저장소 제품이 변경되더라도 검색 서비스의 필터링 규칙과 반환 계약이 바뀌지 않도록 하기 위한 설계입니다.

## 공개 함수 계약
<!--meta: sec=s6; dept=AIAX; level=주니어; ct_band=중; related=CODE-RAG-01-->
대표 공개 함수의 논리적 시그니처는 다음과 같습니다.

    retrieve(
        query: str,
        request_id: str,
        filters: SearchFilters | None = None
    ) -> RetrievalResult

입력 계약은 다음과 같습니다.

| 항목 | 필수 여부 | 설명 |
|---|---:|---|
| `query` | 필수 | 사용자가 입력한 검색 질의 |
| `request_id` | 필수 | 호출 추적용 요청 식별자 |
| `filters` | 선택 | 허용된 문서 범위를 제한하는 검색 필터 |

출력 계약은 다음과 같습니다.

| 필드 | 형식 | 설명 |
|---|---|---|
| `status` | 열거형 | `FOUND`, `NO_RESULT`, `FAILED` 중 하나 |
| `documents` | 목록 | 필터링과 중복 제거가 끝난 검색 문서 |
| `candidate_count` | 정수 | 벡터DB에서 받은 후보 수 |
| `accepted_count` | 정수 | 최종 반환 문서 수 |
| `threshold` | 실수 | 해당 검색에 적용된 기준값, 기본 0.6 |
| `top_k` | 정수 | 벡터DB 요청 건수, 기본 5 |
| `latency_ms` | 정수 | 검색 모듈 전체 처리 시간 |
| `error_code` | 문자열 또는 없음 | 실패 상태의 내부 분류 코드 |
| `no_result_signal` | 불리언 | `"검색 결과 없음"` 상태 여부 |

`status=NO_RESULT`이면 `documents`는 빈 목록이고 `no_result_signal=true`입니다. `status=FAILED`이면 `documents`는 빈 목록일 수 있지만 `no_result_signal`은 거짓이어야 합니다. 장애를 정상적인 무검색 상태로 오해하지 않도록 두 값을 동시에 사용합니다.

## 입력 질의 검증
<!--meta: sec=s7; dept=AIAX; level=주니어; ct_band=하; related=CODE-RAG-01-->
질의 검증은 임베딩 호출 전에 수행합니다. 명백히 잘못된 입력을 외부 모델이나 벡터DB까지 전달하지 않는 것이 목적입니다.

검증 항목은 다음과 같습니다.

- `query`가 문자열인지 확인
- `None` 입력 거부
- 공백 제거 후 빈 문자열인지 확인
- 널 문자와 허용되지 않은 제어문자 포함 여부 확인
- 서비스 설정에서 허용한 최대 길이 초과 여부 확인
- `request_id` 누락 여부 확인
- 필터 값이 허용된 형식인지 확인

빈 문자열은 검색 결과 없음이 아니라 입력 오류입니다. 사용자가 아무 내용도 입력하지 않은 상태와 유효한 질문을 입력했지만 관련 문서를 찾지 못한 상태는 의미가 다릅니다.

검증 실패 시 임베딩 모델과 벡터DB를 호출하지 않습니다. 오류 로그에는 원문 질의를 남기지 않고 입력 길이, 검증 실패 유형, 요청 식별자만 기록합니다.

## 질의 정규화 규칙
<!--meta: sec=s8; dept=AIAX; level=주니어; ct_band=중; related=CODE-RAG-01-->
질의 정규화는 의미를 바꾸지 않는 범위에서만 수행합니다.

기본 정규화 규칙은 다음과 같습니다.

1. 문자열 앞뒤 공백 제거
2. 연속된 일반 공백을 하나로 축소
3. 탭과 줄바꿈을 검색용 공백으로 변환
4. 검색에 불필요한 제어문자 제거
5. 유니코드 표현 차이로 발생하는 비교 불일치 최소화

다음 처리는 기본 정규화에서 수행하지 않습니다.

- 고객명이나 상품명을 임의의 유사어로 치환
- 부정 표현 삭제
- 숫자 또는 날짜 제거
- 조사와 어미의 강제 제거
- 맞춤법 자동 교정 결과의 무조건 적용
- 질의를 LLM으로 재작성
- 상담 의도를 추정해 키워드를 추가

예를 들어 `"해지가 안 되는 이유"`에서 `"안"`을 제거하면 검색 의미가 반대로 바뀔 수 있습니다. 정규화는 형식적 노이즈를 줄이는 단계이지 의미 해석 단계가 아닙니다.

원문 질의와 정규화 질의는 메모리 내에서 구분하되, 운영 로그에는 원문 전체를 기본 기록하지 않습니다. 디버깅이 필요한 경우에도 승인된 진단 절차와 마스킹 정책을 따릅니다.

## 임베딩 어댑터
<!--meta: sec=s9; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
`EmbeddingPort`는 검색 서비스와 임베딩 모델 사이의 경계를 정의합니다.

논리적 인터페이스는 다음과 같습니다.

    embed(text: str) -> EmbeddingVector

`EmbeddingVector`는 최소한 다음 정보를 가집니다.

- `values`: 실수 벡터
- `dimension`: 벡터 차원
- `model_id`: 사용 모델 식별자
- `model_version`: 배포 버전
- `elapsed_ms`: 임베딩 생성 시간

어댑터는 다음 조건을 검사합니다.

- 반환 벡터가 비어 있지 않은지
- 모든 원소가 유한한 실수인지
- `NaN` 또는 무한대가 포함되지 않았는지
- 색인 생성에 사용한 모델과 질의 임베딩 모델이 호환되는지
- 예상 차원과 실제 차원이 일치하는지

차원이 맞지 않는 벡터를 벡터DB에 전달하면 저장소에 따라 검색 실패 또는 무의미한 결과가 발생할 수 있습니다. 따라서 차원 검증은 벡터DB 호출 전에 수행합니다.

임베딩 호출 실패는 `EMBEDDING_ERROR`로 분류합니다. 실패를 0 벡터로 대체하거나 이전 요청의 벡터를 재사용해서는 안 됩니다.

## 벡터DB 검색 어댑터
<!--meta: sec=s10; dept=AIAX; level=시니어; ct_band=상; related=CODE-RAG-01-->
`VectorSearchPort`는 특정 벡터DB 제품의 검색 문법과 반환 형식을 검색 서비스에서 분리합니다.

논리적 인터페이스는 다음과 같습니다.

    search(
        vector: EmbeddingVector,
        top_k: int,
        filters: SearchFilters | None
    ) -> list[RawVectorHit]

기본 `top_k`는 5입니다. 어댑터는 다음 책임을 가집니다.

- 검색 벡터 전달
- 상위 5건 요청
- 허용된 메타데이터 필터 적용
- 저장소 원시 응답을 `RawVectorHit`로 변환
- 저장소별 거리 또는 점수 의미를 명시
- 타임아웃과 연결 오류를 표준 예외로 변환
- 결과에 필요한 최소 메타데이터가 있는지 검사

`RawVectorHit`에는 다음 항목이 포함됩니다.

| 필드 | 설명 |
|---|---|
| `chunk_id` | 검색 단위 청크 식별자 |
| `document_id` | 원문 문서 식별자 |
| `raw_score` | 저장소가 반환한 원시 점수 또는 거리 |
| `score_type` | `COSINE_SIMILARITY`, `COSINE_DISTANCE` 등 점수 의미 |
| `content` | 검색된 청크 내용 |
| `metadata` | 문서 분류, 버전 등 허용된 메타데이터 |

벡터DB 어댑터는 답변 생성에 필요한 프롬프트 문자열을 만들지 않습니다. 검색 결과를 일관된 내부 구조로 변환하는 데까지만 관여합니다.

## 유사도 점수 표준화
<!--meta: sec=s11; dept=AIAX; level=시니어; ct_band=상; related=CODE-RAG-01-->
벡터 저장소마다 높은 값이 더 유사한 경우와 낮은 거리가 더 유사한 경우가 다를 수 있습니다. 따라서 기준값 0.6을 적용하기 전에 점수 의미를 코사인 유사도 기준으로 통일합니다.

점수 처리 원칙은 다음과 같습니다.

- 코사인 유사도가 직접 반환되면 해당 값을 사용합니다.
- 코사인 거리가 반환되면 저장소 정의를 확인한 뒤 유사도로 변환합니다.
- 점수 유형이 누락되거나 알 수 없으면 검색을 실패 처리합니다.
- 점수 방향을 추측하지 않습니다.
- 표시용 반올림 값을 필터 판단에 사용하지 않습니다.
- `NaN`, 무한대, 비정상 범위 값은 오류로 분류합니다.

점수 변환은 어댑터별로 흩어 두지 않고 검증 가능한 단일 함수 또는 명시적인 전략 객체로 관리합니다.

    normalize_score(raw_score, score_type) -> cosine_similarity

기준값 비교는 다음과 같은 의미를 가집니다.

| 표준화 점수 | 처리 |
|---:|---|
| 0.600000 이상 | 결과 후보에 포함 |
| 0.6 미만 | 제외 |
| `NaN` | 오류 |
| 무한대 | 오류 |
| 점수 없음 | 오류 |

부동소수점 비교를 위해 임의의 큰 허용 오차를 추가하지 않습니다. 경계값 테스트에서는 0.599999, 0.600000, 0.600001을 별도로 검증합니다.

## 임계값 필터 정책
<!--meta: sec=s12; dept=AIAX; level=주니어|시니어; ct_band=중; related=INC-AI-01-->
기본 유사도 기준값은 0.6입니다. 이 값 미만인 문서는 검색 결과에서 제외합니다.

필터 함수의 논리적 형태는 다음과 같습니다.

    accepted = [
        hit for hit in normalized_hits
        if hit.score >= 0.6
    ]

임계값은 운영 설정으로 주입할 수 있으나, 호출자가 임의의 요청 파라미터로 변경할 수 없도록 합니다. 요청자가 기준값을 자유롭게 낮출 수 있으면 관련성이 낮은 문서가 답변 근거에 포함될 수 있습니다.

임계값 변경 시 다음 절차를 따릅니다.

1. 변경 목적과 예상 영향을 기록합니다.
2. 오프라인 검색 평가를 수행합니다.
3. 경계값 부근 질의를 별도로 점검합니다.
4. 결과 없음 비율과 오검색 비율의 변화를 비교합니다.
5. 검토 승인 후 설정을 변경합니다.
6. 변경 전후 버전을 추적할 수 있게 기록합니다.

검색 결과가 자주 비어 있다는 이유만으로 기준값을 낮추지 않습니다. 빈 결과 증가는 색인 누락, 질의 분포 변화, 임베딩 모델 불일치, 문서 버전 문제일 수도 있습니다.

## 문서 중복 제거
<!--meta: sec=s13; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
벡터DB 상위 5건에 같은 문서의 유사한 청크가 여러 개 포함될 수 있습니다. 중복 제거는 답변 생성기에 지나치게 반복된 근거가 전달되는 것을 줄이기 위한 방어 처리입니다.

중복 판정의 우선순위는 다음과 같습니다.

1. `chunk_id`가 동일하면 완전 중복으로 판단
2. `document_id`와 청크 위치가 동일하면 중복으로 판단
3. 동일 버전 문서의 내용 해시가 같으면 중복으로 판단
4. 식별자가 불완전하면 자동 병합하지 않고 메타데이터 오류로 기록

동일 문서의 서로 다른 청크는 무조건 제거하지 않습니다. 서로 다른 항목을 설명하는 청크일 수 있기 때문입니다. 다만 같은 `chunk_id`가 반복되면 가장 높은 점수 한 건만 유지합니다.

중복 제거 후 부족한 수를 채우기 위해 벡터DB를 추가 호출하지 않습니다. 현재 계약은 상위 5건 후보를 검색하고 그 안에서 필터링하는 방식입니다. 추가 후보 탐색이 필요하면 별도의 설계 변경으로 다룹니다.

## 결과 정렬과 동점 처리
<!--meta: sec=s14; dept=AIAX; level=시니어; ct_band=상; related=CODE-RAG-01-->
최종 결과는 기본적으로 유사도 점수 내림차순으로 정렬합니다. 동일 점수에서 결과 순서가 매번 달라지면 테스트 재현성과 답변 근거 추적이 어려워질 수 있으므로 안정적인 보조 정렬 기준을 적용합니다.

정렬 우선순위는 다음과 같습니다.

1. 표준화 코사인 유사도 내림차순
2. 문서 버전의 유효성 우선
3. `document_id` 오름차순
4. `chunk_id` 오름차순

정렬 과정에서 점수를 다시 계산하지 않습니다. 점수 표시 시 소수점 자릿수를 줄일 수 있지만, 내부 정렬은 원래 실수 값을 사용합니다.

동일 청크가 서로 다른 점수로 중복 반환되면 높은 점수를 유지합니다. 점수가 같고 메타데이터가 충돌하면 조용히 한 건을 선택하지 않고 데이터 정합성 경고를 기록합니다.

## 검색 필터와 문서 범위
<!--meta: sec=s15; dept=AIAX; level=시니어; ct_band=상; related=CODE-RAG-01-->
`SearchFilters`는 검색 대상 문서 범위를 제한하는 내부 객체입니다. 필터 값은 허용 목록에 기반해 생성하며, 사용자 입력 문자열을 그대로 벡터DB 쿼리 문법에 연결하지 않습니다.

지원 가능한 논리 필터의 예시는 다음과 같습니다.

- 활성 문서 여부
- 문서 버전
- 지식 분류
- 적용 채널
- 유효 기간
- 접근 가능한 문서 범위

필터 처리 원칙은 다음과 같습니다.

- 상위 서비스가 검증된 필터 객체를 전달합니다.
- 검색 모듈은 필터 구조와 값 형식을 재검증합니다.
- 허용되지 않은 필터 키는 거부합니다.
- 필터 적용 실패를 필터 없는 검색으로 대체하지 않습니다.
- 비활성 또는 만료된 문서가 결과에 섞이지 않도록 합니다.
- 필터가 지나치게 제한적이어도 임의로 완화하지 않습니다.

필터 때문에 결과가 0건이 된 경우도 정상적인 `NO_RESULT`일 수 있습니다. 다만 운영 분석을 위해 후보 검색 전 필터 조건과 최종 결과 건수를 구분해 계측합니다.

## 표준 검색 결과 객체
<!--meta: sec=s16; dept=AIAX; level=주니어; ct_band=중; related=CODE-RAG-01-->
최종 문서 항목은 다음 구조를 가집니다.

| 필드 | 설명 |
|---|---|
| `document_id` | 원문 식별자 |
| `chunk_id` | 검색 청크 식별자 |
| `content` | 답변 생성기에 전달할 검색 내용 |
| `score` | 표준화 코사인 유사도 |
| `rank` | 필터링과 중복 제거 후 순위 |
| `source_version` | 검색 문서 버전 |
| `metadata` | 허용된 부가정보 |

`rank`는 1부터 시작하며, 필터링 이후 최종 순서를 기준으로 다시 부여합니다. 벡터DB가 반환한 원래 순위와 다를 수 있습니다.

결과 객체의 불변 조건은 다음과 같습니다.

- `accepted_count == len(documents)`
- `accepted_count <= candidate_count`
- `accepted_count <= 5`
- 모든 반환 문서의 `score >= 0.6`
- `status=FOUND`이면 `accepted_count >= 1`
- `status=NO_RESULT`이면 `accepted_count == 0`
- `status=NO_RESULT`이면 `no_result_signal=true`
- `status=FAILED`이면 `error_code`가 존재

상위 서비스는 이 객체의 `status`를 먼저 확인한 뒤 문서 목록을 사용해야 합니다.

## 결과 없음 처리
<!--meta: sec=s17; dept=AIAX; level=주니어|시니어; ct_band=상; related=INC-AI-01-->
`NO_RESULT`는 다음 상황에서 반환됩니다.

- 벡터DB 후보가 0건인 경우
- 후보는 있으나 모든 점수가 0.6 미만인 경우
- 후보가 모두 정상적인 중복 제거 과정에서 제거되어 최종 결과가 없는 경우
- 유효한 필터 조건 아래 관련 문서가 없는 경우

결과 없음 반환 예시는 다음과 같습니다.

    status = NO_RESULT
    documents = []
    candidate_count = 5
    accepted_count = 0
    threshold = 0.6
    top_k = 5
    no_result_signal = true
    error_code = None

다음 상황은 `NO_RESULT`로 반환하지 않습니다.

- 임베딩 모델 타임아웃
- 벡터DB 연결 실패
- 벡터 차원 불일치
- 점수 유형 해석 실패
- 필수 메타데이터 누락으로 결과를 신뢰할 수 없는 경우
- 내부 직렬화 오류

결과 없음과 시스템 실패를 구분하지 않으면 상위 응답 생성기가 장애 상황에서 잘못된 폴백을 수행할 수 있습니다.

## 예외 분류와 오류 코드
<!--meta: sec=s18; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
검색 모듈은 하위 라이브러리의 원시 예외를 그대로 외부에 노출하지 않고 내부 표준 오류로 변환합니다.

| 오류 코드 | 의미 | 재시도 가능성 |
|---|---|---|
| `INVALID_QUERY` | 질의 형식이 잘못됨 | 낮음 |
| `INVALID_FILTER` | 허용되지 않은 필터 | 낮음 |
| `EMBEDDING_TIMEOUT` | 임베딩 호출 시간 초과 | 조건부 |
| `EMBEDDING_ERROR` | 임베딩 생성 실패 | 조건부 |
| `VECTOR_DIMENSION_MISMATCH` | 벡터 차원 불일치 | 낮음 |
| `VECTOR_DB_TIMEOUT` | 벡터DB 검색 시간 초과 | 조건부 |
| `VECTOR_DB_UNAVAILABLE` | 벡터DB 연결 불가 | 조건부 |
| `INVALID_SCORE` | 점수 값 또는 점수 유형 오류 | 낮음 |
| `INVALID_DOCUMENT_METADATA` | 필수 메타데이터 오류 | 낮음 |
| `RETRIEVAL_INTERNAL_ERROR` | 분류되지 않은 내부 오류 | 조건부 |

재시도 가능성은 오류 코드만으로 결정하지 않습니다. 상위 서비스의 재시도 정책, 요청 시간 제한, 장애 확산 가능성을 함께 고려합니다.

예외 메시지에는 인증정보, 연결 문자열, 원문 질의, 고객 식별정보를 포함하지 않습니다. 상세 스택 추적은 제한된 내부 로그에만 남깁니다.

## 타임아웃과 재시도 경계
<!--meta: sec=s19; dept=AIAX|BACKEND; level=시니어; ct_band=상; related=CODE-RAG-01-->
검색 모듈은 임베딩 모델 호출과 벡터DB 호출 각각에 독립적인 타임아웃을 적용할 수 있어야 합니다. 전체 요청 제한 시간만 두면 어느 단계에서 지연됐는지 구분하기 어렵습니다.

재시도 원칙은 다음과 같습니다.

- 입력 검증 오류는 재시도하지 않습니다.
- 벡터 차원 불일치는 재시도하지 않습니다.
- 잘못된 점수 형식은 재시도하지 않습니다.
- 일시적인 네트워크 오류는 제한적으로 재시도할 수 있습니다.
- 동일 요청의 무제한 재시도를 금지합니다.
- 재시도 전에 남은 전체 처리 시간을 확인합니다.
- 재시도마다 새 임베딩을 생성해야 하는지 오류 단계에 따라 구분합니다.

벡터DB 검색만 실패했다면 이미 생성한 임베딩 벡터를 동일 요청 범위에서 재사용할 수 있습니다. 반면 다른 요청의 임베딩을 공유하거나 전역 임시값으로 보관해서는 안 됩니다.

재시도 횟수와 대기 방식은 운영 설정으로 관리하되, 재시도 후 최종 실패를 빈 결과로 바꾸지 않습니다.

## 동시성 및 상태 관리
<!--meta: sec=s20; dept=AIAX|BACKEND; level=시니어; ct_band=상; related=CODE-RAG-01-->
검색 서비스는 요청 간 상태를 공유하지 않는 것을 기본 원칙으로 합니다.

공유해서는 안 되는 값은 다음과 같습니다.

- 현재 사용자의 원문 질의
- 직전 요청의 임베딩 벡터
- 직전 검색 결과
- 요청별 필터
- 요청별 오류 상태
- 요청별 지연 시간 측정값

설정과 읽기 전용 클라이언트 연결 풀은 공유할 수 있지만, 요청 데이터는 지역 변수 또는 요청 범위 객체에 보관합니다.

동시성 결함의 대표 예시는 다음과 같습니다.

- 전역 변수에 마지막 임베딩을 저장해 다른 요청이 재사용
- 결과 목록을 기본 인자나 싱글턴 객체에 누적
- 요청별 필터를 공유 객체에서 변경
- 비동기 호출 완료 순서에 따라 결과 순위가 바뀜
- 취소된 요청의 콜백이 다음 요청 상태를 덮어씀

비동기 구현에서는 임베딩 호출과 벡터DB 호출의 선후 관계를 지켜야 합니다. 벡터DB 검색은 해당 요청의 임베딩이 정상 완료된 후에만 수행합니다.

## 관측성 및 로그 규칙
<!--meta: sec=s21; dept=AIAX|DATA; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
운영 로그는 검색 품질과 시스템 오류를 구분할 수 있어야 합니다.

기본 구조화 로그 항목은 다음과 같습니다.

- `request_id`
- `module`
- `status`
- `error_code`
- `candidate_count`
- `accepted_count`
- `threshold`
- `top_k`
- `embedding_latency_ms`
- `vector_search_latency_ms`
- `total_latency_ms`
- `embedding_model_version`
- `index_version`
- `filter_applied`
- `lowest_accepted_score`
- `highest_candidate_score`

기본 로그에 기록하지 않는 항목은 다음과 같습니다.

- 사용자 질의 원문
- 검색된 청크 전문
- 고객 식별번호
- 인증 토큰
- 벡터DB 연결정보
- 임베딩 벡터 전체 값

`NO_RESULT`는 오류 로그가 아니라 검색 상태 로그로 기록합니다. 다만 짧은 시간에 결과 없음 비율이 급격히 증가하면 품질 이상 신호가 될 수 있으므로 집계 지표로 감시합니다.

오류 로그는 동일 장애가 대량 발생할 때 로그 폭증을 일으키지 않도록 집계와 샘플링을 고려합니다. 단, 오류 코드별 총 발생 건수는 손실 없이 계측해야 합니다.

## 운영 지표
<!--meta: sec=s22; dept=AIAX|DATA; level=시니어; ct_band=상; related=CODE-RAG-01-->
검색 모듈 운영 시 다음 지표를 구분해 봅니다.

| 지표 | 정의 | 해석 시 주의점 |
|---|---|---|
| 검색 요청 수 | 모듈 호출 총수 | 트래픽 변화와 함께 해석 |
| 검색 성공률 | `FOUND` 비율 | 높다고 항상 품질이 좋은 것은 아님 |
| 결과 없음 비율 | `NO_RESULT` 비율 | 지식 공백 또는 엄격한 기준값 가능 |
| 검색 실패율 | `FAILED` 비율 | 시스템 안정성 지표 |
| 평균 반환 문서 수 | `accepted_count` 평균 | 중복과 임계값 영향을 받음 |
| 임계값 탈락률 | 후보 중 0.6 미만 비율 | 질의·색인 적합성 확인 |
| 검색 지연 시간 | 전체 검색 소요 시간 | 임베딩과 DB 구간 분리 필요 |
| 경계 점수 비율 | 0.6 부근 후보 비율 | 임계값 변경 영향 분석 |
| 중복 제거율 | 후보 중 중복 제거 비율 | 청킹 또는 색인 중복 점검 |
| 점수 오류 건수 | 비정상 점수 발생 건수 | 어댑터 호환성 확인 |

`FOUND` 비율만 높이기 위해 임계값을 낮추는 것은 적절하지 않습니다. 관련성이 낮은 문서를 반환해 답변 근거 품질을 떨어뜨릴 수 있기 때문입니다.

검색 지표는 답변 정확도와 동일하지 않습니다. 검색 결과가 적절해도 응답 생성기가 잘못 사용할 수 있고, 검색 결과 자체가 부적절할 수도 있습니다. 모듈 지표는 검색 단계의 상태를 설명하는 데 사용합니다.

## 단위 테스트 기본 전략
<!--meta: sec=s23; dept=AIAX; level=주니어; ct_band=중; related=CODE-RAG-01-->
단위 테스트에서는 실제 임베딩 모델과 벡터DB를 호출하지 않고 가짜 객체 또는 스텁을 사용합니다.

기본 테스트 구조는 다음과 같습니다.

- 입력 질의와 예상 임베딩을 고정
- 벡터DB 후보와 점수를 고정
- 필터 기준값 0.6을 적용
- 반환 상태와 문서 목록 검증
- 하위 의존성 호출 횟수 검증
- 오류 시 다음 단계가 호출되지 않았는지 검증

필수 정상 테스트 항목은 다음과 같습니다.

1. 상위 5건이 모두 0.6 이상이면 5건 반환
2. 일부만 0.6 이상이면 통과한 문서만 반환
3. 정확히 0.6인 문서는 포함
4. 후보가 5건 미만이어도 정상 처리
5. 후보가 0건이면 `NO_RESULT`
6. 중복 청크가 있으면 높은 점수 한 건만 유지
7. 결과가 점수 내림차순으로 정렬
8. 동점이면 보조 정렬 기준 적용
9. 반환 `rank`가 1부터 연속 부여
10. `accepted_count`와 목록 길이가 일치

테스트는 구현 세부사항보다 공개 계약과 불변 조건을 우선 검증합니다.

## 경계값 및 실패 테스트
<!--meta: sec=s24; dept=AIAX; level=주니어|시니어; ct_band=상; related=CODE-RAG-01-->
경계값 테스트는 다음 점수를 최소 조합으로 포함합니다.

| 테스트 점수 | 예상 결과 |
|---:|---|
| 0.599999 | 제외 |
| 0.600000 | 포함 |
| 0.600001 | 포함 |

실패 테스트 항목은 다음과 같습니다.

- 빈 문자열 입력 시 임베딩 미호출
- 공백만 있는 입력 시 벡터DB 미호출
- 임베딩 모델 타임아웃 시 `FAILED`
- 벡터 차원 불일치 시 벡터DB 미호출
- 벡터DB 타임아웃 시 `FAILED`
- 원시 점수 `NaN` 입력 시 `INVALID_SCORE`
- 점수 유형 누락 시 `INVALID_SCORE`
- 필수 `chunk_id` 누락 시 메타데이터 오류
- 허용되지 않은 필터 입력 시 검색 미실행
- 벡터DB 오류가 `NO_RESULT`로 변환되지 않는지 검증
- 검색 결과 없음일 때 이 모듈이 LLM을 호출하지 않는지 검증

다음 불변 조건을 속성 기반 테스트로 검증할 수 있습니다.

- 반환 문서 수는 항상 5 이하
- 모든 반환 점수는 0.6 이상
- 반환 점수는 내림차순
- 같은 `chunk_id`가 두 번 나타나지 않음
- 실패 상태와 결과 없음 신호가 동시에 참이 아님

## 테스트 더블 설계
<!--meta: sec=s25; dept=AIAX; level=시니어; ct_band=중; related=CODE-RAG-01-->
테스트 더블은 역할에 따라 구분합니다.

- 스텁 임베더: 고정 질의에 고정 벡터 반환
- 실패 임베더: 지정된 예외 발생
- 스텁 벡터 검색기: 정해진 후보 목록 반환
- 지연 검색기: 타임아웃 검증용 지연 발생
- 호출 기록 스파이: 호출 횟수와 전달 인자 기록
- 비정상 점수 검색기: `NaN` 또는 점수 유형 누락 반환

호출 기록 스파이를 사용해 다음을 검증합니다.

- 정규화 질의가 임베더에 전달됐는지
- `top_k=5`가 검색기에 전달됐는지
- 검증 실패 시 임베더가 호출되지 않았는지
- 임베딩 실패 시 벡터 검색기가 호출되지 않았는지
- 허용된 필터만 전달됐는지

실제 외부 시스템을 사용하는 테스트는 단위 테스트가 아니라 통합 테스트로 분리합니다. 단위 테스트가 네트워크 상태에 따라 간헐적으로 실패하지 않도록 합니다.

## 통합 검증 항목
<!--meta: sec=s26; dept=AIAX|BACKEND; level=시니어; ct_band=상; related=CODE-RAG-01-->
통합 환경에서는 어댑터와 실제 색인 간 계약을 검증합니다.

주요 검증 항목은 다음과 같습니다.

- 임베딩 차원과 색인 차원 일치
- 질의 임베딩 모델과 문서 색인 모델의 호환성
- 벡터DB 원시 점수 의미 확인
- 코사인 거리와 유사도 변환 정확성
- 메타데이터 필터 문법과 결과 일치
- `top_k=5` 요청이 실제로 5건 이하 후보를 반환하는지
- 비활성 문서 필터 적용 여부
- 문서 버전 메타데이터 존재 여부
- 타임아웃 예외가 표준 오류로 변환되는지
- 한글 질의의 인코딩 손상 여부
- 같은 입력에서 결과 정렬이 재현 가능한지

통합 테스트 데이터는 운영 상담 원문을 그대로 복사하지 않습니다. 합성 질의와 검증용 문서를 사용하며, 실제 데이터 사용이 필요한 경우 별도 승인과 마스킹 절차를 적용합니다.

## 성능 점검 기준
<!--meta: sec=s27; dept=AIAX|BACKEND; level=시니어; ct_band=상; related=CODE-RAG-01-->
검색 지연은 한 개 숫자로만 보지 않고 다음 구간으로 분해합니다.

1. 입력 검증 및 정규화 시간
2. 임베딩 생성 시간
3. 벡터DB 검색 시간
4. 점수 표준화 시간
5. 필터링 및 중복 제거 시간
6. 결과 객체 조립 시간

성능 점검 시 평균뿐 아니라 상위 지연 구간도 확인합니다. 평균이 안정적이어도 일부 요청에서 임베딩 또는 벡터DB 호출이 크게 지연될 수 있습니다.

성능 최적화 시 지켜야 할 원칙은 다음과 같습니다.

- 정확성 검증 없이 임계값 비교를 생략하지 않음
- 결과 메타데이터 검증을 무조건 제거하지 않음
- 요청 간 임베딩 벡터를 부정확하게 재사용하지 않음
- 원문 질의를 캐시 키에 그대로 노출하지 않음
- 캐시 도입 시 문서 색인 버전과 모델 버전을 키에 반영
- 속도를 위해 실패를 빈 결과로 변환하지 않음

상위 5건 검색은 현재 핵심 계약입니다. 성능 개선을 이유로 임의로 3건으로 줄이거나 품질 개선을 이유로 임의로 더 많은 결과를 반환하면 안 됩니다.

## 보안 및 데이터 최소화
<!--meta: sec=s28; dept=AIAX|BACKEND; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
검색 모듈은 질의와 검색 문서가 민감한 내용을 포함할 수 있다는 전제 아래 최소한의 데이터만 처리하고 기록합니다.

보안 원칙은 다음과 같습니다.

- 사용자 입력을 벡터DB 필터 문법으로 직접 연결하지 않음
- 인증 토큰과 연결 문자열을 코드에 하드코딩하지 않음
- 질의 원문을 일반 로그에 남기지 않음
- 임베딩 벡터 전체를 로그에 남기지 않음
- 검색 문서 전문을 오류 메시지에 포함하지 않음
- 허용된 문서 범위 필터를 우회하지 않음
- 오류 발생 시 내부 저장소 구조를 외부 응답에 노출하지 않음
- 요청 식별자를 이용해 추적하되 고객 식별정보를 대체 식별자로 사용하지 않음

디버깅 목적이라도 운영 질의와 검색 결과를 개발자 개인 환경으로 복사하지 않습니다. 재현이 필요하면 동일 구조의 합성 데이터로 우선 재현합니다.

## 설정 항목과 변경 관리
<!--meta: sec=s29; dept=AIAX; level=시니어; ct_band=상; related=CODE-RAG-01-->
주요 설정 항목은 다음과 같습니다.

| 설정 | 기본값 또는 계약 | 변경 영향 |
|---|---|---|
| `retrieval.top_k` | 5 | 후보 범위와 지연 변화 |
| `retrieval.similarity_threshold` | 0.6 | 결과 없음과 오검색 비율 변화 |
| `retrieval.score_metric` | 코사인 유사도 기준 | 점수 해석 변경 |
| `retrieval.embedding_model` | 배포 설정 참조 | 색인 호환성 영향 |
| `retrieval.index_version` | 배포 설정 참조 | 검색 대상 문서 변경 |
| `retrieval.timeout` | 환경 설정 참조 | 실패율과 지연 영향 |
| `retrieval.filter_policy` | 허용 목록 기반 | 검색 범위 영향 |

`top_k=5`와 기준값 `0.6`은 코드 여기저기에 중복 하드코딩하지 않습니다. 설정 객체에서 읽되, 시작 시 유효성 검증을 수행합니다.

설정 검증 항목은 다음과 같습니다.

- `top_k`가 양의 정수인지
- 현재 계약에서 `top_k`가 5인지
- 기준값이 유효한 실수인지
- 점수 방식이 지원되는 유형인지
- 임베딩 모델 버전과 색인 버전이 호환되는지
- 타임아웃이 0 이하가 아닌지

설정 변경 후에는 애플리케이션 버전, 설정 버전, 임베딩 모델 버전, 색인 버전을 함께 추적할 수 있어야 합니다.

## 코드 리뷰 체크리스트
<!--meta: sec=s30; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
검색 모듈 변경 리뷰 시 다음 항목을 확인합니다.

- [ ] 사용자 질의를 임베딩하기 전에 검증하는가
- [ ] 벡터DB에 상위 5건을 요청하는가
- [ ] 코사인 유사도 기준값 0.6을 적용하는가
- [ ] 점수 0.6을 포함하는가
- [ ] 점수 유형과 방향을 명시적으로 처리하는가
- [ ] 결과 없음과 기술적 실패를 구분하는가
- [ ] 결과 없음일 때 이 모듈이 LLM을 호출하지 않는가
- [ ] 빈 결과를 강제로 저점수 문서로 채우지 않는가
- [ ] 중복 문서 처리 기준이 결정적인가
- [ ] 정렬 순서가 재현 가능한가
- [ ] 원문 질의나 문서 전문을 로그에 남기지 않는가
- [ ] 하위 시스템 오류를 표준 오류 코드로 변환하는가
- [ ] 단위 테스트에 0.6 경계값이 포함되는가
- [ ] 임베딩 차원 불일치 테스트가 있는가
- [ ] 벡터DB 실패를 `NO_RESULT`로 변환하지 않는가
- [ ] 설정 변경이 코드와 테스트에 일관되게 반영되는가

리뷰어는 단순히 테스트 통과 여부만 확인하지 않고 모듈 책임이 응답 생성 영역으로 확장되지 않았는지 확인해야 합니다.

## 유지보수 시 금지되는 변경
<!--meta: sec=s31; dept=AIAX; level=주니어|시니어; ct_band=상; related=INC-AI-01-->
다음 변경은 별도 설계 검토 없이 적용하지 않습니다.

- 결과가 없으면 가장 높은 저점수 문서를 반환하는 변경
- 기준값 0.6을 코드 내부에서 조용히 낮추는 변경
- 벡터DB 오류를 빈 목록으로 치환하는 변경
- 결과 없음 상태에서 LLM을 직접 호출하는 변경
- 상위 5건 계약을 임의로 변경하는 변경
- 점수 유형 확인 없이 원시 값을 유사도로 간주하는 변경
- 서로 다른 임베딩 모델의 벡터를 호환된다고 가정하는 변경
- 비활성 문서 필터를 실패 시 제거하는 변경
- 테스트 편의를 위해 오류 검증을 삭제하는 변경
- 원문 질의 전체를 일반 로그에 추가하는 변경
- 요청 간 결과나 임베딩을 전역 변수로 공유하는 변경

특히 `"어떤 답이라도 보여주는 것이 낫다"`는 판단은 검색 모듈의 기술적 결정이 아닙니다. 관련 문서가 없을 때의 사용자 안내와 후속 흐름은 상위 응답 정책에서 결정합니다.

## 장애 진단 순서
<!--meta: sec=s32; dept=AIAX|BACKEND; level=시니어; ct_band=상; related=CODE-RAG-01-->
검색 품질 또는 검색 실패 신고가 접수되면 다음 순서로 확인합니다.

1. 요청 식별자를 확보합니다.
2. `FOUND`, `NO_RESULT`, `FAILED` 중 어떤 상태였는지 확인합니다.
3. 임베딩 모델 버전과 색인 버전을 확인합니다.
4. 후보 수와 필터 통과 수를 확인합니다.
5. 최고 후보 점수가 0.6 이상이었는지 확인합니다.
6. 필터가 적용됐는지 확인합니다.
7. 점수 유형과 표준화 과정에 오류가 없었는지 확인합니다.
8. 중복 제거로 결과가 사라졌는지 확인합니다.
9. 임베딩 및 벡터 검색 지연 시간을 분리해 확인합니다.
10. 같은 합성 질의로 재현 가능한지 확인합니다.

상태별 우선 점검은 다음과 같습니다.

| 상태 | 우선 확인 항목 |
|---|---|
| `NO_RESULT` | 색인 존재, 점수 분포, 필터 범위, 모델 호환성 |
| `FAILED` | 오류 코드, 타임아웃, 연결 상태, 차원 불일치 |
| `FOUND`이나 부적절한 결과 | 점수 정렬, 문서 버전, 중복, 색인 품질 |
| 결과 순서가 매번 다름 | 동점 보조 정렬, 비동기 결과 병합 |
| 간헐적 타임아웃 | 임베딩과 벡터DB 구간별 지연, 재시도 중첩 |

운영 중 원인을 확인하기 위해 기준값을 임시로 낮추거나 필터를 제거한 결과를 실제 사용자에게 반환해서는 안 됩니다. 진단은 격리된 환경에서 수행합니다.

## 용어 정리
<!--meta: sec=s33; dept=AIAX; level=주니어; ct_band=하; related=CODE-RAG-01-->
| 용어 | 설명 |
|---|---|
| RAG | 검색한 문서를 생성 모델의 근거로 활용하는 방식 |
| 질의 | 사용자가 검색을 위해 입력한 문장 |
| 임베딩 | 문장 의미를 수치 벡터로 표현한 값 |
| 벡터DB | 임베딩 간 유사도를 기반으로 문서를 찾는 저장소 |
| 코사인 유사도 | 두 벡터 방향의 유사성을 나타내는 점수 |
| `top_k` | 벡터DB에서 우선 가져올 후보 개수 |
| 임계값 | 결과로 인정할 최소 유사도 점수 |
| 청크 | 검색을 위해 문서를 나눈 단위 |
| 후보 문서 | 벡터DB가 반환한 필터링 전 결과 |
| 최종 문서 | 기준값과 중복 제거를 통과한 결과 |
| 결과 없음 | 정상 검색을 수행했지만 반환할 문서가 없는 상태 |
| 검색 실패 | 임베딩, 벡터DB, 점수 처리 등 기술적 오류 상태 |
| 어댑터 | 외부 시스템의 형식을 내부 표준 형식으로 바꾸는 구성 요소 |
| 불변 조건 | 처리 과정과 관계없이 항상 지켜져야 하는 규칙 |

## 구현 요약
<!--meta: sec=s34; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-RAG-01-->
이 모듈의 구현 원칙은 다음 문장으로 요약할 수 있습니다.

- 질의를 검증하고 의미를 훼손하지 않는 범위에서 정규화합니다.
- 질의를 임베딩 모델로 벡터화합니다.
- 벡터DB에서 코사인 유사도 기준 상위 5건을 검색합니다.
- 표준화된 유사도가 0.6 미만인 문서를 제외합니다.
- 중복을 제거하고 결정적인 순서로 정렬합니다.
- 남은 문서가 있으면 `FOUND`와 문서 목록을 반환합니다.
- 남은 문서가 없으면 `"검색 결과 없음"` 신호인 `NO_RESULT`를 반환합니다.
- 기술적 실패는 `FAILED`로 분리합니다.
- 검색 결과가 없더라도 이 모듈은 LLM 호출 여부를 판단하지 않습니다.
- INC-AI-01 이후의 핵심 안전 원칙인 결과 없음과 생성 제어의 책임 분리를 유지합니다.
