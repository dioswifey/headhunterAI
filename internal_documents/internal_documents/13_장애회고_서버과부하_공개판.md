# INC-SV-01 배치 서버 과부하로 대시보드 지연 — 요약
<!--meta: doc=INC-SV-PUB; doc_type=incident; tier=2; topic=FC; disclosure=abstract; status=resolved-->

## 개요
<!--meta: sec=s1; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-FC-PUB-->
수요예측 배치 작업이 특정 시점에 서버 자원을 과도하게 사용해, 새벽 대시보드 갱신이 늦어진 사례가 있었습니다. 발주 업무 시작 전에는 정상 복구되었습니다.

이번 장애에서 고객이 확인하는 대시보드 화면 자체는 접근 가능했으나, 일부 지표의 기준 시각이 평소보다 늦게 갱신되었습니다. 헤드헌터랩은 이를 단순한 처리 지연이 아니라 업무 의사결정에 영향을 줄 수 있는 운영 장애로 분류하고 원인 분석, 복구 확인, 재발 방지 조치를 수행했습니다.

본 문서는 공개 가능한 범위에서 장애의 현상, 대응 원칙, 개선 방향을 설명한 요약본입니다. 고객사 식별 정보, 서버 구성값, 세부 임계치, 접근 경로 및 내부 운영 계정과 관련된 정보는 포함하지 않습니다.

## 영향 범위
<!--meta: sec=s2; dept=BE|DATA|CONSULT; level=주니어|시니어; ct_band=하; related=PRJ-FC-PUB-->
장애 영향은 수요예측 결과를 표시하는 새벽 대시보드 갱신 구간에 한정되었습니다.

- 일부 대시보드 지표의 최신 데이터 반영이 지연되었습니다.
- 발주 업무 시작 전에는 최신 결과가 정상 반영되었습니다.
- 원천 데이터가 삭제되거나 임의로 변경된 정황은 없었습니다.
- 복구 후 데이터분석팀이 주요 집계값과 예측 결과의 정합성을 재확인했습니다.
- 장애 대응 중 사용자에게 잘못된 임시 예측값을 제공하지 않았습니다.
- 지연된 결과를 정상 결과로 오인하지 않도록 데이터 기준 시각을 함께 확인했습니다.

이 사례에서 “정상 복구”는 화면이 열리는 것만을 의미하지 않습니다. 배치 완료, 결과 적재, 대시보드 반영, 핵심 지표 검증까지 마친 상태를 정상 복구로 판단했습니다.

## 장애 분류 기준
<!--meta: sec=s3; dept=BE|DATA; level=주니어; ct_band=하; related=INC-SV-01-->
헤드헌터랩은 배치 장애를 다음과 같이 구분합니다.

| 분류 | 의미 | 대표 현상 |
|---|---|---|
| 실행 실패 | 작업이 완료되지 못함 | 프로세스 종료, 예외 발생 |
| 실행 지연 | 작업은 진행되지만 목표 시간 안에 끝나지 못함 | 처리량 저하, 대기열 증가 |
| 결과 지연 | 계산은 끝났으나 사용자 화면 반영이 늦음 | 적재 또는 갱신 대기 |
| 결과 이상 | 작업은 완료됐으나 값의 신뢰성이 낮음 | 누락, 중복, 비정상 범위 |
| 자원 경합 | 여러 작업이 같은 자원을 동시에 과다 사용함 | CPU·메모리·입출력 포화 |

INC-SV-01은 수요예측 배치가 특정 시점에 서버 자원을 과도하게 사용했고, 그 결과 새벽 대시보드 갱신이 지연된 사례입니다. 장애 대응에서는 실행 상태와 결과 신뢰성을 별도로 확인했습니다.

## 주요 징후
<!--meta: sec=s4; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
운영 담당자는 단일 경보만으로 장애를 확정하지 않고 여러 징후를 함께 확인했습니다.

- 평소보다 긴 배치 실행 시간
- 동시에 실행 중인 작업 수 증가
- 처리 대기 작업의 누적
- 서버 자원 사용률의 지속적인 상승
- 결과 테이블의 최신 기준 시각 정체
- 대시보드 갱신 완료 신호의 지연
- 일부 재시도 작업의 반복 실행
- 작업별 처리량 편차 확대

특히 서버 자원 사용률이 일시적으로 높아지는 것은 정상일 수 있으므로, 높은 사용률의 지속 시간과 업무 마감 시각까지 남은 시간을 함께 판단했습니다.

## 탐지 방식
<!--meta: sec=s5; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
장애는 배치 실행 상태와 대시보드 최신성 지표를 함께 점검하는 과정에서 확인되었습니다. 운영 관점에서는 “서버가 살아 있는가”보다 “업무 결과가 약속된 시간 안에 제공되는가”가 더 중요합니다.

탐지 체계는 다음 신호를 결합합니다.

1. 배치 작업 시작·종료 상태
2. 작업별 예상 종료 시각 이탈 여부
3. 실행 노드의 자원 포화 추세
4. 결과 데이터의 최신 기준 시각
5. 대시보드 반영 완료 여부
6. 재시도 횟수와 대기열 증가 속도
7. 발주 업무 시작 전 잔여 복구 시간

이와 같은 다중 신호 방식은 서버 장애가 없어도 발생할 수 있는 데이터 최신성 저하를 조기에 찾는 데 목적이 있습니다.

## 공개 타임라인
<!--meta: sec=s6; dept=BE|DATA|CONSULT; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
보안과 고객사 정보 보호를 위해 실제 시각 대신 탐지 시점을 기준으로 한 상대 순서를 사용합니다.

| 상대 시점 | 조치 |
|---|---|
| T-이전 | 정기 수요예측 배치 작업 시작 |
| T | 배치 실행 지연 및 서버 자원 사용 증가 확인 |
| T+초기 | 백엔드팀과 데이터분석팀이 영향 범위 공동 점검 |
| T+대응 | 비필수 작업의 실행 순서를 조정하고 핵심 작업을 우선 처리 |
| T+검증 | 결과 적재 상태와 대시보드 기준 시각 확인 |
| T+복구 | 새벽 대시보드 갱신 정상화 |
| 업무 시작 전 | 발주 업무에 필요한 결과와 주요 집계값 검증 완료 |
| 사후 | 원인 분석, 개선 항목 등록 및 운영 기준 보완 |

복구 속도를 높이기 위해 원인 분석과 서비스 정상화 작업을 분리했습니다. 초기에는 고객 업무에 필요한 핵심 경로를 우선 복구하고, 세부 원인과 장기 개선은 복구 이후 별도 검토했습니다.

## 직접 원인
<!--meta: sec=s7; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-01-->
직접 원인은 특정 시점에 수요예측 배치 작업의 자원 사용이 집중된 것입니다. 여러 처리 단계가 동일한 시간대에 겹치면서 서버가 감당해야 하는 계산량과 데이터 입출력이 증가했고, 후속 작업의 대기 시간이 길어졌습니다.

배치 시스템은 개별 작업이 정상적으로 실행되더라도 동시 실행되는 작업의 합이 서버 용량을 넘으면 전체 처리 시간이 급격히 늘어날 수 있습니다. 따라서 개별 작업 성공 여부만 감시해서는 이번과 같은 지연을 충분히 예방할 수 없습니다.

본 공개판에서는 내부 인프라 구조, 실행 노드 수, 세부 자원 한도, 작업별 쿼리 및 스케줄 설정값을 제공하지 않습니다.

## 기여 요인
<!--meta: sec=s8; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-01-->
직접 원인 외에도 다음 운영 조건이 장애 영향을 키우는 기여 요인으로 확인되었습니다.

- 작업별 평균 실행 시간은 관리했지만 동시 실행 시의 총부하는 충분히 반영하지 못함
- 데이터량 증가에 따라 작업 시간이 늘어나는 추세를 운영 용량 계획에 즉시 반영하지 못함
- 핵심 작업과 비핵심 작업이 동일한 시간대에 자원을 경쟁함
- 작업 실패 경보에 비해 작업 지연 경보가 상대적으로 늦게 동작함
- 서버 지표와 업무 지표가 분리되어 초기 영향 판단에 추가 확인이 필요했음
- 재시도 정책이 일시적 오류 복구에는 유효했지만 자원 포화 상황에서는 추가 부하가 될 가능성이 있었음

각 요인은 특정 개인의 실수보다 시스템과 운영 절차의 보완 대상으로 다뤘습니다.

## 복구 대응
<!--meta: sec=s9; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
초기 대응의 목표는 발주 업무 시작 전 최신 예측 결과를 안전하게 제공하는 것이었습니다.

대응팀은 다음 순서로 복구를 진행했습니다.

1. 현재 실행 중인 작업과 대기 작업을 구분했습니다.
2. 고객 업무와 직접 관련된 핵심 작업을 식별했습니다.
3. 비필수 작업이 핵심 작업과 자원을 경쟁하지 않도록 실행 순서를 조정했습니다.
4. 중복 실행 가능성이 있는 작업을 확인했습니다.
5. 핵심 배치 완료 후 결과 적재 상태를 점검했습니다.
6. 대시보드의 데이터 기준 시각이 최신 상태로 변경됐는지 확인했습니다.
7. 데이터분석팀이 주요 수요예측 결과와 집계값을 검증했습니다.
8. 발주 업무 시작 전 정상 복구 여부를 최종 확인했습니다.

복구 과정에서는 처리 속도를 높이기 위해 검증 절차를 생략하지 않았습니다. 빠르게 생성된 결과라도 정합성 확인이 끝나지 않으면 정상 결과로 배포하지 않는 원칙을 적용했습니다.

## 데이터 무결성 검증
<!--meta: sec=s10; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
배치 지연은 데이터 손실이나 중복 처리로 이어질 가능성이 있으므로 복구 후 별도 검증을 수행했습니다.

검증 항목은 다음과 같습니다.

- 입력 데이터의 대상 기간이 올바른지
- 필수 데이터가 누락되지 않았는지
- 동일한 입력이 중복 반영되지 않았는지
- 예측 결과 건수가 기대 범위 안에 있는지
- 결과 생성 시각과 대시보드 기준 시각이 일치하는지
- 핵심 품목 및 구간의 값이 비정상 범위를 벗어나지 않았는지
- 재실행된 작업이 기존 정상 결과를 잘못 덮어쓰지 않았는지
- 이전 기준일 데이터가 최신 결과로 표시되지 않았는지

검증 결과는 작업 성공 로그와 별개로 관리합니다. 작업이 기술적으로 성공했다는 사실만으로 결과 데이터가 업무에 사용할 수 있다고 판단하지 않습니다.

## 부서별 역할
<!--meta: sec=s11; dept=BE|DATA|CONSULT; level=주니어|시니어; ct_band=하; related=INC-SV-01-->
장애 대응은 백엔드팀과 데이터분석팀이 공동으로 수행했습니다.

| 부서 | 주요 역할 |
|---|---|
| 백엔드팀 | 서버 자원 상태 확인, 배치 실행 흐름 점검, 작업 우선순위 조정, 복구 상태 확인 |
| 데이터분석팀 | 입력·출력 데이터 검증, 예측 결과 정합성 확인, 업무 영향 판단 지원 |
| 컨설팅팀 | 고객 업무 일정과 영향 범위 확인, 공개 가능한 진행 상황 정리 |
| 영업팀 | 필요한 경우 고객 커뮤니케이션 창구 지원 |
| AI/AX개발팀 | 모델 실행 단계가 포함된 경우 기술 검토 및 개선 의견 제공 |

장애 지휘 역할과 기술 분석 역할을 구분해, 여러 담당자가 동일한 작업을 중복 수행하지 않도록 했습니다.

## 재발 방지
<!--meta: sec=s12; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-FC-PUB-->
배치 작업을 여러 서버로 분산하고, 작업량이 몰리는 시점을 미리 감지해 자원을 조정하도록 개선했습니다.

재발 방지 조치는 단순한 서버 증설에 한정하지 않았습니다. 작업 실행 방식, 탐지 기준, 검증 절차를 함께 개선했습니다.

- 핵심 배치와 비핵심 배치의 실행 시간 분리
- 작업별 동시 실행 수 제한
- 처리량 증가 추세를 반영한 사전 용량 점검
- 실행 시간이 예상 범위를 벗어날 때 조기 알림
- 작업 대기열 증가 속도에 대한 경보 추가
- 자원 포화 시 신규 작업 투입을 늦추는 보호 절차 적용
- 핵심 작업에 대한 우선 처리 정책 수립
- 장애 복구 후 데이터 무결성 확인 절차 표준화
- 대시보드 최신성 지표를 운영 모니터링에 포함
- 재시도 작업이 과도하게 누적되지 않도록 상한과 대기 간격 조정

## 작업 분산 원칙
<!--meta: sec=s13; dept=BE; level=시니어; ct_band=상; related=INC-SV-01-->
여러 서버로 작업을 분산할 때는 단순히 작업 개수를 균등하게 나누는 방식만으로 충분하지 않습니다. 작업마다 필요한 CPU, 메모리, 데이터 입출력량, 예상 실행 시간이 다르기 때문입니다.

개선된 분산 원칙은 다음과 같습니다.

1. 작업의 예상 자원 사용량을 기준으로 실행 위치를 결정합니다.
2. 대용량 작업이 같은 서버에 동시에 배치되지 않도록 합니다.
3. 핵심 결과 생성 작업은 비핵심 분석 작업보다 높은 우선순위를 갖습니다.
4. 특정 서버의 자원 여유가 부족하면 신규 작업을 다른 서버로 전환하거나 대기시킵니다.
5. 작업 실패 시 동일 서버에서 즉시 반복 실행하지 않도록 합니다.
6. 처리 중인 작업을 무리하게 이동시키기보다 다음 작업의 배치를 조정합니다.
7. 분산 후에도 결과 적재 순서와 의존 관계가 유지되는지 확인합니다.

분산의 목표는 모든 서버의 사용률을 같게 만드는 것이 아니라, 업무 마감 시각 안에 핵심 결과를 안정적으로 완성하는 것입니다.

## 과부하 보호 장치
<!--meta: sec=s14; dept=BE; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
과부하가 감지되면 시스템은 다음 단계로 보호 조치를 적용합니다.

- 신규 비핵심 작업의 시작 지연
- 동시에 실행할 수 있는 작업 수 축소
- 대용량 작업의 실행 순서 재조정
- 반복 재시도 작업의 대기 시간 확대
- 핵심 배치용 자원 여유 확보
- 운영 담당자에게 단계별 경보 전달
- 업무 마감 시각 이탈 가능성에 대한 별도 알림

보호 장치는 서버 사용률이 높다는 이유만으로 모든 작업을 중단하지 않습니다. 현재 처리량, 대기열, 남은 작업량, 업무 마감 시각을 함께 고려해 점진적으로 적용합니다.

## 모니터링 개선
<!--meta: sec=s15; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
기존의 서버 중심 모니터링을 업무 결과 중심으로 확장했습니다.

| 관측 영역 | 확인 지표 |
|---|---|
| 서버 상태 | CPU, 메모리, 저장장치 입출력, 네트워크 사용 추세 |
| 작업 상태 | 실행 중·대기·성공·실패·재시도 작업 수 |
| 처리 성능 | 단위 시간당 처리량, 예상 잔여 시간 |
| 데이터 상태 | 입력 도착 여부, 결과 적재 완료 여부 |
| 화면 상태 | 대시보드 기준 시각, 최신 결과 반영 여부 |
| 업무 상태 | 발주 업무 시작 전 완료 가능성 |

특정 자원 지표 하나가 임계치를 넘는 것보다 여러 지표가 동시에 악화되는 상황을 더 높은 위험으로 판단합니다.

## 경보 운영 기준
<!--meta: sec=s16; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-01-->
경보는 정보성, 주의, 대응 필요 단계로 나눠 운영합니다.

- **정보성:** 일시적인 사용량 증가가 있으나 처리량과 예상 종료 시각이 정상인 상태
- **주의:** 실행 시간이 평소 범위를 벗어나거나 대기열이 지속적으로 증가하는 상태
- **대응 필요:** 업무 마감 시각 이탈 가능성이 높거나 결과 최신성이 보장되지 않는 상태

경보 수준은 단순 임계치뿐 아니라 증가 속도와 지속 시간을 반영합니다. 순간적인 자원 급증에는 불필요한 호출을 줄이고, 완만하지만 지속되는 처리 지연에는 더 일찍 대응하도록 설계했습니다.

경보 수신자는 알림 확인 후 다음 사항을 기록합니다.

1. 최초 확인 시각
2. 영향받는 작업 범위
3. 업무 마감 시각까지 남은 시간
4. 즉시 조치 여부
5. 협업이 필요한 부서
6. 복구 확인 기준

## 운영 지표
<!--meta: sec=s17; dept=BE|DATA|CONSULT; level=시니어; ct_band=상; related=INC-SV-01-->
재발 방지 효과는 단순히 장애 건수만으로 평가하지 않습니다. 다음 운영 지표를 함께 관리합니다.

- 배치 완료 시각 준수율
- 예상 실행 시간 대비 실제 실행 시간 편차
- 핵심 작업의 대기 시간
- 비핵심 작업이 핵심 작업에 미치는 자원 경합 정도
- 작업 재시도 비율
- 결과 적재 후 대시보드 반영까지 걸리는 시간
- 데이터 최신성 경보 발생 건수
- 장애 탐지부터 영향 판단까지 걸리는 시간
- 복구 후 검증 완료까지 걸리는 시간
- 동일 원인 경보의 반복 발생 여부

지표는 장애 직후에만 확인하지 않고 정기 운영 점검에서 추세로 검토합니다. 처리량 증가 속도가 자원 확장 속도보다 빠른 경우에는 장애가 발생하기 전에 용량 보강 또는 스케줄 조정을 검토합니다.

## 복구 완료 기준
<!--meta: sec=s18; dept=BE|DATA; level=주니어; ct_band=하; related=INC-SV-01-->
다음 조건을 모두 충족해야 복구 완료로 판단합니다.

- 핵심 수요예측 배치가 정상 종료됨
- 결과 데이터가 지정된 저장 영역에 반영됨
- 대시보드의 데이터 기준 시각이 최신 상태임
- 필수 집계값에 누락과 중복이 없음
- 주요 예측 결과가 검증 범위 안에 있음
- 동일 작업이 불필요하게 재실행되고 있지 않음
- 서버 자원 사용이 안정 구간으로 돌아옴
- 발주 업무 시작 전에 결과 사용이 가능함

일부 작업만 성공했거나 화면만 정상적으로 열리는 상태는 복구 완료로 보지 않습니다.

## 잘된 점
<!--meta: sec=s19; dept=BE|DATA|CONSULT; level=주니어|시니어; ct_band=하; related=INC-SV-01-->
이번 대응에서 유지할 운영 방식은 다음과 같습니다.

- 백엔드팀과 데이터분석팀이 기술 상태와 데이터 상태를 병렬로 확인했습니다.
- 발주 업무 시작 시각을 기준으로 복구 우선순위를 정했습니다.
- 핵심 작업과 비핵심 작업을 구분해 대응했습니다.
- 결과 생성 후 데이터 정합성 검증을 별도로 수행했습니다.
- 원인 분석이 끝날 때까지 복구를 미루지 않았습니다.
- 발주 업무 시작 전 정상 복구를 완료했습니다.
- 개인 책임 추궁보다 시스템 개선 항목 도출에 집중했습니다.

이러한 방식은 유사한 배치 지연 장애에서도 공통 대응 원칙으로 활용합니다.

## 보완할 점
<!--meta: sec=s20; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
사후 검토에서 다음 개선 필요 사항을 확인했습니다.

- 개별 작업 성능뿐 아니라 동시 실행 조합에 대한 사전 시험이 필요했습니다.
- 데이터량 증가와 실행 시간 증가 사이의 관계를 더 일찍 파악할 필요가 있었습니다.
- 기술 지표와 업무 마감 지표를 한 화면에서 비교할 수 있어야 했습니다.
- 지연 경보가 장애 확정 이후가 아니라 위험 증가 단계에서 동작해야 했습니다.
- 재시도 정책이 과부하 상황에서 추가 부하를 만들지 않도록 조건을 세분화할 필요가 있었습니다.
- 복구 담당자와 검증 담당자의 역할을 더 명확히 구분할 필요가 있었습니다.
- 운영 절차서에 작업 중단, 지연, 우선순위 변경의 판단 기준을 보강할 필요가 있었습니다.

각 항목은 담당 부서와 확인 기준을 지정해 후속 조치 대상으로 관리했습니다.

## 운영자 대응 체크리스트
<!--meta: sec=s21; dept=BE|DATA; level=주니어; ct_band=하; related=INC-SV-01-->
유사한 경보를 받은 운영자는 다음 순서로 대응합니다.

### 최초 확인

- 경보가 단일 작업인지 전체 배치 흐름인지 확인합니다.
- 현재 실행 중인 작업과 대기 작업을 구분합니다.
- 대시보드의 데이터 기준 시각을 확인합니다.
- 업무 마감 시각까지 남은 시간을 기록합니다.
- 최근 배포나 스케줄 변경 여부를 확인합니다.

### 영향 판단

- 핵심 수요예측 결과 생성이 지연되는지 확인합니다.
- 원천 데이터 도착 자체가 늦은 상황인지 구분합니다.
- 서버 자원 포화가 일시적인지 지속적인지 확인합니다.
- 재시도 작업이 추가 부하를 만들고 있는지 확인합니다.
- 데이터 손실 또는 중복 가능성을 검토합니다.

### 복구 이후

- 결과 적재 완료 여부를 확인합니다.
- 대시보드 최신성을 확인합니다.
- 주요 집계값을 검증합니다.
- 임시 조치를 원복할지 판단합니다.
- 장애 기록과 후속 개선 항목을 남깁니다.

## 주니어 엔지니어 이해 포인트
<!--meta: sec=s22; dept=BE|DATA; level=주니어; ct_band=하; related=INC-SV-01-->
배치 작업은 사용자가 버튼을 누를 때마다 실행되는 기능과 달리 정해진 시간에 많은 데이터를 한꺼번에 처리합니다. 따라서 평소에는 서버가 여유로워 보여도 여러 배치가 동시에 실행되면 짧은 시간 안에 자원이 부족해질 수 있습니다.

주니어 엔지니어가 기억해야 할 핵심은 다음과 같습니다.

- 프로세스가 실행 중이라는 사실과 정상 속도로 처리 중이라는 사실은 다릅니다.
- 작업 성공과 데이터 정상은 별도로 확인해야 합니다.
- CPU 사용률 하나만 보고 장애를 판단하지 않습니다.
- 재시도는 항상 안전하지 않으며 과부하를 키울 수 있습니다.
- 대시보드가 열려도 데이터가 오래됐으면 업무 장애일 수 있습니다.
- 복구 완료는 기술 지표와 업무 지표를 함께 확인해야 합니다.
- 장애 대응 중 수행한 임시 변경은 반드시 기록해야 합니다.

## 시니어 엔지니어 검토 포인트
<!--meta: sec=s23; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-01-->
시니어 엔지니어는 개별 작업 최적화뿐 아니라 전체 시스템의 동시성, 의존성, 실패 전파를 검토해야 합니다.

- 작업별 자원 사용량 추정이 실제 데이터 증가를 반영하는가
- 동시 실행 제한이 전체 처리 시간을 과도하게 늘리지 않는가
- 우선순위 정책이 특정 작업의 장기 대기를 만들지 않는가
- 재시도 간격과 최대 횟수가 과부하 상황에 적합한가
- 작업 분산 후 결과의 처리 순서가 보장되는가
- 일부 서버 장애 시 나머지 서버가 부하를 감당할 수 있는가
- 경보 기준이 일시적 급증과 지속적 포화를 구분하는가
- 업무 마감 시각을 기준으로 예상 완료 시간을 계산할 수 있는가
- 복구 과정의 수동 조치가 감사 가능한 형태로 기록되는가
- 용량 확대 없이 스케줄 조정만으로 해결하려다 병목을 다른 구간으로 옮기지 않는가

## 유사 사례 INC-SV-02 — 재시도 작업 누적으로 인한 처리 지연
<!--meta: sec=s24; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
INC-SV-02는 일시적으로 실패한 일부 배치가 짧은 간격으로 반복 재시도되면서 정상 작업의 실행 기회를 줄인 유사 사례입니다. 최초 실패 자체보다 재시도 작업의 누적이 전체 처리 지연에 더 큰 영향을 주었습니다.

주요 개선 사항은 다음과 같습니다.

- 재시도 사이에 점진적으로 대기 시간을 늘리는 방식 적용
- 동일 원인으로 실패한 작업의 무제한 반복 방지
- 신규 작업과 재시도 작업의 실행 우선순위 분리
- 재시도 대기열 크기에 대한 별도 경보 추가
- 실패 원인이 해소되지 않은 상태에서는 자동 재시도를 제한
- 운영자가 수동으로 재시도할 때 대상 범위와 사유를 기록

이 사례는 자동 복구 기능이 잘못 설계되면 오히려 정상 작업을 방해할 수 있음을 보여줍니다.

## 유사 사례 INC-SV-03 — 집계 작업과 화면 갱신 작업의 자원 경합
<!--meta: sec=s25; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-01-->
INC-SV-03은 대규모 집계 작업과 대시보드 갱신 작업이 같은 시간대에 실행되면서 데이터 반영이 늦어진 유사 사례입니다. 각 작업은 단독 실행 시 정상 범위였지만 동시에 실행될 때 저장장치 입출력과 데이터베이스 연결을 경쟁했습니다.

개선 과정에서는 다음 원칙을 적용했습니다.

- 대규모 집계와 화면 갱신 작업의 실행 구간 분리
- 대시보드 반영 작업에 필요한 최소 자원 보장
- 장시간 집계 작업을 더 작은 단위로 분할
- 데이터베이스 연결 사용량에 대한 작업별 제한
- 전체 작업 완료가 아니라 중간 결과 준비 상태를 기준으로 후속 작업 실행
- 화면 갱신 지연을 서버 정상 여부와 별개로 감시

INC-SV-03은 서버 전체 사용률이 정상 범위여도 특정 공유 자원이 병목이 될 수 있다는 점을 운영 기준에 반영한 사례입니다.

## 유사 사례 비교
<!--meta: sec=s26; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=INC-SV-01|INC-SV-02|INC-SV-03-->
세 사례는 모두 배치 지연으로 나타났지만 대응해야 할 원인은 달랐습니다.

| 사례 | 핵심 현상 | 주요 원인 범주 | 대표 개선 |
|---|---|---|---|
| INC-SV-01 | 새벽 대시보드 갱신 지연 | 특정 시점의 서버 자원 집중 | 작업 분산, 사전 부하 감지 |
| INC-SV-02 | 재시도 작업 누적 | 자동 재시도 정책 | 대기 간격 조정, 반복 제한 |
| INC-SV-03 | 집계 후 화면 반영 지연 | 공유 자원 경합 | 실행 시간 분리, 자원 한도 설정 |

운영자는 “배치가 느리다”는 공통 현상만 보고 같은 조치를 반복해서는 안 됩니다. 실행 상태, 대기열, 재시도, 공유 자원, 데이터 최신성을 구분해 원인을 좁혀야 합니다.

## 용어 설명
<!--meta: sec=s27; dept=BE|DATA|CONSULT; level=주니어; ct_band=하; related=INC-SV-01-->
- **배치 작업:** 정해진 시간이나 조건에 따라 데이터를 일괄 처리하는 작업입니다.
- **자원 과부하:** CPU, 메모리, 저장장치 입출력 등 시스템 자원의 수요가 처리 가능한 범위를 지속적으로 넘는 상태입니다.
- **대기열:** 아직 실행되지 못하고 순서를 기다리는 작업 목록입니다.
- **재시도:** 실패한 작업을 일정 조건에 따라 다시 실행하는 동작입니다.
- **자원 경합:** 여러 작업이 같은 제한 자원을 동시에 사용하려고 경쟁하는 상태입니다.
- **데이터 최신성:** 사용자가 보는 데이터가 어느 기준 시점까지 반영됐는지를 나타냅니다.
- **정합성 검증:** 누락, 중복, 범위 이상 등 결과 데이터의 문제 여부를 확인하는 절차입니다.
- **용량 계획:** 예상 작업량과 데이터 증가를 바탕으로 필요한 시스템 자원을 미리 산정하는 활동입니다.
- **업무 마감 시각:** 기술 작업이 완료돼야 하는 업무상 최종 시각입니다.
- **점진적 대기:** 재시도가 반복될수록 다음 실행까지 기다리는 시간을 늘리는 방식입니다.

## 공개 커뮤니케이션 원칙
<!--meta: sec=s28; dept=CONSULT|BE|DATA|SALES; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
장애 안내는 확인된 사실과 추정 내용을 구분해 작성합니다.

공개 안내에는 다음 내용을 우선 포함합니다.

- 어떤 업무 기능이 영향을 받았는지
- 데이터가 지연됐는지, 손실됐는지
- 업무 시작 전 복구됐는지
- 결과 검증이 완료됐는지
- 재발 방지를 위해 어떤 방향으로 개선했는지

반대로 다음 정보는 공개 요약에서 제외합니다.

- 고객사 식별 정보
- 서버 주소와 네트워크 구성
- 운영 계정 및 접근 방식
- 내부 보안 설정
- 공격에 악용될 수 있는 세부 임계치
- 고객사별 데이터 구조와 업무 규칙
- 상세 로그 원문

불확실한 원인은 확정적으로 표현하지 않으며, 복구 예상은 검증 가능한 근거가 있을 때만 안내합니다.

## 후속 점검 및 종료 조건
<!--meta: sec=s29; dept=BE|DATA|CONSULT; level=시니어; ct_band=상; related=INC-SV-01-->
장애 상태를 해결됨으로 변경하기 전에 다음 항목을 확인했습니다.

- 복구 조치가 실제 운영 환경에 반영됐는지
- 동일 시간대의 배치가 반복 실행돼도 자원 집중이 완화되는지
- 핵심 작업 우선순위가 의도대로 적용되는지
- 대기열 및 데이터 최신성 경보가 정상 동작하는지
- 복구 후 데이터 검증 절차가 문서화됐는지
- 운영 담당자가 변경된 대응 절차를 확인했는지
- 임시 조치가 장기 설정으로 남아 있지 않은지
- 후속 개선 항목의 담당 부서가 지정됐는지

INC-SV-01은 발주 업무 시작 전 정상 복구됐으며, 사후 개선과 검증을 거쳐 해결 상태로 관리합니다.

## 핵심 교훈
<!--meta: sec=s30; dept=BE|DATA|CONSULT; level=주니어|시니어; ct_band=중; related=INC-SV-01-->
이번 장애에서 얻은 핵심 교훈은 다음과 같습니다.

1. 배치 작업은 개별 성능보다 동시 실행 시의 총부하를 함께 관리해야 합니다.
2. 서버 정상 여부와 업무 결과 최신성은 별도로 감시해야 합니다.
3. 자원 증설만으로 해결하기보다 작업 분산과 우선순위 조정이 함께 필요합니다.
4. 자동 재시도는 과부하 상황에서 추가 부하가 될 수 있습니다.
5. 복구 완료는 배치 성공, 결과 적재, 화면 반영, 데이터 검증을 모두 포함해야 합니다.
6. 장애 대응의 우선순위는 기술 편의가 아니라 고객 업무 마감 시각을 기준으로 정해야 합니다.
7. 재발 방지는 원인 제거뿐 아니라 더 빠른 탐지와 안전한 복구 절차까지 포함해야 합니다.
