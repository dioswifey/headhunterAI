# AI 모델 서빙 설정 단위코드 설명
<!--meta: doc=CODE-SERVE-01; doc_type=unit_code; tier=1; topic=TECH; disclosure=internal; status=active-->

## 개요
<!--meta: sec=s1; dept=AIAX|BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s2|CODE-SERVE-01#s4-->
AI/AX개발팀이 만든 모델(LLM 응답 생성, 수요예측 모델 등)을 백엔드 API 서버가 호출할 수 있도록 서빙 설정을 관리합니다.

이 단위코드는 모델 자체의 학습 로직이나 데이터 전처리 로직을 포함하지 않습니다. 백엔드 API 서버와 모델 실행 환경 사이에서 필요한 버전 선택, 요청 제한 시간, 라우팅 비율, 장애 시 대체 응답, 상태 확인, 롤백 기준을 일관된 설정으로 표현하는 것이 목적입니다.

주요 사용자는 다음과 같습니다.

- AI/AX개발팀: 모델 식별자, 모델 버전, 실행 자원 요구사항, 준비 상태 확인 경로를 정의
- 백엔드팀: API 타임아웃, 재시도 여부, 대체 응답, 동시 요청 제한을 정의
- 데이터분석팀: 수요예측 모델 결과의 기준 버전과 배치 호출 허용 시간을 확인
- 컨설팅팀: 고객 업무의 실시간성 요구사항을 설정 프로파일에 반영하도록 요구사항 전달
- 영업팀: 직접 설정을 변경하지 않으며, 고객에게 약속할 서비스 범위는 승인된 운영 기준을 참조

서빙 설정은 소스코드에 하드코딩하지 않고 환경별 설정 파일과 배포 변수로 분리합니다. 같은 모델이라도 개발·검증·운영 환경에서 엔드포인트, 트래픽 비율, 로그 상세도 및 자원 제한이 달라질 수 있습니다.

## 적용 범위와 비적용 범위
<!--meta: sec=s2; dept=AIAX|BE; level=주니어; ct_band=하; related=CODE-SERVE-01#s1|CODE-SERVE-01#s22-->
적용 범위는 다음과 같습니다.

1. 서비스가 호출할 모델 이름과 버전 지정
2. 모델 엔드포인트 및 프로토콜 설정
3. 요청 타임아웃과 연결 타임아웃 분리
4. 동시 요청 수와 대기열 크기 제한
5. 점진적 전환을 위한 버전별 트래픽 가중치 설정
6. 오류·타임아웃 발생 시 대체 응답 지정
7. 상태 확인 및 준비 상태 확인 조건 지정
8. 모델 호출 지표와 로그 수집 항목 지정
9. 설정 검증과 안전한 롤백 지원

다음 항목은 이 단위코드의 비적용 범위입니다.

- 모델 학습 데이터 생성 및 정제
- 모델 품질 평가 데이터셋의 구축
- RAG 검색·재정렬 로직
- 수요예측 배치 파이프라인의 스케줄링과 데이터 적재
- 백엔드 전체 인증·인가 정책
- 고객사 원천 시스템과의 데이터 연동
- 프롬프트 내용이나 업무별 답변 정책의 직접 설계

비적용 범위의 기능을 이 설정 모듈에 추가하면 배포 책임과 장애 원인 구분이 불명확해집니다. 모델 실행에 필요한 설정인지, 모델이 수행할 업무 로직인지 구분한 뒤 반영해야 합니다.

## 디렉터리와 모듈 구성
<!--meta: sec=s3; dept=AIAX|BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s5|CODE-SERVE-01#s20-->
권장 구성은 다음과 같습니다.

- `serving/config_schema.py`: 설정 필드, 자료형, 필수값 및 범위 정의
- `serving/config_loader.py`: 공통 설정과 환경별 설정 병합
- `serving/config_validator.py`: 버전, 타임아웃, 트래픽 가중치 검증
- `serving/model_registry.py`: 논리 모델명과 실제 배포 버전 연결
- `serving/router.py`: 버전별 트래픽 분배
- `serving/client.py`: 모델 서버 호출과 응답 변환
- `serving/fallback.py`: 대체 응답 생성
- `serving/health.py`: 생존 상태와 준비 상태 확인
- `serving/circuit_breaker.py`: 연속 실패 시 호출 차단
- `serving/metrics.py`: 지연시간, 오류율, 버전별 호출량 기록
- `serving/errors.py`: 서빙 계층의 표준 예외 정의
- `tests/serving/`: 설정 검증, 라우팅 및 실패 처리 테스트

모듈 간 의존 방향은 `API 처리 계층 → 서빙 클라이언트 → 라우터·레지스트리 → 설정` 순서를 기본으로 합니다. 설정 모듈이 API 계층이나 업무별 응답 형식을 직접 참조하지 않도록 합니다.

## 핵심 로직
<!--meta: sec=s4; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s6|CODE-SERVE-01#s9|CODE-SERVE-01#s10-->
1. 모델 버전을 설정 파일로 관리하고, 배포 시 버전 번호를 함께 기록
2. 서빙 요청마다 타임아웃(기본 5초)을 두고, 초과 시 대체 응답(사전 정의된 안내 문구) 반환
3. 모델 교체 시 이전 버전과 새 버전을 동시에 띄워 트래픽 일부만 새 버전으로 보내는 점진적 전환 지원

요청 처리 순서는 다음과 같습니다.

1. API 요청에서 업무 유형과 추적 식별자를 확인합니다.
2. 업무 유형에 연결된 논리 모델명을 조회합니다.
3. 활성화된 모델 버전과 트래픽 가중치를 읽습니다.
4. 요청 단위로 라우팅할 버전을 결정합니다.
5. 해당 업무 프로파일의 타임아웃과 동시 요청 제한을 적용합니다.
6. 모델 서버를 호출하고 응답 형식과 필수 필드를 검증합니다.
7. 성공 응답이면 버전, 지연시간 및 결과 상태를 기록합니다.
8. 타임아웃이나 호출 실패이면 재시도 가능 여부를 판단합니다.
9. 복구되지 않으면 사전 정의된 안내 문구를 반환합니다.
10. 실패 지표를 누적하고 차단 기준을 초과했는지 확인합니다.

점진적 전환 중에는 이전 버전과 새 버전의 호출량, 오류율 및 응답시간을 반드시 분리해 기록합니다. 전체 평균만 확인하면 새 버전에서 발생하는 문제를 조기에 발견하기 어렵습니다.

## 설정 파일 구조
<!--meta: sec=s5; dept=AIAX|BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s3|CODE-SERVE-01#s6|CODE-SERVE-01#s7-->
설정은 공통 기본값, 업무 프로파일, 환경별 재정의 값으로 구분합니다.

예시 구조는 다음과 같습니다.

    serving:
      defaults:
        timeout_ms: 5000
        connect_timeout_ms: 800
        max_retries: 0
        fallback_enabled: true
      models:
        response-generator:
          active_versions:
            - version: "v3"
              traffic_weight: 90
            - version: "v4"
              traffic_weight: 10
          health_path: "/health"
          readiness_path: "/ready"
        demand-forecast:
          active_versions:
            - version: "v12"
              traffic_weight: 100
      profiles:
        realtime:
          timeout_ms: 5000
          queue_limit: 40
        non_realtime:
          timeout_ms: 30000
          queue_limit: 120

위 값은 구조를 설명하기 위한 예시입니다. 프로젝트별 승인값이 존재하면 승인값이 우선합니다. 공통 기본 타임아웃은 5초이지만, 수요예측과 같이 실시간성이 낮은 호출은 별도 프로파일을 사용해야 합니다.

설정 파일에는 비밀번호, 접근 토큰, 개인키를 직접 기록하지 않습니다. 비밀값은 배포 환경의 비밀 저장소나 승인된 환경 변수 참조 키로 연결합니다.

## 설정 로딩 우선순위
<!--meta: sec=s6; dept=BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s5|CODE-SERVE-01#s21-->
설정 병합 우선순위는 낮은 순서부터 다음과 같습니다.

1. 코드에 정의된 안전 기본값
2. 공통 설정 파일
3. 업무 유형별 프로파일
4. 실행 환경별 설정 파일
5. 배포 시 주입되는 승인된 환경 변수
6. 긴급 변경용 운영 오버라이드

뒤 단계의 값이 앞 단계의 값을 덮어쓸 수 있습니다. 단, 다음 보호 필드는 운영 오버라이드만으로 변경할 수 없습니다.

- 모델 버전 식별자
- 외부 공개 엔드포인트
- 트래픽 가중치 총합 검증 정책
- 비밀값 참조 방식
- 로그 비식별화 활성 여부

`load_serving_config()`는 병합된 설정과 함께 각 값의 출처를 반환해야 합니다. 운영 중 실제 적용값을 확인할 때 “현재 값”뿐 아니라 “어느 계층에서 덮어썼는지”도 추적할 수 있어야 합니다.

권장 반환 정보는 다음과 같습니다.

- 최종 설정 객체
- 설정 체크섬
- 로딩 시각
- 실행 환경
- 모델별 활성 버전
- 필드별 출처
- 검증 경고 목록

## 설정 스키마와 검증 규칙
<!--meta: sec=s7; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s5|CODE-SERVE-01#s8|CODE-SERVE-01#s10-->
`validate_serving_config()`는 애플리케이션 시작 전에 다음 조건을 검사합니다.

- 모델 논리명이 비어 있지 않아야 함
- 활성 버전이 한 개 이상이어야 함
- 버전 문자열이 허용된 형식을 따라야 함
- 트래픽 가중치는 음수가 아니어야 함
- 활성 버전의 트래픽 가중치 합은 100이어야 함
- 타임아웃은 0보다 커야 함
- 연결 타임아웃은 전체 타임아웃보다 작아야 함
- 재시도 횟수는 허용 상한 이하여야 함
- 대체 응답을 사용하는 경우 안내 문구 키가 존재해야 함
- 상태 확인 경로는 내부 허용 경로 형식을 따라야 함
- 운영 환경에서는 임시 모델 태그 사용을 금지해야 함
- 동일 모델 버전이 중복 선언되지 않아야 함

오류는 애플리케이션 시작을 중단하는 `ConfigValidationError`와 실행은 허용하지만 확인이 필요한 경고로 구분합니다.

시작을 중단해야 하는 예시는 다음과 같습니다.

- 트래픽 가중치 합이 100이 아님
- 활성 버전의 엔드포인트가 없음
- 타임아웃 값이 음수임
- 운영 모델 버전이 레지스트리에 등록되지 않음
- 대체 응답이 활성화됐지만 문구가 정의되지 않음

경고로 처리할 수 있는 예시는 다음과 같습니다.

- 점진적 전환 중 신규 버전 비율이 권장 범위를 초과함
- 비실시간 프로파일이 공통 5초 값을 그대로 사용함
- 로그 상세도가 운영 권장값보다 높음

## 모델 버전 식별과 등록
<!--meta: sec=s8; dept=AIAX; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s7|CODE-SERVE-01#s9|CODE-SERVE-01#s19-->
모델 버전은 사람이 읽을 수 있는 표시명과 변경되지 않는 배포 식별자를 함께 관리합니다.

필수 등록 정보는 다음과 같습니다.

- 논리 모델명
- 모델 버전
- 모델 아티팩트 식별자
- 실행 이미지 식별자
- 입력 스키마 버전
- 출력 스키마 버전
- 등록 상태
- 배포 가능 환경
- 담당 부서
- 대체 가능한 이전 버전

`resolve_model_version(logical_name, requested_version=None)`은 요청 버전이 있으면 허용 여부를 검증하고, 없으면 활성 라우팅 설정에 따라 버전을 선택합니다.

`latest`, `current`, `temp`와 같이 배포 시점에 의미가 바뀌는 태그는 운영 활성 버전에 사용하지 않습니다. 롤백 시 동일한 설정이 다른 모델을 가리키는 문제를 방지하기 위해 운영 설정에는 고정된 버전 식별자를 기록합니다.

입력 또는 출력 스키마가 변경된 모델은 단순 가중치 조정으로 교체하지 않습니다. 백엔드 호환성 계층이 양쪽 스키마를 모두 처리할 수 있는지 먼저 검증해야 합니다.

## 점진적 트래픽 전환
<!--meta: sec=s9; dept=AIAX|BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s4|CODE-SERVE-01#s8|CODE-SERVE-01#s18-->
`select_version(request_context, routing_config)`는 활성 버전별 가중치를 기준으로 호출 대상을 선택합니다.

점진적 전환은 다음 단계를 기본 흐름으로 사용합니다.

1. 신규 버전을 트래픽 0% 상태로 배포
2. 상태 확인과 준비 상태 확인 통과
3. 내부 검증 요청만 신규 버전으로 전달
4. 승인 후 소량의 운영 트래픽 할당
5. 구간별 오류율과 지연시간 비교
6. 이상이 없으면 트래픽 비율 확대
7. 신규 버전 100% 전환 후 이전 버전 대기
8. 안정화 확인 후 이전 버전 종료

세션 또는 동일 업무 요청의 일관성이 필요한 경우 요청 식별자를 해시해 버전을 선택합니다. 단순 난수 방식은 같은 사용자의 연속 요청이 서로 다른 버전으로 이동할 수 있으므로 대화 문맥이나 비교 결과에 영향을 줄 수 있습니다.

라우팅 결과에는 다음 정보를 기록합니다.

- 논리 모델명
- 선택된 버전
- 라우팅 정책 버전
- 적용 가중치
- 요청 추적 식별자
- 강제 라우팅 여부
- 선택 시각

강제 라우팅 기능은 검증 환경과 승인된 내부 요청에만 사용합니다. 일반 운영 요청이 임의의 모델 버전을 지정할 수 있도록 노출하지 않습니다.

## 타임아웃 정책
<!--meta: sec=s10; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s4|CODE-SERVE-01#s11|CODE-SERVE-01#s12-->
타임아웃은 하나의 숫자로만 관리하지 않고 다음 단계로 구분합니다.

- 연결 타임아웃: 모델 서버와 연결을 맺기까지 허용하는 시간
- 응답 타임아웃: 연결 후 결과를 받을 때까지 허용하는 시간
- 전체 요청 예산: 라우팅, 대기, 모델 호출, 응답 변환을 모두 포함한 시간
- 대기열 타임아웃: 실행 자리가 날 때까지 대기할 수 있는 시간

기본 서빙 요청 타임아웃은 5초입니다. 다만 업무 특성에 따라 별도 프로파일을 사용합니다.

- 콜센터 AI 상담: 실시간성이 중요하므로 짧은 전체 요청 예산과 빠른 대체 응답을 적용
- 수요예측 모델: 실시간성이 낮으므로 더 긴 처리 시간을 허용할 수 있으나 무제한 대기는 금지
- 내부 검증 요청: 운영 요청과 분리된 제한을 적용
- 상태 확인 요청: 모델 추론 요청보다 짧은 제한을 적용

상위 API의 타임아웃이 모델 호출 타임아웃보다 짧으면 모델이 응답을 생성해도 상위 요청이 이미 종료될 수 있습니다. 따라서 타임아웃은 다음 관계를 만족하도록 설계합니다.

`모델 호출 제한 < 백엔드 API 제한 < 외부 호출 주체의 전체 제한`

대체 응답 생성과 로깅에 필요한 시간도 상위 API 제한 안에 포함해야 합니다.

## 재시도 정책
<!--meta: sec=s11; dept=BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s10|CODE-SERVE-01#s14|CODE-SERVE-01#s15-->
모델 호출 재시도는 기본적으로 비활성화하거나 매우 제한적으로 사용합니다. 모델 추론은 비용과 처리시간이 크므로 무조건 재시도하면 장애 시 부하를 증폭시킬 수 있습니다.

재시도를 허용할 수 있는 조건은 다음과 같습니다.

- 연결이 시작되기 전에 일시적 네트워크 오류가 발생한 경우
- 모델 서버가 명시적으로 짧은 재시도를 허용한 경우
- 요청이 멱등적이며 중복 실행의 부작용이 없는 경우
- 남은 전체 요청 예산이 충분한 경우
- 회로 차단기가 열린 상태가 아닌 경우

재시도를 금지하는 조건은 다음과 같습니다.

- 입력값 검증 실패
- 출력 스키마 불일치
- 인증 또는 권한 오류
- 전체 요청 예산 소진
- 모델 서버의 지속적 과부하
- 동일 요청이 이미 모델 실행 단계에 진입했는지 확인할 수 없는 경우

재시도를 수행할 때는 최초 시도와 재시도 횟수를 지표에 분리해 기록합니다. 최종 성공률만 기록하면 재시도로 인해 숨겨진 불안정성을 발견하기 어렵습니다.

## 대체 응답 처리
<!--meta: sec=s12; dept=AIAX|BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s10|CODE-SERVE-01#s13|CODE-SERVE-01#s20-->
`build_fallback_response(reason, profile, trace_id)`는 모델 호출 실패 사유를 외부에 그대로 노출하지 않고 사전 정의된 안내 문구를 반환합니다.

대체 응답의 원칙은 다음과 같습니다.

- 사용자에게 내부 서버 주소나 예외 메시지를 노출하지 않음
- 실제 모델 결과처럼 보이는 임의 답변을 생성하지 않음
- 업무별로 승인된 안내 문구 사용
- 재시도 가능 여부를 일관된 필드로 제공
- 추적 식별자를 내부 로그에만 연결
- 타임아웃, 과부하, 일시적 연결 실패를 외부 문구에서 과도하게 구분하지 않음

권장 내부 응답 상태는 다음과 같습니다.

- `MODEL_TIMEOUT`: 제한 시간 초과
- `MODEL_UNAVAILABLE`: 모델 서버 사용 불가
- `MODEL_OVERLOADED`: 동시 처리 한도 초과
- `MODEL_INVALID_RESPONSE`: 출력 검증 실패
- `MODEL_ROUTE_UNAVAILABLE`: 활성 버전 선택 실패
- `MODEL_CALL_BLOCKED`: 회로 차단기에 의해 호출 차단

대체 응답도 일반 응답과 동일한 출력 스키마를 유지해야 합니다. 백엔드의 후속 처리 코드가 성공 응답과 실패 응답을 안전하게 구분할 수 있도록 `result_status`, `fallback_used` 등의 필드를 명시적으로 사용합니다.

## 동시 요청과 대기열 제한
<!--meta: sec=s13; dept=AIAX|BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s12|CODE-SERVE-01#s14|CODE-SERVE-01#s17-->
모델 서버는 백엔드 일반 API보다 요청 한 건이 소비하는 CPU, GPU 메모리 또는 처리시간이 클 수 있습니다. 따라서 무제한 동시 호출을 허용하지 않습니다.

주요 설정은 다음과 같습니다.

- `max_in_flight`: 동시에 실행할 수 있는 요청 수
- `queue_limit`: 실행 전 대기할 수 있는 요청 수
- `queue_timeout_ms`: 대기열에서 허용되는 최대 시간
- `per_client_limit`: 호출 주체별 동시 요청 제한
- `priority_class`: 실시간·일반·내부 검증 요청 우선순위
- `reject_policy`: 한도 초과 시 즉시 거절 또는 제한된 대기 여부

대기열이 길어지면 처리량이 유지되는 것처럼 보여도 실제 사용자 응답시간은 급격히 증가합니다. 대기열 길이뿐 아니라 대기시간의 상위 백분위 값도 관찰해야 합니다.

실시간 요청과 비실시간 요청이 동일한 모델 실행 자원을 공유할 경우 우선순위를 분리합니다. 비실시간 요청이 대기열을 점유해 실시간 요청의 타임아웃을 유발하지 않도록 별도 제한이나 실행 풀을 구성합니다.

## 회로 차단기
<!--meta: sec=s14; dept=BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s11|CODE-SERVE-01#s13|CODE-SERVE-01#s18-->
회로 차단기는 모델 서버의 연속 실패가 발생할 때 백엔드가 계속 호출해 장애를 확대하는 것을 방지합니다.

상태는 다음과 같이 구분합니다.

- `CLOSED`: 정상 호출 허용
- `OPEN`: 모델 호출을 차단하고 즉시 대체 응답 반환
- `HALF_OPEN`: 제한된 시험 요청만 허용해 복구 여부 확인

`record_call_result(model_version, result)`는 성공, 타임아웃, 연결 실패, 출력 검증 실패를 구분해 기록합니다. 모든 실패를 동일하게 처리하지 않으며, 입력값 오류처럼 모델 서버 상태와 무관한 실패는 회로 차단기 실패 횟수에 포함하지 않습니다.

회로 개방 기준은 단순 연속 실패 횟수뿐 아니라 최소 표본 수와 관찰 구간을 함께 고려합니다. 요청이 거의 없는 모델에서 한 번의 실패만으로 장시간 차단되는 상황을 피해야 합니다.

버전별 상태를 분리해 관리합니다. 신규 버전에서만 실패가 증가한 경우 이전 버전까지 함께 차단하지 않고 신규 버전의 트래픽만 제거할 수 있어야 합니다.

## 상태 확인과 준비 상태
<!--meta: sec=s15; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s11|CODE-SERVE-01#s16|CODE-SERVE-01#s18-->
상태 확인은 생존 상태와 준비 상태를 구분합니다.

- 생존 상태: 프로세스가 실행 중이며 자체 점검에 응답할 수 있는지 확인
- 준비 상태: 실제 모델을 메모리에 적재했고 요청을 처리할 수 있는지 확인

`check_liveness()`는 가볍고 빠르게 수행되어야 하며 모델 추론을 매번 실행하지 않습니다. `check_readiness()`는 다음 항목을 확인할 수 있습니다.

- 설정 로딩 완료
- 모델 아티팩트 접근 가능
- 모델 메모리 적재 완료
- 필수 토크나이저 또는 런타임 초기화 완료
- 입력·출력 스키마 등록 완료
- 요청 처리 대기열 생성 완료
- 치명적 초기화 오류 없음

준비되지 않은 인스턴스는 트래픽 대상에 포함하지 않습니다. 프로세스가 살아 있다는 이유만으로 모델 적재 전 요청을 전달하면 초기 요청에서 타임아웃이 집중될 수 있습니다.

상태 확인 응답에는 모델 파일 경로, 비밀값, 내부 네트워크 정보를 포함하지 않습니다.

## 요청·응답 스키마 보호
<!--meta: sec=s16; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s8|CODE-SERVE-01#s15|CODE-SERVE-01#s20-->
모델 버전이 변경돼도 백엔드 API가 예상하는 계약을 유지해야 합니다.

입력 검증 항목은 다음과 같습니다.

- 필수 필드 존재 여부
- 문자열 길이와 배열 크기 제한
- 허용되지 않은 자료형
- 빈 입력 또는 공백 입력
- 지원하지 않는 언어·업무 유형
- 요청 크기 상한
- 중복 요청 식별자 형식

출력 검증 항목은 다음과 같습니다.

- 필수 결과 필드 존재 여부
- 결과 상태 코드의 허용 범위
- 숫자 필드의 비정상 값 여부
- 빈 결과 처리
- 출력 크기 상한
- 모델 버전과 출력 스키마 버전의 일치 여부
- 처리시간과 추적 정보의 형식

출력 검증 실패 시 원본 결과를 그대로 외부에 반환하지 않습니다. 실패 지표를 남기고 사전 정의된 대체 응답으로 전환합니다.

스키마 변경이 필요한 경우 기존 필드를 즉시 제거하기보다 호환 기간을 둡니다. 신규 모델을 점진적으로 전환할 때 백엔드가 구버전과 신버전 출력을 모두 처리할 수 있어야 합니다.

## 관측 지표
<!--meta: sec=s17; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s9|CODE-SERVE-01#s13|CODE-SERVE-01#s18-->
다음 지표를 모델명과 버전별로 수집합니다.

- 총 호출 수
- 성공 호출 수
- 실패 호출 수
- 타임아웃 수
- 대체 응답 수
- 재시도 수
- 회로 차단 수
- 현재 동시 요청 수
- 대기열 길이
- 대기시간
- 모델 추론시간
- 전체 서빙시간
- 입력 크기
- 출력 크기
- 준비 상태 실패 횟수
- 버전별 트래픽 비율

지연시간은 평균만 사용하지 않고 중앙값과 상위 백분위 값을 함께 확인합니다. 일부 요청만 매우 느린 경우 평균값으로는 사용자가 체감하는 지연을 파악하기 어렵습니다.

지표 라벨에는 사용자 입력 원문, 개인 식별값, 자유 형식 오류 메시지를 넣지 않습니다. 라벨 종류가 무제한으로 증가하면 모니터링 저장소의 부하가 커질 수 있으므로 모델명, 고정 버전, 결과 상태와 같이 제한된 값만 사용합니다.

점진적 전환 중에는 다음 비교 화면을 우선 확인합니다.

- 이전 버전과 신규 버전의 오류율 차이
- 이전 버전과 신규 버전의 타임아웃 비율
- 버전별 전체 응답시간
- 버전별 대체 응답 사용률
- 버전별 출력 검증 실패율

## 로그와 추적 식별자
<!--meta: sec=s18; dept=AIAX|BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s9|CODE-SERVE-01#s14|CODE-SERVE-01#s17-->
모든 모델 호출은 백엔드 요청의 추적 식별자와 연결합니다.

권장 로그 필드는 다음과 같습니다.

- `trace_id`
- `request_id`
- `logical_model`
- `model_version`
- `routing_policy_version`
- `serving_profile`
- `call_result`
- `fallback_used`
- `retry_count`
- `queue_wait_ms`
- `inference_ms`
- `total_elapsed_ms`
- `circuit_state`
- `config_checksum`

로그에 원문 입력과 모델 전체 출력을 기본 저장하지 않습니다. 디버깅 목적의 상세 로그가 필요한 경우 승인된 환경에서 제한적으로 활성화하고, 비식별화와 보관기간 정책을 적용합니다.

오류 로그는 예외 이름과 내부 분류 코드를 기록하되 접근 토큰, 인증 헤더, 내부 비밀값이 포함되지 않도록 필터링합니다.

설정 체크섬을 기록하면 장애 시점에 어떤 설정이 실제 적용됐는지 확인할 수 있습니다. 단, 체크섬 생성을 위해 비밀값의 평문을 로그에 포함해서는 안 됩니다.

## 롤백 기준과 절차
<!--meta: sec=s19; dept=AIAX|BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s8|CODE-SERVE-01#s9|CODE-SERVE-01#s23-->
롤백은 신규 모델의 트래픽 비율을 0으로 낮추고 검증된 이전 버전으로 복귀하는 것을 기본으로 합니다.

롤백 검토 조건은 다음과 같습니다.

- 신규 버전 오류율이 승인 기준을 초과
- 타임아웃 비율이 이전 버전 대비 유의하게 증가
- 출력 스키마 검증 실패 발생
- 대체 응답 비율 급증
- 준비 상태가 반복적으로 실패
- 모델 서버 자원 사용량이 안정 범위를 벗어남
- 업무 담당자가 치명적 결과 이상을 확인

롤백 절차는 다음과 같습니다.

1. 신규 버전의 추가 트래픽 확대를 중지합니다.
2. 현재 설정과 지표 화면을 보존합니다.
3. 신규 버전 가중치를 0으로 조정합니다.
4. 이전 버전 가중치를 100으로 복구합니다.
5. 설정 검증과 체크섬 확인을 수행합니다.
6. 라우팅 반영 여부를 실제 요청으로 확인합니다.
7. 대체 응답 및 오류율이 정상화되는지 확인합니다.
8. 신규 버전 인스턴스는 원인 확인 전까지 즉시 삭제하지 않습니다.
9. 변경 이력에 롤백 사유와 담당 부서를 기록합니다.

입력·출력 스키마가 함께 변경된 배포라면 모델 가중치만 되돌려도 백엔드가 구버전 응답을 처리하지 못할 수 있습니다. 배포 전 모델과 백엔드의 롤백 조합을 함께 검증해야 합니다.

## 주요 함수 설명
<!--meta: sec=s20; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s3|CODE-SERVE-01#s12|CODE-SERVE-01#s16-->
`load_serving_config(environment)`

- 공통 설정과 환경별 설정을 읽습니다.
- 필드별 출처와 설정 체크섬을 생성합니다.
- 읽기 실패 시 불완전한 설정으로 실행하지 않습니다.

`validate_serving_config(config)`

- 필수값, 자료형, 범위 및 상호 조건을 검사합니다.
- 치명적 오류와 경고를 구분해 반환합니다.
- 운영 환경의 임시 버전 사용을 차단합니다.

`resolve_model_version(logical_model, context)`

- 논리 모델명에 연결된 활성 버전을 조회합니다.
- 요청 컨텍스트와 라우팅 정책에 따라 실제 버전을 결정합니다.
- 선택 결과와 정책 버전을 함께 반환합니다.

`invoke_model(request, serving_context)`

- 연결 및 응답 타임아웃을 적용합니다.
- 동시 요청 제한과 회로 차단기 상태를 확인합니다.
- 응답을 표준 스키마로 변환합니다.

`validate_model_response(response, schema_version)`

- 필수 필드와 자료형을 확인합니다.
- 출력 크기와 허용 상태값을 검사합니다.
- 실패하면 `InvalidModelResponseError`를 발생시킵니다.

`build_fallback_response(reason, profile, trace_id)`

- 업무 프로파일에 연결된 사전 정의 안내 문구를 선택합니다.
- 내부 실패 사유를 외부 표준 상태로 변환합니다.
- 정상 응답과 호환되는 구조를 반환합니다.

`record_serving_metrics(result)`

- 모델명, 버전, 결과 상태, 지연시간을 기록합니다.
- 사용자 원문을 지표 라벨로 사용하지 않습니다.

## 표준 예외와 오류 매핑
<!--meta: sec=s21; dept=BE; level=주니어; ct_band=중; related=CODE-SERVE-01#s6|CODE-SERVE-01#s12|CODE-SERVE-01#s20-->
서빙 계층의 예외는 다음과 같이 구분합니다.

- `ConfigLoadError`: 설정 파일 또는 환경 변수 로딩 실패
- `ConfigValidationError`: 설정값 검증 실패
- `ModelVersionNotFoundError`: 요청 가능한 모델 버전 없음
- `ModelRouteError`: 트래픽 라우팅 대상 결정 실패
- `ModelConnectionError`: 모델 서버 연결 실패
- `ModelTimeoutError`: 호출 제한 시간 초과
- `ModelOverloadError`: 동시 요청 또는 대기열 한도 초과
- `InvalidModelResponseError`: 출력 스키마 검증 실패
- `CircuitOpenError`: 회로 차단 상태로 호출 거부

예외는 API 응답 코드와 일대일로 직접 노출하지 않습니다. 내부 예외를 외부 표준 오류 상태로 변환하고, 세부 예외 정보는 내부 로그에만 기록합니다.

입력 검증 오류와 모델 서버 장애를 구분해야 합니다. 잘못된 요청을 모델 장애로 집계하면 회로 차단기가 불필요하게 열리고 운영 지표도 왜곡됩니다.

## 단위 테스트 기준
<!--meta: sec=s22; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s2|CODE-SERVE-01#s7|CODE-SERVE-01#s20-->
필수 단위 테스트는 다음과 같습니다.

### 설정 로딩

- 공통 설정만 있을 때 기본값 적용
- 환경별 설정이 공통값을 정상적으로 덮어씀
- 필수 파일 누락 시 시작 실패
- 허용되지 않은 환경 변수 무시 또는 오류 처리
- 설정 체크섬의 동일 입력 재현성 확인

### 설정 검증

- 트래픽 가중치 합이 100인 경우 통과
- 트래픽 가중치 합이 100이 아닌 경우 실패
- 음수 타임아웃 거부
- 연결 타임아웃이 전체 타임아웃보다 큰 경우 거부
- 중복 모델 버전 선언 거부
- 대체 응답 문구 누락 시 실패

### 라우팅

- 단일 버전 100% 선택
- 두 버전의 가중치 경계값 처리
- 가중치가 0인 버전 미선택
- 동일 요청 식별자에 대한 일관된 버전 선택
- 등록되지 않은 버전 강제 지정 차단

### 실패 처리

- 타임아웃 발생 시 대체 응답 반환
- 출력 스키마 오류 시 원본 결과 미노출
- 회로 차단 상태에서 모델 호출 미수행
- 대기열 한도 초과 시 즉시 표준 오류 반환
- 재시도 금지 오류에서 추가 호출 미수행

### 지표와 로그

- 성공·실패 지표가 버전별로 분리됨
- 대체 응답 사용 여부 기록
- 비밀값과 입력 원문 미기록
- 추적 식별자가 모델 호출 로그에 연결됨

시간과 난수에 의존하는 테스트는 테스트용 시계와 고정 라우팅 시드를 주입해 재현 가능하게 작성합니다.

## 배포 전 점검표
<!--meta: sec=s23; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s18|CODE-SERVE-01#s19|CODE-SERVE-01#s22-->
배포 전 다음 항목을 확인합니다.

- [ ] 모델 버전이 레지스트리에 등록되어 있음
- [ ] 입력·출력 스키마 버전이 백엔드와 호환됨
- [ ] 운영 설정에 고정 버전 식별자가 사용됨
- [ ] 트래픽 가중치 합이 100임
- [ ] 기본 5초 타임아웃 또는 승인된 프로젝트별 값이 적용됨
- [ ] 연결 타임아웃과 전체 타임아웃 관계가 올바름
- [ ] 대체 응답 문구가 등록되어 있음
- [ ] 상태 확인과 준비 상태 확인이 통과함
- [ ] 동시 요청 및 대기열 제한이 설정됨
- [ ] 버전별 지표 화면이 준비됨
- [ ] 로그에 입력 원문과 비밀값이 남지 않음
- [ ] 이전 버전이 즉시 복귀 가능한 상태임
- [ ] 롤백 담당자와 판단 기준이 확인됨
- [ ] 설정 체크섬이 배포 기록에 남음
- [ ] 점진적 전환의 최초 트래픽 비율이 승인됨

배포 완료 후에는 설정 파일 반영 여부만 확인하지 않고 실제 요청이 의도한 모델 버전으로 전달되는지 검증합니다.

## 운영 중 변경 절차
<!--meta: sec=s24; dept=AIAX|BE; level=시니어; ct_band=상; related=CODE-SERVE-01#s6|CODE-SERVE-01#s9|CODE-SERVE-01#s23-->
운영 중 모델 버전, 타임아웃 또는 트래픽 비율을 변경할 때는 다음 정보를 변경 기록에 남깁니다.

- 변경 대상 모델
- 변경 전후 버전
- 변경 전후 트래픽 비율
- 변경 전후 타임아웃
- 변경 사유
- 예상 영향
- 검증 방법
- 롤백 조건
- 담당 부서
- 설정 체크섬

한 번의 변경에서 모델 버전, 타임아웃, 동시 요청 수, 재시도 정책을 동시에 크게 조정하지 않습니다. 여러 변수를 한꺼번에 바꾸면 지표 변화의 원인을 판별하기 어렵습니다.

긴급 변경도 설정 검증을 우회하지 않습니다. 긴급 오버라이드는 유효기간을 두고, 정상 설정 파일에 반영되면 제거합니다. 만료된 오버라이드가 남아 다음 배포의 설정을 예상과 다르게 덮어쓰지 않도록 확인합니다.

## 문제 상황별 점검 순서
<!--meta: sec=s25; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s10|CODE-SERVE-01#s14|CODE-SERVE-01#s17-->
### 응답이 지속적으로 5초에 종료되는 경우

1. 공통 기본 타임아웃이 적용됐는지 확인
2. 프로젝트별 프로파일이 정상 병합됐는지 확인
3. 상위 API 타임아웃이 더 짧지 않은지 확인
4. 대기열 시간이 전체 요청 예산을 소진하는지 확인
5. 모델 추론시간과 네트워크 시간을 분리해 확인

### 신규 버전 호출량이 설정 비율과 다른 경우

1. 활성 인스턴스가 동일한 설정 체크섬을 사용하는지 확인
2. 설정 캐시 갱신 여부 확인
3. 세션 고정 또는 요청 식별자 해시 정책 확인
4. 준비 상태 실패로 신규 버전이 라우팅에서 제외됐는지 확인
5. 강제 라우팅된 내부 검증 요청이 지표에 포함됐는지 확인

### 대체 응답이 급증한 경우

1. 실패 사유별 건수 확인
2. 회로 차단 상태 확인
3. 모델 버전별 타임아웃 비율 비교
4. 대기열 길이와 동시 요청 수 확인
5. 출력 스키마 검증 실패 여부 확인
6. 최근 설정 변경과 배포 이력 확인

### 모델 서버는 정상인데 백엔드에서 실패하는 경우

1. 엔드포인트와 포트 설정 확인
2. 연결 타임아웃 확인
3. 인증 정보 참조 키 확인
4. 백엔드가 기대하는 출력 스키마 확인
5. 응답 크기 제한 확인
6. 추적 식별자로 양쪽 로그 연결

## 용어 설명
<!--meta: sec=s26; dept=AIAX|BE; level=주니어; ct_band=하; related=CODE-SERVE-01#s4|CODE-SERVE-01#s9|CODE-SERVE-01#s14-->
- **모델 서빙**: 학습된 모델이 외부 요청을 받아 추론 결과를 반환하도록 실행하는 방식
- **논리 모델명**: 업무 코드에서 참조하는 안정적인 모델 이름
- **모델 버전**: 특정 모델 아티팩트와 실행 구성을 구분하는 식별자
- **트래픽 가중치**: 여러 모델 버전에 요청을 분배하는 비율
- **점진적 전환**: 신규 버전에 일부 요청만 보내 안정성을 확인하며 비율을 확대하는 방식
- **타임아웃**: 요청 처리를 기다리는 최대 허용 시간
- **대체 응답**: 모델 결과를 받을 수 없을 때 반환하는 사전 정의 안내 응답
- **준비 상태**: 모델 인스턴스가 실제 요청을 처리할 수 있는 상태인지 나타내는 값
- **대기열**: 즉시 실행하지 못한 요청이 처리 순서를 기다리는 공간
- **회로 차단기**: 연속 장애 시 추가 호출을 임시 차단하는 보호 장치
- **설정 체크섬**: 적용된 설정의 동일 여부를 비교하기 위한 요약값
- **롤백**: 문제가 발생한 변경을 취소하고 검증된 이전 상태로 복구하는 작업

## 주의점
<!--meta: sec=s27; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=CODE-SERVE-01#s5|CODE-SERVE-01#s10|CODE-SERVE-01#s24-->
타임아웃 기준값은 콜센터 AI 상담(실시간성 중요)과 수요예측 배치(실시간성 낮음)에서 다르게 설정합니다. 프로젝트별 설정값을 공통 기본값과 혼동하지 않도록 주의합니다.

추가 주의사항은 다음과 같습니다.

1. 운영 설정에 변경 가능한 별칭 대신 고정 모델 버전을 사용합니다.
2. 트래픽 가중치 합이 100이 아닌 설정은 배포하지 않습니다.
3. 신규 버전의 입력·출력 스키마 호환성을 확인하지 않고 점진적 전환을 시작하지 않습니다.
4. 타임아웃을 늘리는 것만으로 성능 문제를 해결하지 않습니다.
5. 재시도를 무조건 활성화해 모델 서버의 과부하를 키우지 않습니다.
6. 대체 응답을 정상 모델 결과와 구분할 수 있어야 합니다.
7. 상태 확인 요청이 실제 추론 자원을 과도하게 사용하지 않도록 합니다.
8. 모델 입력 원문과 전체 출력을 운영 로그에 기본 저장하지 않습니다.
9. 설정 변경 후 일부 인스턴스에만 값이 반영되지 않았는지 체크섬으로 확인합니다.
10. 이전 모델을 제거하기 전에 롤백 가능 여부를 검증합니다.
11. 실시간 요청과 비실시간 요청이 같은 대기열을 무제한 공유하지 않도록 합니다.
12. 모델 서버 오류와 잘못된 입력 오류를 동일한 장애로 집계하지 않습니다.

## 완료 기준
<!--meta: sec=s28; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=CODE-SERVE-01#s22|CODE-SERVE-01#s23|CODE-SERVE-01#s27-->
이 단위코드는 다음 조건을 모두 충족할 때 완료된 것으로 판단합니다.

- 설정 파일에서 모델 버전을 변경할 수 있음
- 배포 기록에서 실제 모델 버전을 확인할 수 있음
- 기본 5초 타임아웃이 적용됨
- 업무별 별도 타임아웃 프로파일을 지원함
- 타임아웃 시 사전 정의된 안내 문구가 반환됨
- 이전 버전과 신규 버전을 동시에 활성화할 수 있음
- 버전별 트래픽 비율을 설정할 수 있음
- 잘못된 가중치와 타임아웃을 시작 전에 차단함
- 상태 확인과 준비 상태 확인을 구분함
- 동시 요청 수와 대기열을 제한할 수 있음
- 버전별 지연시간과 오류율을 관찰할 수 있음
- 실패 시 회로 차단과 대체 응답이 동작함
- 입력·출력 스키마를 검증함
- 설정 체크섬과 추적 식별자를 기록함
- 검증된 이전 버전으로 롤백할 수 있음
- 필수 단위 테스트와 배포 전 점검표를 통과함
