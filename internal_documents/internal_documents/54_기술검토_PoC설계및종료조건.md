# PoC 설계·성공 기준·종료 조건
<!--meta: doc=DSC-04; doc_type=poc_standard; tier=1; topic=DISCOVERY; disclosure=internal; status=active-->

## PoC·파일럿·시범운영 용어 구분
<!--meta: sec=s1; dept=CNS|AIAX; level=주니어|시니어; ct_band=중; related=DSC-02#s1-->

PoC, 파일럿, 시범운영은 검증하려는 불확실성과 실제 업무 적용 수준이 서로 다르다. 고객이 사용하는 명칭을 그대로 채택하지 않고 대상 사용자, 데이터, 환경과 판정 기준을 확인한 뒤 용어를 확정한다. 타당성 검토 단계와의 관계는 DSC-02#s1을 참고한다.

### 용어별 적용 범위

| 구분 | PoC | 파일럿 | 시범운영 | 확인 초점 |
|---|---|---|---|---|
| 목적 | 핵심 기술 가설의 성립 여부 확인 | 제한된 업무 범위에서 효과와 운영 가능성 확인 | 운영 전환 직전의 절차·통제·수용성 확인 | 남아 있는 불확실성 |
| 대상 범위 | 단일 기능 또는 한정된 업무 유형 | 특정 부서·업무·사용자군 | 실제 운영 단위의 일부 | 범위 경계의 명확성 |
| 사용자 | 개발자, 업무 전문가, 지정 평가자 | 제한된 실제 사용자 | 운영 담당자와 실제 사용자 | 실제 업무 참여 수준 |
| 데이터 | 분리된 표본 또는 비식별 검증 데이터 | 승인된 실제 데이터의 제한 범위 | 운영 조건에 준하는 데이터 | 데이터 대표성과 통제 |
| 환경 | 격리된 검증 환경을 원칙으로 함 | 제한된 연동 또는 준운영 환경 | 운영 환경 또는 이에 준하는 환경 | 연동·권한·절차 현실성 |
| 판정 기준 | 기술 가설과 최소 업무 유용성 | 업무 지표, 운영 준비도, 복귀 가능성 | 운영 절차, 통제, 사용자 수용성 | 다음 단계 진입 가능성 |
| 통상 기간 | 범위 한정 시 6주 내외 | 6~12주를 기본 검토 범위로 함 | 업무 주기 1회 이상을 포함해 정함 | 측정에 필요한 최소 주기 |

통상 기간은 자동 승인 기간이 아니며 데이터 준비, 업무 주기와 승인 절차에 따라 조정한다. 인프라와 보안 제약은 DSC-05에서 검토하고 데이터 준비도는 DSC-03#s7의 판정을 따른다.

### 고객 용어 혼용 시 정렬 절차

1. 고객이 사용한 명칭과 기대 결과를 원문 그대로 회의 기록에 남긴다.
2. 실제 사용자 참여 여부와 실제 업무 처리 여부를 확인한다.
3. 학습·조정용 데이터와 평가용 데이터의 구분 가능성을 확인한다.
4. 운영 시스템 연동, 권한 부여와 업무 책임 변경 여부를 확인한다.
5. 검증하려는 불확실성을 기술, 업무 효과, 조직 수용성으로 분류한다.
6. 중단 시 기존 방식으로 복귀할 수 있는지 확인한다.
7. 위 표에 따라 헤드헌터랩 내부 용어를 제시하고 고객과 합의한다.
8. 합의되지 않으면 외부 명칭과 내부 관리 명칭을 병기한다.

### 유형 선택 기준

유형은 산출물의 외형이 아니라 가장 큰 불확실성에 따라 선택한다. 복수 불확실성이 있으면 선행 검증이 필요한 항목을 기준으로 시작하고 후속 단계 진입 조건을 별도로 둔다.

- 모델 또는 알고리즘의 작동 여부가 핵심이면 PoC를 선택한다.
- 정확도·응답시간 등 기술 성능의 최소선 확인이 우선이면 PoC를 선택한다.
- 현행 방식 대비 업무시간·오류·처리량 효과가 불확실하면 파일럿을 선택한다.
- 실제 사용자가 업무 절차 안에서 사용할 수 있는지 확인하려면 파일럿을 선택한다.
- 권한, 승인, 모니터링과 인수인계 절차의 현실성이 핵심이면 시범운영을 선택한다.
- 사용자 수용성과 교육 효과만 남아 있으면 시범운영을 우선 검토한다.
- 실제 운영에 영향을 주면서 복귀 경로가 없으면 세 유형 모두 착수하지 않는다.
- 기술과 업무 불확실성이 모두 높으면 PoC 완료 후 파일럿으로 분리한다.
- 명칭만 시범운영이고 평가 데이터가 고정 표본이면 실질에 따라 PoC로 기록한다.

### 문서 명기 규칙

1. 설계서 첫 페이지에 선택 유형을 하나만 주 유형으로 적는다.
2. 외부 명칭이 다르면 `고객 명칭 / 내부 관리 유형` 순서로 병기한다.
3. 선택 근거는 기술, 업무 효과, 조직 수용성 중 하나 이상으로 적는다.
4. 대상 사용자와 실제 업무 반영 수준을 각각 한 문장으로 적는다.
5. 시작일, 종료 예정일과 판정 회의 예정일을 날짜로 기재한다.
6. 후속 유형으로 자동 전환된다는 표현을 사용하지 않는다.
7. 유형 변경 시 변경일, 사유, 영향 범위와 승인자를 기록한다.
8. 유형 선택 결과는 설계서, 회의록과 측정 계획에서 동일하게 유지한다.

용어 확정 책임자는 CNS 과장 이상이며 AIAX 과장 이상이 기술 범위의 일치 여부를 확인한다. 합의된 유형은 성공 기준과 종료 판정 방식을 정하는 기준으로 사용한다.

## PoC 설계서 필수 항목
<!--meta: sec=s2; dept=CNS|AIAX; level=시니어; ct_band=상; related=DSC-03#s7-->

모든 PoC는 실행 전에 설계서를 작성하고 승인받는다. 구두 합의, 회의자료 또는 기능 목록만으로 착수하지 않는다. 데이터 준비도 등급과 선행 정비 조건은 DSC-03#s7의 결과를 인용한다.

### 필수 항목과 작성 기준

| 항목 | 필수 기재 내용 | 작성 기준 | 공란 금지 사유 | 책임 |
|---|---|---|---|---|
| 해결 대상 업무와 범위 경계 | 대상 업무, 포함·제외 기능, 사용자 범위 | 시작점과 종료점을 업무 단위로 특정 | 범위 확대와 판정 왜곡 방지 | CNS |
| 사용 데이터와 기간 | 출처, 추출 기간, 건수, 사용 승인 상태 | 학습·조정·평가 데이터를 구분 | 재현성과 적법한 사용 확인 필요 | DATA |
| 비교 대조군 | 현행 방식, 기준선 기간, 비교 단위 | 같은 업무 조건으로 비교 | 개선 여부를 판단할 기준 필요 | CNS |
| 실행 환경 | 배치 위치, 접근 권한, 연동 범위 | 확인·미확정 사항을 구분 | 측정 조건과 보안 제약 확인 필요 | AIAX |
| 참여 인원과 역할 | 고객·당사 담당자, 승인자, 평가자 | 이름 대신 역할과 책임을 우선 명시 | 의사결정과 작업 누락 방지 | CNS |
| 일정과 마일스톤 | 주차별 활동, 의존성, 판정일 | 완료 조건이 있는 일정으로 작성 | 단순 진행률 보고 방지 | CNS·AIAX |
| 산출물 | 모델 결과, 측정 기록, 사용 안내 등 | 제출 형식과 보관 위치 명시 | 결과물 기대 차이 방지 | AIAX |
| 측정 계획 | 지표, 산식, 표본, 측정 주체 | s3·s4 기준과 연결 | 사후 유리한 지표 선택 방지 | DATA |
| 종료 판정 회의 | 일시, 참석 역할, 의결 방식 | 착수 전에 예정일 지정 | 종료 지연과 무기한 연장 방지 | CNS |

설계서의 공란은 `미정`으로 대체하지 않는다. 착수에 필수적이지 않은 미확정 사항만 가정, 확인 기한, 확인 책임자와 영향 범위를 함께 적을 수 있다. 실행 환경의 상세 검토는 DSC-05를 따른다.

### 6주 기본 설계

1. 범위를 한정한 AI 개념검증은 6주 규모로 설계할 수 있다.
2. 1주차에는 범위 확정, 기준선 확인과 데이터 수령 검증을 완료한다.
3. 2주차에는 데이터 정제, 평가셋 분리와 초기 구현을 수행한다.
4. 3주차에는 핵심 기능 구현과 내부 검증을 수행한다.
5. 4주차에는 제한된 조정과 오류 유형 분석을 수행한다.
6. 5주차에는 동결된 평가셋으로 측정하고 업무 평가를 병행한다.
7. 6주차에는 결과 검토, 복귀 확인과 종료 판정 회의를 진행한다.
8. 각 주차 완료 조건이 충족되지 않으면 다음 주차 영향과 조치안을 기록한다.

### 기간 연장이 필요한 조건

- 업무 주기가 월 1회 이하라서 최소 1개 주기를 관찰할 수 없는 경우
- 승인된 데이터 확보에 10영업일을 초과하는 선행 절차가 있는 경우
- 망분리 환경에서 반입·설치·검수 절차가 별도로 필요한 경우
- 외부 시스템 연동 시험이 2개 이상이고 고객 작업 일정에 종속되는 경우
- 평가 표본이 최소 규모에 미달해 추가 수집 기간이 필요한 경우
- 고객 평가자가 3개 이상 업무 조직에 분산된 경우
- 규제·보안 검토 결과에 따라 실행 환경을 변경해야 하는 경우
- 연장 사유가 단순 기능 추가이면 기간 연장보다 범위 재승인을 우선한다.

### 승인과 변경 통제

1. 설계서 작성 책임자는 CNS 과장 이상으로 지정한다.
2. 기술 범위와 실행 가능성은 AIAX 과장 이상이 검토한다.
3. 데이터 항목과 측정 계획은 DATA 대리 이상이 검토한다.
4. 고객 측 업무 책임자가 대상 업무, 기준선과 평가 참여 방식을 확인한다.
5. 최종 내부 승인은 CNS 부장 또는 지정된 기술검토 책임자가 수행한다.
6. 승인 전 데이터 처리나 모델 조정을 시작하지 않는다.
7. 범위, 기간, 평가셋 또는 성공 기준 변경은 재승인 대상으로 본다.
8. 경미한 일정 이동도 종료 판정일에 영향을 주면 변경 이력에 남긴다.
9. 제안·가격 관련 사항은 설계서에서 확정하지 않고 소관 문서 계열로 이관한다.

승인본에는 문서 버전, 승인일, 승인 역할과 적용 시작일을 기록한다. 고객 확인이 지연되면 내부 승인만으로 실제 고객 데이터 사용이나 사용자 참여 단계를 진행하지 않는다.

## 성공 기준 정의 규칙
<!--meta: sec=s3; dept=CNS|AIAX; level=시니어; ct_band=상; related=DSC-02#s6-->

운영 전환 기준은 파일럿이 운영으로 넘어가기 전에 충족해야 하는 측정 가능한 조건이다. 해당 기준은 데모가 성공한 뒤 작성하지 않고 파일럿 시작 전에 확정한다. 대상 업무를 선택하는 회의에서 성공 기준 초안을 함께 작성한다.

### 지표 구성과 임계값

| 구분 | 지표 예시 | 임계값 설정 방식 | 판정 용도 | 유의 사항 |
|---|---|---|---|---|
| 기술 품질 | 정확도, 재현율, 근거 일치율 | 평가셋 기준 최소값 | 기술 가설 충족 확인 | 업무 효과를 대신하지 않음 |
| 기술 성능 | 응답시간, 처리 실패율 | 업무 허용시간과 부하 기준 | 사용 가능성 확인 | 평균값만 사용하지 않음 |
| 업무 효율 | 건당 처리시간, 자동 처리율 | 현행 기준선 대비 개선율 | 진행·중단 핵심 판단 | 동일 업무 조건으로 비교 |
| 업무 품질 | 재작업률, 오류율, 검수 통과율 | 허용 오류 수준 또는 개선율 | 진행·중단 핵심 판단 | 오류 영향도를 함께 기록 |
| 사용자 수용성 | 사용 완료율, 수정 빈도 | 지정 사용자군의 최소 비율 | 파일럿·시범운영 판단 | 만족도 단독 사용 금지 |
| 운영 준비도 | 담당자 지정, 모니터링 적용률 | 필수 항목 충족 비율 | 운영 전환 조건 | 기술 점수와 분리 |
| 위험 통제 | 민감정보 노출 건수, 금지 응답률 | 허용 건수 또는 0건 조건 | 즉시 중단 여부 | 표본과 탐지 절차 명시 |
| 복귀 가능성 | 복귀 소요시간, 미처리 건수 | 허용시간과 잔여 업무 한도 | 중단 실행 가능성 | 실제 절차로 확인 |

기술 지표와 업무 지표는 별도 항목으로 두고 각각 임계값을 정한다. 진행·중단 임계값은 정확도 자체가 아니라 처리시간, 오류, 재작업 등 대상 업무 지표에 연동한다. 효과 측정 가능성의 선행 판정은 DSC-02#s6을 따른다.

### 기준선 측정 절차

1. 대상 업무의 현행 처리 절차와 측정 단위를 확정한다.
2. 최근 4주 또는 업무 주기 1회 이상에서 기준선 자료를 수집한다.
3. 계절성, 담당자 숙련도와 예외 업무 포함 여부를 기록한다.
4. PoC 평가와 같은 모집단·단위·산식으로 기준선을 계산한다.
5. 평균과 함께 중앙값, 상위 오류 구간 또는 분포를 확인한다.
6. 고객 업무 책임자와 DATA 검토자가 기준선 수치를 확인한다.
7. 기준선 측정일, 원자료 위치와 계산 버전을 설계서에 연결한다.
8. 기준선 확정 후 성공 기준과 중단 임계값을 승인한다.

### 기준선이 없는 경우

- 원자료가 있으면 최대 5영업일의 표본 측정을 먼저 수행한다.
- 원자료가 없으면 대표 업무 30건 이상을 현행 방식으로 처리해 기준선을 만든다.
- 저빈도 업무는 최근 1개 업무 주기 전체를 사용하고 표본 한계를 명시한다.
- 현행 방식 재현이 불가능하면 고객 승인 목표값과 외부 요구조건을 구분해 적는다.
- 추정치만 존재하면 단일 값 대신 하한·기준·상한의 세 구간으로 기록한다.
- 기준선 신뢰도가 낮으면 확산 판정을 허용하지 않고 학습 목적 결과로 제한한다.
- 기준선 부재를 기술 지표로 대체하지 않는다.
- 기준선 확보가 불가능하고 업무 효과를 측정할 수 없으면 착수를 보류한다.

### 기준 변경과 지표 수 제한

1. 성공 기준은 평가 데이터의 결과를 확인한 뒤 유리하게 변경하지 않는다.
2. 법령·정책, 업무 범위 또는 데이터 모집단이 실질적으로 바뀐 경우에만 변경을 검토한다.
3. 측정 오류나 산식 결함이 확인되면 원인과 영향 표본을 제시한다.
4. 변경 전 수치, 변경 후 수치, 사유, 요청자와 승인일을 기록한다.
5. 변경은 CNS·AIAX 과장 이상과 고객 업무 책임자의 공동 확인을 받는다.
6. 핵심 업무 지표는 2~4개, 핵심 기술 지표는 2~4개로 제한한다.
7. 보조 지표는 최대 5개로 두며 종료 판정의 단독 근거로 사용하지 않는다.
8. 지표가 많아 상충하면 우선순위와 필수 통과 지표를 사전에 지정한다.

지표 수 제한은 측정 비용을 줄이기 위한 목적만이 아니라 판정 기준의 선택적 해석을 막기 위한 것이다. 종료 회의에서는 사전에 지정한 핵심 지표와 임계값을 우선 적용한다.

## 평가 데이터셋과 측정 절차
<!--meta: sec=s4; dept=AIAX|DATA; level=시니어; ct_band=상; related=DSC-03#s5-->

평가 데이터셋은 학습·조정 과정과 분리하고 실제 대상 업무의 유형과 난이도를 대표해야 한다. 평가셋 구성 책임과 측정 주체를 수행사에만 두지 않으며 고객 업무 담당자가 표본과 판정 기준을 확인한다. 라벨·정답 데이터 확보 가능성은 DSC-03#s5를 따른다.

### 평가셋 구성 기준

| 항목 | 기본 기준 | 최소선 | 확인 책임 | 금지 사항 |
|---|---|---|---|---|
| 학습·조정 분리 | 평가 사례와 정답을 별도 보관 | 중복 0건 | DATA | 평가 결과를 이용한 재조정 |
| 업무 유형 비중 | 실제 발생 비중을 반영 | 핵심 유형별 30건 이상 | 고객 업무 담당자 | 쉬운 유형만 선별 |
| 난이도 분포 | 일반·경계·예외 사례 포함 | 경계·예외 합계 20% 이상 | DATA·CNS | 실패 사례 임의 제외 |
| 전체 규모 | 지표 산식과 업무 위험에 맞춰 산정 | 총 200건 이상을 기본값으로 함 | DATA | 근거 없는 소표본 사용 |
| 시간 분포 | 서로 다른 날짜·업무 주기 포함 | 4주 또는 1개 업무 주기 | 고객 업무 담당자 | 특정 일자 편중 |
| 정답 품질 | 업무 기준에 따른 정답과 근거 보유 | 미확정 정답 5% 이하 | 고객 평가 책임자 | 모델 출력을 정답으로 사용 |
| 갱신 금지 | 평가 시작 전 데이터셋 동결 | 측정 종료까지 변경 금지 | AIAX | 불리한 표본 교체 |
| 식별·버전 | 사례 ID, 버전, 해시값 기록 | 모든 사례 추적 가능 | DATA | 원본 덮어쓰기 |

최소 200건은 범위 한정 PoC의 기본값이며 오류 비용, 유형 수와 통계적 불확실성에 따라 늘린다. 데이터가 200건 미만이면 전체 모집단 평가 또는 별도 승인된 소표본 평가를 사용하고 결과의 제한을 명시한다. 평가셋 갱신이 불가피하면 기존 세트를 보존하고 새 버전으로 재측정한다.

### 블라인드 평가 운영

1. 모델 출력과 비교 대조군 결과의 출처를 채점자에게 숨긴다.
2. 채점자는 고객 업무 전문가 2명 이상과 당사 DATA 또는 CNS 1명으로 구성한다.
3. 채점 기준서에는 등급 정의, 오류 유형과 경계 사례 예시를 포함한다.
4. 본 평가 전 20건 이상을 공동 채점해 기준 해석을 맞춘다.
5. 본 평가에서는 사례 순서를 무작위화하고 채점자별 기록을 분리한다.
6. 등급형 지표는 채점자 간 일치율 80% 이상을 기본선으로 둔다.
7. 일치율이 80% 미만이면 기준서를 보완하고 불일치 표본을 재채점한다.
8. 재채점은 최초 점수를 삭제하지 않고 변경 사유와 최종 합의를 함께 남긴다.
9. 이해관계가 직접 연결된 구현 담당자는 단독 최종 채점자가 될 수 없다.

### 고객 참여와 측정 통제

- 고객은 업무 유형 비중, 정답 기준과 허용 오류 수준을 확인한다.
- 고객 평가 책임자는 평가셋 동결 사실과 측정 개시일을 승인한다.
- 당사 AIAX는 실행 버전, 입력 조건과 출력 원본을 고정한다.
- DATA는 산식 적용, 중복 검사와 집계 재현성을 확인한다.
- CNS는 업무 지표 해석과 현행 대조군의 비교 가능성을 확인한다.
- 수행사 단독 측정은 유리한 표본 선택과 해석 편향 위험 때문에 허용하지 않는다.
- 고객이 직접 채점할 수 없으면 고객 지정 업무 전문가 또는 감사 역할이 표본을 검수한다.
- 고객 참여가 전혀 불가능하면 결과를 잠정치로 표시하고 확산 판정 근거로 사용하지 않는다.

### 결과 기록과 기준 결함 처리

1. 결과 기록에는 평가셋 버전, 실행 버전, 측정일과 측정자를 포함한다.
2. 지표별 산식, 분모·분자, 제외 건수와 제외 사유를 기록한다.
3. 사례별 입력, 출력, 정답, 채점자 점수와 오류 유형을 보존한다.
4. 원자료는 승인된 저장소에 읽기 전용으로 보관하고 접근 기록을 유지한다.
5. 집계 파일과 원자료의 연결 키를 보존하며 고객 식별 정보는 최소화한다.
6. 측정 중 기준 결함이 발견되면 해당 지표 판정을 즉시 보류한다.
7. 결함 영향 범위, 관련 사례와 기존 결과의 유효성을 공동 검토한다.
8. 기준서 수정 후 영향 표본 전체를 재채점하고 변경 전 결과도 보존한다.
9. 측정 결과가 기대와 다르다는 이유만으로 평가셋이나 채점 기준을 변경하지 않는다.

원자료 보관 기간과 열람 권한은 고객과 합의한 데이터 처리 조건을 따른다. 보관 조건이 확정되지 않으면 평가용 원자료를 임의 복제하거나 개인 저장공간에 두지 않는다.

## 네 가지 종료 상태
<!--meta: sec=s5; dept=CNS|AIAX; level=시니어; ct_band=상; related=DSC-06#s4-->

모든 PoC는 종료 판정일에 확산(Scale), 학습 지속(Continue Learning), 재설계(Redesign), 중단(Stop) 중 하나로 종료한다. 네 상태는 상호 배타적이며 복수 상태를 병기하지 않는다. 성공 기준과 운영 전환 기준은 대상 업무를 선정하는 회의에서 함께 확정한다.

진행·중단 임계값은 정확도 등 기술 벤치마크만으로 정하지 않고 처리시간, 재작업률, 업무량, 오류 건수 등 사전 합의한 업무 지표에 연결한다. 확산 판정은 제안·계약 또는 운영 전환을 자동 확정하지 않으며 DSC-06#s4의 후속 판단 근거로 사용한다.

| 종료 상태 | 진입 조건 | 필요한 증빙 | 후속 절차 | 필수 기록 |
|---|---|---|---|---|
| 확산(Scale) | 핵심 업무 지표와 운영 전환 기준을 모두 충족하고 중대한 미해결 위험이 없음 | 기준선 대비 결과, 반복 측정값, 사용자 확인, 운영 준비 점검표 | DSC-06#s4에 따라 추진 권고 여부를 검토하고 운영 후보 범위를 분리 | 충족 임계값, 적용 가능 범위, 잔여 위험, 책임자 |
| 학습 지속(Continue Learning) | 가설과 설계는 유효하나 사전 정의한 관측 기간·표본이 부족해 판정 불가 | 현재 측정값, 부족 표본 수, 추가 학습으로 해소 가능한 근거 | 기존 PoC를 종료하고 추가 학습 과제의 기간·질문·상한을 별도 승인 | 미확정 항목, 추가 증거량, 완료 예정일, 재판정일 |
| 재설계(Redesign) | 임계값을 충족하지 못했으나 원인이 특정되었고 범위·흐름·데이터·모델 변경으로 검증 가능 | 실패 구간 분석, 원인 가설, 변경 전후 비교 계획, 복귀 가능성 | 기존 PoC를 종료하고 변경된 가설과 성공 기준으로 새 설계서를 작성 | 실패 기준, 설계 변경점, 재사용 항목, 폐기 항목 |
| 중단(Stop) | 업무 효과가 없거나 위험을 허용선까지 낮출 수 없고 추가 검증의 실익이 없음 | 미달 지표, 위험 평가, 반복 실패 기록, 대안 비교 | 환경과 접근권한을 철수하고 데이터·산출물을 정해진 방식으로 처리 | 중단 사유, 철수 완료일, 보존·삭제 결과, 재개 금지 조건 |

### 종료 판정 회의

- 종료 판정 회의는 최종 측정 완료 후 3영업일 이내 개최한다.
- 필수 참석자는 CNS 책임자, AIAX 기술책임자, SALES 기회 담당자, 고객 업무지표 책임자로 한다.
- 데이터 평가가 핵심 근거이면 DATA 담당자 1명 이상을 포함한다.
- 연동 또는 배포 제약이 판정에 영향을 주면 BE 담당자를 포함한다.
- CNS 책임자는 업무 지표 충족 여부와 회의 진행을 책임진다.
- AIAX 책임자는 기술 증빙의 재현성과 한계가 기록되었는지 확인한다.
- 고객 업무지표 책임자는 기준선, 측정 결과, 업무 해석에 대한 확인 의견을 남긴다.
- 내부 종료 상태의 최종 결정권자는 해당 지점 CNS 부장으로 한다.

필수 참석자가 결석하거나 핵심 측정값의 출처를 확인할 수 없으면 상태를 임의 확정하지 않는다. 이 경우 회의를 5영업일 이내 다시 열되 PoC 수행은 추가하지 않는다. 재개최일까지 확인되지 않은 항목은 증거 부족으로 처리해 네 상태 중 하나를 결정한다.

### 판정 절차

1. 서기는 사전 확정한 성공 기준과 실제 측정값을 같은 단위로 제시한다.
2. CNS 책임자는 업무 지표별 충족·미달·측정 불가를 구분한다.
3. AIAX 책임자는 결과의 재현성, 평가 누수, 기술적 제한을 확인한다.
4. 참석자는 운영 전환 기준과 되돌릴 수 있는 복귀 경로를 확인한다.
5. 네 상태의 진입 조건을 확산부터 중단까지 순서대로 대조한다.
6. 의견이 갈리면 CNS 부장이 증빙 충족 여부를 기준으로 단일 상태를 결정한다.
7. 결정문은 회의 종료 후 1영업일 이내 참석자에게 배포한다.

### 필수 기록 항목

- PoC 식별번호와 대상 업무
- 시작일, 측정 종료일, 판정일
- 성공 기준의 기준선·목표값·실측값
- 운영 전환 기준별 충족 여부
- 평가 데이터와 측정 절차의 버전
- 선택한 종료 상태와 선택 근거
- 배제한 나머지 세 상태의 배제 사유
- 참석자, 확인 의견, 반대 의견
- 후속 책임자와 완료 예정일
- 환경 철수 또는 후속 검토 연결 상태

### 허용하지 않는 종료 표현

- 보류
- 추후 검토
- 잠정 성공
- 사실상 완료
- 고객 결정 대기
- 추가 논의 필요

모호한 표현은 공수 투입, 환경 유지, 데이터 보관의 종료 시점을 정하지 못하게 하므로 종료 상태로 인정하지 않는다. 외부 의사결정이 남아 있어도 PoC 자체는 네 상태 중 하나로 닫는다. 이후 상황이 변경되면 기존 기록을 수정하지 않고 새 검토 건으로 연결한다.

## 기간·공수 상한과 연장 승인
<!--meta: sec=s6; dept=CNS|AIAX; level=시니어; ct_band=중; related=SLS-01#s8-->

범위를 한정한 AI PoC의 기본 기간은 착수일부터 6주, 내부 투입 공수는 총 60인일 이하로 한다. 기본 배분 상한은 CNS 12인일, AIAX 36인일, BE·DATA 합계 12인일로 하며 역할별 조정은 총상한 안에서 허용한다. 고객 대기일과 환경 미제공 기간도 달력상 기간에 포함한다.

연장은 1회만 허용하며 최대 2주와 20인일 중 먼저 도달하는 값을 상한으로 한다. 따라서 연장 포함 총기간은 8주, 총공수는 80인일을 넘지 않는다. 연장 여부와 무관하게 최초 종료 예정일에는 현재까지의 측정 결과를 작성한다.

|---|---|---|---|
| 허용 | 사전 정의한 업무 관측 주기가 종료일 이후 완성됨 | 최초 설계서에 관측 주기와 필요 표본이 기재되어 있음 | 부족 기간만 연장 |

### 공수 산정 기준

- 1인일은 1명이 정상 근무일 기준으로 투입한 8시간으로 계산한다.
- 회의, 데이터 확인, 모델 실험, 평가, 문서화, 환경 철수를 모두 공수에 포함한다.
- 고객 대응 대기만 발생한 날은 공수에 넣지 않지만 전체 기간에는 포함한다.
- CNS는 업무 범위, 지표 정의, 사용자 확인, 종료 판정 공수를 기록한다.
- AIAX는 실험 구성, 모델 적용, 평가, 기술 문서화 공수를 기록한다.
- BE와 DATA는 실제 참여한 연동·데이터 점검 공수만 기록한다.
- 계획 대비 누적 공수가 80%에 도달하면 잔여 작업과 종료 가능성을 재점검한다.
- 주간 공수 기록은 매주 마지막 근무일까지 CNS 책임자에게 제출한다.

연장 요청은 최초 종료 예정일 5영업일 전까지 제출한다. 연장 요청 시 기존 성공 기준을 삭제하거나 낮추지 않으며 업무 지표, 기준선, 목표값, 측정 절차를 다시 확인한다. 측정 조건을 바꿔야 하면 연장이 아니라 재설계 종료 대상으로 판단한다.

### 연장 승인 절차

1. 수행 책임자는 연장 사유, 부족 증거, 추가 작업, 기간, 공수를 작성한다.
2. CNS 책임자는 추가 학습이 업무 판단에 필요한지 검토한다.
3. AIAX 책임자는 추가 기간 내 검증 완료 가능성과 기술 범위를 확인한다.
4. BE·DATA 추가 투입이 있으면 해당 부서 과장 이상 책임자의 동의를 받는다.
5. 해당 지점 CNS 부장이 기간과 공수 상한 안에서 연장을 승인한다.
6. 승인 결과는 최초 종료 예정일 3영업일 전까지 수행자에게 통보한다.
7. 두 번째 연장 요청은 접수하지 않고 네 가지 종료 상태 중 하나로 종결한다.

### 연장 요청 필수 항목

- 최초 설계서와 PoC 식별번호
- 현재 누적 기간과 부서별 누적 인일
- 최초 성공 기준의 변경 없음 확인
- 현재까지 확보한 측정값과 미확정 항목
- 연장이 필요한 직접 원인과 책임 구분
- 추가로 확보할 증거와 최소 표본 수
- 추가 기간과 역할별 인일
- 연장 종료일의 판정 회의 일정
- 연장 불승인 시 적용할 종료 상태

### 조직 영향 판단

- 연장 기간에 필요한 핵심 인력의 주별 배정률을 확인한다.
- 핵심 인력 배정률이 2주 연속 80%를 넘으면 인력 고정 위험으로 본다.
- 연장으로 다른 승인 업무의 시작이 5영업일 이상 늦어지면 기회 상실 위험을 기록한다.
- 대체 인력 투입 시 인수인계 공수가 3인일을 넘으면 총상한에 반영한다.
- SLS-01#s8의 계획 공수와 충돌하는지 해당 부서 책임자가 확인한다.
- 조직 영향의 최종 판단은 CNS 부장과 투입 부서 부장이 공동으로 한다.

기간·공수 상한을 넘겨 계속 수행하면 특정 인력이 고정되고 다른 기술 검토의 착수가 지연된다. 추가 학습의 가치보다 다른 기회의 지연 영향이 크면 연장을 승인하지 않는다. 총상한 이후 검증이 필요하면 기존 PoC를 종료하고 새 가설과 자원 계획으로 별도 검토한다.

## PoC 수행 조건과 산출물 취급
<!--meta: sec=s7; dept=CNS|AIAX; level=시니어; ct_band=상; related=SLS-05#s6-->

기술 검토 측은 착수 전에 투입 범위, 환경, 데이터, 산출물, 인계 형태, 철수 절차를 문서로 확정한다. 수행 조건이 확인되지 않은 상태에서 시연 일정부터 정하거나 개발을 시작하지 않는다. 데이터 준비도는 DSC-03, 아키텍처·인프라 제약은 DSC-05를 따른다.

유상·무상 여부, 가격, 계약 조건, 권리 귀속의 최종 결정은 제안·가격 소관 문서 계열에서 처리한다. 이 섹션에서는 해당 결정을 내리는 데 필요한 기술 범위와 자원 정보를 식별하며 금액이나 계약 문안을 작성하지 않는다.

| 환경 철수 | 계정 폐기, 자원 삭제, 데이터 반환·삭제 절차 | 철수 점검표 | AIAX·BE | 종료 승인 전 보완 |

### 투입 및 환경 조건

- 내부 수행자는 부서 코드와 직급, 역할, 예정 인일을 기록한다.
- 고객 측 업무 책임자와 기술 연락 창구를 각각 1명 이상 지정한다.
- 고객 환경 제공 여부와 헤드헌터랩 임시 환경 사용 여부를 구분한다.
- 계정 발급 목표일은 착수일보다 최소 2영업일 앞서 정한다.
- 외부 접속, 파일 반출, 이동식 매체 사용 제한을 사전에 확인한다.
- 라이선스가 필요한 도구는 명칭, 사용 기간, 제공 주체만 기록한다.
- 운영 시스템 직접 변경은 PoC 범위에서 원칙적으로 제외한다.
- 예외적으로 연동하면 복귀 절차와 변경 승인자를 지정한다.

산출물은 PoC 목적의 검증 결과와 재현에 필요한 최소 자료로 한정한다. 인계 가능 여부와 인계 형식은 별도 항목으로 구분하며 소스, 모델, 설정, 데이터가 모두 같은 방식으로 제공된다고 간주하지 않는다. 제3자 구성요소가 포함되면 명칭, 버전, 사용 조건, 재배포 제한을 기록한다.

### 제안·가격 판단에 제공할 정보

- 부서별 예상 인일과 역할 구성
- 컴퓨팅 자원의 종류, 수량, 예상 사용 기간
- 별도 라이선스가 필요한 구성요소
- 고객 제공 환경과 당사 준비 환경의 구분
- 데이터 정비·가명처리·이관 작업의 유무
- 소스, 모델, 문서별 인계 요청 형태
- 종료 후 지원 또는 유지 요청의 범위와 기간
- 환경 철수와 데이터 삭제에 필요한 공수
- 제3자 권리 또는 재배포 제한 항목

### 산출물 취급 기준

- 각 산출물에 작성자, 작성일, 버전, 열람 범위를 표시한다.
- 원본 데이터와 평가용 파생 데이터는 산출물 목록에서 분리한다.
- 소스는 저장소 내보내기, 압축 패키지, 실행 이미지 중 형태를 명시한다.
- 모델은 가중치, 호출 설정, 프롬프트, 평가 코드 제공 여부를 각각 표시한다.
- 실행에 필요한 비밀키와 개인 계정 정보는 인계 대상에 포함하지 않는다.
- 제공이 제한된 항목은 대체 문서 또는 재현 절차의 제공 가능성을 기록한다.
- 인계 시 파일 해시 또는 저장소 태그로 대상 버전을 고정한다.
- 수령 확인자는 항목별 수령 여부와 열람 가능 여부를 기록한다.
- 종료 후 보존 기간이 지나면 정해진 삭제 절차를 수행한다.
- 철수 완료 기록은 종료 판정 기록과 같은 위치에 연결한다.

### 공개·레퍼런스 활용 확인

- 고객 식별정보 공개 동의 여부
- 고객 명칭·로고 사용 가능 여부
- 과제명과 업무 영역 공개 가능 범위
- 측정 수치와 전후 비교 결과 공개 가능 범위
- 화면 이미지, 도표, 산출물 일부 사용 가능 여부
- 익명화 또는 범주화가 필요한 표현
- 공개 채널, 공개 기간, 사전 검수 절차

공개나 레퍼런스 활용은 수행 동의와 분리해 서면으로 확인한다. 동의가 없거나 범위가 불명확하면 외부 발표, 영업 자료, 웹 게시물에 사용하지 않는다. 내부 열람도 승인된 목적과 범위 안에서만 허용하며 기존 레퍼런스의 상세 내용은 관련 문서 ID로만 연결한다.

## PoC 환경 구성과 데이터 처리 준수
<!--meta: sec=s8; dept=AIAX|BE; level=시니어; ct_band=상; related=DSC-05#s5-->

PoC 환경은 검증 목적, 데이터 민감도, 고객사 망 정책, 기존 시스템 연동 범위에 따라 선택한다. 편의성만을 이유로 운영 환경을 직접 사용하지 않으며, 상세 인프라 제약과 용량 조건은 DSC-05#s5를 따른다. 환경 준비가 완료되기 전에는 고객 데이터를 반입하지 않는다.

| 구성 선택지 | 적용 조건 | 분리 원칙 | 표준 준비 기간 | 주요 확인 사항 |
|---|---|---|---:|---|
| 사내 격리 개발환경 | 비식별·합성 데이터로 검증 가능 | 업무망·운영계와 계정 및 저장소 분리 | 3~5영업일 | 반입 승인, 저장 위치, 외부 통신 |
| 고객사 개발환경 | 고객사 내부 데이터 접근이 필요 | 운영 DB 직접 연결 금지, 복제본 사용 | 5~10영업일 | 계정 발급, 방화벽, 개발 도구 반입 |
| 고객사 검증환경 | 기존 시스템 연동 검증이 핵심 | 운영 인터페이스와 별도 엔드포인트 사용 | 10~15영업일 | 연동 명세, 호출 제한, 장애 격리 |
| 별도 클라우드 환경 | 단기간 자원 증설과 실험 반복이 필요 | 전용 프로젝트·네트워크·키 사용 | 5~10영업일 | 리전, 암호화, 로그, 반출 경로 |
| 폐쇄망·망분리 환경 | 외부 통신과 데이터 반출이 제한됨 | 승인된 반입 매체와 내부 저장소만 사용 | 15~25영업일 | 보안 심사, 패키지 반입, 모델 배포 방식 |
| 외부 모델 API 연계환경 | 외부 추론 서비스 사용이 허용됨 | 중계 계층을 두고 원문 전송을 제한 | 7~15영업일 | 전송 데이터, 보존 정책, 장애 시 대체 경로 |

준비 기간은 고객사 승인 대기와 장비 조달 기간을 제외한 기준값으로 기록한다. 실제 준비 기간이 상한을 5영업일 이상 초과할 것으로 예상되면 원인, 일정 영향, 대체 환경 가능 여부를 설계서에 갱신한다.

### 데이터 반입과 분리 원칙

- PoC 데이터는 성공 기준 측정에 필요한 최소 필드와 최소 기간만 반입한다.
- 필드별 필요 근거를 기록하며, 사용 목적이 없는 식별자와 원문 첨부파일은 제외한다.
- 운영 데이터 원본은 변경하지 않고 승인된 복제본 또는 추출본을 사용한다.
- 운영 저장소와 PoC 저장소는 프로젝트, 경로, 데이터베이스 또는 버킷 단위로 분리한다.
- PoC 처리 결과를 운영 시스템에 자동 반영하지 않으며 별도 승인된 인터페이스만 사용한다.
- 학습용, 평가용, 시연용 데이터는 논리적으로 분리하고 혼합 이력을 남긴다.
- 데이터 추가 반입은 최초 승인 범위와 비교한 뒤 DATA 또는 고객 데이터 책임자의 확인을 받는다.

### 가명처리와 접근 통제

- 가명처리는 원본 추출 후 PoC 환경 반입 전에 적용하는 것을 원칙으로 한다.
- 반입 전 처리가 불가능하면 격리 구역에서 처리하고 가명처리 전 데이터의 저장 시간을 기록한다.
- 직접 식별자는 삭제·치환하고, 간접 식별자는 결합 가능성을 검토해 범주화 또는 마스킹한다.
- 재식별 키가 필요한 경우 PoC 저장소와 분리하며 지정 관리자 1인 이상에게만 접근을 허용한다.
- 개인 공용 계정과 팀 공용 계정을 사용하지 않고 사용자별 계정을 발급한다.
- 권한은 역할별 최소 범위로 부여하고 30일마다 또는 참여자 변경 시 재검토한다.
- 퇴사·전배·철수 인력의 권한은 통보 후 1영업일 이내 회수한다.

### 로그와 종료 처리

- 로그인, 데이터 조회·다운로드, 모델 실행, 결과 반출, 권한 변경을 작업 로그로 남긴다.
- 로그에는 수행자, 시각, 대상, 작업 유형, 성공 여부를 포함한다.
- 작업 로그는 PoC 종료 후 90일 이상 보존하되 고객사 정책이 더 엄격하면 해당 정책을 따른다.
- 원본 데이터와 중간 산출물의 보존 위치 및 삭제 예정일을 데이터 목록에 연결한다.
- 종료 후 5영업일 이내 저장소, 임시 파일, 캐시, 로컬 사본의 삭제 여부를 점검한다.
- 법정·감사상 보존이 필요한 자료는 삭제 대상에서 분리하고 근거와 보존 기한을 기록한다.
- 삭제 완료 확인서에는 대상, 위치, 삭제 방식, 수행자, 검토자, 완료일을 기재한다.
- 백업본의 즉시 삭제가 불가능하면 접근 차단일과 최종 파기 예정일을 확인서에 적는다.

### 외부 모델 API 사전 확인

- 전송되는 필드와 프롬프트에 개인정보·기밀정보가 포함되는지 확인한다.
- 입력·출력 데이터의 저장 여부, 저장 위치, 보존 기간, 학습 재사용 여부를 확인한다.
- 데이터 처리 지역과 국외 이전 가능성은 고객 담당자와 사전에 확인한다.
- API 제공자의 하위 처리자 사용 여부와 변경 통지 방식을 확인한다.
- 전송 암호화, 인증키 보관, 호출 권한, 키 교체 주기를 합의한다.
- 호출 로그에 원문을 남길지 여부와 마스킹 적용 지점을 정한다.
- 호출량 제한, 응답 지연, 서비스 중단 시 시험 중지 또는 대체 경로를 정한다.
- 모델 버전 변경 통지와 평가 결과 재현에 필요한 버전 고정 가능성을 확인한다.
- 확인되지 않은 항목은 추정값으로 대체하지 않고 미확정 상태와 확인 책임자를 기록한다.

외부 모델 API 사용 승인은 기술 적합성만으로 판단하지 않는다. 고객사의 데이터 처리 정책과 필요한 내부 검토가 완료된 범위에서만 호출하며, 합의 범위를 벗어난 데이터는 전송하지 않는다.

## 운영 전환 준비와 되돌릴 수 있는 설계
<!--meta: sec=s9; dept=AIAX|CNS; level=시니어; ct_band=상; related=DSC-02#s9-->

파일럿은 중단 시 기존 업무 방식으로 복귀할 수 있도록 설계한다. 복귀 경로가 없는 설계는 중단 선택지를 사실상 제거하므로 되돌릴 수 있음(reversibility)을 필수 요구 조건으로 둔다. 복귀 가능 여부는 기능 구현 완료가 아니라 업무, 데이터, 권한, 사용자 전환을 포함해 판단한다.

### 운영 전환과 복귀 설계 기준

| 구분 | 사전 확정 항목 | 최소 기준 | 확인 시점 | 기록 책임 |
|---|---|---|---|---|
| 기존 절차 병행 | 병행 대상, 담당자, 종료 조건 | 파일럿 안정화 후 최소 10영업일 유지 | 파일럿 시작 전 | CNS |
| 데이터 원복 | 원본 보존, 변경분 식별, 복원 순서 | 복원 시험 1회와 결과 기록 | 연동 개시 전 | BE |
| 권한 회수 | 계정·역할·키·토큰 목록 | 중단 결정 후 1영업일 이내 회수 | 계정 발급 전 | AIAX |
| 사용자 복귀 | 기존 절차 안내와 문의 창구 | 복귀 안내문 및 교육 자료 확보 | 사용자 투입 전 | CNS |
| 인터페이스 차단 | 호출 중지 순서와 의존 시스템 | 단독 차단 시험 1회 수행 | 파일럿 개시 전 | BE |
| 결과물 격리 | 자동 반영 차단과 수동 검토 | 운영 반영 전 승인 단계 1개 이상 | 결과 생성 전 | AIAX |
| 책임자 지정 | 복귀 결정자와 실행 담당자 | 결정자 1인, 기능별 담당자 지정 | 설계 승인 전 | CNS |

복귀 절차는 비상 상황에서 처음 작성하지 않으며 파일럿 설계서에 시작 조건과 함께 포함한다. 복귀 시험을 수행할 수 없는 경우 그 제약, 수동 복구 절차, 예상 복구 시간을 기록하고 별도 게이트에서 수용 여부를 판단한다.

### 복귀 경로 필수 항목

- 기존 절차의 병행 유지 기간과 종료 승인자를 정한다.
- AI 결과를 사용하지 않아도 업무를 처리할 수 있는 대체 절차를 유지한다.
- 자동화 이전 데이터와 파일럿 중 생성된 변경 데이터를 구분한다.
- 데이터 원복 단위, 복원 순서, 검증 쿼리 또는 대조 방법을 정한다.
- 운영 데이터에 쓰기가 발생하면 변경 이력과 원복 키를 남긴다.
- 모델, 애플리케이션, 데이터 저장소의 계정과 권한 목록을 작성한다.
- 중단 시 회수할 API 키, 토큰, 서비스 계정, 사용자 역할을 구분한다.
- 사용자에게 복귀 결정, 적용 시각, 처리 방법을 통지하는 경로를 정한다.
- 기존 절차가 변경된 경우 복귀 교육을 1회 이상 실시하고 참석자를 기록한다.
- 복귀 완료 후 미처리 건과 중복 처리 건을 확인하는 업무 점검을 수행한다.

### 운영 전환 준비 점검

- 운영 인수 부서와 운영 책임자를 파일럿 시작 전에 후보로 지정한다.
- 운영 책임자가 없으면 확산(Scale) 종료 상태를 선택하지 않는다.
- 서비스 상태, 응답 시간, 오류율, 업무 처리량의 모니터링 항목을 정의한다.
- 업무 영향이 큰 오류에 대해 경보 임계값과 통보 대상을 정한다.
- 장애 등급, 최초 대응 시간, 우회 절차, 복구 확인자를 기록한다.
- 모델 성능 저하와 데이터 분포 변화의 점검 주기를 정한다.
- 재학습 필요 조건, 승인자, 평가셋 재검증 절차를 마련한다.
- 월별 호출량, 컴퓨팅 사용량, 저장량과 단위당 비용 추이를 기록한다.
- 비용이 기준 대비 20% 이상 증가하면 원인 분석과 사용량 재산정을 수행한다.
- 사용자 문의, 결과 이의제기, 수동 수정 기록의 접수 경로를 정한다.
- 운영 문서, 계정 목록, 배포 절차, 점검표의 인수 완료 여부를 확인한다.

### 운영 전환 기준의 사전 정의

- 운영 전환 기준은 대상 업무를 선정하는 회의에서 성공 기준과 함께 작성한다.
- 데모 성공 후에 전환 기준을 추가하지 않으며 변경 시 사유와 승인자를 남긴다.
- 진행·중단 임계값은 모델 정확도만이 아니라 처리시간, 재작업률, 오류 건수 등 업무 지표에 연결한다.
- 각 지표에는 기준선, 목표값, 측정 기간, 표본 수, 측정 주체를 기재한다.
- 전환 기준을 충족해도 보안·인프라·운영 인수 조건이 미확정이면 자동 전환하지 않는다.
- 파일럿 종료 상태는 확산, 학습 지속, 재설계, 중단 중 하나로만 확정한다.
- 학습 지속을 선택하면 미확인 가설과 추가 측정 기간을 명시한다.
- 재설계를 선택하면 변경 범위와 기존 결과의 재사용 가능 여부를 기록한다.
- 중단을 선택하면 복귀 절차를 실행하고 완료 확인자를 지정한다.

운영 전환 결정 전이라도 모니터링 정의, 장애 연락망, 권한 회수표, 복귀 안내문, 데이터 원복 절차는 미리 준비한다. 준비 행위는 전환 승인을 의미하지 않으며, 최종 판단은 사전에 정한 종료 상태와 운영 전환 기준에 따라 별도로 기록한다.

## PoC 실패 유형과 사전 차단 장치
<!--meta: sec=s10; dept=CNS|AIAX; level=시니어; ct_band=상; related=SLS-06#s6-->

PoC 실패는 모델 성능 미달만을 의미하지 않는다. 판단 기준이 없거나 결과를 재현·설명할 수 없어 종료 상태를 선택하지 못한 경우도 실패로 기록한다. 실패 유형별 조기 징후를 설계 단계에서 확인하고 게이트와 기록 의무로 차단한다.

### 실패 유형별 통제

| 실패 유형 | 조기 징후 | 사전 차단 장치 | 적용 게이트 | 필수 기록 |
|---|---|---|---|---|
| 성공 기준 미합의 | 목표값·측정 기간·승인자 중 하나가 공란 | 성공 기준표 공동 검토와 서명 | 착수 승인 | 기준선, 목표값, 승인자 |
| 평가셋 오염 | 학습 데이터와 평가 데이터의 출처·기간이 겹침 | 데이터 분할 고정과 해시 기록 | 학습 개시 | 데이터 버전, 분할 규칙, 해시 |
| 대조군 없음 | 개선 전 기준선이 없거나 비교 방식이 수시 변경됨 | 기존 방식 측정 또는 고정 비교군 설정 | 평가 개시 | 대조군 정의, 표본 수, 측정일 |
| 범위 확대 | 신규 업무·연동·사용자 요청이 연속 추가됨 | 범위 동결표와 변경 게이트 운영 | 주간 점검 | 변경 요청, 영향, 승인·보류 결과 |

게이트 미통과 항목은 관행적으로 면제하지 않는다. 예외가 필요한 경우 영향, 임시 통제, 해소 기한, 승인자를 기록하며 해소 기한이 지난 예외는 다음 게이트에서 다시 심사한다.

### 공통 차단 절차

- 착수 승인 전 성공 기준표의 공란 수가 0건인지 확인한다.
- 평가셋은 최초 확정 후 읽기 전용으로 보관하고 변경 이력을 남긴다.
- 평가셋 변경 시 기존 결과와 신규 결과를 같은 표에 병기한다.
- 기준선 측정이 불가능하면 대체 비교 방식과 해석 한계를 승인받는다.
- 범위 변경 요청은 구두 지시로 반영하지 않고 요청 번호를 부여한다.
- 변경으로 일정이 5영업일 이상 늘어나면 종료 조건을 재검토한다.
- 데이터 제공이 3영업일 이상 지연되면 대체 데이터 또는 일정 중지를 판단한다.
- 측정 수행자와 결과 승인자를 가능하면 서로 다른 인원으로 지정한다.
- 업무 효과는 최소 1개의 처리시간·오류·재작업·처리량 지표와 연결한다.
- 운영 인수 후보가 철회되면 확산 판단을 보류하고 다른 종료 상태를 검토한다.
- 주간 점검마다 조기 징후의 발생 여부를 정상·주의·차단 3등급으로 기록한다.

### 실패 종료 기록의 자산화

- 종료 상태는 확산, 학습 지속, 재설계, 중단 중 하나로 확정한다.
- 실패 원인은 직접 원인, 기여 요인, 통제 실패로 구분해 기록한다.
- 최초 조기 징후 발생일과 실제 대응일의 차이를 영업일로 계산한다.
- 미통과 게이트와 예외 승인 내역을 종료 보고서에 연결한다.
- 재사용 가능한 평가 산식, 질문, 점검 항목만 일반화해 별도 등록한다.
- 고객사 식별 정보, 원본 데이터, 화면 캡처는 자산화 자료에서 제거한다.
- 모델 출력 예시는 재식별 가능성과 이용 범위를 확인한 뒤 포함 여부를 정한다.
- 후속 PoC에 적용할 금지 조건과 필수 선행 조건을 각각 1건 이상 작성한다.
- 관련 영업 활동의 디브리핑 연결은 SLS-06#s6을 참고한다.
- 기존 레퍼런스는 문서 ID 또는 명칭만 연결하고 수행 내용을 재서술하지 않는다.

### 반복 실패와 기준 개정

- 동일 실패 유형이 최근 6개월 내 2건 발생하면 기준 개정 검토를 개시한다.
- 동일 게이트 누락이 최근 3건 중 2건 이상이면 양식의 필수 입력 통제를 검토한다.
- CNS는 반복 패턴과 업무 영향, AIAX는 기술 통제 가능성을 각각 작성한다.
- DATA·BE 관련 원인이 있으면 해당 부서 검토 의견을 추가한다.
- 개정안에는 변경 대상 항목, 예상 차단 효과, 적용일, 기존 PoC 처리 방식을 포함한다.
- 개정 전 진행 중인 PoC에는 소급 적용 여부를 위험 수준에 따라 따로 결정한다.
- 개정 후 최초 3건의 PoC에서 누락 건수와 예외 발생 건수를 점검한다.
- 효과가 확인되지 않으면 임계값, 게이트 위치 또는 기록 양식을 다시 조정한다.

기준 개정은 개별 담당자의 주의 강화만으로 종결하지 않는다. 반복 실패가 설계서 구조, 승인 절차, 측정 방식에서 비롯된 경우 해당 통제를 문서와 양식에 반영하고 개정 이력을 남긴다.
