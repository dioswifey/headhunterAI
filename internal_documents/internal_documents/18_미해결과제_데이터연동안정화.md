# 고객사 시스템 데이터 연동 안정화 과제
<!--meta: doc=ISS-01; doc_type=open_challenge; tier=1; topic=TECH; disclosure=internal; status=resolved; related=PRJ-CC-DET|PRJ-FC-DET-->

## 현황
<!--meta: sec=s1; dept=BE|DE; level=시니어; ct_band=상; related=s2|s4|s6-->
<!--forbid: 대한전자|한빛유통|ISS-->
콜센터 AI 상담, 수요예측 대시보드 모두 고객사 내부 시스템(CRM, ERP)과 데이터를 주고받는데, 고객사마다 API 형식·인증 방식·장애 시 재시도 정책이 달라 연동 코드가 프로젝트마다 중복 작성되고 있습니다. 한 고객사의 API가 사전 공지 없이 바뀌어 연동이 끊긴 사례도 있었습니다.

현재 연동 구현은 각 프로젝트의 일정과 고객사 환경에 맞춰 개별 최적화되어 있습니다. 이 방식은 초기 구축 속도에는 유리하지만, 운영 단계에서 다음 문제가 반복됩니다.

- 같은 의미의 고객·상담·상품·주문 데이터를 프로젝트마다 서로 다른 내부 객체로 변환합니다.
- HTTP 상태 코드가 같아도 고객사별 오류 의미가 달라 공통 대응이 어렵습니다.
- 인증 토큰 발급, 갱신, 만료 처리 코드가 서비스별로 분산되어 있습니다.
- 타임아웃과 재시도 횟수가 개발자 판단에 따라 달라집니다.
- 고객사 응답 필드가 추가·삭제·변경되어도 실제 처리 실패 전까지 발견하지 못하는 경우가 있습니다.
- 장애 복구 과정에서 어느 데이터까지 정상 반영되었는지 빠르게 확인하기 어렵습니다.
- 신규 프로젝트가 시작될 때 기존 연동 코드를 복사한 뒤 수정하는 관행이 남아 있습니다.
- 운영 인수인계 시 고객사별 예외 조건이 코드와 담당자 경험에만 남는 경우가 있습니다.

이 과제는 특정 프로젝트의 단일 장애를 수정하는 작업이 아니라, 여러 고객사 시스템과 연결되는 백엔드 연동 계층을 공통 자산으로 전환하는 중장기 기술 과제입니다.

## 해결해야 할 것
<!--meta: sec=s2; dept=BE|DE; level=시니어; ct_band=상; related=s1|s6|s23-->
<!--forbid: 대한전자|한빛유통|ISS-->
- 공통 연동 어댑터 구조 설계(고객사별 차이는 어댑터 하나로 흡수)
- 고객사 API 변경 감지(응답 형식 변화) 시 조기 경보 체계
- 연동 실패 시 재시도·대체 동작 정책을 프로젝트마다 다시 정의하지 않도록 표준화

추가로 다음 항목을 공통 설계 범위에 포함해야 합니다.

- 인증, 요청 서명, 토큰 갱신과 같은 접속 절차 표준화
- 내부 표준 데이터 모델과 고객사 데이터 모델 간 변환 규칙 관리
- 중복 요청과 중복 반영을 방지하는 멱등성 보장 방식
- 동기 API와 비동기 파일·메시지 연동을 함께 수용할 수 있는 확장 구조
- 장애 격리를 위한 타임아웃, 회로 차단, 호출량 제한 정책
- 실패 데이터를 유실하지 않고 재처리할 수 있는 보관 구조
- 요청·응답 추적에 필요한 공통 로그와 상관관계 식별자
- 고객사별 설정값과 비밀정보를 코드에서 분리하는 방법
- 어댑터 버전, 계약 버전, 배포 버전을 구분하는 변경관리 절차
- 프로젝트팀이 공통 모듈을 채택하기 위한 문서·예제·검증 도구 제공

완료 기준은 공통 라이브러리를 만드는 것에 그치지 않습니다. 신규 고객사 연동을 추가할 때 핵심 실행 엔진을 수정하지 않고도 고객사별 어댑터와 설정을 등록할 수 있어야 하며, 장애가 발생했을 때 운영자가 코드 분석 전에 원인 범주와 재처리 가능 여부를 판단할 수 있어야 합니다.

## 담당
<!--meta: sec=s3; dept=BE|DE; level=시니어; ct_band=하; related=s21|s22-->
<!--forbid: 대한전자|한빛유통|ISS-->
백엔드팀 시니어 엔지니어 중심으로 2026년 4분기 내 공통 어댑터 설계안 마련 예정.

백엔드팀은 공통 인터페이스, 실행 정책, 오류 체계와 운영 도구의 기술 책임을 맡습니다. 다른 부서는 다음 방식으로 검토에 참여합니다.

- 컨설팅팀: 고객사 업무 흐름, 연동 제약, 승인 절차와 예외 업무 확인
- AI/AX개발팀: AI 서비스가 요구하는 입력·출력 계약과 지연 허용 범위 검토
- 데이터분석팀: 분석용 데이터의 완전성, 시점 일관성, 재처리 요구사항 검토
- 영업팀: 제안·계약 단계에서 확인해야 할 연동 전제조건 정리
- 프로젝트별 운영 담당자: 기존 장애 유형, 수작업 복구 절차, 고객사 연락 체계 제공

설계안 확정 전까지 프로젝트별 신규 연동 개발은 계속 가능하나, 새로 발견된 예외 조건과 인증 방식은 공통 과제 목록에 등록하여 후속 설계에서 누락되지 않도록 합니다.

## 과제 범위와 제외 범위
<!--meta: sec=s4; dept=BE|DE; level=주니어; ct_band=중; related=s1|s5|s23-->
<!--forbid: 대한전자|한빛유통|ISS-->
과제 범위는 고객사 시스템과 헤드헌터랩 서비스 사이의 데이터 교환 경계입니다.

포함 범위:

- REST API, 파일 전송, 메시지 기반 연동을 위한 공통 실행 구조
- 요청 생성, 인증, 전송, 응답 검증, 데이터 변환, 오류 분류
- 재시도, 지연 실행, 실패 보관, 수동 재처리
- 스키마 변화 감지와 호환성 판정
- 연동 상태 관측을 위한 로그, 지표, 추적 정보
- 어댑터 개발·테스트·배포·폐기 절차
- 고객사별 연결 설정과 운영 정책 관리
- 개인정보 최소 수집 및 로그 마스킹

제외 범위:

- 고객사 CRM 또는 ERP 자체 기능 개선
- 고객사 내부 네트워크 장비 운영
- AI 모델의 품질 개선이나 추론 로직 변경
- 수요예측 알고리즘 및 분석 모델 재설계
- 프로젝트 화면 기능과 사용자 경험 개편
- 고객사 데이터의 업무상 정합성을 대신 보증하는 작업

연동 계층은 전달받은 데이터의 구조와 전송 결과를 검증하지만, 고객사 원천 데이터가 실제 업무 사실과 일치하는지까지 자동으로 보증하지 않습니다.

## 핵심 용어
<!--meta: sec=s5; dept=BE|DE; level=주니어; ct_band=하; related=s4|s6|s8-->
<!--forbid: 대한전자|한빛유통|ISS-->
- **커넥터**: 네트워크 연결, 인증, 프로토콜 처리처럼 외부 시스템과 통신하는 공통 구성요소
- **어댑터**: 고객사별 API와 내부 표준 인터페이스 사이의 차이를 변환하는 구성요소
- **내부 표준 모델**: 프로젝트와 고객사에 종속되지 않도록 정의한 공통 데이터 표현
- **계약**: 요청 필드, 응답 필드, 타입, 필수 여부, 오류 의미를 합의한 규칙
- **스키마 드리프트**: 사전 합의 없이 필드, 타입, 구조 또는 값의 범위가 달라지는 현상
- **멱등성**: 동일 요청을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같도록 하는 성질
- **재시도 가능 오류**: 일정 시간 후 같은 요청을 다시 보내면 성공할 가능성이 있는 오류
- **영구 오류**: 입력 수정이나 계약 변경 없이는 재시도해도 성공하기 어려운 오류
- **회로 차단**: 반복 실패 시 외부 호출을 일시 중지하여 장애 확산을 막는 방식
- **격리 보관소**: 자동 재처리할 수 없는 실패 데이터를 원인 정보와 함께 보관하는 영역
- **상관관계 식별자**: 한 데이터 처리 흐름을 여러 서비스와 로그에서 연결해 찾기 위한 값
- **호환성**: 기존 소비자나 제공자를 수정하지 않고 변경된 계약을 계속 사용할 수 있는 정도

## 목표 아키텍처 개요
<!--meta: sec=s6; dept=BE|DE; level=시니어; ct_band=상; related=s2|s7|s8|s12-->
<!--forbid: 대한전자|한빛유통|ISS-->
목표 구조는 업무 서비스, 공통 연동 실행 계층, 고객사별 어댑터, 외부 시스템의 네 영역으로 구분합니다.

1. 업무 서비스는 `고객 조회`, `상담 결과 전달`, `재고 수신`과 같은 내부 표준 명령을 호출합니다.
2. 공통 연동 실행 계층은 타임아웃, 재시도, 회로 차단, 추적, 감사 로그를 일관되게 적용합니다.
3. 고객사별 어댑터는 내부 표준 명령을 외부 API 요청으로 바꾸고 응답을 내부 표준 결과로 변환합니다.
4. 커넥터는 실제 프로토콜 통신과 인증 헤더 적용을 담당합니다.
5. 검증기는 응답 스키마, 필수 필드, 허용 값과 데이터 크기를 확인합니다.
6. 정책 엔진은 오류 유형과 업무 중요도에 따라 재시도, 보류, 대체 동작을 결정합니다.
7. 실패 저장소는 재처리 가능한 원문과 처리 이력을 보존합니다.
8. 관측 계층은 성공률, 지연시간, 연속 실패, 스키마 차이를 수집합니다.

업무 서비스는 고객사별 URL, 토큰 형식, 원본 오류 코드에 직접 의존하지 않아야 합니다. 반대로 어댑터는 AI 추론이나 분석 계산 같은 프로젝트 핵심 업무를 수행하지 않아야 합니다. 이 경계를 지켜야 공통 계층이 지나치게 비대해지는 것을 막을 수 있습니다.

## 공통 어댑터 인터페이스
<!--meta: sec=s7; dept=BE|DE; level=시니어; ct_band=상; related=s6|s8|s18-->
<!--forbid: 대한전자|한빛유통|ISS-->
모든 고객사 어댑터는 최소한 다음 수명주기와 처리 계약을 제공하는 방향으로 검토합니다.

- `validateConfig`: 필수 설정, URL 형식, 인증 항목의 유효성 확인
- `buildRequest`: 내부 표준 명령을 고객사 요청 구조로 변환
- `authenticate`: 토큰, 키, 서명 등 인증 정보 적용
- `send`: 공통 커넥터를 이용한 요청 전송
- `parseResponse`: 원문 응답을 안전하게 해석
- `validateResponse`: 필수 필드와 타입, 값 범위 검증
- `mapResult`: 고객사 응답을 내부 표준 결과로 변환
- `classifyError`: 고객사 오류를 공통 오류 분류로 매핑
- `healthCheck`: 실제 업무 데이터를 변경하지 않는 연결 상태 확인
- `describeContract`: 어댑터가 기대하는 계약 버전과 기능 정보 제공

인터페이스 설계 시 다음 제약을 둡니다.

- 공통 실행 정책을 우회하는 직접 네트워크 호출은 원칙적으로 금지합니다.
- 어댑터 내부에 장기 보관이 필요한 상태를 두지 않습니다.
- 고객사 응답 원문을 업무 코드에 그대로 반환하지 않습니다.
- 원문 오류 메시지는 기록할 수 있으나 개인정보와 인증정보를 제거해야 합니다.
- 선택 기능은 기능 플래그나 역량 정보로 선언하여, 미지원 기능을 호출 전에 판별할 수 있어야 합니다.
- 어댑터의 변환 로직과 전송 로직은 독립적으로 단위 검증할 수 있어야 합니다.

## 내부 표준 데이터 모델
<!--meta: sec=s8; dept=BE|DE; level=시니어; ct_band=상; related=s5|s7|s9|s19-->
<!--forbid: 대한전자|한빛유통|ISS-->
내부 표준 모델은 모든 고객사 필드를 합친 거대한 통합 모델이 아니라, 헤드헌터랩 서비스가 실제로 사용하는 최소 공통 의미를 표현해야 합니다.

표준 필드의 기본 원칙은 다음과 같습니다.

- 식별자는 값뿐 아니라 식별자 종류와 발급 주체를 함께 표현합니다.
- 날짜와 시각은 시간대 정보를 분리하거나 명시적으로 포함합니다.
- 금액은 숫자와 통화 단위를 함께 보관합니다.
- 상태값은 내부 열거형으로 정규화하되 고객사 원본 값도 추적 가능하게 남깁니다.
- 누락, 빈 문자열, 명시적 `null`, 값 없음의 의미를 구분합니다.
- 문자열 길이와 허용 문자 규칙을 계약에 포함합니다.
- 고객사 전용 확장값은 무제한 자유 형식이 아니라 이름공간이 있는 확장 영역에 둡니다.
- 데이터 출처, 수집 시각, 계약 버전, 변환 버전을 메타데이터로 기록합니다.

표준 모델 변경은 하위 호환성을 우선합니다. 필드 추가는 기본적으로 선택 항목으로 시작하고, 필드 삭제나 의미 변경은 신규 계약 버전에서 처리합니다. 서로 다른 의미를 단지 이름이 같다는 이유로 하나의 필드에 합치지 않습니다.

## 고객사별 차이 흡수 원칙
<!--meta: sec=s9; dept=BE|DE; level=주니어; ct_band=중; related=s8|s10|s11-->
<!--forbid: 대한전자|한빛유통|ISS-->
고객사별 차이는 다음 순서로 흡수합니다.

1. URL, 타임아웃, 페이지 크기처럼 값만 다른 경우에는 설정으로 처리합니다.
2. 헤더명, 필드명, 상태값 매핑처럼 규칙이 다른 경우에는 선언형 매핑으로 처리합니다.
3. 요청 서명, 중첩 구조 변환처럼 실행 로직이 다른 경우에는 어댑터 확장점으로 처리합니다.
4. 업무 의미 자체가 다른 경우에는 공통화하지 않고 별도 기능 계약으로 분리합니다.

모든 차이를 조건문으로 처리하면 공통 모듈이 고객사 이름에 의존하게 됩니다. 반대로 모든 차이를 별도 코드로 만들면 중복 문제가 유지됩니다. 따라서 설정, 선언형 규칙, 코드 확장의 세 단계를 구분하고 코드 확장은 마지막 수단으로 사용합니다.

고객사별 예외를 추가할 때는 예외 사유, 적용 범위, 만료 또는 재검토 조건, 테스트 사례를 함께 등록해야 합니다.

## 인증 방식 표준화
<!--meta: sec=s10; dept=BE|DE; level=시니어; ct_band=중; related=s9|s17|s20-->
<!--forbid: 대한전자|한빛유통|ISS-->
공통 계층은 API 키, 고정 토큰, 토큰 발급형 인증, 요청 서명형 인증, 상호 인증서 기반 연결을 확장 가능한 인증 전략으로 취급합니다.

인증 처리 기준:

- 비밀값은 소스 코드와 일반 설정 파일에 저장하지 않습니다.
- 토큰 만료 시각은 서버 시각 오차를 고려해 실제 만료보다 앞서 갱신합니다.
- 동시에 여러 요청이 토큰 갱신을 시도하지 않도록 단일 갱신 제어를 둡니다.
- 인증 실패와 권한 부족을 구분합니다.
- 인증서 만료 예정일과 키 교체 예정일을 운영 지표로 관리합니다.
- 요청 로그에는 토큰, 서명 원문, 비밀키, 인증 쿠키를 남기지 않습니다.
- 비밀정보가 변경되어도 전체 애플리케이션을 다시 빌드하지 않고 반영할 수 있어야 합니다.
- 개발·검증·운영 환경의 인증정보를 분리합니다.

인증 실패는 무조건 재시도하지 않습니다. 일시적인 토큰 발급 서버 오류는 제한적으로 재시도할 수 있지만, 잘못된 자격증명이나 권한 부족은 운영자 조치가 필요한 영구 오류로 분류합니다.

## 타임아웃과 재시도 정책
<!--meta: sec=s11; dept=BE|DE; level=시니어; ct_band=상; related=s9|s12|s13|s16-->
<!--forbid: 대한전자|한빛유통|ISS-->
재시도는 성공률을 높일 수 있지만 외부 시스템 과부하와 중복 반영을 유발할 수 있으므로 중앙 정책으로 관리해야 합니다.

타임아웃은 다음 단계로 분리합니다.

- 연결 수립 제한시간
- 응답 대기 제한시간
- 요청 한 건의 전체 제한시간
- 여러 재시도를 포함한 업무 처리 전체 제한시간

재시도 대상 후보:

- 일시적 네트워크 단절
- 연결 제한시간 초과
- 외부 시스템의 명시적인 일시 장애 응답
- 호출량 제한 응답 중 재시도 가능 시각이 제공된 경우
- 읽기 작업에서 발생한 일시적 서버 오류

기본적으로 재시도하지 않는 대상:

- 필수 입력 누락
- 인증정보 오류
- 접근 권한 부족
- 존재하지 않는 리소스
- 계약과 다른 응답 구조
- 멱등성이 보장되지 않은 쓰기 요청의 결과 불명 상태
- 업무 규칙 위반

재시도 간격은 고정 간격보다 지수 증가와 무작위 분산을 적용하는 방식을 우선 검토합니다. 단, 실제 횟수와 시간은 연동 업무의 중요도, 고객사 제한 정책, 전체 응답시간 목표에 따라 설정하며 코드에 직접 고정하지 않습니다.

## 멱등성과 중복 방지
<!--meta: sec=s12; dept=BE|DE; level=시니어; ct_band=상; related=s6|s11|s13|s14-->
<!--forbid: 대한전자|한빛유통|ISS-->
외부 시스템이 요청을 처리했지만 응답이 도착하지 않은 경우, 호출자는 성공 여부를 알 수 없습니다. 이 상태에서 같은 쓰기 요청을 다시 보내면 상담 결과, 주문 상태, 집계 데이터 등이 중복 반영될 수 있습니다.

중복 방지 수단:

- 업무 단위의 멱등성 키 발급
- 요청 내용의 안정적인 해시 생성
- 고객사에서 제공하는 중복 방지 키 활용
- 처리 완료 키와 결과의 제한 기간 저장
- 동일 키에 서로 다른 요청 내용이 들어오면 충돌로 분류
- 재처리 시 최초 요청의 상관관계 식별자 유지
- 중복으로 판단된 요청도 감사 가능한 처리 이력 기록

멱등성 키는 네트워크 요청마다 새로 만들지 않고 업무 사건 단위로 유지해야 합니다. 예를 들어 같은 업무 데이터를 재전송하는 경우에는 같은 키를 사용하고, 업무상 수정된 데이터를 새로 전송하는 경우에는 새 버전 또는 새 키를 사용합니다.

외부 시스템이 멱등성 기능을 제공하지 않는 경우에는 사전 조회, 내부 처리 원장, 후속 대사 중 어떤 방식을 적용할지 업무별로 결정해야 합니다.

## 회로 차단과 장애 격리
<!--meta: sec=s13; dept=BE|DE; level=시니어; ct_band=상; related=s11|s12|s14|s16-->
<!--forbid: 대한전자|한빛유통|ISS-->
고객사 시스템의 반복 실패가 헤드헌터랩 서비스의 스레드, 연결 자원, 작업 큐를 소진하지 않도록 연동 대상별 회로 차단을 적용하는 방안을 검토합니다.

회로 상태는 다음 개념으로 관리합니다.

- **정상**: 호출을 허용하고 실패율을 관찰
- **차단**: 일정 조건을 넘은 대상의 호출을 빠르게 실패 처리
- **시험 호출**: 복구 여부 확인을 위해 제한된 호출만 허용

격리 단위는 전체 고객사, 개별 시스템, API 기능, 인증 주체 중 장애 전파 범위에 맞춰 정합니다. 한 기능의 실패 때문에 정상적인 다른 기능까지 차단되지 않도록 지나치게 큰 단위를 피합니다.

회로 차단 시 업무 서비스가 취할 수 있는 대체 동작은 다음과 같습니다.

- 읽기 요청에 대해 허용된 범위의 최근 캐시 사용
- 쓰기 요청을 즉시 실패시키지 않고 비동기 보류
- 기능을 제한 모드로 전환하고 사용자에게 지연 상태 표시
- 자동 처리가 위험한 경우 수동 확인 대상으로 전환

대체 동작은 데이터 최신성이나 업무 결과를 바꿀 수 있으므로 개발자가 임의로 선택하지 않고 업무 책임자와 합의한 정책으로 등록해야 합니다.

## 동기·비동기 연동 기준
<!--meta: sec=s14; dept=BE|DE; level=대리; ct_band=중; related=s12|s13|s15-->
<!--forbid: 대한전자|한빛유통|ISS-->
동기 연동은 즉시 결과가 필요한 조회나 검증에 적합하지만 외부 시스템 지연이 사용자 응답시간에 직접 영향을 줍니다. 비동기 연동은 지연과 일시 장애를 흡수하기 쉽지만 처리 완료 시점과 순서를 별도로 관리해야 합니다.

동기 연동 선택 조건:

- 호출자가 즉시 결과를 받아야 다음 업무를 진행할 수 있음
- 예상 처리시간이 짧고 안정적임
- 실패를 사용자 흐름에서 즉시 처리할 수 있음
- 중복 호출 위험이 통제됨

비동기 연동 선택 조건:

- 외부 시스템 지연이 길거나 변동이 큼
- 일정 시간 내 최종 반영이면 충분함
- 대량 데이터를 순차 또는 병렬 처리해야 함
- 재처리와 처리 순서 관리가 필요함
- 외부 시스템 점검 시간에도 요청을 받아야 함

비동기 처리에서는 메시지 자체의 전달 성공과 업무 반영 성공을 구분합니다. 소비 완료 표시는 업무 반영이 끝난 뒤 수행하며, 반복 실패 메시지는 격리 보관소로 이동시켜 정상 메시지 처리를 막지 않도록 합니다.

## 실패 보관과 재처리
<!--meta: sec=s15; dept=BE|DE; level=대리; ct_band=중; related=s14|s16|s20-->
<!--forbid: 대한전자|한빛유통|ISS-->
자동 복구되지 않은 실패 건은 원인 분석과 재처리가 가능하도록 보관해야 합니다.

보관 항목:

- 상관관계 식별자
- 업무 식별자와 멱등성 키
- 어댑터 및 계약 버전
- 요청 발생 시각과 마지막 시도 시각
- 시도 횟수와 재시도 정책
- 공통 오류 코드와 외부 오류 코드
- 마스킹된 요청·응답 요약
- 다음 처리 가능 시각
- 수동 조치 필요 여부
- 최종 처리 상태와 조치 담당자

재처리 유형은 단건 재처리, 조건 기반 일괄 재처리, 변환 규칙 수정 후 재변환, 고객사 복구 후 재전송으로 구분합니다. 운영자가 원문을 임의 수정하여 재전송하는 기능은 감사성과 재현성을 해칠 수 있으므로 제한합니다.

재처리 전에는 동일 업무가 이미 다른 경로로 반영되었는지 확인해야 합니다. 재처리 결과도 최초 처리와 동일한 관측·감사 기준을 적용합니다.

## 공통 오류 분류 체계
<!--meta: sec=s16; dept=BE|DE; level=주니어; ct_band=중; related=s11|s13|s15|s19-->
<!--forbid: 대한전자|한빛유통|ISS-->
고객사마다 다른 오류 코드와 메시지를 다음 공통 범주로 정규화합니다.

| 공통 범주 | 의미 | 기본 처리 방향 |
|---|---|---|
| 연결 오류 | 네트워크 연결을 만들지 못함 | 제한적 재시도 |
| 시간 초과 | 정해진 시간 내 결과 미수신 | 멱등성 확인 후 판단 |
| 인증 실패 | 자격증명 또는 토큰 문제 | 갱신 또는 운영 조치 |
| 권한 부족 | 호출 권한이 없음 | 재시도 금지 |
| 호출량 제한 | 허용량을 초과함 | 지연 후 재시도 |
| 입력 검증 실패 | 요청 데이터가 계약에 맞지 않음 | 데이터 수정 필요 |
| 계약 불일치 | 응답 구조나 타입이 예상과 다름 | 차단 및 변경 확인 |
| 외부 업무 오류 | 고객사 업무 규칙에 의해 거절됨 | 업무별 조치 |
| 외부 일시 장애 | 외부 시스템이 일시적으로 처리 불가 | 제한적 재시도 |
| 결과 불명 | 처리 여부를 확정할 수 없음 | 대사 후 결정 |
| 내부 변환 오류 | 어댑터의 변환 처리 실패 | 배포·규칙 점검 |
| 알 수 없는 오류 | 기존 분류로 판정할 수 없음 | 원문 보존 후 분석 |

공통 오류 객체에는 기술 메시지와 운영자 메시지를 분리합니다. 기술 메시지는 진단에 필요한 상세 내용을 포함할 수 있지만, 운영자 메시지는 조치 가능성과 영향 범위를 중심으로 작성합니다.

## 설정과 비밀정보 관리
<!--meta: sec=s17; dept=BE|DE; level=대리; ct_band=중; related=s10|s18|s20-->
<!--forbid: 대한전자|한빛유통|ISS-->
고객사별 연결 정보는 실행 코드와 분리하여 관리합니다.

일반 설정 후보:

- 대상 시스템 식별자
- 기본 URL과 경로
- 연결·응답 제한시간
- 재시도 정책 식별자
- 호출량 제한값
- 계약 버전
- 기능 활성화 여부
- 페이지 크기와 최대 데이터 크기
- 점검 시간대
- 담당 운영 그룹

비밀정보 후보:

- API 키
- 비밀 토큰
- 인증서 개인키
- 요청 서명 키
- 비밀번호
- 토큰 발급용 자격증명

설정 변경은 작성과 승인을 분리하고 변경 이력을 남깁니다. 잘못된 설정이 여러 인스턴스에 동시에 반영되는 것을 막기 위해 검증, 일부 적용, 상태 확인, 전체 적용 순서를 사용합니다. 비밀정보는 조회 권한과 변경 권한을 최소화하고, 출력·내보내기·로그 기록을 제한합니다.

## 스키마 변경 감지
<!--meta: sec=s18; dept=BE|DE; level=시니어; ct_band=상; related=s7|s17|s19|s22-->
<!--forbid: 대한전자|한빛유통|ISS-->
API 변경을 조기에 발견하기 위해 정적 계약 검증과 운영 중 관찰을 함께 사용합니다.

정적 검증:

- 합의된 요청·응답 예제와 스키마 보관
- 고객사 검증 환경에 대한 주기적 계약 테스트
- 필수 필드, 타입, 중첩 구조, 열거값 비교
- 어댑터 배포 전 기존 계약 사례 회귀 검증
- 계약 버전별 호환성 판정

운영 중 관찰:

- 알려지지 않은 필드 출현
- 기존 필드의 미출현 비율 증가
- 숫자에서 문자열처럼 필드 타입이 바뀐 사례
- 새로운 상태값 또는 오류 코드 출현
- 응답 크기의 급격한 변화
- 빈 값과 `null` 비율의 변화
- 날짜 형식과 문자 인코딩 변화

모든 변화가 장애는 아닙니다. 선택 필드 추가는 호환 가능한 변경일 수 있지만, 필수 필드 삭제나 타입 변경은 즉시 처리 실패를 유발할 수 있습니다. 감지 결과는 `정보`, `주의`, `차단 후보`로 구분하여 불필요한 경보를 줄입니다.

원문 전체를 장기간 저장하지 않고도 변화를 관찰할 수 있도록 필드 경로, 타입, 출현 빈도, 값 범위 요약을 중심으로 기록합니다.

## 데이터 품질과 계약 검증

스키마가 동일해도 데이터 의미가 달라질 수 있으므로 구조 검증과 품질 검증을 분리합니다.

구조 검증 항목:

- 필수 필드 존재 여부
- 타입과 형식
- 최대 길이와 배열 크기
- 허용된 중첩 깊이
- 날짜·시각 파싱 가능 여부
- 문자 인코딩

품질 검증 항목:

- 식별자 중복률
- 기준 기간 대비 누락률 변화

- 같은 업무 키에 대한 상충 값

품질 이상이 발견되었다고 모든 데이터를 폐기하지는 않습니다. 치명적 오류는 격리하고, 경미한 이상은 경고와 함께 처리하며, 분석에 영향을 주는 항목은 품질 표식을 남기는 방식으로 구분합니다. 어떤 수준에서 차단할지는 데이터 사용 목적별로 정의해야 합니다.

## 운영 책임과 대응 절차
<!--meta: sec=s21; dept=BE|DE; level=과장; ct_band=중; related=s3|s20|s22-->
<!--forbid: 대한전자|한빛유통|ISS-->
연동 이상 발생 시 기본 대응 흐름은 다음과 같습니다.

1. 경보 또는 사용자 신고를 통해 이상을 접수합니다.
2. 상관관계 식별자와 공통 오류 범주를 확인합니다.
3. 내부 배포·설정 변경 여부와 외부 시스템 상태를 구분합니다.
4. 재시도 가능성, 중복 위험, 데이터 유실 가능성을 판정합니다.
5. 필요한 경우 회로 차단, 비동기 보류, 기능 제한을 적용합니다.
6. 고객사 확인이 필요하면 재현 시각, 기능, 마스킹된 오류 정보를 전달합니다.
7. 복구 후 시험 호출과 보류 데이터 재처리를 수행합니다.
8. 데이터 누락·중복 여부를 대사합니다.
9. 원인과 조치 내용을 운영 기록에 남깁니다.

역할 기준:

- 백엔드팀: 공통 계층, 어댑터, 연결 상태와 오류 분류 확인
- 프로젝트 담당팀: 사용자 영향과 업무 우선순위 판단
- 데이터분석팀: 누락·중복·시점 불일치 검증 지원
- 컨설팅팀: 고객사 업무 담당자와 변경 내용 및 복구 기준 조율
- 영업팀: 계약 범위나 추가 협의가 필요한 사안의 대외 창구 지원

복구 속도를 높이기 위해 기술적 정상화와 업무 데이터 정상화를 구분합니다. API 호출이 다시 성공해도 장애 시간 동안의 누락 데이터가 반영되지 않았다면 업무 복구는 완료된 것이 아닙니다.

## 테스트 전략
<!--meta: sec=s22; dept=BE|DE; level=시니어; ct_band=상; related=s3|s18|s21|s24-->
<!--forbid: 대한전자|한빛유통|ISS-->
공통 어댑터는 정상 응답만 확인하는 방식으로 검증할 수 없습니다. 다음 테스트 계층을 구성합니다.

- **변환 단위 테스트**: 요청·응답 매핑, 날짜, 상태값, 빈 값 처리 검증
- **계약 테스트**: 합의된 스키마와 실제 어댑터 동작의 일치 여부 확인
- **모의 서버 테스트**: 지연, 연결 종료, 잘못된 JSON, 오류 코드 재현
- **멱등성 테스트**: 동일 요청 반복 시 중복 반영 여부 확인
- **재시도 테스트**: 재시도 대상과 금지 대상이 정확히 분리되는지 확인
- **회로 차단 테스트**: 반복 실패, 차단, 시험 호출, 복구 흐름 검증
- **호환성 테스트**: 선택 필드 추가, 필드 순서 변경, 신규 상태값 대응 확인
- **보안 테스트**: 로그와 오류 메시지에 비밀정보가 노출되지 않는지 확인
- **부하 테스트**: 연결 풀, 작업 큐, 호출량 제한이 예상 처리량을 견디는지 확인
- **복구 테스트**: 격리 데이터의 단건·일괄 재처리와 중복 방지 확인
- **운영 훈련**: 경보 접수부터 원인 분류, 제한 조치, 대사까지 절차 검증

고객사 검증 환경이 운영 환경과 다를 수 있으므로 모의 서버만으로 완료 판정하지 않습니다. 다만 운영 데이터 변경 위험이 있는 API는 읽기 전용 확인, 고객사 승인된 시험 데이터, 비업무 시간대 시험 중 적절한 방식을 선택합니다.

## 단계별 추진 계획
<!--meta: sec=s23; dept=BE|DE; level=부장; ct_band=중; related=s2|s4|s20|s24-->
<!--forbid: 대한전자|한빛유통|ISS-->
2026년 4분기 내 마련할 공통 어댑터 설계안은 다음 단계로 구체화합니다.

### 1단계: 현행 조사

- 프로젝트별 연동 목록 작성
- 인증 방식, 프로토콜, 호출 방향, 데이터량 분류
- 중복 코드와 고객사별 예외 수집
- 최근 실패 유형과 수동 복구 절차 정리
- 고객사 변경 통지 및 검증 환경 제공 여부 확인

### 2단계: 공통 계약 설계

- 어댑터 인터페이스 초안 작성
- 공통 오류 분류와 재시도 기준 정의
- 표준 메타데이터와 추적 필드 정의
- 내부 표준 모델 적용 범위 결정
- 설정·비밀정보 관리 경계 확정

### 3단계: 대표 연동 검증

- 서로 다른 인증·응답 특성을 가진 연동을 대표 사례로 선정
- 기존 코드와 공통 구조의 차이 분석
- 모의 장애와 스키마 변경 검증
- 프로젝트 코드 변경량과 운영 복잡도 평가
- 공통화가 부적절한 예외 조건 식별

### 4단계: 운영 기준 확정

- 지표와 경보 기준 수립
- 실패 보관 및 재처리 권한 정의
- 버전 관리와 배포 승인 절차 확정
- 어댑터 개발 가이드와 점검표 작성
- 기존 프로젝트 전환 우선순위 결정

설계안 마련과 전체 프로젝트 전환은 별도 단계입니다. 기존 연동을 한 번에 교체하지 않고, 신규 연동 우선 적용 후 변경 필요성이 높은 기존 연동부터 순차적으로 전환하는 방식을 검토합니다.

## 주요 위험과 대응 방향
<!--meta: sec=s25; dept=BE|DE; level=차장; ct_band=상; related=s24|s26|s27-->
<!--forbid: 대한전자|한빛유통|ISS-->
### 공통 계층의 과도한 비대화

모든 업무 예외를 공통 모듈에 넣으면 변경 영향 범위가 커집니다. 공통 계층은 전송과 안정성 정책에 집중하고, 업무 의미는 프로젝트 또는 기능 계약에 남깁니다.

### 기존 프로젝트 전환 부담

기존 연동을 일괄 전환하면 회귀 위험이 커집니다. 신규 기능 우선 적용, 병행 비교, 기능별 전환 방식을 사용합니다.

### 고객사 검증 환경 부족

운영 환경에서만 확인 가능한 조건이 있을 수 있습니다. 모의 서버, 계약 샘플, 제한된 시험 호출, 운영 관찰을 조합합니다.

### 잘못된 자동 재시도

영구 오류나 비멱등 요청을 반복하면 장애가 확대될 수 있습니다. 오류 분류가 불명확하면 자동 재시도보다 격리를 우선합니다.

### 경보 과다

선택 필드 추가나 단건 지연까지 모두 경보로 만들면 중요한 이상을 놓칠 수 있습니다. 변화의 심각도와 지속시간을 기준으로 알림을 단계화합니다.

### 원문 데이터 과다 보관

문제 분석을 위해 요청·응답 전체를 저장하면 개인정보와 저장비용 위험이 커집니다. 기본적으로 구조 요약과 마스킹된 진단 정보만 보관하고 원문 보관은 승인된 범위로 제한합니다.

### 공통 모듈 장애의 확산

공통 계층의 결함이 여러 프로젝트에 영향을 줄 수 있습니다. 버전 고정, 단계적 배포, 빠른 이전 버전 복귀, 어댑터별 격리를 적용합니다.

## 미결정 사항
<!--meta: sec=s26; dept=BE|DE; level=시니어; ct_band=상; related=s25|s27-->
<!--forbid: 대한전자|한빛유통|ISS-->
설계안 확정 전 다음 사항에 대한 의사결정이 필요합니다.

- 공통 연동 계층을 라이브러리로 제공할지 독립 서비스로 제공할지
- 내부 표준 모델을 전사 공통으로 둘지 업무 영역별로 분리할지
- 실패 원문을 어느 범위와 기간으로 보관할지
- 고객사별 어댑터 소유권을 중앙 백엔드팀과 프로젝트팀 중 어디에 둘지
- 설정 변경 승인과 긴급 변경 권한을 어떻게 분리할지
- 계약 변경 감지를 실제 트래픽 기반으로 할지 주기적 시험 호출과 병행할지
- 멱등성 기록의 보존 기간을 업무별로 어떻게 결정할지
- 고객사 시스템이 호출량 정보를 제공하지 않을 때 안전 한도를 어떻게 설정할지
- 비동기 실패 데이터의 자동 폐기 금지 기간을 어떻게 정할지
- 공통 모듈 버전 지원 범위와 구버전 종료 절차를 어떻게 운영할지

의사결정 시 개발 편의성만 보지 않고 운영 책임, 고객사 제약, 데이터 위험, 기존 프로젝트 전환 비용을 함께 평가합니다.

## 설계 검토 체크리스트
<!--meta: sec=s27; dept=BE|DE; level=대리; ct_band=중; related=s25|s26|s28-->
<!--forbid: 대한전자|한빛유통|ISS-->
신규 또는 변경 연동을 설계할 때 다음 질문을 확인합니다.

### 계약

- 요청과 응답의 필수 필드가 구분되어 있는가?
- 빈 값, 누락, `null`의 의미가 정의되어 있는가?
- 날짜·시각과 시간대가 명확한가?
- 새 필드와 새 상태값이 들어와도 안전하게 처리되는가?
- 계약 버전과 어댑터 버전을 추적할 수 있는가?

### 안정성

- 연결, 응답, 전체 처리 제한시간이 분리되어 있는가?
- 재시도 가능한 오류가 명시되어 있는가?
- 쓰기 요청의 멱등성을 보장할 수 있는가?
- 외부 시스템 반복 실패 시 자원 고갈을 막을 수 있는가?
- 결과 불명 상태를 대사할 방법이 있는가?

### 운영

- 상관관계 식별자로 전체 흐름을 찾을 수 있는가?
- 실패 데이터를 안전하게 재처리할 수 있는가?
- 경보 수신자가 취할 조치가 문서화되어 있는가?
- 외부 복구 후 누락·중복 데이터를 검증할 수 있는가?
- 고객사 변경 통지 연락 경로가 확인되어 있는가?

### 보안

- 인증정보가 코드와 로그에 남지 않는가?
- 개인정보가 불필요하게 저장되지 않는가?
- 운영자 조회 화면에서 민감 필드가 마스킹되는가?
- 설정과 비밀정보 변경 이력이 남는가?
- 재처리 권한과 조회 권한이 분리되어 있는가?

## 기대 효과
<!--meta: sec=s28; dept=BE|DE; level=주니어; ct_band=하; related=s27|s29-->
<!--forbid: 대한전자|한빛유통|ISS-->
공통 연동 구조가 정착되면 다음 효과를 기대할 수 있습니다.

- 신규 고객사 연동 시 반복 구현해야 하는 기반 코드 감소
- 인증, 타임아웃, 재시도 정책의 일관성 향상
- API 변경의 조기 발견과 영향 범위 파악
- 장애 발생 시 원인 분류와 담당자 전달 속도 향상
- 실패 데이터 유실 및 중복 반영 위험 감소
- 프로젝트 간 운영 방식의 편차 축소
- 신규 개발자의 연동 구조 이해와 인수인계 부담 완화
- 고객사별 예외 조건의 문서화와 추적 가능성 향상
- 기존 프로젝트에서 발견된 안정성 개선 사항의 재사용
- 고객사와 변경·복구 기준을 협의할 때 사용할 공통 언어 확보

이 과제의 핵심 성과는 특정 기술을 도입하는 것이 아니라, 고객사별 차이를 인정하면서도 반복되는 안정성 문제를 공통 방식으로 통제할 수 있게 되는 것입니다.

## 면접 질문 생성용 관찰 포인트
<!--meta: sec=s29; dept=BE|DE; level=시니어; ct_band=중; related=s28|s30-->
<!--forbid: 대한전자|한빛유통|ISS-->
이 문서를 바탕으로 기술 역량을 확인할 때는 단순한 용어 암기보다 판단 과정과 운영 경험을 관찰합니다.

주니어 후보자에게 확인할 수 있는 항목:

- 타임아웃과 재시도의 차이를 설명할 수 있는가?
- 모든 오류를 재시도하면 안 되는 이유를 이해하는가?
- API 응답 필드가 갑자기 없어졌을 때 어떤 검증이 필요한지 설명할 수 있는가?
- 인증정보를 코드나 로그에 남기면 안 되는 이유를 설명할 수 있는가?
- 상관관계 식별자가 장애 분석에 어떻게 도움이 되는지 이해하는가?

시니어 후보자에게 확인할 수 있는 항목:

- 라이브러리와 독립 연동 서비스의 장단점을 비교할 수 있는가?
- 결과 불명 상태의 쓰기 요청을 안전하게 처리하는 방안을 제시할 수 있는가?
- 공통화 범위와 고객사별 예외의 경계를 설정할 수 있는가?
- 스키마 변화 감지의 오탐과 미탐을 줄이는 전략을 설명할 수 있는가?
- 기존 프로젝트를 중단 없이 공통 구조로 전환하는 계획을 세울 수 있는가?
- 기술적 복구와 업무 데이터 복구를 구분하여 설명할 수 있는가?

좋은 답변은 특정 제품명 나열보다 실패 유형, 데이터 위험, 운영 절차, 점진적 전환을 함께 고려합니다.
