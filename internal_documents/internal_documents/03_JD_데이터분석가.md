# 데이터 분석가 직무기술서
<!--meta: doc=JD-DATA-01; doc_type=jd; tier=2; topic=ORG; disclosure=public; status=active-->

## 직무 개요
<!--meta: sec=s1; dept=DATA; level=주니어|시니어; ct_band=하; related=s2|s5|s6-->
데이터분석팀은 고객사의 과거 데이터를 분석해 수요예측·대시보드를 만들고, AI/AX개발팀이 만든 모델의 운영 성능을 데이터로 감시합니다.

데이터 분석가는 단순히 데이터를 조회해 표와 그래프를 만드는 역할에 머무르지 않습니다. 고객사의 업무 질문을 측정 가능한 분석 문제로 바꾸고, 필요한 데이터의 의미와 품질을 확인하며, 분석 결과가 실제 의사결정에 활용될 수 있도록 지표·보고서·대시보드 형태로 전달합니다.

헤드헌터랩은 한국 B2B AI/AX 컨설팅·구축 테크기업으로, 데이터분석팀은 컨설팅팀·AI/AX개발팀·백엔드팀·영업팀과 협업합니다. 서울·경기·인천 3개 지점은 모두 컨설팅과 개발을 함께 수행할 수 있는 풀스택 조직으로 운영되므로, 데이터 분석가는 특정 지점에 한정되지 않고 프로젝트 목적과 고객 상황에 맞춰 협업할 수 있어야 합니다.

본 직무의 핵심 책임은 다음 세 가지입니다.

1. 고객사의 업무 현상을 데이터로 설명합니다.
2. 수요예측 및 통계 분석 결과를 검증 가능한 지표로 제공합니다.
3. 운영 중인 AI 시스템과 데이터 제품의 상태를 지속적으로 관찰할 수 있게 만듭니다.

## 주요 업무
<!--meta: sec=s2; dept=DATA; level=주니어|시니어; ct_band=중; related=s1|s7|s8|s9-->
- 고객사 데이터 전처리·탐색적 분석(EDA)
- 수요예측 모델링 및 지표 설계
- 운영 중인 AI 시스템의 성능 지표 집계·대시보드 구축
- 데이터 품질 점검, 라벨·지표 정의서 관리
- 고객사의 업무 요청을 분석 질문과 검증 가설로 구체화
- 원천 데이터의 구조, 생성 주기, 누락 조건 및 변경 이력 파악
- 분석용 데이터셋의 집계 기준과 관측 단위 설계
- 기초 통계량, 분포, 상관관계, 이상치 및 결측 패턴 분석
- 기준선 모델과 후보 모델의 성능 비교
- 시계열 검증 방식과 예측 평가 구간 설계
- 대시보드 이용자별 조회 목적과 핵심 지표 정의
- 분석 결과의 업무적 의미, 한계 및 활용 조건 문서화
- 운영 지표의 급격한 변동과 데이터 품질 저하 징후 확인
- 정기 분석 보고서 및 고객 설명 자료 작성
- 반복 분석 절차의 재현성을 높이기 위한 코드·쿼리·산출물 관리

업무 비중은 프로젝트 단계에 따라 달라집니다. 초기에는 데이터 구조 파악과 품질 진단 비중이 높고, 구축 중에는 지표 정의와 모델 검증이 중심이 되며, 운영 단계에서는 모니터링·리포팅·변화 원인 분석이 중요해집니다.

## 자격 요건
<!--meta: sec=s3; dept=DATA; level=주니어|시니어; ct_band=하; related=s11|s12|s13-->
- SQL, Python(pandas) 기반 데이터 분석 경험
- 시계열 예측 또는 통계 분석 경험
- 주니어(0~3년): 지도 하에 분석 보고서 작성 가능
- 시니어(4년+): 분석 설계부터 고객 보고까지 단독 수행 가능
- 데이터의 행 수만 확인하는 데 그치지 않고 값의 의미와 생성 과정을 질문할 수 있는 역량
- 분석 결과와 업무적 해석을 구분하여 설명할 수 있는 역량
- 지표의 분모·분자·집계 기간·제외 조건을 명확히 정의할 수 있는 역량
- 코드, 쿼리, 분석 조건 및 결과를 다른 구성원이 재현할 수 있게 기록하는 습관
- 비기술 직군에게 통계적 결과를 과도한 전문용어 없이 설명할 수 있는 의사소통 능력
- 데이터가 불완전한 상황에서 확인된 사실, 가정, 미확인 사항을 구분하는 태도

특정 도구의 사용 연수보다 데이터를 구조적으로 이해하고 분석 과정을 검증 가능하게 만드는 능력을 중요하게 봅니다.

## 우대 사항
<!--meta: sec=s4; dept=DATA; level=주니어|시니어; ct_band=중; related=s10|s14|s16-->
- BI 대시보드 도구(Tableau, Metabase 등) 사용 경험
- 수요예측·재고관리 도메인 경험
- 고객사 실무자와 지표 정의 워크숍을 진행한 경험
- 시계열 교차검증, 백테스트 또는 롤링 검증 경험
- 데이터 품질 규칙과 검증 쿼리를 설계한 경험
- 데이터 사전, 지표 정의서 또는 분석 명세서를 작성한 경험
- 분석용 SQL의 정확성과 실행 효율을 함께 개선한 경험
- 실험 결과나 모델 성능을 대시보드로 운영한 경험
- 결측치, 중복, 지연 수집, 코드 체계 변경이 분석 결과에 미치는 영향을 설명한 경험
- 분석 결과를 경영진용 요약과 실무자용 상세 내용으로 구분해 전달한 경험
- Git 기반으로 분석 코드와 문서를 협업한 경험
- 통계적 유의성과 업무적 중요성을 구분하여 판단한 경험

우대 사항은 필수 조건이 아닙니다. 모든 항목을 경험하지 않았더라도 본인이 수행한 분석의 목적, 판단 과정, 한계 및 개선 방향을 구체적으로 설명할 수 있다면 직무 적합성을 검토할 수 있습니다.

## 직무의 주요 산출물
<!--meta: sec=s5; dept=DATA; level=주니어|시니어; ct_band=하; related=s1|s7|s15-->
데이터 분석가는 프로젝트 단계와 역할 범위에 따라 다음 산출물을 작성하거나 관리합니다.

- 데이터 프로파일링 결과서
- 탐색적 데이터 분석 보고서
- 분석 가설 및 검증 계획서
- 지표 정의서
- 데이터 사전 및 컬럼 설명서
- 수요예측 기준선 비교표
- 모델 성능 평가표
- 백테스트 결과서
- 대시보드 화면 및 사용자 안내 자료
- 운영 성능 모니터링 리포트
- 데이터 품질 점검표
- 이상 징후 분석 메모
- 고객 보고용 요약 자료
- 분석 코드, SQL 및 실행 조건
- 분석 결과 재현 절차
- 변경 전후 지표 영향도 확인서

좋은 산출물은 결론만 제시하지 않습니다. 사용한 데이터의 기준 시점, 대상 범위, 제외 조건, 계산 방식, 가정, 한계 및 후속 확인 항목을 함께 포함해야 합니다.

## 업무 수행 흐름
<!--meta: sec=s6; dept=DATA; level=주니어|시니어; ct_band=중; related=s1|s5|s8-->
일반적인 분석 업무는 다음 순서로 진행됩니다.

1. **업무 질문 확인:** 고객 또는 프로젝트 구성원이 해결하려는 문제를 파악합니다.
2. **분석 질문 전환:** 모호한 요청을 측정 가능한 질문으로 구체화합니다.
3. **데이터 후보 확인:** 질문에 필요한 원천, 기준 정보 및 보조 데이터를 식별합니다.
4. **데이터 의미 검증:** 컬럼 정의와 실제 값의 생성 방식이 일치하는지 확인합니다.
5. **품질 진단:** 결측, 중복, 이상치, 지연, 코드 불일치 및 기간 단절을 점검합니다.
6. **분석 설계:** 관측 단위, 비교 집단, 평가 기간, 지표 및 검증 방식을 결정합니다.
7. **분석 실행:** SQL과 Python 등을 활용해 데이터셋과 결과를 생성합니다.
8. **결과 검증:** 표본 확인, 대조 집계, 상식적 범위 점검 및 동료 검토를 수행합니다.
9. **업무 해석:** 통계적 결과가 고객 업무에서 의미하는 바를 정리합니다.
10. **전달 및 기록:** 보고서나 대시보드로 제공하고 재현에 필요한 조건을 남깁니다.
11. **운영 추적:** 데이터와 지표의 변화 여부를 정기적으로 확인합니다.

분석 요청을 받자마자 코드를 작성하기보다, 먼저 질문과 데이터의 단위를 일치시키는 것이 중요합니다.

## 탐색적 데이터 분석 기준
<!--meta: sec=s7; dept=DATA; level=주니어|시니어; ct_band=중; related=s2|s5|s17-->
탐색적 데이터 분석은 그래프를 많이 만드는 활동이 아니라 데이터의 구조와 위험 요소를 체계적으로 파악하는 과정입니다. 기본 확인 범위는 다음과 같습니다.

- 전체 행 수와 고유 키 수
- 분석 대상 기간과 데이터 공백 구간
- 컬럼별 데이터형과 실제 값 형식
- 결측률과 결측 발생 조건
- 중복 키와 중복 레코드의 발생 유형
- 범주형 값의 종류와 빈도
- 숫자형 값의 최소·최대·중앙값·분위수
- 음수, 0, 비정상적으로 큰 값의 업무적 의미
- 시간대, 일자 경계 및 마감 시각의 영향
- 신규 코드와 폐기 코드의 혼재 여부
- 특정 기간 전후의 분포 변화
- 데이터 생성 시스템별 값 차이
- 집계 전후 총량 일치 여부
- 표본 레코드의 원천 화면 또는 업무 기록과의 일치 여부

EDA 결과에는 발견 사항뿐 아니라 해당 현상이 오류인지 정상적인 업무 특성인지 확인할 담당자와 확인 상태를 함께 기록하는 것을 권장합니다.

## 분석 질문과 가설 정의
<!--meta: sec=s8; dept=DATA; level=주니어|시니어; ct_band=중; related=s2|s6|s18-->
고객의 요청은 종종 “매출이 왜 줄었는가”, “예측 정확도를 높여 달라”, “대시보드를 보기 좋게 만들어 달라”와 같이 넓은 형태로 제시됩니다. 데이터 분석가는 이를 다음 요소로 구체화합니다.

- 분석 대상: 어떤 고객, 상품, 지점, 채널 또는 기간을 볼 것인가
- 기준 단위: 거래, 일, 주, 월, 상품 또는 고객 중 무엇을 한 행으로 볼 것인가
- 비교 기준: 전주, 전월, 전년, 계획값 또는 유사 집단 중 무엇과 비교할 것인가
- 결과 변수: 매출액, 주문 수량, 재고량, 전환율 또는 오류율 중 무엇을 측정할 것인가
- 설명 후보: 가격, 프로모션, 휴일, 품절, 신규 상품, 채널 변화 등 어떤 요인을 검토할 것인가
- 활용 결정: 분석 결과로 어떤 업무 행동이 달라져야 하는가
- 검증 한계: 현재 데이터로 확인할 수 없는 내용은 무엇인가

좋은 분석 가설은 결과가 맞을 때뿐 아니라 틀릴 때도 다음 판단으로 이어질 수 있어야 합니다.

## 수요예측 분석 책임
<!--meta: sec=s9; dept=DATA; level=주니어|시니어; ct_band=상; related=s2|s10|s19-->
수요예측 업무에서 데이터 분석가는 모델 알고리즘 선택만이 아니라 예측 문제가 올바르게 정의되었는지를 책임집니다.

주요 확인 항목은 다음과 같습니다.

- 예측 대상의 업무적 정의
- 예측 단위와 시간 간격
- 예측 시점에 실제로 사용할 수 있는 입력값
- 예측 기간과 업무 의사결정 기간의 일치 여부
- 학습·검증·테스트 기간의 시간 순서 보존
- 품절로 인해 관측되지 않은 잠재 수요의 처리
- 신규 상품과 판매 종료 상품의 구분
- 휴일, 행사 및 프로모션 변수의 사전 가용성
- 기준선 예측과 후보 모델의 비교
- 전체 평균뿐 아니라 중요 세그먼트별 성능
- 과소예측과 과대예측의 업무 비용 차이
- 예측값의 사용 조건과 적용 제외 조건

예측 정확도는 단일 숫자로만 판단하지 않습니다. 데이터 분석가는 오차가 언제, 어디에서, 어떤 방향으로 커지는지 분해하고 실제 업무에서 허용 가능한 수준인지 설명해야 합니다.

## 예측 평가 지표 해석
<!--meta: sec=s10; dept=DATA; level=주니어|시니어; ct_band=상; related=s4|s9|s20-->
수요예측 평가에는 문제 특성에 맞는 지표를 선택해야 합니다.

- **MAE:** 예측 오차의 절대값 평균입니다. 원래 단위로 해석하기 쉬우나 규모가 큰 항목의 영향이 커질 수 있습니다.
- **RMSE:** 큰 오차에 더 큰 불이익을 주는 지표입니다. 일부 대형 오차가 중요한 업무에 적합할 수 있습니다.
- **MAPE:** 실제값 대비 오차 비율을 나타냅니다. 실제값이 0이거나 매우 작을 때 불안정할 수 있습니다.
- **WAPE:** 전체 실제값 대비 절대오차 합의 비율입니다. 전체 규모 관점에서 해석하기 쉽지만 소량 항목의 문제를 가릴 수 있습니다.
- **Bias:** 예측이 지속적으로 과대 또는 과소 방향을 보이는지 확인합니다.
- **예측 구간 포함률:** 실제값이 제시된 불확실성 범위 안에 얼마나 포함되는지 확인합니다.

평가 시에는 다음 원칙을 적용합니다.

1. 모델 개발 전에 주 평가 지표와 보조 지표를 합의합니다.
2. 전체 성능과 세그먼트별 성능을 함께 확인합니다.
3. 평균 성능과 최악 구간 성능을 구분합니다.
4. 기존 방식 또는 단순 기준선보다 개선되었는지 비교합니다.
5. 통계적 개선이 실제 운영 비용 감소로 이어지는지 검토합니다.
6. 동일한 평가 구간과 동일한 제외 조건으로 비교합니다.

## 데이터 품질 관리 책임
<!--meta: sec=s11; dept=DATA; level=주니어|시니어; ct_band=중; related=s3|s7|s21-->
데이터 분석가는 원천 시스템의 소유자가 아니더라도 분석 결과에 영향을 주는 품질 문제를 발견하고 기록할 책임이 있습니다.

주요 품질 차원은 다음과 같습니다.

- **완전성:** 필요한 레코드와 값이 빠짐없이 수집되었는가
- **유일성:** 동일 업무 사건이 중복 저장되지 않았는가
- **유효성:** 값이 허용된 형식과 범위에 들어오는가
- **일관성:** 시스템이나 테이블 간 동일 개념이 같은 의미를 가지는가
- **정확성:** 값이 실제 업무 사실과 일치하는가
- **적시성:** 분석이나 운영에 필요한 시점까지 데이터가 도착하는가
- **연속성:** 수집량과 분포가 예기치 않게 끊기거나 급변하지 않았는가

품질 문제를 보고할 때에는 현상, 최초 확인 시점, 영향 범위, 재현 조건, 임시 처리, 담당 조직 및 후속 확인 항목을 구분합니다. 원인을 확인하지 않은 상태에서 임의로 값을 보정하고 정상 데이터처럼 취급해서는 안 됩니다.

## SQL 활용 수준
<!--meta: sec=s12; dept=DATA; level=주니어|시니어; ct_band=중; related=s3|s13|s17-->
데이터 분석가에게 SQL은 단순 조회 도구가 아니라 분석 기준을 정확하게 구현하는 수단입니다.

주니어에게 기대하는 범위는 다음과 같습니다.

- 기본적인 `SELECT`, `WHERE`, `GROUP BY`, `JOIN` 활용
- 날짜와 문자열 함수 활용
- 중복 및 결측 확인 쿼리 작성
- 집계 전후 행 수와 합계 검증
- 기존 쿼리의 조건과 결과 설명
- 작은 단위의 공통 테이블 표현식과 서브쿼리 이해

시니어에게 기대하는 범위는 다음과 같습니다.

- 복수 원천을 결합하는 분석 데이터셋 설계
- 윈도 함수와 조건부 집계를 활용한 지표 구현
- 시점 기준 조인과 이력 데이터 처리
- 중복 증폭과 누락을 방지하는 조인 설계
- 대규모 조회의 병목 원인 파악
- 반복 사용되는 분석 로직의 검증 가능성 개선
- 쿼리 변경이 기존 지표에 미치는 영향 분석
- 동료가 검토할 수 있는 구조와 명명 방식 적용

SQL 결과는 일부 샘플만 보고 신뢰하지 않습니다. 원천 총량, 고유 키, 기간별 건수 및 업무 기준값과의 대조가 필요합니다.

## Python 분석 역량
<!--meta: sec=s13; dept=DATA; level=주니어|시니어; ct_band=중; related=s3|s12|s22-->
Python은 전처리, 통계 분석, 시각화, 예측 검증 및 반복 작업 자동화에 활용합니다. pandas 사용 경험은 필수적인 기반 역량이지만, 라이브러리 함수 호출보다 데이터 변환 과정의 정확성을 중요하게 봅니다.

기대 역량은 다음과 같습니다.

- 명시적인 데이터형 변환
- 결측값과 중복값 처리 조건 기록
- 그룹 집계와 피벗 결과 검증
- 날짜 인덱스와 시계열 정렬 처리
- 함수 단위로 반복 로직 분리
- 입력값과 출력값의 기본 검증
- 난수 시드와 실행 환경 등 재현 조건 관리
- 중간 산출물의 목적과 생성 기준 기록
- 분석용 시각화와 보고용 시각화 구분
- 메모리 사용량을 고려한 데이터 처리
- 코드 실행 순서에 따라 결과가 달라지는 상태 최소화

노트북 환경을 사용할 수 있으나, 중요한 분석 결과는 셀 실행 순서에 의존하지 않도록 정리해야 합니다. 반복 수행되는 분석은 가능한 범위에서 함수나 스크립트로 구조화합니다.

## 대시보드 설계 원칙
<!--meta: sec=s14; dept=DATA; level=주니어|시니어; ct_band=중; related=s4|s5|s18-->
대시보드는 많은 차트를 한 화면에 배치하는 것이 아니라 사용자가 필요한 결정을 빠르게 내릴 수 있도록 정보를 구조화한 제품입니다.

설계 시 다음을 확인합니다.

- 주요 사용자는 누구인가
- 사용자가 대시보드를 보는 빈도는 어느 정도인가
- 조회 후 어떤 행동이나 판단을 수행하는가
- 가장 먼저 확인해야 할 핵심 지표는 무엇인가
- 지표가 정상인지 비정상인지 판단할 기준이 있는가
- 필터 선택에 따라 지표 정의가 달라지지 않는가
- 데이터 기준 시각과 최근 갱신 시각이 표시되는가
- 빈 값과 0이 시각적으로 구분되는가
- 상세 데이터로 내려갈 수 있는 경로가 필요한가
- 조회 결과를 해석할 때 주의할 조건이 표시되는가

차트 유형은 데이터 특성과 질문에 맞춰 선택합니다. 시간 변화는 선 그래프, 항목 간 규모 비교는 막대그래프, 구성 비율은 제한된 범주에서 활용하며, 의미 없는 3차원 효과나 과도한 색상 사용은 지양합니다.

지표 정의서는 같은 이름의 지표가 사람마다 다르게 계산되는 문제를 방지하기 위한 기준 문서입니다. 각 지표에는 가능한 범위에서 다음 항목을 포함합니다.

- 지표명과 영문명
- 지표의 업무 목적
- 계산식
- 분자와 분모
- 집계 단위

- 값이 확정되는 시점
- 반올림 및 표시 규칙

## 운영 AI 성능 모니터링

데이터분석팀은 AI/AX개발팀이 만든 모델의 운영 성능을 데이터로 감시합니다. 이때 데이터 분석가는 모델을 직접 서빙하는 역할과 구분하여, 성능 측정 기준과 변화 해석에 집중합니다.

모니터링 범위에는 다음 항목이 포함될 수 있습니다.

- 입력 데이터 건수와 누락률
- 입력값 분포 변화
- 예측 결과 분포 변화
- 실제값 확보율과 확보 지연
- 평가 가능한 표본의 대표성
- 전체 및 세그먼트별 성능
- 기준선 대비 성능 차이
- 과대·과소 예측 편향
- 저신뢰 결과의 비율
- 업무 예외 케이스의 증가 여부
- 모델 또는 데이터 변경 전후 차이
- 지표 산출 실패와 갱신 지연

운영 성능이 저하되었다고 판단하기 전에 실제 모델 문제, 입력 데이터 변화, 정답 데이터 지연, 지표 계산 오류 및 고객 업무 정책 변경을 구분해야 합니다.

## 분석 검증과 재현성
<!--meta: sec=s17; dept=DATA; level=주니어|시니어; ct_band=상; related=s7|s12|s22-->
분석 결과는 작성자 개인의 환경에서 한 번 생성되는 것으로 끝나지 않아야 합니다. 다른 구성원이 동일한 조건으로 유사한 결과를 재현할 수 있어야 합니다.

기본 검증 항목은 다음과 같습니다.

- 사용 데이터의 기준 시점 기록
- 원천 테이블과 추출 조건 기록
- 분석 대상 기간 명시
- 코드 및 쿼리 버전 관리
- 실행 순서와 의존 파일 설명
- 주요 중간 산출물의 행 수와 합계 확인
- 조인 전후 고유 키 수 비교
- 표본 레코드 수동 대조
- 계산 결과의 독립적인 대조식 확인
- 시각화 값과 원본 집계값 일치 여부 확인
- 결과 변경 시 원인과 영향 범위 기록
- 동료 검토 결과와 수정 사항 반영

재현성은 모든 작업을 완전히 자동화한다는 의미가 아닙니다. 누가, 언제, 어떤 조건으로 수행했는지를 설명할 수 있고 핵심 결론을 다시 검증할 수 있는 상태를 의미합니다.

## 고객 커뮤니케이션
<!--meta: sec=s18; dept=DATA; level=주니어|시니어; ct_band=중; related=s8|s14|s15-->
데이터 분석가는 기술적 결과를 고객의 업무 언어로 번역해야 합니다. 고객 보고 시 다음 구조를 권장합니다.

1. 해결하려는 업무 질문
2. 분석 대상과 데이터 범위
3. 핵심 발견 사항
4. 발견 사항의 업무적 의미
5. 확인된 한계와 미확인 사항
6. 권고 행동 또는 추가 검토 항목
7. 다음 갱신 또는 재검증 계획

다음과 같은 표현은 주의해야 합니다.

- 상관관계만으로 원인 관계가 확정되었다고 설명하는 표현
- 제한된 기간의 결과를 전체 기간에 일반화하는 표현
- 표본 수가 작은 세그먼트의 수치를 단정적으로 해석하는 표현
- 데이터가 존재하지 않는 항목을 0으로 간주하는 표현
- 모델 개선이 곧바로 업무 성과 개선을 보장한다는 표현
- 검증되지 않은 추정을 확정된 사실처럼 전달하는 표현

주니어는 검토된 자료를 바탕으로 담당 범위를 설명할 수 있어야 하며, 시니어는 분석 설계와 한계를 포함한 전체 보고를 주도할 수 있어야 합니다.

## 직급 및 경력 수준별 기대 역할
<!--meta: sec=s19; dept=DATA; level=사원|대리|과장|차장|부장; ct_band=중; related=s3|s9|s23-->
헤드헌터랩의 직급 체계는 사원-대리-과장-차장-부장으로 구성됩니다. 직급은 역할 판단의 한 요소이며, 실제 책임 범위는 경력, 프로젝트 경험 및 과업 난이도를 함께 고려합니다.

- 정해진 분석 기준에 따라 데이터 추출과 기초 분석 수행
- 데이터 품질 점검표 작성
- 기존 지표와 쿼리의 의미 파악
- 분석 과정과 결과를 문서로 남김
- 검토 의견을 반영하여 산출물 수정

- 지표 정의의 모호한 부분을 식별하고 질문

- 수요예측 평가 체계와 품질 기준 설계

- 고난도 의사결정 및 대외 커뮤니케이션 지원
- 분석 역량 체계와 구성원 성장 방향 관리
- 반복 가능한 분석 자산과 운영 기준 확산

## 주니어와 시니어의 차이
<!--meta: sec=s20; dept=DATA; level=주니어|시니어; ct_band=하; related=s10|s16|s19-->
헤드헌터랩은 0~3년 경력자를 주니어, 4년 이상 경력자를 시니어로 구분합니다.

### 주니어 데이터 분석가
- 주어진 질문을 이해하고 필요한 데이터를 확인합니다.
- 지도 하에 전처리, EDA 및 분석 보고서를 작성합니다.
- 기존 지표 정의와 검증 절차를 정확히 따릅니다.
- 이상한 값이나 모호한 조건을 발견하면 임의 처리하지 않고 공유합니다.
- 본인이 수행한 코드와 결과를 설명할 수 있어야 합니다.
- 피드백을 반영해 분석의 정확성과 문서 품질을 개선합니다.

### 시니어 데이터 분석가
- 모호한 업무 요청을 분석 가능한 문제로 정의합니다.
- 데이터 확보 가능성과 한계를 고려해 분석 설계를 수립합니다.
- 분석 설계부터 고객 보고까지 단독 수행할 수 있습니다.
- 지표, 검증 기준 및 운영 모니터링 방식을 설계합니다.
- 데이터 문제와 모델 문제를 구분해 조사 방향을 제시합니다.
- 주니어의 분석 결과를 검토하고 판단 근거를 설명합니다.
- 기술적 정확성과 고객 활용 가능성 사이의 균형을 관리합니다.

시니어는 단순히 더 복잡한 코드를 작성하는 사람이 아니라, 불확실한 상황에서 분석 범위와 판단 기준을 명확히 세우는 사람입니다.

## 협업 부서와 역할 경계
<!--meta: sec=s21; dept=DATA; level=주니어|시니어; ct_band=중; related=s11|s15|s24-->
데이터분석팀은 여러 부서와 긴밀하게 협업하되 각 조직의 책임을 구분합니다.

### 컨설팅팀과의 협업
- 고객의 업무 목표와 의사결정 구조 확인
- 분석 질문과 기대 효과 구체화
- 고객 커뮤니케이션 일정 및 보고 범위 조율
- 분석 결과의 업무 적용 시나리오 검토

### AI/AX개발팀과의 협업
- 모델 학습 및 평가에 필요한 데이터 기준 협의
- 모델 성능 지표와 세그먼트 정의
- 운영 성능 변화와 데이터 분포 변화 분석
- 모델 결과의 업무적 해석 지원

### 백엔드팀과의 협업
- 분석 및 대시보드에 필요한 데이터 제공 방식 협의
- 컬럼 의미, 키 구조, 갱신 주기 및 상태값 확인
- 데이터 변경이 분석 지표에 미치는 영향 전달
- 조회 결과 불일치 시 재현 조건 공유

### 영업팀과의 협업
- 제안 전 분석 가능 범위와 전제조건 검토
- 고객이 기대하는 결과와 실제 제공 가능한 결과의 차이 설명
- 분석 산출물의 공개 가능 범위 확인
- 과도하게 확정적인 성능 표현 방지

데이터 분석가는 백엔드 서비스 구현이나 모델 서빙 설정을 직접 소유하지 않으며, 분석 관점에서 필요한 기준과 검증 결과를 명확히 제공하는 역할을 담당합니다.

## 분석 코드 및 문서 관리
<!--meta: sec=s22; dept=DATA; level=주니어|시니어; ct_band=중; related=s13|s17|s25-->
분석 자산은 개인 PC나 임시 파일에만 남기지 않고 프로젝트에서 합의한 저장 위치와 명명 규칙에 따라 관리합니다.

권장 관리 원칙은 다음과 같습니다.

- 파일명에 목적과 기준 기간을 식별할 수 있게 작성
- 원본 데이터와 가공 데이터를 구분
- 수동 수정된 파일은 수정 이유와 담당자를 기록
- 분석 코드와 보고용 결과 파일을 연결할 수 있게 관리
- 임시 실험과 공식 산출물을 구분
- 쿼리와 코드에 업무 조건을 주석으로 기록
- 주요 변경은 버전 관리 이력에 목적을 남김
- 사용하지 않는 코드와 폐기된 지표를 명확히 표시
- 외부 공유 전 데이터와 메타정보의 공개 가능 범위 확인
- 동일한 지표를 여러 파일에서 독립적으로 계산하지 않도록 관리

문서화는 분석 완료 후 형식적으로 추가하는 작업이 아니라, 분석 과정 중 판단과 변경을 축적하는 활동입니다.

## 업무 품질 기준과 완료 조건
<!--meta: sec=s23; dept=DATA; level=주니어|시니어; ct_band=상; related=s5|s17|s19-->
분석 업무는 그래프나 보고서 파일을 전달했다는 이유만으로 완료되지 않습니다. 다음 조건을 충족했는지 확인합니다.

- 업무 질문과 분석 결과가 직접 연결되어 있음
- 데이터 범위와 기준 시점이 명시되어 있음
- 지표 계산 방식이 문서화되어 있음
- 핵심 결과가 원천 또는 대조 집계와 일치함
- 결측, 중복 및 이상치 처리 방식이 설명되어 있음
- 결과를 왜곡할 수 있는 제한 사항이 기재되어 있음
- 고객 또는 내부 사용자가 결과를 해석할 수 있음
- 후속 갱신이 필요한 경우 담당과 주기가 정리되어 있음
- 코드와 쿼리를 다시 실행할 수 있는 조건이 남아 있음
- 검토 의견과 반영 여부가 확인됨
- 외부 공유 범위가 적절한지 점검됨

고난도 분석의 경우 추가로 민감도 분석, 세그먼트별 검증, 기준선 비교 및 변경 영향도 확인을 수행할 수 있습니다.

## 직무에서 자주 마주치는 상황
<!--meta: sec=s24; dept=DATA; level=주니어|시니어; ct_band=상; related=s8|s16|s21-->
### 데이터 총량이 고객의 기존 보고서와 다른 경우
즉시 어느 한쪽이 틀렸다고 판단하지 않습니다. 기준 기간, 취소 처리, 중복 제거, 상태값, 시간대, 마감 시점 및 제외 조건을 차례로 비교합니다.

### 고객이 정확도 하나만 요청하는 경우
정확도의 정의, 평가 대상, 평가 기간 및 업무 비용을 확인합니다. 필요하면 편향이나 세그먼트별 오차 등 보조 지표를 함께 제안합니다.

### 모델 성능이 갑자기 낮아진 경우
모델 자체의 변화뿐 아니라 입력 데이터 분포, 실제값 수집 지연, 평가 표본 구성, 지표 로직 변경 및 업무 정책 변경을 함께 확인합니다.

### 대시보드 수치와 보고서 수치가 다른 경우
두 산출물의 원천, 갱신 시각, 집계 단위, 필터 기본값, 반올림 및 확정 데이터 기준을 비교합니다.

### 원천 데이터의 의미가 문서와 다른 경우
실제 레코드와 업무 담당자의 설명을 확인하고, 기존 정의서의 수정 필요 여부를 기록합니다. 임의 해석으로 분석을 계속하지 않습니다.

### 요청 기한 내 충분한 검증이 어려운 경우
검증된 범위와 미검증 범위를 구분하고, 임시 결과의 사용 제한을 명시합니다. 확정 결과처럼 표현하지 않습니다.

초기 적응 기간에는 회사와 프로젝트의 분석 기준을 이해하고 작은 범위의 과업부터 책임지는 것을 목표로 합니다.

### 초기 단계
- 헤드헌터랩의 부서별 역할과 협업 방식 이해
- 프로젝트 문서와 데이터 용어 확인
- 기존 지표 정의서와 분석 보고서 검토
- 개발 환경과 저장소 사용 방식 숙지
- 샘플 데이터로 기존 분석 결과 재현

### 과업 참여 단계

- 동료 검토를 통한 분석 방식 개선

### 역할 확장 단계

- 반복 업무의 표준화 또는 자동화 제안
- 지표 정의와 품질 규칙 개선에 참여

시니어는 적응 속도에 따라 초기부터 분석 설계, 고객 협의 및 구성원 검토 역할을 함께 수행할 수 있습니다.

## 성장 경로
<!--meta: sec=s26; dept=DATA; level=주니어|시니어; ct_band=중; related=s19|s25|s27-->
데이터 분석가는 개인의 강점과 프로젝트 경험에 따라 다음 방향으로 전문성을 확장할 수 있습니다.

- **분석 전문가:** 복잡한 데이터 구조와 통계 문제를 깊이 있게 해결
- **수요예측 전문가:** 시계열 검증, 재고 및 수요 의사결정에 특화
- **BI·지표 전문가:** 경영 및 운영 대시보드와 지표 체계를 설계
- **데이터 품질 전문가:** 품질 규칙, 데이터 계약 및 검증 체계를 고도화
- **AI 성능 분석 전문가:** 운영 모델의 성능과 데이터 변화를 분석
- **분석 리드:** 복수 분석 과업의 방향, 품질 및 고객 커뮤니케이션을 관리

성장은 더 많은 도구를 사용하는 것만으로 판단하지 않습니다. 문제 정의의 정확성, 결과의 신뢰성, 고객 의사결정 기여도, 협업 품질 및 동료 성장 지원을 함께 고려합니다.

## 직무 적합성을 보여주는 경험
<!--meta: sec=s27; dept=DATA; level=주니어|시니어; ct_band=중; related=s3|s4|s26-->
다음과 같은 경험은 데이터 분석가 직무 역량을 구체적으로 보여줄 수 있습니다.

- 모호한 요청을 분석 가능한 질문으로 바꾼 경험
- 잘못된 조인이나 집계 기준을 발견해 결과를 수정한 경험
- 결측치나 중복의 업무적 원인을 확인한 경험
- 단순 기준선과 후보 모델을 공정하게 비교한 경험
- 평균 지표에 가려진 특정 세그먼트 문제를 발견한 경험
- 고객의 기존 수치와 분석 결과가 다른 원인을 설명한 경험
- 대시보드 사용자의 행동을 고려해 화면을 개선한 경험
- 분석 한계와 불확실성을 명시해 잘못된 의사결정을 예방한 경험
- 반복 분석을 재현 가능한 코드나 문서로 정리한 경험
- 본인의 분석 결과가 틀렸음을 확인하고 수정한 경험

경험을 설명할 때에는 사용 도구만 나열하기보다 문제, 데이터, 본인의 판단, 검증 방식, 결과, 한계 및 개선 내용을 함께 제시하는 것이 좋습니다.

## 직무 수행 시 지양하는 방식
<!--meta: sec=s28; dept=DATA; level=주니어|시니어; ct_band=하; related=s17|s18|s23-->
다음과 같은 방식은 분석 결과의 신뢰성과 협업 품질을 낮출 수 있습니다.

- 데이터 정의를 확인하지 않고 컬럼명만으로 의미를 추정
- 결측값과 이상치를 근거 없이 삭제
- 시간 순서를 무시한 학습·검증 데이터 분할
- 좋은 결과가 나온 지표만 선택해 보고
- 전체 평균만 제시하고 중요한 세그먼트 차이를 숨김
- 상관관계를 원인 관계로 단정
- 수동 수정한 데이터를 원본처럼 사용
- 지표 계산식을 문서화하지 않음
- 고객이 원하는 결론에 맞춰 분석 조건을 변경
- 검증되지 않은 결과를 확정 수치로 전달
- 오류를 발견하고도 영향 범위를 확인하지 않음
- 코드와 결과를 개인 환경에만 보관

헤드헌터랩은 빠른 결과만큼 검증 가능한 결과를 중요하게 봅니다. 불확실성을 숨기는 것보다 현재 확인 가능한 범위와 추가 확인이 필요한 범위를 명확히 구분하는 태도를 기대합니다.

## 주요 용어
<!--meta: sec=s29; dept=DATA; level=주니어|시니어; ct_band=하; related=s7|s9|s15-->
- **EDA:** 탐색적 데이터 분석. 데이터 구조, 분포, 이상치 및 품질 문제를 파악하는 과정입니다.
- **관측 단위:** 분석 데이터 한 행이 의미하는 대상입니다. 거래, 고객, 상품, 일자 등이 될 수 있습니다.
- **기준선 모델:** 복잡한 모델의 개선 여부를 판단하기 위한 단순 비교 방식입니다.
- **백테스트:** 과거 시점에 예측했다고 가정하여 미래 구간의 성능을 검증하는 방법입니다.
- **데이터 누수:** 예측 시점에는 알 수 없는 정보가 학습이나 평가에 포함되는 문제입니다.
- **편향:** 예측값이 실제값보다 지속적으로 높거나 낮은 방향성을 보이는 현상입니다.
- **세그먼트:** 상품군, 고객군, 채널, 지점 등 분석 목적에 따라 구분한 집단입니다.
- **데이터 드리프트:** 운영 중 입력 데이터의 분포나 특성이 기존과 달라지는 현상입니다.
- **지표 정의서:** 지표의 목적, 계산식, 대상, 기간, 제외 조건 및 갱신 기준을 정리한 문서입니다.
- **재현성:** 동일한 데이터와 조건에서 분석 과정을 다시 수행하고 결과를 검증할 수 있는 성질입니다.
- **데이터 사전:** 테이블과 컬럼의 의미, 형식, 값 범위 및 관계를 정리한 문서입니다.
- **업무적 중요성:** 통계적으로 관찰된 차이가 실제 업무 의사결정이나 비용에 의미 있는 영향을 주는 정도입니다.
