# 업셀·크로스셀 기회 발굴 가이드
<!--meta: doc=CSM-06; doc_type=playbook; tier=2; topic=CS; disclosure=internal; status=active-->

## 목적과 원칙 — 고객 성과가 먼저다
<!--meta: sec=s1; dept=CNS|SALES; level=주니어|시니어; ct_band=하; related=s2-->
확장은 고객이 기존 계약 범위에서 확인한 성과를 더 넓히는 활동입니다. 헤드헌터랩은 추가 매출 자체를 확장 제안의 출발점으로 삼지 않으며, 고객의 업무 성과·정착 수준·해결되지 않은 사업 과제를 먼저 확인합니다.

성과 확인 없이 기능, 인력, 사용 범위 또는 운영 서비스를 추가로 제안하면 고객이 판매 압박으로 받아들일 수 있습니다. 또한 미정착 원인을 추가 구매로 덮어 구축 실패, 운영 공수 증가, 갱신 위험을 동시에 키울 수 있으므로 근거 없는 확장 제안을 금지합니다.

**확장 검토 개시 원칙**

| 판정 항목 | 최소 기준 | 기준 미달 시 처리 | 확인 책임 |
| --- | --- | --- | --- |
| 기존 성과 | 합의된 성공 지표 중 1개 이상 개선 확인 | 확장 대화를 시작하지 않음 | CNS |
| 고객 확인 | 현업 책임자가 성과 또는 개선 효과를 확인 | 내부 추정으로 제안하지 않음 | CNS |
| 기존 범위 안정성 | 치명적 미결 이슈가 없고 핵심 업무가 사용 중 | 안정화 조치를 우선함 | CNS·수행팀 |
| 추가 과제 | 현재 계약 범위 밖의 문제 또는 확대 수요가 식별됨 | 일반 문의로 관리함 | CNS·SALES |

성과 증거는 고객이 승인한 KPI, 사용 데이터, 완료된 마일스톤, 업무시간 절감 기록 또는 운영 책임자의 확인 중 하나 이상이어야 합니다. 단순한 긍정 발언, 담당자의 개인적 관심, 예산 잔액 추정만으로는 성과 확인을 대체할 수 없습니다.

**문서 적용 범위**

| 구분 | 이 문서에서 다루는 범위 | 후속 담당 문서 |
| --- | --- | --- |
| 확장 신호 | 사용·관계·상업 신호의 식별과 분류 | CSM-06 |
| 기회 판단 | 신호 강도와 고객 적합성에 대한 자격 검증 | CSM-06 |
| 영업 연결 | CNS에서 SALES로 넘기는 기준과 정보 | CSM-06 |
| 제안 실행 | 제안서, 가격, 견적, 계약 조건 | PRP-xx |
| 신규 고객 | 타겟 선정, 리드 발굴, 최초 접촉 | SLS-xx |
| 기술 검토 | 구현 가능성 및 기술 검증 | DSC-xx |

이 문서는 구축 프로젝트의 추가 범위와 구축 후 운영·유지보수 고객의 확장을 모두 적용 대상으로 합니다. 기존 계약의 단순 갱신이나 물가·요율 조정은 확장 기회로 다루지 않으며 CSM-05를 적용합니다.

**실무 행동 원칙**

- 고객 성과를 설명할 수 없는 담당자는 확장 미팅을 요청하지 않습니다.
- 고객 문제보다 판매 품목을 먼저 정하지 않습니다.
- 기존 미결 장애나 납기 지연을 추가 계약의 조건으로 연결하지 않습니다.
- 성과 근거와 추가 과제를 분리하여 확인합니다.
- SALES 이관 전까지 CNS가 고객 맥락과 성과 근거의 정확성을 책임집니다.

## 업셀과 크로스셀의 구분
<!--meta: sec=s2; dept=CNS|SALES; level=주니어; ct_band=중; related=s1|s3-->
업셀은 고객이 현재 구매한 범위의 용량, 수준 또는 성능을 상향하는 확장입니다. 크로스셀은 현재 계약과 구별되는 인접 업무, 신규 서비스 또는 별도 과제를 추가하는 확장입니다.

두 유형은 매출 증가라는 결과는 같지만 구매 논리가 다릅니다. 업셀은 기존 사용과 한도에 대한 증거가 중심이며, 크로스셀은 새로운 문제의 중요성, 별도 예산, 신규 이해관계자 확인이 중심입니다.

**유형별 구분 기준**

| 유형 | 정의 | 예시 범주 | 통상 리드타임 | 주 담당 |
| --- | --- | --- | --- | --- |
| 업셀－사용 범위 | 동일 솔루션의 부서·지점·사용자·처리량 확대 | 추가 사용자, 추가 지점, 용량 증설 | 2~6주 | CNS·SALES |
| 업셀－서비스 수준 | 동일 운영 범위의 지원 수준 또는 관리 강도 상향 | 운영 등급 상향, 모니터링 범위 확대 | 2~4주 | CNS·SALES |
| 업셀－기능 수준 | 기존 업무 흐름의 기능·자동화·성능 고도화 | 고급 기능, 추가 연동, 모델 성능 개선 | 4~12주 | CNS·SALES |
| 크로스셀－인접 업무 | 기존 성과를 다른 업무 영역에 적용 | 타 부서 업무, 신규 업무 프로세스 | 6~16주 | CNS·SALES |
| 크로스셀－별도 전문 과제 | 기존 계약과 다른 산출물·전문역량을 추가 | 데이터 분석, 별도 AI/AX 과제 | 6~16주 이상 | CNS·SALES |

리드타임은 고객 수요 확인일부터 계약 범위 합의일까지의 내부 계획 기준입니다. 고객의 예산 승인, 보안 심사, 데이터 제공 또는 구매 절차가 추가되면 표의 상한을 넘을 수 있으며, 해당 사실만으로 유형을 변경하지 않습니다.

**구분 판정 질문**

| 판정 질문 | ‘예’인 경우 | ‘아니요’인 경우 |
| --- | --- | --- |
| 기존 계약의 동일 업무를 더 많이 사용하는가 | 사용 범위 업셀 | 다음 질문으로 이동 |
| 동일 업무의 서비스·기능 수준을 높이는가 | 서비스 또는 기능 업셀 | 다음 질문으로 이동 |
| 새로운 부서라도 동일 업무와 동일 산출물을 쓰는가 | 사용 범위 업셀 가능 | 신규 업무 여부 확인 |
| 별도 업무 문제와 독립 산출물이 필요한가 | 크로스셀 | 변경 요청 가능성 확인 |

업셀의 주요 의사결정자는 기존 서비스 책임자, 운영 책임자 또는 예산 소유자인 경우가 많습니다. 크로스셀은 신규 업무 부서장, 데이터 책임자, 정보기술 책임자 등 기존 계약에 참여하지 않았던 의사결정자가 추가될 가능성이 높습니다.

따라서 유형을 잘못 분류하면 필요한 인터뷰 대상과 자격 검증 자료가 누락됩니다. 하나의 요구에 용량 확대와 신규 업무가 함께 포함되면 각각을 분리해 판정하고, 고객의 구매 단위가 확정된 뒤 하나의 확장안으로 묶을 수 있습니다.

**분류 시 제외 사항**

- 기존 계약 범위에 이미 포함된 기능 제공은 업셀이 아닙니다.
- 하자 보완이나 미완료 산출물 처리는 크로스셀이 아닙니다.
- 단순 갱신 가격 조정은 CSM-05를 적용합니다.
- 파이프라인 등록 및 단계 판정은 FCT-01을 적용합니다.

## 확장 제품·서비스 지도
<!--meta: sec=s3; dept=CNS|AIAX|BE|DATA; level=시니어; ct_band=상; related=s2|s4-->
확장 제품·서비스 지도는 고객의 추가 과제를 헤드헌터랩의 수행 범주와 연결하기 위한 내부 라우팅 기준입니다. 고객 요청 문구를 그대로 품목으로 만들지 않고, 기대 성과와 기존 계약 대비 변경되는 범위를 기준으로 분류합니다.

각 범주는 표에 명시된 전제 조건이 충족될 때만 후보로 유지합니다. 전제 조건은 수주 가능성이 아니라 검토를 계속할 수 있는 최소 조건이며, 구현 가능성에 대한 최종 판단은 DSC-xx를 적용합니다.

**확장 범주 지도**

| 범주 | 내용 | 전제 조건 | 담당팀 |
| --- | --- | --- | --- |
| 사용 범위 확대 | 기존 솔루션을 추가 부서·지점·사용자 또는 처리량에 적용 | 기존 범위가 안정적으로 사용되고 신규 대상의 업무가 동일하거나 표준화 가능함 | CNS 주관, AIAX·BE 협업 |
| 기능 고도화 | 자동화 단계, 연동, 관리 기능 또는 사용자 기능 추가 | 기존 기능의 실제 사용 근거와 미충족 업무 요구가 구분되어 있음 | CNS 주관, AIAX·BE |
| 운영 서비스 등급 상향 | 관제, 대응시간, 운영 리포트 또는 지원 범위 강화 | 현재 운영량과 지원 공수가 측정되고 상향 필요성이 반복적으로 확인됨 | CNS 주관, BE·AIAX |
| 인접 업무 영역 확장 | 기존 성과를 다른 프로세스나 조직 업무에 적용 | 신규 업무 책임자와 문제 정의가 존재하고 기존 자산의 재사용 가능성이 있음 | CNS 주관, AIAX·BE·DATA |
| 데이터 분석 과제 추가 | 별도 분석, 지표 체계, 예측 또는 의사결정 지원 과제 수행 | 분석 목적, 활용 의사결정, 데이터 보유 주체가 확인됨 | DATA 주관, CNS 협업 |
| 모델 재학습·성능 개선 | 데이터 변화에 따른 재학습, 평가, 튜닝 또는 성능 개선 | 기준 성능, 최근 성능 저하, 평가 데이터와 목표 지표가 확인됨 | AIAX 주관, DATA 협업 |

사용 범위 확대는 신규 대상이 기존 업무 정의를 그대로 사용할 수 있는지가 핵심입니다. 대상 부서별로 승인 절차, 데이터 구조 또는 결과물 정의가 달라지면 단순 증설이 아니라 인접 업무 영역 확장으로 재분류합니다.

기능 고도화는 고객이 실제로 사용하는 업무 흐름에서 병목이 확인되어야 합니다. 사용되지 않는 기존 기능이 남아 있는 상태에서 유사 기능을 추가해 달라는 요청은 교육·구성 문제와 개발 요구를 먼저 분리합니다.

**범주 선택 시 확인할 경계**

| 경계 상황 | 적용 범주 | 판정 근거 |
| --- | --- | --- |
| 동일 기능을 다른 지점에 배포 | 사용 범위 확대 | 업무와 산출물이 동일함 |
| 기존 결과에 승인 자동화를 추가 | 기능 고도화 | 동일 업무 흐름의 단계가 늘어남 |
| 신규 조직의 별도 의사결정 문제 해결 | 인접 업무 영역 확장 | 문제 소유자와 업무 목적이 달라짐 |
| 성능 저하 없이 정기 재학습만 요청 | 운영 범위 또는 별도 과제 검토 | 계약상 포함 여부를 먼저 확인함 |
| 신규 데이터로 별도 예측 지표 개발 | 데이터 분석 과제 추가 | 신규 분석 목적과 평가 지표가 존재함 |

하나의 요청이 여러 범주에 걸치면 고객 성과를 직접 만드는 주 범주 1개와 이를 가능하게 하는 보조 범주를 구분합니다. 예를 들어 신규 부서 적용에 연동 개발이 필요한 경우 주 범주는 사용 범위 확대이며, 연동은 기능 고도화 검토 항목으로 둡니다.

고객에게 범주명을 그대로 제시할 필요는 없습니다. 내부에서는 범주별 주 담당팀을 먼저 지정하고, 데이터·보안·아키텍처 검토가 필요한 팀을 협업 담당으로 연결합니다.

## 확장 신호 분류 — 사용·관계·상업
<!--meta: sec=s4; dept=CNS|DATA; level=시니어; ct_band=상; related=s3|s5-->
확장 신호는 사용 신호, 관계·이해관계자 신호, 상업적 신호의 세 종류로 분류합니다. 분류 목적은 고객의 발언 하나를 즉시 영업 기회로 간주하지 않고, 신호가 나타난 원인과 확인해야 할 증거를 구별하는 데 있습니다.

사용·참여 신호는 갱신 캘린더 날짜보다 실제 업셀 적기를 더 잘 예측합니다. 따라서 정기 갱신일이 가까워졌다는 이유만으로 확장을 제안하지 않으며, 고객 행동과 조직 참여의 변화가 발생한 시점을 우선 관찰합니다.

**신호 3분류 기준**

| 분류 | 의미와 대표 관찰 대상 | 관찰 난이도 | 통상 선행 기간 | 상대 신뢰도 |
| --- | --- | --- | --- | --- |
| 사용 신호 | 사용량, 처리량, 기능 깊이, 용량 한도, 수작업 우회, 외부 도구 반출 | 낮음~중간 | 구매 검토 30~120일 전 | 높음 |
| 관계·이해관계자 신호 | 챔피언 참여, 신규 부서 문의, 경영진 관심, 담당 조직 확대 | 중간 | 구매 검토 30~90일 전 | 중간~높음 |
| 상업적 신호 | 예산 편성, 견적 요청, 구매 절차 문의, 계약 범위 질문 | 낮음 | 구매 검토 7~60일 전 | 높으나 시점이 늦음 |

사용 신호는 시스템 로그나 운영 데이터로 반복 확인할 수 있어 가장 객관적입니다. 다만 사용량 증가는 업무량의 일시적 급증일 수 있고, 사용량 감소는 계절성이나 조직 휴무의 영향일 수 있으므로 해당 계정의 기존 기준선과 비교합니다.

상업적 신호는 구매 행동과 가까워 관찰 후 대응 시간이 짧습니다. 견적 요청이 있더라도 고객 문제, 예산 소유자 또는 적용 범위가 확인되지 않으면 가격 탐색이나 시장 조사일 수 있으므로 즉시 확정 기회로 해석하지 않습니다.

1. 발견자는 원문 URL, 게시일, 확인일, 핵심 문구를 기록합니다.
2. CNS는 2영업일 내 기존 고객 조직도 및 이해관계자 목록과 대조합니다.

개인의 가족관계, 사적 활동, 정치 성향, 비공개 경력은 수집하지 않습니다. 공개 정보라도 확장 판단에 필요하지 않은 개인 정보는 기록 대상에서 제외합니다.

**해석 제한**

- 채용 공고만으로 구매 일정이나 인원 충원을 확정하지 않습니다.
- 조직명 변경만으로 실제 업무 범위 확대를 인정하지 않습니다.
- 챔피언 승진 시 후임 부재가 확인되면 확장보다 관계 복구를 우선합니다.

| 약 | 1점 | 단일 관찰이며 고객 행동·지속성이 확인되지 않습니다 | 일시적 사용량 증가, 관련 채용 공고 1건 | 근거를 보강하고 다음 관찰일을 지정합니다 |
| 중 | 2점 | 2회 이상 반복되거나 고객이 문제·관심을 명시합니다 | 2주 연속 수작업 우회, 타 부서의 기능 문의 | 5영업일 내 업무 배경을 확인합니다 |
| 강 | 3점 | 예산·일정·담당자·기술 행동 중 2개 이상이 확인됩니다 | 용량 80% 도달과 증설 일정 문의, 공식 연동 요청 | 2영업일 내 확장 검토를 개시합니다 |

복합 신호 점수는 사용 신호 45%, 관계·조직 신호 30%, 상업적 신호 25%로 계산합니다. 각 분류의 점수는 해당 분류에서 가장 강한 신호 2개의 평균을 사용하며, 신호가 없으면 0점으로 처리합니다.

`기본점수 = [(사용 평균÷3)×45] + [(관계 평균÷3)×30] + [(상업 평균÷3)×25]`

| 복합 조건 | 가산점 | 적용 조건 |
| --- | ---: | --- |
| 서로 다른 2개 분류에서 신호 발생 | +10점 | 각 분류에 중 이상 신호가 1개 이상 있습니다 |
| 3개 분류 모두에서 신호 발생 | +15점 | +10점과 중복 적용하지 않습니다 |
| 동일 활용 사례를 지지하는 강 신호 2개 | +10점 | 지표·고객 발언 등 근거 출처가 서로 다릅니다 |
| 사용량 증가+신규 채용+신규 활용 사례 | 최우선 P0 | 세 신호가 모두 유효기간 내 확인됩니다 |
| 상충 신호 발생 | -15점 | 예산 동결, 프로젝트 중단 등 반대 근거가 확인됩니다 |

가산 후 점수는 최대 100점으로 제한합니다. 70점 이상은 강, 40~69점은 중, 39점 이하는 약으로 분류합니다.

확장 신호가 2개 이상 동시에 나타난 계정은 단일 신호 계정보다 우선합니다. 특히 `사용량 증가 + 신규 채용 + 신규 활용 사례` 조합은 업셀 전환율이 가장 높은 패턴이므로 점수와 무관하게 당일 검토 목록의 최상단에 배치합니다.

**신호 점수와 헬스 밴드 교차 우선순위**

| 헬스 밴드 | 강 신호 70~100 | 중 신호 40~69 | 약 신호 0~39 |
| --- | --- | --- | --- |
| 정상 | P0: 2영업일 내 확장 가설 검토 | P1: 5영업일 내 확인 대화 | P2: 다음 정례 접점에서 확인 |
| 관찰 | P1: 원인 확인 후 성과 연계 가능 시 검토 | P2: 7일 내 관계·사용 맥락 보강 | P3: 모니터링만 유지 |
| 위험 | P2: 고객 업무 연속성 관련 수요만 검토 | P3: 위험 원인 해소 전 제안 보류 | 제외: 확장 접촉 금지 |

헬스 밴드는 CSM-03의 확정 값을 사용하며 확장 기대를 이유로 수동 상향하지 않습니다. 위험 계정에서 발견된 기술 증설 필요는 매출 기회가 아니라 서비스 연속성 조치인지 먼저 구분합니다.

판정자는 신호별 근거일, 강도, 분류, 중복 제외 사유를 남깁니다. 점수만 있고 원문 근거가 없으면 복합 신호로 인정하지 않습니다.

## 신호의 유효기간과 대응 속도
<!--meta: sec=s8; dept=CNS; level=시니어; ct_band=중; related=s7|s9-->
모든 확장 신호에는 유효기간이 있습니다. 고객이 내부 개발, 경쟁 도구 도입, 업무 중단, 예산 전용 등 다른 방법으로 문제를 해결하면 최초 신호가 강했더라도 기회는 소멸합니다.

대응 기한은 제안서 발송 기한이 아니라 사실 확인을 시작해야 하는 시점입니다. CNS는 기한 안에 고객의 문제 지속 여부, 담당자, 목표 시점 중 최소 2개를 확인합니다.

**신호별 유효기간과 권장 대응 기한**

| 신호 유형 | 유효기간 | 최초 대응 기한 | 재확인 항목 |
| --- | ---: | ---: | --- |
| 용량 한도 80% 도달 | 14일 | 2영업일 | 현재 사용률, 예상 소진일, 일시적 증가 여부 |
| 처리량·사용자 급증 | 21일 | 3영업일 | 증가 원인, 지속 기간, 신규 업무 유입 여부 |
| 프리미엄 기능 수작업 우회 | 30일 | 5영업일 | 반복 빈도, 투입 시간, 대체 프로세스 도입 여부 |
| 외부 도구로 데이터 반출 | 21일 | 3영업일 | 반출 목적, 후속 작업, 이미 채택한 도구 여부 |
| 신규 채널·활용 사례 요청 | 30일 | 2영업일 | 적용 일정, 담당 부서, 필수 연동 범위 |
| 모델 성능 한계 도달 | 14일 | 2영업일 | 목표 지표, 데이터 변화, 수동 보정 방식 |
| 신규 채용 공고 | 45일 | 7영업일 | 채용 지속 여부, 담당 과업, 내부 구축 계획 |
| 신규 임원·조직 통합 | 60일 | 10영업일 | 의사결정권 변화, 우선순위, 기존 챔피언 역할 |
| 신규 사업 발표 | 60일 | 7영업일 | 사업 개시일, 시스템 필요 시점, 적용 조직 |
| 타 부서 문의 유입 | 30일 | 2영업일 | 구체적 문제, 예상 사용자, 내부 승인 경로 |

유효기간은 최초 발생일이 아니라 마지막으로 사실이 확인된 날부터 계산합니다. 단순 열람, 자동 메일 발송, 담당자의 추측은 확인일을 갱신하지 않습니다.

고객이 “검토 중”이라고만 답한 경우 신호는 1회에 한해 14일 연장할 수 있습니다. 연장하려면 다음 확인일과 확인할 질문을 함께 기록해야 합니다.

**기한 초과 신호 처리**

1. 유효기간은 남았지만 대응 기한을 넘겼으면 ‘지연’으로 표시하고 1영업일 내 재확인합니다.
2. 유효기간이 끝났으면 동일 지표의 최신 값 또는 최신 공개 출처를 다시 확인합니다.
3. 최신 근거가 확인되면 새로운 확인일을 부여하되 최초 발견일은 보존합니다.
4. 근거가 없거나 고객 문제가 해소됐으면 ‘기간 만료’로 폐기합니다.
5. 고객이 다른 도구 도입, 내부 개발 완료, 업무 중단을 확인하면 잔여 기간과 관계없이 ‘대체 해결’로 종료합니다.
6. 2회 연속 재확인에 응답이 없으면 활성 기회 후보에서 제외하고 정례 관찰 대상으로 전환합니다.

폐기된 신호를 새 기회 근거로 재사용하려면 새로운 고객 행동이나 최신 계측값이 필요합니다. 날짜만 갱신하거나 동일 자료를 다시 첨부하는 방식은 금지합니다.

사용·참여 신호는 갱신 캘린더 날짜보다 업셀 적기를 더 잘 예측합니다. 따라서 갱신 시점까지 대화를 미루지 않으며, 유효기간 안에 고객이 아직 해결 방식을 선택하지 않았는지를 확인합니다.

## 기회 자격 검증 체크리스트
<!--meta: sec=s9; dept=CNS|SALES; level=시니어; ct_band=상; related=s8|s10-->
기회 자격 검증은 고객의 관심 표현을 실제 확장 기회로 오인하지 않기 위한 통제 절차입니다. CNS는 고객 발언, 운영 기록, 계약 현황과 내부 공급 역량을 근거로 검증하며 추정만으로 항목을 완료 처리하지 않습니다.
검증 결과는 `충족·미충족·확인 중` 중 하나로 기록합니다. 6개 항목이 모두 `충족`일 때만 SALES에 이관하며, 하나라도 비어 있거나 `확인 중`이면 CNS가 보완 책임을 유지합니다.
**필수 검증 항목표**
| 검증 항목 | 충족 판정 기준 | 인정 근거 | 미충족 시 조치 |
| --- | --- | --- | --- |
| 고객 업무 문제 | 해결하려는 문제가 고객의 업무 용어로 2문장 이내 서술됨 | 고객 인터뷰 기록, 회의록, 이메일 | 문제 소유자와 재확인 |
| 예산 주체·집행 시기 | 예산 보유 부서 또는 승인자가 식별되고 집행 가능 월·분기가 확인됨 | 고객 담당자 확인, 예산 절차 메모 | 예산 책임자와 확인 일정 확보 |
| 현 계약의 미해결 과제 | 미결 과제, 책임자, 목표일과 확장 범위 영향이 정리됨 | 이슈 목록, 운영 회의록 | 기존 과제 처리계획부터 확정 |
| 기술 가능성 | 사전 타당성 확인 결과가 `가능` 또는 조건부 가능으로 회신됨 | DSC-xx 검토 회신 | s12 절차로 검토 요청 |
| 내부 인력 공급 가능성 | 필요한 부서·역할·예상 투입 시기와 가용 여부가 확인됨 | 부서 책임자 확인 | 착수 가능 시기 재산정 |
| 기존 운영 영향 | 운영 SLA, 담당 인력, 배포 일정에 중대한 충돌이 없음 | 운영 담당 검토 의견 | 분리 일정 또는 완화안 수립 |
**고객 언어 판정 규칙**
고객 언어에는 업무 주체, 현재 불편 또는 손실, 발생 빈도, 영향받는 업무 흐름이 포함되어야 합니다. “AI 고도화가 필요함”, “자동화를 원함”처럼 공급사 관점의 솔루션 명칭만 있는 문장은 불충족입니다.
예를 들어 “제조업 고객사 생산관리팀이 매주 2회 수작업으로 데이터를 합산하여 보고 지연이 발생함”은 검증 가능한 문제 서술입니다. 원인이 확인되지 않았다면 원인을 단정하지 않고 관찰된 현상만 기록합니다.
**검증 완료 판정**
1. CNS 담당자가 각 항목의 근거 링크와 확인일을 입력합니다.
2. CNS 과장 이상이 문제 서술과 현 계약 미결 과제의 누락 여부를 검토합니다.
3. SALES 과장 이상이 예산 주체와 집행 시기의 명확성을 확인합니다.
4. 기술 가능성과 인력 공급 가능성은 해당 부서의 명시적 회신으로만 완료합니다.
5. 모든 항목 완료일이 이관 예정일 기준 30일을 넘으면 변동 여부를 재확인합니다.
조건부 가능 판정에는 선행조건, 조건 해소 책임자와 확인 기한이 있어야 합니다. “추후 협의”, “리소스 확인 예정”처럼 책임자나 날짜가 없는 조건은 미충족으로 처리합니다.
검증 실패는 기회 상실을 의미하지 않습니다. CNS는 미충족 항목별 다음 확인 행동과 기한을 지정하되, 완료 전에는 SALES 이관·견적 요청·제안 일정 확정을 진행하지 않습니다.

## 고객성공 → 영업 이관 기준과 절차
<!--meta: sec=s10; dept=CNS|SALES; level=시니어; ct_band=상; related=s9|s11|FCT-01#s1-->
고객성공에서 영업으로의 이관은 고객 문제와 확장 의도가 검증된 뒤 상업적 논의를 공식적으로 시작하는 시점입니다. 이관은 담당자 변경이 아니라 고객 맥락을 보존하면서 협상 책임을 SALES로 전환하는 절차입니다.
이관 시점은 s9의 6개 검증 항목이 모두 충족되고, 고객이 범위·예산·추진 일정에 관한 후속 대화에 동의한 때로 정합니다. 단순 문의, 기능 아이디어, 가격 탐색 발언만으로는 이관하지 않습니다.
**이관 패킷 필수 항목**
| 항목 | 작성 내용 | 작성 책임 |
| --- | --- | --- |
| 고객 문제 | 고객 언어로 작성한 문제, 발생 빈도, 업무 영향 | CNS |
| 관계자 지도 | 문제 소유자, 챔피언, 예산 주체, 승인자와 반대 가능 이해관계자 | CNS |
| 현재 성과 | 기존 계약에서 달성한 결과와 고객이 인정한 근거 | CNS |
| 가치 가설 | 현재 상태, 원하는 상태, 지표, 전제와 검증 방법 | CNS |
| 상업 정보 | 예산 주체, 집행 시기, 구매 절차와 경쟁 검토 여부 | CNS·SALES |
| 제약·리스크 | 미해결 과제, 기술 조건, 운영 영향과 인력 가용 시점 | CNS |
| 고객 합의사항 | 다음 미팅 목적, 참석 예정자, 고객이 요청한 산출물 | CNS |
이관 패킷에는 회의록·운영 지표·기술 회신의 원문 링크를 포함합니다. 고객 비밀정보는 승인된 저장소 링크로 연결하고 메신저 본문이나 개인 저장공간에 복제하지 않습니다.
**15분 이관 회의 아젠다**
| 시간 | 논의 항목 | 종료 조건 |
| --- | --- | --- |
| 0~3분 | 고객 문제와 확장 계기 | SALES가 문제를 한 문장으로 재확인 |
| 3~6분 | 이해관계자와 의사결정 구조 | 접촉 대상과 고객 내 역할 확정 |
| 6~9분 | 가치 가설과 증거 | 검증된 사실과 가정을 구분 |
| 9~12분 | 기술·운영·계약 제약 | 선행조건과 담당자 확인 |
| 12~15분 | 고객 후속 일정과 역할 | 회의 주도자·자료·기한 지정 |
이관 후 CNS는 고객의 기존 성과, 운영 맥락, 관계 연속성과 가치 검증을 담당합니다. SALES는 상업 조건, 구매 절차, 제안 조율과 협상을 담당하며 고객 앞에서 서로 다른 범위나 일정을 제시하지 않습니다.
CNS가 이관 없이 직접 제안하면 가격·계약 권한이 불명확해지고, 검증되지 않은 범위가 고객 기대치로 고착될 수 있습니다. 또한 기존 운영 관계를 이용한 압박으로 받아들여질 수 있으므로 CNS는 상업적 확약을 하지 않습니다.
SALES가 패킷 누락을 발견하면 이관 회의 종료 전에 보완 책임자와 기한을 지정합니다. 필수 항목이 빠진 경우 회의를 종료하고 CNS 보완 상태로 되돌리며 부분 이관은 허용하지 않습니다.
이관 완료 후 기회 레코드 등록과 파이프라인 단계 판정은 FCT-01을 따릅니다. 활동·근거 자료의 CRM 입력 형식은 FCT-05를 참조합니다.

## 가치 가설 작성 방법
<!--meta: sec=s11; dept=CNS; level=시니어; ct_band=상; related=s10|s12-->
가치 가설은 확장 구매가 고객 업무에 어떤 변화를 만들지 검증 가능한 문장과 지표로 정리한 한 장 문서입니다. 확정 효과나 제안서 문구가 아니라 고객과 함께 사실 여부를 확인할 임시 가설로 작성합니다.
CNS는 고객 문제를 솔루션 기능으로 치환하지 않습니다. 현재값과 목표값을 분리하고, 목표값은 고객이 동의한 경우에만 수치로 기재하며 미확인 상태는 `기준선 측정 필요`로 표시합니다.
**가치 가설 한 장 양식**
| 항목 | 작성 기준 | 필수 기재값 |
| --- | --- | --- |
| 현재 상태 | 현재 업무 흐름과 관찰된 손실·제약을 서술 | 담당 조직, 기준 기간, 현재값 |
| 원하는 상태 | 고객이 원하는 업무 결과를 서술 | 목표 시점, 목표값 또는 방향 |
| 측정 지표 | 전후 비교가 가능한 지표를 선정 | 정의, 단위, 데이터 출처 |
| 전제 | 결과 달성에 필요한 조건을 명시 | 고객 제공사항, 내부 조건, 제외조건 |
| 검증 방법 | 가설을 확인할 활동과 판정 방식을 정의 | 표본, 기간, 성공 기준, 책임자 |
문서는 A4 1쪽 또는 화면 1페이지를 넘기지 않습니다. 지표는 최대 3개로 제한하며, 기능 사용량이 아니라 처리시간·오류율·리드타임 등 고객 업무 결과를 우선합니다.
**작성 예시 — 제조업 고객사 보고 업무 확장**
| 항목 | 예시 내용 |
| --- | --- |
| 현재 상태 | 생산관리 담당자 2명이 주 2회 데이터를 수작업 취합하며, 최근 4주 평균 합산 공수는 주 16시간임 |
| 원하는 상태 | 8주 검증 종료 시 주간 합산 공수를 6시간 이하로 줄이는 것을 목표로 함 |
| 측정 지표 | 주간 합산 공수, 마감 후 수정 건수, 보고서 확정 소요일 |
| 전제 | 원천 데이터 접근 승인, 항목 정의 유지, 고객 담당자 주 1회 검증 참여 |
| 검증 방법 | 4주 기준선과 4주 시험 운영을 비교하고, 평균 공수 6시간 이하 여부를 고객과 공동 판정 |
예시의 6시간은 고객과 합의할 목표값이며 보장 수치가 아닙니다. 기준선이 확인되지 않았거나 고객이 목표값에 동의하지 않았다면 숫자를 제안 효과로 사용하지 않습니다.
**고객 공동 검증 질문 5개**
1. 이 문제가 가장 크게 영향을 주는 업무와 담당자는 누구입니까?
2. 현재 상태를 수치로 확인할 수 있는 데이터와 기준 기간은 무엇입니까?
3. 개선되었다고 판단할 최소 변화량과 목표 시점은 언제입니까?
4. 이 결과를 막을 수 있는 데이터·정책·인력 전제는 무엇입니까?
5. 검증 결과를 확인하고 다음 투자를 승인할 사람은 누구입니까?
효과 수치는 고객 데이터, 동일 계정의 측정 결과 또는 합의된 시험 결과 중 하나로 근거를 제시해야 합니다. 외부 평균, 일반적 생산성 향상률, 유사 사례 수치를 해당 고객의 예상 성과처럼 전용하지 않습니다.
수치 근거에는 출처, 측정 기간, 계산식과 확인자를 붙입니다. 근거가 없으면 `효과 산정 전`, 범위만 추정되면 `가설 범위`라고 표시하며 단일 확정값으로 바꾸지 않습니다.
고객이 가설을 수정하면 기존 내용을 덮어쓰지 않고 변경일, 변경 사유와 합의자를 남깁니다. 최종 검증 여부는 고객 확인 기록으로 판정하며 내부 기대만으로 `검증 완료` 처리하지 않습니다.

## 제안 전 사전 확인 — 기술 타당성
<!--meta: sec=s12; dept=CNS|AIAX|BE; level=시니어; ct_band=중; related=s11|s13-->
기술 타당성 사전 확인은 고객에게 제안 방향을 제시하기 전에 구현 가능 여부와 필수 선행조건을 기술 부서로부터 회신받는 절차입니다. CNS는 고객 요구를 그대로 전달하지 않고 검토 가능한 입력정보로 구조화해야 합니다.
요청 시점은 s9의 고객 문제·예산 주체·집행 시기·현 계약 미해결 과제가 정리되고, 고객이 구체적 후속 검토에 동의한 직후입니다. 제안서 작성 착수, 견적 요청 또는 고객 일정 제시보다 먼저 요청합니다.
**요청 전 CNS 정리 정보**
| 정보 구분 | 필수 내용 | 미확인 시 표기 |
| --- | --- | --- |
| 업무 요구 | 사용자, 업무 흐름, 입력·처리·출력과 기대 결과 | 고객 확인 필요 |
| 현행 환경 | 시스템 구성, 연동 대상, 운영 주체와 배포 제약 | 자료 요청 중 |
| 데이터 | 데이터 유형, 보유 위치, 표본 유무, 접근 승인 상태 | 접근 미승인 |
| 비기능 요구 | 사용자 규모, 처리 빈도, 가용 시간대, 보안·망 조건 | 기준 미합의 |
| 변경 범위 | 기존 기능 영향, 신규 개발 예상 영역, 제외 범위 | 범위 미확정 |
| 일정 조건 | 고객 목표일, 고정 행사·감사·배포 제한일 | 희망일 수준 |
| 검증 질문 | 기술 부서가 답해야 할 질문을 최대 5개로 명시 | 질문 보완 필요 |
미확인 정보는 추정값으로 채우지 않습니다. 검토에 필수적인 정보가 없으면 고객 확인 일정과 담당자를 함께 적고, 기술 부서는 `정보 부족`으로 반려할 수 있습니다.
**타당성 확인 요청 양식**
| 필드 | 입력 규칙 | 예시 형식 |
| --- | --- | --- |
| 요청 제목 | 고객 업종·확장 주제·희망 회신일 | 제조업 고객사·보고 자동화·11/18 |
| 검토 유형 | AIAX, BE 또는 공동 검토 | AIAX+BE |
| 요구 요약 | 고객 문제와 원하는 결과를 각 2문장 이내 작성 | 문제/결과 구분 |
| 첨부 근거 | 구성도, 데이터 명세, 화면, 회의록 링크 | 승인 저장소 URL |
| 회신 요청 | 가능 상태, 선행조건, 추가 확인사항 | 표준 회신 항목 |
| 요청자 | CNS 담당자와 고객 질의 창구 | 성명 대신 사내 계정 |
표준 회신 기한은 접수 다음 영업일부터 3영업일입니다. 복수 시스템 연동, 보안·망 검토 또는 표본 데이터 확인이 필요한 건은 담당 기술 부서가 접수 후 1영업일 안에 예상 회신일을 지정하며 최대 5영업일을 기준으로 합니다.
긴급 요청은 고객 마감이 아니라 내부 요청 지연만을 이유로 사용할 수 없습니다. 1영업일 내 검토가 필요한 경우 CNS 부장과 해당 기술 부서 부장의 합의가 있어야 하며, 합의되지 않으면 표준 기한을 적용합니다.
회신 상태는 `가능·조건부 가능·정보 부족·불가` 중 하나로 받습니다. 조건부 가능에는 선행조건과 재확인 담당자가 포함되어야 하며, 세부 판단 기준과 검토 절차는 DSC-xx 기술 타당성 검토 문서를 참조합니다.
기술 타당성이 확인되지 않은 상태에서는 고객에게 착수일, 완료일, 투입 인원, 구현 범위 또는 금액을 말하지 않습니다. 고객이 즉답을 요구하면 “기술 검토 후 회신 예정”과 확정 가능한 회신 날짜만 안내합니다.
회신 후 CNS는 기술 의견을 임의로 완화하거나 고객용 확약 문장으로 변환하지 않습니다. 고객 설명이 필요한 조건은 AIAX·BE 담당자와 표현을 합의하고, 변경된 요구는 기존 회신을 재사용하지 않고 재검토를 요청합니다.

## 확장 대화를 미뤄야 하는 상황
<!--meta: sec=s13; dept=CNS; level=시니어; ct_band=상; related=s12|s14-->
확장 대화 보류는 기회를 폐기하는 조치가 아니라 고객 신뢰와 기존 성과를 우선하기 위한 일시 정지입니다. 보류 기간에도 신호의 증거 수집과 내부 검토는 계속할 수 있지만, 고객에게 가격·계약·추가 구매 결정을 요구하지 않습니다.
두 조건 이상이 겹치면 가장 엄격한 해제 조건을 적용합니다. 보류 판단일로부터 5영업일마다 상태를 재확인하며, 해제 증거가 기록되기 전에는 담당자의 주관적 판단으로 대화를 재개하지 않습니다.

**보류 조건과 해제 기준**
| 상황 | 보류 판정 기준 | 확장 대화 해제 조건 |
| --- | --- | --- |
| 헬스 밴드 관찰 | 헬스 스코어 60~69점 | 80점 이상으로 회복하고 14일간 하위 밴드 재진입이 없음 |
| 헬스 밴드 위험 | 헬스 스코어 59점 이하 | 위험 원인이 종결되고 80점 이상을 14일간 유지함 |
| 하이퍼케어 진행 | 공식 하이퍼케어 종료 승인이 나지 않음 | 종료 심사 승인과 운영 인수인계 노트가 모두 완료됨 |
| P1 장애 미종결 | 복구 전이거나 복구 후 안정성 관찰 중임 | 복구 완료 후 2영업일간 재발이 없고 고객 담당자가 정상화를 확인함 |
| SLA 미달 지속 | 최근 30일 내 동일 SLA 2회 이상 미달 또는 2개월 연속 미달 | 시정 계획을 고객과 합의하고 이후 30일간 같은 항목의 추가 미달이 없음 |
| 미해결 과제 다수 | 미종결 P2 이상 이슈 2건 이상 또는 기한 초과 과제 5건 이상 | P2 이상 이슈가 0건이고 기한 초과 과제가 2건 이하이며 잔여 건의 담당·완료일이 확정됨 |
| 고객 조직 개편 | 의사결정자·예산 책임자·챔피언 중 하나 이상이 미확정이거나 예산 집행이 중지됨 | 역할과 예산 권한이 서면 확인되고 신규 책임자와 1회 이상 미팅을 완료함 |
| 갱신 협상 중첩 | 갱신 가격·범위·기간 중 하나 이상이 미합의 상태임 | 갱신 계약이 체결되거나 고객이 갱신·확장 통합 협상을 서면 요청함 |

오픈 직후에는 안정화가 우선입니다. “오픈(Go-Live)은 끝이 아니라 중간 지점이다.”라는 원칙에 따라 하이퍼케어 중 발견된 추가 요구를 즉시 판매 기회로 전환하지 않으며, 운영 안정성과 별개의 요구인지 먼저 구분합니다.
하이퍼케어 기간·종료 심사와 P1 대응 기준은 CSM-02를 참조합니다. 헬스 밴드 산정과 회복 판정은 CSM-03을 참조합니다.

**예외 허용 범위**
- 고객이 먼저 확장 검토를 요청한 경우에는 요구사항 청취와 일정 확인까지만 진행할 수 있습니다.
- 법규·보안·서비스 연속성을 위해 추가 범위가 불가피한 경우에는 CNS 부장과 SALES 부장의 공동 승인으로 기술 검토를 시작할 수 있습니다.
- 예산 소멸 등 고객의 불가역적 기한이 10영업일 이내인 경우에는 사실 확인 후 조건부 검토가 가능하지만, 보류 원인을 제안서에서 숨기지 않습니다.
- 미종결 P1 장애가 있으면 예외 사유와 관계없이 가격 제시, 계약 요청, 임원 대상 확장 제안은 금지합니다.

예외 검토 기록에는 고객 요청 원문, 기한, 보류 원인, 허용 활동, 금지 활동, 승인자와 재검토일을 남깁니다. 고객 요청 없이 내부 실적 목표만을 사유로 예외를 승인하지 않습니다.
갱신과 확장을 통합할 경우 가격 조정이나 유지보수 요율을 이 문서에서 판단하지 않으며 CSM-05를 참조합니다.

## 헬스 스코어와 확장 판단의 관계
<!--meta: sec=s14; dept=CNS|DATA; level=시니어; ct_band=중; related=s13|s15|CSM-03#s1-->
헬스 스코어는 기존 도입 범위가 안정적으로 가치를 내는지를 판단하는 지표이고, 확장 신호는 추가 문제와 투자 의지가 존재하는지를 판단하는 지표입니다. 기본적으로 확장 제안은 판단일 기준 헬스 스코어 80점 이상이며 최근 14일 동안 하위 밴드로 이동하지 않은 계정에만 실시합니다.
높은 헬스 점수만으로 확장 기회가 성립하지는 않습니다. 건강한 계정에서도 추가 활용 사례, 용량 압박, 신규 이해관계자 또는 예산 신호가 확인되지 않으면 관계 유지 활동만 진행합니다. 점수 산정·가중치·최근성 감쇠는 CSM-03을 참조합니다.

**동일 데이터를 다르게 읽는 기준**
| 데이터 | 헬스 판단: 수준 중심 | 확장 판단: 변화율·여유 용량 중심 |
| --- | --- | --- |
| 활성 사용자 | 계약 또는 기준선 대비 현재 활성 비율이 안정적인지 확인함 | 최근 4주 증가율과 신규 조직의 유입 속도를 확인함 |
| 핵심 기능 사용 | 필수 업무 흐름이 정기적으로 수행되는지 확인함 | 고급 기능 진입, 수작업 우회, 신규 활용 사례 증가를 확인함 |
| 용량 사용 | 현재 사용량이 서비스 운영에 문제를 만들지 않는지 확인함 | 한도의 80% 도달 여부와 소진 예상일을 확인함 |
| 챔피언 참여 | 기존 챔피언이 응답하고 의사결정에 참여하는지 확인함 | 신규 임원·부서·예산 책임자의 참여 증가를 확인함 |
| 지원 활동 | 티켓 심각도, 재오픈, 해결시간이 안정적인지 확인함 | 반복 문의가 교육·자동화·추가 모듈 수요로 전환될 수 있는지 확인함 |

예를 들어 사용량 80% 도달은 증설 신호가 될 수 있지만, 장애 재시도로 사용량이 비정상 증가한 경우에는 확장 신호가 아닙니다. 증가 원인이 실제 업무량, 사용자 수 또는 활용 범위 확대인지 데이터와 고객 확인을 통해 구분합니다.
반대로 현재 활성률이 높더라도 최근 8주 연속 하락 중이면 확장 대화를 시작하지 않습니다. 헬스는 현재 수준을, 확장은 방향과 속도를 보므로 단일 시점 수치만으로 두 판단을 동시에 내리지 않습니다.

**헬스와 확장 신호 결합 판정**
| 헬스 상태 | 확장 신호 | 처리 |
| --- | --- | --- |
| 80점 이상·안정 | 복합 신호 2개 이상 | 자격 검증 후 확장 대화를 진행함 |
| 80점 이상·안정 | 신호 1개 | 추가 증거를 수집하고 고객 문제를 확인함 |
| 80점 이상·하락 추세 | 신호 존재 | 하락 원인을 확인할 때까지 고객 제안을 보류함 |
| 관찰·위험 밴드 | 신호 존재 | 회복 활동을 우선하고 신호 유효기간만 관리함 |

예외는 고객이 먼저 요청한 필수 증설, 규제 대응, 보안 보완 또는 서비스 중단 방지를 위한 용량 확보로 제한합니다. 이 경우에도 고객 요청을 곧바로 수주 가능성으로 해석하지 않고 문제 확인과 기술 타당성 검토까지만 진행합니다.
챔피언 이탈, 지원 공수 급증, 만족도 하락과 같이 헬스를 악화시키는 신호를 확장 근거로 바꾸어 기록해서는 안 됩니다. 문제 해결을 유료 범위로 전환해야 하는 경우에는 기존 계약 범위와 책임 경계를 먼저 확인합니다.

## 확장 성과 지표와 NRR 기여
<!--meta: sec=s15; dept=CNS|DATA; level=시니어; ct_band=상; related=s14|s16|CSM-05#s1-->
확장 성과는 신호 발견, 영업 이관, 수주, 순환매출 기여를 분리하여 측정합니다. 하나의 지표만 보면 과도한 신호 등록, 자격 미달 이관 또는 저품질 수주가 성과로 보일 수 있으므로 전환 지표와 금액 지표를 함께 관리합니다.
구축 프로젝트의 추가 계약과 운영·유지보수 계약의 순환매출 증가는 별도 열로 집계합니다. 단건 구축 확장액은 확장 실적에는 포함하지만 NRR에는 포함하지 않습니다.

**핵심 지표와 집계 기준**
| 지표 | 간단 산식·정의 | 측정 주기 | 귀속 규칙 |
| --- | --- | --- | --- |
| 확장 기회 생성 건수 | SALES가 이관을 수락해 기회 레코드가 생성된 건수 | 월간, 분기 누적 | 기회 생성일 기준이며 한 기회에 여러 신호가 있어도 1건으로 계산함 |
| 신호 대비 이관율 | 수락된 이관 신호 수 ÷ 검토 대상 유효 신호 수 | 월간, 분기 코호트 | 신호 최초 발견월에 귀속하고 만료·중복 신호는 분모에서 제외함 |
| 이관 대비 수주율 | 확장 수주 건수 ÷ SALES 수락 이관 건수 | 분기 코호트 | 동일 이관 코호트를 180일까지 추적하며 미결 건은 수주율 계산에서 별도 표시함 |
| 확장 수주액 | 확장 계약의 부가세 제외 계약금액 | 월간, 분기, 연간 | 계약 체결일 기준이며 단건 금액과 연간 순환매출 증가분을 분리함 |
| 계정당 연간 확장률 | 최근 12개월 확장 수주액 ÷ 해당 계정의 비교 기준 계약금액 | 월간 이동 12개월 | 계정·계약형태별로 계산하며 기준금액이 0인 신규 계정은 제외함 |
| NRR 기여도 | 순환매출 확장분 ÷ 기초 순환매출 | 월간 모니터링, 분기 확정 | 운영·유지보수 등 반복 청구되는 확장분만 퍼센트포인트로 반영함 |

NRR은 기존 고객의 기초 순환매출에서 가격 인상·업셀·크로스셀을 더하고 축소·이탈을 차감한 결과를 봅니다. GRR은 확장분을 제외하므로 확장 활동의 직접 기여도를 평가할 때에는 NRR 기여도와 함께 표시하되 두 지표를 합산하지 않습니다.
가격 인상분과 실제 범위 확장분은 계약 항목을 기준으로 분리합니다. 기존 범위의 단가 조정은 갱신 인상으로, 사용자·용량·기능·조직·서비스 범위 추가는 확장으로 귀속합니다.

**측정 운영 규칙**
- 신호 대비 이관율은 같은 달의 이관 건수를 단순 나누지 않고 신호 발견월 코호트로 추적합니다.
- 이관 대비 수주율은 취소·중복·고객 요청 철회를 실패 사유별로 남기며, 장기 미결 건을 임의로 제외하지 않습니다.
- 확장 수주액은 CNS의 신호 발굴 실적과 SALES의 수주 실적을 각각 표시하되 전사 수주액에는 한 번만 합산합니다.
- 여러 지점이 관여한 계정은 계약 시점의 계정 소유 지점에 금액을 귀속하고, 발굴 지점은 소스 기여로 별도 표시합니다.
- 기존 계약에 없던 단건 분석·개발 과업은 구축 확장으로 집계하며 순환매출로 환산하지 않습니다.
- 계약 취소나 감액 합의가 발생하면 최초 집계월을 수정하지 않고 조정 발생월에 음수 조정액을 기록합니다.

갱신 성공률과 확장 수주율을 섞으면 가격 인상만으로 확장 성과가 높아 보이거나, 정상 갱신이 신규 범위 발굴 성과로 오인됩니다. 갱신 지표·GRR·가격 조정 기준은 CSM-05를 참조합니다.
DATA는 월 마감 후 3영업일 이내에 지표를 산출하고 CNS와 SALES는 2영업일 이내에 예외·중복·귀속 오류를 확인합니다. 분기 확정 이후의 수정은 수정 사유와 영향 지표를 함께 남깁니다.

## 확장 기회 기록 규칙
<!--meta: sec=s16; dept=CNS|SALES; level=주니어; ct_band=중; related=s15|s17|FCT-05#s1-->
확장 신호와 확장 기회는 별도 레코드로 기록합니다. 신호는 아직 고객의 구매 의사나 예산이 검증되지 않은 관찰 정보이며, 기회는 자격 검증과 영업 이관 수락을 거쳐 상업적 추적이 시작된 대상입니다.
두 단계를 하나로 기록하면 미검증 신호가 파이프라인으로 과대 계상되고, 기회가 실패했을 때 원래 신호의 학습 데이터도 사라집니다. 모든 기회는 최소 1개의 신호 ID와 연결하며, 하나의 신호가 여러 기회에 중복 연결될 때에는 분할 사유를 남깁니다.

**신호 레코드 필수 항목**
| 항목군 | 기록 내용 | 최초 소유자 |
| --- | --- | --- |
| 식별 | 신호 ID, 고객 계정, 관련 프로젝트·계약, 지점 | 발견한 CNS 담당자 |
| 분류 | 사용·관계·상업 신호 구분, 업셀·크로스셀 예상 유형 | CNS 담당자 |
| 증거 | 관측값, 비교 기준선, 변화율, 데이터 출처, 관측일 | CNS 담당자 또는 DATA 지원자 |
| 유효성 | 최초 발견일, 유효기간, 만료 예정일, 마지막 확인일 | CNS 담당자 |
| 강도 | 단일·복합 여부, 연결 신호 ID, 고객 영향 범위 | CNS 과장 이상 검토 |
| 후속 | 다음 확인일, 고객 확인 필요사항, 현재 상태, 종료 사유 | CNS 담당자 |

신호는 관측 후 1영업일 이내에 등록합니다. 자동 탐지 신호는 생성 후 3영업일 이내에 담당자가 증거를 확인하며, 오류이면 삭제하지 않고 `무효-데이터 오류` 상태로 종결합니다.
신호가 만료되거나 고객이 다른 방식으로 문제를 해결한 경우에는 1영업일 이내에 만료일과 소멸 사유를 기록합니다. 과거 신호의 날짜를 변경하여 새 신호처럼 재사용하지 않습니다.

**기회 레코드 필수 항목**
| 항목군 | 기록 내용 | 소유자 |
| --- | --- | --- |
| 연결 정보 | 원천 신호 ID, 이관일, 이관자, 수락자 | SALES 담당자 |
| 고객 과제 | 확인된 문제, 대상 조직, 기대 결과, 고객 발언 근거 | CNS 작성·SALES 확인 |
| 상업 정보 | 업셀·크로스셀 구분, 계약 형태, 금액 범위와 산정 근거 | SALES 담당자 |
| 관계 정보 | 챔피언, 의사결정자, 예산 책임자, 참여 상태 | SALES 담당자 |
| 검토 상태 | 가치 가설 링크, 기술 타당성 검토 상태, 보류 사유 | CNS·SALES 공동 |
| 일정 | 고객 목표일, 다음 액션일, 신호 만료일, 의사결정 예상일 | SALES 담당자 |

SALES가 이관을 수락하면 당일 기회 레코드를 생성하고 원천 신호 상태를 `기회 전환`으로 변경합니다. 수락하지 않으면 2영업일 이내에 거절 사유를 기록하고 신호 소유권은 CNS에 유지합니다.
기회가 종결되어도 원천 신호 레코드는 삭제하지 않습니다. 수주·실패·보류 결과를 신호에 역연결하여 어떤 신호 조합이 실제 확장으로 이어졌는지 분석할 수 있게 합니다.

동일 고객의 서로 다른 문제, 예산, 의사결정자가 확인되면 별도 기회로 기록할 수 있습니다. 단일 구매 결정으로 묶이는 기능·용량·서비스 항목은 금액 라인이 여러 개여도 하나의 기회로 유지합니다.
CRM 필드 형식, 활동 입력 기한, 중복 제거와 데이터 위생 규칙은 FCT-05를 참조합니다. 파이프라인 단계 선택과 전환 판정은 FCT-01을 참조합니다.

## 금지 행위
<!--meta: sec=s17; dept=CNS|SALES; level=시니어; ct_band=중; related=s16|s18-->
확장 제안은 고객의 확인된 성과와 추가 과제를 연결해야 합니다. 단기 매출을 위해 신뢰·납품 품질·정보보호를 훼손하는 행위는 예상 계약금액이나 고객 요청 여부와 관계없이 금지합니다.

고객 담당자의 구두 동의나 내부 상급자의 지시는 금지 행위의 면책 사유가 아닙니다. CNS와 SALES는 제안 전 근거 자료, 수행 범위, 투입 가능 인력을 각각 확인합니다.

**금지 목록과 차단 기준**
| 금지 행위 | 금지 이유 | 현장 차단 기준 |
| --- | --- | --- |
| 미해결 과제를 덮으려 확장 제안하기 | 기존 책임을 유상 범위로 전가하여 신뢰와 갱신 가능성을 훼손합니다. | 장애·결함·약속된 산출물이 미해결이면 원인과 조치 책임을 먼저 확정합니다. |

금지 가능성이 발견되면 제안 발송과 고객 확약을 즉시 멈춥니다. 단순 문구 수정으로 해소할 수 없는 사안은 근거 확인과 책임자 승인을 완료할 때까지 보류합니다.

**발견 시 처리 절차**
1. 발견자는 당일 CRM 활동 기록에 `확장 제안 보류`와 사실 근거를 남깁니다.
2. CNS 과장 이상과 SALES 과장 이상이 1영업일 내 위반 여부와 고객 영향도를 공동 판정합니다.
3. 비밀정보 노출, 수치 조작, 고의적 범위 은폐는 지점 부장에게 즉시 보고하고 외부 발송물을 회수합니다.
4. 고객에게 이미 전달된 경우 1영업일 내 정정 내용, 영향 범위, 후속 책임자를 안내합니다.

판정 기록에는 문제 문구 또는 행동, 최초 발견 시각, 고객 노출 여부, 중단한 액션, 재개 조건을 포함합니다. 재개 조건에는 원인 해소를 증명할 문서와 승인자 이름이 있어야 합니다.

**재개가 허용되지 않는 근거**
- “경쟁사도 같은 표현을 쓴다”는 주장은 검증 근거로 인정하지 않습니다.
- 향후 채용 예정 인력은 확정된 운영 여력으로 계산하지 않습니다.
- 고객 내부 관계자의 비공식 정보는 구매 의사나 예산 승인으로 간주하지 않습니다.
- 익명화 표시만 추가한 고객 자료는 비밀정보 사용 승인이 되지 않습니다.

반복 위반은 개인의 영업 방식이 아니라 운영 통제 실패로 분류하며, 해당 제안의 책임자 교체와 발송 전 검토 단계를 지정합니다.
기술 타당성 검토 절차는 DSC-xx, 가격·계약 문구 통제는 PRP-xx를 참조합니다.

## 사례 패턴 모음

아래 사례는 업종만 남긴 익명 복합 패턴이며 특정 고객의 사실관계를 재현하지 않습니다. 결과는 계약 규모가 아니라 신호 포착 후 검증 품질과 고객 성과의 연결 여부로 판정합니다.

주니어 담당자는 신호만으로 확장 가능성을 단정하지 않습니다. 성공 패턴은 검증된 복합 신호가 행동으로 이어진 경우이며, 실패 패턴은 누락된 검증 항목이 의사결정 지연이나 신뢰 저하를 만든 경우입니다.

**패턴 1 — 성공: 제조업 고객사의 용량 증설**
- 신호 → 4주 연속 용량 사용률 80% 초과와 수작업 우회 처리가 동시에 확인되었습니다.
- 검증 → 기준선 대비 증가율, 업무 지연 시간, 예산 책임자, 증설 희망일을 확인했습니다.
- 결과 → 용량 증설 업셀과 수작업 제거를 위한 추가 구축 범위가 승인되었습니다.
- 배운 것 → 사용 신호 두 개에 상업적 준비도까지 결합하면 단일 임계값보다 전환 가능성이 높아집니다.
**패턴 2 — 실패: 유통 고객사의 일시적 사용 급증**
- 신호 → 판촉 기간 1주 동안 사용량이 한도의 83%까지 상승했습니다.
- 검증 → 증가 지속성 및 예산 항목을 확인하지 않았습니다. 빈 항목은 기준선 대비 추세, 신호 유효기간, 예산 보유 여부였습니다.
- 결과 → 판촉 종료 후 사용량이 정상화되어 제안 검토가 중단되고 기회가 소멸했습니다.
- 배운 것 → 일회성 피크는 증설 수요가 아니며 최소 3~4주의 지속 추세를 확인해야 합니다.
**패턴 3 — 성공: 서비스업 고객사의 신규 조직 확대**
- 신호 → 신규 조직 출범, 관련 직무 채용, 기존 챔피언의 활용 사례 추가 요청이 함께 발생했습니다.
- 검증 → 신규 조직 책임자와 인터뷰하여 사용자 수, 업무 목표, 데이터 접근 권한, 의사결정 일정을 확인했습니다.
- 결과 → 기존 운영 계약과 분리된 신규 조직 대상 크로스셀 검토가 유상 진단으로 시작되었습니다.
- 배운 것 → 조직 변화는 관계 신호이며 신규 채용과 활용 사례가 동반될 때 실행 시점을 특정할 수 있습니다.
**패턴 4 — 실패: 교육업 고객사의 경영진 요청**
- 신호 → 고객 경영진이 회의 중 신규 AI 기능의 즉시 도입을 요청했습니다.
- 검증 → 데이터 확보와 보안 제약을 확인하지 않았습니다. 빈 항목은 데이터 권리, 연동 구조, 성능 검증 조건, AIAX 투입 가능성이었습니다.
- 결과 → 제안 후 기술 제약이 발견되어 범위를 철회하고 의사결정 일정이 연기되었습니다.
- 배운 것 → 직급이 높은 요청도 기술 타당성 검증을 대체하지 못합니다.
**패턴 5 — 성공: 물류업 고객사의 반복 보고 업무**
- 신호 → 정착률 상승과 함께 동일한 수작업 보고 요청이 3회 연속 접수되었습니다.
- 검증 → 반복 공수, 보고 사용 부서, 원천 데이터 품질, 자동화 후 절감 시간을 고객과 공동 산정했습니다.
- 결과 → 기존 구축 범위와 구분된 보고 자동화 크로스셀 과제가 승인되었습니다.
- 배운 것 → 불편 호소보다 반복 빈도와 절감 가능 시간을 수치화해야 가치 가설이 구매 근거가 됩니다.
**패턴 6 — 실패: 제조업 고객사의 미해결 이슈 중 제안**
- 신호 → 추가 기능 문의가 있었지만 운영 결함과 고객 만족도 하락이 동시에 존재했습니다.
- 검증 → 문의 내용만 기록했습니다. 빈 항목은 기존 결함의 책임·완료일, 고객 신뢰 회복 여부, 확장 논의 동의였습니다.
- 결과 → 고객은 제안을 책임 회피로 받아들였고 확장 논의와 갱신 검토를 모두 연기했습니다.
- 배운 것 → 미해결 과제가 고객 핵심 업무에 영향을 주면 확장보다 원인 해소와 관계 복구를 우선해야 합니다.
