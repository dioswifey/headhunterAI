# 수요예측 배치 파이프라인 단위코드 설명
<!--meta: doc=CODE-BATCH-01; doc_type=unit_code; tier=1; topic=FC; disclosure=internal; status=active; related=PRJ-FC-DET|INC-SV-DET-->

## 개요
<!--meta: sec=s1; dept=DATA; level=주니어; ct_band=중; related=PRJ-FC-DET-->
매일 새벽 실행되는 배치 작업은 지점별 판매 데이터를 모아 전처리하고 예측 모델에 넣어 다음 7일 수요를 계산합니다.

이 문서는 배치 파이프라인을 구성하는 단위 모듈, 함수 책임, 입력·출력 계약, 병렬 실행 방식, 중간 저장 규칙, 부분 실패 처리 및 운영 검증 기준을 설명합니다. 프로젝트 전체 아키텍처보다 코드 단위의 실행 흐름과 변경 시 주의사항에 초점을 둡니다.

파이프라인의 상위 실행 순서는 다음과 같습니다.

1. 실행 기준일과 배치 식별자를 확정합니다.
2. 처리 대상 지점 목록을 조회하고 유효성을 검사합니다.
3. 지점별 데이터량과 실행 환경을 기준으로 처리 그룹을 구성합니다.
4. 각 그룹을 서버별 작업 단위로 제출합니다.
5. 판매 데이터 전처리와 예측을 그룹 단위로 수행합니다.
6. 완료된 그룹 결과를 중간 저장소에 즉시 적재합니다.
7. 전체 그룹의 성공·실패 상태를 판정합니다.
8. 성공한 결과를 대시보드용 테이블로 병합합니다.
9. 실패한 지점에는 `갱신 지연` 상태를 기록합니다.
10. 실행 요약과 재처리 대상을 운영 로그에 남깁니다.

## 코드 구성과 모듈 경계
<!--meta: sec=s2; dept=DATA|BE; level=주니어; ct_band=하; related=CODE-BATCH-01-->
배치 코드는 책임에 따라 다음 모듈로 분리합니다. 모듈명은 논리적 구성 기준이며, 구현 파일을 분리하거나 패키지 내부 클래스로 구성할 수 있습니다.

| 모듈 | 주요 책임 | 대표 함수 |
|---|---|---|
| `batch_context` | 실행 기준일, 배치 ID, 옵션 관리 | `create_batch_context` |
| `branch_loader` | 대상 지점 조회와 제외 조건 적용 | `load_target_branches` |
| `workload_estimator` | 지점별 예상 처리량 산정 | `estimate_branch_load` |
| `group_planner` | N개 처리 그룹 구성 | `plan_branch_groups` |
| `group_executor` | 그룹별 전처리·예측 실행 | `execute_group` |
| `feature_builder` | 판매 데이터 정제와 피처 생성 | `build_features` |
| `forecast_runner` | 다음 7일 수요 계산 | `run_seven_day_forecast` |
| `checkpoint_store` | 중간 결과와 실행 상태 저장 | `save_group_checkpoint` |
| `result_merger` | 성공 그룹 결과 병합 | `merge_completed_groups` |
| `delay_marker` | 실패 지점 갱신 지연 표시 | `mark_delayed_branches` |
| `retry_planner` | 실패 지점 재처리 목록 생성 | `build_retry_plan` |
| `batch_reporter` | 실행 요약과 운영 지표 기록 | `publish_batch_summary` |

각 모듈은 하나의 명확한 책임만 가져야 합니다. 예를 들어 `feature_builder`가 지점 그룹을 재구성하거나, `result_merger`가 원천 판매 데이터를 다시 조회하도록 구현하지 않습니다. 이런 역방향 의존은 부분 재처리와 단위 테스트를 어렵게 만듭니다.

## 실행 컨텍스트 생성
<!--meta: sec=s3; dept=DATA; level=주니어; ct_band=중; related=CODE-BATCH-01-->
`create_batch_context`는 한 번의 배치 실행을 식별하는 불변 정보를 생성합니다. 이후 모든 로그, 중간 결과 및 대시보드 반영 기록은 같은 컨텍스트를 참조해야 합니다.

주요 필드는 다음과 같습니다.

| 필드 | 설명 |
|---|---|
| `batch_id` | 한 번의 실행을 구분하는 고유 식별자 |
| `base_date` | 수요예측의 기준일 |
| `forecast_horizon` | 예측 기간이며 이 파이프라인에서는 7일 |
| `started_at` | 배치 시작 시각 |
| `requested_group_count` | 호출자가 요청한 그룹 수 |
| `effective_group_count` | 자동 조정 후 실제 적용한 그룹 수 |
| `run_mode` | 전체 실행 또는 실패 지점 재처리 구분 |
| `code_version` | 실행 코드 버전 |
| `input_snapshot_key` | 입력 데이터 스냅샷 식별자 |

`batch_id`는 재시도 횟수와 구분되어야 합니다. 동일 입력을 대상으로 한 기술적 재시도는 원본 배치 ID를 유지하고 `attempt_no`만 증가시킵니다. 운영자가 기준일을 바꾸거나 입력 스냅샷을 새로 확정한 경우에는 새로운 배치 ID를 생성합니다.

컨텍스트가 생성된 뒤에는 `base_date`, `forecast_horizon`, `input_snapshot_key`를 변경하지 않습니다. 실행 도중 이 값이 바뀌면 일부 그룹이 서로 다른 기준의 예측 결과를 생성할 수 있습니다.

## 대상 지점 조회 함수
<!--meta: sec=s4; dept=DATA|BE; level=주니어; ct_band=중; related=PRJ-FC-DET-->
`load_target_branches(context)`는 해당 실행에서 처리해야 할 지점 목록을 반환합니다. 반환 순서는 처리 결과에 영향을 주지 않아야 하지만, 재현 가능한 그룹 구성을 위해 지점 식별자 기준의 안정 정렬을 적용합니다.

함수의 처리 절차는 다음과 같습니다.

1. 기준일에 유효한 지점 목록을 조회합니다.
2. 폐점되었거나 집계 대상이 아닌 지점을 제외합니다.
3. 지점 식별자 중복을 제거합니다.
4. 판매 데이터 조회 가능 여부를 사전 점검합니다.
5. 지점별 예상 레코드 수와 최근 처리시간 정보를 결합합니다.
6. 지점 식별자 기준으로 안정 정렬한 목록을 반환합니다.

반환 객체에는 최소한 다음 정보가 포함됩니다.

- `branch_id`: 내부 지점 식별자
- `source_partition`: 원천 데이터 파티션 위치
- `estimated_rows`: 예상 입력 레코드 수
- `recent_runtime_sec`: 최근 정상 실행 시 처리시간
- `priority`: 일반 또는 우선 처리 여부
- `eligible`: 이번 실행의 처리 가능 여부
- `exclude_reason`: 제외된 경우의 사유

대상 지점이 0개라면 성공으로 종료하지 않고 `NO_TARGET_BRANCH` 상태로 기록합니다. 이는 실제 무처리일 수 있지만, 대상 조회 오류로 인해 빈 목록이 반환된 상황과 구분하기 위해서입니다.

## 입력 데이터 계약
<!--meta: sec=s5; dept=DATA; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
전처리 모듈이 받는 지점별 판매 데이터는 다음 논리 필드를 가져야 합니다.

| 필드 | 자료형 | 필수 여부 | 검증 규칙 |
|---|---|---:|---|
| `branch_id` | 문자열 | 필수 | 대상 지점과 일치해야 함 |
| `sales_date` | 날짜 | 필수 | 기준일 이후일 수 없음 |
| `item_id` | 문자열 | 필수 | 공백 문자열 금지 |
| `sales_qty` | 수치 | 필수 | 결측 금지, 음수는 별도 정책 적용 |
| `unit_price` | 수치 | 선택 | 음수 금지 |
| `promotion_flag` | 불리언 | 선택 | 결측 시 기본값 적용 |
| `stockout_flag` | 불리언 | 선택 | 결측 시 미확인 상태로 처리 |
| `loaded_at` | 시각 | 필수 | 입력 스냅샷 확정 시각 이전이어야 함 |

입력 계약 검증은 데이터프레임 생성 직후 수행합니다. 필수 열 누락은 그룹 전체 실행을 중단시키는 구조 오류로 분류하고, 일부 행의 값 오류는 허용 임계치 이내에서 제외할 수 있습니다.

지점별 오류 행의 비율이 설정 임계치를 초과하면 해당 지점만 실패 처리합니다. 같은 그룹 안의 다른 지점은 계속 처리할 수 있어야 합니다. 이를 위해 검증 결과는 단순한 참·거짓이 아니라 `valid_rows`, `rejected_rows`, `fatal_errors`로 분리해 반환합니다.

## 지점별 부하 추정
<!--meta: sec=s6; dept=DATA; level=시니어; ct_band=상; related=INC-SV-DET-->
`estimate_branch_load`는 그룹 구성 전에 각 지점의 예상 작업량을 점수로 환산합니다. 단순히 지점 수만 균등 분배하면 판매 레코드가 많은 지점이 특정 서버에 몰릴 수 있으므로, 데이터량과 최근 실행시간을 함께 고려합니다.

예상 부하 점수의 개념식은 다음과 같습니다.

    load_score =
        row_weight * normalized_estimated_rows
        + runtime_weight * normalized_recent_runtime
        + priority_weight * priority_adjustment

최근 실행 이력이 없는 신규 지점은 전체 지점의 중앙 처리시간을 기본값으로 사용합니다. 평균값은 일부 대형 지점의 영향이 크므로 기본 대체값으로 사용하지 않습니다.

부하 추정값은 정확한 완료시간을 예측하기 위한 값이 아니라 그룹 간 편차를 줄이기 위한 상대 점수입니다. 따라서 모델처럼 복잡하게 관리하지 않고, 다음 조건을 만족하는지를 운영 기준으로 봅니다.

- 같은 실행 안에서 지점 간 상대적 크기를 안정적으로 구분할 것
- 입력 레코드 수가 증가하면 부하 점수가 감소하지 않을 것
- 최근 처리시간이 비정상적으로 큰 단일 실행에 과도하게 끌리지 않을 것
- 신규 지점도 그룹 배치에서 누락되지 않을 것

## 그룹 수 자동 결정
<!--meta: sec=s7; dept=DATA|BE; level=시니어; ct_band=상; related=INC-SV-DET-->
그룹 수를 늘리면 병렬성은 좋아지지만 서버 간 통신 비용이 늘어나므로, 월말처럼 데이터량이 많은 시점에는 그룹 수를 자동으로 늘리는 로직이 포함되어 있습니다.

`resolve_group_count`는 요청 그룹 수, 처리 대상 지점 수, 전체 예상 레코드 수, 실행 가능한 서버 수를 입력으로 받아 실제 그룹 수를 결정합니다.

기본 제약은 다음과 같습니다.

- 그룹 수는 처리 대상 지점 수를 초과하지 않습니다.
- 실행 가능한 서버가 0대이면 그룹을 만들지 않고 실행 준비 실패로 종료합니다.
- 서버당 동시 그룹 수는 메모리와 CPU 보호 한도를 넘지 않습니다.
- 예상 데이터량이 적으면 통신 비용을 줄이기 위해 그룹 수를 축소합니다.
- 월말 데이터량 증가가 감지되면 상한 범위 안에서 그룹 수를 확대합니다.
- 재처리 모드에서는 실패 지점 수를 기준으로 그룹 수를 다시 계산합니다.

자동 조정 결과는 반드시 `requested_group_count`와 `effective_group_count`로 나누어 기록합니다. 운영자가 지정한 값과 실제 적용값이 다를 때 그 사유도 함께 남깁니다.

대표 조정 사유는 `LOW_VOLUME_SHRINK`, `MONTH_END_EXPAND`, `SERVER_CAP_LIMIT`, `BRANCH_COUNT_LIMIT`입니다.

## 지점 그룹 편성 알고리즘
<!--meta: sec=s8; dept=DATA; level=시니어; ct_band=상; related=CODE-BATCH-01-->
`plan_branch_groups`는 부하 점수가 큰 지점부터 가장 가벼운 그룹에 배치하는 방식으로 그룹 간 예상 부하를 평준화합니다. 지점 목록을 순서대로 같은 개수씩 자르는 방식은 구현은 간단하지만 대형 지점이 연속되어 있을 때 편차가 커질 수 있습니다.

개념적인 처리 절차는 다음과 같습니다.

    branches = sort_by_load_desc(branches)
    groups = create_empty_groups(effective_group_count)

    for branch in branches:
        target = group_with_minimum_total_load(groups)
        target.add(branch)

    return sort_members_stably(groups)

그룹 객체에는 다음 값이 포함됩니다.

- `group_id`
- `branch_ids`
- `estimated_total_rows`
- `estimated_total_load`
- `assigned_server`
- `attempt_no`
- `group_status`

같은 입력 스냅샷과 같은 그룹 수를 사용하면 동일한 그룹 구성이 나와야 합니다. 부하 점수가 같은 지점은 `branch_id`를 보조 정렬 키로 사용해 비결정적 결과를 방지합니다.

그룹 간 예상 부하 편차는 별도의 품질 지표로 남깁니다. 편차가 크더라도 배치를 즉시 실패시키지는 않지만, 반복적으로 특정 그룹만 늦게 끝나는 경우 부하 추정 가중치를 재조정합니다.

## 핵심 로직 (INC-SV-01 이후 개선판)
<!--meta: sec=s9; dept=DATA; level=주니어|시니어; ct_band=상; related=INC-SV-DET-->
1. 지점 목록을 N개 그룹으로 나눠 서버별로 병렬 처리(기존: 전체를 한 프로세스에서 순차 처리)
2. 그룹별 처리가 끝나는 대로 결과를 중간 저장소에 적재
3. 전체 그룹 완료 시 대시보드용 테이블로 병합
4. 일부 그룹이 실패해도 성공한 그룹 결과는 대시보드에 반영하고, 실패한 지점만 "갱신 지연"으로 표시

개선판의 핵심은 병렬화 자체보다 실패 범위를 그룹과 지점 단위로 격리한 것입니다. 한 그룹의 실패가 이미 계산된 다른 그룹 결과를 무효화하지 않으며, 병합 단계는 성공한 체크포인트만 읽습니다.

실행 상태는 다음 순서로 전이합니다.

- 배치: `CREATED` → `PLANNED` → `RUNNING` → `MERGING` → `COMPLETED` 또는 `PARTIAL_SUCCESS`
- 그룹: `PENDING` → `RUNNING` → `CHECKPOINTED` → `MERGED`
- 실패 그룹: `RUNNING` → `FAILED` → `RETRY_PENDING`
- 제외 지점: `VALIDATING` → `EXCLUDED` 또는 `DELAYED`

그룹이 예측 계산을 마쳤더라도 중간 저장이 완료되지 않았다면 성공 그룹으로 보지 않습니다. `CHECKPOINTED` 상태는 결과 데이터와 완료 메타데이터가 모두 저장된 뒤에만 기록합니다.

## 그룹 실행 함수
<!--meta: sec=s10; dept=DATA; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
`execute_group(context, group)`는 하나의 그룹에 포함된 지점을 순회하면서 전처리와 예측을 수행합니다. 그룹 내부는 메모리 사용량을 통제하기 위해 지점 단위로 처리하며, 모든 지점 데이터를 한 번에 결합하지 않습니다.

권장 흐름은 다음과 같습니다.

    validate_group_assignment(group)
    mark_group_running(group)

    for branch in group.branches:
        raw = load_branch_sales(context, branch)
        validated = validate_branch_input(raw)
        features = build_features(context, branch, validated)
        forecast = run_seven_day_forecast(context, branch, features)
        append_to_group_buffer(forecast)
        flush_if_needed()

    checkpoint = save_group_checkpoint(context, group)
    mark_group_checkpointed(group, checkpoint)

지점 한 곳에서 데이터 값 오류가 발생한 경우 해당 지점만 실패 목록에 추가하고 다음 지점을 계속 처리합니다. 반면 스키마 전체 누락, 저장소 접근 불가, 실행 컨텍스트 불일치처럼 그룹 결과의 일관성을 보장할 수 없는 오류는 그룹 전체 실패로 처리합니다.

그룹 버퍼는 크기 기준 또는 지점 수 기준으로 주기적으로 비웁니다. 버퍼 비우기는 최종 체크포인트 확정과 다르며, 임시 조각이 모두 저장된 뒤 완료 매니페스트가 생성되어야 그룹 처리가 완료됩니다.

## 판매 데이터 전처리
<!--meta: sec=s11; dept=DATA; level=주니어; ct_band=중; related=CODE-BATCH-01-->
`build_features`는 원천 판매 데이터를 예측 입력 형태로 변환합니다. 주요 단계는 다음과 같습니다.

1. 날짜와 수량 자료형을 표준화합니다.
2. 지점·상품·날짜 단위 중복 행을 집계합니다.
3. 누락 날짜를 연속 시계열 구조로 보완합니다.
4. 반품 또는 정정 데이터의 음수 수량을 정책에 따라 처리합니다.
5. 품절 여부와 프로모션 여부를 보조 변수로 결합합니다.
6. 최근 판매량 기반의 지연값과 이동 통계량을 계산합니다.
7. 예측 기준일 이후 데이터가 포함되지 않았는지 재검사합니다.
8. 예측 모듈이 요구하는 열 순서와 자료형으로 변환합니다.

결측값은 일괄적으로 0으로 바꾸지 않습니다. 판매가 없어서 0인 경우와 원천 데이터가 누락된 경우는 의미가 다르기 때문입니다. 누락 원인이 확인되지 않은 값에는 결측 표시 피처를 함께 생성하거나 해당 지점을 지연 처리합니다.

전처리 결과에는 데이터 품질 요약을 첨부합니다.

- 입력 행 수
- 유효 행 수
- 제외 행 수
- 중복 병합 건수
- 누락 날짜 보완 건수
- 음수 수량 발견 건수
- 마지막 판매 데이터 날짜
- 생성된 피처 열 개수

## 시계열 누수 방지
<!--meta: sec=s12; dept=DATA; level=시니어; ct_band=상; related=CODE-BATCH-01-->
수요예측 피처는 반드시 `base_date` 이전에 관측 가능한 데이터만 사용해야 합니다. 배치 재실행 시점에 이미 미래 실제값이 적재되어 있더라도 기준일 이후 데이터는 피처 생성에서 제외합니다.

`assert_no_future_leakage`는 다음 조건을 검증합니다.

- 판매 데이터의 최대 날짜가 `base_date`를 초과하지 않는지
- 이동 평균 계산 구간이 현재 행 이후 값을 참조하지 않는지
- 프로모션 정보가 예측 시점에 사전 확정된 정보인지
- 정답 열이 피처 목록에 포함되지 않았는지
- 재처리 실행에서도 원본 입력 스냅샷이 유지되는지

누수 검증 실패는 자동 보정하지 않고 해당 지점을 실패 처리합니다. 잘못된 미래 데이터가 포함된 결과는 수치상 자연스러워 보일 수 있어 운영 화면만으로 발견하기 어렵기 때문입니다.

피처 추가 시 개발자는 해당 값의 관측 가능 시점을 단위 테스트에 명시해야 합니다. 단순 상관관계가 높다는 이유만으로 기준일에 알 수 없는 값을 입력으로 사용할 수 없습니다.

## 7일 예측 실행 인터페이스
<!--meta: sec=s13; dept=DATA; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
`run_seven_day_forecast`는 전처리 결과를 받아 다음 7일의 지점별 수요 결과를 반환합니다. 이 모듈은 모델 내부 구현을 직접 다루지 않고, 배치 코드가 필요로 하는 호출 규약만 정의합니다.

입력은 다음 정보를 포함합니다.

- `batch_id`
- `base_date`
- `branch_id`
- 표준화된 피처 데이터
- 예측 기간 7일
- 실행에 사용할 모델 식별 정보

출력은 최소한 다음 열을 가집니다.

| 필드 | 설명 |
|---|---|
| `batch_id` | 결과를 생성한 배치 |
| `base_date` | 예측 기준일 |
| `branch_id` | 대상 지점 |
| `item_id` | 대상 상품 |
| `forecast_date` | 기준일 다음 날부터 7일 범위의 날짜 |
| `forecast_qty` | 예측 수요량 |
| `generated_at` | 결과 생성 시각 |
| `quality_flag` | 입력 품질 또는 결과 보정 상태 |

반환된 `forecast_date`가 정확히 7일 범위에 속하는지 검증합니다. 일부 날짜가 빠지거나 기준일이 포함되면 결과 저장 전에 실패 처리합니다. 예측 수량이 음수인 경우 모델 출력을 그대로 저장하지 않고 정의된 후처리 규칙을 적용한 뒤 보정 여부를 `quality_flag`에 기록합니다.

## 중간 저장소와 체크포인트
<!--meta: sec=s14; dept=DATA|BE; level=시니어; ct_band=상; related=INC-SV-DET-->
그룹별 결과는 전체 그룹 완료를 기다리지 않고 처리 종료 즉시 중간 저장소에 적재합니다. 중간 저장 경로는 최소한 `base_date`, `batch_id`, `group_id`, `attempt_no`를 구분할 수 있어야 합니다.

체크포인트는 결과 데이터와 매니페스트로 구성합니다.

결과 데이터에는 지점별 7일 예측값이 들어가고, 매니페스트에는 다음 값이 들어갑니다.

- 그룹 ID
- 포함된 지점 목록
- 성공 지점 목록
- 실패 지점 목록
- 결과 행 수
- 결과 파일 또는 파티션 목록
- 스키마 버전
- 입력 스냅샷 키
- 결과 체크섬
- 시작·종료 시각
- 재시도 횟수

저장 순서는 결과 데이터 작성, 체크섬 검증, 매니페스트 작성, 완료 상태 갱신 순으로 고정합니다. 완료 상태를 먼저 기록하면 병합 모듈이 아직 쓰는 중인 데이터를 읽을 수 있습니다.

임시 파일은 완료 매니페스트의 대상에 포함되지 않습니다. 작업 도중 프로세스가 종료되면 다음 실행에서 임시 파일을 정리하되, 이미 완료된 다른 그룹 체크포인트는 삭제하지 않습니다.

## 멱등성 보장
<!--meta: sec=s15; dept=DATA|BE; level=시니어; ct_band=상; related=CODE-BATCH-01-->
같은 배치를 재시도해도 대시보드용 결과가 중복 적재되지 않아야 합니다. 이를 위해 논리적 결과 키는 다음 항목의 조합으로 관리합니다.

- `batch_id`
- `branch_id`
- `item_id`
- `forecast_date`

`attempt_no`는 기술적 실행 이력을 구분하지만 최종 결과의 논리 키에는 포함하지 않습니다. 재시도에서 정상 결과가 생성되면 이전 실패 시도의 임시 결과를 대체할 수 있어야 합니다.

`save_group_checkpoint`는 동일한 그룹과 시도 번호의 완료 체크포인트가 이미 존재할 때 다음과 같이 동작합니다.

1. 기존 체크포인트의 체크섬과 새 결과 체크섬을 비교합니다.
2. 체크섬이 같으면 중복 저장 없이 기존 결과를 재사용합니다.
3. 체크섬이 다르면 입력 스냅샷과 코드 버전을 비교합니다.
4. 같은 조건에서 결과가 달라졌다면 비결정성 오류로 기록하고 자동 병합하지 않습니다.
5. 입력이나 코드 버전이 달라졌다면 새로운 배치 실행으로 분리해야 하는지 검사합니다.

대시보드용 테이블 반영도 동일 키 기준의 교체 방식으로 수행합니다. 단순 추가 삽입은 재시도 때 중복 행을 만들 수 있으므로 금지합니다.

## 결과 병합
<!--meta: sec=s16; dept=DATA|BE; level=주니어|시니어; ct_band=상; related=PRJ-FC-DET-->
`merge_completed_groups`는 `CHECKPOINTED` 상태인 그룹의 매니페스트만 읽어 대시보드용 테이블로 병합합니다.

병합 전 검증 항목은 다음과 같습니다.

- 모든 체크포인트의 `batch_id`가 같은지
- 기준일과 입력 스냅샷이 같은지
- 그룹 간 지점이 중복 배정되지 않았는지
- 체크포인트 체크섬이 유효한지
- 예측 날짜가 다음 7일 범위인지
- 필수 결과 열이 모두 존재하는지
- 같은 논리 키가 둘 이상 존재하지 않는지

일부 그룹이 실패했어도 성공 그룹 결과는 병합합니다. 다만 성공 그룹에 속한 지점 중 내부 처리 실패가 발생한 지점은 결과 대상에서 제외하고 `갱신 지연` 목록에 포함합니다.

병합은 준비 테이블 작성, 행 수 검증, 대상 파티션 교체, 상태 반영 순으로 수행합니다. 준비 테이블 검증 전에 운영 조회 대상 파티션을 변경하지 않습니다.

## 부분 성공과 갱신 지연 표시
<!--meta: sec=s17; dept=DATA|BE; level=주니어; ct_band=중; related=INC-SV-DET-->
배치 전체 상태는 모든 지점이 성공하면 `COMPLETED`, 하나 이상의 지점 또는 그룹이 실패했지만 성공 결과를 반영할 수 있으면 `PARTIAL_SUCCESS`로 기록합니다.

실패한 지점은 대시보드에서 `갱신 지연`으로 표시합니다. 표시 데이터에는 다음 정보가 포함됩니다.

- 지점 식별자
- 마지막 정상 갱신 시각
- 이번 실행의 배치 ID
- 실패 단계
- 재처리 예정 여부
- 운영용 오류 코드
- 사용자 화면에 노출할 상태 문구

내부 예외 메시지나 스택 추적 정보는 대시보드 상태 문구에 포함하지 않습니다. 운영자는 상세 로그에서 원인을 확인하고, 대시보드는 결과의 최신성만 명확히 표현합니다.

성공 지점의 새 결과와 실패 지점의 이전 정상 결과를 섞어 보여줄 때는 지점별 기준일을 함께 관리해야 합니다. 실패 지점의 기존 결과를 새 결과처럼 표시해서는 안 됩니다.

## 오류 분류와 예외 처리
<!--meta: sec=s18; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
예외는 재시도 가능성 및 영향 범위에 따라 분류합니다.

| 오류 분류 | 예시 | 영향 범위 | 기본 처리 |
|---|---|---|---|
| `INPUT_SCHEMA_ERROR` | 필수 열 누락 | 그룹 또는 지점 | 자동 재시도 안 함 |
| `INPUT_VALUE_ERROR` | 허용 범위 초과 값 | 지점 | 지점 실패 처리 |
| `SOURCE_TIMEOUT` | 원천 조회 시간 초과 | 지점 또는 그룹 | 제한적 재시도 |
| `RESOURCE_EXHAUSTED` | 메모리 부족 | 그룹 | 그룹 크기 축소 후 재처리 |
| `CHECKPOINT_WRITE_ERROR` | 중간 저장 실패 | 그룹 | 저장 단계 재시도 |
| `CHECKSUM_MISMATCH` | 저장 결과 손상 | 그룹 | 결과 폐기 후 재실행 |
| `MERGE_CONFLICT` | 중복 논리 키 | 배치 | 자동 병합 중단 |
| `CONTEXT_MISMATCH` | 기준일·스냅샷 불일치 | 배치 | 즉시 중단 |
| `UNKNOWN_ERROR` | 분류되지 않은 예외 | 발생 단위 | 로그 보존 후 수동 판단 |

모든 예외를 동일한 횟수로 재시도하지 않습니다. 입력 스키마 오류처럼 반복해도 해결되지 않는 오류는 즉시 실패시키고, 일시적 조회 시간 초과처럼 회복 가능한 오류만 지수형 대기 후 재시도합니다.

예외 객체는 `error_code`, `stage`, `batch_id`, `group_id`, `branch_id`, `retryable`, `message`를 포함합니다. 고객 데이터의 실제 값은 오류 메시지에 직접 기록하지 않습니다.

## 재시도와 실패 지점 재처리
<!--meta: sec=s19; dept=DATA|BE; level=시니어; ct_band=상; related=INC-SV-DET-->
`build_retry_plan`은 실패한 전체 그룹을 무조건 다시 실행하지 않고 실패 범위를 최소화합니다.

재처리 단위 결정 규칙은 다음과 같습니다.

1. 특정 지점의 값 오류이면 해당 지점만 재처리 대상으로 만듭니다.
2. 그룹 체크포인트 저장 실패이면 그룹 계산 결과의 재사용 가능성을 확인합니다.
3. 프로세스 종료로 그룹 완료 여부를 확인할 수 없으면 완료 매니페스트 존재 여부를 검사합니다.
4. 체크포인트가 정상이라면 예측 계산을 반복하지 않고 병합부터 재개합니다.
5. 그룹 전체 자원 부족이면 지점 목록을 더 작은 그룹으로 재분할합니다.
6. 컨텍스트 불일치이면 부분 재처리를 금지하고 새 배치 실행을 요구합니다.

재시도 대기시간에는 작은 무작위 편차를 적용해 여러 그룹이 동시에 재접속하는 현상을 줄입니다. 최대 재시도 횟수를 초과한 지점은 `갱신 지연` 상태로 남기고 운영 검토 목록에 추가합니다.

부분 재처리 결과는 최초 실행과 같은 `batch_id`를 사용할 수 있지만, 원본과 다른 입력 스냅샷을 사용해서는 안 됩니다. 데이터가 수정되어 새 스냅샷이 필요한 경우에는 새 배치로 실행합니다.

## 자원 사용 보호 장치
<!--meta: sec=s20; dept=DATA|BE; level=시니어; ct_band=상; related=INC-SV-DET-->
병렬 실행 수는 서버 수만으로 결정하지 않고 프로세스당 예상 메모리와 데이터 크기를 함께 고려합니다. 그룹 수가 많더라도 서버가 동시에 실행할 수 있는 그룹 수에는 제한을 둡니다.

보호 장치는 다음과 같습니다.

- 그룹별 최대 입력 행 수 사전 검사
- 지점 단위 데이터 로딩
- 결과 버퍼의 주기적 비우기
- 서버별 동시 작업 수 제한
- 메모리 사용률이 높을 때 신규 그룹 제출 일시 중지
- 처리시간 제한을 초과한 그룹의 상태 점검
- 원천 저장소와 중간 저장소의 동시 연결 수 제한
- 실패 재시도의 동시 실행 수 제한

`group_executor`는 전체 판매 데이터를 전역 변수나 프로세스 공용 캐시에 보관하지 않습니다. 장시간 유지되는 캐시는 지점 처리 완료 후에도 메모리가 반환되지 않는 원인이 될 수 있습니다.

자원 임계치에 도달했을 때 실행 중인 그룹을 즉시 종료하기보다 신규 그룹 할당을 중단하고 현재 그룹의 체크포인트 완료를 우선합니다. 다만 프로세스 생존이 어려운 수준이면 중간 버퍼를 저장한 뒤 안전 종료를 시도합니다.

## 동시성 제어
<!--meta: sec=s21; dept=BE|DATA; level=시니어; ct_band=상; related=CODE-BATCH-01-->
같은 기준일의 배치가 중복 실행될 수 있으므로 실행 잠금과 병합 잠금을 분리합니다.

- 실행 잠금은 동일 입력 스냅샷으로 전체 배치가 중복 시작되는 것을 방지합니다.
- 그룹 잠금은 같은 그룹을 둘 이상의 작업자가 동시에 처리하는 것을 방지합니다.
- 병합 잠금은 같은 대시보드 파티션을 동시에 교체하는 것을 방지합니다.

작업자가 그룹 잠금을 획득한 뒤 비정상 종료할 수 있으므로 잠금에는 만료시간을 둡니다. 잠금 만료만으로 즉시 다른 작업자가 결과를 덮어쓰지 않고, 기존 체크포인트와 작업자 상태를 먼저 확인합니다.

그룹 작업자는 주기적으로 생존 신호를 갱신합니다. 생존 신호가 끊겼지만 완료 매니페스트가 존재하면 성공으로 간주할 수 있고, 매니페스트가 없으면 재처리 대상으로 전환합니다.

병합 단계에서는 낙관적 버전 검사를 함께 사용합니다. 준비 테이블 생성 이후 대상 파티션 버전이 달라졌다면 다른 배치가 먼저 반영된 것이므로 자동 교체를 중단합니다.

## 로깅 규칙
<!--meta: sec=s22; dept=DATA|BE; level=주니어; ct_band=하; related=CODE-BATCH-01-->
모든 로그는 검색 가능한 구조화 필드를 포함해야 합니다.

필수 로그 필드는 다음과 같습니다.

- `batch_id`
- `base_date`
- `stage`
- `group_id`
- `branch_id`
- `attempt_no`
- `status`
- `elapsed_ms`
- `error_code`
- `code_version`

지점과 무관한 배치 로그에서는 `branch_id`를 비워둘 수 있습니다. 그룹과 무관한 초기화 로그에서는 `group_id`를 비워둘 수 있지만, 필드 자체는 유지해 검색 형식을 통일합니다.

로그 수준은 다음 기준으로 사용합니다.

- `INFO`: 정상 상태 전이, 그룹 시작·완료, 병합 완료
- `WARN`: 자동 복구된 입력 이상, 지연, 재시도 예정
- `ERROR`: 지점 또는 그룹 실패, 체크포인트 오류
- `CRITICAL`: 배치 컨텍스트 불일치, 전체 병합 불가

반복 처리되는 행 단위 로그는 남기지 않습니다. 데이터 품질 문제는 건별 값 대신 집계 건수와 대표 오류 코드로 기록합니다.

## 운영 지표
<!--meta: sec=s23; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
`publish_batch_summary`는 배치 종료 시 실행 결과를 지표로 남깁니다.

핵심 지표는 다음과 같습니다.

| 지표 | 의미 |
|---|---|
| `batch_total_duration` | 전체 배치 소요시간 |
| `group_runtime` | 그룹별 처리시간 |
| `branch_runtime` | 지점별 처리시간 |
| `group_load_skew` | 그룹 간 예상·실제 부하 편차 |
| `checkpoint_write_duration` | 중간 결과 저장시간 |
| `merge_duration` | 대시보드용 병합시간 |
| `success_branch_count` | 성공 지점 수 |
| `delayed_branch_count` | 갱신 지연 지점 수 |
| `retry_count` | 재시도 횟수 |
| `input_rejected_row_count` | 입력 검증 제외 행 수 |
| `forecast_output_row_count` | 최종 예측 결과 행 수 |
| `peak_memory_usage` | 작업자별 최대 메모리 사용량 |

평균 처리시간만으로 상태를 판단하지 않습니다. 일부 대형 지점이 오래 걸리는 문제를 확인하기 위해 중앙값과 상위 구간 처리시간도 함께 봅니다.

그룹별 실제 처리시간과 예상 부하 점수의 관계가 지속해서 어긋나면 `workload_estimator`를 점검합니다. 통신·저장 시간이 전체 실행시간에서 차지하는 비율이 증가하면 그룹 수를 더 늘리기보다 그룹 수를 줄이는 편이 유리할 수 있습니다.

## 단위 테스트 기준
<!--meta: sec=s24; dept=DATA; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
단위 테스트는 외부 저장소와 실제 예측 모델에 의존하지 않고 고정된 입력과 가짜 구현을 사용합니다.

필수 테스트 항목은 다음과 같습니다.

### 컨텍스트 테스트

- 예측 기간이 7일로 설정되는지 확인
- 같은 실행에서 기준일이 변경되지 않는지 확인
- 재시도 시 배치 ID가 유지되고 시도 번호만 증가하는지 확인
- 입력 스냅샷 변경 시 기존 컨텍스트를 재사용하지 않는지 확인

### 대상 지점 테스트

- 중복 지점이 제거되는지 확인
- 제외 지점 사유가 기록되는지 확인
- 대상이 없을 때 `NO_TARGET_BRANCH`가 반환되는지 확인
- 안정 정렬 결과가 실행마다 같은지 확인

### 그룹 편성 테스트

- 모든 지점이 정확히 한 그룹에 배정되는지 확인
- 그룹 수가 지점 수보다 많아지지 않는지 확인
- 같은 입력에서 같은 그룹 구성이 생성되는지 확인
- 대형 지점이 한 그룹에만 몰리지 않는지 확인
- 월말 조건에서 허용 상한 내 그룹 수가 증가하는지 확인

### 전처리 테스트

- 누락 날짜가 올바르게 보완되는지 확인
- 기준일 이후 데이터가 제거되는지 확인
- 중복 행이 정의된 단위로 집계되는지 확인
- 음수 판매 수량이 정책대로 처리되는지 확인
- 미래 데이터 누수 시 예외가 발생하는지 확인

### 저장·병합 테스트

- 체크포인트 완료 전에는 병합 대상이 되지 않는지 확인
- 동일 결과 재저장이 중복을 만들지 않는지 확인
- 일부 그룹 실패 시 성공 그룹만 병합되는지 확인
- 실패 지점이 `갱신 지연`으로 기록되는지 확인
- 중복 논리 키가 있으면 병합이 중단되는지 확인

## 통합 테스트 시나리오
<!--meta: sec=s25; dept=DATA|BE; level=시니어; ct_band=상; related=CODE-BATCH-01-->
통합 테스트는 그룹 실행, 중간 저장 및 최종 병합의 연결 상태를 검증합니다.

### 시나리오 A: 전체 성공

- 여러 지점을 N개 그룹으로 구성합니다.
- 모든 그룹이 체크포인트를 생성합니다.
- 대시보드용 테이블에 모든 지점의 7일 결과가 반영되는지 확인합니다.
- 배치 상태가 `COMPLETED`인지 확인합니다.

### 시나리오 B: 한 그룹 실패

- 특정 그룹에서 원천 조회 시간 초과를 발생시킵니다.
- 다른 그룹이 중단되지 않는지 확인합니다.
- 성공 그룹 결과가 병합되는지 확인합니다.
- 실패 그룹의 지점이 `갱신 지연`으로 표시되는지 확인합니다.
- 배치 상태가 `PARTIAL_SUCCESS`인지 확인합니다.

### 시나리오 C: 그룹 내부 일부 지점 실패

- 한 지점에 필수 열 누락 데이터를 주입합니다.
- 같은 그룹의 다른 지점이 정상 완료되는지 확인합니다.
- 실패 지점만 재처리 목록에 포함되는지 확인합니다.

### 시나리오 D: 체크포인트 작성 중 종료

- 결과 조각 저장 후 완료 매니페스트 작성 전에 작업자를 종료합니다.
- 미완료 결과가 병합 대상에서 제외되는지 확인합니다.
- 재실행 시 임시 결과가 정리되는지 확인합니다.

### 시나리오 E: 병합 재실행

- 병합 완료 직후 같은 작업을 다시 호출합니다.
- 결과 행이 중복되지 않는지 확인합니다.
- 최종 파티션의 논리 키가 유일한지 확인합니다.

### 시나리오 F: 월말 대량 입력

- 평시보다 큰 예상 데이터량을 입력합니다.
- 그룹 수가 허용 범위에서 자동 확대되는지 확인합니다.
- 서버별 동시 작업 한도가 유지되는지 확인합니다.
- 통신 비용 증가가 지표로 기록되는지 확인합니다.

## 성능 검증 기준
<!--meta: sec=s26; dept=DATA|BE; level=시니어; ct_band=상; related=INC-SV-DET-->
성능 검증은 단순한 총 실행시간 비교뿐 아니라 자원 사용량과 그룹 간 편차를 함께 확인합니다.

검증 절차는 다음과 같습니다.

1. 고정된 입력 스냅샷과 동일한 코드 버전을 사용합니다.
2. 그룹 수를 단계적으로 변경해 실행합니다.
3. 전체 처리시간, 그룹별 처리시간, 최대 메모리, 저장시간을 기록합니다.
4. 병렬성 증가로 절감된 계산시간과 늘어난 통신시간을 분리합니다.
5. 가장 늦게 끝난 그룹의 지점 구성을 확인합니다.
6. 재시도 없이 완료된 실행끼리 비교합니다.
7. 결과 행 수와 체크섬이 같은지 검증합니다.

그룹 수가 증가했는데 전체 시간이 줄지 않거나 체크포인트 저장시간이 크게 증가하면 더 높은 병렬성이 효율적이라고 판단하지 않습니다. 서버 CPU가 남더라도 원천 조회나 중간 저장소가 병목이면 그룹 수 확대가 오히려 실행을 지연시킬 수 있습니다.

성능 변경은 결과 정확성과 멱등성 테스트를 통과한 뒤 반영합니다. 처리시간 개선을 위해 지점 검증, 체크섬 또는 누수 검사를 제거할 수 없습니다.

## 코드 변경 시 검토 체크리스트
<!--meta: sec=s27; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=CODE-BATCH-01-->
배치 코드 변경자는 다음 항목을 확인합니다.

- 다음 7일 예측 범위가 유지되는가
- 기준일 이후 데이터가 입력에 포함되지 않는가
- 지점이 둘 이상의 그룹에 중복 배정되지 않는가
- 그룹 수 자동 조정의 상한과 하한이 유지되는가
- 성공한 그룹이 실패한 그룹 때문에 폐기되지 않는가
- 실패 지점에만 `갱신 지연`이 표시되는가
- 체크포인트 완료 전에 병합되지 않는가
- 재시도 시 결과가 중복 적재되지 않는가
- 같은 입력과 같은 버전에서 결과가 재현되는가
- 신규 로그에 원천 데이터 값이 직접 노출되지 않는가
- 서버별 동시 작업 제한을 우회하지 않는가
- 전체 성공과 부분 성공 상태가 구분되는가
- 기존 완료 체크포인트를 불필요하게 재계산하지 않는가
- 결과 스키마 버전 변경이 병합 코드에 반영되는가

그룹 편성, 체크포인트 키 또는 논리적 결과 키를 변경하는 작업은 일반 전처리 변경보다 영향 범위가 큽니다. 이 경우 부분 재처리, 중복 실행 및 이전 체크포인트 호환성까지 함께 검토합니다.

## 용어 정의
<!--meta: sec=s28; dept=DATA|BE; level=주니어; ct_band=하; related=CODE-BATCH-01-->
- **배치**: 정해진 기준일과 입력 스냅샷으로 여러 지점의 예측을 일괄 수행하는 실행 단위입니다.
- **지점**: 판매 데이터를 수집하고 수요예측 결과를 생성하는 기본 업무 단위입니다.
- **그룹**: 병렬 처리를 위해 여러 지점을 묶은 작업 단위입니다.
- **작업자**: 하나의 그룹을 할당받아 전처리와 예측을 수행하는 실행 프로세스입니다.
- **입력 스냅샷**: 배치가 참조하는 판매 데이터의 확정된 시점 또는 버전입니다.
- **체크포인트**: 완료된 그룹 결과를 재사용할 수 있도록 저장한 데이터와 매니페스트입니다.
- **매니페스트**: 체크포인트의 지점 목록, 행 수, 체크섬 및 완료 상태를 설명하는 메타데이터입니다.
- **멱등성**: 같은 작업을 여러 번 실행해도 최종 결과가 중복되거나 달라지지 않는 성질입니다.
- **부분 성공**: 일부 지점이 실패했지만 성공 지점 결과를 정상 반영한 상태입니다.
- **갱신 지연**: 해당 지점의 최신 예측 결과가 이번 배치에서 생성되지 않았음을 나타내는 상태입니다.
- **부하 점수**: 지점별 예상 데이터량과 최근 처리시간을 조합한 상대적 작업량입니다.
- **병합**: 성공한 그룹의 체크포인트를 대시보드 조회용 테이블에 반영하는 단계입니다.

## 주의점
<!--meta: sec=s29; dept=DATA|BE; level=주니어|시니어; ct_band=상; related=INC-SV-DET-->
그룹 수를 늘리면 병렬성은 좋아지지만 서버 간 통신 비용이 늘어나므로, 월말처럼 데이터량이 많은 시점에는 그룹 수를 자동으로 늘리는 로직이 포함되어 있습니다.

그룹 수 자동 확대는 무조건적인 성능 향상을 의미하지 않습니다. 다음 사항을 함께 확인해야 합니다.

1. 그룹 수 변경 전후의 입력 데이터량이 같은지 확인합니다.
2. 서버 수보다 그룹 수가 많을 때 대기 그룹이 과도하게 늘지 않는지 확인합니다.
3. 중간 저장소 쓰기 시간이 전체 실행시간에서 차지하는 비율을 확인합니다.
4. 지점별 부하 편차가 그룹 수 증가보다 더 큰 병목인지 확인합니다.
5. 실패 재시도가 정상 그룹과 동시에 몰리지 않도록 제한합니다.
6. 수동으로 그룹 수를 지정해도 자원 보호 상한은 우회할 수 없게 합니다.
7. 병렬 실행 순서가 달라져도 최종 결과가 같아야 합니다.
8. 일부 그룹 실패 시 전체 결과를 삭제하는 복구 스크립트를 사용하지 않습니다.
9. 재처리할 때 완료된 지점을 다시 계산하지 않도록 체크포인트를 우선 확인합니다.
10. 대시보드 반영 여부와 예측 계산 완료 여부를 같은 상태로 간주하지 않습니다.

운영 중 그룹 수를 변경할 때는 코드 배포 없이 설정만 바꾸더라도 변경 전후 지표를 기록합니다. 특히 전체 처리시간만 보고 판단하지 말고 최대 메모리, 체크포인트 저장시간, 그룹 간 완료시간 편차 및 갱신 지연 지점 수를 함께 확인합니다.
