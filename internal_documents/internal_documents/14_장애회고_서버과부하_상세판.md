# INC-SV-01 수요예측 배치 서버 과부하(다운) — 상세
<!--meta: doc=INC-SV-DET; doc_type=incident; tier=1; topic=FC; disclosure=internal; status=resolved-->

## 개요
<!--meta: sec=s1; dept=BE|DATA; level=주니어|시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
2026년 11월, 한빛유통 월말 재고 마감과 배치 예측 작업 시점이 겹치면서 배치 서버의 메모리 사용량이 한계를 넘어 서버가 재시작되었습니다. 새벽 4시부터 6시 20분까지 대시보드 갱신이 지연되었고, 발주 담당자 출근 시각인 오전 8시 전에 복구되어 업무 영향은 없었습니다.

이번 장애는 수요예측 모델의 정확도나 예측 로직 오류가 아니라, 월말에 급증한 입력 데이터를 기존 단일 프로세스 중심 구조로 처리하는 과정에서 발생한 인프라 자원 고갈 장애입니다. 장애 구간에는 신규 예측 결과가 대시보드에 반영되지 않았으나 직전 성공 배치 결과는 보존되어 있었고, 원천 재고 및 판매 데이터도 유실되지 않았습니다.

장애 종료 기준은 다음 세 조건이 모두 충족된 시점으로 정의했습니다.

- 45개 지점의 예측 작업이 재실행 또는 검증 완료 상태일 것
- 대시보드에 최신 정상 예측 기준 시각이 표시될 것
- 배치 서버의 메모리 사용률이 안정 구간으로 복귀하고 추가 재시작 징후가 없을 것

복구 완료 시각은 오전 6시 20분이며, 발주 담당자의 실제 업무 개시 전에 정상 상태를 확인했습니다. 다만 고객 업무에 직접적인 차질이 없었다는 이유로 장애를 경미하게 분류하지 않고, 동일 조건에서 업무 시간대 장애로 확대될 수 있었던 고위험 용량 관리 실패로 평가했습니다.

## 장애 등급과 영향 범위
<!--meta: sec=s2; dept=BE|DATA; level=주니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
내부 장애 분류 기준상 본 건은 서비스 전체 접속 불가가 아닌 배치 결과 갱신 지연에 해당합니다. 그러나 서버 재시작과 배치 중단이 동시에 발생했고, 복구가 지연되면 발주 업무에 영향을 줄 가능성이 있었으므로 기술 심각도는 높게 판단했습니다.

| 구분 | 영향 내용 |
|---|---|
| 영향 기능 | 수요예측 배치 실행, 예측 결과 적재, 대시보드 최신 결과 갱신 |
| 비영향 기능 | 사용자 로그인, 기존 대시보드 조회, 원천 데이터 수집, 직전 예측 결과 조회 |
| 영향 대상 | 45개 지점의 신규 예측 결과 |
| 지연 구간 | 새벽 4시부터 오전 6시 20분까지 |
| 데이터 유실 | 없음 |
| 사용자 업무 영향 | 없음 |
| 잠재 업무 영향 | 오전 8시까지 미복구 시 발주 검토 지연 가능 |
| 외부 공지 | 별도 대외 장애 공지 없음 |
| 내부 보고 | 백엔드팀, 데이터분석팀 및 프로젝트 책임자에게 보고 |

기존 결과가 유지되었기 때문에 대시보드 화면 자체는 열렸지만, 최신 결과가 생성되지 않은 상태에서 사용자가 이전 결과를 최신 결과로 오인할 가능성이 있었습니다. 이에 따라 후속 조치에는 단순 복구뿐 아니라 결과 기준 시각과 갱신 지연 상태를 명시적으로 표시하는 개선도 포함했습니다.

## 정상 배치 처리 흐름
<!--meta: sec=s3; dept=BE|DATA; level=주니어; ct_band=하; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
정상적인 수요예측 배치는 다음 순서로 진행됩니다.

1. 지점별 판매·재고·입출고 데이터를 조회합니다.
2. 품목과 영업일 기준으로 데이터를 정렬하고 결측값을 보정합니다.
3. 예측에 필요한 파생 변수를 생성합니다.
4. 지점별·품목별 예측 작업을 수행합니다.
5. 예측 결과와 품질 검증 결과를 저장합니다.
6. 전체 지점 작업이 완료되면 대시보드용 집계 테이블을 갱신합니다.
7. 완료 시각, 처리 건수, 실패 지점 수를 운영 로그에 기록합니다.

장애 당시에는 45개 지점 전체를 하나의 서버 프로세스에서 순차 처리했습니다. 각 지점 처리는 순차적이었지만, 이전 단계에서 만든 중간 데이터와 집계 객체 일부가 프로세스 종료 시점까지 메모리에 남아 있었습니다. 따라서 처리 시간이 길어질수록 메모리가 충분히 회수되지 않았고, 데이터량이 큰 월말에는 평시보다 높은 최대 메모리 사용량이 나타났습니다.

## 장애 전후 시스템 상태
<!--meta: sec=s4; dept=BE; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
장애 전에는 배치 서버가 정상 상태였으며 직전 일자 배치도 성공했습니다. CPU 사용률과 처리 시간은 다소 증가하는 추세였지만 기존 경보 기준을 넘지 않았습니다. 메모리 사용량에 대한 세부 경보는 없었고, 서버가 재시작된 이후에야 실행 중이던 배치의 중단이 확인되었습니다.

| 시점 | 상태 |
|---|---|
| 직전 정상 배치 | 45개 지점 처리 완료, 대시보드 갱신 정상 |
| 장애 당일 입력 적재 | 월말 마감 데이터 포함, 평소보다 데이터량 증가 |
| 배치 시작 초기 | 입력 조회와 전처리 정상 |
| 처리 중반 | 메모리 사용량이 지속 상승하고 회수 속도 저하 |
| 한계 도달 | 운영체제 수준에서 프로세스 유지가 어려워짐 |
| 서버 재시작 후 | 실행 중 작업 중단, 일부 중간 산출물만 존재 |
| 복구 처리 | 지점별 작업 범위를 분리해 재실행 |
| 복구 완료 | 결과 검증 후 대시보드 최신 결과 반영 |

장애 직후에는 서버가 다시 기동되었지만, 기존과 동일한 방식으로 전체 작업을 즉시 재실행하면 같은 문제가 반복될 가능성이 높았습니다. 운영 담당자는 입력 범위를 나누고 지점별 처리 상태를 확인하면서 재실행하는 방식을 선택했습니다.

## 직접 원인
<!--meta: sec=s6; dept=BE|DATA; level=주니어|시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
45개 지점의 전체 품목을 한 서버 프로세스에서 순차 처리하도록 설계했는데, 월말 마감 데이터가 평소보다 3배 많아지면서 메모리에 올린 중간 데이터가 한계를 넘었습니다. 지점별 처리량 변동을 고려한 자원 산정이 없었습니다.

직접적인 실패 과정은 다음과 같습니다.

1. 월말 마감 데이터가 평시보다 크게 증가했습니다.
2. 입력 데이터 조회 결과와 전처리 결과가 동시에 메모리에 유지되었습니다.
3. 지점 처리가 끝날 때마다 불필요한 객체가 충분히 해제되지 않았습니다.
4. 후반 지점 처리 시점에 누적 메모리 사용량이 서버 한계에 근접했습니다.
5. 서버가 재시작되면서 실행 중이던 배치 프로세스가 종료되었습니다.
6. 전체 완료 신호가 생성되지 않아 대시보드 집계 작업도 시작되지 못했습니다.

모델 계산 한 건의 메모리 사용량이 비정상적으로 커진 것은 아니었습니다. 여러 지점의 중간 결과를 장시간 유지하는 처리 구조와 평시 기준으로 설정된 서버 용량이 결합한 것이 직접 원인입니다.

## 근본 원인 분석
<!--meta: sec=s7; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
근본 원인은 단순한 서버 사양 부족이 아니라, 입력량 변화와 실패 격리를 고려하지 않은 배치 아키텍처 및 운영 기준의 부재입니다.

### 1. 처리 단위가 지나치게 큼

45개 지점을 하나의 실행 단위로 묶어 한 지점의 데이터 증가가 전체 작업의 안정성에 영향을 주었습니다. 일부 지점까지 정상 처리되었더라도 프로세스가 종료되면 전체 배치를 실패로 판단해야 했습니다.

### 2. 최대 입력량 기준의 용량 산정 부재

서버 자원은 평시 처리량과 평균 실행 시간을 중심으로 산정되었습니다. 월말 마감, 행사 종료, 재고 실사와 같이 데이터가 집중되는 시점의 최대 입력량은 별도 기준으로 관리하지 않았습니다.

### 3. 중간 데이터 생명주기 관리 미흡

지점 처리가 끝난 후 더 이상 필요하지 않은 전처리 결과와 집계 객체가 즉시 정리되지 않았습니다. 순차 처리라는 이유로 동시성 위험은 낮다고 판단했지만, 장시간 실행 프로세스의 누적 메모리 위험을 충분히 검토하지 않았습니다.

### 4. 조기 경보 부족

서버 생존 여부와 배치 성공 여부는 확인할 수 있었지만, 메모리 사용률 상승 속도와 예상 고갈 시점을 알려주는 경보는 없었습니다. 따라서 장애가 발생하기 전에 작업을 중단하거나 처리 순서를 조정할 기회를 놓쳤습니다.

### 5. 부분 완료 상태 관리 부족

지점별 완료 상태는 로그에 남았지만 운영자가 즉시 재실행 범위를 결정할 수 있는 형태로 구조화되지 않았습니다. 이로 인해 복구 과정에서 로그와 저장 결과를 수동으로 대조해야 했습니다.

따라서 근본 개선 방향은 서버 메모리를 단순 증설하는 것이 아니라, 처리 단위를 분리하고 입력량 기반으로 작업을 분산하며 부분 실패를 격리하는 것입니다. 메모리 증설은 안전 여유를 확보하는 보조 조치로만 사용합니다.

- 전체 성공 여부 중심의 모니터링으로 인해 지점별 진행률을 한눈에 확인하기 어려웠습니다.
- 개발 환경의 시험 데이터가 평시 데이터 분포에 가까워 월말 최대 부하를 재현하지 못했습니다.

## 탐지 과정과 한계
<!--meta: sec=s11; dept=BE; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
장애 당시 탐지는 메모리 임계치 경보가 아니라 대시보드 갱신 지연 확인을 통해 이뤄졌습니다. 즉, 자원 고갈의 선행 신호가 아니라 최종 결과 미생성이라는 후행 신호로 장애를 발견했습니다.

기존 감시 항목은 다음과 같았습니다.

- 서버 실행 여부
- 배치 시작 및 종료 로그
- 최종 성공 여부
- 전체 실행 시간
- 대시보드 결과 적재 시각

그러나 다음 항목은 수집 또는 경보 대상이 아니었습니다.

- 지점 처리 완료 후 메모리 반환 여부
- 지점별 최대 메모리 사용량
- 메모리 사용량 증가 기울기
- 남은 지점 수를 고려한 예상 최대 사용량
- 장시간 유지되는 중간 객체 규모
- 서버 재시작 직전의 자원 상태
- 지점별 처리 지연과 정체 구간

개선 후에는 메모리 사용률이 기준치의 80%를 넘으면 경보가 발생하도록 하고, 단순 순간값뿐 아니라 일정 시간 이상 지속되는지 함께 확인합니다. 반복 경보를 줄이기 위해 경보 발생, 유지, 해제 상태를 구분해 기록합니다.

## 초기 대응과 의사결정
<!--meta: sec=s12; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
초기 대응에서는 “서버를 재기동하고 전체 배치를 다시 실행하는 방안”과 “처리 범위를 분할하여 완료되지 않은 지점만 재실행하는 방안”을 비교했습니다.

전체 재실행은 절차가 단순하지만 다음 위험이 있었습니다.

- 같은 데이터량과 처리 구조로 인해 재차 메모리가 고갈될 수 있음
- 이미 저장된 일부 결과와 재실행 결과가 중복될 수 있음
- 재발 시 오전 8시 이전 복구 가능성이 낮아짐
- 원인 분석에 필요한 실패 시점의 상태가 덮어써질 수 있음

지점 분할 재실행은 운영 절차가 복잡하지만 다음 장점이 있었습니다.

- 작업별 메모리 사용량을 제한할 수 있음
- 완료 지점과 미완료 지점을 분리할 수 있음
- 데이터량이 적은 지점부터 결과를 확보할 수 있음
- 특정 지점 실패가 전체 배치에 미치는 영향을 줄일 수 있음

최종적으로 지점 분할 재실행을 선택했습니다. 복구 속도만을 우선하지 않고 동일 장애의 즉시 재발 가능성을 낮추는 방향으로 판단한 것입니다.

## 복구 절차
<!--meta: sec=s13; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
복구는 다음 순서로 수행했습니다.

1. 서버 재시작 기록과 종료된 배치 프로세스의 마지막 로그를 확보했습니다.
2. 원천 데이터 적재가 완료되었는지 확인했습니다.
3. 45개 지점별 결과 저장 상태를 조회했습니다.
4. 정상 완료, 부분 완료, 미시작 상태로 지점을 구분했습니다.
5. 부분 완료 결과는 집계 대상에서 제외하고 재처리 대상으로 표시했습니다.
6. 입력량이 상대적으로 적은 지점부터 분할 재실행했습니다.
7. 각 지점 처리 종료 후 메모리 사용량과 결과 건수를 확인했습니다.
8. 전체 지점 결과가 준비된 후 집계 작업을 별도로 실행했습니다.
9. 직전 결과 대비 급격한 예측값 변동과 누락 지점을 검증했습니다.
10. 대시보드 기준 시각을 확인하고 오전 6시 20분에 정상화를 선언했습니다.

복구 중에는 원천 데이터를 수정하지 않았으며, 실패한 중간 산출물만 격리했습니다. 재실행 결과에는 동일 실행 기준일을 적용해 지점별 예측 기준이 달라지지 않도록 했습니다.

## 데이터 정합성 검증
<!--meta: sec=s14; dept=DATA|BE; level=주니어|시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
서버 재시작 이후 가장 중요한 검증 항목은 데이터 유실보다 부분 결과의 혼입 여부였습니다. 일부 지점은 예측 계산이 끝났지만 전체 완료 신호가 생성되기 전에 서버가 종료되었을 수 있기 때문입니다.

다음 검증을 수행했습니다.

- 지점별 입력 기준일이 동일한지 확인
- 45개 지점이 모두 결과 집합에 포함되었는지 확인
- 동일 지점·동일 품목·동일 예측일의 중복 결과 확인
- 입력 품목 수와 결과 품목 수의 차이 확인
- 실패 실행에서 생성된 부분 결과의 집계 제외 여부 확인
- 직전 정상 배치 대비 결과 건수 급감 여부 확인
- 예측값의 비정상적 0 또는 음수 발생 여부 확인
- 대시보드 집계 값과 저장된 원본 예측 결과의 합계 대조
- 실행 기준일과 대시보드 표시 기준일 일치 여부 확인

검증 결과 원천 데이터와 최종 예측 결과에는 유실이 없었습니다. 실패 시점에 생성된 중간 결과는 최종 집계 대상에서 제외했고, 재실행으로 생성된 검증 완료 결과만 대시보드에 반영했습니다.

## 메모리 사용 특성 분석
<!--meta: sec=s15; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
배치 메모리 사용량은 단순히 입력 행 수에 비례하지 않았습니다. 원천 데이터 조회 결과 외에도 정렬, 결측 보정, 파생 변수 생성, 예측 입력 변환 및 결과 집계를 위한 복수의 중간 표현이 동시에 존재했기 때문입니다.

특히 다음 구간에서 메모리 사용량이 크게 증가했습니다.

- 원천 데이터와 전처리 복사본이 동시에 존재하는 구간
- 품목별 시계열을 지점 단위로 재구성하는 구간
- 파생 변수 계산 결과를 원본 데이터와 결합하는 구간
- 예측 결과를 저장 전 일괄 집계하는 구간
- 완료된 지점의 요약 데이터를 전체 배치 종료까지 유지하는 구간

월말 데이터가 평소보다 3배 증가했다고 해서 메모리 사용량도 정확히 3배로 증가하는 것은 아닙니다. 정렬 및 결합 과정에서는 복사본과 색인 구조가 추가될 수 있어 최대 메모리 사용량이 비선형적으로 증가할 수 있습니다. 향후 용량 산정에서는 평균 사용량이 아니라 최대 동시 상주 데이터와 변환 단계별 복제 비용을 기준으로 계산합니다.

## 지점 단위 분산 처리 설계
<!--meta: sec=s16; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
후속 구조에서는 45개 지점을 하나의 실패 단위로 취급하지 않고 지점별 작업으로 분리합니다. 각 작업은 독립적인 입력 범위, 실행 상태, 재시도 횟수 및 결과 검증 상태를 가집니다.

분산 처리의 기본 원칙은 다음과 같습니다.

- 한 작업은 원칙적으로 한 지점 범위만 처리합니다.
- 데이터량이 큰 지점은 품목 그룹 단위로 추가 분할할 수 있습니다.
- 작업 완료 후 사용한 중간 데이터는 즉시 해제합니다.
- 전체 성공 여부와 별도로 지점별 성공 여부를 저장합니다.
- 실패 지점만 선택적으로 재실행할 수 있어야 합니다.
- 동일 지점 작업의 중복 실행을 방지합니다.
- 작업 결과가 검증되기 전에는 최종 집계에 포함하지 않습니다.
- 여러 서버가 작업을 가져가되 특정 서버에 대형 지점이 몰리지 않도록 배분합니다.

분산 처리 서버 수는 고정값으로만 운영하지 않습니다. 대기 작업 수, 예상 입력량 및 현재 메모리 여유를 기준으로 동시 실행 수를 조절합니다. 데이터가 적은 날에는 불필요한 서버 사용을 줄이고, 월말에는 작업을 더 세분화하여 최대 메모리 사용량을 제한합니다.

## 작업 우선순위 정책
<!--meta: sec=s17; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
월말 등 데이터량이 몰리는 시점을 사전에 감지해 처리 순서를 조정합니다. 단순히 지점 번호 순서대로 실행하지 않고, 예상 처리량과 업무 중요도를 함께 반영합니다.

우선순위 산정 시 고려하는 항목은 다음과 같습니다.

- 전일 및 최근 7일 입력 건수
- 월말 마감 여부
- 지점별 품목 수
- 직전 배치 실행 시간
- 최근 실패 또는 재시도 이력
- 발주 검토 우선 시각
- 대형 행사나 재고 실사 일정
- 예상 메모리 사용량

초기에는 소형 작업을 먼저 처리해 빠르게 다수 지점의 결과를 확보하고, 대형 작업은 여유 자원이 있는 서버에 배정합니다. 다만 대형 지점이 계속 뒤로 밀리는 현상을 방지하기 위해 대기 시간이 길어질수록 우선순위를 높이는 정책을 적용합니다.

## 모니터링과 경보 기준
<!--meta: sec=s18; dept=BE; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
메모리 사용량이 기준치의 80%를 넘으면 경보가 가도록 모니터링을 추가합니다. 경보는 운영자가 원인을 판단할 수 있도록 서버 상태와 작업 문맥을 함께 제공합니다.

필수 경보 정보는 다음과 같습니다.

- 대상 서버
- 현재 메모리 사용률
- 메모리 사용률의 최근 증가 추세
- 실행 중인 지점 작업
- 완료 작업 수와 남은 작업 수
- 현재 작업의 입력 건수
- 최근 정상 배치의 동일 구간 사용량
- 자동 조치 수행 여부
- 담당 부서와 확인 상태

경보 단계는 다음과 같이 운영합니다.

| 단계 | 조건 | 기본 조치 |
|---|---|---|
| 주의 | 메모리 사용률이 기준치의 80% 초과 | 신규 작업 할당 축소, 담당자 알림 |

순간적인 사용량 상승만으로 불필요한 작업 중단이 발생하지 않도록 지속 시간과 증가 추세를 함께 판단합니다. 단, 서버 재시작 징후가 있거나 운영체제 수준의 메모리 부족 이벤트가 발생하면 지속 시간 조건 없이 즉시 위험 단계로 전환합니다.

## 대시보드 저하 운영 방식
<!--meta: sec=s19; dept=BE|DATA; level=주니어; ct_band=하; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
배치 실패 시 부분 결과라도 대시보드에 “갱신 지연” 표시와 함께 이전 결과를 유지하도록 변경합니다. 검증되지 않은 일부 지점의 신규 결과와 직전 결과를 혼합해 최신 결과처럼 제공하지 않는 것이 원칙입니다.

대시보드 표시 규칙은 다음과 같습니다.

- 전체 배치가 정상 완료되면 최신 결과와 완료 시각을 표시합니다.
- 일부 지점이 처리 중이면 “갱신 중” 상태를 표시합니다.
- 예정 완료 시각을 넘기면 “갱신 지연” 상태를 표시합니다.
- 신규 결과 검증이 끝나지 않았으면 직전 정상 결과를 유지합니다.
- 직전 결과를 표시할 때는 해당 결과의 기준일과 생성 시각을 명시합니다.
- 사용자가 결과를 내려받을 때도 동일한 상태 정보를 포함합니다.
- 모든 지점이 실패한 경우에도 빈 화면 대신 직전 정상 결과를 제공합니다.

이 방식은 데이터가 없는 것처럼 보이는 문제를 줄이지만, 오래된 결과가 최신 결과로 오인되지 않도록 상태 배지와 기준 시각을 함께 표시해야 합니다.

## 재시도와 중복 방지 원칙
<!--meta: sec=s20; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
분산 처리에서는 자동 재시도가 가능하지만, 동일 작업의 중복 실행과 결과 중복 적재를 방지해야 합니다. 재시도는 실패 원인에 따라 구분합니다.

- 일시적 서버 자원 부족은 다른 서버에서 재시도합니다.
- 입력 데이터 형식 오류는 자동 재시도하지 않고 검증 실패로 분류합니다.
- 메모리 사용량 초과는 작업 범위를 더 작게 나눈 후 재시도합니다.
- 결과 저장 직전 실패는 기존 저장 여부를 먼저 확인합니다.
- 동일 원인으로 반복 실패하면 자동 재시도를 중단하고 수동 확인으로 전환합니다.

각 작업은 실행 기준일, 지점, 작업 유형을 조합한 고유 식별 기준을 가집니다. 동일 기준의 결과가 이미 검증 완료 상태라면 후속 실행은 결과를 덮어쓰지 않습니다. 실패 실행에서 일부 결과가 저장된 경우에는 검증 완료 표시가 없으므로 최종 집계에서 제외됩니다.

## 용량 산정 기준 개선
<!--meta: sec=s21; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
향후 배치 서버 용량은 평균 처리량이 아니라 최대 처리 시나리오와 안전 여유를 기준으로 산정합니다. 용량 검토 시 다음 요소를 포함합니다.

- 전체 입력 건수와 지점별 최대 입력 건수
- 전처리 단계별 데이터 확대 비율
- 한 작업의 최대 메모리 사용량
- 동시에 실행할 작업 수
- 서버 운영체제와 공통 프로세스가 사용하는 기본 메모리
- 장애 분석 및 모니터링을 위한 여유 공간
- 월말, 행사, 재고 실사 등 데이터 집중 이벤트
- 데이터 증가 추세와 향후 지점 확대 가능성

검증 시나리오는 최소 다음 세 수준으로 구분합니다.

| 수준 | 목적 |
|---|---|
| 평시 부하 | 일반 영업일 처리 시간과 자원 사용량 확인 |
| 월말 부하 | 평소보다 3배 많은 입력 조건에서 안정성 확인 |
| 한계 부하 | 작업 분할, 경보, 자동 중단이 정상 작동하는지 확인 |

한계 부하 시험의 목적은 서버가 무조건 모든 입력을 처리하도록 만드는 것이 아닙니다. 위험 수준에 도달하기 전에 신규 작업을 제한하고, 이미 처리한 결과를 보존하며, 안전하게 재개할 수 있는지를 확인하는 데 있습니다.

<!--forbid: 한빛유통|INC-SV-->
INC-SV-02는 분산 처리 전환 시험 중 의도적으로 발생시킨 재시도 집중 사례입니다. 다수 작업이 동일한 일시 오류를 만났을 때 즉시 재시도되면서, 짧은 시간에 작업 요청이 한 서버로 몰리는 현상이 확인되었습니다.

INC-SV-01이 장시간 누적된 메모리 사용량으로 인한 과부하였다면, INC-SV-02는 재시도 정책이 순간 부하를 확대할 수 있음을 확인한 사례입니다. 운영 장애로 확대되기 전 시험 환경에서 차단했으며 다음 개선을 적용했습니다.

- 재시도 간 대기 시간을 두고 작업별로 시작 시점을 분산
- 동일 서버로 즉시 재할당하지 않도록 제한
- 전체 재시도 작업 수의 상한 설정
- 반복 실패 작업을 별도 대기 상태로 전환
- 재시도 원인과 횟수를 모니터링 항목에 포함

이 사례를 통해 분산 처리 자체가 과부하를 자동으로 해결하는 것은 아니며, 작업 생성 속도와 재시도 속도도 서버 수용량에 맞춰 통제해야 한다는 점을 확인했습니다.

## 유사 장애 사례 INC-SV-03
<!--meta: sec=s28; dept=BE|DATA; level=시니어; ct_band=상; related=INC-SV-DET-->
<!--forbid: 한빛유통|INC-SV-->
INC-SV-03은 대량 부하 시험 중 중간 산출물 저장 공간이 빠르게 증가한 사례입니다. 메모리 사용량은 안정적이었으나 실패 분석을 위해 보존한 임시 결과가 정리되지 않아 저장 공간 부족 위험이 발생했습니다.

INC-SV-01 후속 조치에서 메모리 안정성에 집중하는 과정에서 다른 자원인 저장 공간과 파일 식별자 사용량을 함께 확인해야 한다는 교훈을 얻었습니다. 다음 운영 기준을 추가했습니다.

- 임시 산출물에 만료 시각 부여
- 성공 작업의 중간 파일 즉시 정리
- 실패 작업의 중간 파일 보존 기간 제한
- 저장 공간 사용률 경보 추가
- 작업별 임시 파일 크기 기록
- 복구 완료 후 잔여 파일 점검

INC-SV-02와 INC-SV-03은 모두 INC-SV-01의 후속 검증 과정에서 발견한 별도 실패 유형입니다. 세 사례를 통합해 메모리, 재시도 요청량, 저장 공간을 배치 안정성의 핵심 자원으로 관리합니다.

## 재발 방지 완료 기준
<!--meta: sec=s29; dept=BE|DATA; level=시니어; ct_band=상; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
본 장애의 재발 방지는 서버 재시작이 한 번도 발생하지 않는 것만으로 판단하지 않습니다. 다음 조건이 모두 충족되어야 합니다.

- 45개 지점 작업이 독립된 실패 단위로 실행됨
- 평소보다 3배 많은 입력 조건에서 전체 결과 생성 가능
- 단일 서버 종료 시 다른 지점 작업이 계속 진행됨
- 실패 지점만 선별 재실행 가능
- 메모리 사용량 80% 초과 시 경보 발생
- 위험 수준에서 신규 작업 할당이 제한됨
- 검증되지 않은 부분 결과가 대시보드에 혼입되지 않음
- 갱신 지연 시 직전 정상 결과와 기준 시각이 표시됨
- 운영자가 지점별 진행 상태와 실패 원인을 조회할 수 있음
- 재시도 집중과 임시 저장 공간 증가가 통제됨
- 월말 사전 점검과 부하 시험 결과가 기록됨

개선 이후에도 최대 메모리 사용량이 매월 증가한다면 해결 완료 상태와 별개로 용량 재검토를 수행합니다. 처리량 증가가 구조적 추세인지 일시적 이벤트인지 구분하고, 필요하면 지점 작업을 품목 그룹 단위로 추가 분할합니다.

## 회고와 교훈
<!--meta: sec=s30; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-FC-DET-->
<!--forbid: 한빛유통|INC-SV-->
이번 장애에서 잘된 점은 원천 데이터와 직전 정상 결과가 보존되었고, 전체 재실행 대신 지점 분할 복구를 선택해 오전 8시 이전에 정상화한 것입니다. 백엔드팀과 데이터분석팀이 서버 상태와 결과 정합성을 병렬로 확인해 복구 판단의 정확도를 높였습니다.

개선이 필요한 점은 평균 처리량을 정상 기준으로 삼았고, 월말 최대 입력량을 별도 운영 시나리오로 관리하지 않았다는 것입니다. 또한 서버가 재시작되기 전에 위험을 감지할 수 있는 메모리 경보와 지점별 진행 상태가 부족했습니다.

핵심 교훈은 다음과 같습니다.

1. 순차 처리도 중간 데이터가 누적되면 메모리 과부하가 발생할 수 있습니다.
2. 평균 처리량 기준의 용량 산정만으로 월말 안정성을 보장할 수 없습니다.
3. 배치 작업은 전체 성공 여부뿐 아니라 부분 완료 상태를 관리해야 합니다.
4. 재실행 가능성은 장애 발생 후가 아니라 정상 설계 단계에서 확보해야 합니다.
5. 화면 접근 가능 여부와 데이터 최신성은 별도의 서비스 지표입니다.
6. 단순 서버 증설보다 실패 단위 축소와 작업 격리가 우선입니다.
7. 경보는 자원 수치뿐 아니라 실행 중인 업무 문맥을 함께 제공해야 합니다.
8. 메모리 개선 이후에는 재시도 집중과 저장 공간 같은 인접 자원 위험도 점검해야 합니다.
9. 고객 업무 영향이 없었더라도 잠재 영향이 컸다면 동일 수준의 회고와 개선이 필요합니다.
10. 장애 종료는 서버 복구, 데이터 검증, 사용자 표시 정상화가 모두 끝난 뒤 선언해야 합니다.
