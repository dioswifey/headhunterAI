# 기술 부채와 납기 사이 의사결정 가이드
<!--meta: doc=PSY-06; doc_type=decision_guide; tier=1; topic=PROCESS; disclosure=internal; status=active-->

## 목적과 적용 대상
<!--meta: sec=s1; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->
이 가이드는 납기와 기술 품질이 충돌할 때 담당자의 성향, 회의 분위기 또는 고객의 일시적 압박만으로 결론을 내리는 상태를 없애기 위해 사용한다.

목표는 지름길을 전면 금지하는 것이 아니라, 선택의 근거와 후속 책임을 확인할 수 있게 만드는 것이다. 일정 준수를 위해 부채를 받아들이는 결정도 허용하되 기록 없이 남겨 두는 결정은 허용하지 않는다.

| 구분 | 적용 여부 | 적용 범위 |
|---|---|---|
| 고객 사업 수행 | 적용 | 설계, 구현, 시험, 배포 준비 과정에서 납기와 구조적 품질이 충돌하는 결정 |
| 사내 공통 자산 | 적용 | 여러 사업이나 팀이 재사용하는 코드, 모델, 데이터 처리 구성, 자동화 도구 |
| 운영 중 시스템 | 적용 | 변경, 유지보수, 성능 개선 과정에서 미래 작업 비용을 발생시키는 선택 |
| 장애 대응 중 긴급 조치 | 제외 | 서비스 복구를 우선하는 임시 조치와 현장 지휘 |
| 리팩터링 구현 방법 | 제외 | 코드 분리, 패턴 적용, 모듈 재구성 등 구체적 기법 |
| 일반 코드 품질 판정 | 제외 | 명명, 포맷, 정적 분석 규칙 등 개발 표준이 정하는 항목 |

장애 대응 중 긴급 조치는 이 가이드의 사전 판정을 거치지 않는다. 다만 복구가 끝난 뒤 임시 조치가 지속되는 경우에는 적용 대상에 포함한다.

이 문서는 다음 세 가지를 정한다.

1. 어떤 선택을 기술 부채로 판정하고 어떻게 구분하는지 정한다.
2. 납기를 우선할 때 남겨야 할 근거, 책임자, 후속 조치 기록을 정한다.
3. 담당자가 단독으로 결정할 수 있는 범위와 상위 판단이 필요한 조건을 정한다.

적용자는 AI/AX개발팀, 백엔드팀, 데이터분석팀에서 설계·개발·검토·운영 변경에 참여하는 사원부터 부장까지이다.

두 팀 이상에 영향을 주는 선택은 특정 팀의 내부 사정만으로 종결하지 않는다. 영향을 받는 구성요소와 후속 작업의 소유 주체가 확인된 상태에서 결론을 남긴다.

다음 사항은 이 문서가 정하지 않는다.

- 특정 언어, 프레임워크 또는 데이터 플랫폼에 맞춘 리팩터링 절차
- 함수 길이, 테스트 커버리지, 복잡도 등 개별 코드 품질 기준값
- 장애 발생 중 복구 명령과 비상 대응 순서
- 고객 계약의 해석이나 법률적 책임에 대한 확정 판단

계약 또는 법률상 의무와 연결되는 사안은 사안별 확인이 필요하다.

구두 합의, 메신저 반응, 회의 참석자의 묵시적 동의는 기록을 대신하지 못한다. 결정 결과를 추적할 수 없는 경우에는 결정이 완료되지 않은 것으로 본다.

## 기술 부채의 정의와 부채가 아닌 것
<!--meta: sec=s2; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=s1-->
기술 부채는 트레이드오프의 비용이다. 더 낫고 덜 제약된 해법 대신 현재의 시간을 산 대가로, 이후 변경·검증·배포·운영에 추가 비용이나 제약을 발생시키는 상태를 뜻한다.

현재 결과물이 불완전하거나 오래되었다는 사실만으로 기술 부채가 되지는 않는다. 최초 선택과 미래 비용 사이의 인과관계를 확인해야 한다.

| 사례 | 판정 | 판정 근거 |
|---|---|---|
| 임시 우회로가 정식 구조처럼 남은 상태 | 부채 | 이후 변경이 우회 경로에 종속된다 |
| 시험 없이 반영한 변경 | 부채 | 회귀 여부를 매번 수동으로 확인해야 한다 |
| 동일 로직을 복사해 만든 중복 구현 | 부채 | 수정 지점이 늘고 결과 불일치 가능성이 생긴다 |
| 하드코딩된 고객별 분기 | 부채 | 고객 추가 시 조건문과 검증 범위가 함께 증가한다 |
| 되돌릴 수 없게 얽힌 데이터 구조 | 부채 | 변경·복구·이관 선택지가 제한된다 |
| 요구대로 동작하지 않는 단순 결함 | 버그 | 기대 동작과 실제 동작의 불일치이다 |
| 계약 또는 계획에 포함되지 않은 기능 | 미구현 기능 | 구현 약속이 없는 상태 자체는 부채가 아니다 |
| 지원 중인 오래된 기술 | 부채 아님 | 연식만으로 추가 비용이 확정되지 않는다 |
| 코드 스타일에 대한 개인별 선호 차이 | 부채 아님 | 유지 비용의 객관적 증가가 확인되지 않는다 |
| 애초에 필요하지 않았던 문서의 부재 | 부채 아님 | 작성 의무와 활용 목적이 존재하지 않는다 |

단순한 버그는 수정 대상이지만 기술 부채 집계에는 넣지 않는다. 다만 결함을 막을 시험 구조가 의도적으로 생략되어 같은 종류의 오류가 반복된다면, 결함과 별도로 시험 구조의 부채를 식별한다.

미구현 기능도 독립적인 부채가 아니다. 이미 구현하기로 한 기능을 임시 분기로 대체해 다른 변경을 어렵게 만든 경우에는 그 임시 구조만 부채로 본다.

오래된 라이브러리나 프레임워크는 다음 중 하나가 확인될 때 부채 후보가 된다.

- 필요한 변경을 지원하지 않아 별도 우회 구현이 계속 추가된다.
- 유지 중단으로 패치나 호환성 확보에 반복 작업이 발생한다.
- 교체 지연으로 연동 가능한 선택지가 실제로 축소된다.

문서가 없다는 사유도 동일하게 구분한다. 운영 인수, 변경 판단 또는 복구에 필요한 문서를 생략해 매번 담당자에게 의존한다면 부채가 될 수 있다. 반대로 사용 목적이 없는 문서까지 생성하지 않았다는 이유로 등록하지 않는다.

판정자는 다음 질문에 모두 답한다.

1. 당시 더 나은 대안이 존재했거나 이후 확인되었는가.
2. 현재 선택으로 시간을 절약했거나 검토를 생략했는가.
3. 그 선택 때문에 미래 작업에 추가 비용, 제약 또는 반복 위험이 생기는가.

세 질문 중 세 번째가 확인되지 않으면 개선 의견으로 취급하며 기술 부채로 집계하지 않는다.

“코드가 지저분하다”, “구조가 낡았다”, “마음에 들지 않는다”와 같은 표현은 판정 근거로 사용하지 않는다. 추가되는 작업이나 제한되는 선택지를 특정해야 한다.

용어를 느슨하게 사용하면 버그, 기능 요청, 유지보수 작업이 하나의 수치에 섞여 추세 비교가 불가능해진다. 따라서 등록 명칭에는 상태와 발생 비용을 함께 적고, 평가적 표현만으로 제목을 작성하지 않는다.

## 부채 4분면 분류
<!--meta: sec=s3; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s2|s4-->
부채는 두 축으로 분류한다. 첫 번째 축은 지름길을 의도적으로 택했는지 또는 모르고 빠졌는지이며, 두 번째 축은 신중한 판단이었는지 또는 생각 없이 모서리를 잘랐는지이다.

분류는 작성자의 의도를 추측하지 않고 당시 기록, 검토 흔적, 대안 검토 여부와 재검토 계획을 근거로 한다.

| 4분면 | 판단 특성 | 전형적 예시 | 기본 처리 방침 |
|---|---|---|---|
| 의도적·신중 | 비용과 제약을 알고 합리적 트레이드오프로 선택 | 출시일 준수를 위해 확장 구조를 다음 반복 주기로 미룬 경우 | 합의한 재검토일까지 관찰하고 조건 도래 시 다시 판단한다 |
| 의도적·무모 | 위험을 알면서 근거·책임·복구 계획 없이 생략 | 시험 실패를 인지하고도 후속 조치 없이 배포 경로에 남긴 경우 | 작업 중단 필요성을 검토하고 책임자와 보완 기한을 즉시 지정한다 |
| 비의도적·신중 | 당시 정보로 합리적으로 설계했으나 이후 제약을 발견 | 신규 연동 조건이 추가되면서 기존 인터페이스 결합이 드러난 경우 | 새 정보가 미치는 범위를 확인한 뒤 계획 가능한 작업으로 전환한다 |
| 비의도적·무모 | 검토 없이 만들어져 결합이나 취약성이 뒤늦게 발견 | 문서화되지 않은 구성요소 결합, 되돌아볼 계획이 없던 취약한 배포 경로 | 발견 즉시 영향 범위를 조사하고 다른 항목보다 빠르게 조치 여부를 판단한다 |

출시일이나 시장 검증을 위한 지름길은 다음 항목이 모두 명시되어 있으면 의도적·신중 분류가 가능하다.

- 선택에 책임지는 소유자
- 얻는 일정상 이익과 포기하는 기술적 선택
- 영향을 받는 구성요소와 작업
- 결정을 다시 볼 날짜 또는 사건 조건

재검토일 없이 “나중에 개선”이라고만 적은 선택은 의도적·신중으로 분류하지 않는다. 일정 압박이 있었다는 사실도 신중성을 자동으로 증명하지 않는다.

비의도적 부채는 발견 전까지 통제되지 않았다는 점을 반영한다. 특히 문서화되지 않은 결합이나 복구 계획이 없는 배포 경로는 영향 범위를 알 수 없으므로 조사를 앞당긴다.

분류 절차는 다음과 같다.

1. 부채를 발견한 사람이 발견 당일 두 축의 잠정값과 근거를 작성한다.
2. 해당 구성요소의 기술 책임자가 1영업일 이내 당시 대안 검토와 위험 인지 여부를 확인한다.
3. 영향을 받는 팀이 둘 이상이면 각 팀의 기술 검토자가 분류 근거에 의견을 남긴다.
4. 증거가 부족하면 신중으로 간주하지 않고 `판정 보류`로 표시한다.
5. 보류 상태에서는 확인할 자료와 확인 담당자를 함께 지정한다.

의도성은 “누군가 알고 있었다”가 아니라 선택 당시 지름길임을 인식하고 채택했는지로 판정한다. 신중성은 회의 개최 여부가 아니라 대안, 손실, 책임, 재검토 조건이 실제로 다뤄졌는지로 판정한다.

분류는 고정값이 아니며 다음 사건이 발생하면 다시 확인한다.

- 기존 기록에서 확인되지 않았던 의도적 선택 근거가 발견된 경우
- 예상한 영향 범위를 넘어 다른 서비스나 데이터 흐름으로 제약이 확산된 경우
- 지정한 재검토일이 지났는데도 후속 판단이 없었던 경우
- 담당자 변경으로 소유권이나 복구 계획이 사라진 경우
- 합리적이라고 본 일정 이익이 실제로 발생하지 않은 것으로 확인된 경우

의도적·신중 항목이라도 재검토 조건을 반복해서 넘기면 기존 분류를 유지하지 않는다. 계획의 존재와 계획의 이행은 별도로 확인한다.

반대로 비의도적으로 발견된 항목도 당시 설계 자료와 검토 기록에서 합리적 판단이 확인되면 비의도적·신중으로 조정할 수 있다.

4분면은 발생 경위와 통제 수준을 표시하는 분류값이다. 이 값만으로 상환 순서, 작업량 또는 완료 기한을 확정하지 않는다.

## 부채 등록부 항목과 등록 시점
<!--meta: sec=s4; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=상; related=s3-->
부채 등록부는 코드, 모델, 데이터 처리 로직, 배포 구성 및 기술 산출물에 남은 부채를 한 행 단위로 기록한다.
하나의 행에는 독립적으로 상환 여부를 결정할 수 있는 범위만 담는다.

| 열 | 필수 기재 내용 |
|---|---|
| 부채 ID | 다른 항목과 중복되지 않는 식별자 |
| 등록일 | 지름길을 결정하거나 부채를 확인한 날짜 |
| 등록자 | 최초로 항목을 작성한 담당자 |
| 위치(모듈·산출물) | 저장소, 모듈, 모델, 파이프라인 또는 기술 산출물 위치 |
| 내용 | 현재 상태와 원래 기대한 상태의 차이 |
| 4분면 분류 | PSY-06#s3 기준 분류 |
| 발생 사유 | 일정, 자원, 정보 부족, 설계 누락 등 직접 원인 |
| 결정 근거와 결정자 | 의도적 결정인 경우 검토한 대안, 선택 이유 및 결정자 |
| 영향 | 느려지는 작업, 제약받는 변경 또는 증가하는 위험 |
| 추정 이자 | PSY-06#s5에 따라 산정한 값 또는 `이자 미측정` |
| 상환 추정 공수 | 분석, 수정, 시험 및 배포를 포함한 예상 공수 |
| 재검토일 | 유지·상환·종결 여부를 다시 판단할 날짜 |
| 소유자 | 후속 산정과 상태 갱신에 책임지는 담당자 |
| 상태 | 등록, 분석 중, 상환 예정, 상환 중, 종결, 상환하지 않음 중 하나 |

등록 위치는 파일명만 적지 않고 담당자가 대상을 다시 찾을 수 있는 수준으로 작성한다.
여러 저장소에 걸친 항목은 대표 위치와 영향받는 위치를 함께 적는다.
내용에는 해결 방법을 확정해 쓰지 않으며, 관찰된 제약과 기대 상태를 구분해 기록한다.

등록 의무가 발생하는 시점은 다음과 같다.

1. 의도적으로 지름길을 택할 때에는 구현을 시작하기 전에 등록한다.
2. 구현 중 지름길이 필요해졌다면 해당 변경을 병합하거나 배포하기 전에 등록한다.
3. 코드 검토, 시험 또는 운영 중 비의도적 부채를 확인했다면 발견한 근무일 안에 등록한다.
4. 기존 항목과 원인이 같더라도 위치나 상환 판단이 다르면 별도 행으로 등록하고 연관 ID를 남긴다.
5. 회의에서만 합의하고 나중에 일괄 정리하는 방식은 등록으로 인정하지 않는다.

최초 등록에 필요한 최소 필드는 부채 ID, 등록일, 등록자, 위치, 내용, 4분면 분류, 발생 사유, 영향, 소유자 및 상태이다.
의도적 결정에는 결정 근거, 결정자와 재검토일을 최초 등록 단계에서 추가한다.
추정 이자와 상환 공수를 즉시 계산할 수 없으면 빈칸으로 두지 않고 각각 `이자 미측정`, `산정 전`으로 표시한다.
해당 두 값은 상환 우선순위를 판정하기 전에 보완한다.

등록 없이 지름길을 구현·병합·배포하는 행위는 금지한다.
등록 작성 시간이 길어지는 경우에는 최소 필드로 먼저 생성하고 상세 근거를 첨부 자료로 연결한다.
설계 설명, 대안 비교 또는 시험 결과를 등록부 셀에 모두 복사하지 않는다.

코드 주석은 특정 구현 위치를 설명할 뿐 부채 등록부를 대체하지 못한다.
주석만 남기면 여러 모듈의 영향을 집계할 수 없고, 결정자·재검토일·상환 공수를 확인할 수 없다.
코드가 이동되거나 삭제되면 주석도 함께 사라질 수 있으므로 등록부 ID를 주석에 연결하는 방식만 허용한다.
상환이 끝난 항목은 삭제하지 않고 완료 근거를 남긴 뒤 상태를 `종결`로 바꾼다.

## 이자 추정 방법
<!--meta: sec=s5; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s4|s6-->
부채의 이자는 해당 상태를 유지함으로써 반복해서 발생하거나 앞으로 발생할 것으로 예상되는 추가 비용이다.
추정은 정상 구조였을 때 필요한 기준 공수와 현재 구조에서 실제로 드는 공수의 차이를 사용한다.
기능 개발 자체의 공수는 이자에 포함하지 않는다.

| 이자 유형 | 추정 단위 | 측정 방법 | 우선 근거 자료 |
|---|---|---|---|
| 추가 작업 시간 | 인시/월 | 동일 영역 작업 1회당 여분 공수 × 월간 예상 작업 횟수 | 작업 기록, 커밋, 코드 검토 기록 |
| 사고 위험 | 기대 손실 인시/월 | 월간 발생 가능성 × 발생 시 복구·검증 공수 | 장애 기록, 시험 결과, 운영 로그 |
| 변경 지연 | 지연 일수/배포 | 정상 경로 대비 분석·시험·승인 지연을 측정 | 배포 기록, 작업 시작·완료 시각 |
| 신규 인력 적응 비용 | 인시/인원 | 표준 온보딩 외에 구조 파악과 우회 절차 학습에 든 시간 | 인수인계 기록, 질의 기록 |
| 고객 대응 공수 | 인시/월 | 부채로 인해 추가된 설명, 확인, 재시험 및 회신 시간을 합산 | 고객 요청 기록, 회의록, 작업 내역 |

추가 작업 시간은 최근 동일 영역을 변경한 사례를 우선 사용한다.
비교 사례가 없으면 예정된 변경 건수와 단계별 추가 작업을 분리해 추정한다.
월간 작업 횟수가 일정하지 않으면 최근 관측 기간과 환산 근거를 함께 적는다.

사고 위험의 발생 가능성은 추측성 표현 대신 관측 횟수, 재현 결과 또는 시험 실패율로 뒷받침한다.
영향에는 복구뿐 아니라 원인 분석, 재시험 및 재배포에 필요한 시간을 포함한다.
금전 손실이나 법률상 영향은 기술 공수로 임의 환산하지 않으며 사안별 확인이 필요하다고 표시한다.

변경 지연은 전체 프로젝트 일정을 적지 않고 해당 부채 때문에 추가된 기간만 계산한다.
여러 작업이 병렬로 진행되어 실제 납기가 늦어지지 않았다면 지연 일수는 0으로 기록할 수 있다.
다만 동일한 대기 시간이 담당자 공수로 발생했다면 추가 작업 시간에 반영한다.

신규 인력 적응 비용은 최초 1회 비용과 인원 증가에 따라 반복되는 비용을 구분한다.
고객 대응 공수는 일반적인 정기 보고 시간을 제외하고 부채로 인해 추가된 활동만 합산한다.
하나의 활동을 두 이자 유형에 중복 계상하지 않고 가장 직접적인 유형 하나에 배정한다.

추정 절차는 다음과 같다.

1. 소유자가 계산 대상 기간과 기준 상태를 먼저 고정한다.
2. 소유자와 해당 영역 검토자가 같은 근거 자료를 사용해 서로의 값을 보지 않고 독립 추정한다.
3. 두 기준값의 차이가 큰 값 대비 25% 이내이면 평균값을 등록한다.
4. 차이가 25%를 넘으면 빈도, 회당 공수 및 영향 범위를 다시 분해한 뒤 재추정한다.
5. 최종값에는 계산식, 관측 기간, 자료 위치와 마지막 갱신일을 연결한다.

측정 자료가 없거나 두 추정자가 합의 가능한 범위를 만들지 못하면 `이자 미측정`으로 표시한다.
`이자 미측정` 항목은 낮은 값으로 간주하지 않으며 PSY-06#s6의 이자 점수 중간값을 적용한다.
이후 실제 작업이나 사고가 발생하면 해당 기록을 사용해 값을 갱신한다.

월간 추가 공수가 1인시 미만이고 변경 지연과 측정 가능한 사고 위험이 없는 항목은 이자가 0에 가까운 것으로 본다.
이 경우 상환 자체가 더 많은 비용을 만들 수 있으므로 유지가 정상적인 판단이다.
상환하지 않는 결론은 추정 근거와 관측 기간이 유효한 동안만 적용한다.

## 상환 우선순위 판정 모델
<!--meta: sec=s6; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s5-->
상환 우선순위는 이자 크기, 영향 범위, 확산 속도 및 상환 비용의 네 요소를 각각 1점부터 5점까지 평가해 계산한다.
총점은 네 점수의 합이며 범위는 4점부터 20점까지이다.
상환 비용은 적은 공수로 큰 제약을 제거할 수 있는 항목이 앞서도록 역점수를 적용한다.

| 점수 | 이자 크기 I | 영향 범위 B | 확산 속도 S | 상환 비용 C |
|---|---|---|---|---|
| 1 | 월 2인시 미만 | 단일 사업의 단일 모듈 | 격리되어 복제 가능성이 없음 | 20 M/D 초과 |
| 2 | 월 2인시 이상 8인시 이하 | 단일 사업의 복수 모듈 | 수동 복제 가능성이 있으나 예정 작업이 없음 | 10 M/D 초과 20 M/D 이하 |
| 3 | 월 8인시 초과 24인시 이하 또는 이자 미측정 | 2개 사업 또는 3개 이상 모듈 | 예정된 변경에서 한 차례 이상 복제될 가능성이 있음 | 3 M/D 초과 10 M/D 이하 |
| 4 | 월 24인시 초과 80인시 이하 | 3개 이상 사업 | 반복 주기마다 같은 우회가 추가됨 | 1 M/D 초과 3 M/D 이하 |
| 5 | 월 80인시 초과 | 다수 사업이 공통으로 사용하는 구성요소 | 템플릿·자동 생성·공통 의존성으로 계속 전파됨 | 1 M/D 이하 |

사고 위험, 변경 지연, 적응 비용 및 고객 대응 공수는 PSY-06#s5에서 산정한 월간 환산값에 합산한다.
상환 추정 공수에는 분석, 수정, 회귀시험, 배포 및 관련 문서 갱신을 포함한다.
점수 근거가 두 구간에 걸치면 현재 확인된 값이 속한 구간을 적용하고 추정 범위를 별도로 남긴다.

우선순위 총점은 `I + B + S + C`로 계산한다.

| 총점 | 처리 구간 | 처리 기준 |
|---|---|---|
| 17~20점 | 즉시 | 현재 작업과의 충돌을 확인하고 2영업일 안에 착수 계획을 확정한다 |
| 14~16점 | 다음 반복 주기 | 다음 반복 주기 계획에 상환 작업과 완료 조건을 편성한다 |
| 10~13점 | 분기 내 | 해당 분기 종료 전 실행 가능한 반복 주기에 배치한다 |
| 7~9점 | 보류 | 상환 작업을 편성하지 않고 재산정 조건을 기록한다 |
| 4~6점 | 상환하지 않음 | 유지 비용이 상환 비용보다 작다는 근거를 남기고 비상환 상태로 종결한다 |

이 표의 `즉시`는 우선순위상 착수 시점을 뜻한다.
작업을 중단해야 하는 금지선 해당 여부는 점수와 별개로 PSY-06#s9를 적용한다.
결정 권한은 PSY-06#s12를 따른다.

전체 등록부를 동일한 수준으로 정리하려 하지 않는다.
누적 고통의 80%를 유발하는 상위 20% 부채를 먼저 식별하고 해당 집합에 상환 역량을 집중한다.
상위 집합은 총점뿐 아니라 실제 이자 합계와 반복 발생 기록을 함께 사용해 확인한다.

곧 폐기될 코드의 부채는 폐기 예정일, 대체 경로 및 추가 확산이 없다는 근거가 확인되면 상환하지 않을 수 있다.
폐기 예정일이 취소되거나 대체 경로가 지연되면 해당 항목을 즉시 재산정한다.
비상환 결정에는 판단일, 근거, 수용한 잔여 영향 및 다음 확인 조건을 기록한다.

열린 부채의 점수는 매월 한 번 재산정한다.
사고 발생, 적용 사업 증가, 공통 모듈 복제 또는 상환 공수 변경이 확인되면 정기 주기를 기다리지 않는다.
`상환하지 않음` 항목은 폐기 계획 변경이나 영향 범위 확대가 발생했을 때 다시 연다.
재산정 결과 처리 구간이 바뀌면 등록부의 이전 점수를 보존하고 변경 사유를 추가한다.

## 반복 주기 할당 비율
<!--meta: sec=s7; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s6-->
AIAX·BE·DATA는 모든 반복 주기에서 가용 기술 공수의 15~25%를 부채 축소에 배정한다.  
가용 기술 공수는 해당 주기에 실제 투입 가능한 인원의 총공수에서 휴가, 교육, 영업 지원 및 확정된 회의 시간을 제외한 값이다.  
부채 축소 공수에는 원인 제거, 회귀시험, 문서 보정 및 배포 검증을 포함한다.  
단순 현상 조사나 신규 기능 구현은 이 할당에 계상하지 않는다.

| 사업 단계 | 기준 비율 | 적용 대상 | 배정 목적 |
|---|---:|---|---|
| 착수·설계 구간 | 15% | 기반 구조, 개발·시험 환경 | 초기 구조 제약과 임시 설정의 고착 방지 |
| 구현 피크 구간 | 15% | 기능 구현, 연동, 데이터 처리 | 변경이 잦은 영역의 누적 억제 |
| 안정화 구간 | 25% | 통합시험, 성능 조정, 배포 준비 | 반복 장애와 운영 우회 절차 제거 |
| 운영 전환 후 | 20% | 운영 코드, 모델, 파이프라인, 배포 구성 | 변경 리드타임과 운영 부담 축소 |

단계가 한 주기 안에서 겹치면 주기 종료 시점의 주요 작업이 속한 단계를 적용한다.  
두 단계의 작업량이 같으면 더 높은 비율을 사용한다.  
선정 대상은 PSY-06#s6의 판정 결과에서 우선순위가 높은 항목부터 채운다.  
고통의 80%를 유발하는 20%의 항목에 먼저 집중하며, 등록된 부채 전체의 일괄 정리를 목표로 삼지 않는다.

1. 주기 계획 시 기술 담당자는 배정 공수를 시간 또는 인일로 환산한다.
2. 각 상환 작업에 부채 ID와 완료 조건을 연결한다.
3. 주기 종료 시 계획 공수, 실제 공수 및 미집행 사유를 기록한다.
4. 미사용 공수는 다음 주기의 할당량에 더하지 않는다.
5. 같은 사업에서 2회 연속 기준 비율을 지키지 못하면 수행 책임자에게 보고한다.

미집행 사유는 고객 승인 지연, 선행 작업 미완료, 운영 장애 대응, 인력 변동 또는 납기 우선 결정 중 하나로 분류한다.  
단순히 “시간 부족”이라고 기록할 수 없으며, 공수를 대체 사용한 작업 ID를 함께 남긴다.  
2회 연속 보고에는 미집행 누계, 영향을 받은 부채 ID, 다음 주기 복구안 및 일정 영향 전망을 포함한다.

고정가 사업은 견적 공수 안에 단계별 배정 시간을 선반영한다.  
계약 후 남는 시간으로 처리하거나 프로젝트 예비비와 중복 계상하지 않는다.  
T&M 사업도 예상 투입량에 해당 시간을 포함하되, 고객 청구 가능 여부는 계약 범위와 승인된 작업 항목에 따라 구분한다.  
산정 시 개발 외 검토·시험·문서 공수는 PRP-03#s5의 비개발 공수 가산과 연결한다.  
계약상 청구할 수 없는 시간이더라도 내부 배정 기준 자체가 소멸하지는 않는다.

신규 기능에 할당 시간을 전용하라는 요청은 요청자, 대상 기능, 필요한 공수 및 미상환 부채 ID를 기록한 뒤 판단한다.  
기술 담당자는 구두 요청만으로 계획을 변경하지 않는다.  
단일 주기의 전용은 수행 책임자가 승인하며, 그 결과가 15% 미만이면 납기 우선 결정 기록을 추가한다.  
반복 전용이나 2개 팀 이상에 영향을 주는 변경은 PSY-06#s12를 따른다.

할당이 0인 주기가 지속되면 기능 변경 리드타임, 변경 실패율, 장애 복구시간 및 수동 우회 횟수를 함께 관찰한다.  
직전 4개 주기 대비 이 지표 중 둘 이상이 악화되면 등록부 상위 항목과의 연관성을 분석한다.  
원인이 확인되면 다음 계획 회의에서 신규 기능 공수와 분리된 상환 작업으로 편성한다.

## 납기 우선 결정 시 필수 기록
<!--meta: sec=s8; dept=AIAX|BE|DATA|CNS; level=시니어; ct_band=상; related=s3|s4-->
납기를 맞추기 위해 더 제약이 큰 해법을 선택할 때는 소유자, 트레이드오프, 재검토일 및 안전장치를 반드시 기록한다.  
네 항목이 모두 구체적으로 명시된 지름길은 사업 상황에 따른 합리적 선택으로 판정할 수 있다.  
한 항목이라도 비어 있으면 구현 착수나 배포 승인의 근거로 사용할 수 없다.

| 필수 항목 | 기재 기준 | 허용하지 않는 기재 |
|---|---|---|
| 소유자 | 재검토와 후속 조치를 책임지는 개인 1명 | 개발팀, 담당자 미정 |
| 트레이드오프 | 확보한 일정·범위와 포기한 품질·유연성·자동화 수준 | 빠르게 처리, 일단 적용 |
| 재검토일 | 연·월·일로 특정한 날짜 | 추후, 안정화 후, 여유 있을 때 |
| 안전장치 | 감시 지표, 수동 점검, 사용 범위 제한 중 적용 항목과 실행 주기 | 주의해서 운영, 문제 시 대응 |

소유자는 부채를 직접 수정하는 사람과 달라도 되지만, 상태 확인과 의사결정 요청을 다른 사람에게 넘길 수 없다.  
담당자가 변경되면 인수자가 명시적으로 수락한 날짜를 남긴다.  
수락 전까지 기존 소유자의 책임이 유지된다.

트레이드오프에는 다음 내용을 한 문장씩 분리해 적는다.

1. 얻는 것: 단축되는 일정, 유지되는 납품 범위 또는 회피하는 즉시 비용을 적는다.
2. 포기하는 것: 추가 검증, 구조적 유연성, 자동화 또는 변경 용이성 중 실제 손실을 적는다.
3. 영향 경계: 적용되는 모듈, 데이터, 사용자군, 환경 및 종료 조건을 적는다.
4. 대안 배제 이유: 검토한 정상 해법을 현재 선택하지 않은 이유를 적는다.

재검토일은 해당 선택의 전제가 끝나는 날보다 늦게 잡을 수 없다.  
출시일 때문에 선택했다면 출시 후 최초 계획 회의 이전 날짜로 지정한다.  
외부 승인 일정이 불확실하면 확정일 대신 최대 대기기한을 날짜로 적는다.

안전장치는 상환을 대신하지 않으며 재검토일까지 위험 노출을 제한하는 통제이다.  
감시 지표에는 측정값, 경보 기준 및 확인자를 기재한다.  
수동 점검에는 점검 항목, 수행 주기와 증적 위치를 기재한다.  
사용 범위 제한에는 허용 고객·환경·데이터 범위와 차단 방법을 기재한다.

기록은 부채 등록부의 해당 행과 결정 로그에 동시에 남긴다.  
등록부에는 현재 상태와 추적 정보를 두고, 결정 로그에는 당시 맥락과 승인 흔적을 둔다.  
결정 로그 작성 방식은 PSY-02#s8을 따른다.  
두 기록은 동일한 부채 ID로 연결하며 서로 다른 재검토일을 사용할 수 없다.

재검토일이 지나면 해당 항목의 상태를 자동으로 `재검토 기한 초과`로 전환한다.  
소유자는 다음 영업일 안에 상환, 기한 재설정 또는 현상 유지 중 하나를 제안한다.  
기한 재설정에는 새로운 사업 근거, 안전장치의 유효성 확인 및 승인자를 추가한다.  
처리 전에는 해당 영역의 신규 구조 변경 승인을 보류한다.

고객 산출물의 기능, 성능, 시험 결과 또는 운영 절차에 영향을 주는 결정은 수행 책임자의 승인을 받아야 한다.  
고객 합의나 계약 변경이 필요한지는 PRP-04#s9를 참조한다.  
승인 없는 납기 우선 선택은 완료된 작업으로 인정하지 않으며 정상 해법으로 복구한다.

## 즉시 상환해야 하는 금지선
<!--meta: sec=s9; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s6-->
금지선은 일정, 비용 또는 고객 요청을 이유로 잔존시킬 수 없는 기술 상태이다.  
발견 즉시 관련 작업과 배포를 중단하고 제거 또는 통제된 방식으로 복구한다.  
금지선 항목에는 일반 부채의 우선순위 점수를 적용하지 않는다.

| 금지선 항목 | 금지 이유 | 발견 시 즉시 처리 |
|---|---|---|
| 인증·권한 우회 | 승인되지 않은 주체가 기능이나 데이터에 접근할 수 있다 | 우회 경로 차단 후 권한 검증을 재수행한다 |
| 비밀값의 코드·설정 하드코딩 | 저장소·산출물·배포본을 통해 비밀값이 확산될 수 있다 | 값을 폐기·교체하고 승인된 비밀 관리 경로로 이전한다 |
| 개인정보의 평문 보관 또는 로그 기록 | 불필요한 노출과 복제 범위를 통제하기 어렵다 | 기록을 중단하고 잔존 위치와 접근 흔적을 확인한다 |
| 되돌릴 수 없는 데이터 변환의 무검증 실행 | 오류 발생 시 원상 복구가 불가능할 수 있다 | 실행을 차단하고 백업·검증·복구 절차를 확보한다 |
| 고객 데이터의 허용 범위 밖 전송 | 합의되지 않은 위치·시스템·수신자에게 데이터가 이동한다 | 전송을 차단하고 이동 범위와 잔존 사본을 확인한다 |
| 감사 대상 행위의 로그 미기록 | 변경 주체와 시점을 사후 확인할 수 없다 | 해당 행위를 중단하고 감사 기록 경로를 복구한다 |
| 테스트 없는 과금·정산 로직 | 금액 산출 오류가 거래 결과에 직접 반영될 수 있다 | 단위·경계·회귀시험을 통과하기 전 반영하지 않는다 |
| 운영 환경의 수동 직접 변경 | 변경 재현, 검토, 추적 및 복구가 보장되지 않는다 | 변경을 멈추고 승인된 배포 경로로 다시 수행한다 |

개인정보 해당 여부, 전송 허용 범위 또는 보존 의무는 계약과 처리 맥락에 따라 사안별 확인이 필요하다.  
확인 중이라는 이유로 의심되는 처리를 계속할 수는 없다.  
범위가 확정될 때까지 해당 데이터 흐름을 중지하거나 비식별 시험 데이터로 대체한다.

금지선 여부는 다음 순서로 판정한다.

1. 현재 상태가 표의 금지 행위에 직접 해당하는지 확인한다.
2. 배포 전이라도 실행 가능한 코드·설정·절차로 남아 있는지 확인한다.
3. 단순 불편이나 추가 공수가 아니라 접근, 데이터, 금액, 추적성 또는 복구 가능성을 훼손하는지 확인한다.
4. 하나라도 해당하면 일반 부채 등록 후 대기시키지 않고 즉시 조치한다.

일반 부채는 제한된 기간 동안 안전장치 아래 유지할 수 있고 상환 시점을 비교할 수 있는 상태이다.  
금지선은 안전장치만으로 잔존을 승인할 수 없으며 제거 완료가 재개 조건이다.  
판정이 불분명하면 더 낮은 위험 등급으로 임의 분류하지 않고 배포 보류 상태를 유지한다.

발견자는 직급과 관계없이 관련 빌드, 데이터 작업 또는 배포의 보류를 선언할 수 있다.  
배포 담당자와 해당 업무를 수행하는 AIAX·BE·DATA의 과장 이상은 중단 권한을 가진다.  
수행 책임자는 영향 범위를 확인하고 고객 일정 변경 필요 여부를 즉시 판단한다.  
중단을 해제하려면 수정 증적, 시험 결과, 잔존 영향 확인 및 해당 팀 과장 이상의 승인이 필요하다.

금지선에는 예외를 두지 않는다.  
고객이 일정 유지를 요청하더라도 위험 상태를 그대로 배포하는 대신 범위 축소, 배포 순서 변경 또는 일정 조정을 선택한다.  
일정·범위 변경의 승인과 에스컬레이션은 PSY-06#s12를 따른다.

## 고객 계약·검수와의 관계
<!--meta: sec=s10; dept=CNS|BE|AIAX; level=시니어; ct_band=상; related=s8-->
기술 부채는 내부 기술 상태를 분류하는 용어이며 계약상 의무를 변경하거나 검수 기준을 낮추는 근거가 아니다. 계약서, 과업범위, 산출물 명세 및 합의된 수용 기준을 충족하는지는 부채 등록 여부와 별도로 판정한다.

| 구분 | 판정 기준 | 검수 처리 | 내부 조치 |
|---|---|---|---|
| 검수 비영향 부채 | 요구 기능·성능·보안·산출물 형식과 수용 기준을 모두 충족한다 | 해당 부채만으로 검수 불합격 사유로 보지 않는다 | 등록부에 남기고 상환 일정을 배정한다 |
| 검수 영향 부채 | 합의된 기능, 성능 수치, 연동 조건 또는 필수 시험 결과를 충족하지 못한다 | 미충족 요건으로 처리한다 | 검수 전 보완하거나 고객과 범위·일정을 다시 합의한다 |
| 판정 불명확 | 계약 문구와 시험 결과의 대응 관계가 불분명하다 | 수행 책임자가 임의로 합격 처리하지 않는다 | CNS가 계약 문서와 승인 이력을 대조한다 |
| 범위 외 개선 | 수용 기준에는 없으나 장기 유지관리 효율을 높이는 작업이다 | 검수 항목에 임의로 추가하지 않는다 | 차기 유지관리 또는 별도 변경 협의 대상으로 분리한다 |

산출물 명세에 기재된 요건을 “기술 부채로 등록한다”는 이유로 이행 이후로 미룰 수 없다. 내부 등록부는 고객과 합의한 의무의 대체 문서가 아니며, 검수 및 하자보수 경계는 각각 `PRP-04#s4 참조`, `PRP-04#s5 참조`에 따른다.

검수 전에는 다음 순서로 계약 영향을 확인한다.

1. BE 또는 AIAX 담당자가 부채가 접촉하는 요구사항 ID와 시험 항목을 표시한다.
2. CNS가 계약서, 과업범위 및 승인된 변경 내역에서 해당 요건의 구속 범위를 확인한다.
3. 수행 책임자가 검수 비영향, 검수 영향 또는 판정 불명확 중 하나로 결론을 기록한다.
4. 검수 영향으로 판정되면 고객 제출본에서 완료 상태로 표시하지 않는다.
5. 계약 해석이나 비용 책임은 사안별 확인이 필요하며, 확인 전에는 고객에게 확정 표현을 사용하지 않는다.

하자보수 기간에 부채와 관련된 결함이 발생하면 원인과 계약 경계를 먼저 분리한다.

| 발생 유형 | 비용 검토 기준 | 처리 원칙 |
|---|---|---|
| 합의된 요건의 미충족이 뒤늦게 확인됨 | 검수 당시 충족 여부와 하자보수 조항 | 결함 복구 공수와 내부 구조 개선 공수를 구분한다 |
| 검수 후 고객 요청으로 사용 조건이 변경됨 | 변경 요청·승인 기록과 기존 전제 | 기존 하자로 단정하지 않고 별도 협의한다 |
| 내부 지름길이 동일 결함을 반복 유발함 | 최초 결정 기록, 재현 결과, 영향 범위 | 고객 복구를 우선하고 재발 방지 작업을 별도 산정한다 |
| 계약 범위를 넘는 예방적 리팩터링 | 수용 기준 및 유지관리 범위 | 무상 하자보수에 자동 포함하지 않는다 |

운영 인수인계에는 고객의 운영 판단에 필요한 부채만 알린다. 대상은 장애 대응 절차, 확장 한계, 특정 설정의 제약, 예정된 교체 또는 운영자가 피해야 할 조작처럼 사용·운영에 직접 영향을 주는 항목이다.

- 내부 클래스명, 개인별 작업 메모, 미확정 대안 비교는 고객 문서에서 제외한다.
- 표현은 “부실”, “임시방편” 같은 평가어 대신 현재 제약, 발생 조건, 운영 조치, 해소 예정 여부를 적는다.
- 보안상 세부 공개가 위험한 경우에는 노출 경로나 비밀값을 적지 않고 필요한 통제와 문의 경로만 제공한다.
- 검수 비영향 판정은 고객 고지 불필요 판정과 동일하지 않다.

부채로 유지관리 공수가 증가하면 담당자는 월별 추가 인시, 반복 발생 작업 및 적용 모듈을 근거로 CNS에 전달한다. CNS는 현 계약 범위 안의 작업인지 확인하고, 범위를 넘는 경우 유지관리 조건 조정이나 별도 변경 협의 안건으로 제출한다. 고객 합의 전까지 예상 추가 공수를 확정 매출이나 승인된 작업으로 간주하지 않는다.

## 제안·견적 단계에서의 부채 예방
<!--meta: sec=s11; dept=CNS|SALES|AIAX|BE; level=시니어; ct_band=상; related=s7-->
제안·견적 단계의 과소 산정은 수행 중 검증 생략, 임시 구현 고착 및 반복 주기 축소로 이어질 수 있다. 이 섹션은 산정 공식을 정하지 않고, 산정 결과에 필요한 작업과 제약이 반영되었는지를 점검한다. 단가, 난이도 계수, 버퍼 및 가격 바닥선의 계산은 `PRP-03 참조`에 따른다.

| 점검 항목 | 확인 질문 | 1차 책임자 | 확인 근거 |
|---|---|---|---|
| 비개발 공수 | 요구사항 정제, 설계 검토, 회의, 문서화, 배포 준비가 포함되었는가 | CNS | 작업분해표, 제안 일정 |
| 부채 축소 시간 | 반복 주기의 부채 축소 배정이 가용 공수에서 제거되지 않았는가 | AIAX·BE 수행 검토자 | 인력 투입표, 반복 주기 계획 |
| 난이도 반영 | 기존 연동, 데이터 품질, 모델 검증, 배포 환경 제약이 계수 근거에 적혔는가 | 해당 기술팀 검토자 | 사전 질의, 환경 정보 |
| 버퍼 용도 | 위험 대응분이 가격 할인 재원으로 중복 사용되는 구조가 아닌가 | SALES·CNS | 견적 원가표, 할인안 |
| 검증 일정 | 단위·통합·성능·보안·사용자 수용 시험 시간이 일정에 존재하는가 | 수행 책임자 예정자 | 마일스톤, 시험 계획 초안 |
| 고객 제공 지연 | 데이터, 계정, 장비, 승인 및 연동 정보의 지연 조건이 반영되었는가 | CNS | 전제·의존성 목록 |

수주 전 점검은 제안 제출 또는 최종 견적 승인 중 먼저 도래하는 시점 이전에 완료한다. SALES는 최신 일정안과 범위를 수행 예정 부서에 전달하고, AIAX·BE 중 실제 영향 부서가 기술 검토 의견을 남긴다. DATA 작업이 포함된 경우 DATA도 데이터 확보와 검증 가능성을 확인한다.

수행 부서는 다음 사유가 있으면 일정 실현 가능성에 이견을 제기한다.

- 필수 활동의 공수가 0으로 잡혀 있거나 다른 작업과 동일 시간대에 중복 배정되어 있다.
- 고객 제공물이 지연되어도 종료일이 변하지 않는 전제로 작성되어 있다.
- 시험 실패 후 수정·재시험 구간이 없다.
- 기술 검토 전에 할인으로 인력 또는 기간이 축소되었다.
- 운영 전환에 필요한 문서와 인수인계 작업이 작업분해표에 없다.

이견 제출과 회의 상정 경로는 `PSY-02#s5 참조`에 따른다. 구두 반대만으로 검토를 완료한 것으로 보지 않으며, 수행 부서는 검토 대상 버전과 근거를 식별할 수 있게 남긴다.

일정이 불가능하다고 판단한 검토자는 다음 항목을 기록한다.

1. 불가능 판정 대상인 제안서·견적서·일정표의 버전
2. 충돌하는 작업, 필요한 선행조건 및 부족한 인시
3. 생략될 가능성이 있는 검증 또는 산출물
4. 예상되는 품질 제약과 영향을 받는 계약 요건
5. 실행 가능한 대안 일정, 범위 축소안 또는 인력 보강안
6. 의견 제출일, 작성자 및 최종 결정 요청 기한

SALES와 CNS는 일정 단축안을 고객에게 제시하기 전에 수행 부서의 반대 의견이 해소되었는지 확인한다. 반대 의견을 수용하지 않는 결정이 내려지면 결정권자, 채택 사유 및 선택하지 않은 대안을 제안 기록에 연결한다.

부채 축소 시간은 미사용 예비 공수가 아니다. 가격 협상 과정에서 해당 시간을 줄이려면 제거 대상, 반복 주기 영향 및 대체 통제를 다시 검토한다. 단순히 “수행 중 효율화”한다는 문구는 조정 근거로 인정하지 않는다.

## 의사결정 권한과 에스컬레이션
<!--meta: sec=s12; dept=AIAX|BE|DATA|CNS; level=시니어; ct_band=상; related=s8|s9-->
기술 부채 결정권은 변경이 미치는 범위에 따라 배정한다. 직급이 높다는 이유만으로 계약·검수·배포 권한까지 자동 확대되지 않으며, 아래 권한자가 결정 기록의 승인 주체가 된다.

| 결정 유형 | 결정 권한 | 필수 협의 | 권한 경계 |
|---|---|---|---|
| 모듈 내부 구현 선택 | 해당 담당자 | 코드 검토자 | 외부 인터페이스와 산출물 기준이 변하지 않는 범위 |
| 산출물 품질 기준 완화 | 수행 책임자 | 영향받는 AIAX·BE·DATA 리드 | 계약상 수용 기준은 단독 완화할 수 없다 |
| 검수 범위에 영향 | 수행 책임자와 CNS | 해당 기술팀 | 양측 확인 전 고객 확정안으로 제시할 수 없다 |
| 일정 변경 필요 | 지점 책임자 | 수행 책임자, CNS | 고객 통지와 계약 조정은 별도 승인 절차를 따른다 |
| 금지선 관련 | 최초 발견자가 배포 중단 | 수행 책임자와 지점 책임자에게 즉시 보고 | 일정·비용을 근거로 배포를 재개할 수 없다 |

담당자는 모듈 내부 결정이라도 공용 API, 데이터 스키마, 모델 입출력, 배포 구성 또는 다른 팀의 작업 방식에 영향을 주면 상위 유형으로 올린다. 영향 범위를 판단하기 어려운 경우에는 단독 결정을 보류하고 수행 책임자에게 판정을 요청한다.

권한을 넘는 결정을 혼자 내린 사실이 확인되면 다음과 같이 처리한다.

1. 발견자는 추가 구현, 병합 또는 배포를 멈추고 현재 상태를 보존한다.
2. 결정자는 선택 내용, 적용 범위, 이미 발생한 영향 및 되돌리기 가능 여부를 작성한다.
3. 원래 권한자가 유지, 수정 또는 원복 중 하나를 판정한다.
4. 고객 전달 내용에 영향이 있으면 CNS가 기존 안내와의 불일치를 확인한다.
5. 승인 없는 결정으로 생긴 부채는 사후 승인만으로 종결하지 않고 등록부와 결정 기록을 연결한다.

에스컬레이션 경로와 응답 시한은 `PSY-02#s11 참조`에 따른다. 이 문서에서는 다음 상황을 추가 트리거로 사용한다.

| 추가 트리거 | 최초 보고자 | 첨부 자료 | 즉시 조치 |
|---|---|---|---|
| 부채 축소 할당 비율이 2개 반복 주기 연속 기준 미달 | 수행 책임자 | 두 주기의 가용 공수와 실제 사용 내역 | 다음 계획 확정 전 원인과 회복안을 상정한다 |
| 금지선 위반 발견 | 발견자 | 재현 조건, 영향 범위, 차단 상태 | 관련 배포와 병합을 중단한다 |
| 재검토일 초과 항목 누적 | 등록부 소유자 | 초과 목록, 소유자, 지연 사유 | 미지정 소유자와 미확정 일정을 우선 보정한다 |
| 부채 결정이 검수 또는 고객 일정에 새로 영향 | CNS 또는 수행 책임자 | 관련 요건, 일정 차이, 선택지 | 고객 확정 안내를 보류한다 |

재검토일 초과 누적은 동일 사업에서 기한이 지난 항목이 3건 이상이거나, 단일 항목이 별도 승인 없이 10영업일을 넘긴 경우로 본다. 날짜만 뒤로 옮긴 항목은 해소로 계산하지 않는다.

결정 기한까지 승인이 나오지 않으면 기본값은 안전한 선택이다. 배포 전이면 변경을 포함하지 않고, 운영 중이면 영향 확대를 차단하며, 검수 관련이면 충족 여부를 확정하지 않는다. 담당자는 적용한 기본값, 중단된 작업, 재개에 필요한 승인 및 판단 시각을 기록한다.

금지선이 아닌 사안에서 안전한 선택 때문에 일정 변경이 예상되면 담당자가 임의로 품질 기준을 낮추지 않는다. 수행 책임자는 일정 영향안을 지점 책임자에게 올리고, CNS는 고객 커뮤니케이션 필요 여부를 판단한다.

## 부채 가시화 보고 양식
<!--meta: sec=s13; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=s4|s14-->
부채 가시화 보고서는 등록부의 상태, 유입·상환 흐름 및 일정 압력을 한 장에서 확인하는 월간 자료이다. 각 사업의 AIAX·BE·DATA 담당자는 월말 기준 데이터를 마감하고 다음 달 3영업일 이내에 수행 책임자에게 제출한다. 여러 부서가 같은 등록부를 사용하는 경우 수행 책임자가 중복을 제거한 통합본을 작성한다.

| 보고 블록 | 표시 항목 | 작성 기준 |
|---|---|---|
| 보유 현황 | 월말 등록 건수, 4분면별 건수·비중 | 종료되지 않은 항목만 집계한다 |
| 이자 상위 | 추정 이자가 큰 상위 5건 | 부채 ID, 위치, 월간 이자, 소유자를 표시한다 |
| 기한 초과 | 재검토일 초과 건수 | 기준일 이전에 재검토되지 않은 항목을 센다 |
| 공수 사용 | 주기별 할당 비율 계획·실적 | 실제 부채 축소에 사용한 공수를 기준으로 한다 |
| 유입과 상환 | 신규 등록 건수, 상환 건수 | 같은 월의 두 수치를 나란히 표시한다 |
| 금지선 | 발견 건수, 처리 상태 | 발견 0건도 명시하며 미종결 건은 별도 강조한다 |
| 집중 영역 | 같은 위치의 반복 등록 건수 | 저장소·모듈·파이프라인 단위로 묶는다 |

보고서 머리에는 사업명, 기준월, 작성자, 데이터 기준 시각 및 등록부 링크를 적는다. 본문에는 다음 순서로 배치한다.

1. 첫째 줄에 보유 현황과 전월 대비 증감을 표시한다.
2. 둘째 블록에 이자 상위 항목과 재검토일 초과 항목을 배치한다.
3. 셋째 블록에 계획 대비 공수 사용량과 신규·상환 흐름을 표시한다.
4. 마지막 블록에 금지선 발견 현황과 다음 달 조치 필요 사항을 적는다.
5. 수치 산식과 해석 기준은 `PSY-06#s14 참조`로 연결하고 본문에서 재정의하지 않는다.

월간 보고 대상은 해당 사업의 수행 책임자와 영향받는 AIAX·BE·DATA 책임자이다. 계약 일정이나 고객 인수인계에 영향을 줄 수 있는 항목이 있으면 CNS 담당자를 수신 대상에 추가한다.

다음 용도로는 보고서를 사용하지 않는다.

- 개인별 등록 건수, 상환 건수 또는 보유 건수를 비교하지 않는다.
- 등록 건수가 적다는 이유만으로 팀이나 사업의 품질이 높다고 판정하지 않는다.
- 상환 건수만으로 생산성·인사평가·사업 성과를 산정하지 않는다.
- 크기가 다른 항목을 단순 건수로 합산해 부서 순위를 만들지 않는다.

## 측정 지표
<!--meta: sec=s14; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=s13-->
측정 지표는 부채의 양만 세지 않고 유입, 상환, 기한 준수, 반복 발생 및 운영 영향을 함께 해석하기 위해 사용한다. 산출 기준일은 월말이며 분기 해석에는 같은 방식으로 계산한 최근 3개월 값을 사용한다.

| 지표 | 목표 | 측정 방법 | 해석 주의 |
|---|---|---|---|
| 신규 등록 대비 상환 비율 | 유입보다 상환이 지속적으로 뒤처지는 상태를 식별한다 | 해당 기간 상환 건수 ÷ 신규 등록 건수 × 100 | 신규 등록이 0건이면 비율을 계산하지 않고 상환 건수를 병기한다 |
| 재검토일 준수율 | 기한 도래 항목을 누락 없이 판단한다 | 기한 내 재검토 완료 건수 ÷ 기간 내 재검토 대상 건수 × 100 | 날짜만 변경하고 판단 근거가 없으면 완료로 세지 않는다 |
| 의도적 부채 비중 | 계획된 트레이드오프의 규모를 확인한다 | 의도적 분류 건수 ÷ 전체 활성 건수 × 100 | 높은 비중이 반드시 나쁜 것은 아니며 승인·후속 계획의 충실도를 함께 본다 |
| 비의도적 부채 비중 | 예측하지 못한 구조적 제약의 변화를 추적한다 | 비의도적 분류 건수 ÷ 전체 활성 건수 × 100 | 점검 강화 직후의 증가는 발견 능력 향상일 수 있다 |

| 부채 기인 장애 건수 | 운영 결과로 나타난 영향을 확인한다 | 원인 분석에서 등록 부채가 직접·기여 원인으로 확인된 장애 수를 센다 | 추정만 있는 장애는 별도 후보로 두고 확정 건수에 넣지 않는다 |
| 할당 비율 실적 | 계획한 축소 공수가 실제 집행되었는지 확인한다 | 부채 축소 실공수 ÷ 가용 기술 공수 × 100 | 기준 범위는 15~25%이며 신규 기능 공수를 섞지 않는다 |
| 평균 상환 소요 기간 | 발견부터 종료까지의 체류 시간을 확인한다 | 상환 항목별 등록일~종료일 일수의 합 ÷ 상환 건수 | 미종결 항목이 빠지므로 최장 체류 항목과 함께 본다 |

지표는 단일 목표치로 인사평가하거나 사업 간 순위를 정하는 데 사용하지 않는다. 특히 등록 건수를 낮추는 목표를 부여하면 발견된 문제를 기록하지 않거나 여러 항목을 한 건으로 합치는 왜곡이 생긴다.

왜곡 방지를 위해 다음 규칙을 적용한다.

- 등록량 증감에는 점검 범위, 출시 규모 및 등록부 정비 여부를 주석으로 남긴다.
- 상환 비율은 이자 상위 항목의 감소 여부와 함께 확인한다.
- 평균값만 보고하지 않고 기한 초과 건수와 최장 체류 기간을 병기한다.
- 분류 변경으로 비중이 달라졌으면 변경 전후 건수와 사유를 남긴다.
- 지표 산출을 위해 원본 등록 행을 분할·병합할 때 변경 이력을 보존한다.

분기 해석 회의는 다음 순서로 진행한다.

1. 금지선 발견 및 부채 기인 장애부터 확인한다.
2. 재검토일 준수율과 초과 항목의 체류 기간을 본다.
3. 신규 등록 대비 상환 흐름과 반복 등록 위치를 비교한다.
4. 의도적·비의도적 분포 변화의 원인을 검토한다.
5. 할당 비율 실적과 이자 상위 항목 감소 여부를 대조한다.
6. 다음 분기 역량·일정 조정 사항을 확정해 `PSY-06#s13 참조`의 보고 자료에 반영한다.

## 리팩터링과 재작성 판단 기준
<!--meta: sec=s16; dept=AIAX|BE; level=시니어; ct_band=상; related=s6-->
상환 대상으로 확정된 부채는 기존 구조를 단계적으로 고치는 리팩터링과 기존 구현을 대체하는 재작성 중 하나로 처리한다. 상환 여부와 순서는 `PSY-06#s6 참조`에 따르며, 코드 선호나 기존 투입 공수는 방식 선택의 근거로 사용하지 않는다.

다섯 조건을 모두 충족한 경우에만 재작성을 후보안으로 올린다. 하나라도 충족하지 못하면 점진 개선을 선택하며, “새로 만드는 편이 빠를 것 같다”는 진술만으로 예외를 허용하지 않는다.

2. 재작성 계획은 기존 구현의 제거가 아니라 동작 동등성 확인과 전환 완료를 종료 조건으로 삼는다.
3. 양쪽 방안의 예상 공수에는 기능 구현 외에 회귀시험, 전환, 운영 감시 및 실패 복구를 포함한다.
4. 비교 결과가 비슷하면 되돌리기 쉽고 변경 범위가 작은 점진 개선을 선택한다.
