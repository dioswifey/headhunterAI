# CRM 입력 규칙과 데이터 위생 점검
<!--meta: doc=FCT-05; doc_type=revops; tier=1; topic=SALES; disclosure=internal; status=active-->

## 문서의 목적과 책임 구분
<!--meta: sec=s1; dept=SALES; level=주니어|시니어; ct_band=하; related=s2-->
이 문서는 서울·경기·인천 3개 지점의 SALES가 구축 프로젝트와 운영·유지보수 계약 관련 CRM 레코드를 동일한 기준으로 생성·관리하도록 데이터 위생의 책임과 통제 원칙을 정합니다. 기회, 계정, 담당자, 활동 데이터가 영업 판단과 후속 업무에 사용할 수 있는 상태인지 관리하는 내부 기준입니다.
데이터 위생은 단순한 오탈자 수정이 아니라 `규칙 + 습관 + 소유권 + 점검 + 시스템 통제`의 집합으로 정의합니다. 다섯 요소 중 하나라도 빠지면 데이터 품질이 담당자의 주의력에만 의존하므로 지속 가능한 위생 체계로 인정하지 않습니다.
**데이터 위생의 구성 요소**
| 요소 | 적용 기준 | 책임 주체 |
| --- | --- | --- |
| 규칙 | 필드 정의, 허용값, 명명법, 중복 판정 조건을 문서화합니다. | RevOps 담당 |
| 습관 | 레코드 소유자가 정해진 기한에 입력하고 정기적으로 사실 여부를 확인합니다. | 기회·계정 소유자 |
| 소유권 | 각 레코드와 관리 규칙에 최종 책임자를 1명씩 지정합니다. | 영업 관리자·RevOps 담당 |
| 점검 | 주간·월간·분기 단위로 완전성, 최신성, 중복, 정체 여부를 검사합니다. | 영업 관리자·RevOps 담당 |
| 시스템 통제 | 필수값, 검증식, 권한, 자동화, 변경 이력으로 오류 입력을 제한합니다. | RevOps 담당 |
RevOps 담당은 SALES 내 CRM 운영 책임자로서 입력 표준, 중복 매칭 규칙, 접근 권한, 자동화, 데이터 감사와 구조적 수정을 소유합니다. 구조적 수정에는 필드 신설·폐기, 선택값 변경, 검증식 변경, 일괄 보정, 중복 병합 규칙 변경이 포함됩니다.
영업 관리자는 파이프라인 리뷰에서 영업 판단의 근거, 종료예정일의 현실성, 장기간 진전이 없는 정체 딜을 확인합니다. 검토 과정에서 발견된 개별 오류는 레코드 소유자에게 수정 기한을 지정하고, 반복되거나 시스템에서 예방할 수 있는 오류는 RevOps 담당에게 전달합니다.
**역할별 책임 경계**
| 역할 | 직접 책임 | 책임에 포함하지 않는 사항 |
| --- | --- | --- |
| RevOps 담당 | 표준, 중복 규칙, 권한, 자동화, 감사, 구조적 수정 | 고객 사실의 최초 확인 |
| 영업 관리자 | 근거·종료예정일·정체 딜 검토, 수정 지시 | 필드 구조와 자동화의 임의 변경 |
| 기회 소유자 | 기회·활동·담당자 정보의 정확성 및 최신성 | 다른 소유자의 레코드 대리 확정 |
| 계정 소유자 | 법인 기본정보와 대표 연락관계 유지 | 중복 계정의 직접 병합 |
| CNS·AIAX·BE·DATA 협업자 | 자신이 확인한 기술·과업 사실의 오류 제보 | 영업 필드의 무단 수정 |
| 지점 SALES 부장 | 지점 내 이행 확인과 미해결 위반의 에스컬레이션 | 지점별 독자 규칙 제정 |
모든 레코드는 개인이 아닌 지정된 소유자에게 귀속하며, 공동 영업도 최종 소유자는 1명만 둡니다. 협업자가 입력을 지원했더라도 정확성 확인과 기한 준수 책임은 레코드 소유자에게 남습니다.
위생 통제는 `규칙 적용 → 정기 점검 → 오류 수정 → 규칙이 놓친 오류 재점검 → 구조 개선` 순환으로 운영합니다. 권한 확대, 대량 변경, 병합 등 위험 변경에는 승인 단계를 적용하며 세부 권한은 s16을 따릅니다.
파이프라인 단계와 전환 근거는 FCT-01, 포캐스트 범주와 확률은 FCT-02, 리뷰 진행 방식은 FCT-03을 참조합니다.

## 기회 레코드 필수 필드 정의
<!--meta: sec=s2; dept=SALES; level=주니어; ct_band=중; related=s1|s3-->
기회 레코드는 고객의 구매 가능성과 예상 계약을 식별하는 기본 단위입니다. 필수 필드가 누락된 레코드는 보고·포캐스트·협업에 사용할 수 없으므로 임시 메모나 개인 일정으로 대체하지 않습니다.
필드의 의미가 불명확할 때 임의의 값을 선택하지 않습니다. 레코드 소유자는 확인 전까지 허용된 미확인 코드를 사용하고, 허용 코드가 없는 필드는 영업 관리자 또는 RevOps 담당에게 확인합니다.
**기회 레코드 필수 필드**
| 필드명 | 의미 | 입력 주체 | 입력 시점 | 검증 방식 |
| --- | --- | --- | --- | --- |
| 기회 ID | 레코드를 식별하는 고유번호 | 시스템 | 생성 즉시 | 자동 생성·중복 불가 |
| 기회명 | 계정과 과업을 식별하는 명칭 | 기회 소유자 | 최초 생성 시 | `{계정명}-{과업명}-{연도}` 형식 |
| 연결 계정 | 계약 상대가 될 법인 계정 | 기회 소유자 | 최초 생성 시 | 활성 계정 ID 존재 여부 |
| 계약 형태 | 구축 또는 운영·유지보수 구분 | 기회 소유자 | 최초 생성 시 | 허용값 선택만 가능 |
| ★ 소유자 | 기회의 최종 관리 책임자 1명 | 영업 관리자 | 생성·이관 시 | 재직자 및 SALES 권한 확인 |
| ★ 상태 | 열림·보류·수주·실패 등 현재 상태 | 기회 소유자 | 생성·상태 변경 시 | 단계와 상태의 허용 조합 검사 |
| 파이프라인 단계 | 현재 영업 진행 단계 | 기회 소유자 | 생성·단계 변경 시 | FCT-01 전환 기준 연계 |
| 단계 근거 | 현재 단계 판정을 뒷받침하는 사실 | 기회 소유자 | 단계 진입 시 | 근거일·근거 유형 필수 |
| 종료예정일 | 수주 또는 실패가 확정될 예상일 | 기회 소유자 | 최초 등록·변경 시 | 과거 날짜 차단, 변경 사유 저장 |
| 예상 계약금액 | 현재 범위 기준 공급가액 | 기회 소유자 | 금액 추정 가능 시 | 0원·음수 차단, 통화 필수 |
| ★ 다음 액션 | 기회를 전진시키기 위한 후속 행동 | 기회 소유자 | 고객 접촉·리뷰 후 | 액션일·책임자 존재 여부 검사 |
| 주 담당자 | 고객 측 핵심 연락 담당자 | 기회 소유자 | 기회 생성 시 | 연결된 활성 담당자 ID 확인 |
| ★ 연락처 최근 검증 여부 | 담당자의 재직·연락 가능 상태 | 기회 소유자 | 확인 접촉 후 | 검증일 기준 30일 이내 자동 판정 |
| 귀속 지점 | 서울·경기·인천 중 관리 지점 | 영업 관리자 | 최초 생성 시 | 허용값 및 소유자 지점 대조 |
| 협업 부서 | CNS·AIAX·BE·DATA의 참여 범위 | 기회 소유자 | 협업 요청 시 | 부서 코드만 선택 가능 |
| 유입 경로 | 기회가 시작된 최초 경로 | 기회 소유자 | 최초 생성 시 | 표준 경로 코드 선택 |
`★` 표시는 모든 열린 기회가 매주 점검받아야 하는 핵심 4개 필드입니다. 소유자, 상태, 다음 액션, 연락처 최근 검증 여부 중 하나라도 비어 있거나 유효하지 않으면 해당 기회는 주간 위생 점검 미통과로 처리합니다.
연락처 최근 검증은 고객의 회신, 통화, 회의 참석 또는 고객 조직의 공식 확인으로 재직과 연락 가능 상태를 확인한 경우에만 인정합니다. 단순 발송, 자동 회신, 과거 명함 보유는 검증으로 인정하지 않습니다.
종료예정일을 변경할 때는 새 날짜만 덮어쓰지 않고 변경 사유 코드를 남깁니다. 영업 관리자는 고객 일정, 내부 승인, 제안·계약 진행 사실 등 날짜를 뒷받침하는 근거가 없는 변경을 반려합니다.
단계 정의, 기회 등록 조건, 금액 범위와 단계 전환 승인 기준은 FCT-01을 참조합니다. 다음 액션의 문장 형식과 완료 판정은 s5를 적용합니다.

## 고객·계정 레코드 입력 규칙
<!--meta: sec=s3; dept=SALES; level=주니어; ct_band=중; related=s2|s4-->
계정 레코드는 실제 계약·거래 관계의 기준이 되는 법인 단위로 생성합니다. 동일 법인의 지점, 공장, 연구소, 사업부를 별도 법인처럼 중복 생성하면 기회와 활동 이력이 분산되므로 조직 단위는 원칙적으로 상위 법인 계정 아래에 구분합니다.
계정 생성자는 검색 결과가 없다는 사실만으로 신규 계정을 확정하지 않습니다. 법인명, 사업자 식별정보, 영문명, 기존 거래명칭을 교차 검색하고 중복 가능성을 해소한 뒤 생성합니다.
**계정명 표기 규칙**
| 대상 | 입력 형식 | 판정 기준 |
| --- | --- | --- |
| 국내 법인 | 등기 또는 사업자등록 기준의 정식 법인명 | `주식회사` 등 법인 형태를 임의 생략하지 않음 |
| 법인 지점 | `{법인명} / {지점명}` | 본점과 사업자 단위가 같으면 하위 조직으로 연결 |
| 사업부·본부 | `{법인명} / {사업부명}` | 별도 법인이 아니면 독립 계정 생성 금지 |
| 공장·센터 | `{법인명} / {시설명}` | 소재지와 시설 유형을 하위 조직 필드에 기록 |
| 영문 법인명 | 공식 영문명을 영문명 필드에 입력 | 한글 계정명을 영문으로 대체하지 않음 |
| 약칭·브랜드명 | 별칭 필드에 입력 | 계정명 필드의 법인명을 약칭으로 변경하지 않음 |
법인 형태의 위치는 공식 표기를 그대로 유지합니다. 띄어쓰기와 특수문자도 공적 문서 기준을 적용하며, CRM 검색 편의를 위한 공백 제거명이나 약칭은 별칭 필드에 저장합니다.
지점 또는 사업부가 독립된 계약 당사자이고 별도 사업자 식별정보를 보유한 경우에만 별도 계정을 생성할 수 있습니다. 별도 생성 시 상위 법인 계정 ID를 반드시 연결합니다.
**산업 분류 코드**
| 코드 | 산업 분류 | 선택 기준 |
| --- | --- | --- |
| MFG | 제조 | 제품 생산·가공이 주된 사업인 법인 |
| DIST | 유통 | 도매·소매·상품 유통이 주된 사업인 법인 |
| FIN | 금융 | 금융·보험 서비스가 주된 사업인 법인 |
| ICT | 정보통신 | 소프트웨어·통신·정보서비스가 주된 사업인 법인 |
| LOGI | 물류 | 운송·보관·배송이 주된 사업인 법인 |
| PUB | 공공·비영리 | 공공기관 또는 비영리 조직 |
| OTH | 기타·미확인 | 상기 코드로 확정할 근거가 없는 경우 |
복수 산업을 영위하는 계정은 계약 상대 조직의 주된 사업을 기준으로 대표 코드 1개를 선택합니다. `OTH`를 선택한 경우 사유를 입력하고 5영업일 이내에 재확인합니다.
본사 소재지는 공식 주소의 시·도와 시·군·구를 각각 구조화된 필드에 입력합니다. 영업 담당 지점, 프로젝트 수행 장소 또는 고객 담당자의 근무지를 본사 소재지로 입력하지 않습니다.
**신규 계정 생성 전 중복 방지 절차**
1. 정식 법인명과 법인 형태를 포함해 전체 계정을 검색합니다.
2. 공백·괄호·법인 형태를 제거한 정규화 명칭으로 다시 검색합니다.
3. 영문명, 약칭, 브랜드명과 사업자 식별정보로 교차 검색합니다.
4. 명칭 유사도 90% 이상 또는 사업자 식별정보가 일치하면 신규 생성을 중단합니다.
5. 기존 계정의 사용 가능 여부를 계정 소유자에게 확인하고 해당 계정에 기회를 연결합니다.
6. 별도 계정이 필요하다고 판단되면 근거를 첨부해 RevOps 담당의 승인을 받습니다.
검색을 생략하고 만든 계정은 실제 중복 여부와 관계없이 절차 위반으로 기록합니다. 중복 후보의 병합과 전수 정리는 s10에 따라 RevOps 담당이 수행합니다.

## 활동 기록 규칙
<!--meta: sec=s4; dept=SALES; level=주니어; ct_band=중; related=s3|s5-->
CRM 활동은 고객과 헤드헌터랩 사이에서 실질적인 정보가 오간 양방향 접촉만을 의미합니다. 고객의 요구, 판단, 질문, 반론, 승인 또는 일정 합의가 확인되어야 하며 단순 발송이나 내부 작업은 고객 활동으로 계산하지 않습니다.
활동 기록은 회의록 원문을 그대로 붙이는 저장소가 아니라 기회의 진행 사실을 재구성할 수 있는 영업 기록입니다. 기록을 읽은 다른 담당자가 접촉 목적, 고객 발언, 당사 답변, 결정 사항을 구분할 수 있어야 합니다.
**활동으로 남기는 접촉**
| 활동 유형 | 인정 조건 | 기록 예시 범위 |
| --- | --- | --- |
| 대면·화상 회의 | 고객 참석자와 양방향 논의가 이루어짐 | 요구 확인, 제안 설명, 일정 협의 |
| 전화 통화 | 고객과 연결되어 실질 대화가 이루어짐 | 의사결정 절차, 예산·일정 확인 |
| 이메일 | 고객의 질문·답변·확인 회신이 존재함 | 자료 검토 의견, 조건 확인 |
| 업무 메신저 | 고객의 실질 회신이 존재함 | 일정 확정, 쟁점 답변 |
| 워크숍·데모 | 고객 피드백 또는 질의가 수집됨 | 시연 반응, 검토 조건 |
| 협상 접촉 | 계약·가격·범위에 관한 상호 의견 교환 | 조건 요청, 수정 합의 |
자동 발송 메일, 뉴스레터 수신, 읽음 표시, 부재중 전화, 고객 회신이 없는 발신 메일은 양방향 활동으로 남기지 않습니다. 접촉 시도 관리가 필요하면 CRM 업무 항목에 결과를 기록하되 고객 활동 건수에서는 제외합니다.
내부 회의, 제안서 편집, 개발 검토, 개인 메모, 일정 알림, 결재 요청도 고객 활동으로 등록하지 않습니다. 고객 접촉 없이 수행한 내부 업무는 해당 내부 업무 항목 또는 협업 시스템에 기록합니다.
**기록 시한과 분량**
| 기준 | 필수값 | 미준수 판정 |
| --- | --- | --- |
| 입력 기한 | 접촉 종료 후 1영업일 이내 | 다음 영업일 종료 시 미입력 |
| 기본 길이 | 한글 기준 200~800자 | 200자 미만이면 핵심 내용 누락 여부 확인 |
| 장문 기준 | 800자 초과 시 핵심 요약을 첫 5문장에 배치 | 원문만 첨부하고 요약이 없으면 미완료 |
| 필수 식별 | 일시, 채널, 참석자, 접촉 목적 | 하나라도 없으면 불완전 기록 |
| 필수 내용 | 고객 발언, 당사 답변, 결정·미결 사항 | 사실 구분이 없으면 수정 대상 |
금요일 접촉은 다음 영업일 종료 전까지 입력합니다. 다만 소유자 이관이나 단계 변경이 먼저 발생하면 해당 처리 전에 활동 기록을 완료합니다.
발언은 문장 앞에 `[고객]`, `[헤드헌터랩]`, `[합의]`, `[미결]` 표기를 사용해 주체를 구분합니다. 여러 고객 참석자의 의견이 다르면 `[고객-역할명]`으로 구분하며, 발언자를 확인하지 못한 내용을 특정인의 의견으로 단정하지 않습니다.
`좋은 반응`, `검토 예정`, `논의 완료`처럼 근거가 없는 표현만 기록해서는 안 됩니다. 고객이 무엇을 확인했고 누가 어떤 조건에서 답변하기로 했는지 관찰 가능한 사실로 작성합니다.
접촉 후 발생한 후속 행동은 활동 본문과 별도로 다음 액션 필드에 연결합니다. 다음 액션 작성 기준은 s5, 개인정보와 고객 비밀정보의 입력 제한은 s14를 적용합니다.

## 다음 액션 작성 기준
<!--meta: sec=s5; dept=SALES; level=주니어|시니어; ct_band=중; related=s4|s6-->
‘다음 액션’에는 영업 담당자가 혼자 수행할 내부 업무가 아니라 고객과 합의한 다음 접점을 기록합니다. 고객 참석 회의, 고객 검토 결과 회신, 자료 제공, 의사결정 확인처럼 고객 측 담당자와 일정이 특정된 약속이어야 합니다.

내부 준비 업무는 활동 기록이나 개인 업무 도구에서 관리합니다. CRM에는 고객 약속의 완료 여부를 제3자가 판정할 수 있도록 날짜, 고객 역할, 약속 내용, 완료 조건을 함께 입력합니다.

**좋은 예와 나쁜 예**

| 나쁜 예 | 좋은 예 |
| --- | --- |
| 제안서 작성 | `2026-11-18` 제조업 고객사 현업 책임자가 제안서 초안을 검토하고 수정 의견을 회신합니다. |
| CNS와 요구사항 논의 | `2026-11-20` 유통 고객사 운영팀장과 CNS 과장이 요구사항 확정 회의를 진행합니다. |
| 고객에게 다시 연락 | `2026-11-21` 금융업 고객사 구매 담당자가 예산 승인 여부를 전화로 회신합니다. |
| 계약서 검토 | `2026-11-24` 서비스업 고객사 법무 담당자가 계약서 수정 의견을 이메일로 전달합니다. |
| 데모 준비 | `2026-11-25` 제조업 고객사 의사결정권자와 AI 기능 데모를 실시하고 평가 결과를 확인합니다. |
| 유지보수 의향 확인 | `2026-11-27` 유통 고객사 운영 책임자가 갱신 범위와 계약 기간에 대한 의견을 회신합니다. |

좋은 다음 액션은 완료 여부가 `완료`, `미완료`, `재합의` 중 하나로 판정되어야 합니다. “협의 예정”, “추후 확인”, “관계 유지”처럼 결과를 확인할 수 없는 문구는 사용하지 않습니다.

**필수 작성 요소**

1. 날짜는 `YYYY-MM-DD` 형식으로 입력하며, 열린 기회의 다음 액션 날짜는 입력일 이후여야 합니다.
2. 고객 측 참여자는 성명 대신 회사 내 역할 또는 직책으로 식별할 수 있습니다.
3. 회의라면 논의 주제와 산출할 결론을 쓰고, 회신이라면 고객이 제공할 정보나 승인 사항을 씁니다.
4. 고객과 일정이 확정되지 않았다면 확정 전까지 포캐스트 근거로 사용하지 않고, 합의 예정일 자체를 고객 약속으로 꾸미지 않습니다.

날짜가 없는 다음 액션은 문구가 구체적이어도 유효한 입력으로 인정하지 않습니다. 날짜가 지났는데 완료되지 않은 경우에는 기존 값을 덮어쓰지 않고 결과를 활동 기록에 남긴 후 고객과 재합의한 새 날짜와 내용을 입력합니다.

**판정 기준**

| 상태 | 판정 조건 |
| --- | --- |
| 유효 | 미래 날짜, 고객 역할, 약속 내용, 완료 조건이 모두 있습니다. |
| 보완 필요 | 날짜는 있으나 고객 역할 또는 완료 조건이 없습니다. |
| 무효 | 날짜가 없거나 내부 업무만 기재되어 있습니다. |
| 기한 경과 | 날짜가 지났으나 완료 기록 또는 재합의 기록이 없습니다. |

다음 액션의 고객 약속이 파이프라인 단계 전환 근거가 되는지는 FCT-01을 적용합니다. 단순 일정 변경은 기존 활동 이력을 삭제하지 않으며, 변경 사유와 고객 재합의 일시를 남깁니다.

## 입력 시점 규칙
<!--meta: sec=s6; dept=SALES; level=주니어; ct_band=중; related=s5|s7-->
CRM 입력 시점은 담당자가 기억하기 편한 때가 아니라 고객 사실이 발생한 시점을 기준으로 합니다. 영업일은 서울·경기·인천 지점의 공통 영업일을 적용하며, 시스템 기록 시각이 준수 여부의 기준입니다.

고객 이메일, 회의록 또는 승인 문서가 근거인 경우 레코드 수정과 동시에 해당 근거의 링크를 연결합니다. 입력 기한이 서로 겹치면 더 짧은 기한을 적용합니다.

**항목별 입력 기한**

| 항목 | 기한 기산점 | 입력 기한 | 필수 동시 입력 |
| --- | --- | --- | --- |
| 기회 생성 | 기회 등록 요건 충족 사실을 확인한 때 | 1영업일 이내 | 소유자, 계정, 예상 금액, 종료예정일 |
| 단계 전환 | 전환 근거가 확보된 때 | 당일 18:00까지, 18:00 이후 발생 시 다음 영업일 12:00까지 | 전환일, 근거 링크, 다음 액션 |
| 금액 변경 | 고객 범위·수량·기간 또는 승인 견적이 변경된 때 | 4영업시간 이내 | 변경 전·후 금액, 변경 사유, 근거 |
| 종료예정일 변경 | 고객 일정 또는 의사결정 일정 변경을 확인한 때 | 당일 18:00까지 | 이전 날짜, 새 날짜, 고객 근거 |
| 실패 확정 | 고객의 중단·타사 선정·예산 철회가 확인된 때 | 1영업일 이내 | 실패일, 실패 사유 코드, 근거 |

금액과 종료예정일은 담당자의 기대만으로 수정하지 않습니다. 고객 발언이나 승인 자료가 없고 내부 판단만 바뀐 경우에는 판단 메모를 활동 기록에 남기며, 사실 필드는 유지합니다.

**시간 계산 규칙**

- 금요일 17:00에 확인한 4영업시간 기한은 다음 영업일의 잔여 시간까지 이어서 계산합니다.
- 휴일과 회사 공통 휴무일은 영업시간 계산에서 제외합니다.
- 모바일·이메일 연동 장애가 발생하면 복구 후 2시간 이내 입력하고 장애 티켓 번호를 남깁니다.
- 잘못 입력한 값은 과거 시점으로 소급 입력하지 않고 현재 시점에 정정하며 변경 사유를 기록합니다.
- 회의 참석자가 여러 명이어도 레코드 소유자 1명이 기한 준수 책임을 집니다.

리뷰 직전에 여러 건을 몰아 입력하면 단계 체류시간, 변경 이력, 라우팅 시간과 데이터 품질 점수가 실제보다 왜곡됩니다. 그 결과 리뷰 참여자는 고객 진행과 CRM 수정 작업을 구분할 수 없고, 자동 알림도 필요한 시점보다 늦게 발생합니다.

**기한 초과 판정**

| 구분 | 판정 기준 | 처리 |
| --- | --- | --- |
| 경미 지연 | 기한 후 4영업시간 이내 입력 | 지연 사유 코드 기록 |
| 일반 지연 | 4영업시간 초과, 1영업일 이내 | 소유자 보완 및 영업 관리자 확인 |
| 중대 지연 | 1영업일 초과 | 주간 위생 점검 이슈로 등록 |
| 반복 지연 | 최근 4주간 3회 이상 | FCT-05 s17 절차 적용 |

주간 리뷰를 위한 데이터 마감과 회의 운영은 FCT-03을 따릅니다. 마감 준수는 본래 입력 기한을 연장하지 않으며, 리뷰가 없는 주에도 동일한 기한을 적용합니다.

## 검증 규칙과 자동 차단 항목
<!--meta: sec=s7; dept=SALES; level=시니어; ct_band=상; related=s6|s8-->
검증 규칙은 오류가 후속 집계에 들어가기 전에 차단하는 통제와, 사용자의 판단을 요구하는 경고로 구분합니다. 차단 오류는 조건을 해소하기 전까지 저장·단계 변경·종료 처리가 완료되지 않습니다.

자동 차단은 참·거짓을 시스템이 일관되게 판정할 수 있고, 잘못 저장될 경우 귀속·포캐스트·계약 연결에 직접 영향을 주는 항목에 한정합니다. 맥락에 따라 정당한 예외가 생기는 항목은 경고와 사후 점검을 사용합니다.

**시스템 자동 차단 항목**

| 검증 항목 | 차단 조건 | 사용자 해소 방법 |
| --- | --- | --- |
| 필수 필드 | 해당 상태의 필수 필드가 공백 또는 공백 문자만 존재 | 유효한 값을 입력한 후 재저장 |
| 종료예정일 | 열린 기회의 종료예정일이 저장일보다 과거 | 미래 날짜 입력 또는 확정 종료 처리 |
| 금액 범위 | 예상 금액이 0원 이하이거나 승인된 하한·상한 범위 밖 | 근거 범위 안으로 수정하거나 승인 절차 진행 |
| 단계 건너뛰기 | 현재 단계에서 허용되지 않은 다음 단계로 직접 이동 | FCT-01의 순차 전환 또는 승인된 예외 사용 |
| 다음 액션 | 열린 기회의 다음 액션 날짜 또는 내용이 공백 | 고객과 합의한 날짜와 약속 입력 |
| 소유자 | 활성 사용자 또는 허용 영업 큐가 지정되지 않음 | 유효 소유자나 큐 지정 |
| 계정 연결 | 기회에 고객 계정이 연결되지 않음 | 기존 계정 선택 또는 계정 생성 요청 |

단계별 필수 필드와 허용 전환 경로는 FCT-01을 적용합니다. 금액 승인 범위 자체의 결정은 PRP-xx를 따르며, CRM은 승인 결과와 입력값의 일치 여부만 검사합니다.

**경고만 표시하는 항목**

| 경고 조건 | 표시 기준 | 후속 확인 |
| --- | --- | --- |
| 종료예정일 장기 설정 | 저장일로부터 180일 초과 | 영업 관리자가 고객 일정 근거 확인 |

경고는 저장을 허용하지만 무시 사유를 선택하도록 할 수 있습니다. 동일 경고가 2주 연속 남아 있으면 주간 점검 이슈로 전환하며, 단순히 경고 창을 닫은 기록은 해소로 보지 않습니다.

**차단 확대 판단 기준**

새 차단 규칙은 `판정 가능성 → 영향도 → 해소 가능성 → 우회 위험` 순서로 검토합니다. 사용자가 5분 안에 오류 원인과 수정 방법을 이해할 수 있고, 최근 8주 표본에서 오탐률이 2% 이하일 때만 상시 차단 후보가 됩니다.

적용 전 2주간 경고 모드로 시험하며, 저장 포기율이 기존 대비 10% 이상 증가하거나 임시 값·허위 날짜 등 우회 입력이 대상 건의 5%를 넘으면 차단하지 않습니다. 위험 변경의 승인 및 긴급 해제 권한은 FCT-05 s16을 따릅니다.

## 분기 점검과 중복 제거 절차
<!--meta: sec=s10; dept=SALES|DATA; level=시니어; ct_band=상; related=s9|s11-->
분기 점검은 3·6·9·12월의 마지막 10영업일에 SALES와 DATA가 공동 수행합니다. 활성 여부와 관계없이 계정·담당자 레코드 전체를 탐지 대상으로 하며, 삭제가 아닌 대표 레코드로의 병합을 원칙으로 합니다.

DATA는 후보 탐지와 병합 배치 실행을 담당하고, SALES는 동일 고객 여부와 대표 레코드를 판정합니다. 계약 당사자 또는 영업 관계가 다른 경우에는 명칭이 유사해도 병합하지 않습니다.

**중복 매칭 규칙**

| 매칭 키 | 정규화 방법 | 후보 판정 | 자동 병합 |
| --- | --- | --- | --- |
| 법인등록번호 | 숫자 외 문자 제거 후 13자리 비교 | 완전 일치 | 금지 |
| 회사 도메인 | 소문자화, `www.`·경로·공백 제거 | 완전 일치 | 금지 |
| 정규화된 상호 | 법인 표기·공백·괄호·특수문자 제거 | 완전 일치 | 금지 |
| 복합 매칭 | 상호 일치와 도메인 또는 주소 일부 일치 | 검토 후보 | 금지 |
| 담당자 이메일 | 소문자화 후 전체 주소 비교 | 담당자 중복 후보 | 금지 |

공용 메일 도메인, 계열사 공동 도메인, 지주사·자회사 관계는 도메인 일치만으로 중복 판정하지 않습니다. 법인등록번호가 다르면 동일 상호라도 별도 계정으로 유지합니다.

**분기 전수 중복 제거 3단계**

1. `탐지`: DATA가 세 가지 핵심 매칭 키를 전체 레코드에 적용하고 후보군 ID를 부여합니다.
2. 탐지 결과에는 매칭 키, 신뢰 근거, 연결된 기회 수, 최근 활동일, 계약 관련 표시를 포함합니다.
3. `병합 판정`: SALES 과장 이상이 동일 법인 여부와 거래 관계를 확인해 병합·분리 유지·보류로 판정합니다.
4. 판정 충돌 또는 법인 관계 불명확 건은 SALES 부장과 DATA 책임자가 공동 승인할 때까지 보류합니다.
5. `병합 실행`: DATA가 승인된 후보만 백업한 뒤 샌드박스 검증과 운영 반영 순서로 실행합니다.
6. 실행 후 원본 ID와 대표 ID 매핑, 레코드 수, 연결 객체 수를 대조하고 2영업일 동안 오류를 관찰합니다.

**병합 실행 전 확인표**

| 확인 항목 | 보존·판정 기준 | 미충족 시 처리 |
| --- | --- | --- |
| 대표 레코드 | 법인 식별값이 있고 최근 검증된 계정 | 실행 보류 |
| 활동 이력 | 이메일·회의·통화·메모를 생성일과 작성자 그대로 재연결 | 백업 후 재시험 |
| 기회 이력 | 수주·실패·진행 기회를 모두 대표 계정으로 재연결 | 누락 시 실행 금지 |
| 필드 충돌 | 검증일이 최근인 값 우선, 계약 식별값은 수동 판정 | SALES 승인 |
| 되돌리기 제한 | 폐기 ID, 생성자, 일부 감사 로그의 복원 불가 여부 확인 | 서면 승인 |
| 첨부·링크 | 접근 권한과 연결 대상이 유지되는지 확인 | 오류 수정 후 재실행 |

동일 상업 건으로 의심되는 기회는 계정 병합 과정에서 삭제하거나 합산하지 않습니다. 기회 중복 여부는 별도 검토하고, 양쪽의 활동·단계 변경·금액 변경 이력을 보존합니다.

병합 실행 파일, 승인 기록, 백업본, ID 매핑표는 5년간 제한 저장소에 보관합니다. 분기 종료 후 후보 수·병합 수·오탐 수를 기록해 다음 분기 매칭 규칙을 조정합니다.

## 데이터 품질 점수 산정
<!--meta: sec=s11; dept=SALES|DATA; level=시니어; ct_band=상; related=s10|s12-->
데이터 품질 점수는 CRM 데이터가 영업 운영과 보고에 사용할 수 있는 상태인지 판단하는 통제 지표입니다. 점수는 완전성·정확성·적시성·중복률·일관성의 다섯 요소를 0~100점으로 계산합니다.

월간 점검 종료 후 DATA가 산출하고 SALES가 표본 근거를 확인합니다. 지점 간 레코드 규모 차이 때문에 개인별 점수의 단순 평균은 사용하지 않습니다.

**구성 요소와 가중치**

| 요소 | 가중치 | 100점 기준 | 산식 |
| --- | ---: | --- | --- |
| 완전성(C) | 30% | 필수 입력 셀이 모두 채워짐 | `유효 입력 셀 ÷ 필수 입력 셀 × 100` |
| 정확성(A) | 25% | 원천 자료와 검증값이 일치함 | `정확 판정값 ÷ 확인값 × 100` |
| 적시성(T) | 20% | 입력·갱신 기한 안에 처리됨 | `기한 준수 건 ÷ 기한 도래 건 × 100` |
| 중복 품질(D) | 15% | 확정 중복 레코드가 없음 | `100 × (1 - 확정 중복 수 ÷ 대상 레코드 수)` |
| 일관성(I) | 10% | 코드·날짜·객체 관계 규칙을 통과함 | `통과 규칙 수 ÷ 평가 규칙 수 × 100` |

종합 점수는 `0.30C + 0.25A + 0.20T + 0.15D + 0.10I`로 계산하며 소수점 첫째 자리에서 반올림합니다. 개별 요소가 0점 미만이 되면 0점, 100점을 초과하면 100점으로 제한합니다.

정확성은 지점별 월 최소 50개 레코드를 무작위 표본으로 확인합니다. 대상이 50개 미만이면 전수 확인하며, 제안·계약 원문, 고객이 확인한 연락처, 유효한 법인 식별값을 검증 근거로 사용합니다.

**집계 단위**

1. 팀 점수는 팀 소유 레코드의 원시 분자·분모를 합산한 뒤 각 요소를 다시 계산합니다.
2. 지점 점수는 서울·경기·인천 지점별 팀 데이터를 같은 방식으로 합산합니다.
3. 전사 점수는 지점 점수의 산술평균이 아니라 전체 원시 분자·분모로 재계산합니다.
4. 표본이 20건 미만인 세부 집단은 점수를 공표하지 않고 상위 집계에만 포함합니다.

**점수 밴드와 필수 조치**

| 점수 밴드 | 상태 | 필수 조치 | 완료 기한 |
| --- | --- | --- | --- |
| 95.0~100 | 정상 | 현행 통제 유지 | 다음 월 점검 |
| 90.0~94.9 | 관찰 | 최저 요소의 오류 상위 2개 수정 | 10영업일 |
| 80.0~89.9 | 개선 필요 | 팀 단위 개선 계획과 재검증 | 5영업일 계획, 30일 실행 |
| 0~79.9 | 통제 실패 | 신규 대량 변경 중지, 원인 분석, 부장 승인 후 재개 | 2영업일 |

품질 점수는 개인 인사평가나 판매 실적 평가에 사용하지 않습니다. 역할별 입력량 차이, 소량 표본의 변동성, 시스템·라우팅 오류가 개인 점수에 혼입되며 평가에 연결하면 공란 은폐나 중복 삭제 같은 지표 조작을 유발할 수 있기 때문입니다.

오류 레코드의 수정 책임은 소유자에게 배정할 수 있으나, 점수는 지점·팀의 프로세스 개선에만 사용합니다. 규칙·권한·자동화 결함은 RevOps/CRM 관리자의 개선 과제로 분리합니다.

## 정체·고아 레코드 처리
<!--meta: sec=s12; dept=SALES; level=주니어|시니어; ct_band=중; related=s11|s13-->
정체 레코드는 영업 가능성이 없다고 확정된 레코드가 아니라, 필요한 갱신이나 고객 접점이 멈춘 레코드입니다. 정체 표시는 삭제 사유가 아니며 소유자가 진행·보류·종료 중 하나를 다시 판정하게 하는 통제 신호입니다.

고아 레코드는 소유자가 공란이거나 비활성 사용자에게 배정된 레코드입니다. 임시 배정 큐가 2영업일을 초과한 경우도 고아로 판정합니다.

**판정 기준**

| 구분 | 판정 조건 | 예외 |
| --- | --- | --- |
| 활동 정체 | 열린 기회에 고객 대면 활동이 30일간 없음 | 고객이 정한 대기일이 기록된 건 |
| 액션 정체 | 다음 액션 기한이 14일 이상 경과 | 승인된 보류 종료일이 있는 건 |
| 종료일 정체 | 종료예정일이 과거인데 상태가 열림 | 종료일 변경 승인 대기 2영업일 이내 |
| 장기 과거 건 | 종료예정일이 90일 이상 과거 | 예외 없음, 월간 필수 감사 |
| 고아 건 | 소유자 공란·비활성·임시 큐 2영업일 초과 | 시스템 이관 작업 중인 1영업일 |

운영·유지보수 계약 자체는 영업 활동이 없다는 이유로 정체 처리하지 않습니다. 갱신 또는 확장 목적으로 열린 기회만 이 기준을 적용하며 갱신 절차는 CSM-05를 참조합니다.

**정체 레코드 처리 경로**

1. CRM이 조건 충족 다음 날 소유자와 직속 영업 관리자에게 정체 알림을 발송합니다.
2. 소유자는 5영업일 안에 고객 접점 기록, 다음 액션, 종료예정일 중 필요한 값을 갱신합니다.
3. 계속 대기해야 하면 보류 사유, 고객 근거, 재확인일을 입력하고 과장 이상 승인을 받습니다.
4. 근거가 없거나 고객이 중단을 확인한 경우 실패 상태로 종료하고 승인된 실패 사유 코드를 사용합니다.
5. 5영업일 내 조치가 없으면 SALES 관리자가 소유자와 관리자에게 자동 종료 사전 통보를 발송합니다.

**고아 레코드 처리 경로**

| 시점 | 처리 | 책임자 |
| --- | --- | --- |
| 탐지 후 1영업일 | 해당 지점 SALES 관리자 큐로 임시 배정 | CRM 관리자 |
| 탐지 후 3영업일 | 기존 관계와 활동 이력을 확인해 새 소유자 지정 | SALES 과장 이상 |
| 탐지 후 5영업일 | 미배정 사유를 부장에게 에스컬레이션 | SALES 관리자 |
| 담당자 변경·퇴사 발생 | 이관 절차 적용 | FCT-05 s13 참조 |

자동 종료는 `고객 대면 활동 90일 없음`, `다음 액션이 30일 이상 없거나 경과`, `종료예정일이 30일 이상 과거`, `보류 승인 없음`을 모두 충족한 열린 기회에만 적용합니다. 소유자와 관리자에게 10영업일 전에 대상 ID와 종료 예정일을 통보하며, 이의가 등록되면 자동 처리를 중지합니다.

자동 종료된 기회는 삭제하지 않고 실패 사유를 `관리상 장기 미활동`으로 기록합니다. 종료 레코드와 활동 이력은 5년간 보관하고, 자동 종료 전 추출한 검토 목록은 1년간 보관합니다. 개인정보 보존·삭제 조건은 s14를 우선 적용합니다.

## 담당자 변경·퇴사 시 레코드 이관
<!--meta: sec=s13; dept=SALES; level=시니어; ct_band=중; related=s12|s14-->
담당자 변경·퇴사 시 레코드 이관은 고객 응답 중단과 약속 누락을 방지하기 위한 필수 통제입니다. 적용 대상은 담당자가 소유한 계정, 연락처, 열린 기회, 활동, 후속 과제 및 구축 후 운영·유지보수 관련 영업 레코드입니다.

계획된 인사이동은 변경일 5영업일 전, 퇴사는 최종 근무일 3영업일 전까지 이관을 완료합니다. 갑작스러운 휴직·퇴사로 인계가 불가능하면 직속 과장 이상이 당일 임시 소유자를 지정합니다.

**표준 이관 흐름**

`대상 추출 → 기존 담당자 정리 → 신규 담당자 검토 → 고객 안내 → 소유자 변경 → 3영업일 후 확인`

| 단계 | 필수 작업 | 담당 | 기한 |
| --- | --- | --- | --- |
| 대상 추출 | 소유 레코드와 30일 이내 예정 활동을 목록화합니다. | 기존 담당자 | 변경일 5영업일 전 |
| 내용 정리 | 진행 상황, 연락처, 약속, 민감 사항을 갱신합니다. | 기존 담당자 | 변경일 3영업일 전 |
| 인수 검토 | 누락 필드와 고객 접촉 우선순위를 확인합니다. | 신규 담당자 | 소유자 변경 전 |
| 고객 안내 | 담당자 변경과 신규 연락 수단을 업무 채널로 알립니다. | 기존·신규 담당자 | 변경일 전후 1영업일 |
| 소유권 변경 | 계정과 하위 열린 레코드의 owner를 함께 변경합니다. | SALES 관리자 | 고객 안내 당일 |
| 사후 확인 | 미완료 약속과 회신 여부를 확인합니다. | 신규 담당자 | 변경 후 3영업일 |

**이관 전 필수 정리 항목**

| 항목 | 입력 기준 | 완료 판정 |
| --- | --- | --- |
| 진행 상황 요약 | 최근 합의, 현재 장애 요인, 다음 의사결정 지점을 5문장 이내로 작성합니다. | 신규 담당자가 추가 질문 없이 현 상태를 설명할 수 있습니다. |
| 고객 측 연락처 | 성명, 부서·직책, 업무용 이메일·전화, 의사결정 역할, 최근 검증일을 확인합니다. | 핵심 연락처 1명 이상이 최근 30일 이내 검증되었습니다. |
| 미완료 약속 | 제공 자료, 회신, 미팅, 견적 수정 등 약속별 담당자와 기한을 기록합니다. | 기한이 없는 열린 약속이 0건입니다. |
| 민감 사항 | 공식 보안 요구, 조달 제약, 커뮤니케이션 유의점 등 업무상 위험만 적습니다. | s14 금지정보가 포함되지 않습니다. |
| 인계 근거 | 최근 회의 기록과 승인된 문서의 CRM 링크를 연결합니다. | 링크 열람 권한과 유효성이 확인됩니다. |

이관 누락은 고객 중복 연락, 회신 지연, 제안 조건 불일치, 만료 일정 누락 및 소유자 없는 고아 레코드를 만듭니다. 특히 계정 owner만 변경하고 열린 기회·활동 owner를 남겨 두는 부분 이관은 완료로 인정하지 않습니다.

| 점검 시점 | 확인자 | 점검 항목 | 이상 시 조치 |
| --- | --- | --- | --- |
| 소유자 변경 직전 | 직속 과장 이상 | 필수 정리 항목과 신규 담당자 수락 여부 | 변경을 보류하고 당일 보완합니다. |
| 변경 후 3영업일 | 신규 담당자 | 미완료 약속, 고객 안내, 링크 접근 | 누락분을 1영업일 내 보완합니다. |
| 다음 주간 점검 | SALES 관리자 | owner, status, next step, 연락처 검증일 | 미확인 레코드를 점검 대상에 유지합니다. |
| 변경 후 30일 | SALES 부장 | 고객 이슈와 남은 고아 레코드 | 재배정 또는 종료 판단을 지시합니다. |

## 개인정보와 고객 비밀정보 입력 금지 범위
<!--meta: sec=s14; dept=SALES|CNS; level=시니어; ct_band=상; related=s13|s15-->
CRM에는 영업 수행에 필요한 최소한의 업무 연락정보만 저장합니다. 수집 가능한 항목이라는 이유만으로 입력하지 않으며, 자유서술 필드·활동 메모·첨부 파일에도 동일한 금지 기준을 적용합니다.

고객이 이메일이나 회의에서 금지정보를 전달한 경우에도 CRM에 전재하지 않습니다. 업무상 조치가 필요하면 비식별화한 결과만 기록하고, 원문 취급은 승인된 보안 저장소와 해당 업무 문서를 따릅니다.

**입력 금지 범위**

| 구분 | 금지 예시 | CRM 기록 방식 |
| --- | --- | --- |
| 개인 신상 | 가족관계, 건강·질병, 장애, 종교, 정치 성향, 사적 주소 | 입력하지 않습니다. |
| 고객사 내부 인사정보 | 미공개 퇴사·징계·평가·보상·승진 후보 정보 | 공식 발표된 담당 변경 결과만 반영합니다. |
| 금융정보 | 신용카드 번호, 유효기간, 인증값, 개인·법인 계좌번호 | 저장하지 않고 FIN-xx 절차를 참조합니다. |
| 제3자 비밀정보 | 타 공급사 원가, 제3자 계약 조건, 외부 데이터 원문 | 권한과 제공 근거가 확인되지 않으면 입력하지 않습니다. |
| 인증정보 | 비밀번호, API 키, 토큰, 인증서 개인키, 일회용 코드 | CRM 및 첨부 파일에 저장하지 않습니다. |
| 계약서 원문 스캔 | 서명·날인·주민정보가 포함된 스캔본의 직접 첨부 | 제한 저장소의 권한 통제 링크만 기록합니다. |
| 고객 비밀 원문 | 소스코드, 원천 데이터, 미공개 재무자료, 상세 보안 구성 | 문서명·보관 위치·접근 책임자만 기록합니다. |

계약 검토가 필요하더라도 계약서 원문을 CRM에 반복 첨부하지 않습니다. CRM에는 계약 유형, 체결일, 유효기간, 문서 식별번호 및 제한 저장소 링크까지만 두며, 접근 권한은 해당 계정 담당자와 승인된 검토자에게 한정합니다.

**허용되는 최소 정보**

| 정보 | 허용 범위 | 입력 조건 |
| --- | --- | --- |
| 기본 식별 | 성명, 소속 회사, 부서, 직책 | 업무 관계 식별에 필요한 경우 |
| 업무 연락 | 회사 이메일, 회사 전화, 업무용으로 제공된 휴대전화 | 제공 경로와 최근 검증일을 기록합니다. |
| 관계 정보 | 의사결정자·실무자·검토자 등 업무 역할 | 사적 평가 없이 객관적 역할만 기록합니다. |
| 수집 근거 | 문의, 소개, 행사, 기존 계약 등 접촉 출처 | 출처와 최초 접촉일을 기록합니다. |
| 수신 상태 | 연락 허용, 거부, 회신 중단 요청 | 거부 요청은 접수 당일 반영합니다. |

보관 기간은 목적별로 적용하며, 기간 만료 후 30일 이내 삭제 또는 비식별 처리합니다. 소송·감사·법적 보존 지시가 있으면 임의 삭제하지 않고 CNS와 지정 관리자의 확인을 받습니다.

| 대상 | 내부 보관 기준 | 만료 시 처리 |
| --- | --- | --- |
| 활성 기회가 없는 잠재고객 연락처 | 마지막 유효 업무 접촉일부터 12개월 | 연락처 삭제 또는 재검증합니다. |
| 실패·철회 기회 연락처 | 종료일부터 24개월 | 분쟁·재접촉 필요가 없으면 삭제합니다. |
| 계약 고객 연락처 | 최종 구축 또는 운영·유지보수 계약 종료 후 3년 | 계약 증빙과 분리하여 삭제합니다. |
| 수신 거부 기록 | 거부일부터 3년 | 재연락 방지용 최소 식별값만 유지합니다. |

금지정보를 발견한 사용자는 내용을 복사하거나 재배포하지 않고 즉시 접근을 중단합니다. 발견 시각, 레코드 ID, 정보 유형만 보안 담당 경로로 알리며 금지정보 자체를 신고 티켓에 붙이지 않습니다.

## 첨부 문서·링크 관리 규칙
<!--meta: sec=s15; dept=SALES; level=주니어; ct_band=중; related=s14|s16-->
CRM 첨부는 특정 시점의 확정본을 보존해야 할 때만 사용합니다. 계속 수정되는 문서, 공동 편집 문서, 대용량 파일은 회사 승인 저장소에 보관하고 CRM에는 내부 접근 링크를 연결합니다.

개인 클라우드, 개인 이메일 첨부, 고객이 임의 생성한 공개 링크는 공식 보관 위치로 인정하지 않습니다. 링크를 등록한 사용자는 대상 문서의 소유자, 접근 권한 및 문서 상태를 확인해야 합니다.

**첨부와 링크 선택 기준**

| 문서 상태 | 사용 방식 | 예시 | 제한 |
| --- | --- | --- | --- |
| 편집 중 | 내부 저장소 링크 | 검토 중 제안자료, 요구사항 목록 | CRM 직접 첨부를 금지합니다. |
| 공동 작업 중 | 내부 저장소 링크 | 회의 준비자료, 질의응답 목록 | 편집 권한자를 지정합니다. |
| 고객 발송 확정본 | PDF 첨부 또는 읽기 전용 내부 링크 | 최종 발송 제안서 | 발송일과 버전을 기록합니다. |
| 반복 갱신 문서 | 단일 대표 링크 | 일정표, 이슈 목록 | 최신본 위치를 하나로 유지합니다. |
| 대용량 산출물 | 제한 저장소 링크 | 분석 결과, 설계 산출물 | 원본을 CRM에 올리지 않습니다. |

파일명은 `[계정약어]_[문서유형]_[YYYYMMDD]_v주버전.부버전_[상태].[확장자]` 형식을 사용합니다. 예시는 `제조업고객사_제안서_20261111_v2.1_Final.pdf`이며, 실제 고객사명 대신 CRM 계정에 등록된 익명 표기 또는 승인된 계정 코드를 사용합니다.

| 요소 | 규칙 | 허용 예시 | 금지 예시 |
| --- | --- | --- | --- |
| 날짜 | 문서 기준일을 `YYYYMMDD`로 표기합니다. | `20261111` | `최신`, `오늘` |
| 주버전 | 범위·가격·구조 변경 시 1씩 올립니다. | `v2.0` | `최종2` |
| 부버전 | 오탈자·표현 수정 시 1씩 올립니다. | `v2.1` | `수정본` |
| 상태 | `Draft`, `Review`, `Final`, `Signed`만 사용합니다. | `v1.0_Final` | `진짜최종` |
| 확정본 | Final 이후 수정하지 않고 새 버전을 생성합니다. | `v3.0_Final` | 기존 파일 덮어쓰기 |

파일 1개당 CRM 직접 첨부 한도는 10MB이며, 레코드당 직접 첨부 총량은 30MB입니다. 한도를 넘는 파일, 압축 원천데이터 및 동영상은 승인 저장소 링크로 대체합니다.

외부 공유 링크, URL을 아는 사람 모두에게 열린 링크, 만료일 없는 고객 공개 링크는 CRM에 등록하지 않습니다. 내부 링크는 회사 계정 인증을 요구하고 최소 권한 그룹에만 열어야 하며, 고객 공유가 필요하면 별도 승인된 전달 경로를 사용합니다.

| 등록 전 확인 | 합격 기준 | 불합격 시 처리 |
| --- | --- | --- |
| 파일명 | 표준 형식과 버전이 일치합니다. | 이름을 수정한 후 등록합니다. |
| 접근 권한 | 담당자와 승인된 협업자만 열 수 있습니다. | 권한을 축소합니다. |
| 링크 유효성 | 시크릿·비로그인 상태에서 공개되지 않습니다. | 공개 설정을 해제합니다. |
| 중복 여부 | 같은 버전의 파일이 1개만 존재합니다. | 구버전은 링크 해제 또는 보관 처리합니다. |
| 금지정보 | s14 금지정보가 포함되지 않습니다. | 등록하지 않고 보안 절차로 전환합니다. |

담당자 변경 시 링크 소유권도 회사 공용 계정 또는 신규 담당자로 이전합니다. 개인 계정 삭제로 끊어진 링크는 정상 이관으로 인정하지 않습니다.

## 수정 권한과 승인 필요 변경
<!--meta: sec=s16; dept=SALES; level=시니어; ct_band=중; related=s15|s17-->
CRM 수정 권한은 직급만으로 부여하지 않고 직급, 지정 역할, 소유 범위를 함께 적용합니다. 상위 직급이라도 RevOps 관리자 권한이 없으면 계정 병합, 권한 변경, 대량 수정 및 감사 로그 변경을 직접 수행할 수 없습니다.

RevOps/CRM 관리자는 필드 표준, 중복 매칭 규칙, 권한, 자동화, 감사 및 구조적 수정을 소유합니다. SALES 관리자는 변경의 업무상 근거를 승인하며, 두 역할을 한 사람이 겸임하는 경우 SALES 부장의 추가 승인을 받아야 합니다.

**직급·역할별 기본 수정 권한**

| 직급·역할 | 허용 범위 | 허용하지 않는 작업 |
| --- | --- | --- |
| 사원 | 본인 소유 연락처·활동·열린 기회의 일반 필드 | 계정 병합, 과거 확정 데이터 수정 |
| 대리 | 본인 소유 레코드와 배정받은 공동 기회 | 대량 수정, 타 지점 소유권 변경 |
| 과장 | 소속 팀 레코드 검토와 팀 내 재배정 | 계정 병합 실행, 잠금 기간 수정 |
| 차장 | 지점 단위 변경 검토와 임시 소유자 지정 | 시스템 규칙·권한 변경 |
| 부장 | 지점 또는 SALES 부서의 위험 변경 승인 | RevOps 전용 실행 작업 |
| 지정 SALES 관리자 | 파이프라인 근거 확인, 소유권 조정 승인 | 중복 규칙과 자동화 변경 |
| CNS·AIAX·BE·DATA 협업자 | 배정된 기술 검토 필드와 활동 기록 | 영업 금액·소유자·계정 정보 변경 |
| RevOps/CRM 관리자 | 병합, 대량 수정, 권한·자동화·감사 수행 | 업무 근거 없는 임의 수정 |

금액 변경은 고객 발송 제안 또는 내부 승인 금액 대비 `20% 이상` 또는 `5,000만원 이상` 중 먼저 충족하는 경우 대폭 변경으로 봅니다. 단순 오탈자 교정이라도 잠금된 월·분기의 데이터에 영향을 주면 과거 기간 데이터 수정으로 처리합니다.

**승인이 필요한 위험 변경**

| 변경 유형 | 판정 기준 | 승인 경로 | 실행자 |
| --- | --- | --- | --- |
| 계정 병합 | 서로 다른 계정 ID를 하나로 통합 | 계정 owner → SALES 과장 이상 → RevOps | RevOps |
| 금액 대폭 변경 | 20% 이상 또는 5,000만원 이상 증감 | owner → SALES 차장 검토 → 부장 승인 | owner 또는 RevOps |
| 과거 기간 수정 | 마감·잠금된 월 또는 분기 데이터 변경 | SALES 부장 → RevOps, 회계 영향 시 FIN-xx 참조 | RevOps |
| 대량 일괄 수정 | 20건 이상 또는 2개 이상 지점 대상 | SALES 관리자 → 부장 → RevOps | RevOps |
| 초대량 수정 | 100건 이상 | SALES 부장과 RevOps 공동 승인 | RevOps |
| 확정 레코드 재개방 | 수주·실패 확정 후 상태 재개방 | 직속 과장 → SALES 부장 → RevOps | RevOps |
| 소유권의 지점 간 이동 | 계정 또는 기회의 지점 귀속 변경 | 양 지점 SALES 관리자 → SALES 부장 | RevOps |

승인 요청에는 변경 사유, 대상 레코드 ID, 변경 전·후 값, 영향 건수, 요청 기한 및 복구 방법을 포함합니다. 구두 승인이나 메신저 반응 표시는 승인으로 인정하지 않으며 CRM 변경 티켓에 승인 이력이 남아야 합니다.

`요청 등록 → 업무 책임자 검토 → 승인권자 전자 승인 → 변경 전 추출본 저장 → RevOps 실행 → 표본 검증 → 결과 통지`

RevOps는 실행 전 대상 레코드 추출본을 제한 저장소에 보관하고, 실행 후 전체 건수와 무작위 10건 또는 변경 건수의 10% 중 큰 수를 검증합니다. 검증 결과 불일치가 1건이라도 발견되면 추가 변경을 중단하고 전체 대상의 복구 가능성을 확인합니다.

일반 위험 변경 요청은 1영업일 이내 검토를 시작하고, 고객 대응 중단이 예상되는 긴급 소유권 변경은 4업무시간 이내 처리합니다. 긴급 처리도 사후 승인을 허용하지 않으며 최소 1명의 승인권자 확인을 받은 뒤 실행합니다.

## 위생 규칙 위반 시 처리 절차
<!--meta: sec=s17; dept=SALES; level=시니어; ct_band=중; related=s16|s18-->
**처리 원칙**
CRM 위생 위반은 개인의 태도 문제로 단정하지 않고 규칙의 불명확성, 입력 화면의 마찰, 자동화 오류, 업무량, 교육 누락을 먼저 확인합니다. 목적은 벌점 부과가 아니라 레코드 신뢰도 회복과 재발 방지입니다.
처리는 `발견 → 통보 → 수정 → 재확인 → 종결 또는 원인 개선` 순서로 진행합니다. 잘못된 데이터가 보고·라우팅·자동화에 확산될 위험이 있으면 해당 필드의 사용이나 연동만 임시 제한합니다.
**위반 등급과 처리 기한**
| 등급 | 판정 기준 | 통보 기한 | 수정 기한 | 재확인 기한 |
| --- | --- | --- | --- | --- |
| 긴급 | 개인정보·고객 비밀정보 오입력, 잘못된 권한 공개, 자동화 오작동 유발 | 발견 후 1시간 이내 | 즉시, 최대 4시간 | 수정 후 1시간 이내 |
| 중대 | 소유자·상태·다음 액션·연락처 검증 여부 오류로 라우팅 또는 보고 왜곡 | 발견 후 4영업시간 이내 | 1영업일 이내 | 다음 영업일 12:00까지 |
| 일반 | 필수값 누락, 명명 규칙 위반, 활동 기록 지연, 링크 오류 | 1영업일 이내 | 3영업일 이내 | 수정 기한 후 2영업일 이내 |
| 경미 | 표기 불일치 등 집계 영향이 없는 단건 오류 | 주간 점검 결과와 함께 | 5영업일 이내 | 다음 주간 점검 시 |
기한은 CRM 알림 또는 사내 지정 채널에 통보가 도달한 시점부터 계산합니다. 소유자가 휴가·출장 중이면 직속 영업 관리자에게 동시에 통보하고, 관리자가 당일 대리 수정자를 지정합니다.
긴급 위반은 SALES 내 RevOps/CRM 관리자가 노출 차단, 권한 회수, 자동화 중지를 우선 실행할 수 있습니다. 개인정보와 고객 비밀정보의 상세 처리 범위는 본 문서 s14를 따릅니다.
통보에는 레코드 URL, 위반 규칙, 등급, 잘못된 값, 요구 수정값, 수정 기한, 문의 담당자를 포함합니다. 화면 캡처만 전달하거나 수정 방향 없이 오류 사실만 알리는 통보는 유효한 통보로 보지 않습니다.
**단계별 실행**
1. 발견자는 레코드 URL, 발견 시각, 오류 화면과 예상 영향 범위를 위반 티켓에 기록합니다.
2. RevOps/CRM 관리자는 중복 신고 여부와 등급을 확인한 뒤 소유자와 영업 관리자에게 통보합니다.
3. 소유자는 값을 수정하고 원인을 `규칙 미인지·입력 실수·정보 미확보·시스템 오류·업무 이관 누락·기타` 중 하나로 기록합니다.
4. RevOps/CRM 관리자는 저장값, 검증 규칙 통과 여부, 연동 결과를 확인합니다. 소유자의 자체 확인만으로 종결하지 않습니다.
5. 오류 제거와 후속 연동 정상화가 확인되면 종결일과 재발 방지 필요 여부를 기록하고 티켓을 완료 처리합니다.
재확인에서 반려되면 일반·경미는 1영업일, 중대는 4영업시간, 긴급은 1시간 내 재수정합니다. 두 번째 반려부터 영업 관리자가 수정 방법을 직접 확인합니다.
수정할 수 없는 시스템 결함은 개인 위반으로 유지하지 않습니다. RevOps/CRM 관리자가 구조 개선 티켓으로 전환하고 임시 우회 절차, 영향 레코드 목록, 복구 예정일을 공지합니다.
위반 티켓과 확인 증적은 종결일로부터 12개월간 보관합니다. 원본 값에 고객 비밀정보가 포함된 경우 해당 값을 복사하지 않고 레코드 식별자와 조치 사실만 남깁니다.
**반복 위반과 에스컬레이션**
동일 규칙을 같은 소유자가 30일 내 2회 위반하면 15분 원인 확인을 실시합니다. 30일 내 3회 또는 팀 내 동일 오류 5건 이상이면 구조적 반복으로 판정하여 규칙 문구, 입력 화면, 자동화, 교육 여부를 점검합니다.
| 반복 수준 | 필수 조치 | 책임자 | 완료 기한 |
| --- | --- | --- | --- |
| 동일인 2회 | 원인 코드 확인과 1:1 입력 시연 | 영업 관리자 | 3영업일 |
| 동일인 3회 | 5-Why 분석, 레코드 10건 표본 감사, 개선안 등록 | RevOps/CRM 관리자 | 5영업일 |
| 팀 내 5건 이상 | 시스템 통제 또는 규칙 개정 필요성 검토 | SALES 부장·RevOps/CRM 관리자 | 10영업일 |
| 개선 적용 후 재발 | 통제 효과 검증과 추가 자동화·교육 결정 | SALES 부장 | 10영업일 |
반복 횟수는 원인 개선 기회 제공 여부와 함께 해석하며, 건수만으로 개인 평가에 사용하지 않습니다. 성문화된 규칙, 주간 점검, 위험 변경 승인, 규칙 누락 재점검이 갖춰졌는지도 함께 확인합니다.
구조적 원인이 제거된 뒤에도 고의적 미수정, 허위값 입력, 승인 없는 우회가 반복되면 SALES 부장이 사실관계와 업무 영향을 기록해 별도 인사 절차 검토를 요청할 수 있습니다. 벌점·징계 기준은 HR-xx만 참조합니다.

## 규칙 변경 요청 경로
<!--meta: sec=s18; dept=SALES; level=주니어|시니어; ct_band=하; related=s17-->
**변경 요청 원칙**
CRM 필드와 검증 규칙은 개인 편의를 위해 즉시 변경하지 않습니다. 신규 데이터가 의사결정·보고·자동화에 사용되는지, 기존 데이터로 대체할 수 없는지, 입력 부담보다 효용이 큰지를 확인한 뒤 반영합니다.
현장 요청은 모두 동일한 변경 요청 양식을 사용합니다. 구두 요청, 메신저 단독 요청, 회의록의 제안 문구는 검토 대기열에 등록되지 않으며 긴급 요청도 사후 양식 등록이 필요합니다.
**접수 경로와 필수 정보**
변경 흐름은 `요청자 → CRM 변경 요청 양식 → RevOps/CRM 관리자 형식 검토 → 영향 부서 검토 → 결정 통보 → 배포`로 운영합니다.
| 요청 유형 | 필수 기재 사항 | 필수 첨부 | 1차 검토자 |
| --- | --- | --- | --- |
| 필드 추가 | 필드명, 데이터 형식, 사용 목적, 입력 주체, 사용 보고서 | 예상 입력 예시 3건 | RevOps/CRM 관리자 |
| 필드 삭제 | 미사용 근거, 대체 필드, 기존 데이터 처리안 | 최근 90일 사용 현황 | RevOps/CRM 관리자 |
| 검증 규칙 변경 | 현재 조건, 변경 조건, 차단·경고 방식, 예외 사례 | 오류 또는 누락 사례 5건 | RevOps/CRM 관리자 |
| 양식·화면 변경 | 대상 사용자, 화면 위치, 작업 단계, 예상 절감 시간 | 변경 전·후 화면안 | RevOps/CRM 관리자 |
양식은 사내 CRM 운영 포털의 `CRM 변경 요청` 메뉴로 접수합니다. 접수 후 2영업일 내 필수 정보 충족 여부를 확인하며, 누락 요청은 검토 상태로 전환하지 않고 보완 요청합니다.
요청자는 대상 지점·부서, 월간 예상 사용 건수, 사용자 1인당 추가 또는 절감 시간, 기존 보고서·자동화·연동 영향, 희망 적용일을 수치로 작성합니다. “필요함”, “불편함”만 적은 요청은 반려합니다.
**현장 부담 대비 효용 검토**
| 평가 요소 | 0점 | 1점 | 2점 |
| --- | --- | --- | --- |
| 의사결정·보고 효용 | 사용처 없음 | 단일 팀 참고 | 전사·지점 공식 보고 또는 필수 의사결정 |
| 오류 감소·자동화 효용 | 변화 없음 | 수동 점검 일부 감소 | 반복 오류 차단 또는 자동화 필수값 |
| 사용 범위 | 월 10건 미만 | 월 10~49건 | 월 50건 이상 또는 2개 이상 지점 사용 |
| 건당 입력 부담 | 15초 미만 | 15~30초 | 30초 초과 |
| 적용·유지 부담 | 설정만 필요 | 데이터 이관 또는 교육 필요 | 연동 수정과 과거 데이터 보정 모두 필요 |
효용 점수는 앞의 3개 항목 합계, 부담 점수는 뒤의 2개 항목 합계로 계산합니다. `순효용 = 효용 점수 - 부담 점수`이며 요청자는 추정치, RevOps/CRM 관리자는 표본 측정값을 기록합니다.
| 순효용 | 결정 기준 | 처리 방식 |
| --- | --- | --- |
| 3점 이상 | 반영 후보 | 영향 검토 후 정기 배포에 포함 |
| 1~2점 | 효과 불확실 | 2~4주 파일럿 후 재판정 |
| 0점 이하 | 부담이 효용 이상 | 반려하거나 기존 기능으로 대체 |
| 점수 산정 불가 | 근거 부족 | 월간 사용량 또는 입력시간을 10건 이상 측정 후 재접수 |
필드 삭제는 점수와 별도로 보고서, 자동화, API 연동, 첨부 양식, 과거 레코드 보존 필요성을 확인합니다. 영향 객체가 하나라도 확인되지 않으면 삭제 대신 숨김 상태로 90일 운영한 뒤 재검토합니다.
승인 필요 변경과 실제 수정 권한은 본 문서 s16을 참조합니다.
