# 백엔드 개발자 직무기술서
<!--meta: doc=JD-BE-01; doc_type=jd; tier=2; topic=ORG; disclosure=public; status=active-->

## 직무 개요
<!--meta: sec=s1; dept=BE; level=주니어|시니어; ct_band=하; related=s2|s5|s8-->
백엔드팀은 AI/AX개발팀이 만든 모델을 실제 서비스로 띄우는 API 서버, 데이터 파이프라인, 연동 인프라를 책임집니다. 고객사 시스템과의 연동(RPA, 기존 ERP/CRM API)도 백엔드팀이 설계합니다.

헤드헌터랩의 백엔드 개발자는 일반적인 웹 서비스 기능 개발에 그치지 않고, AI 모델과 고객사 업무 시스템 사이를 안정적으로 연결하는 실행 계층을 구축합니다. 모델의 추론 결과가 고객 업무에 안전하게 전달되도록 요청 검증, 인증·인가, 비동기 처리, 오류 복구, 감사 로그, 모니터링을 함께 설계합니다.

근무 조직은 백엔드팀이며 서울·경기·인천 3개 지점에서 컨설팅팀, AI/AX개발팀, 데이터분석팀, 영업팀과 협업합니다. 모든 지점이 컨설팅과 개발 기능을 함께 보유하고 있으므로 특정 지점에 한정되지 않고 프로젝트 상황에 따라 원격 협업, 고객사 회의, 현장 기술 지원이 이루어질 수 있습니다.

이 직무가 만드는 핵심 가치는 다음과 같습니다.

- AI 기능을 반복 호출할 수 있는 안정적인 서비스 인터페이스로 전환
- 고객사 ERP·CRM·그룹웨어·RPA 환경과 헤드헌터랩 솔루션의 연결
- 장시간 작업과 대량 작업을 안전하게 처리하는 비동기 실행 구조 제공
- 배포 이후의 성능, 장애, 비용, 보안 상태를 관찰할 수 있는 운영 기반 마련
- 요구사항 변경에도 전체 시스템을 다시 만들지 않도록 경계와 계약을 명확히 설계

## 주요 업무
<!--meta: sec=s2; dept=BE; level=주니어|시니어; ct_band=중; related=s1|s6|s9|s10-->
- AI 모델 서빙 API 설계·개발(FastAPI 등)
- 고객사 시스템 연동(API, RPA 트리거) 구축
- 비동기 작업 큐, 배치 파이프라인 운영
- 운영 모니터링·장애 대응, 로그·경보 체계 구축
- REST 기반 요청·응답 인터페이스와 내부 서비스 계약 정의
- 입력값 검증, 예외 표준화, 타임아웃, 재시도, 중복 요청 방지 기능 구현
- 고객사별 인증 방식과 네트워크 조건을 반영한 연동 어댑터 개발
- 장시간 추론, 파일 처리, 대량 전송을 위한 비동기 실행 흐름 설계
- 관계형 데이터베이스의 테이블, 인덱스, 트랜잭션 범위 설계
- 서비스 상태 확인을 위한 헬스 체크와 운영 지표 노출
- 개발·검증·운영 환경별 설정 분리와 배포 절차 자동화
- 장애 발생 시 로그와 지표를 기반으로 영향 범위 확인 및 복구 지원
- API 명세, 운영 절차, 변경 이력, 장애 대응 방법 문서화
- 코드리뷰, 테스트 작성, 기술 부채 정리 등 팀 공통 개발 활동 참여

주니어는 범위가 명확한 기능과 연동 단위를 담당하며 리뷰를 통해 품질 기준을 학습합니다. 시니어는 여러 시스템의 제약을 조정하고, 실패 가능성을 선제적으로 분석하며, 설계 결정과 운영 결과에 대한 책임을 집니다.

## 자격 요건
<!--meta: sec=s3; dept=BE; level=주니어|시니어; ct_band=하; related=s7|s13|s14-->
- Python 기반 서버 개발 경험(FastAPI/Django 등)
- RDB·메시지 큐 활용 경험
- 주니어(0~3년): 기능 단위 API 개발, 코드리뷰 하에 배포 가능
- 시니어(4년+): 시스템 아키텍처 설계, 장애 대응 리드 경험
- HTTP 요청·응답 구조와 상태 코드의 기본 의미를 설명할 수 있는 역량
- Git 기반 협업과 브랜치, 커밋, 코드리뷰 절차에 대한 이해
- 오류 상황을 재현하고 로그를 근거로 원인을 좁혀갈 수 있는 문제 해결 능력
- 요구사항을 구현 항목, 예외 조건, 검증 기준으로 구체화할 수 있는 역량
- 운영 환경에서의 변경이 사용자와 고객사 업무에 미치는 영향을 고려하는 태도
- 본인이 작성한 코드와 설계 의도를 문서와 구두로 설명할 수 있는 의사소통 능력

특정 프레임워크 사용 연수보다 서버 동작 원리, 데이터 정합성, 실패 처리, 운영 가능성에 대한 이해를 중요하게 평가합니다. 실무 경력이 짧더라도 개인·교육·오픈소스 프로젝트에서 설계 선택과 검증 과정을 명확히 설명할 수 있다면 관련 경험으로 검토합니다.

## 우대 사항
<!--meta: sec=s4; dept=BE; level=주니어|시니어; ct_band=중; related=s8|s10|s11|s12-->
- 외부 고객사 시스템과의 연동 경험(인증, 레이트리밋 처리 포함)
- 대용량 배치 처리·스케줄링 경험
- 컨테이너 기반 애플리케이션 패키징과 배포 경험
- 작업 큐의 재시도, 지연 실행, 실패 작업 분리 운영 경험
- 데이터베이스 실행 계획 확인과 인덱스 개선 경험
- 구조화 로그, 메트릭, 분산 추적 중 하나 이상의 관측 체계 구축 경험
- API 버전 관리와 하위 호환성 유지 경험
- 웹훅, 폴링, 파일 교환 등 다양한 시스템 연동 패턴 경험
- 개인정보 또는 고객사 업무 데이터를 다루는 서비스 개발 경험
- 테스트 자동화와 배포 전 품질 게이트 운영 경험
- 장애 회고를 통해 재발 방지 항목을 실제 코드나 운영 절차에 반영한 경험
- 비개발 직군과 기술 제약, 일정, 위험을 조율한 경험

우대 사항은 필수 조건이 아닙니다. 모든 항목을 보유하기보다 특정 영역에서 깊이 있는 문제 해결 경험을 보여주는 것이 중요합니다.

## 직무 범위와 책임 경계
<!--meta: sec=s5; dept=BE; level=주니어|시니어; ct_band=중; related=s1|s6|s17-->
백엔드 개발자는 모델 자체의 학습 품질이나 통계 분석 결과를 단독으로 책임지는 역할이 아닙니다. 대신 모델과 분석 결과가 서비스 환경에서 예측 가능한 방식으로 호출되고 저장되며 전달되도록 책임집니다.

주요 책임 경계는 다음과 같습니다.

| 구분 | 백엔드팀의 주 책임 | 협업이 필요한 영역 |
|---|---|---|
| 모델 호출 | 요청 변환, 타임아웃, 응답 검증, 오류 처리 | 모델 입력·출력 정의 |
| 업무 연동 | 인증, 전송, 재시도, 중복 방지 | 고객 업무 규칙 확인 |
| 데이터 저장 | 스키마, 트랜잭션, 조회 성능 | 분석 목적과 보존 요건 확인 |
| 배포 | 애플리케이션 패키징, 설정, 상태 점검 | 모델 산출물과 실행 조건 확인 |
| 운영 | 로그, 지표, 알림, 복구 절차 | 영향 분석과 고객 커뮤니케이션 |
| 보안 | 접근 제어 적용, 비밀정보 안전한 사용 | 고객사 정책 및 계약 조건 확인 |

역할 경계가 있다는 것은 문제를 다른 부서에 넘긴다는 의미가 아닙니다. 백엔드 개발자는 시스템 간 접점에서 발생한 문제를 재현 가능한 형태로 정리하고, 담당 조직과 함께 해결될 때까지 기술적 연결 고리를 유지해야 합니다.

## API 설계 및 구현 책임
<!--meta: sec=s6; dept=BE; level=주니어|시니어; ct_band=중; related=s2|s9|s14-->
API 개발은 경로와 응답 JSON을 만드는 작업뿐 아니라 서비스 계약을 정의하는 작업입니다. 개발자는 호출자가 어떤 값을 보내야 하는지, 어떤 결과를 받을 수 있는지, 실패 시 무엇을 해야 하는지를 명확히 표현해야 합니다.

기본 설계 항목은 다음과 같습니다.

- 리소스와 작업의 성격에 맞는 엔드포인트 구조
- 필수값, 선택값, 길이, 범위, 형식에 대한 입력 검증
- 일관된 성공·실패 응답 형식과 오류 코드
- 호출 추적을 위한 요청 식별자와 상관관계 식별자
- 동기 처리와 비동기 처리의 선택 기준
- 페이지네이션, 정렬, 필터 조건의 명시
- 멱등성이 필요한 작업의 중복 실행 방지 방식
- 클라이언트 타임아웃과 서버 내부 타임아웃의 구분
- 기능 변경 시 기존 호출자를 보호하기 위한 호환성 정책
- 민감정보가 응답과 로그에 노출되지 않도록 하는 필드 제어

주니어는 기존 API 규칙에 따라 기능을 구현하고 테스트합니다. 시니어는 API 경계, 오류 분류, 버전 전환, 성능 한도와 같은 장기 운영 규칙을 결정합니다.

## 개발 언어와 기본 기술 역량
<!--meta: sec=s7; dept=BE; level=주니어|시니어; ct_band=하; related=s3|s13|s18-->
주요 개발 언어는 Python이며 FastAPI 또는 Django와 같은 Python 기반 서버 프레임워크 경험을 활용합니다. 다만 채용 평가는 프레임워크 문법 암기보다 다음 기본기를 중심으로 이루어집니다.

- 함수와 모듈의 책임을 작게 나누는 능력
- 예외를 숨기지 않고 의미 있는 오류로 변환하는 능력
- 타입과 데이터 모델을 통해 인터페이스를 표현하는 능력
- 동기 실행과 비동기 실행의 차이에 대한 이해
- 네트워크 I/O와 CPU 연산의 특성 구분
- 설정값과 소스코드를 분리하는 습관
- 의존성을 명시적으로 관리하고 재현 가능한 실행 환경을 만드는 능력
- 읽기 쉬운 이름, 일관된 구조, 필요한 수준의 주석을 사용하는 능력

새로운 라이브러리를 도입할 때는 편의성뿐 아니라 유지보수 상태, 라이선스, 보안 업데이트, 팀 학습 비용, 기존 시스템과의 호환성을 검토합니다.

## 고객사 시스템 연동
<!--meta: sec=s8; dept=BE; level=주니어|시니어; ct_band=상; related=s1|s4|s10|s17-->
고객사 연동은 백엔드 직무에서 높은 비중을 차지합니다. 고객사마다 인증 방식, 네트워크 개방 범위, 데이터 형식, 호출 가능 시간, 오류 응답 품질이 다르므로 표준 API 개발과 다른 접근이 필요합니다.

연동 개발자는 다음 사항을 확인합니다.

1. 호출 주체와 수신 주체가 각각 누구인지 식별
2. 개발·검증·운영 환경의 주소와 인증정보 분리
3. 연결 제한, 방화벽, 프록시, 인증서 조건 확인
4. 요청·응답 필드의 의미와 필수 여부 합의
5. 타임아웃, 초당 호출 한도, 일일 처리량 조건 확인
6. 재시도 가능한 오류와 즉시 중단해야 하는 오류 구분
7. 동일 요청 재전송 시 중복 업무가 발생하는지 확인
8. 상대 시스템 점검 또는 지연 시 임시 보관 방식 결정
9. 개인정보 및 민감 필드의 전송·저장·로그 정책 확인
10. 연동 변경 시 사전 통보와 호환 기간 정의

ERP·CRM API를 직접 호출할 수 없는 환경에서는 승인된 RPA 트리거, 파일 교환, 중계 서버, 예약 실행 방식을 검토합니다. 이때 연동 방식의 제약을 숨기지 않고 지연 가능성, 실패 감지 방식, 수동 복구 절차까지 요구사항에 포함합니다.

## 비동기 작업과 작업 큐
<!--meta: sec=s9; dept=BE; level=시니어; ct_band=상; related=s2|s6|s10|s15-->
모델 추론, 대용량 파일 처리, 외부 시스템 전송처럼 처리 시간이 길거나 실패 가능성이 높은 작업은 요청 처리 스레드에서 분리할 수 있습니다. 비동기 구조를 적용할 때는 단순히 큐에 작업을 넣는 것보다 작업의 생명주기를 정의하는 것이 중요합니다.

일반적인 작업 상태는 접수, 대기, 실행, 성공, 재시도 대기, 최종 실패, 취소로 구분합니다. 각 상태 전이는 로그와 저장소에서 확인할 수 있어야 하며, 사용자가 결과를 조회할 방법도 제공해야 합니다.

설계 시 검토할 항목은 다음과 같습니다.

- 작업 메시지에 포함할 최소 정보와 원본 데이터 참조 방식
- 메시지 중복 전달을 고려한 멱등 처리
- 지수형 또는 고정형 재시도 간격
- 재시도 횟수와 최종 실패 판정 기준
- 독성 메시지가 전체 큐를 막지 않도록 하는 격리 방식
- 작업 우선순위와 고객사별 자원 점유 제한
- 워커 종료 시 진행 중 작업의 안전한 처리
- 장시간 작업의 진행 상태와 만료 기준
- 취소 요청이 가능한 시점과 보상 처리
- 큐 적체량, 대기 시간, 실패율에 대한 경보 기준

시니어는 처리량만 높이는 설계보다 중복, 순서 역전, 부분 성공, 워커 재시작과 같은 현실적인 실패 조건을 포함해 구조를 검토해야 합니다.

## 배치 및 스케줄링 업무
<!--meta: sec=s10; dept=BE; level=주니어|시니어; ct_band=중; related=s2|s4|s8|s9-->
배치 작업은 정해진 시간에 데이터를 수집·가공·전송하거나 운영 정보를 정리하는 데 사용됩니다. 백엔드 개발자는 실행 시각만 설정하는 것이 아니라 배치의 입력 범위, 재실행 방식, 실패 복구 단위를 설계합니다.

배치 구현 시 다음 원칙을 적용합니다.

- 처리 기준일과 실제 실행 시각을 분리
- 대상 데이터 범위를 명시적으로 기록
- 부분 실패 데이터를 식별하고 선택적으로 재처리
- 동일 기준일을 재실행해도 결과가 중복되지 않도록 설계
- 선행 작업 완료 여부와 의존 관계 확인
- 전체 성공 건수, 실패 건수, 제외 건수를 집계
- 작업 시작·종료·소요 시간과 실패 원인을 기록
- 업무 시간에 영향을 주는 고부하 작업의 실행 창구 제한
- 수동 실행 권한과 승인 절차 구분
- 장기 미실행 또는 연속 실패에 대한 알림 제공

대량 데이터를 한 번에 메모리에 적재하는 방식은 피하고, 페이지 또는 청크 단위 처리와 체크포인트 사용을 검토합니다.

## 데이터베이스 설계와 트랜잭션
<!--meta: sec=s11; dept=BE; level=주니어|시니어; ct_band=상; related=s4|s12|s15-->
백엔드 개발자는 관계형 데이터베이스를 활용해 서비스 상태와 업무 데이터를 일관되게 관리합니다. 테이블 생성뿐 아니라 데이터 생명주기와 조회 패턴을 고려해 스키마를 설계해야 합니다.

핵심 역량은 다음과 같습니다.

- 업무 식별자와 내부 식별자의 구분
- 필수값, 유일성, 참조 관계를 제약조건으로 표현
- 트랜잭션 범위를 과도하게 넓히지 않는 설계
- 외부 API 호출과 데이터베이스 트랜잭션의 결합 위험 이해
- 자주 조회하는 조건에 맞는 인덱스 설계
- 실행 계획을 통한 전체 스캔, 비효율 조인 확인
- 상태값 변경 이력과 감사 목적 기록의 분리
- 논리 삭제와 물리 삭제의 선택 기준
- 스키마 변경 시 기존 데이터와 애플리케이션 호환성 검토
- 보존 기간이 지난 데이터의 삭제 또는 보관 정책 적용

시니어는 동시성 충돌, 잠금 대기, 교착 상태, 읽기 일관성, 장애 중 부분 반영 문제를 고려해 트랜잭션 경계를 정해야 합니다.

## 캐시와 성능 최적화
<!--meta: sec=s12; dept=BE; level=시니어; ct_band=상; related=s4|s11|s15|s19-->
성능 최적화는 체감 속도가 느리다는 이유만으로 캐시를 추가하는 작업이 아닙니다. 먼저 요청 구간별 소요 시간, 데이터베이스 조회 비용, 외부 API 응답 시간, 모델 호출 시간, 직렬화 비용을 측정해야 합니다.

캐시 도입 시 다음 질문에 답할 수 있어야 합니다.

- 어떤 데이터가 캐시 대상이며 원본은 어디에 있는가?
- 값이 오래되어도 허용되는 시간은 얼마인가?
- 키는 고객사, 사용자, 버전별로 안전하게 분리되는가?
- 원본 변경 시 즉시 무효화할 것인가, 만료를 기다릴 것인가?
- 캐시 장애 시 원본으로 우회할 수 있는가?
- 다수의 요청이 동시에 만료된 값을 갱신하지 않도록 할 수 있는가?
- 캐시 적중률이 낮을 때 유지 비용보다 이점이 큰가?
- 민감정보를 캐시에 저장해도 되는가?

최적화 결과는 변경 전후의 지연 시간, 처리량, 오류율, 자원 사용량으로 비교합니다. 평균값만 보지 않고 상위 지연 구간과 급격한 부하 증가 시의 변화도 확인합니다.

## 코드 품질 기준
<!--meta: sec=s13; dept=BE; level=주니어|시니어; ct_band=하; related=s3|s7|s14|s18-->
백엔드팀은 코드가 실행되는 것뿐 아니라 다른 개발자가 안전하게 변경할 수 있는 상태를 품질 기준으로 봅니다.

기본 기준은 다음과 같습니다.

- 함수와 클래스가 하나의 주요 책임을 갖도록 구성
- 업무 규칙과 외부 시스템 호출 코드를 분리
- 중복된 예외 처리와 데이터 변환을 공통 계층으로 정리
- 의미 없는 약어보다 도메인을 설명하는 이름 사용
- 실패를 무시하는 광범위한 예외 처리 금지
- 로그만 남기고 성공으로 응답하는 모호한 처리 지양
- 하드코딩된 주소, 인증정보, 환경별 값을 설정으로 분리
- 변경 이유가 드러나는 작은 단위의 커밋 작성
- 공개 인터페이스와 복잡한 업무 규칙에 필요한 설명 작성
- 사용하지 않는 코드와 임시 우회 로직의 정리 기한 명시

코드리뷰에서는 개인의 선호보다 정확성, 가독성, 테스트 가능성, 장애 가능성, 기존 규칙과의 일관성을 우선합니다.

## 테스트 책임
<!--meta: sec=s14; dept=BE; level=주니어|시니어; ct_band=중; related=s3|s6|s13|s20-->
개발자는 본인이 구현한 기능이 정상 조건뿐 아니라 오류 조건에서도 의도대로 동작하는지 검증해야 합니다. 테스트 작성은 별도 품질 담당자에게 넘기는 부가 작업이 아니라 개발 완료 조건에 포함됩니다.

권장 테스트 범위는 다음과 같습니다.

- 데이터 변환과 업무 규칙에 대한 단위 테스트
- API 입력값, 상태 코드, 응답 구조 검증
- 데이터베이스 저장과 트랜잭션 롤백 검증
- 외부 API 타임아웃과 오류 응답 처리 검증
- 재시도와 중복 요청 방지 검증
- 권한이 없는 사용자의 접근 차단 검증
- 배치 재실행과 부분 실패 복구 검증
- 스키마 변경 전후의 호환성 검증
- 주요 조회 경로의 성능 저하 여부 확인
- 운영 배포 전 핵심 기능 스모크 테스트

외부 시스템은 테스트 대역으로 대체할 수 있지만, 실제 환경과 다른 응답 형식이나 지연 특성이 존재할 수 있으므로 통합 검증 계획을 별도로 마련합니다.

## 운영 모니터링과 관측 가능성
<!--meta: sec=s15; dept=BE; level=주니어|시니어; ct_band=상; related=s2|s9|s11|s12|s16-->
운영 가능한 서비스는 문제가 발생했을 때 현재 상태와 원인을 확인할 수 있어야 합니다. 백엔드 개발자는 기능 구현 단계부터 로그, 메트릭, 추적 정보가 필요한 지점을 설계합니다.

주요 관측 항목은 다음과 같습니다.

| 영역 | 대표 확인 항목 |
|---|---|
| API | 요청 수, 성공률, 오류율, 응답 시간 |
| 외부 연동 | 호출 수, 타임아웃, 인증 실패, 레이트리밋 |
| 작업 큐 | 대기 작업 수, 대기 시간, 재시도 수, 최종 실패 |
| 배치 | 시작·종료 시각, 처리 건수, 실패 건수, 최근 성공 시각 |
| 데이터베이스 | 연결 사용량, 느린 쿼리, 잠금 대기 |
| 애플리케이션 | 프로세스 상태, 메모리, CPU, 재시작 횟수 |

로그에는 시간, 서비스명, 환경, 요청 식별자, 처리 단계, 결과, 오류 분류를 포함할 수 있습니다. 비밀번호, 인증 토큰, 주민등록번호, 원문 개인정보 등은 로그에 기록하지 않습니다.

경보는 모든 오류를 즉시 알리는 방식이 아니라 사용자 영향, 지속 시간, 자동 복구 가능성에 따라 우선순위를 구분합니다. 경보를 받은 사람이 다음 행동을 판단할 수 있도록 대상 서비스, 증상, 확인 위치, 초기 대응 절차를 함께 제공합니다.

## 장애 대응 역할
<!--meta: sec=s16; dept=BE; level=주니어|시니어; ct_band=상; related=s15|s17|s20-->
장애 발생 시 백엔드 개발자는 추측보다 관측된 사실을 바탕으로 대응합니다. 초기 대응의 우선순위는 원인 규명보다 고객 영향 확산 방지와 안전한 복구입니다.

기본 대응 흐름은 다음과 같습니다.

1. 장애 발생 시각과 최초 탐지 경로 확인
2. 영향을 받는 고객사, 기능, 요청 범위 파악
3. 최근 배포, 설정 변경, 외부 시스템 상태 확인
4. 우회, 기능 제한, 롤백 등 즉시 완화 수단 검토
5. 로그와 지표를 근거로 원인 후보 축소
6. 복구 후 누락·중복·오염 데이터 확인
7. 고객 업무 재처리가 필요한 항목 식별
8. 원인, 영향, 대응, 재발 방지 조치 기록

주니어는 담당자의 지시에 따라 로그 수집, 재현, 검증, 복구 확인을 수행합니다. 시니어는 상황을 지휘하고, 변경 승인과 위험 판단을 수행하며, 관련 부서에 기술 상태를 명확하게 전달합니다.

장애 대응 과정에서 운영 데이터를 임의로 수정하거나 검증 없이 서비스를 반복 재시작하지 않습니다. 긴급 조치도 실행자, 시각, 대상, 결과를 기록해야 합니다.

## 보안과 접근 제어
<!--meta: sec=s17; dept=BE; level=주니어|시니어; ct_band=중; related=s5|s8|s16|s20-->
백엔드 개발자는 인증된 사용자가 허용된 기능과 데이터에만 접근하도록 서버 측 통제를 구현합니다. 화면에서 버튼을 숨기는 것은 접근 제어가 아니며 모든 권한 검증은 신뢰 가능한 서버 영역에서 수행해야 합니다.

기본 보안 책임은 다음과 같습니다.

- 사용자·서비스 계정의 인증 결과 검증
- 역할과 고객사 범위에 따른 권한 확인
- 고객사별 데이터가 섞이지 않도록 조회 조건 강제
- 인증정보와 비밀키를 소스코드에 저장하지 않기
- 입력값을 신뢰하지 않고 형식과 범위를 검증
- 파일 업로드 시 확장자, 크기, 저장 위치 제한
- 오류 응답에 내부 경로와 스택 정보를 노출하지 않기
- 로그와 응답에서 민감정보 마스킹
- 의존성 보안 업데이트와 취약점 영향 확인
- 불필요한 관리용 엔드포인트와 디버그 기능 비활성화

고객사 환경에 접근할 때는 승인된 계정과 접속 방식을 사용합니다. 개발 편의를 위해 운영 데이터를 개인 장비나 승인되지 않은 외부 서비스로 이동하지 않습니다.

## 배포와 변경 관리
<!--meta: sec=s18; dept=BE; level=주니어|시니어; ct_band=중; related=s7|s13|s14|s20-->
배포는 코드 병합 이후의 단순 실행 단계가 아니라 변경 위험을 관리하는 과정입니다. 개발자는 변경 내용, 적용 대상, 사전 조건, 검증 방법, 되돌리기 방법을 설명할 수 있어야 합니다.

배포 준비 항목은 다음과 같습니다.

- 자동화 테스트와 정적 검사 결과 확인
- 환경별 설정값과 비밀정보 주입 방식 확인
- 데이터베이스 스키마 변경의 선후 관계 확인
- 이전 버전과 동시에 실행될 때의 호환성 검토
- 배포 중 처리 중인 요청과 작업 큐 영향 검토
- 배포 직후 확인할 API와 운영 지표 정의
- 실패 시 롤백 가능 여부와 데이터 복구 방법 확인
- 고객사 연동 변경 시 적용 일정과 상대 시스템 준비 상태 확인
- 운영 문서와 API 명세의 동시 갱신
- 변경 담당자와 확인 담당자의 역할 구분

위험도가 높은 변경은 작은 범위에서 먼저 검증하거나 기능 활성화 시점을 분리하는 방식을 고려합니다. 데이터 변환처럼 단순 롤백이 어려운 작업은 사전 백업과 검증 쿼리, 중단 기준을 별도로 준비합니다.

## 협업 방식
<!--meta: sec=s19; dept=BE; level=주니어|시니어; ct_band=하; related=s1|s5|s21-->
백엔드 개발자는 여러 부서의 요구를 기술적으로 연결합니다. 협업에서는 상대 부서의 요청을 그대로 구현하기보다 목표, 사용자, 데이터 출처, 완료 기준, 운영 주체를 확인합니다.

부서별 주요 협업 내용은 다음과 같습니다.

- 컨설팅팀: 고객 업무 흐름, 요구사항 우선순위, 적용 범위 확인
- AI/AX개발팀: 모델 호출 규격, 실행 조건, 오류 유형, 버전 전환 협의
- 데이터분석팀: 데이터 정의, 집계 기준, 조회 요구사항, 결과 전달 방식 협의
- 영업팀: 제안 범위와 기술 가능성, 구축 전제조건, 일정 위험 공유
- 백엔드팀 내부: API 규칙, 공통 모듈, 운영 표준, 코드리뷰 수행

기술적 제약을 설명할 때는 “불가능하다”는 결론만 전달하지 않고 제약의 원인, 가능한 대안, 일정·비용·품질에 미치는 영향을 함께 제시합니다. 회의 결과는 결정 사항, 미결 사항, 담당자, 확인 기한으로 구분해 기록합니다.

## 문서화 책임
<!--meta: sec=s20; dept=BE; level=주니어|시니어; ct_band=하; related=s14|s16|s17|s18-->
백엔드 개발자가 작성하는 문서는 코드를 대체하기 위한 것이 아니라 개발, 검증, 배포, 운영 과정에서 필요한 판단 정보를 보존하기 위한 것입니다.

기본 문서화 대상은 다음과 같습니다.

- API 경로, 요청값, 응답값, 오류 코드
- 외부 시스템 연동 조건과 인증 방식
- 환경별 설정 항목과 필수값
- 데이터베이스 주요 테이블과 상태값
- 배치 실행 조건과 재실행 방법
- 운영 지표와 경보 발생 시 확인 절차
- 배포 순서와 롤백 방법
- 알려진 제한사항과 임시 조치
- 장애 대응 결과와 후속 작업
- 주요 아키텍처 결정의 배경과 대안 검토 내용

문서는 독자가 개발자 본인에게 직접 질문하지 않아도 기본 작업을 수행할 수 있는 수준을 목표로 합니다. 단, 비밀번호·토큰·개인정보와 같은 민감한 값은 문서에 직접 기록하지 않습니다.

## 직급 및 경력 단계별 기대 역할
<!--meta: sec=s21; dept=BE; level=사원|대리|과장|차장|부장; ct_band=중; related=s3|s19|s22-->
헤드헌터랩의 직급 체계는 사원-대리-과장-차장-부장이며, 실무 경력 기준으로 0~3년을 주니어, 4년 이상을 시니어로 구분합니다. 직급과 경력 구분은 책임 범위를 판단하는 기준 중 하나이며 실제 역할은 프로젝트 난이도와 역량에 따라 조정될 수 있습니다.

| 구분 | 일반적인 기대 역할 |
|---|---|
| 사원 | 정해진 명세에 따른 API 구현, 단위 테스트, 로그 확인, 문서 갱신 |
| 대리 | 기능 단위 설계, 외부 연동 구현, 배포 준비, 코드리뷰 참여 |
| 과장 | 서비스 단위 설계, 일정·위험 관리, 장애 원인 분석, 주니어 지원 |
| 차장 | 복수 시스템 아키텍처 조정, 중요 장애 대응 리드, 기술 표준 개선 |
| 부장 | 조직 기술 방향, 대형 프로젝트 위험 통제, 대외 기술 의사결정 지원 |

주니어에게는 질문 없이 모든 문제를 독립적으로 해결하는 능력보다 문제를 작게 나누고, 막힌 지점을 근거와 함께 공유하며, 리뷰 내용을 다음 작업에 반영하는 역량을 기대합니다.

시니어에게는 직접 구현 능력과 함께 설계의 장단점을 설명하고, 운영 위험을 예측하며, 구성원이 일관된 품질로 일할 수 있도록 기준을 만드는 역할을 기대합니다.

## 입사 후 초기 업무 범위
<!--meta: sec=s22; dept=BE; level=주니어|시니어; ct_band=하; related=s21|s23|s24-->
입사 초기에는 내부 개발 규칙과 운영 환경을 이해한 뒤 점진적으로 담당 범위를 넓힙니다. 실제 배정 업무는 프로젝트 상황과 경력에 따라 달라질 수 있습니다.

초기 적응 과정에서 다루는 대표 항목은 다음과 같습니다.

- 로컬 개발 환경과 의존성 구성
- 저장소 구조, 브랜치, 리뷰, 병합 절차 이해
- 공통 API 응답과 예외 처리 규칙 확인
- 개발·검증·운영 환경의 차이 이해
- 기존 서비스의 요청 흐름과 주요 데이터 구조 파악
- 로그 검색과 기본 모니터링 화면 사용
- 작은 오류 수정 또는 조회 API 개선
- 테스트 추가와 개발 문서 보완
- 배포 전 점검 및 배포 후 상태 확인 참여
- 담당 서비스의 운영 문의 대응 관찰

주니어는 리뷰 가능한 작은 작업부터 시작하며, 시니어는 초기 구조 파악 이후 설계 검토와 운영 위험 개선 업무를 함께 맡을 수 있습니다.

## 성과 판단 기준
<!--meta: sec=s23; dept=BE; level=주니어|시니어; ct_band=중; related=s15|s21|s22-->
백엔드 개발자의 성과는 작성한 코드 줄 수나 완료한 기능 수만으로 판단하지 않습니다. 기능의 정확성, 운영 안정성, 변경 용이성, 협업 기여를 함께 봅니다.

대표적인 판단 기준은 다음과 같습니다.

- 요구사항과 예외 조건을 정확히 반영했는가
- 테스트와 리뷰를 거쳐 예측 가능한 품질로 배포했는가
- 장애와 오류를 관찰할 수 있는 정보를 제공했는가
- 변경으로 인한 기존 기능 영향과 호환성을 검토했는가
- 반복되는 수작업이나 오류 원인을 구조적으로 줄였는가
- 일정 위험과 기술 제약을 늦지 않게 공유했는가
- 장애 발생 시 사실을 기반으로 대응하고 후속 조치를 완료했는가
- 다른 구성원이 유지보수할 수 있도록 코드와 문서를 남겼는가
- 리뷰 의견을 수용하고 본인의 기술 판단도 근거 있게 설명했는가
- 프로젝트 종료 이후에도 운영 가능한 상태를 만들었는가

시니어는 개인 산출물 외에도 팀의 개발 속도와 품질을 높인 기여, 중요한 기술 의사결정, 후배 개발자의 성장 지원을 추가로 평가합니다.

## 기술 면접에서 확인하는 역량
<!--meta: sec=s24; dept=BE; level=주니어|시니어; ct_band=중; related=s3|s6|s11|s16-->
기술 면접에서는 특정 답안을 암기했는지보다 경험한 문제를 어떤 기준으로 분석하고 해결했는지 확인합니다. 지원자가 실제로 담당한 범위와 팀이 담당한 범위를 구분해 설명하는 것이 중요합니다.

주요 확인 영역은 다음과 같습니다.

- 하나의 API 요청이 서버와 데이터베이스를 거쳐 응답되는 과정
- 잘못된 입력과 서버 내부 오류를 구분하는 방식
- 외부 API가 느리거나 실패할 때의 처리 방법
- 중복 요청으로 같은 업무가 두 번 실행되는 것을 막는 방법
- 데이터베이스 인덱스가 필요한 상황과 주의점
- 트랜잭션 범위를 정할 때 고려한 요소
- 비동기 작업을 적용한 이유와 실패 처리 방식
- 배포 후 오류를 탐지하고 이전 상태로 복구하는 방법
- 로그에 포함해야 할 정보와 포함하면 안 되는 정보
- 본인이 경험한 장애 또는 성능 문제의 재현·분석 과정
- 코드리뷰에서 의견이 달랐을 때 합의한 방식
- 일정이 촉박한 상황에서 품질과 범위를 조정한 기준

주니어에게는 기본 개념과 학습 방식, 구현 과정의 정확성을 중점적으로 확인합니다. 시니어에게는 여러 대안의 비교, 장애 시나리오, 운영 비용, 조직 차원의 재발 방지까지 질문할 수 있습니다.

## 직무 수행 예시
<!--meta: sec=s25; dept=BE; level=주니어|시니어; ct_band=중; related=s2|s8|s9|s19-->
백엔드 개발자가 수행할 수 있는 일반적인 업무 예시는 다음과 같습니다. 이는 특정 고객사 프로젝트의 상세 구조가 아니라 직무 범위를 설명하기 위한 예시입니다.

### 예시 1: AI 기능 호출 API 추가

1. AI/AX개발팀과 입력·출력 형식을 확인합니다.
2. 요청 데이터의 필수값과 허용 범위를 정의합니다.
3. 모델 호출 제한 시간과 오류 변환 규칙을 정합니다.
4. API와 테스트를 구현합니다.
5. 호출 시간, 성공 여부, 오류 유형을 관측할 수 있게 합니다.
6. 검증 환경에서 정상·오류 조건을 확인한 뒤 배포합니다.

### 예시 2: 고객사 CRM 연동 추가

1. 인증 방식과 호출 가능 네트워크를 확인합니다.
2. 고객사 필드와 내부 필드의 매핑표를 작성합니다.
3. 레이트리밋과 타임아웃 조건을 반영합니다.
4. 전송 실패 시 재시도와 최종 실패 처리 방식을 구현합니다.
5. 중복 전송이 고객 업무를 반복 실행하지 않도록 식별자를 관리합니다.
6. 운영자가 실패 건을 확인하고 재처리할 수 있는 절차를 문서화합니다.

### 예시 3: 장시간 파일 처리 비동기화

1. 동기 요청에서 처리하기 어려운 이유를 측정합니다.
2. 파일 접수와 실제 처리를 분리합니다.
3. 작업 상태와 결과 조회 인터페이스를 제공합니다.
4. 워커 실패와 재시작 조건을 검증합니다.
5. 최종 실패 작업을 확인할 수 있도록 격리합니다.
6. 대기 시간과 실패율에 대한 운영 경보를 구성합니다.

## 직무에서 자주 사용하는 용어
<!--meta: sec=s26; dept=BE; level=주니어|시니어; ct_band=하; related=s6|s9|s11|s15-->
- **API**: 서로 다른 프로그램이 정해진 규칙에 따라 기능과 데이터를 주고받는 인터페이스입니다.
- **엔드포인트**: API가 요청을 받는 주소와 메서드의 조합입니다.
- **RDB**: 테이블과 관계를 중심으로 데이터를 관리하는 관계형 데이터베이스입니다.
- **트랜잭션**: 여러 데이터 변경을 하나의 논리적 작업으로 처리하는 단위입니다.
- **메시지 큐**: 처리할 작업이나 이벤트를 생산자와 소비자 사이에 보관하는 구성요소입니다.
- **비동기 처리**: 요청한 작업의 완료를 즉시 기다리지 않고 별도 실행 흐름에서 처리하는 방식입니다.
- **배치**: 정해진 범위의 작업을 일정 또는 조건에 따라 묶어서 실행하는 방식입니다.
- **멱등성**: 같은 요청을 여러 번 실행해도 최종 결과가 한 번 실행한 것과 같도록 하는 성질입니다.
- **타임아웃**: 정해진 시간 안에 작업이 끝나지 않으면 실패로 판단하는 기준입니다.
- **레이트리밋**: 일정 시간 동안 허용하는 요청 수를 제한하는 정책입니다.
- **스키마**: 데이터의 구조, 타입, 관계, 제약조건을 정의한 규칙입니다.
- **인덱스**: 특정 조건의 데이터를 빠르게 찾도록 돕는 데이터베이스 구조입니다.
- **구조화 로그**: 검색과 집계가 쉽도록 필드를 일정한 형식으로 기록한 로그입니다.
- **메트릭**: 요청 수, 오류율, 지연 시간처럼 시간에 따라 측정하는 운영 수치입니다.
- **헬스 체크**: 서비스가 요청을 받을 수 있는 상태인지 확인하는 기능입니다.
- **롤백**: 문제가 발생한 변경을 이전의 안정된 상태로 되돌리는 절차입니다.

## 지원자에게 기대하는 업무 태도
<!--meta: sec=s27; dept=BE; level=주니어|시니어; ct_band=하; related=s13|s19|s23-->
헤드헌터랩은 백엔드 개발자가 불확실한 상황을 숨기지 않고 확인 가능한 문제로 전환하기를 기대합니다. 요구사항이 모호하면 구현부터 시작하기보다 사용자, 입력, 출력, 예외, 완료 기준을 질문해야 합니다.

다음과 같은 태도를 중요하게 봅니다.

- 모르는 내용을 추측으로 확정하지 않고 확인하는 태도
- 오류와 실수를 숨기지 않고 빠르게 공유하는 태도
- 본인의 코드가 운영자와 고객 업무에 미치는 영향을 고려하는 태도
- 단기 우회책과 근본 해결책을 구분하는 태도
- 리뷰를 비판이 아니라 품질을 높이는 협업 과정으로 받아들이는 태도
- 반복되는 문제를 자동화와 표준화로 개선하는 태도
- 기술 용어를 비개발 직군이 이해할 수 있는 언어로 설명하는 태도
- 본인의 담당 범위를 넘어선 문제도 적절한 담당자와 연결하는 태도

완벽한 사전 지식보다 근거를 찾고, 검증하고, 기록하며, 같은 문제가 반복되지 않게 개선하는 능력을 중요하게 평가합니다.

## 직무 성장 방향
<!--meta: sec=s28; dept=BE; level=주니어|시니어; ct_band=상; related=s21|s23|s24-->
백엔드 개발자는 경험과 강점에 따라 여러 방향으로 성장할 수 있습니다.

- **서비스 백엔드 전문가**: API 설계, 도메인 모델링, 트랜잭션과 서비스 구조에 집중
- **연동 아키텍트**: 고객사 시스템, 인증, 네트워크, 메시징, 데이터 교환 구조에 집중
- **플랫폼 엔지니어**: 배포 표준, 공통 모듈, 관측 체계, 개발 생산성 개선에 집중
- **데이터 처리 백엔드 전문가**: 대량 작업, 스케줄링, 작업 큐, 데이터 품질 제어에 집중
- **테크 리드**: 시스템 설계, 기술 의사결정, 위험 관리, 구성원 성장을 함께 담당
- **기술 관리 역할**: 복수 프로젝트의 인력·품질·일정·운영 책임을 조정

성장은 관리 직급으로의 승진만을 의미하지 않습니다. 특정 기술 영역에서 조직이 반복적으로 의존할 수 있는 전문성을 확보하고, 그 지식을 표준과 문서로 확산하는 것도 중요한 성장 경로입니다.
