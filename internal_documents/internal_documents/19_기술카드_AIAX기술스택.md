# AI/AX 기술스택 카드
<!--meta: doc=TECH-01; doc_type=tech_card; tier=1; topic=TECH; disclosure=internal; status=active-->

## 개요
<!--meta: sec=s1; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->

헤드헌터랩이 고객사 프로젝트에 공통으로 쓰는 기술 스택을 영역별로 정리합니다. 채점 근거용 문서이며, 질문 생성에는 직접 쓰지 않습니다.

본 카드는 특정 고객사의 상세 아키텍처나 프로젝트 수행 이력을 설명하는 문서가 아니다. 기술 면접 및 역량 검토 과정에서 지원자가 언급한 기술의 적용 범위, 설계 관점, 운영 이해도를 일관되게 해석하기 위한 내부 기준으로 사용한다.

헤드헌터랩은 서울·경기·인천 3개 지점에서 컨설팅과 개발을 모두 수행하므로, 지점별로 기술을 임의 선정하기보다 다음 공통 원칙을 적용한다.

- 고객사 보안 정책과 구축 환경을 우선한다.
- 클라우드, 온프레미스, 폐쇄망 중 하나만을 기본값으로 가정하지 않는다.
- 오픈소스와 상용 제품은 기능뿐 아니라 운영 인력, 라이선스, 장애 대응 체계까지 비교한다.
- 모델 정확도와 시스템 안정성을 별도 지표로 관리한다.
- 기술 도입 자체보다 데이터 흐름, 실패 처리, 관측 가능성, 변경 가능성을 중시한다.
- 시범 구축 단계와 운영 전환 단계의 기술 기준을 구분한다.
- 프로젝트 종료 후 고객사 운영 조직이 인수할 수 있는 수준의 문서화와 표준화를 요구한다.

이 문서에서 말하는 “공통 기술 스택”은 모든 프로젝트에 동일 제품을 강제한다는 의미가 아니다. 동일한 문제를 해결할 때 우선 검토하는 기술군과 평가 기준을 뜻한다.

## 기술 스택 분류 기준
<!--meta: sec=s2; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->

기술은 다음 다섯 계층으로 구분한다.

| 계층 | 주요 범위 | 핵심 검토 항목 |
|---|---|---|
| 데이터 계층 | 원천 데이터, 저장소, 정제, 품질 관리 | 정합성, 보존 기간, 접근 통제 |
| 모델 계층 | LLM, 임베딩, OCR, 예측 모델 | 정확도, 재현성, 추론 비용 |
| 애플리케이션 계층 | API, 업무 규칙, 사용자 기능 | 계약 안정성, 예외 처리, 확장성 |
| 자동화 계층 | RPA, 배치, 워크플로 | 재실행, 중복 방지, 작업 추적 |
| 운영 계층 | 배포, 모니터링, 보안, 감사 | 가용성, 복구성, 변경 이력 |

기술 숙련도는 단순 사용 경험이 아니라 다음 단계로 판단한다.

1. **사용 단계:** 도구의 기본 기능을 설명하고 정해진 절차에 따라 사용할 수 있다.
2. **구성 단계:** 요구사항에 맞게 주요 옵션과 연결 방식을 설정할 수 있다.
3. **설계 단계:** 대안을 비교하고 제약 조건에 맞는 구조를 선택할 수 있다.
4. **운영 단계:** 성능 저하, 데이터 오류, 비용 증가, 장애 상황을 진단할 수 있다.
5. **개선 단계:** 측정 결과를 바탕으로 구조를 변경하고 변경 효과를 검증할 수 있다.

제품명만 나열하거나 튜토리얼 수준의 구현 경험만 설명하는 경우에는 해당 기술의 운영 역량이 확인된 것으로 보지 않는다.

## 기술 선정 공통 원칙
<!--meta: sec=s3; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=none-->

기술 선정 시 기능 적합성 외에 총소유비용과 운영 위험을 함께 평가한다. 평가표는 프로젝트 특성에 따라 가중치를 조정하되, 아래 항목 자체는 생략하지 않는다.

| 평가 영역 | 확인 질문 | 대표 증빙 |
|---|---|---|
| 요구 적합성 | 필수 기능을 우회 구현 없이 제공하는가 | 기능 검증 결과 |
| 성능 | 목표 처리량과 지연시간을 만족하는가 | 부하 시험 결과 |
| 안정성 | 실패 시 데이터 유실과 중복을 통제할 수 있는가 | 실패 주입 시험 |
| 보안 | 인증, 권한, 암호화, 감사 요건을 충족하는가 | 보안 점검표 |
| 운영성 | 모니터링, 백업, 복구, 업그레이드가 가능한가 | 운영 절차서 |
| 이식성 | 특정 공급자 종속이 허용 가능한 수준인가 | 대체안 비교표 |
| 비용 | 개발비와 운영비를 함께 예측할 수 있는가 | 용량별 비용 추정 |
| 인력 | 사내 또는 고객사에서 운영 가능한 역량이 있는가 | 인수인계 계획 |
| 생태계 | 장기 지원, 보안 패치, 커뮤니티가 안정적인가 | 지원 정책 검토 |
| 규제 대응 | 데이터 위치와 보존 요건을 지킬 수 있는가 | 데이터 흐름도 |

신규 기술은 개념검증에서 성공했다는 이유만으로 운영 표준에 편입하지 않는다. 최소한 정상 처리, 저품질 입력, 외부 시스템 지연, 재시작, 데이터 증가, 버전 변경 상황을 검증한 뒤 채택 여부를 결정한다.

## LLM·RAG (콜센터 AI 상담)
<!--meta: sec=s4; dept=AIAX; level=주니어|시니어; ct_band=중; related=none-->

LLM API 또는 자체 호스팅 모델 + 벡터DB(임베딩 검색) 조합. 검색 결과 없음 처리, 응답 근거 표시가 핵심 설계 포인트입니다.

일반적인 구성 요소는 다음과 같다.

- 질의 정규화 및 의도 보정
- 문서 분할과 메타데이터 부여
- 임베딩 생성 및 벡터 색인
- 키워드 검색 또는 메타데이터 필터
- 후보 문서 재정렬
- 프롬프트 조립
- LLM 응답 생성
- 근거 문서 연결
- 정책 위반 및 개인정보 출력 검사
- 응답 로그와 품질 피드백 저장

헤드헌터랩은 RAG를 “LLM에 문서를 붙이는 기능”으로만 정의하지 않는다. 검색 실패와 생성 실패를 분리해서 측정할 수 있어야 하며, 검색된 문서가 질문과 관련이 없을 때 답변을 중단하거나 확인 요청으로 전환할 수 있어야 한다.

기본 검토 항목은 다음과 같다.

| 항목 | 확인 내용 |
|---|---|
| 검색 범위 | 사용자·조직·업무별 접근 가능한 문서만 조회되는가 |
| 최신성 | 문서 변경 후 색인 반영 시점이 관리되는가 |
| 근거성 | 최종 응답의 주요 주장과 근거 문서가 연결되는가 |
| 무응답 | 충분한 근거가 없을 때 추측하지 않는가 |
| 일관성 | 동일한 입력에서 허용 범위 내 결과를 내는가 |
| 비용 | 질의당 토큰, 재정렬, 임베딩 비용을 추적하는가 |
| 지연시간 | 검색, 재정렬, 생성 단계별 지연을 분리하는가 |
| 개인정보 | 검색 문맥과 응답에 불필요한 개인정보가 포함되지 않는가 |

## LLM 모델 선택과 실행 방식
<!--meta: sec=s5; dept=AIAX; level=시니어; ct_band=상; related=none-->

LLM은 외부 API형과 자체 호스팅형으로 구분해 검토한다. 어느 한 방식이 항상 우월하다고 판단하지 않으며 데이터 민감도, 응답 지연, 사용량, 모델 변경 가능성, 운영 인력에 따라 결정한다.

### 외부 API형 검토 항목

- 입력 데이터의 저장 및 학습 사용 여부
- 서비스 제공 지역과 데이터 전송 경로
- 호출 제한과 초과 사용 정책
- 모델 버전 고정 또는 자동 변경 여부
- 장애 시 대체 모델 전환 가능성
- 입력·출력 토큰 단가와 부가 기능 비용
- 구조화 출력, 도구 호출, 스트리밍 지원 여부

### 자체 호스팅형 검토 항목

- 모델 크기와 GPU 메모리 요구량
- 양자화 적용 시 품질 저하 범위
- 동시 요청 수와 배치 처리 효율
- 모델 로딩 및 재기동 시간
- GPU 장애 또는 자원 부족 시 대체 경로
- 모델 파일 출처와 라이선스 조건
- 추론 엔진 버전 호환성
- 보안 패치와 모델 교체 절차

모델 평가는 단일 평균 점수만으로 완료하지 않는다. 업무 유형별 정답률, 근거 누락률, 금지 응답률, 무응답 정확도, 응답 형식 준수율을 분리한다. 품질이 비슷하다면 더 작은 모델이나 더 단순한 실행 구조를 우선 검토한다.

## 프롬프트 및 컨텍스트 관리
<!--meta: sec=s6; dept=AIAX; level=주니어|시니어; ct_band=중; related=none-->

프롬프트는 애플리케이션 코드에 흩어져 있는 문자열이 아니라 버전 관리 대상인 운영 자산으로 취급한다.

관리 단위에는 다음 내용이 포함된다.

- 시스템 지시문
- 업무별 답변 원칙
- 금지 행위와 거절 문구
- 검색 문맥 삽입 형식
- 사용자 입력 구분자
- 구조화 출력 스키마
- 예시 입력과 예시 출력
- 모델명과 추론 옵션
- 적용 시작일과 변경 사유
- 품질 평가 결과와 승인자

프롬프트 변경은 문구 수정, 검색 범위 변경, 출력 필드 변경을 각각 구분한다. 출력 스키마 변경은 백엔드와 화면에 영향을 줄 수 있으므로 일반 문구 수정과 동일하게 취급하지 않는다.

긴 컨텍스트를 사용할 수 있다는 이유로 모든 문서를 한 번에 입력하지 않는다. 불필요한 문맥은 비용과 지연시간을 증가시키고, 서로 충돌하는 정보를 모델에 제공할 가능성을 높인다. 컨텍스트 예산은 시스템 지시문, 대화 이력, 검색 문서, 사용자 질의, 출력 여유분으로 나누어 관리한다.

## 임베딩·벡터 검색 기술
<!--meta: sec=s7; dept=AIAX|DATA; level=시니어; ct_band=상; related=none-->

임베딩 모델과 벡터DB는 함께 평가하되 독립적으로 교체할 수 있도록 구성한다. 색인에는 원문 전체보다 검색 단위 텍스트, 문서 식별자, 원문 위치, 권한, 유효 기간, 버전 등의 메타데이터를 저장한다.

주요 설계 항목은 다음과 같다.

- 문서 유형별 분할 길이와 중첩 범위
- 표, 목록, 제목, 각주 보존 방식
- 한국어와 영문 혼합 문서 처리
- 숫자, 코드, 제품명과 같은 고유 토큰 보존
- 유사도 기준값과 최대 후보 수
- 근사 최근접 탐색 방식
- 키워드 검색과 벡터 검색의 결합 비율
- 메타데이터 사전 필터와 사후 필터 구분
- 문서 삭제 시 색인 삭제 보장
- 임베딩 모델 교체 시 재색인 전략

검색 평가는 최종 답변의 인상 평가로 대체하지 않는다. 대표 질의 집합에 대해 정답 문서가 상위 후보에 포함되는 비율, 무관 문서의 상위 노출 비율, 권한 밖 문서의 노출 여부를 측정한다.

임베딩 모델 변경 시 기존 벡터와 신규 벡터를 같은 공간의 값으로 간주해서는 안 된다. 모델 버전별 별도 색인을 구성하거나 전체 재색인을 수행하며, 전환 기간에는 검색 결과 비교가 가능하도록 모델 버전을 로그에 남긴다.

## 검색 재정렬과 근거 연결
<!--meta: sec=s8; dept=AIAX; level=시니어; ct_band=상; related=none-->

1차 검색은 넓게 후보를 수집하고, 재정렬 단계는 질문과 문서 조각의 직접 관련성을 다시 평가한다. 재정렬 모델을 추가하면 품질이 개선될 수 있지만 지연시간과 비용이 증가하므로 질의 유형에 따라 선택적으로 적용할 수 있다.

근거 연결은 단순히 참고 문서 목록을 마지막에 붙이는 방식으로 끝나지 않는다. 다음 정보가 추적 가능해야 한다.

- 답변 생성에 실제 입력된 문서 조각
- 각 조각의 원문 문서와 위치
- 문서 버전과 색인 시각
- 검색 점수와 재정렬 점수
- 답변에서 해당 근거가 사용된 문장
- 문서 접근 권한 판정 결과

답변의 모든 문장에 인용을 강제할 필요는 없지만, 금액, 기간, 계약 조건, 업무 절차와 같은 사실성 문장은 근거 연결 대상에 포함한다. 서로 다른 문서가 충돌할 때에는 최신성, 승인 상태, 적용 범위를 기준으로 우선순위를 결정하며, 자동 판정이 어렵다면 충돌 사실을 사용자에게 표시한다.

## OCR·문서처리
<!--meta: sec=s9; dept=AIAX; level=주니어|시니어; ct_band=중; related=none-->

OCR 엔진으로 문서를 텍스트화한 뒤, 정해진 항목(계약 조건, 금액 등)을 추출하는 규칙·모델을 함께 씁니다. 스캔 품질이 낮은 문서의 오인식 처리가 주요 과제입니다.

문서처리 파이프라인은 일반적으로 다음 단계로 나눈다.

1. 파일 형식 및 손상 여부 확인
2. 페이지 이미지 변환
3. 회전, 기울기, 노이즈 보정
4. 문서 유형 분류
5. 텍스트와 좌표 추출
6. 표, 문단, 체크박스 등 레이아웃 분석
7. 업무 필드 추출
8. 형식 및 업무 규칙 검증
9. 신뢰도 기준에 따른 자동 승인 또는 수동 검수
10. 결과 저장과 원문 연결

텍스트 인식률이 높아도 필요한 필드가 잘못 추출되면 업무 자동화에 사용할 수 없다. 따라서 문자 단위 정확도와 필드 단위 정확도를 구분하며, 금액·날짜·계약 주체와 같이 오류 영향이 큰 필드는 별도 기준을 적용한다.

## 문서 유형별 OCR 처리 기준
<!--meta: sec=s10; dept=AIAX|DATA; level=주니어|시니어; ct_band=중; related=none-->

| 문서 유형 | 주요 난점 | 권장 처리 |
|---|---|---|
| 정형 서식 | 칸 밀림, 도장 겹침 | 좌표 기반 추출과 값 검증 |
| 반정형 계약서 | 조항 위치 변경, 표현 다양성 | 제목 구조와 의미 기반 추출 병행 |
| 표 중심 문서 | 셀 병합, 페이지 분할 | 레이아웃 분석과 행·열 복원 |
| 팩스·저해상도 스캔 | 번짐, 누락, 기울어짐 | 전처리 후 저신뢰 영역 검수 |
| 사진 촬영 문서 | 원근 왜곡, 그림자 | 원근 보정과 영역별 대비 조정 |
| 혼합 언어 문서 | 언어별 인식률 차이 | 언어 감지 후 모델 분기 |
| 손글씨 포함 문서 | 개인별 필체 차이 | 제한 필드 인식 또는 수동 확인 |

OCR 결과에는 텍스트만 저장하지 않고 페이지 번호, 좌표, 인식 신뢰도, 사용 엔진과 버전을 함께 남긴다. 이를 통해 추출 결과를 원문 화면에 표시하고, 오류가 전처리·인식·필드 추출 중 어느 단계에서 발생했는지 판단할 수 있다.

## 문서 필드 추출과 검증
<!--meta: sec=s11; dept=AIAX|DATA; level=시니어; ct_band=상; related=none-->

문서 필드 추출은 규칙, 통계 모델, 언어 모델을 단독 또는 혼합해 적용한다.

- 정해진 위치와 형식을 가진 값은 좌표 및 정규식 기반 처리를 우선한다.
- 표현이 다양하지만 후보 범위가 제한된 값은 분류 모델이나 개체명 인식을 검토한다.
- 문맥 해석이 필요한 조항은 언어 모델을 사용할 수 있으나 원문 인용과 검증 규칙을 함께 둔다.
- 중요 필드는 두 방식의 결과를 비교하거나 업무 시스템의 기준정보와 대조한다.

대표 검증 규칙은 다음과 같다.

- 날짜의 실제 존재 여부와 시작일·종료일 순서
- 공급가액, 세액, 합계의 산술 관계
- 사업자번호나 계좌번호의 형식
- 계약 주체와 서명·날인 주체의 일치 여부
- 통화 단위와 금액 표기의 일관성
- 필수 조항 존재 여부
- 동일 문서 내 반복 표기의 상호 일치 여부

신뢰도가 기준보다 낮거나 검증 규칙을 통과하지 못한 결과는 임의 보정하지 않고 검수 대상으로 전환한다. 검수자가 수정한 값은 모델 개선용 데이터와 운영 확정값을 구분해 저장한다.

## 데이터분석·예측 모델링
<!--meta: sec=s12; dept=DATA; level=주니어|시니어; ct_band=중; related=none-->

시계열 예측 모델(계절성·프로모션 변수 포함) + 배치 파이프라인. 예측 오차(MAPE) 모니터링이 핵심입니다.

예측 모델은 데이터 빈도, 예측 구간, 품목 수, 외부 변수, 결측 패턴에 따라 선택한다. 단순 기준 모델을 먼저 수립하고 복잡한 모델이 기준 모델보다 안정적으로 개선되는지 확인한다.

대표 기술군은 다음과 같다.

- 이동평균 및 계절성 기준 모델
- 지수평활 계열
- 자기회귀 계열
- 트리 기반 회귀 모델
- 부스팅 기반 모델
- 딥러닝 시계열 모델
- 여러 모델의 앙상블
- 계층형 또는 다변량 예측

MAPE는 해석이 쉽지만 실제값이 0이거나 매우 작을 때 왜곡될 수 있다. 데이터 특성에 따라 MAE, RMSE, WAPE, 편향 지표를 함께 본다. 전체 평균만 확인하지 않고 기간, 지역, 상품군, 예측 거리별로 분리한다.

## 데이터 준비와 특징 관리
<!--meta: sec=s13; dept=DATA; level=주니어|시니어; ct_band=중; related=none-->

모델 입력 데이터는 원천 데이터, 정제 데이터, 학습용 특징 데이터로 구분한다. 정제 과정에서 누락값을 0으로 변환하거나 이상값을 제거할 경우 업무 의미를 확인해야 한다. 판매가 없었던 경우와 데이터가 수집되지 않은 경우는 동일한 0으로 취급하지 않는다.

시계열 특징의 예시는 다음과 같다.

- 요일, 주차, 월, 분기
- 공휴일 전후 여부
- 계절과 기상 구간
- 프로모션 종류와 기간
- 가격 및 할인율
- 최근 판매량의 지연값
- 이동 평균과 이동 편차
- 재고 부족 여부
- 신규 또는 단종 상태
- 지역 및 상품 계층 정보

특징 생성 시 미래 정보를 실수로 사용하는 데이터 누수를 방지한다. 학습 시점에 알 수 없었던 확정 실적, 사후 수정값, 미래 집계값은 입력에 포함하지 않는다.

특징 정의에는 계산식, 데이터 출처, 갱신 주기, 결측 처리, 책임 부서를 기록한다. 동일한 이름의 특징이 학습과 운영 환경에서 서로 다른 방식으로 계산되지 않도록 공통 정의를 사용한다.

## 모델 학습·검증 원칙
<!--meta: sec=s14; dept=DATA|AIAX; level=시니어; ct_band=상; related=none-->

시계열 데이터는 임의 섞기 방식의 검증을 기본으로 사용하지 않는다. 시간 순서를 유지한 학습·검증 분리 또는 이동 창 검증을 적용한다.

검증 시 확인할 항목은 다음과 같다.

- 기준 모델 대비 개선 폭
- 예측 기간이 길어질 때의 오차 변화
- 특정 상품군 또는 지역의 편향
- 프로모션 기간과 비프로모션 기간의 차이
- 결측 또는 이상값 구간의 민감도
- 데이터 수정 후 재학습 결과의 변동
- 모델 초기화 값에 따른 결과 편차
- 학습 시간과 추론 자원
- 설명 가능한 주요 영향 변수
- 운영 데이터에서 재현 가능한 전처리 여부

모델 성능이 개선되더라도 처리 시간이 배치 허용 시간을 초과하거나 운영 환경에서 필요한 라이브러리를 사용할 수 없다면 채택하지 않는다. 후보 모델은 정확도, 안정성, 비용, 설명 가능성, 유지보수성을 종합해 선택한다.

## 모델 레지스트리와 생명주기
<!--meta: sec=s15; dept=AIAX|DATA; level=시니어; ct_band=상; related=none-->

학습 완료 파일을 공유 폴더에 저장하는 것만으로 모델 관리가 완료된 것으로 보지 않는다. 운영 후보 모델은 최소한 다음 정보를 가진다.

- 모델 식별자와 버전
- 학습 코드 버전
- 학습 데이터 기준 시점
- 입력 특징 목록과 정의 버전
- 사용 라이브러리와 실행 환경
- 평가 데이터와 평가 결과
- 알려진 한계와 적용 제외 범위
- 승인 상태
- 배포 이력
- 이전 모델로의 복구 가능 여부

모델 상태는 실험, 검증, 승인, 운영, 중단, 보관으로 구분할 수 있다. 운영 모델을 교체할 때에는 파일만 바꾸지 않고 입력 스키마, 전처리, 임계값, 후처리 규칙을 하나의 배포 단위로 관리한다.

재학습은 일정 주기만으로 실행하지 않을 수 있다. 데이터 분포 변화, 오차 증가, 신규 범주 발생, 업무 정책 변경을 재학습 조건으로 사용할 수 있다. 자동 재학습 결과를 검증 없이 즉시 운영 반영하는 방식은 원칙적으로 지양한다.

## RPA 연동
<!--meta: sec=s16; dept=BE; level=주니어|시니어; ct_band=중; related=none-->

반복 업무(데이터 입력, 보고서 생성 등)를 RPA 도구로 자동화하고, 고객사 기존 시스템과는 API 또는 화면 자동화로 연동합니다.

연동 방식은 다음 우선순위로 검토한다.

1. 공식 API
2. 파일 교환 또는 관리된 데이터 연계
3. 메시지 또는 이벤트 기반 연계
4. 데이터베이스 연계
5. 화면 자동화

화면 자동화는 대상 시스템 변경에 취약하므로 API 사용이 불가능한 경우에 제한적으로 선택한다. 좌표 클릭보다 안정적인 요소 식별자를 사용하고, 화면 해상도·팝업·세션 만료·처리 지연을 고려한다.

RPA 작업에는 실행 ID를 부여하며 시작, 종료, 처리 건수, 실패 단계, 재시도 횟수를 기록한다. 자동화가 실패했을 때 사람이 어느 단계부터 이어서 처리할 수 있는지 정의해야 한다.

## RPA 작업 안정성 기준
<!--meta: sec=s17; dept=BE; level=시니어; ct_band=상; related=none-->

RPA는 정상 경로보다 예외 경로 설계가 중요하다. 다음 상황을 기본 시험 범위에 포함한다.

- 로그인 실패 또는 비밀번호 만료
- 다중 인증 요청
- 대상 시스템 점검 화면
- 예상하지 못한 팝업
- 입력 데이터 형식 오류
- 동일 건의 중복 처리
- 파일 다운로드 지연
- 브라우저 또는 애플리케이션 강제 종료
- 네트워크 단절 후 재연결
- 작업 중간 단계에서의 서버 재시작

중복 실행이 금전, 주문, 승인 상태에 영향을 줄 수 있는 작업에는 업무 키를 이용한 중복 방지 장치를 둔다. 재시도 가능 오류와 사람 확인이 필요한 오류를 구분하며, 무제한 자동 재시도를 허용하지 않는다.

로봇 계정은 개인 계정을 공유해서 사용하지 않는다. 계정별 허용 업무와 접근 시스템을 제한하고, 비밀번호나 인증 정보는 소스 코드와 작업 파일에 평문으로 저장하지 않는다.

## 백엔드 API 기술
<!--meta: sec=s18; dept=BE; level=주니어|시니어; ct_band=중; related=none-->

백엔드 API는 AI 모델, 데이터 파이프라인, 고객사 업무 시스템 사이의 계약 역할을 한다. 구현 언어나 프레임워크보다 입력·출력 계약과 실패 처리의 명확성을 우선한다.

공통 설계 항목은 다음과 같다.

- 자원과 행위를 구분한 API 경로
- 요청 및 응답 스키마
- 필수값, 허용 범위, 문자열 길이 검증
- 인증과 권한 확인
- 요청 추적 ID
- 중복 요청 방지 키
- 시간 제한과 취소 처리
- 오류 코드와 사용자 메시지 분리
- 버전 변경 정책
- 페이지네이션과 정렬 기준
- 대용량 파일의 별도 전송 방식

AI 추론처럼 처리 시간이 긴 기능은 일반 조회 API와 동일한 시간 제한을 적용하기 어렵다. 예상 처리 시간에 따라 동기 응답, 스트리밍, 비동기 작업 조회 방식 중 하나를 선택한다.

외부에 노출되는 오류 메시지에는 내부 서버 주소, 파일 경로, SQL 문장, 모델 프롬프트 등 운영 정보를 포함하지 않는다.

## 비동기 처리·메시징
<!--meta: sec=s19; dept=BE|AIAX; level=시니어; ct_band=상; related=none-->

처리량 변동이 크거나 즉시 완료할 필요가 없는 작업은 메시지 큐 또는 작업 큐를 검토한다. 대표 대상은 문서 변환, 임베딩 생성, 대량 추론, 보고서 생성, 외부 시스템 전송이다.

메시지 기반 구조에서 확인할 사항은 다음과 같다.

- 적어도 한 번 전달과 정확히 한 번 처리의 차이
- 소비자 재시작 후 재처리 범위
- 메시지 순서 보장 필요성
- 처리 실패 메시지의 격리
- 재시도 횟수와 간격
- 메시지 보존 기간
- 메시지 크기 제한
- 민감정보 포함 여부
- 생산자와 소비자의 스키마 호환성
- 처리 지연과 적체량 모니터링

메시지가 한 번만 전달된다고 가정하지 않는다. 소비자는 동일 메시지가 다시 들어와도 결과가 중복 생성되지 않도록 멱등성을 고려한다. 대용량 원문을 메시지에 직접 넣기보다 접근 통제된 저장소 위치와 식별자를 전달하는 방식을 우선 검토한다.

## 데이터 저장소 선택
<!--meta: sec=s20; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=none-->

저장소는 데이터 형태와 접근 패턴에 맞게 선택한다.

| 저장소 유형 | 적합한 용도 | 주요 주의점 |
|---|---|---|
| 관계형 DB | 거래 데이터, 상태 관리, 기준정보 | 스키마 변경과 인덱스 관리 |
| 문서형 DB | 가변 구조의 JSON 문서 | 일관성 및 질의 패턴 |
| 키-값 저장소 | 캐시, 세션, 짧은 상태 | 만료와 원본 데이터 구분 |
| 객체 저장소 | 원문 파일, 모델 파일, 대용량 결과 | 접근 권한과 수명주기 |
| 분석 저장소 | 대규모 집계와 분석 질의 | 적재 지연과 비용 |
| 벡터DB | 임베딩 유사도 검색 | 재색인과 권한 필터 |
| 시계열 저장소 | 시간 순 측정값과 지표 | 보존 기간과 집계 단위 |

데이터를 여러 저장소에 복제할 경우 어느 저장소가 원본인지 정한다. 캐시나 검색 색인을 원본으로 취급하지 않으며, 원본 변경 후 파생 저장소가 갱신되지 않았을 때 이를 탐지할 수 있어야 한다.

저장소 선택 시 초기 데이터 규모만 보지 않고 증가율, 조회 패턴, 삭제 요구, 백업 시간, 복구 시간을 함께 검토한다.

## 캐시 적용 기준
<!--meta: sec=s21; dept=BE|AIAX; level=시니어; ct_band=중; related=none-->

캐시는 반복 조회 비용과 응답 지연을 줄이기 위해 사용하지만, 데이터 불일치 위험을 추가한다. 다음 대상에 적용할 수 있다.

- 변경이 적은 기준정보
- 반복되는 검색 결과
- 동일 입력의 임베딩 결과
- 단기간 재사용되는 모델 결과
- 사용자 세션 정보
- 외부 API의 제한된 조회 결과

캐시 키에는 결과를 바꾸는 입력 조건을 빠짐없이 포함한다. 사용자 권한에 따라 결과가 달라지는 경우 권한 범위를 캐시 키 또는 저장 영역에 반영한다. 그렇지 않으면 다른 사용자의 검색 결과나 문서 정보가 노출될 수 있다.

만료 시간은 데이터 변경 주기와 오류 영향도를 기준으로 정한다. 데이터 갱신 시 즉시 무효화가 필요한지, 일정 시간의 지연을 허용할 수 있는지 업무 부서와 합의한다. 캐시 장애가 전체 서비스 장애로 확대되지 않도록 원본 조회로 우회하거나 제한된 기능으로 전환하는 방식을 마련한다.

## 배치·워크플로 오케스트레이션
<!--meta: sec=s22; dept=DATA|BE|AIAX; level=주니어|시니어; ct_band=중; related=none-->

배치 작업은 단순 예약 실행이 아니라 데이터 기준 시점과 단계 간 의존성을 관리하는 워크플로로 본다.

배치 정의에는 다음 정보가 포함된다.

- 작업명과 업무 목적
- 실행 주기와 기준 시간대
- 입력 데이터 기준 시점
- 선행 작업과 후행 작업
- 예상 처리 시간
- 재시도 가능 여부
- 재실행 단위
- 결과 건수와 품질 검증
- 알림 대상
- 수동 실행 권한
- 완료 시각 요구사항

작업 성공 여부는 프로세스 종료 코드만으로 판단하지 않는다. 입력 건수, 출력 건수, 누락률, 중복률, 기준 합계 등 데이터 검증을 함께 수행한다.

재실행 시 전체 기간을 다시 처리할지 실패 구간만 처리할지 명확히 한다. 동일 기준일 작업을 반복 실행해도 결과가 불필요하게 중복되지 않도록 실행 식별자와 처리 기준일을 분리한다.

## 데이터 품질 관리
<!--meta: sec=s23; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=none-->

데이터 품질은 모델 학습 이전 단계에서만 확인하는 일회성 작업이 아니다. 수집, 변환, 저장, 제공 단계마다 품질 규칙을 배치한다.

주요 품질 차원은 다음과 같다.

| 품질 차원 | 설명 | 예시 |
|---|---|---|
| 완전성 | 필수 값이 존재하는가 | 필수 고객 구분값 누락률 |
| 유효성 | 값이 허용 형식과 범위에 맞는가 | 음수가 될 수 없는 수량 |
| 유일성 | 중복되지 않아야 할 값이 중복되지 않는가 | 거래 식별자 중복 |
| 일관성 | 서로 다른 필드와 시스템의 값이 맞는가 | 합계와 상세 금액 |
| 적시성 | 필요한 시점까지 데이터가 도착하는가 | 일별 마감 시각 |
| 정확성 | 실제 업무 사실과 일치하는가 | 확정 실적 대조 |
| 연속성 | 시계열에 비정상 공백이 없는가 | 시간대별 수집 누락 |

품질 규칙 위반은 경고, 처리 보류, 전체 중단으로 등급을 나눈다. 일부 값의 오류로 전체 작업을 중단할 필요가 없는 경우에는 오류 레코드를 격리하고 정상 건을 처리할 수 있다. 단, 격리된 데이터의 후속 처리 책임과 기한을 명확히 한다.

## 데이터 계보와 메타데이터
<!--meta: sec=s24; dept=DATA|BE|AIAX; level=시니어; ct_band=상; related=none-->

데이터 계보는 최종 보고서나 모델 결과가 어떤 원천과 변환 과정을 거쳤는지 추적하는 정보다. 문제 발생 시 영향 범위를 판단하고 재처리 대상을 결정하는 데 사용한다.

관리 대상은 다음과 같다.

- 원천 시스템과 원천 테이블 또는 파일
- 수집 시각과 데이터 기준 시점
- 변환 작업 식별자
- 적용한 규칙과 코드 버전
- 중간 및 최종 데이터셋
- 모델 입력 데이터셋
- 결과를 소비하는 API와 화면
- 개인정보 포함 여부
- 보존 및 삭제 기준
- 데이터 책임 조직

동일한 이름의 지표가 부서별로 다른 계산식을 갖는 경우 이름만으로 통합하지 않는다. 지표 정의에는 산식, 집계 단위, 포함·제외 조건, 기준 시간대, 확정 시점을 기록한다.

모델 결과에도 계보를 적용한다. 어떤 모델 버전이 어떤 입력 데이터와 특징 버전을 사용해 결과를 생성했는지 추적할 수 있어야 한다.

## 컨테이너·실행 환경
<!--meta: sec=s25; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=none-->

개발, 시험, 운영 환경의 차이를 줄이기 위해 컨테이너 기반 실행을 우선 검토한다. 다만 고객사 인프라 정책에 따라 가상머신 또는 지정 실행 환경을 사용할 수 있다.

컨테이너 이미지 관리 기준은 다음과 같다.

- 검증된 기본 이미지 사용
- 불필요한 패키지 제거
- 고정 가능한 의존성 버전 명시
- 애플리케이션과 모델 파일의 분리 여부 검토
- 비관리자 계정으로 실행
- 이미지 취약점 점검
- 빌드 시각과 소스 버전 기록
- 환경별 설정과 이미지 분리
- 임시 파일과 로그 저장 위치 지정
- 종료 신호 처리 및 정상 종료 시간 확보

이미지에 비밀번호, API 키, 인증서 개인키를 포함하지 않는다. 실행 환경에서 비밀정보를 주입하며, 로그와 오류 화면에 값이 노출되지 않도록 한다.

GPU 기반 실행 환경에서는 드라이버, 가속 라이브러리, 추론 엔진, 모델 형식의 호환성을 함께 관리한다. 단순히 GPU가 존재한다는 사실만으로 모델 실행 가능성을 판단하지 않는다.

## 배포 전략과 변경 관리
<!--meta: sec=s26; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=none-->

배포 단위는 애플리케이션, 모델, 프롬프트, 데이터 스키마, 환경 설정으로 나누어 식별한다. 여러 요소가 함께 변경될 경우 상호 호환되는 버전 조합을 기록한다.

대표 배포 방식은 다음과 같다.

- 전체 교체 배포
- 순차 교체 배포
- 이중 환경 전환
- 일부 사용자 또는 일부 트래픽 대상 배포
- 기존 버전과 신규 버전의 동시 비교
- 기능 플래그를 이용한 단계적 활성화

변경 전에는 영향 범위와 복구 기준을 정의한다. 복구는 이전 애플리케이션 이미지로 되돌리는 것만을 의미하지 않는다. 데이터 스키마 변경, 신규 특징 생성, 색인 변경, 모델 입력 형식 변경은 역방향 호환 여부를 별도로 검토한다.

모델 변경은 일반 코드 배포와 동일한 절차만으로 충분하지 않을 수 있다. 기술적 정상 여부 외에 출력 품질, 금지 응답, 편향, 비용 변화를 확인한다.

## 관측 가능성과 모니터링
<!--meta: sec=s27; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=none-->

모니터링은 로그, 지표, 추적 정보로 구분한다.

### 로그

- 요청 식별자와 작업 식별자
- 처리 단계와 결과 상태
- 오류 유형과 원인 분류
- 모델 및 프롬프트 버전
- 데이터 기준 시점
- 외부 연동 대상과 응답 상태
- 개인정보를 제거한 진단 정보

### 지표

- 요청 수와 성공률
- 응답시간 분포
- 작업 큐 적체량
- CPU, 메모리, GPU 사용률
- 데이터 처리 건수
- 모델 품질 지표
- 검색 무응답률
- 외부 API 오류율
- 단위 요청당 비용

### 추적 정보

- 사용자 요청에서 API, 검색, 모델, 저장소까지의 호출 흐름
- 단계별 소요 시간
- 재시도와 대체 경로
- 비동기 작업의 원요청 연결

평균 응답시간만 사용하지 않고 상위 지연 구간을 함께 본다. 알림은 모든 오류를 즉시 통보하는 방식보다 영향도와 지속 시간을 기준으로 설계한다. 동일 원인의 반복 알림은 묶어서 전달하고, 담당자가 확인해야 할 진단 정보를 함께 제공한다.

## AI 품질 모니터링
<!--meta: sec=s28; dept=AIAX|DATA; level=시니어; ct_band=상; related=none-->

AI 기능은 서버가 정상 응답하더라도 품질 장애가 발생할 수 있다. 따라서 인프라 지표와 별도로 모델 및 응답 품질을 관찰한다.

LLM·RAG 기능의 대표 지표는 다음과 같다.

- 검색 결과 없음 비율
- 정답 문서 상위 포함률
- 근거 없는 주장 비율
- 근거 표시 누락률
- 금지 정보 출력률
- 답변 형식 위반률
- 사용자 재질문 비율
- 상담원 또는 검수자의 수정 비율
- 질의당 토큰 사용량
- 모델별 응답시간과 오류율

OCR 기능의 대표 지표는 다음과 같다.

- 문서 유형 분류 정확도
- 문자 및 단어 인식 정확도
- 필수 필드 추출 성공률
- 중요 필드 오류율
- 자동 승인 비율
- 수동 검수 전환 비율
- 페이지당 처리 시간

예측 기능의 대표 지표는 다음과 같다.

- MAPE 및 보조 오차 지표
- 과대·과소 예측 편향
- 범주별 성능 격차
- 입력 특징 결측률
- 데이터 분포 변화
- 기존 기준 모델 대비 성능 차이

품질 지표의 악화가 확인되면 모델만 원인으로 단정하지 않는다. 원천 데이터, 전처리, 검색 색인, 프롬프트, 업무 정책, 사용자 입력 변화도 함께 확인한다.

기술 영역별 테스트를 분리하면서 전체 업무 흐름에 대한 통합 검증을 수행한다.

| 부하 테스트 | 처리량과 지연시간 한계 확인 |
| 복구 테스트 | 재시작, 재처리, 백업 복구 확인 |
| 보안 테스트 | 권한 우회와 정보 노출 확인 |
| 사용자 검증 | 실제 업무 적합성과 예외 흐름 확인 |

AI 결과는 출력이 완전히 동일해야 하는 테스트와 의미가 허용 범위에 들어와야 하는 테스트를 구분한다. 구조화 출력의 필드, 데이터 형식, 금지 표현은 결정적으로 검증할 수 있으며, 자연어 답변 품질은 평가 데이터셋과 검수 기준을 함께 사용한다.

시험 데이터에는 정상 사례뿐 아니라 빈 입력, 지나치게 긴 입력, 잘못된 파일, 권한 없는 요청, 경계값, 외부 시스템 지연, 중복 요청을 포함한다.

## 보안·개인정보 기본 기술
<!--meta: sec=s30; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=none-->

AI/AX 시스템은 원문 문서, 상담 내용, 업무 데이터 등 민감할 수 있는 정보를 처리한다. 기술 구현 단계에서 다음 통제를 적용한다.

- 전송 구간 암호화
- 저장 데이터 암호화 또는 보호 조치
- 역할 기반 접근 제어
- 최소 권한 계정 발급
- 개발·시험·운영 계정 분리
- 비밀정보 중앙 관리
- 접속 및 변경 이력 기록
- 개인정보 마스킹
- 보존 기간 경과 데이터 삭제
- 백업 데이터의 동일한 접근 통제
- 외부 모델 API 전송 항목 제한
- 운영 로그의 민감정보 제거

개발자가 문제 분석을 위해 운영 원문을 개인 장비로 내려받는 방식을 허용하지 않는다. 시험 환경에서는 비식별 데이터나 생성 데이터를 우선 사용한다.

LLM 입력에 개인정보가 포함될 수 있는 경우 전송 전 탐지·마스킹, 모델 제공자의 데이터 처리 조건, 로그 저장 범위를 확인한다. 프롬프트에 “개인정보를 출력하지 말라”고 지시하는 것만으로 보안 통제가 완료된 것으로 보지 않는다.

## 권한과 테넌트 분리
<!--meta: sec=s31; dept=BE|AIAX; level=시니어; ct_band=상; related=none-->

사용자 인증 후에도 데이터와 기능 단위의 권한 확인이 필요하다. 권한은 화면 표시 여부가 아니라 서버와 검색 계층에서 강제한다.

권한 판정 대상은 다음과 같다.

- 문서 원문 열람
- 검색 색인 접근
- 모델 실행
- 결과 다운로드
- 프롬프트 또는 모델 설정 변경
- 배치 수동 실행
- 검수 결과 확정
- 운영 로그 열람
- 관리자 기능 사용

여러 조직이나 고객 단위를 한 시스템에서 처리할 때에는 테넌트 식별자를 모든 데이터 흐름에 일관되게 적용한다. 캐시, 벡터 검색, 파일 저장소, 비동기 메시지에서도 테넌트 경계를 유지해야 한다.

권한 변경은 신규 요청부터 적용되는지, 이미 생성된 결과와 캐시에도 즉시 적용되는지 정의한다. 문서 권한이 회수된 뒤 기존 검색 색인에서 계속 조회되지 않도록 삭제 또는 필터 갱신 절차를 둔다.

## 비용·용량 관리
<!--meta: sec=s32; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=none-->

AI/AX 시스템 비용은 서버 사양만으로 추정하지 않는다. 사용량과 데이터 증가에 따라 변하는 비용 항목을 분리한다.

- LLM 입력·출력 토큰
- 임베딩 생성과 재색인
- GPU 또는 추론 인스턴스
- OCR 페이지 처리
- 객체 저장소 용량
- 데이터베이스 및 분석 질의
- 네트워크 전송량
- 로그와 모니터링 저장량
- 백업 보존
- 상용 소프트웨어 라이선스
- 운영 인력과 수동 검수 시간

용량 계획에는 평균 사용량뿐 아니라 업무 마감, 대량 문서 등록, 일괄 재색인, 모델 재학습 같은 최고 부하 상황을 포함한다.

비용 최적화는 단순한 자원 축소가 아니다. 검색 후보 수 조정, 컨텍스트 축약, 결과 캐시, 작은 모델 분기, 비동기 처리, 데이터 보존 기간 조정을 검토할 수 있다. 비용을 줄인 뒤 품질과 처리시간이 허용 범위를 유지하는지 재검증한다.

## 환경별 운영 기준
<!--meta: sec=s33; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->

환경은 최소한 개발, 시험, 운영으로 구분한다. 프로젝트에 따라 통합 시험, 사용자 검증, 사전 운영 환경을 추가할 수 있다.

| 환경 | 목적 | 데이터 기준 |
|---|---|---|
| 개발 | 기능 구현과 개발자 검증 | 생성·비식별 데이터 우선 |
| 시험 | 통합 및 품질 검증 | 통제된 시험 데이터 |
| 사용자 검증 | 업무 적합성 확인 | 승인된 대표 데이터 |
| 운영 | 실제 업무 처리 | 운영 권한과 보존 정책 적용 |

환경별 설정은 파일 복사와 수동 수정에 의존하지 않는다. 데이터베이스 주소, 외부 API 주소, 로그 수준, 기능 활성화 상태를 환경 설정으로 분리한다.

운영 환경에서만 발생하는 문제를 줄이기 위해 주요 라이브러리 버전과 실행 방식을 가능한 한 일치시킨다. 단, 운영 비밀정보와 실제 개인정보를 하위 환경에 복제하지 않는다.

## 기술 문서화 기준
<!--meta: sec=s34; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->

기술 문서는 작성 여부보다 최신성과 사용 가능성을 기준으로 관리한다. 최소 문서 세트는 다음과 같다.

- 시스템 구성도
- 데이터 흐름도
- 외부 연동 목록
- API 및 데이터 스키마
- 모델 및 프롬프트 버전 정보
- 배포 절차
- 운영 점검 절차
- 장애 시 확인 순서
- 백업 및 복구 절차
- 권한 목록
- 알려진 제약 사항
- 변경 이력

구성도에는 제품 아이콘만 배치하지 않고 데이터 방향, 호출 주체, 인증 경계, 저장 위치를 표시한다. 운영 절차서는 담당자가 명령을 복사하는 수준을 넘어 실행 전 조건, 정상 결과, 실패 시 조치를 포함해야 한다.

문서의 실제 상태와 시스템 구성이 다르면 문서를 기준으로 운영할 수 없으므로, 주요 변경의 완료 조건에 문서 갱신을 포함한다.

## 기술 부채와 교체 기준
<!--meta: sec=s35; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=none-->

기술 부채는 오래된 기술을 사용한다는 사실 자체가 아니라 변경 비용과 운영 위험이 누적된 상태를 의미한다.

대표 기술 부채는 다음과 같다.

- 지원이 종료된 라이브러리
- 특정 담당자만 이해하는 수동 절차
- 테스트 없이 변경되는 프롬프트
- 원본과 동기화되지 않는 검색 색인
- 스키마가 정의되지 않은 데이터 교환
- 환경별로 다른 수동 설정
- 복구가 검증되지 않은 저장소
- 모델과 전처리 버전의 불일치
- 로그가 없어 원인을 추적할 수 없는 자동화
- 임시 예외 규칙의 장기 사용

교체 여부는 최신 기술이라는 이유만으로 결정하지 않는다. 현재 위험, 유지 비용, 교체 비용, 업무 중단 가능성, 대체 기술의 성숙도를 비교한다. 즉시 교체가 어렵다면 영향 범위를 줄이고 관측 지표를 추가하며 단계적 전환 계획을 수립한다.

## 난이도별 기술 이해 기준
<!--meta: sec=s36; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=하; related=none-->

### 하 난이도

- 기술의 목적과 기본 용어를 설명할 수 있다.
- 정해진 개발·배포 절차를 따를 수 있다.
- 정상 처리와 기본 오류를 구분할 수 있다.
- 로그와 지표의 위치를 알고 필요한 정보를 수집할 수 있다.
- 데이터와 모델, API의 역할 차이를 설명할 수 있다.

### 중 난이도

- 여러 기술 대안을 요구사항에 따라 비교할 수 있다.
- 예외 처리, 재시도, 중복 방지 방식을 설계할 수 있다.
- 품질과 성능 지표를 정의하고 결과를 해석할 수 있다.
- 데이터 스키마와 API 계약을 관리할 수 있다.
- 운영 문제를 단계별로 분리해 진단할 수 있다.

### 상 난이도

- 기능, 비용, 보안, 운영성을 함께 고려해 아키텍처를 결정할 수 있다.
- 모델 품질 저하와 시스템 장애를 구분해 원인을 분석할 수 있다.
- 버전 전환과 복구 전략을 설계할 수 있다.
- 조직과 고객사의 운영 역량을 고려해 기술 복잡도를 조정할 수 있다.
- 장기적인 기술 부채와 공급자 종속 위험을 판단할 수 있다.

난이도는 사용한 제품의 유명도나 모델 크기로 판단하지 않는다. 동일한 기술이라도 단순 호출 경험과 운영 설계 경험은 다른 수준으로 평가한다.

## 적용 제외와 예외 승인
<!--meta: sec=s38; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=none-->

고객사 보안 정책, 지정 제품, 폐쇄망 제약, 기존 시스템 호환성으로 인해 본 카드의 권장 방식을 적용하지 못할 수 있다. 예외 자체를 실패로 판단하지 않지만, 예외 사유와 보완 통제를 기록해야 한다.

예외 기록에는 다음 항목을 포함한다.

- 적용하지 못한 기준
- 업무 및 기술적 사유
- 예상 위험
- 대체 통제
- 적용 범위
- 종료 또는 재검토 조건
- 승인 주체
- 검토 일자

예를 들어 공식 API가 없어 화면 자동화를 선택했다면, 화면 변경 감지, 실패 알림, 수동 처리 절차를 보완 통제로 둘 수 있다. 최신 라이브러리를 사용할 수 없다면 지원 종료 시점, 취약점 대응 방법, 교체 계획을 함께 관리한다.

## 기술 스택 카드 유지관리
<!--meta: sec=s39; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=none-->

본 카드는 특정 제품 버전의 설치 안내서가 아니라 헤드헌터랩의 공통 기술 판단 기준이다. 다음 상황에서 내용을 검토한다.

- 주요 기술의 장기 지원 종료
- 고객사 보안 요구의 반복적 변경
- 새로운 구축 방식의 운영 전환
- 라이선스 정책 변경
- 품질 또는 비용 기준 변경
- 동일 유형 프로젝트에서 반복되는 기술 문제 확인
- 사내 표준 도구의 변경
- 관련 법규 또는 데이터 처리 정책 변경

개정 시에는 기존 기준을 삭제하기보다 변경 사유와 대체 기준을 명확히 한다. 개별 프로젝트에서 검증된 방식이라도 범용성이 확인되지 않으면 즉시 공통 표준으로 승격하지 않는다.

이 카드의 목적은 특정 기술의 사용 여부만으로 지원자나 구성원의 역량을 판단하는 데 있지 않다. 문제 정의, 대안 비교, 실패 처리, 품질 측정, 운영 전환을 얼마나 구체적으로 설명하는지 확인하기 위한 공통 기술 배경으로 활용한다.
