# 수요예측 대시보드 구축 프로젝트 — 공개판
<!--meta: doc=PRJ-FC-PUB; doc_type=project; tier=2; topic=FC; disclosure=public; status=done-->

## 프로젝트 개요
<!--meta: sec=s1; dept=DATA|BE; level=주니어|시니어; ct_band=하; related=s2|s3|s4-->
유통업 고객사의 과거 판매 데이터를 분석해 지점별·품목별 수요를 예측하고, 발주 담당자가 매일 확인하는 대시보드를 구축했습니다.

본 프로젝트는 단순한 매출 현황 시각화가 아니라, 다음 7일 동안 예상되는 수요를 실무자가 발주 판단에 활용할 수 있도록 데이터 수집·정제·예측·조회 과정을 하나의 업무 흐름으로 연결한 프로젝트입니다. 데이터분석팀이 판매 데이터의 특성을 분석하고 예측 결과를 생성했으며, 백엔드팀이 결과 조회용 API와 발주 담당자 화면을 구현했습니다.

핵심 산출물은 다음과 같습니다.

- 지점별·품목별 7일 수요 예측 결과
- 과거 실제 판매량과 예측값을 비교하는 조회 기능
- 발주 담당자가 매일 확인할 수 있는 대시보드
- 매일 새벽 실행되는 배치 기반 예측 갱신 흐름
- 데이터 누락과 비정상 값을 구분하기 위한 기본 검증 절차
- 예측 결과의 생성 시점과 조회 기준일을 확인할 수 있는 운영 정보
- 지점·품목·기간 조건을 이용한 탐색 및 비교 기능

이 문서는 외부 공개가 가능한 수준에서 프로젝트의 목표, 구성, 사용자 흐름과 적용 원칙을 설명합니다. 모델별 성능 수치, 고객사 내부 운영 기준, 상세 인프라 구성, 장애 대응 기록 및 구현 코드는 별도 내부 문서에서 관리합니다.

## 추진 배경
<!--meta: sec=s2; dept=CONSULT|DATA; level=주니어|시니어; ct_band=하; related=s1|s3|s5-->
유통업의 발주 업무에서는 판매량의 변동, 지점별 수요 차이, 품목별 판매 주기와 계절성 등을 함께 고려해야 합니다. 그러나 발주 담당자가 다수의 지점과 품목을 관리하는 경우 모든 조합을 수기로 검토하기 어렵고, 개인 경험에 따라 판단 기준이 달라질 수 있습니다.

고객사의 기존 업무에서는 과거 판매 실적이 발주 판단의 주요 근거로 사용됐지만, 다음과 같은 제약이 있었습니다.

- 최근 판매량만 확인하면 요일별 반복 패턴을 놓칠 수 있음
- 전체 판매량만 보면 지점별 수요 차이가 가려질 수 있음
- 품목 수가 많을수록 담당자의 검토 시간이 증가함
- 일시적인 판매 급증이나 품절로 인한 판매 감소를 정상 수요로 오인할 수 있음
- 여러 화면이나 파일을 오가며 확인하면 판단 근거를 재현하기 어려움
- 담당자가 변경되면 경험 기반 기준이 충분히 인계되지 않을 수 있음

헤드헌터랩은 이러한 문제를 해결하기 위해 예측 모델 자체뿐 아니라, 예측 결과가 실제 발주 업무에 자연스럽게 연결되는 조회 경험과 운영 흐름을 함께 설계했습니다.

## 프로젝트 목표와 범위
<!--meta: sec=s3; dept=CONSULT|DATA|BE; level=주니어|시니어; ct_band=중; related=s1|s4|s6-->
프로젝트의 목표는 판매 이력을 기반으로 미래 수요를 예측하고, 발주 담당자가 이를 일관된 방식으로 확인하도록 지원하는 것입니다.

주요 구축 범위는 다음과 같습니다.

| 구분 | 구축 범위 |
| --- | --- |
| 데이터 준비 | 과거 판매 데이터의 지점·품목·일자 기준 정리 |
| 데이터 검증 | 필수 항목 누락, 중복, 비정상 값 확인 |
| 수요 예측 | 품목·지점별 향후 7일 수요 예측 |
| 결과 저장 | 예측 기준일, 대상일, 지점, 품목별 결과 저장 |
| API 제공 | 예측 결과와 실제 판매 실적 조회 |
| 화면 구축 | 발주 담당자용 검색·필터·비교 화면 |
| 운영 지원 | 배치 실행 결과와 데이터 최신성 확인 |
| 활용 정착 | 예측값을 참고 정보로 사용하는 업무 흐름 정의 |

프로젝트 범위는 발주 담당자의 의사결정을 지원하는 데 초점을 맞췄습니다. 최종 발주량을 시스템이 자동 확정하거나 담당자의 승인 없이 주문을 실행하는 기능은 본 공개판에서 설명하는 범위에 포함하지 않습니다.

## 사용자와 업무 시나리오
<!--meta: sec=s4; dept=CONSULT|DATA|BE; level=주니어|시니어; ct_band=하; related=s3|s10|s11-->
주요 사용자는 매일 판매 실적과 재고 상황을 확인하고 발주량을 검토하는 발주 담당자입니다. 사용자는 예측 결과를 절대적인 주문 지시가 아니라, 과거 실적과 함께 검토하는 참고 지표로 활용합니다.

대표적인 일일 업무 흐름은 다음과 같습니다.

1. 담당자가 대시보드에 접속합니다.
2. 데이터 기준일과 최근 예측 생성 시점을 확인합니다.
3. 담당 지점 또는 확인할 지점을 선택합니다.
4. 품목명이나 품목 분류를 이용해 조회 대상을 좁힙니다.
5. 향후 7일의 일자별 예측 수요를 확인합니다.
6. 최근 실제 판매량과 예측 추이를 비교합니다.
7. 평소와 다른 변화가 있는 품목을 우선 검토합니다.
8. 프로모션, 휴일, 입고 가능 여부 등 현장 정보를 함께 고려합니다.
9. 예측값을 참고해 내부 발주 업무를 수행합니다.

이 흐름은 담당자가 모든 품목을 동일한 깊이로 확인하기보다, 변화가 크거나 추가 검토가 필요한 대상을 먼저 찾도록 돕는 방식으로 설계됐습니다.

## 시스템 구성
<!--meta: sec=s5; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=s6|s7|s8-->
| 구성요소 | 역할 | 담당팀 |
| --- | --- | --- |
| 배치 파이프라인 | 매일 새벽 판매 데이터 집계·예측 모델 실행 | 데이터분석팀 |
| 예측 모델 | 품목·지점별 7일 수요 예측 | 데이터분석팀 |
| 대시보드 API | 예측 결과·실제 판매 비교 제공 | 백엔드팀 |
| 발주 담당자 화면 | 예측 결과 조회, 발주량 참고 | 백엔드팀 |

전체 흐름은 판매 데이터가 준비된 이후 예측 결과가 대시보드에 노출되는 순서로 구성됩니다.

`판매 데이터 준비 → 데이터 검증 → 일자별 집계 → 예측 실행 → 결과 저장 → API 조회 → 대시보드 표시`

각 구성요소는 역할을 분리해 운영합니다. 데이터분석팀은 데이터의 분석 적합성과 예측 결과 생성을 담당하고, 백엔드팀은 사용자가 안정적으로 결과를 조회할 수 있도록 API와 화면 흐름을 담당합니다. 양 팀은 예측 기준일, 지점 코드, 품목 코드, 대상일 등 공통 데이터 항목을 합의해 연동 오류를 줄였습니다.

## 데이터 처리 흐름
<!--meta: sec=s6; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=s5|s7|s12-->
수요예측에 사용되는 데이터는 지점, 품목, 판매일자와 판매량을 기준으로 정리됩니다. 원천 데이터가 분석용 형태와 다를 수 있으므로 예측 전에 표준화와 검증 과정을 거칩니다.

| 단계 | 주요 처리 내용 | 확인 항목 |
| --- | --- | --- |
| 수집 | 판매 데이터 수신 | 대상 기간, 파일 또는 연동 상태 |
| 표준화 | 날짜·코드·수량 형식 통일 | 날짜 형식, 코드 공백, 자료형 |
| 정합성 검증 | 누락·중복·범위 확인 | 필수 키, 중복 행, 음수·비정상 값 |
| 집계 | 지점·품목·일자 단위 정리 | 집계 기준과 합산 결과 |
| 특징 생성 | 예측 입력용 파생 정보 구성 | 요일, 최근 판매 흐름, 반복 패턴 |
| 예측 | 향후 7일 수요 계산 | 대상 지점·품목과 기준일 |
| 적재 | 결과 저장 및 조회 준비 | 생성 시점, 모델 구분, 대상일 |
| 제공 | API와 화면을 통한 조회 | 필터 조건, 응답 상태, 최신성 |

데이터가 존재하지 않는 경우와 실제 판매량이 0인 경우는 의미가 다를 수 있으므로 구분해서 처리합니다. 예를 들어 판매 기록이 없는 것이 무판매를 의미하는지, 데이터 수신 누락을 의미하는지는 업무 정의와 원천 시스템의 기록 방식에 따라 판단해야 합니다.

## 분석 단위 정의
<!--meta: sec=s7; dept=DATA; level=주니어|시니어; ct_band=중; related=s6|s8|s9-->
프로젝트의 기본 분석 단위는 `지점 × 품목 × 일자`입니다. 동일한 품목이라도 지점의 상권과 방문 패턴에 따라 판매 흐름이 다를 수 있으므로, 전체 평균만으로 수요를 예측하지 않고 지점별 차이를 반영합니다.

각 단위는 다음 정보를 중심으로 관리합니다.

- 지점 식별 정보
- 품목 식별 정보
- 판매일자
- 일 판매량
- 예측 기준일
- 예측 대상일
- 예측 수요
- 결과 생성 시점
- 비교 가능한 실제 판매량
- 데이터 상태 정보

분석 단위를 명확히 정의하면 데이터분석팀의 예측 결과와 백엔드팀의 조회 결과가 같은 의미를 갖게 됩니다. 특히 “7일 예측”이 예측 실행일을 포함하는지, 다음 날부터 계산하는지와 같은 기준은 화면 문구와 API 정의에서 일치하도록 관리합니다.

## 예측 접근 방식
<!--meta: sec=s8; dept=DATA; level=주니어|시니어; ct_band=상; related=s6|s7|s9-->
예측 모델은 과거 판매 데이터에서 반복되는 흐름과 최근 변화를 학습해 지점별·품목별 향후 7일 수요를 계산합니다. 특정 알고리즘 하나를 모든 대상에 일괄 적용하기보다, 데이터의 길이와 판매 패턴을 고려해 안정적으로 운영할 수 있는 방식을 채택했습니다.

예측 과정에서 검토하는 대표 요소는 다음과 같습니다.

- 최근 판매량의 수준과 변화 방향
- 요일별 반복 패턴
- 일정 기간의 이동 평균과 변동성
- 판매가 간헐적으로 발생하는 품목의 특성
- 지점별 판매 규모 차이
- 품목별 판매 주기와 회전 특성
- 일시적 급증 또는 급감이 예측에 미치는 영향
- 학습에 사용할 수 있는 과거 데이터의 충분성

예측값은 미래 판매를 완벽하게 확정하는 값이 아니라, 주어진 데이터에서 기대되는 수요를 수치로 표현한 결과입니다. 따라서 프로모션, 갑작스러운 기상 변화, 지역 행사, 공급 제한과 같이 과거 데이터만으로 충분히 파악하기 어려운 정보는 담당자의 현장 판단과 함께 고려해야 합니다.

## 모델 선택과 검증 원칙
<!--meta: sec=s9; dept=DATA; level=시니어; ct_band=상; related=s8|s14|s18-->
모델은 복잡도만으로 선택하지 않고 예측 품질, 운영 안정성, 설명 가능성, 실행 시간과 유지보수성을 함께 평가했습니다. 예측 모델이 정교하더라도 매일 정해진 시간 안에 전체 지점·품목 결과를 생성하지 못하면 실무 활용성이 낮아질 수 있기 때문입니다.

검증 시 적용한 원칙은 다음과 같습니다.

1. 미래 정보를 학습 데이터에 포함하지 않습니다.
2. 시간 순서를 유지한 상태에서 과거 구간과 검증 구간을 나눕니다.
3. 전체 평균뿐 아니라 지점별·품목별 편차를 함께 확인합니다.
4. 판매량이 큰 품목만 결과를 지배하지 않도록 여러 관점의 지표를 검토합니다.
5. 신규 또는 저판매 품목처럼 데이터가 적은 대상을 별도로 확인합니다.
6. 실제 업무에서 해석하기 어려운 과도한 음수나 급격한 진동이 발생하지 않도록 후처리 기준을 적용합니다.
7. 비교 기준이 되는 단순 예측 방식보다 안정적인 개선이 있는지 확인합니다.

공개판에서는 모델별 세부 성능 수치와 비교 결과를 제공하지 않습니다. 해당 수치는 고객사 데이터 분포와 내부 평가 조건에 영향을 받으므로 내부 상세판에서 관리합니다.

## 대시보드 주요 기능
<!--meta: sec=s10; dept=BE|DATA; level=주니어|시니어; ct_band=하; related=s4|s11|s13-->
대시보드는 발주 담당자가 예측 결과를 빠르게 탐색하고 최근 실적과 비교할 수 있도록 구성했습니다.

| 기능 | 설명 |
| --- | --- |
| 기준일 확인 | 현재 화면에 표시된 데이터와 예측의 기준일 확인 |
| 지점 선택 | 담당 지점 또는 비교 대상 지점 선택 |
| 품목 검색 | 품목명이나 식별 정보로 조회 대상 검색 |
| 기간 조회 | 최근 실적과 향후 7일 예측 구간 확인 |
| 추이 비교 | 실제 판매와 예측 수요를 시간 흐름에 따라 비교 |
| 상세 목록 | 지점·품목·대상일별 예측값 확인 |
| 정렬·필터 | 변화가 크거나 검토가 필요한 항목을 우선 탐색 |
| 상태 안내 | 데이터 준비 여부와 마지막 갱신 상태 표시 |
| 빈 결과 안내 | 조회 조건에 해당하는 결과가 없을 때 원인과 조치 안내 |

화면은 많은 정보를 한 번에 제시하기보다, 사용자가 지점과 품목을 선택한 뒤 필요한 세부 정보를 단계적으로 확인하도록 설계했습니다. 색상만으로 상태를 구분하지 않고 문구, 아이콘 또는 값 표시를 함께 사용해 정보 전달의 명확성을 높였습니다.

## 화면 정보 구조
<!--meta: sec=s11; dept=BE|CONSULT; level=주니어|시니어; ct_band=중; related=s4|s10|s16-->
대시보드의 정보는 상단 요약, 검색 조건, 추이 영역, 상세 목록 순으로 배치했습니다.

### 상단 요약 영역

- 선택한 지점
- 조회 기준일
- 예측 생성 시점
- 예측 대상 기간
- 데이터 갱신 상태

### 검색 및 필터 영역

- 지점 선택
- 품목 검색
- 품목 분류 필터
- 조회 조건 초기화
- 조회 실행

### 추이 영역

- 최근 실제 판매량
- 향후 7일 예측 수요
- 실제와 예측의 구간 구분
- 날짜별 값 확인
- 데이터가 없는 구간의 별도 표시

### 상세 목록 영역

- 지점
- 품목
- 예측 대상일
- 예측 수요
- 비교 가능한 실제 판매량
- 데이터 상태

사용자가 예측값을 실제 확정 발주량으로 오인하지 않도록 화면 문구에서 “예측 수요”와 “발주량”을 구분했습니다. 조회 화면은 의사결정 지원 도구이며, 최종 발주 판단에는 재고, 입고 일정과 현장 상황이 추가로 반영됩니다.

## API 제공 범위
<!--meta: sec=s12; dept=BE|DATA; level=주니어|시니어; ct_band=중; related=s5|s6|s13-->
대시보드 API는 화면에 필요한 예측 결과와 실제 판매 비교 정보를 제공합니다. API 계약은 화면 구현과 데이터 적재가 서로 독립적으로 변경될 수 있도록 조회 목적별로 구분했습니다.

대표적인 제공 정보는 다음과 같습니다.

- 조회 가능한 지점 목록
- 지점 또는 품목 조건에 따른 예측 결과
- 최근 실제 판매 실적
- 예측 기준일과 생성 시점
- 조회 결과의 데이터 상태
- 조건에 해당하는 결과의 존재 여부
- 화면 목록 구성을 위한 기본 품목 정보

API 응답에서 날짜와 시점의 의미를 구분했습니다.

| 항목 | 의미 |
| --- | --- |
| 기준일 | 예측 계산이 기준으로 삼은 날짜 |
| 대상일 | 예측값이 설명하는 미래 날짜 |
| 생성 시점 | 예측 결과가 시스템에 저장된 시각 |
| 실제 판매일 | 비교용 판매 실적이 발생한 날짜 |

조회 조건이 잘못됐거나 결과가 없는 경우에도 동일한 형태의 오류 안내 원칙을 적용해 화면이 원인을 구분할 수 있도록 했습니다.

## 조회 성능과 응답 설계
<!--meta: sec=s13; dept=BE; level=시니어; ct_band=상; related=s10|s12|s19-->
지점과 품목의 조합이 증가하면 예측 결과의 행 수도 함께 증가합니다. 따라서 API는 전체 결과를 한 번에 반환하지 않고 사용자의 조회 조건에 따라 필요한 범위만 제공하도록 설계했습니다.

주요 설계 원칙은 다음과 같습니다.

- 지점과 기간 조건을 명시적으로 적용
- 대량 목록의 페이지 또는 구간 단위 조회
- 화면에 필요하지 않은 필드의 불필요한 반환 방지
- 반복 조회되는 기준 정보와 예측 결과의 역할 분리
- 예측 대상일과 생성 시점 기준의 검색 효율 고려
- 동일 조건의 반복 요청에 대한 부하 완화
- 결과가 많은 경우 정렬 기준을 고정해 조회 일관성 유지

성능 최적화는 응답 속도만이 아니라 정확한 최신 데이터 제공과 함께 검토했습니다. 오래된 결과를 빠르게 보여주는 것보다 현재 화면의 데이터 기준일과 생성 시점을 명확히 안내하는 것이 발주 업무에서는 더 중요할 수 있습니다.

## 예측 품질 평가 관점
<!--meta: sec=s14; dept=DATA|CONSULT; level=주니어|시니어; ct_band=중; related=s8|s9|s15-->
예측 품질은 하나의 평균 오차만으로 판단하지 않았습니다. 유통 데이터는 판매 규모와 발생 빈도가 품목별로 크게 다를 수 있으므로, 여러 관점에서 결과를 확인했습니다.

| 평가 관점 | 확인 목적 |
| --- | --- |
| 전체 오차 | 전반적인 예측 수준 확인 |
| 지점별 오차 | 특정 지점에 편향된 결과가 있는지 확인 |
| 품목별 오차 | 일부 품목군의 성능 저하 여부 확인 |
| 기간별 오차 | 특정 시기 또는 요일의 성능 변화 확인 |
| 과대 예측 | 불필요한 재고 증가 가능성 확인 |
| 과소 예측 | 판매 기회 손실 가능성 확인 |
| 저판매 품목 | 간헐적 판매 품목의 오차 특성 확인 |
| 변동 품목 | 판매량 변화가 큰 대상의 안정성 확인 |

오차는 업무 영향과 함께 해석해야 합니다. 동일한 수량 차이라도 판매 규모가 작은 품목과 큰 품목에서 의미가 다르며, 보관 기간이나 공급 주기에 따라서도 과대·과소 예측의 비용이 달라질 수 있습니다.

## 예외 데이터 처리 원칙
<!--meta: sec=s15; dept=DATA; level=주니어|시니어; ct_band=중; related=s6|s14|s17-->
예측 입력 데이터에는 정상 판매 흐름만 존재하지 않습니다. 품절, 반품, 코드 변경, 일시적 대량 구매와 같은 사건이 기록될 수 있으므로 예외값을 무조건 제거하지 않고 업무 의미를 먼저 확인합니다.

대표적인 처리 관점은 다음과 같습니다.

- 판매량 0과 데이터 누락을 구분
- 음수 값이 반품 또는 정정 거래인지 확인
- 동일 지점·품목·일자 데이터의 중복 여부 확인
- 품목 코드 변경 전후의 연결 가능성 검토
- 지점 신규 개설 또는 운영 종료 구간 구분
- 일시적인 대량 판매가 실제 수요일 가능성 고려
- 장기간 판매가 없는 품목의 운영 상태 확인
- 품절로 인해 관측 판매량이 실제 수요보다 작을 가능성 검토

데이터 보정은 예측 성능을 높이기 위한 임의 수정이 아니라, 원천 기록의 의미를 보존하면서 분석 가능한 상태로 정리하는 과정으로 수행했습니다.

## 사용자 경험 설계 원칙
<!--meta: sec=s16; dept=CONSULT|BE; level=주니어|시니어; ct_band=하; related=s10|s11|s21-->
대시보드의 사용자 경험은 발주 담당자의 반복 업무를 방해하지 않는 것을 우선했습니다.

주요 원칙은 다음과 같습니다.

1. 화면을 열었을 때 데이터의 최신 상태를 먼저 알 수 있어야 합니다.
2. 담당자가 자주 사용하는 조회 조건을 빠르게 선택할 수 있어야 합니다.
3. 실제 판매와 예측값의 구간이 시각적으로 구분돼야 합니다.
4. 예측값의 단위와 대상일이 명확해야 합니다.
5. 결과가 없을 때 단순 공백이 아니라 이유를 안내해야 합니다.
6. 데이터 준비 중인 상태와 조회 오류를 구분해야 합니다.
7. 과도한 색상과 장식을 줄이고 업무상 중요한 차이를 강조해야 합니다.
8. 표와 그래프에서 동일한 지점·품목·날짜 기준을 사용해야 합니다.

화면 용어는 분석가와 개발자 중심의 표현보다 발주 담당자가 업무에서 사용하는 표현을 우선했습니다. 기술적 모델 이름보다 “예측 기준일”, “예측 대상일”, “최근 실제 판매”와 같이 사용 목적이 드러나는 문구를 적용했습니다.

## 데이터 품질 관리
<!--meta: sec=s17; dept=DATA|BE; level=시니어; ct_band=상; related=s6|s15|s19-->
예측 결과의 신뢰성은 모델뿐 아니라 입력 데이터의 품질에 크게 영향을 받습니다. 이에 따라 데이터 품질을 형식, 완전성, 일관성, 최신성의 관점에서 확인했습니다.

| 품질 영역 | 확인 예시 | 처리 방향 |
| --- | --- | --- |
| 형식 | 날짜와 수량의 자료형이 올바른지 | 표준 형식으로 변환 |
| 완전성 | 필수 지점·품목·일자 정보가 있는지 | 누락 상태 기록 및 제외 여부 판단 |
| 유일성 | 동일 키가 중복으로 존재하는지 | 중복 원인 확인 후 집계 또는 정정 |
| 일관성 | 지점·품목 코드가 기준 정보와 일치하는지 | 매핑 기준 적용 |
| 유효성 | 판매량이 허용 가능한 범위인지 | 업무 의미 확인 |
| 최신성 | 예정된 기준일까지 데이터가 도착했는지 | 대시보드 상태에 반영 |

품질 검증에서 이상이 발견되면 모든 데이터를 일괄 폐기하기보다 영향 범위를 구분합니다. 특정 지점이나 일부 기간에만 문제가 있는 경우 정상 범위의 결과 제공 가능성과 사용자 안내 방법을 함께 검토합니다.

## 배치 운영 개요
<!--meta: sec=s18; dept=DATA; level=주니어|시니어; ct_band=중; related=s5|s9|s19-->
배치 파이프라인은 매일 새벽 판매 데이터 집계와 예측 모델 실행을 담당합니다. 배치가 완료되면 새 기준일의 예측 결과가 저장되고 대시보드에서 조회할 수 있습니다.

운영 단계는 다음과 같이 구분됩니다.

1. 실행 대상 기준일 확인
2. 판매 데이터 준비 상태 점검
3. 데이터 형식과 필수 항목 검증
4. 지점·품목·일자별 집계
5. 예측 입력 데이터 생성
6. 품목·지점별 7일 예측 실행
7. 결과 형식 검증
8. 예측 결과 저장
9. 조회 가능 상태 갱신
10. 실행 결과 기록

배치의 세부 구현 코드와 서버 자원 설정은 본 공개판의 범위에 포함하지 않습니다. 공개판에서는 예측 결과가 정기적으로 생성되고, 사용자가 갱신 상태를 확인할 수 있다는 운영 원칙만 설명합니다.

## 운영 모니터링 항목
<!--meta: sec=s19; dept=DATA|BE; level=시니어; ct_band=상; related=s13|s17|s18-->
운영 모니터링은 배치 실행 여부, 데이터 최신성, 예측 결과의 생성 상태와 API 조회 상태를 구분해 확인합니다.

| 모니터링 영역 | 주요 확인 항목 |
| --- | --- |
| 데이터 수신 | 예정된 판매 데이터가 준비됐는지 |
| 데이터 품질 | 누락·중복·비정상 값이 증가했는지 |
| 배치 실행 | 예정된 배치가 시작·완료됐는지 |
| 예측 결과 | 대상 지점·품목 결과가 생성됐는지 |
| 결과 최신성 | 대시보드의 기준일이 최신인지 |
| API 상태 | 조회 요청이 정상 처리되는지 |
| 화면 상태 | 사용자가 최신성 및 오류 상태를 확인할 수 있는지 |
| 품질 추이 | 실제 판매 확보 후 예측 오차가 급변하지 않는지 |

운영 상태는 단순 성공과 실패만으로 구분하지 않습니다. 일부 대상만 처리됐거나 데이터가 늦게 도착한 경우처럼 제한적으로 사용할 수 있는 상태도 존재하므로, 영향 범위와 사용자 안내가 함께 관리돼야 합니다.

## 역할과 협업 방식
<!--meta: sec=s20; dept=CONSULT|DATA|BE; level=주니어|시니어; ct_band=중; related=s3|s5|s21-->
프로젝트는 데이터분석팀과 백엔드팀을 중심으로 수행했으며, 업무 정의와 사용자 활용 방식은 컨설팅 관점에서 함께 정리했습니다.

| 역할 | 주요 책임 |
| --- | --- |
| 컨설팅 관점 | 발주 업무 흐름 정리, 사용자 요구사항 구조화, 활용 기준 조율 |
| 데이터분석팀 | 데이터 탐색, 품질 검증, 예측 모델 개발, 결과 생성 |
| 백엔드팀 | 대시보드 API, 조회 화면, 접근 흐름, 상태 안내 구현 |
| 고객사 업무 담당자 | 발주 업무 기준 설명, 결과 검토, 현장 예외사항 공유 |
| 고객사 시스템 담당자 | 판매 데이터 제공 방식과 기준 정보 확인 |

협업 과정에서는 기술 용어보다 데이터 항목과 업무 의미를 중심으로 의사소통했습니다. 예를 들어 “예측 시점”이라는 표현이 실행 시각과 예측 대상일 중 무엇을 의미하는지 불명확할 수 있으므로, 공통 용어를 정의한 뒤 화면·API·분석 결과에서 동일하게 사용했습니다.

## 사용자 검증과 적용 절차
<!--meta: sec=s21; dept=CONSULT|DATA|BE; level=주니어|시니어; ct_band=중; related=s4|s16|s20-->
구축 결과는 기능 동작 여부뿐 아니라 발주 담당자가 실제 업무에서 이해하고 사용할 수 있는지를 기준으로 검증했습니다.

대표적인 검증 항목은 다음과 같습니다.

- 사용자가 담당 지점을 쉽게 찾을 수 있는지
- 품목 검색 결과가 업무상 사용하는 명칭과 일치하는지
- 실제 판매와 예측 수요를 혼동하지 않는지
- 예측 기준일과 대상 기간을 이해할 수 있는지
- 결과가 없거나 준비 중일 때 다음 행동을 알 수 있는지
- 데이터 갱신 시점을 화면에서 확인할 수 있는지
- 많은 품목 중 우선 검토 대상을 찾을 수 있는지
- 화면의 수치와 조회용 데이터가 동일한 기준을 사용하는지

적용 과정에서는 예측값을 곧바로 자동 발주 기준으로 사용하지 않고, 기존 업무와 병행해 결과를 확인하는 방식을 우선했습니다. 이를 통해 사용자 피드백을 수집하고 데이터 특성과 현장 판단의 차이를 점검했습니다.

## 보안과 공개 범위 원칙
<!--meta: sec=s22; dept=CONSULT|DATA|BE; level=주니어|시니어; ct_band=하; related=s1|s12|s25-->
본 문서는 공개판이므로 고객사를 식별할 수 있는 명칭, 실제 지점 정보, 품목 정보, 판매 실적, 인프라 주소, 계정 정보와 상세 성능 수치를 포함하지 않습니다.

프로젝트 수행 시에는 다음과 같은 원칙을 적용합니다.

- 업무에 필요한 범위에서 데이터 접근
- 사용자 권한에 따른 조회 범위 구분
- 고객사 식별 정보의 외부 문서 노출 방지
- 화면과 로그에 불필요한 원천 데이터 표시 제한
- 개발·검증 과정에서 데이터 취급 기준 준수
- 외부 공유 자료 작성 시 수치와 화면 정보 재검토
- 운영 정보와 공개 가능한 프로젝트 소개 정보 분리

공개판에 포함된 화면·데이터 설명은 시스템 구조를 이해하기 위한 일반화된 내용이며, 실제 고객사 데이터와 운영 설정을 재현하지 않습니다.

## 기술 난이도별 이해 포인트
<!--meta: sec=s24; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=s5|s8|s13-->
### 기초 수준

- 판매 데이터를 날짜별로 집계하는 이유
- 실제 판매량과 예측 수요의 차이
- 지점별·품목별로 결과를 나누는 이유
- 매일 새벽 배치를 실행하는 목적
- 대시보드에서 기준일을 표시하는 이유

### 중급 수준

- 요일 패턴과 최근 판매 흐름을 예측에 반영하는 방법
- 결측과 판매량 0을 구분해야 하는 이유
- API 응답에서 기준일·대상일·생성 시점을 분리하는 방법
- 대량 결과를 필터와 페이지 단위로 제공하는 이유
- 지점별·품목별 오차를 별도로 확인하는 이유

### 고급 수준

- 시계열 검증에서 미래 정보 유입을 방지하는 방법
- 간헐적 수요 품목의 평가 지표를 선택하는 기준
- 모델 복잡도와 매일 실행 가능한 운영 시간 사이의 균형
- 데이터 최신성과 API 응답 성능을 함께 관리하는 방법
- 일부 데이터 이상이 전체 예측 결과에 미치는 영향을 제한하는 설계

## 구축 과정에서 얻은 교훈
<!--meta: sec=s25; dept=CONSULT|DATA|BE; level=시니어; ct_band=상; related=s20|s21|s26-->
첫째, 예측 모델의 정확도만으로 프로젝트 성공을 설명하기 어렵습니다. 사용자가 결과의 기준일과 대상일을 이해하지 못하면 높은 품질의 예측도 업무에 활용되기 어렵습니다.

둘째, 판매 데이터의 0은 단순한 숫자가 아닐 수 있습니다. 실제 무판매, 품절, 휴점 또는 데이터 누락이 같은 값으로 보일 수 있으므로 업무 의미를 확인해야 합니다.

셋째, 지점과 품목 수가 증가하면 분석 문제와 조회 성능 문제가 동시에 커집니다. 결과 생성 단계와 API 제공 단계를 분리하되, 공통 식별자와 날짜 기준은 엄격하게 맞춰야 합니다.

넷째, 예측값을 자동 의사결정으로 바로 연결하기보다 담당자의 판단을 돕는 방식으로 시작하는 것이 활용 정착에 유리합니다. 사용자는 실제 업무 사례를 통해 예측의 강점과 한계를 이해할 수 있습니다.

다섯째, 데이터가 준비되지 않은 상태를 정상적인 0으로 표시하면 잘못된 발주 판단으로 이어질 수 있습니다. 따라서 값 자체뿐 아니라 데이터 상태와 최신성을 함께 제공해야 합니다.

여섯째, 평균 성능이 개선돼도 특정 지점이나 품목군에서는 결과가 나빠질 수 있습니다. 운영 관점에서는 전체 지표와 세부 구간을 함께 살펴야 합니다.

## 확장 방향
<!--meta: sec=s26; dept=CONSULT|DATA|BE; level=시니어; ct_band=상; related=s8|s19|s25-->
향후 확장 시에는 데이터 가용성과 고객사 업무 기준을 확인한 뒤 다음 기능을 검토할 수 있습니다.

- 프로모션 일정과 가격 변동 정보 반영
- 공휴일과 지역 행사 등 달력 정보 반영
- 기상 정보가 수요에 미치는 영향 분석
- 품목 분류별 예측 결과 비교
- 신규 품목을 위한 대체 예측 기준
- 지점 간 유사성을 활용한 보완 예측
- 예측 불확실성 또는 범위 표시
- 재고와 입고 예정량을 함께 고려한 조회 화면
- 담당자 피드백을 기록하는 기능
- 예측 품질 변화에 대한 운영 알림
- 다수 지점의 비교 조회 기능
- 모바일 환경에서의 핵심 정보 확인

확장 기능은 기술적으로 구현 가능하다는 이유만으로 적용하지 않습니다. 데이터 확보 가능성, 업무상 활용 가치, 사용자 부담, 운영 비용과 설명 가능성을 함께 검토한 뒤 우선순위를 결정합니다.

## 도입 효과
<!--meta: sec=s3; dept=DATA|BE; level=주니어|시니어; ct_band=중; related=s1|s4|s10-->
발주 담당자의 수기 예측 대비 재고 과부족이 줄었습니다. 세부 수치는 내부 상세판에서 다룹니다.

정성적인 도입 효과는 다음과 같습니다.

- 지점별·품목별 수요를 동일한 기준으로 확인할 수 있게 됨
- 과거 판매 실적과 향후 예측을 한 화면에서 비교할 수 있게 됨
- 담당자가 다수 품목 중 우선 검토할 대상을 찾기 쉬워짐
- 경험에만 의존하던 판단에 데이터 기반 참고 근거가 추가됨
- 예측 결과의 기준일과 생성 시점을 확인할 수 있게 됨
- 데이터분석 결과가 일회성 보고서가 아니라 일일 업무 화면으로 연결됨
- 데이터분석팀과 백엔드팀 사이의 공통 데이터 기준이 정립됨
- 향후 외부 요인과 재고 정보를 결합할 수 있는 확장 기반이 마련됨

본 프로젝트는 예측 모델 개발, 데이터 운영과 사용자 화면을 하나의 서비스 흐름으로 연결했다는 점에 의의가 있습니다. 헤드헌터랩은 분석 결과를 제공하는 데 그치지 않고, 고객사의 반복 업무 안에서 실제로 확인하고 활용할 수 있는 형태로 구현했습니다.
