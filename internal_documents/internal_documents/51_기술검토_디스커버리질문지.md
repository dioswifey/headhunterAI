# 디스커버리 미팅 질문지 및 운영 절차
<!--meta: doc=DSC-01; doc_type=discovery_guide; tier=2; topic=DISCOVERY; disclosure=internal; status=active-->

## 디스커버리의 목적과 초기 미팅과의 차이
<!--meta: sec=s1; dept=CNS|SALES; level=주니어|시니어; ct_band=중; related=SLS-05#s5-->

디스커버리의 목적은 회사·기능·레퍼런스를 소개하는 것이 아니라 고객의 과제를 진단하는 데 있다. 고객이 요청한 기능을 곧바로 요구사항으로 확정하지 않는다. 질문과 근거 확인을 통해 문제의 실재성, 규모, 해결 가능한 형태인지를 판별한다.

초기 미팅은 상호 적합성과 추가 진단 필요성을 확인하는 단계이며 운영 기준은 SLS-05#s5를 따른다. 디스커버리는 초기 미팅을 통과한 기회에 대해 현재 업무, 데이터, 조직, 제약과 성공 조건을 구체화하는 별도 단계로 운영한다.

| 구분 | 초기 미팅 | 디스커버리 |
|---|---|---|
| 목적 | 관심 배경과 기본 적합성 확인 | 문제의 실재성·규모·해결 가능 형태 진단 |
| 참석자 | 영업 담당자와 고객 접점 담당자 중심 | 컨설턴트, 엔지니어, 영업과 고객 업무·기술 관계자 |
| 소요 시간 | 원칙적으로 30~45분 | 원칙적으로 60~90분 |
| 산출물 | 디스커버리 이관 여부와 미확인 항목 | 업무 흐름, 문제 근거, 제약, 원하는 결과의 기록 |
| 다음 단계 | 디스커버리 진행 또는 보류 | 추가 확인, 타당성 검토 또는 종료 분기 |

### 세 가지 판별 과제

1. **문제의 실재성**: 현상, 발생 빈도, 영향을 받는 사용자와 확인 가능한 사례가 있는지 판별한다.
2. **문제의 규모**: 처리량, 투입 시간, 오류·반송·지연과 같은 영향을 수치화할 수 있는지 확인한다.
3. **해결 가능한 형태**: 입력과 출력, 업무 경계, 예외 조건을 정의하여 후속 검토가 가능한지 판단한다.

디스커버리 중 확인된 고객의 희망 기능은 가설로 기록하며 즉시 구현 범위로 확정하지 않는다. 정량 근거가 없으면 추정치와 확인치를 구분하고, 확인 책임자와 회신 기한을 함께 남긴다. 모순되는 답변은 임의로 정리하지 않고 의견별로 기록한다.

### 디스커버리에서 결론을 내리지 않는 사항

- 최종 기술 구조와 배치 방식을 확정하지 않는다.
- AI 도입 타당성 등급을 단독으로 판정하지 않는다.
- 데이터 준비도와 모델 성능을 보장하지 않는다.
- 법률·규제·보안 적합성을 확정적으로 판단하지 않는다.
- 제안, 가격, 견적, 계약 또는 수주 조건을 합의하지 않는다.
- 고객 내부의 예산 승인과 의사결정 완료를 추정하지 않는다.

기술 타당성은 DSC-02 이후 검토 결과를 따르며, 제안과 가격은 제안·가격 소관 문서 계열에서 처리한다. 디스커버리 산출물은 후속 판단의 입력자료이며 최종 승인 문서로 사용하지 않는다.

## 참석자 구성·준비물·사전 질문지 발송
<!--meta: sec=s2; dept=CNS|SALES; level=주니어|시니어; ct_band=중; related=SLS-05#s8-->

디스커버리는 CNS 컨설턴트가 주도하고 AIAX 엔지니어와 SALES 담당자가 배석하는 구성을 원칙으로 한다. 참석자는 각자 맡은 질문과 기록 범위를 사전에 확인한다. 고객 참석자 구성은 초기 미팅 이관 기록인 SLS-05#s8을 기준으로 보완한다.

| 구분 | 참석자 | 필수 여부 | 주요 역할 |
|---|---|---:|---|
| 헤드헌터랩 | CNS 컨설턴트 | 필수 | 진행, 질문 구조 조정, 문제·성과 가설 정리 |
| 헤드헌터랩 | AIAX 엔지니어 | 원칙적 필수 | 기술 용어 확인, 연동·데이터·운영 제약 식별 |
| 헤드헌터랩 | SALES 담당자 | 필수 | 접점 맥락 공유, 참석자 관계 확인, 후속 일정 조율 |
| 고객 | 업무 책임자 | 필수 | 과제 배경, 목표, 우선순위와 영향 범위 설명 |
| 고객 | 현업 실무자 | 권고 | 실제 업무 흐름, 예외, 도구와 처리량 설명 |
| 고객 | IT·데이터·보안 관계자 | 조건부 | 시스템·데이터·접근 제약에 대한 사실 확인 |

고객 측에는 업무 책임자 1명과 실제 업무를 수행하는 실무자 1명 이상을 우선 요청한다. 시스템 연동, 데이터 접근 또는 망 제약이 예상되면 관련 담당자 1명을 추가로 요청하되 참석이 어렵다면 후속 서면 확인으로 분리한다.

> 요청 문구: 이번 미팅은 기능 소개보다 현재 업무와 과제를 확인하는 진단 미팅으로 진행한다. 업무 책임자와 실제 처리 절차를 설명할 수 있는 실무자, 필요 시 IT·데이터 관계자의 참석을 요청한다.

### 사전 질문지 발송 기준

- 관련 부서가 2개 이상이거나 확인 대상 시스템이 3개 이상이면 사전 질문지를 발송한다.
- 고객 내부에서 참석자별 확인 사항을 미리 배분해야 하는 경우 발송한다.
- 과제 범위가 불명확하고 질문지가 특정 해법을 전제할 우려가 크면 발송하지 않는다.
- 고객이 문서 작성 부담을 명시한 경우 핵심 질문 5개 이내의 이메일로 대체한다.
- 발송 시점은 미팅 3영업일 전을 원칙으로 하며 늦어도 1영업일 전까지 전달한다.
- 분량은 A4 2쪽 또는 객관식·단답형을 포함한 15문항 이내로 제한한다.
- 고객 식별 정보나 원본 데이터의 이메일 첨부를 사전 질문지에서 요구하지 않는다.

사전 질문지는 답변 완성을 참석 조건으로 삼지 않으며 미리 생각할 항목을 안내하는 용도로 사용한다. 미회신 항목은 회의 중 확인하되 답변을 압박하지 않는다. 회신 내용과 구두 답변이 다르면 최신 답변과 변경 사유를 기록한다.

### 준비물

- 초기 미팅 기록과 미확인 항목 목록
- 고객 조직·업무에 관한 공개 정보와 용어 목록
- 질문 체크리스트와 90분 기준 아젠다
- 업무 흐름을 그릴 수 있는 화면 또는 보드
- 미확인 사항·담당자·기한 기록표
- 회의 기록 동의 여부 확인 문구

### 회의 기록 담당

- SALES 담당자를 기본 기록 담당자로 지정하고 초대장에 이름을 표시한다.
- 기록 담당자는 발언 전문보다 사실, 수치, 근거, 미확인 항목을 우선 기록한다.
- SALES가 진행 역할을 겸하면 CNS 또는 AIAX 참석자 중 1명을 대체 지정한다.

녹음·자동 전사는 고객의 명시적 동의와 내부 사용 범위를 확인한 경우에만 수행한다. 기록은 미팅 종료 후 24시간 이내에 진행자가 검토하고 추정과 확인 사실을 구분한다.

## 질문 설계 원칙
<!--meta: sec=s3; dept=CNS; level=시니어; ct_band=상; related=none-->

질문은 고객의 사업 맥락에서 시작하여 구체적인 업무 영향으로 좁혀 간다. 기능 요청부터 묻거나 특정 AI 방식의 필요성을 전제하지 않는다. 각 질문은 앞선 답변을 확인하거나 다음 판단에 필요한 근거를 얻는 역할을 가져야 한다.

### 넓은 질문에서 좁은 질문으로 내려가는 순서

1. **사업과 목표**: 조직이 달성하려는 목표와 해당 업무의 역할을 확인한다.
2. **막고 있는 문제**: 목표 달성을 방해하는 현상과 발생 조건을 찾는다.
3. **현재 처리 방식**: 담당자, 단계, 입력·출력, 도구와 예외 처리를 확인한다.
4. **비용과 시급성**: 시간·오류·지연의 영향과 지금 해결해야 하는 이유를 확인한다.

각 단계의 답이 추상적이면 사례, 기간, 건수 순으로 구체화를 요청한다. 고객이 먼저 영향이나 해결 가치를 설명하면 정해진 순서를 고집하지 않고 관련 현재 상태와 문제 근거를 거슬러 확인한다.

| SPIN 유형 | 정의 | 사용 시점 | 질문 예시 |
|---|---|---|---|
| Situation | 현재 상태와 운영 맥락을 확인하는 질문 | 대화 초반과 새로운 업무 영역 진입 시 | 월말 정산 자료를 지금 어떤 흐름과 도구로 취합하십니까? |
| Problem | 불편, 오류, 지연 또는 미충족 요구를 찾는 질문 | 현재 흐름이 확인된 뒤 | 수요 보고서를 작성할 때 가장 자주 다시 작업하는 단계는 어디입니까? |
| Implication | 문제가 초래하는 업무·고객·운영 결과를 확인하는 질문 | 문제 사례가 확인된 뒤 | 문의 분류가 늦어지면 후속 상담과 고객 응답 시간에 어떤 영향이 생깁니까? |
| Need-payoff | 문제가 해결될 때 얻는 가치를 고객 언어로 확인하는 질문 | 영향과 우선순위가 확인된 뒤 | 품질 확인 시간을 절반으로 줄이면 담당자는 확보된 시간을 어디에 사용할 수 있습니까? |

질문지는 누락을 방지하는 체크리스트이며 낭독용 대본이 아니다. 순서대로 읽으면 고객 답변과 무관한 질문이 이어지고, 이미 확인한 내용을 반복하며, 중요한 후속 질문을 놓치기 쉽다. 진행자는 대화 흐름을 따르면서 항목별 확인 상태만 표시한다.

### 체크리스트 운용

- 미팅 전 필수 확인 항목 8~12개에 우선순위를 표시한다.
- 고객 답변에서 새 쟁점이 나오면 관련 후속 질문을 먼저 한다.
- 이미 답변된 항목은 다시 질문하지 않고 표현과 수치만 확인한다.
- 현재 참석자가 답할 수 없는 질문은 별도 확인 항목으로 이동한다.
- 종료 10분 전에 미확인 필수 항목과 후속 담당자를 점검한다.

### 피해야 할 질문

- **폐쇄형 질문**: “현재 방식이 비효율적입니까?” 대신 “현재 방식에서 시간이 가장 많이 드는 단계는 어디입니까?”라고 묻는다.
- **유도 질문**: “자동화하면 오류가 줄겠지요?” 대신 “오류가 발생하는 조건과 현재 확인 방식은 무엇입니까?”라고 묻는다.
- **이중 질문**: 처리량과 승인 절차를 한 문장에 묻지 않고 두 질문으로 분리한다.
- **해법 전제 질문**: 특정 모델이나 배치 방식의 채택을 전제로 효과를 묻지 않는다.
- **추상 질문**: “업무가 어렵습니까?” 대신 최근 3개월의 사례와 빈도를 요청한다.

진행자는 답변을 임의의 원인이나 요구사항으로 변환하지 않고 고객 표현과 해석을 분리한다. 해석이 필요한 경우 “말씀하신 내용을 이렇게 이해했는데 맞습니까?”라고 확인한다.

## 업무 영역 질문
<!--meta: sec=s4; dept=CNS; level=주니어|시니어; ct_band=중; related=none-->

업무 영역 질문은 현재 업무 흐름을 시작 조건부터 종료 조건까지 그릴 수 있는 수준으로 수행한다. 정상 흐름뿐 아니라 예외, 반송, 재작업과 품질 확인 단계를 포함한다. 답변은 최근 3개월 또는 대표 운영 기간을 기준으로 요청한다.

| 확인 항목 | 질문 | 질문 의도 | 답이 없으면 판단할 수 없는 사항 |
|---|---|---|---|
| 처리 단위·월 처리량 | 한 건의 기준은 무엇이며 최근 3개월 월평균 처리량은 몇 건입니까? | 업무 규모와 반복성 확인 | 자동화 대상 규모와 효과 측정 기준 |
| 담당 인원·소요 시간 | 단계별 담당자는 몇 명이며 건당·월간 소요 시간은 얼마입니까? | 병목과 인력 투입 구조 확인 | 우선 개선 단계와 시간 절감 여지 |
| 입력물·산출물 | 업무 시작 시 받는 자료와 종료 시 만드는 결과물의 형식은 무엇입니까? | 업무 경계와 변환 관계 확인 | 입력·출력 정의와 연동 대상 |
| 예외·반송 처리 | 정상 처리되지 않는 사례는 월 몇 건이며 누구에게 어떤 방식으로 반송합니까? | 예외율과 재작업 경로 확인 | 표준화 가능 범위와 사람 개입 지점 |
| 현재 도구 | 각 단계에서 사용하는 시스템, 문서, 메신저 또는 수작업 도구는 무엇입니까? | 도구 간 이동과 수기 처리 확인 | 연동 범위와 업무 전환 부담 |
| 품질 확인 주체 | 결과를 누가 어떤 기준으로 검사하고 오류는 어떻게 기록합니까? | 정답 기준과 책임 구조 확인 | 품질 지표와 검증 절차 |
| 성수기 편차 | 성수기와 평시의 처리량·대기 시간 차이는 어느 정도입니까? | 부하 변동과 최대 수요 확인 | 용량 기준과 대표 측정 기간 |

수치가 없으면 정확한 값을 요구하기보다 산출 가능한 원천과 담당자를 확인한다. 추정치는 추정 주체, 기준 기간, 산정 방법을 함께 기록하며 확인값과 동일하게 취급하지 않는다. 부서별 흐름이 다르면 공통 흐름으로 합치지 않고 각각 작성한다.

### 업무 흐름 완성 확인

- 업무가 시작되는 사건과 종료로 인정하는 상태를 확인한다.
- 단계 간 전달 매체와 대기 시간을 구분하여 기록한다.
- 승인, 검수, 반송과 재처리 경로를 별도 표시한다.
- 사람의 판단이 필요한 단계와 판단 기준을 확인한다.
- 외부 조직이나 다른 부서로 넘어가는 경계를 표시한다.
- 정상 처리 1건을 기준으로 단계 순서를 고객에게 다시 확인한다.

### 현장 관찰·업무 샘플 요청

설명만으로 단계나 예외를 구분하기 어렵다면 30~60분의 화면 시연 또는 현장 관찰을 요청한다. 업무 샘플은 정상 2건, 예외 2건, 반송 1건 등 최소 범위로 요청하며 고객이 제공 가능 범위를 먼저 정하도록 한다.

> 요청 문구: 설명해 주신 흐름을 정확히 이해하기 위해 실제 업무 화면 또는 식별 정보를 제거한 샘플을 확인하고자 한다. 제공이 어려운 항목은 가상 예시나 화면 구조 설명으로 대체할 수 있다.

- 관찰 목적, 대상 단계, 예상 시간을 사전에 알린다.
- 고객 승인 없이 화면을 촬영하거나 자료를 복사하지 않는다.
- 개인·고객·거래 식별 정보는 마스킹된 형태를 우선 요청한다.
- 원본 자료 반출이 어려우면 고객 환경에서 열람만 수행한다.
- 관찰 내용과 설명이 다르면 차이를 기록하고 업무 책임자에게 확인한다.

샘플 확인만으로 전체 업무의 빈도나 품질을 일반화하지 않는다. 추가 자료가 필요한 경우 자료명, 확인 목적, 제공 방식, 담당자와 목표 회신일을 기록한다.

## 데이터 영역 질문
<!--meta: sec=s5; dept=CNS|DATA; level=주니어|시니어; ct_band=중; related=DSC-03#s2-->

데이터 영역 질문은 데이터의 존재 여부가 아니라 위치, 구조, 기간, 관리 책임과 사용 가능 조건을 파악하기 위해 사용한다. 이 단계에서는 고객 답변을 기록하며 품질 점수나 준비도 등급을 판정하지 않는다. 채점과 등급 판정은 DSC-03 소관으로 넘긴다.

### 기본 질문 항목

질문은 업무 흐름에 맞춰 필요한 순서로 제시하며 질문지를 그대로 읽지 않는다. 고객이 답한 명칭은 내부 용어로 임의 변환하지 않고 원문과 해석을 함께 기록한다.

| 확인 항목 | 기본 질문 | 추가 확인 기준 | 기록 단위 |
|---|---|---|---|
| 데이터 종류 | 해당 업무에서 생성하거나 참조하는 데이터는 무엇입니까 | 원천·가공·결과 데이터 구분 | 데이터셋·테이블·문서군 |
| 저장 형태 | 데이터는 어떤 형식과 시스템에 저장되어 있습니까 | 정형·비정형, 파일·DB·시스템 구분 | 형식, 저장 위치 |
| 보유 기간 | 가장 오래된 데이터와 실제 활용 가능한 기간은 얼마입니까 | 법정 보존과 실사용 가능 기간 분리 | 시작일, 개월·연 |
| 갱신 주기 | 데이터는 언제 생성되고 언제 반영됩니까 | 배치·실시간·수기 갱신 구분 | 분·시간·일·월 |
| 소유 부서 | 생성·관리·접근 승인 책임은 어느 부서에 있습니까 | 실무 관리자와 승인권자 분리 | 부서, 역할 |
| 정비 이력 | 중복 제거, 코드 통합, 결측 보완을 수행한 적이 있습니까 | 시기·범위·수행 주체 확인 | 작업명, 완료일 |
| 반출 가능성 | 사내망 밖 또는 별도 분석 환경으로 이동할 수 있습니까 | 비식별·가명처리 조건과 승인 절차 확인 | 가능·조건부·미확인 |
| 라벨·정답 | 결과를 판정할 라벨이나 검증된 정답 데이터가 있습니까 | 생성 기준·검수자·최근 갱신일 확인 | 건수, 비율, 기준일 |

### “데이터는 충분히 있다”는 답변의 후속 질문

“충분하다”는 답변은 수량, 기간, 범위가 확인되지 않은 상태로 기록한다. 담당자는 충분성의 기준을 추정하지 않고 다음 질문으로 답변을 구체화한다.

- 전체 데이터 건수와 최근 12개월 데이터 건수는 각각 얼마입니까.
- 한 건의 기준은 고객, 상담, 거래, 문서 중 무엇입니까.
- 동일 업무 범위에서 누락된 기간이나 시스템이 있습니까.
- 실제 조회하거나 추출해 본 가장 최근 날짜는 언제입니까.
- 오류·중복·결측을 제외한 사용 가능 건수를 별도로 집계했습니까.
- 라벨 또는 정답이 있다면 전체 대비 부여 비율은 몇 퍼센트입니까.

### 숫자 기록과 즉석 검증

숫자는 값만 받아 적지 않고 단위, 기준 시점, 산출 범위와 답변 출처를 함께 기록한다. 미팅 중에는 원천 접근권과 산식이 확보되지 않은 경우가 많으므로 수량의 진위를 즉석에서 검증하지 않는다. 현장 계산으로 대화 흐름을 중단하거나 잠정 수치를 확정값으로 오인하게 하지 않는다.

- 수량은 `약 120만 건`처럼 고객이 사용한 근사 표현을 유지한다.
- 기간은 `2023-01~2026-09`처럼 시작일과 종료일을 분리한다.
- 비율은 분자와 분모를 함께 확인하고, 없으면 `산식 미확인`으로 적는다.
- 구두 답변에는 `답변자 역할·답변일`을 붙인다.
- 문서 근거가 언급되면 문서명, 기준일과 제공 가능 여부를 기록한다.
- 후속 검증이 필요하면 담당자와 확인 예정일을 지정한다.

## 조직·의사결정 영역 질문
<!--meta: sec=s6; dept=CNS|SALES; level=시니어; ct_band=상; related=SLS-02#s7-->

조직·의사결정 영역에서는 과제를 실제로 추진하는 주체, 승인 경로와 현업 참여 가능성을 파악한다. 직급만으로 결정권을 추정하지 않으며 참석자의 발언을 조직 전체의 확정 의견으로 간주하지 않는다. 구매 관여자 구조의 기본 분류는 SLS-02#s7을 참고한다.

### 관여자와 절차 확인 질문

질문은 개인의 권한을 캐묻는 방식보다 업무상 역할과 승인 절차를 확인하는 방식으로 제시한다. 이름을 제공하기 어려운 경우에는 부서와 역할 수준으로 기록한다.

| 확인 항목 | 질문 | 확인해야 할 답변 요소 | MEDDIC 입력 |
|---|---|---|---|
| 추진 주체 | 이 과제를 주도하고 실무를 조정하는 조직은 어디입니까 | 책임자, 실무 창구, 보고 라인 | 챔피언 후보 |
| 승인 단계 | 검토부터 최종 승인까지 어떤 단계를 거칩니까 | 단계 순서, 회의체, 필수 검토 | 구매 절차 |
| 단계별 기준 | 각 단계에서는 무엇을 근거로 통과 여부를 판단합니까 | 성능, 보안, 운영성, 효과 기준 | 결정 기준 |
| 현업 공수 | 현업 담당자는 주당 몇 시간 참여할 수 있습니까 | 인원, 기간, 대체 가능자 | 챔피언·실행 조건 |
| 과거 시도 | 유사한 시도를 언제 했고 어떤 상태로 종료했습니까 | 범위, 결과, 중단 사유, 잔여 쟁점 | 결정 기준·위험 |
| 성과 보고 | 성과는 누구에게 어떤 주기와 지표로 보고합니까 | 보고 대상, 기준선, 목표값, 주기 | 메트릭 |

### 과거 시도와 회피 신호

과거 시도는 기술 문제 외에 승인 지연, 담당 조직 변경, 현업 공수 부족과 같은 반복 요인을 드러내므로 반드시 묻는다. 중단 사유는 실패 책임을 묻기 위한 것이 아니라 이번 과제에서도 재현될 조건을 찾기 위한 정보로 다룬다. 답변 회피는 단독 탈락 사유가 아니며 미확인 위험 신호로 기록한다.

- 승인권자를 계속 `상위 조직`으로만 표현하면 승인 경로 미식별로 해석한다.
- 현업 참여를 `필요할 때 지원`으로 답하면 공수 미확보로 해석한다.
- 과거 시도를 `검토만 했다`고 답하면 범위와 중단 사유를 추가 확인한다.
- 판단 기준을 `모두 중요하다`고 답하면 우선순위 미확정으로 해석한다.
- 추진 주체와 보고 대상이 서로 다르면 조정 책임자를 별도로 확인한다.

### 심층 자격심사 이관

디스커버리 결과는 MEDDIC 계열 심층 자격심사의 확정 결론이 아니라 입력 자료로 넘긴다. 각 항목에는 답변자, 확인일, 근거와 미확인 사항을 붙이며 추정 인물을 챔피언으로 확정하지 않는다.

- **메트릭:** 현재 기준선, 목표값, 측정 주기와 성과 보고 대상을 이관한다.
- **구매 절차:** 승인 단계, 단계 순서, 필수 회의체와 남은 확인 항목을 이관한다.
- **결정 기준:** 단계별 통과 기준, 우선순위와 기준 간 충돌 여부를 이관한다.
- **챔피언:** 추진 의지, 내부 조정 가능성, 정보 접근성과 현업 공수를 구분해 이관한다.

## 제약 영역 질문
<!--meta: sec=s7; dept=CNS|AIAX; level=시니어; ct_band=상; related=DSC-05#s2-->

제약 영역 질문은 일정, 보안, 규제, 연계, 운영과 인프라 조건을 기술 검토 전에 드러내기 위해 사용한다. 제약의 존재만으로 가능 또는 불가능을 단정하지 않으며 요구 품질과 함께 검토한다. 배치 유형별 상세 검토는 DSC-05#s2로 넘긴다.

### 제약 확인 질문

희망 조건과 필수 조건을 구분하고, 고객이 정한 조건인지 외부 일정이나 내부 정책에서 파생된 조건인지 확인한다. 규제 명칭이나 정책 조항이 불명확하면 담당자의 법률 판단으로 보완하지 않는다.

| 제약 항목 | 질문 | 추가 확인 사항 | 기록 예시 |
|---|---|---|---|
| 일정 | 희망 완료일은 언제이며 그 날짜가 필요한 근거는 무엇입니까 | 행사·감사·정책·내부 목표 구분 | 2027-03-31, 내부 목표 |
| 보안·전송 | 외부 환경으로 전송 가능한 데이터 범위는 어디까지입니까 | 원문·가공본·메타데이터별 허용 여부 | 가공본 조건부 가능 |
| 적용 규제 | 적용 대상으로 검토 중인 규제와 내부 정책은 무엇입니까 | 담당 부서, 확인 문서, 검토 상태 | 정책명, 버전 미확인 |
| 시스템 연계 | 어떤 시스템과 어떤 방식으로 연계해야 합니까 | API·파일·DB, 호출 주기, 시험 환경 | API 사양 미확인 |
| 운영 인수 | 구축 후 운영과 변경 승인은 어느 조직이 맡습니까 | 관리자, 사용자 지원, 장애 접수 주체 | 운영부서 추정 |
| 사용 인프라 | 사용할 수 있는 서버·저장소·망 환경은 무엇입니까 | CPU·GPU, 용량, 개발·시험·운영 분리 | GPU 수량 미확인 |

### 답변 상태 분류

모든 제약 답변에는 `확정·추정·미확인` 중 하나의 상태를 붙인다. 상태는 답변의 중요도가 아니라 근거와 확인 수준을 나타내며, 미확인 값을 안전한 조건이나 완화된 조건으로 임의 해석하지 않는다.

- **확정:** 권한 있는 담당자가 정책 문서, 시스템 사양 또는 승인 기록을 근거로 확인한 상태로 기록한다.
- **추정:** 담당자의 경험이나 계획에 근거한 답변으로, 추정 근거와 확인 예정일을 함께 기록한다.
- **미확인:** 답변자나 근거가 없거나 상충하는 상태로, 확인 책임자와 목표일을 지정한다.

### 기록 필드

제약별로 답변 원문과 내부 해석을 분리해 기록한다. 동일 제약에 상충하는 답변이 있으면 최근 답변으로 덮어쓰지 않고 출처별로 병기한다.

- `상태 / 답변 원문 / 근거 문서·답변자 역할`
- `적용 범위 / 예외 조건 / 기준일`
- `확인 책임 부서 / 확인 예정일`
- `요구 품질에 미치는 영향 / 후속 검토 문서 ID`

### 제약과 요구 품질의 충돌 조합

- 4주 완료와 높은 정확도 요구가 함께 제시되면 범위 축소 가능성과 평가 데이터 확보 시점을 먼저 확인한다.
- 외부 전송 금지와 외부 API 사용 가정이 충돌하면 전송을 진행하지 않고 DSC-05의 배치 대안을 검토한다.
- 실시간 연계 요구와 인터페이스 사양·시험 환경 부재가 겹치면 연계 가능성을 미확인으로 유지하고 시스템 담당자 확인을 요청한다.
- 운영 인수 일정이 정해졌으나 운영 주체가 없으면 인수 책임자 지정 전까지 운영 조건을 미확정으로 기록한다.
- 규제 대상 데이터와 외부 처리 요구가 함께 있으면 고객 보안·개인정보 담당 부서에 적용 범위와 필요한 검토 절차를 확인한다.

## 성공 기준 질문
<!--meta: sec=s8; dept=CNS; level=시니어; ct_band=상; related=DSC-04#s3-->

성공 기준 질문은 고객의 기대를 측정 가능한 지표로 변환하는 데 목적이 있다. 개선 대상, 기준선, 목표값, 측정 기간을 구분해 확인한다. “효율화”, “정확도 향상”, “사용성 개선”만으로는 성공 기준이 확정된 것으로 보지 않는다.

목표값은 고객이 희망하는 수치만 받지 않고 산정 근거와 업무상 의미를 함께 묻는다. 성공 판정 주체와 측정 방법이 다르면 같은 결과를 두고도 판단이 달라질 수 있으므로 사전에 합의한다. 상세 성공 기준 설계는 DSC-04#s3을 참고한다.

| 확인 요소 | 기본 질문 | 추가 확인 | 기록 기준 | 미확인 시 표시 |
|---|---|---|---|---|
| 개선 대상 | 무엇이 개선되면 성공으로 보십니까 | 업무 단계와 사용자 범위는 어디입니까 | 지표명과 적용 범위 | 범위 미확인 |
| 현재 기준선 | 현재 수치와 산정 기간은 얼마입니까 | 원천 자료와 집계 주기는 무엇입니까 | 값·기간·출처 | 기준선 없음 |
| 목표 수치 | 어느 수준까지 개선되어야 합니까 | 최소 기준과 희망 기준이 다릅니까 | 목표값·단위 | 목표 미확정 |
| 목표 근거 | 해당 수치를 정한 근거는 무엇입니까 | 내부 목표·운영 기준·과거 추세 중 무엇입니까 | 근거 유형과 자료 | 근거 미제시 |
| 측정 방법 | 누가 어떤 자료로 계산합니까 | 표본·제외 조건·계산식은 무엇입니까 | 산식·데이터·주기 | 측정법 미확정 |
| 판정 주체 | 최종 성공 여부는 누가 판단합니까 | 이견 발생 시 확인할 책임자는 누구입니까 | 역할·조직·확인 시점 | 판정자 미확인 |

### 질문 순서

1. “현재 가장 개선이 필요한 결과는 무엇입니까”라고 묻는다.
2. “그 결과를 지금은 어떤 수치로 관리합니까”라고 기준선을 확인한다.
3. “최근 3개월 또는 12개월 수치를 확인할 자료가 있습니까”라고 출처를 묻는다.
4. “최소한 어느 수치에 도달해야 도입 의미가 있다고 보십니까”라고 하한을 확인한다.
5. “그 목표는 어떤 운영 목표나 내부 판단에서 나온 것입니까”라고 근거를 묻는다.
6. “누가, 언제, 어떤 계산 방식으로 성공 여부를 확정합니까”라고 판정 절차를 확인한다.

### 기준선이 없을 때

- 동일 업무의 최근 4주 이상 표본을 수집할 수 있는지 확인한다.
- 시스템 로그가 없으면 수기 집계, 표본 관찰 또는 담당자 기록의 사용 가능성을 구분한다.
- 기준선 산출 전까지 목표값을 잠정값으로 표시하고 확정값처럼 기록하지 않는다.
- 기준선 확보가 불가능하면 대체 지표의 정의, 수집 기간, 책임자를 미확인 항목으로 남긴다.

기준선과 목표값은 동일한 단위, 모집단, 제외 조건으로 비교할 수 있어야 한다. 측정 방식이 달라지는 경우 환산 가능 여부를 확인하고 비교 불가 가능성을 기록한다. 고객 진술만으로 검증되지 않은 수치는 “고객 제시값”으로 표시한다.

### 다시 묻는 문장 예시

- “업무가 좋아졌다는 판단을 수치나 관찰 가능한 상태로 표현하면 무엇입니까.”
- “정확도가 높아진다는 것은 어떤 데이터에서 어떤 계산식으로 확인합니까.”
- “처리 시간이 줄어든다는 기준의 시작 시점과 종료 시점은 어디입니까.”
- “10% 개선의 분모가 건수, 시간, 비용 중 무엇인지 확인해 주시겠습니까.”
- “이 기준을 최종 승인할 역할과 실제 측정을 담당할 역할은 각각 누구입니까.”

## 기록 양식과 미확인 항목 처리
<!--meta: sec=s9; dept=CNS; level=주니어; ct_band=중; related=none-->

디스커버리 기록은 사실, 고객 진술, 내부 해석을 구분해 작성한다. 고객이 말하지 않은 인과관계나 우선순위를 사실처럼 보완하지 않는다. 발언 출처는 실명 대신 참석자 역할과 발언 일시로 식별한다.

기록 담당자는 미팅 종료 후 1영업일 이내에 초안을 작성한다. 확인되지 않은 내용은 빈칸으로 두지 않고 미확인 사유, 확인 책임자, 기한을 남긴다. 후속 확인으로 내용이 변경되면 최초 기록을 삭제하지 않고 변경일과 근거를 추가한다.

| 기록 항목 | 필수 내용 | 작성 규칙 | 미확인 처리 |
|---|---|---|---|
| 회의 기본정보 | 일시·방식·참석 역할 | 고객명 대신 내부 기회 식별자 사용 | 참석 역할 미확인 표시 |
| 고객 진술 | 과제·현행 방식·요구 결과 | 원문 요지와 발언 역할 기재 | 상충 진술 병기 |
| 내부 해석 | 원인 가설·검토 필요사항 | `[내부 해석]` 표기 | 근거 부족 표시 |
| 데이터 단서 | 데이터 유형·보유 여부 | 존재 확인과 사용 가능성 분리 | 확인 책임자 지정 |
| 의사결정 정보 | 절차·관여 역할·예정 시점 | 추정과 확정 구분 | 확인 예정일 기재 |
| 제약 사항 | 일정·환경·보안·운영 제약 | 고객 진술과 자료 근거 구분 | 영향도 미평가 표시 |
| 성공 기준 | 기준선·목표·측정 주체 | 단위와 측정 기간 포함 | 잠정값 표시 |
| 미확인 목록 | 질문·필요 자료·차단 영향 | 항목별 한 줄 작성 | 책임자·기한 필수 |
| 후속 조치 | 확인 요청·내부 검토 | 담당 부서와 완료 조건 기재 | 지연 사유 추가 |

### 작성 및 미확인 처리 규칙

- 직접 들은 내용은 `[고객 진술]`, 담당자의 판단은 `[내부 해석]`으로 구분한다.
- 수치에는 단위, 기준 기간, 출처를 함께 적고 출처가 없으면 “출처 미확인”으로 표시한다.
- 미확인 항목마다 고객 측 또는 내부 확인 책임 역할을 1명 이상 지정한다.
- 확인 기한은 원칙적으로 다음 단계 판단일의 2영업일 전까지로 정한다.
- 서로 다른 참석자의 진술이 충돌하면 하나를 선택하지 않고 양쪽 내용을 함께 남긴다.
- 기한이 지난 항목은 삭제하지 않고 영향도를 상·중·하로 갱신한다.

기록은 진단과 후속 판단에 필요한 범위로 제한한다. 계정 비밀번호, 접근 토큰, 불필요한 개인정보, 확인되지 않은 평판성 발언은 남기지 않는다. 녹음·녹화는 고객의 명시적 동의와 내부 보관 기준이 확인되지 않으면 수행하지 않는다.

### 보존·공유 규칙

- 기본 공유 범위는 해당 기회의 SALES 담당자, CNS 책임자와 지정된 기술 검토자로 제한한다.
- DATA·AIAX·BE에는 담당 검토에 필요한 항목만 공유하고 전체 기록을 자동 배포하지 않는다.
- 고객에게 내부 해석, 내부 우려 수준, 추진 가능성에 관한 메모를 그대로 전달하지 않는다.
- 기준선, 목표값, 의사결정 절차처럼 후속 판단에 직접 영향을 주는 항목은 고객 확인을 요청한다.
- 고객 확인 요청본에는 고객 진술 요약과 미확인 질문만 포함하고 내부 판단은 제외한다.
- 고객의 수정 회신은 수신일, 수정 항목, 수정 전후 내용을 함께 보존한다.
- 전체 회의록 승인을 받지 못했다는 이유만으로 고객 진술을 확정 사실로 변경하지 않는다.

## 디스커버리 종료 조건과 다음 단계 분기
<!--meta: sec=s10; dept=CNS|SALES; level=시니어; ct_band=상; related=DSC-02#s1-->

디스커버리는 모든 질문에 답을 받았을 때가 아니라 세 가지 판별 과제에 대해 판단 가능한 정보가 모였을 때 종료한다. 판정 결과는 긍정일 필요가 없으며, 해결 필요성이 낮거나 검증이 불가능하다는 결론도 종료 근거가 된다. 핵심 미확인 항목이 결론을 바꿀 수 있으면 종료하지 않는다.

종료 점검은 CNS 책임자와 SALES 기회 담당자가 공동으로 수행한다. 기술 타당성 자체를 확정하지 않고, DSC-02#s1의 검토에 들어갈 입력이 갖춰졌는지를 판단한다. 데이터·인프라의 상세 평가는 해당 소관 문서로 넘긴다.

| 판별 과제 | 종료 시 필요한 정보 | 판정 가능 기준 | 미충족 예시 | 후속 처리 |
|---|---|---|---|---|
| 문제가 실재하는가 | 현행 업무·발생 상황·영향 대상 | 구체적 사례 1건 이상과 담당 역할 확인 | 기대 기능만 있고 업무 문제가 없음 | 추가 확인 또는 중단 권고 |
| 문제 규모가 유의미한가 | 빈도·시간·오류·비용 중 1개 이상 | 기준선 또는 산출 가능한 자료 확인 | 영향 표현만 있고 단위가 없음 | 기준선 확인 |
| 해결 가능한 형태인가 | 입력·처리·출력·사용 흐름 | 검토 대상 범위와 주요 제약 식별 | 요구 범위가 전사 혁신 수준으로 포괄적임 | 범위 재정의 |
| 공통 완결성 | 성공 기준·관여 역할·미확인 목록 | 다음 판단을 막는 상위 위험이 식별됨 | 책임자와 확인 기한이 없음 | 기록 보완 |

### 다음 단계 네 가지

- **타당성 검토 착수**: 세 가지 판별 과제가 모두 판단 가능하고 핵심 미확인 항목의 책임자와 기한이 정해진 경우 적용한다.
- **추가 디스커버리**: 결론을 바꿀 수 있는 정보가 부족하지만 담당자 또는 자료를 추가로 확보할 수 있는 경우 적용한다.
- **보류**: 과제는 존재하나 고객 일정, 내부 우선순위 또는 필수 자료 준비 시점이 확정되지 않은 경우 적용한다.
- **중단 권고**: 문제가 확인되지 않거나 범위 정의가 불가능하고 추가 확인 가능성도 낮은 경우 적용한다.

분기 결정은 CNS 시니어 이상 책임자와 SALES 담당자가 공동 기록하며, 기술 쟁점은 AIAX·BE·DATA 담당 의견을 첨부한다. 의견이 다르면 단일 결론으로 덮지 않고 쟁점, 각 의견, 재판정 조건을 남긴다. 분기 결과는 디스커버리 종료일로부터 2영업일 이내에 등록한다.

### 분기 결정 기록

1. 세 가지 판별 과제별 결론과 근거를 기재한다.
2. 핵심 미확인 항목과 결과에 미치는 영향을 기재한다.
3. 선택한 분기와 선택하지 않은 분기의 배제 사유를 기재한다.
4. 공동 결정자와 기술 검토 참여 역할을 기재한다.
5. 다음 확인일 또는 검토 착수 예정일을 기재한다.
6. 고객에게 전달할 확인 사항과 내부 한정 사항을 구분한다.

### 추가 회차 운영 상한

- 최초 디스커버리 외 추가 회차는 원칙적으로 최대 2회로 제한한다.
- 추가 회차는 1회당 90분 이하로 운영하고 확인할 미해결 항목을 사전에 지정한다.
- 동일 질문을 반복하기보다 신규 참석자, 자료 또는 의사결정 정보를 확보할 때만 회차를 연다.
- 총 3회 후에도 핵심 정보가 없으면 보류 또는 중단 권고 중 하나로 분기한다.
- 예외 연장은 CNS 부장과 SALES 부장의 공동 승인 1회만 허용한다.
- 연장 기록에는 추가 확보 대상, 책임자, 완료 기한과 미확보 시 분기를 명시한다.
