# 재사용 자산 등록·공유 제도
<!--meta: doc=PSY-05; doc_type=asset_registry; tier=1; topic=PROCESS; disclosure=internal; status=active-->

## 제도의 목적과 자산의 정의
<!--meta: sec=s1; dept=AIAX|BE|DATA|CNS; level=주니어|시니어; ct_band=하; related=none-->
이 제도는 프로젝트마다 유사한 코드, 문서, 평가 도구와 운영 절차를 처음부터 다시 만드는 비용을 줄이기 위해 운영한다.  
재사용 가능한 결과물을 찾고 검증된 형태로 공유하여 착수 기간, 구현 공수와 품질 편차를 줄이는 것이 목적이다.  
모든 구현을 하나로 통합하거나 고객별 요구사항을 강제로 공통화하는 제도는 아니다.

| 판단 항목 | 자산으로 인정하는 상태 | 인정하지 않는 상태 |
|---|---|---|
| 재사용성 | 둘 이상의 사업에서 수정 없이 또는 설정 변경만으로 사용할 수 있다 | 특정 사업의 구조와 값에 묶여 있다 |
| 소유권 | 담당 소유자가 이름 또는 역할 단위로 지정되어 있다 | 유지 여부를 판단할 담당자가 없다 |
| 완결성 | 사용 문서와 검증 수단이 결과물에 포함되어 있다 | 코드나 파일만 존재한다 |

세 가지 판단 항목을 모두 충족한 결과물만 재사용 자산으로 본다.  
한 항목이라도 충족하지 못하면 해당 결과물은 자산이 아니라 코드 조각이다.  
코드 조각에는 미완성 스크립트, 출처를 확인하지 않은 복사 코드, 특정 고객 환경에 고정된 설정 파일이 포함된다.  
코드 조각은 등록 대상이 아니며 프로젝트 저장소 안에서만 관리한다.

재사용성의 ‘설정 변경’은 문서에 정의된 입력값, 환경 변수, 매핑 파일 또는 배포 옵션을 바꾸는 행위를 뜻한다.  
핵심 로직을 고치거나 데이터 구조를 다시 설계해야 하면 동일 자산의 설정 사용으로 보지 않는다.  
둘 이상의 사업은 계약이나 프로젝트 식별자가 서로 다른 수행 건을 기준으로 판정한다.  
같은 사업의 개발·검증·운영 환경에 반복 배포한 것은 하나의 사용 사례로 계산한다.

소유자는 다음 책임을 인수한 개인 또는 부서 역할이어야 한다.

- 사용 문의를 접수하고 적용 가능 여부를 판단한다.
- 결함과 개선 요청의 처리 방향을 결정한다.
- 더 이상 유지할 수 없을 때 대체 담당자 지정 또는 폐기를 요청한다.
- 문서와 검증 수단이 실제 결과물과 어긋나지 않는지 확인한다.

사용 문서는 최소한 목적, 적용 조건, 입력값, 실행 또는 적용 방법, 알려진 제한을 식별할 수 있어야 한다.  
검증 수단은 자동 테스트에 한정하지 않으며 재현 가능한 점검표, 평가 명령, 예시 입출력 또는 검수 절차도 허용한다.  
다만 검증 결과를 제3자가 같은 조건에서 재확인할 수 있어야 한다.

다음 항목은 이 제도의 판단 범위에서 제외한다.

- 고객 산출물의 소유권과 지식재산권 귀속은 PRP-04#s7 참조
- 자산 변경 사항의 릴리즈 노트 작성과 버전 공지는 「릴리즈 노트 작성 및 내부 공유 규칙」#s10 참조
- 프로젝트별 납품 범위와 고객 사용권은 해당 계약 문서에 따라 사안별 확인이 필요하다.

등록 여부가 불명확하면 신청자는 결과물을 먼저 코드 조각으로 취급한다.  
심사를 통과하기 전까지 자산 명칭, 표준 제공물 또는 공식 공용 모듈이라는 표현을 사용하지 않는다.

## 자산 유형 분류
<!--meta: sec=s2; dept=AIAX|BE|DATA|CNS; level=주니어|시니어; ct_band=중; related=s1-->
등록 신청자는 심사 전에 자산 유형을 하나로 지정한다.  
유형은 저장 형식이 아니라 주된 사용 목적과 소비 방식으로 판정한다.  
여러 구성요소가 결합된 묶음은 사용자가 직접 적용하는 핵심 결과물을 주 유형으로 삼고 나머지를 첨부물로 표시한다.

| 유형 | 포함 예시 | 유형별 최소 등록 요건 | 대표 사용 방식 |
|---|---|---|---|
| 코드 모듈 | 라이브러리, 시스템 어댑터 | 공개 인터페이스 설명, 의존성 목록, 실행 테스트 | 프로젝트 코드에서 패키지 또는 모듈로 호출한다 |
| 서비스 템플릿 | 기동 가능한 애플리케이션 뼈대 | 기동 절차, 기본 설정표, 상태 확인 방법 | 복제 후 서비스별 설정과 업무 로직을 추가한다 |
| 설정·인프라 정의 | 배포 설정, 환경 구성 정의 | 변수 목록, 적용 순서, 되돌리기 확인 절차 | 대상 환경의 값만 주입하여 배포 기반을 구성한다 |
| 데이터 처리 파이프라인 | 수집·정제·변환 흐름 | 입력·출력 스키마, 품질 점검, 실패 재처리 방법 | 데이터 원천과 목적지 매핑을 바꾸어 실행한다 |
| 평가셋과 평가 절차 | 평가 데이터, 채점 규칙, 실행 도구 | 데이터 설명, 지표 산식, 기준 결과, 재현 절차 | 모델 또는 기능 후보를 동일 조건에서 비교한다 |
| 프롬프트와 프롬프트 검증 묶음 | 프롬프트, 예시, 판정 기준 | 적용 모델 조건, 입력 제약, 평가 사례, 실패 조건 | 변수값을 치환하고 검증 묶음으로 결과를 확인한다 |
| 문서 템플릿 | 제안 서술 블록, 설계 문서 양식, 점검표 | 사용 목적, 필수·선택 항목, 작성 예시, 금지 사례 | 프로젝트 맥락에 맞춰 항목을 선택하고 내용을 채운다 |
| 운영 절차서 | 배포, 점검, 장애 대응 절차 | 역할, 시작 조건, 단계, 완료 증적, 예외 처리 | 담당자가 순서와 판정 기준에 따라 업무를 수행한다 |

코드 모듈과 서비스 템플릿은 실행 가능 여부로 구분한다.  
독립 기동 단위와 기본 실행 경로가 있으면 서비스 템플릿으로 분류한다.  
다른 프로그램에 포함되어 호출될 때만 동작하면 코드 모듈로 분류한다.

설정·인프라 정의는 비밀값 자체를 포함하지 않고 값의 자리, 형식과 적용 규칙을 제공한다.  
데이터 처리 파이프라인은 단순 쿼리 모음이 아니라 입력부터 결과 생성까지의 실행 순서를 가져야 한다.  
평가셋만 있고 판정 절차가 없거나 판정 절차만 있고 재현용 입력이 없으면 등록 신청을 보완한다.  
프롬프트는 단일 문장만 제출하지 않고 검증 사례와 기대 판정을 하나의 묶음으로 구성한다.

제안 서술 블록은 반복되는 제안 논리를 검토 가능한 문장 단위로 제공하므로 문서 템플릿 자산에 해당한다.  
단순히 이전 제안서의 고객명만 지운 문단은 제안 서술 블록으로 인정하지 않는다.  
CNS가 해당 블록의 등록 책임 부서이며 기술 내용이 포함되면 AIAX, BE 또는 DATA의 검토자를 지정한다.  
등록본에는 적용 가능한 제안 상황, 필요한 근거 입력, 수정이 필요한 자리와 사용 금지 조건을 표시한다.

유형을 잘못 지정한 경우 다음 순서로 변경한다.

1. 신청자 또는 소유자가 오분류 사유와 변경할 유형을 등록 기록에 남긴다.
2. 기존 유형의 심사가 진행 중이면 심사를 중단하고 새 유형의 최소 요건으로 다시 점검한다.
3. 이미 등록된 자산이면 소유자가 사용 프로젝트에 유형 변경 사실과 적용 영향을 알린다.
4. 식별자는 유지하되 유형 이력에 변경 전·후 값과 변경일을 기록한다.
5. 변경으로 구성 단위가 둘 이상으로 나뉘면 각각 별도 등록 신청을 제출한다.

유형 변경만으로 등급이나 사용 승인이 자동 변경되지는 않는다.  
명칭이 비슷하다는 이유로 서로 다른 유형을 하나의 등록 건에 합치지 않는다.

## 자산 등급 체계
<!--meta: sec=s3; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s2|s8-->
등급은 자산의 사용 실적, 검증 수준과 지원 가능 상태를 나타낸다.  
신규 프로젝트는 등급을 확인한 뒤 적용 여부와 필요한 승인을 판단한다.

| 등급 | 의미와 보증 수준 | 사용 조건 | 승격 또는 전환 요건 |
|---|---|---|---|
| 실험 | 한 사업에서만 검증되었으며 회사 차원의 재사용 적합성을 보증하지 않는다 | 사용 프로젝트가 검증과 장애 위험을 직접 부담한다 | 두 개 이상 사업의 사용 증적, 문서와 테스트를 확보하면 검증 승격을 신청한다 |
| 검증 | 둘 이상 사업에서 사용했고 문서와 테스트를 보유한다 | 적용 조건과 알려진 제한을 확인한 프로젝트가 사용할 수 있다 | 반복 사용 실적, 지원 담당, 호환성 관리 근거를 갖추면 표준 승격을 신청한다 |
| 표준 | 신규 사업에서 대안을 만들기 전에 먼저 검토해야 하는 기본 선택이다 | 미사용 시 프로젝트가 기능·비용·제약 사유를 기록한다 | 별도 상위 등급은 없으며 기준 충족 여부를 정기 재확인한다 |
| 폐기예정 | 지원 종료가 결정되어 신규 사용을 금지한 상태이다 | 기존 사용 건만 이동 기한까지 제한적으로 운영한다 | 대체 또는 제거가 끝나면 폐기 절차로 전환한다 |

표준 등급은 모든 프로젝트에 강제로 적용한다는 뜻이 아니다.  
고객 환경, 성능 조건, 계약 범위 또는 기술 제약이 맞지 않으면 다른 방식을 선택할 수 있다.  
이 경우 비교한 자산 식별자와 배제 근거를 프로젝트 설계 기록에 남긴다.

| 등급 | 소유자 최초 응답 시한 | 호환성 약속 |
|---|---:|---|
| 실험 | 문의 접수 후 5영업일 이내 | 기존 인터페이스와 동작의 유지 약속이 없다 |
| 검증 | 문의 접수 후 3영업일 이내 | 동일 주 버전 안에서 문서화된 사용 방식의 변경 여부를 알린다 |
| 표준 | 문의 접수 후 1영업일 이내 | 호환성 파괴 변경에 대체 경로와 전환 정보를 제공한다 |
| 폐기예정 | 문의 접수 후 5영업일 이내 | 공지된 이동 기한까지만 기존 사용에 필요한 정보를 제공한다 |

최초 응답은 해결 완료가 아니라 접수 확인, 담당자, 다음 조치와 예상 회신일을 전달하는 것을 뜻한다.  
등급별 버전 번호 부여와 지원 범위의 세부 기준은 s8에서 정한다.

승격 신청은 소유자가 사용 증적, 최신 검증 결과와 미해결 제한 사항을 제출하여 개시한다.  
실험에서 검증으로 올릴 때 같은 사업의 환경별 배포 횟수를 복수 사업 실적으로 계산하지 않는다.  
검증에서 표준으로 올릴 때는 신규 사업의 기본 선택으로 제시해도 되는 적용 범위가 명시되어야 한다.  
심사자는 높은 등급에 맞는 응답 시한을 소유자가 이행할 수 있는지도 확인한다.

다음 사유가 발생하면 한 단계 하향 또는 폐기예정 전환을 검토한다.

- 최근 사용 사업이 줄어 현재 등급의 실적 근거를 충족하지 못한다.
- 소유자가 퇴직·이동했으며 대체 담당자가 지정되지 않았다.
- 보안 이슈로 안전한 사용 조건을 즉시 제시할 수 없다.
- 테스트가 반복 실패하거나 문서와 실제 동작의 불일치가 확인된다.
- 핵심 의존성이 종료되어 호환성 약속을 이행할 수 없다.

보안 이슈가 사용 프로젝트에 영향을 줄 가능성이 있으면 등급 심사가 끝날 때까지 신규 적용을 중단한다.  
소유자 부재 상태가 10영업일을 넘으면 검증 또는 표준 등급을 유지하지 않는다.  
사용 사업 감소만으로 즉시 폐기하지 않으며 대체 수단, 유지 비용과 향후 수요를 함께 심사한다.

등급이 표시되지 않은 결과물은 미등록 상태로 간주하고 신규 사업에 사용하지 않는다.  
저장소 이름, 과거 사용 경험 또는 작성자의 직급으로 등급 표시를 대신할 수 없다.  
등록 화면과 배포 가능한 결과물의 문서에는 동일한 등급을 표시한다.

실험 등급을 고객 인수 산출물에 포함하려면 수행 부서 부장과 자산 소유자의 사전 승인을 받는다.  
승인 기록에는 채택 사유, 예상 영향, 프로젝트 자체 검증 항목과 문제 발생 시 대체 방안을 포함한다.  
고객 계약상 고지나 동의가 필요한지는 계약 문서에 따라 사안별 확인이 필요하다.

## 등록 요건
<!--meta: sec=s4; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=상; related=s3-->
등록 신청자는 자산 본체와 등록 문서를 함께 제출한다.  
등록 문서는 아래 항목의 명칭과 순서를 유지하며, 해당 내용이 없으면 빈칸 대신 `없음`과 판단 근거를 적는다.

| 제출 항목 | 필수 기재 내용 | 합격 기준 | 누락 시 처리 |
|---|---|---|---|
| 개요 | 해결하는 문제, 대상 사용자, 입력과 출력, 쓰지 말아야 하는 경우 | 적용 여부를 문서만으로 판단할 수 있다 | 거절 |
| 사용 예제 | 준비 조건, 실행 명령 또는 순서, 예상 결과 | 새 환경에서 복사해 실행할 수 있는 최소 예제이다 | 거절 |
| 설정 항목 | 항목명, 자료형, 기본값, 허용 범위, 필수 여부 | 실제 구현과 명칭·기본값이 일치한다 | 보완 요청 |
| 검증 수단 | 테스트 또는 검증 절차, 실행 방법, 합격 조건 | 제3자가 성공과 실패를 재현해 판정할 수 있다 | 거절 |
| 의존성 | 구성요소명, 최소·최대 버전 또는 고정 버전, 필수 여부 | 설치 파일 및 실제 참조 상태와 일치한다 | 거절 |
| 라이선스 정보 | 자산 자체 라이선스와 제3자 구성요소 정보의 위치 | 불명확한 항목이 없고 확인 근거에 접근할 수 있다 | 거절 |
| 소유자·부소유자 | 소속 부서, 이름, 연락 경로, 역할 구분 | 두 역할이 모두 지정되고 현재 재직자가 맡는다 | 거절 |
| 지원 범위 | 문의 대상, 지원 버전, 지원하지 않는 작업 | 사용자가 지원 가능 범위를 사전에 구분할 수 있다 | 보완 요청 |
| 알려진 제한 | 성능·환경·데이터·호환성 제약과 우회 방법 | 발견된 제한을 숨기지 않고 영향 조건을 적는다 | 보완 요청 |
| 변경 이력 | 버전, 일자, 변경 내용, 호환성 영향 | 최초 등록을 포함해 배포 단위별 변경을 추적할 수 있다 | 보완 요청 |

개요에는 기능 목록보다 먼저 해결하려는 문제를 한 문장으로 적는다.  
이어 적용 가능한 입력 조건과 기대 결과를 수치, 형식 또는 상태로 표현한다.  
`쓰지 말아야 하는 경우`에는 오판 가능성이 높은 데이터 조건, 미지원 환경과 대체 자산 선택 기준을 적는다.  
이 항목은 재사용 횟수를 늘리기 위한 설명이 아니라 부적합한 적용과 후속 재작업을 차단하기 위한 기준이다.

사용 예제는 외부에 존재하는 개발 환경이나 작성자 개인 계정에 의존해서는 안 된다.  
예제 입력은 비밀정보 제거 검사를 통과한 고정 자료를 사용하며 PSY-05#s5 참조로 연결한다.  
실행 결과가 파일이면 파일명과 확인할 필드를, 화면이면 확인할 상태를 명시한다.  
무작위 결과가 발생하는 자산은 허용 오차 또는 판정 규칙을 함께 기재한다.

설정 항목의 기본값은 코드, 배포 파일과 설명서에서 동일해야 한다.  
환경별 권장값은 기본값으로 표시하지 않고 별도 권장 설정으로 구분한다.  
버전 범위를 특정할 수 없는 의존성은 그 사유와 마지막 검증 버전을 적어 보완 심사를 받는다.

검증 수단은 자동 테스트를 우선 제출하되 자동화가 불가능하면 수동 절차를 허용한다.  
수동 절차에는 준비 상태, 작업 순서, 예상 결과와 실패 판정을 모두 포함한다.  
테스트 존재 여부만 적거나 내부 실행 화면만 첨부한 신청은 재현 가능한 검증으로 인정하지 않는다.

소유자는 기술 판단과 변경 승인 창구를 맡고 부소유자는 소유자 부재 시 등록 질의에 응답한다.  
동일인을 두 역할에 중복 지정할 수 없다.  
지원 범위에는 적용 대행, 오류 분석, 환경 구성 중 제공하는 작업과 제공하지 않는 작업을 나눈다.

등록 문서는 코드 또는 실행 가능한 자산과 같은 저장소에서 관리한다.  
같은 변경 요청에서 구현과 설명의 차이를 검토하고, 버전별 문서를 자산 상태와 함께 되돌릴 수 있어야 하기 때문이다.  
별도 문서 시스템의 안내 페이지는 허용하지만 원본 등록 문서를 대신할 수 없다.

신청자는 제출 직전에 문서의 버전 표기, 예제 실행 결과와 의존성 잠금 정보를 확인한다.  
심사자는 필수 항목의 빈칸을 추정해 채우지 않으며, 거절 항목이 하나라도 있으면 심사를 종료한다.  
보완 요청만 있는 경우 신청자에게 항목별 수정 위치와 재제출 조건을 기록해 돌려보낸다.  
등급 판정과 승격 조건은 PSY-05#s3 참조로 처리한다.

## 반출 전 비밀정보 제거 검사
<!--meta: sec=s5; dept=BE|AIAX|DATA|CNS; level=시니어; ct_band=상; related=s4-->
특정 고객 사업에서 작성한 결과물을 공통 자산 저장소로 옮기기 전에 비밀정보 제거 검사를 실시한다.  
검사를 통과하지 않은 브랜치, 파일, 데이터와 커밋 이력은 등록 심사에 제출할 수 없다.

| 제거 대상 | 발견 위치 예시 | 통과 기준 |
|---|---|---|
| 고객사명과 식별 가능한 약어 | 패키지명, 변수명, 주석, 파일 경로 | 명칭과 조합 가능한 약어가 남아 있지 않다 |
| 사람 이름과 연락처 | 예제, 로그, 문서 작성자란, 테스트 계정 | 이름, 전화번호, 전자우편 주소가 제거되었다 |
| 내부 호스트명·IP·엔드포인트·계정 | 설정 파일, 실행 스크립트, 오류 로그 | 실제 접속 정보가 일반화된 대체값으로 바뀌었다 |
| 실데이터와 그 표본 | 테스트 픽스처, 노트북 출력, 화면 캡처 | 원본·부분 행·집계 전 표본이 포함되지 않았다 |
| 영업비밀 성격의 고객 업무 규칙 | 조건식, 프롬프트, 의사결정표 | 고객 고유 규칙을 역추론할 수 없다 |
| 고객 조직도와 승인 단계 | 절차 문서, 역할표, 워크플로 | 조직 구조와 내부 결재 흐름이 남아 있지 않다 |
| 고객 시스템 오류 메시지 원문 | 로그, 테스트 예상값, 이슈 기록 | 원문 대신 일반화된 오류 유형을 사용한다 |
| 계약 금액과 단가 | 주석, 계산 시트, 샘플 설정 | 금액, 단가와 산식 식별값이 제거되었다 |

작성자는 검사 전에 고객별 검색어 목록을 만든다.  
검색어에는 정식 명칭, 통용 약어, 도메인, 담당자명, 시스템명, 내부 코드와 프로젝트 식별자를 포함한다.  
대소문자, 공백, 하이픈과 한글·영문 표기 차이를 각각 검색한다.  
압축 파일, 이미지, 노트북 출력 셀과 생성된 산출물도 검색 범위에 넣는다.

검사자는 다음 순서로 확인한다.

1. 저장소 전체에서 검색어 목록과 IP·전자우편·URL 형식 문자열을 검색한다.
2. 테스트 픽스처의 원천, 행 수, 필드명과 값 조합을 확인한다.
3. 문서, 화면 캡처, 로그 및 실행 결과에 식별 단서가 있는지 점검한다.
4. 전체 커밋 이력에서 삭제 전 파일과 과거 문자열을 검색한다.
5. 발견 항목의 제거 또는 일반화 결과를 다시 실행해 검증한다.

현재 파일에서 삭제했더라도 커밋 이력에 대상 정보가 남아 있으면 제거된 것으로 보지 않는다.  
이 경우 정제된 이력으로 반출본을 다시 만들고 원본 저장소와의 연결 여부를 재검사한다.  
단순히 최신 커밋에서 파일을 지우거나 접근 권한을 낮춘 조치는 합격으로 인정하지 않는다.

검사 책임자는 작성자와 다른 사람으로 지정한다.  
작성자는 고객 맥락에 익숙해 약어, 축약 필드와 익명화가 불충분한 표본을 일반 정보로 오인할 수 있기 때문이다.  
검사 책임자는 AIAX·BE·DATA·CNS 중 해당 결과물의 내용을 판독할 수 있는 시니어가 맡는다.

| 검사 기록 항목 | 기록 방법 |
|---|---|
| 자산명·후보 버전 | 등록 신청과 동일한 식별자를 기재한다 |
| 원천 프로젝트 | 내부 추적이 가능한 명칭만 제한된 기록에 남긴다 |
| 검사 대상 | 저장소, 브랜치, 커밋 식별자, 첨부 파일을 열거한다 |
| 검색어 목록 | 실제 사용한 문자열과 형식 규칙을 첨부한다 |
| 발견 내역 | 위치, 정보 유형, 조치 결과를 건별 기록한다 |
| 이력 검사 결과 | 사용 도구 또는 절차와 최종 판정을 적는다 |
| 작성자·검사자 | 이름, 부서, 검사일을 남긴다 |
| 판정 | 통과, 재검사, 등록 불가 중 하나를 선택한다 |

검사 기록에는 제거 대상의 실제 값을 복사하지 않고 유형과 위치만 적는다.  
재검사 판정이면 작성자가 수정한 뒤 동일 검사자가 변경 범위와 이력을 다시 확인한다.  
고객 업무 규칙이 일반 원리인지 영업비밀 성격인지 판단하기 어려우면 등록을 보류한다.

계약상 반출 제한이 설정된 산출물은 자산 등급과 관계없이 등록할 수 없다.  
산출물 귀속, 데이터 이용 및 비밀유지 범위는 계약별로 다르므로 사안별 확인이 필요하다.  
판단 근거와 확인 절차는 PRP-04#s7·s14 참조로 처리한다.

## 라이선스와 제3자 코드 확인
<!--meta: sec=s6; dept=AIAX|BE; level=시니어; ct_band=상; related=s4|s5-->
등록 신청자는 자산에 포함되거나 실행·배포 과정에서 호출되는 제3자 구성요소 목록을 제출한다.  
패키지 관리 파일만 첨부하지 않고 직접 사용과 전이 의존성을 구분해 사람이 확인할 수 있는 목록으로 만든다.

| 목록 항목 | 기재 기준 |
|---|---|
| 구성요소 | 패키지, 라이브러리, 모델, SDK, API 또는 도구의 식별 가능한 명칭을 적는다 |
| 버전 | 고정 버전 또는 허용 범위를 기재하고 미확정 표기는 허용하지 않는다 |
| 라이선스 종류 | 확인한 라이선스 명칭과 원문 위치를 적는다 |
| 사용 형태 | 수정, 링크, 포함, 호출, 개발 도구 사용 중 해당 방식을 표시한다 |
| 배포 여부 | 고객 전달물 포함, 서버 배포, 내부 전용 중 하나 이상을 표시한다 |
| 확인 근거 | 배포본 고지문, 저장소 파일, 공식 약관 등 확인 위치를 연결한다 |

라이선스 종류를 추정하거나 검색 결과의 요약문만 근거로 작성해서는 안 된다.  
복수 라이선스가 제시된 구성요소는 실제 선택한 조건과 선택 근거를 기록한다.  
소스와 바이너리의 조건이 다르면 각각 별도 행으로 관리한다.  
버전 변경으로 조건이 달라질 수 있으므로 `최신 버전과 동일`이라는 표현은 사용하지 않는다.

라이선스 정보가 없거나 원문과 배포 조건을 확인할 수 없는 코드는 등록하지 않는다.  
출처 미상의 코드 조각, 작성자를 확인할 수 없는 복사본과 라이선스 표기가 제거된 파일도 동일하게 처리한다.  
해당 부분을 제거하거나 사용 조건이 확인된 대체물로 교체한 뒤 새 등록 신청을 한다.

카피레프트 성격의 라이선스가 포함된 자산을 고객 전달물에 사용할 때에는 적용 전에 별도 확인을 받는다.  
신청자는 사용 형태, 수정 여부, 링크 방식, 전달 범위와 소스 제공 관련 조건을 정리한다.  
AIAX 또는 BE의 해당 자산 소유 부서 부장이 검토 결과와 사용 허용 범위를 승인한다.  
조건 해석이나 계약과의 양립 여부가 불명확하면 사용을 중단하고 사안별 확인을 진행한다.

외부 모델과 API를 사용하는 자산은 다음 제한을 자산 설명에 명시한다.

- 입력·출력물의 허용된 사용 범위와 보관 조건
- 제공자가 입력 또는 출력물을 학습에 사용하는지 여부
- 결과물 또는 서비스의 재판매 금지 조건
- 호출 지역, 계정 유형이나 용도에 따른 제한
- 약관 확인일과 적용한 서비스 버전

이 정보는 동일한 코드라도 고객 전달 방식과 데이터 흐름에 따라 사용할 수 없는 경우를 사전에 구분하기 위해 기록한다.  
약관 링크만 남기지 않고 실제 적용에 영향을 주는 제한을 요약한다.  
학습 사용 여부를 확인할 수 없으면 `미확인`으로 배포하지 않고 확인 완료 전까지 등록 심사를 보류한다.

자산 사용자가 적용 과정에서 제공한 자료는 제3자 구성요소 라이선스의 별도 확인 대상으로 보지 않는다.  
이 경우 제공자, 제공일, 자료명과 사용 목적을 출처 기록으로 남긴다.  
다만 그 자료를 자산 본체에 포함하거나 다른 프로젝트에 배포하려는 순간에는 제3자 구성요소로 다시 분류한다.  
비밀정보와 계약상 반출 가능성 판단은 이 기준으로 대체하지 않으며 PSY-05#s5 참조로 처리한다.

소유자는 지원 중인 버전의 의존성 라이선스와 외부 서비스 약관 변경을 확인한다.  
변경을 발견한 사람은 소유자와 부소유자에게 변경 원문, 확인일, 영향 버전을 전달한다.  
소유자는 사용 프로젝트 목록을 기준으로 영향 대상을 식별하고 해당 프로젝트의 기술 책임자에게 통지한다.  
계속 사용이 불가능하거나 추가 의무가 발생할 가능성이 있으면 신규 적용과 배포를 즉시 보류한다.  
변경에 따른 버전 조정과 지원 종료 처리는 PSY-05#s8 참조로 진행한다.

## 심사 절차와 심사 항목
<!--meta: sec=s7; dept=AIAX|BE|DATA|CNS; level=시니어; ct_band=상; related=s4|s5|s6-->
심사는 신청자가 제출한 증적을 기준으로 진행하며, 구두 설명만으로 합격 처리하지 않는다. 기술 심사자는 자산 소속팀 시니어 1명과 실제 적용 가능성이 있는 다른 팀 시니어 1명으로 구성한다.

| 단계 | 담당 | 기준 소요일 | 산출물 |
|---|---|---:|---|
| 등록 신청 | 신청자 | 1영업일 | 등록 신청서, 자산 본체, 증적 링크 |
| 요건 확인 | 자산 심사 담당자 | 2영업일 | 형식 확인표, 누락 목록 |
| 기술 심사 | 기술 심사자 2명 | 5영업일 | 기술 심사표, 보완 의견, 시험 결과 |
| 반출 검사 확인 | 자산 심사 담당자 | 1영업일 | 비밀정보 제거 검사 확인 기록 |
| 라이선스 확인 | 기술 심사자 중 지정자 | 2영업일 | 제3자 구성요소 확인 결과 |
| 등급 판정 | 기술 심사자 2명 | 1영업일 | 판정 등급, 판정 근거, 제한 조건 |
| 등록 공개 | 자산 심사 담당자 | 1영업일 | 저장소 등록, 검색 항목, 공개 통지 |

기준 소요일은 직전 단계의 산출물이 완성된 다음 영업일부터 계산한다. 보완 요청일부터 신청자의 수정 제출일까지는 심사 소요일에서 제외한다.

기술 심사자는 다음 항목을 순서대로 확인한다.

1. 문제 정의가 특정 고객의 조직명, 업무 명칭 또는 단일 사업의 운영 방식에 묶여 있지 않은지 확인한다.
2. 사업별 입력값, 연동 주소, 임계치와 실행 환경의 차이를 코드 수정이 아니라 설정으로 흡수할 수 있는지 확인한다.
3. 실제 재사용 범위를 넘어선 계층, 인터페이스 또는 확장 지점이 추가되어 적용 난도가 높아지지 않았는지 확인한다.
4. 입력 오류, 외부 연동 실패, 처리 지연과 부분 성공 시 반환값 및 후속 동작이 정의되어 있는지 확인한다.
5. 로그, 지표, 상태 코드 또는 검증 결과처럼 정상 여부와 실패 원인을 식별할 수단이 있는지 확인한다.
6. 적용 실패나 결함 발견 시 이전 상태로 되돌리는 절차와 필요한 백업 대상이 있는지 확인한다.

심사자는 각 항목을 `적합`, `조건부 적합`, `부적합`, `해당 없음`으로 기록한다. `해당 없음`에는 적용되지 않는 이유를 적고, `조건부 적합`에는 공개 전에 끝낼 조치와 공개 후 처리할 조치를 구분한다.

다음 사유 중 하나가 있으면 등급 판정으로 넘기지 않고 반송한다.

- 필수 등록 항목이나 실행 증적을 확인할 수 없는 경우
- 재현 절차를 따라도 예시 결과가 나오지 않는 경우
- 고객 식별정보 또는 확인되지 않은 제3자 구성요소가 발견된 경우
- 실패 동작이 정의되지 않아 사용 프로젝트가 영향 범위를 판단할 수 없는 경우
- 심사 의견에 대한 수정 내역과 미수정 사유가 제출되지 않은 경우

재신청자는 반송 의견별 조치 결과, 변경 파일, 재시험 결과와 미조치 항목의 근거를 대조표로 제출한다. 최초 제출물을 삭제하거나 새 신청으로 우회하지 않고 기존 심사 번호에 연결한다.

심사자가 해당 자산을 사용한 경험이 없으면 문서 검토만으로 판정하지 않는다. 신청자가 제공하는 60분 이내의 실행 시연, 독립 설치 또는 샘플 적용 중 하나를 실시하고, 심사자는 직접 확인한 환경과 결과를 심사표에 남긴다. 독립 검증이 불가능하면 사용 경험이 있는 시니어를 추가 검토자로 지정하거나 등급 판정을 보류한다.

반출 검사 확인은 PSY-05#s5 참조, 라이선스 확인 기준은 PSY-05#s6 참조로 처리한다. 두 단계에서는 기존 검사 결과의 유효성과 대상 버전 일치 여부만 확인한다.

고객 요청 트리아지에서 반복 문제에 대한 공통화 제안이 발생하면 PSY-03#s14의 기록을 등록 신청서에 연결한다. 해당 기록은 재사용 수요의 근거로 사용하지만 기술 적합성의 합격 증거를 대신하지 않는다.

## 버전·지원 정책
<!--meta: sec=s8; dept=BE|AIAX; level=시니어; ct_band=상; related=s3-->
코드, 실행 패키지, 설정 스키마와 API를 포함하는 자산은 `MAJOR.MINOR.PATCH` 형식으로 버전을 부여한다. 호환성을 깨는 변경은 MAJOR, 하위 호환 신규 기능은 MINOR, 하위 호환 결함 수정은 PATCH를 올린다. 문서 전용 자산은 `연도.순번` 형식을 사용할 수 있으며 적용 기준일을 함께 표시한다.

| 등급 | 파괴적 변경 예고 | 이전 주 버전 지원 | 보안 수정 범위 | 호환성 약속 |
|---|---:|---:|---|---|
| 실험 | 의무 없음 | 제공하지 않음 | 현행 버전에 한해 가용 공수 내 처리 | 버전 간 호환성을 보증하지 않음 |
| 검증 | 최소 10영업일 전 | 신규 주 버전 공개 후 30일 | 현행 주 버전의 확인된 취약점 | 공개 인터페이스 변경을 변경 기록에 표시 |
| 표준 | 최소 30일 전 | 신규 주 버전 공개 후 90일 | 현행 및 직전 주 버전의 확인된 취약점 | 공지 기간 중 기존 인터페이스 유지 |

표의 지원 기간은 버전 공개일 다음 날부터 계산한다. 외부 구성요소의 지원 종료로 약속을 지킬 수 없으면 소유자는 확인한 날부터 2영업일 이내에 영향 버전과 대체 방안을 공지한다.

호환성 파괴 변경의 표기와 릴리즈 노트 작성은 PSY-04#s3·s10을 따른다. 재사용 자산에는 다음 절차를 추가한다.

1. 자산 등록부와 지원 요청 기록에서 해당 버전에 의존하는 사업 목록을 확인한다.
2. 각 사업 담당자에게 종료 버전, 대체 버전, 변경 예정일과 예상 작업을 통지한다.
3. 이동 지원 범위를 자동 변환, 설정 예제 제공, 질의 대응 중에서 명시한다.
4. 전환하지 않은 사업이 있으면 사유와 잔여 위험을 변경 승인 기록에 첨부한다.
5. 공지 후 발견된 의존 사업에도 동일한 종료일을 적용할 수 있는지 개별 확인한다.

지원 요청은 자산 저장소의 지정 요청 양식으로 접수한다. 개인 메신저나 구두 문의로 시작한 경우 요청자가 같은 영업일 안에 양식으로 옮겨야 응답 시한을 계산한다.

| 요청 구분 | 최초 응답 시한 | 최초 응답에 포함할 내용 |
|---|---:|---|
| 사용 방법·설정 문의 | 2영업일 | 확인 담당자, 답변 예정일, 추가 정보 |
| 재현 가능한 일반 결함 | 1영업일 | 재현 여부, 영향 버전, 우회 가능성 |
| 보안 또는 다수 사업 중단 가능성 | 4업무시간 | 접수 확인, 임시 담당자, 다음 갱신 시각 |
| 기능 개선 제안 | 5영업일 | 수용·보류·거절 상태와 판단 경로 |

최초 응답은 수정 완료를 뜻하지 않는다. 수정 목표일은 재현 결과와 영향 범위를 확인한 뒤 별도로 기록한다.

요청이 소유자 개인에게 집중되지 않도록 소유자와 부소유자가 공동 알림을 받는 큐를 사용한다. 반복 문의는 답변 후 2영업일 이내에 사용 문서나 문제 해결 항목으로 전환하며, 월 3건 이상 반복된 질문은 다음 MINOR 계획에서 문서 개선 대상으로 표시한다.

다음 조건에서는 버전 범위 지정 대신 정확한 버전 고정을 권장한다.

- 검증 등급 또는 실험 등급을 운영 환경에 적용하는 경우
- 모델 출력, 데이터 변환 또는 계산 결과의 재현성이 검수 조건인 경우
- 자동 업데이트가 고객 환경의 설정이나 연동 규격을 바꿀 수 있는 경우
- 규제·계약상 사용 구성요소의 버전 증적을 남겨야 하는 경우
- 배포 시점에 통합 시험을 다시 수행할 여력이 없는 경우

보안 수정 버전으로 이동하기 위해 핀을 해제해야 할 때에는 기존 시험 결과를 그대로 인정하지 않고 영향 구간을 다시 검증한다.

## 소유자와 유지보수 의무
<!--meta: sec=s9; dept=AIAX|BE|DATA; level=시니어; ct_band=상; related=s8-->
등록 자산에는 소유자 1명과 부소유자 1명을 지정한다. 소유자는 변경과 지원 판단의 최종 책임을 맡고, 부소유자는 부재 시 응답 중단과 승인 공백을 막는다. 두 역할을 같은 사람이 겸임할 수 없다.

소유자와 부소유자는 자산의 구조를 설명하고 실행 또는 검증 절차를 수행할 수 있는 AIAX·BE·DATA 구성원 중에서 지정한다. 신청자의 소속팀 시니어가 후보자의 수락 여부와 업무 배정 가능성을 확인한 뒤 등록 문서에 반영한다.

| 의무 | 수행 기준 | 완료 증적 |
|---|---|---|
| 지원 요청 대응 | PSY-05#s8의 최초 응답 시한 준수 | 요청별 상태와 응답 기록 |
| 결함 수정 | 재현 후 영향도와 수정 목표일 결정 | 수정 버전 또는 미수정 근거 |
| 의존성 보안 갱신 | 확인된 영향 버전과 대체 버전 검토 | 갱신 결과, 시험 결과 |
| 문서 최신화 | 사용 방식이나 기본값 변경과 동시에 반영 | 변경된 문서 링크 |
| 분기 상태 점검 | 분기 종료 후 5영업일 이내 제출 | 상태 점검 보고 |
| 폐기 판단 | 지원 불가 또는 대체 자산 발생 시 검토 개시 | 유지·강하·폐기 의견 |

분기 상태 점검 보고에는 현행 버전, 지원 중인 버전, 사용 사업 수, 미해결 결함, 보안 갱신 상태, 반복 문의와 다음 분기 작업을 포함한다. 수치가 없는 항목은 `0`으로 적고 미확인 상태로 남기지 않는다.

소유자가 프로젝트에 전담 투입되어 5영업일 이상 통상 의무를 수행하기 어려우면 전담 시작 전에 완화 기간을 등록한다. 이 기간에는 부소유자가 지원 요청 분류, 긴급 결함 판단과 공지를 대행하고, 소유자는 호환성 파괴 변경 및 폐기 결정에만 참여한다.

부소유자도 대행할 수 없으면 소속팀 시니어가 임시 담당자를 지정한다. 임시 담당자의 종료일은 최초 20영업일 이내로 두며, 연장이 필요하면 미처리 요청과 교체 계획을 함께 기록한다.

소유자 교체는 다음 순서로 진행한다.

1. 기존 소유자 또는 소속팀 시니어가 변경 사유와 희망 인계일을 등록한다.
2. 후임자가 저장소 접근권한과 지원 큐 알림을 확인한다.
3. 기존 소유자가 구조 설명, 배포 방법, 미해결 결함, 지원 대상 버전과 예정 변경을 인계한다.
4. 후임자가 대표 예제를 실행하고 결과를 인계 기록에 첨부한다.
5. 부소유자와 소속팀 시니어가 완료 여부를 확인한 날에 등록부의 소유자를 변경한다.

인계 시에는 최근 분기 점검 보고, 의존성 목록, 보안 관련 미조치 항목, 사용 사업 목록, 반복 문의, 폐기 검토 이력을 빠뜨리지 않는다. 기존 소유자가 퇴직·휴직 등으로 참여할 수 없으면 부소유자가 보유 기록을 기준으로 인계서를 작성한다.

소유자와 부소유자에게 동시에 연락할 수 없고 지원 큐에도 5영업일 동안 응답이 없으면 소속팀 시니어가 무소유 상태로 표시한다. 10영업일 안에 후임자가 지정되지 않으면 표준 등급은 검증 등급으로, 검증 등급은 실험 등급으로 강하한다. 진행 중인 사용 사업에는 등급 변경일과 지원 공백을 통지한다.

유지보수에 사용한 시간은 고객 프로젝트 공수와 분리하여 자산 식별번호, 작업 유형, 대상 버전 단위로 기록한다. 이는 공통 자산 지원 비용을 특정 사업의 원가로 잘못 귀속하지 않고 반복 주기의 부채 축소 배정과 구분하기 위한 것이다. 반복 주기 할당 기준은 PSY-06#s7 참조로 처리한다.

## 사용 측 프로젝트의 의무
<!--meta: sec=s10; dept=AIAX|BE|DATA|CNS; level=주니어|시니어; ct_band=중; related=s9-->
프로젝트 수행책임자는 자산을 최초 반영하기 전에 사용 등록을 완료한다. 등록되지 않은 프로젝트는 파괴적 변경, 보안 수정과 지원 종료 통지의 수신 대상에 포함되지 않는다.

| 등록 항목 | 기재 기준 | 변경 시점 |
|---|---|---|
| 프로젝트 식별자 | 내부에서 구분 가능한 사업명 또는 관리번호 | 프로젝트 명칭 변경 시 |
| 자산과 버전 | 자산 ID와 정확한 버전을 함께 기록한다 | 버전 변경 전 |
| 적용 위치 | 서비스, 배치, 분석 작업 또는 문서 산출물의 위치를 적는다 | 적용 범위 변경 시 |
| 사용 책임자 | 문의와 갱신 판단을 담당할 1명을 지정한다 | 담당자 교체 시 |
| 기본값 변경 | 변경 전후 값, 변경 이유와 영향 범위를 적는다 | 설정 반영 전 |
| 사용 종료 예정일 | 계약 일정 또는 내부 운영 계획에 따른 예상일을 적는다 | 일정 확정 시 |

사용 프로젝트는 배포와 재현에 쓰는 버전을 잠금 파일, 이미지 태그 또는 명시적 버전 값으로 고정한다. `latest`, 범위 없는 브랜치 참조와 실행 시점 자동 갱신은 허용하지 않는다.

1. 사용 책임자는 월 1회 등록 버전과 최신 지원 버전을 비교한다.
2. 보안 수정 통지를 받으면 영향 여부를 1영업일 내 확인하고 적용 계획을 회신한다.
3. MINOR 또는 PATCH 갱신은 프로젝트 테스트 통과 후 반영한다.
4. MAJOR 갱신은 호환성 영향과 전환 공수를 산정한 뒤 프로젝트 수행책임자의 승인을 받는다.
5. 고객 검수 기간에는 갱신으로 얻는 효과가 결함 발생 위험보다 큰지 별도로 판정한다.

자산 본체를 수정하거나 래퍼, 패치 파일, 런타임 치환으로 동작을 바꾼 경우에도 수정 신고 대상이다. 신고에는 원본 버전, 변경 파일, 변경 이유, 적용 일시와 원본 복귀 가능 여부를 포함한다.

결함 발견자는 다음 양식으로 자산 소유자에게 보고한다.

- 발생 버전과 실행 환경
- 재현 절차와 재현 빈도
- 기대 결과와 실제 결과
- 로그, 오류 메시지와 최소 재현 자료
- 고객 업무 영향과 우회 방법 유무
- 최초 발견 시각과 보고자
- 비밀정보 제거 여부

원본을 별도 저장소에 몰래 복사해 수정하면 사용 현황에서 누락되어 보안 수정과 파괴적 변경 통지가 전달되지 않는다. 대안은 설정 오버라이드, 정식 기여 또는 등록된 포크이며 각각 PSY-05#s11 및 PSY-05#s12를 따른다.

고객에게는 기능 한계, 지원 입력 범위, 필요한 전제조건과 예상되는 운영 영향만 설명한다. 다른 고객의 적용 정보, 내부 취약점 세부사항, 저장소 구조와 미확정 수정 일정은 전달하지 않는다.

자산 제약으로 계약 범위나 수용 기준의 변경이 예상되면 고객에게 확정 답변하기 전에 CNS와 프로젝트 수행책임자가 계약 문서 기준으로 확인한다. 법률상 고지 필요 여부는 사안별 확인이 필요하다.

## 기여 절차
<!--meta: sec=s11; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=s9|s10-->
사용 과정에서 공통 활용 가치가 있는 수정이 생기면 프로젝트 전용 변경으로 남기지 않고 기여 후보로 제출한다. 기여자는 자산 소유자의 사전 동의 없이 기본 브랜치에 직접 병합하지 않는다.

| 단계 | 담당 | 목표 소요일 | 완료 조건 |
|---|---|---:|---|
| 제안 | 기여자 | 1영업일 | 문제, 사용 사례, 예상 영향과 대안을 등록한다 |
| 소유자 협의 | 자산 소유자·기여자 | 2영업일 | 수용 방향, 호환성 원칙과 작업 범위를 합의한다 |
| 변경 제출 | 기여자 | 합의 일정 | 코드 또는 문서, 테스트와 변경 설명을 제출한다 |
| 리뷰 | 자산 소유자·지정 검토자 | 3영업일 | 필수 의견이 해소되고 승인 기록이 남는다 |
| 병합 | 자산 소유자 | 1영업일 | 기본 브랜치 반영과 자동 검증이 완료된다 |
| 버전 올림 | 자산 소유자 | 1영업일 | 변경 성격에 맞는 버전이 부여된다 |
| 공지 | 자산 소유자 | 버전 발행 당일 | 등록 사용처에 변경점과 적용 조건을 알린다 |

소유자는 제안 접수 후 2영업일 내 수용, 보완 요청, 보류 또는 거절 중 하나로 응답한다. 보완 요청에는 부족한 증적과 재제출 조건을 명시한다.

리뷰어는 다음 순서로 변경을 판정한다.

1. 기존 공개 인터페이스와 등록 사용처의 동작을 깨지 않는지 확인한다.
2. 사용처별 차이를 코드 분기보다 설정으로 분리할 수 있는지 검토한다.
3. 변경 동작, 실패 조건과 회귀 범위를 다루는 테스트가 추가되었는지 확인한다.
4. 사용법, 설정 항목, 제한사항과 예제가 실제 동작에 맞게 갱신되었는지 대조한다.
5. 불필요한 의존성 증가와 실행 환경 제한이 생기지 않았는지 점검한다.

특정 고객사명, 고객 전용 필드와 단일 사업의 업무 규칙은 공통 경로에 직접 넣지 않는다. 필요한 경우 확장점으로 설계하며 다음 기준을 적용한다.

- 기본 동작은 확장 모듈이 없어도 유지한다.
- 확장 인터페이스의 입력, 출력과 실패 처리를 명시한다.
- 고객별 구현은 공통 패키지와 분리해 교체 가능하게 한다.
- 확장 기능이 비활성화된 상태를 테스트한다.
- 권한 확대나 외부 전송이 필요한 확장은 별도 위험 검토 대상으로 표시한다.

기여가 거절되면 기여자는 프로젝트 설정으로 요구를 해소하거나, 다음 버전까지 변경을 보류하거나, PSY-05#s12에 따라 포크를 신청한다. 거절 사유가 해소된 경우 기존 제안을 갱신해 재심사를 요청할 수 있다.

운영 중단 방지를 위한 긴급 수정은 프로젝트 브랜치에 먼저 적용할 수 있다. 적용자는 1영업일 내 소유자에게 수정 내용과 위험을 알리고, 5영업일 내 정식 변경 제출 또는 원복 중 하나를 완료한다.

긴급 수정이 보안 사고, 고객 데이터 영향 또는 반복 장애와 관련되면 프로젝트 내부 공유·대응 절차를 별도로 적용한다. 기여 절차가 해당 대응을 대신하지 않는다.

## 포크 허용 조건과 복귀
<!--meta: sec=s12; dept=AIAX|BE; level=시니어; ct_band=상; related=s11-->
포크는 원 자산을 복제해 독립적으로 변경하는 방식이다. 납기, 상충하는 기술 제약 또는 원 자산의 지원 일정 때문에 필요할 수 있으므로 일률적으로 금지하지 않지만, 두 코드 계열을 유지하는 비용이 발생하므로 사전 등록을 조건으로 허용한다.

| 허용 조건 | 필수 기준 | 미충족 시 처리 |
|---|---|---|
| 사유 | 정식 기여나 설정 변경으로 해결할 수 없는 근거를 적는다 | 승인 보류 |
| 기한 | 원 자산 복귀일 또는 포크 폐기일을 지정한다 | 등록 반려 |
| 차이 목록 | 파일, 인터페이스, 설정과 의존성 차이를 유지한다 | 신규 배포 중단 |
| 보안 수정 책임 | 확인 담당자와 반영 목표일을 지정한다 | 사용 승인 취소 검토 |
| 사용 범위 | 적용 프로젝트와 실행 환경을 한정한다 | 범위 재승인 |
| 복귀 판단일 | 종료 기한보다 최소 10영업일 앞서 지정한다 | 즉시 판단 일정 지정 |

포크 등록 양식에는 원 자산 ID와 버전, 포크 저장소, 책임자, 생성일, 기술적 사유, 대안 검토 결과, 차이 목록 링크, 적용 프로젝트, 복귀 또는 폐기 기한, 보안 수정 반영 방법과 승인자를 기재한다.

허용 여부는 원 자산 소유자와 포크 사용 프로젝트의 AIAX 또는 BE 시니어가 공동 판정한다. 두 사람이 합의하지 못하면 각 소속팀 부장이 기한과 유지비용을 기준으로 결정한다.

복귀는 다음 절차로 수행한다.

1. 원 자산 최신 지원 버전과 포크의 차이를 다시 산출한다.
2. 고객 전용 요소와 공통 개선 요소를 분리한다.
3. 공통 개선 요소는 PSY-05#s11에 따라 변경 제출한다.
4. 병합된 원 자산 버전으로 프로젝트 회귀 테스트를 수행한다.
5. 배포 전후 결과가 같음을 확인한 뒤 사용 등록을 원 자산 버전으로 변경한다.
6. 포크 저장소는 읽기 전용으로 전환하고 종료 상태를 기록한다.

복귀가 기술적으로 불가능하면 별도 자산 승격 또는 폐기 중 하나를 선택한다. 별도 자산 승격은 기존 포크 상태만으로 인정하지 않으며 PSY-05#s4부터 PSY-05#s7까지의 등록과 심사를 새로 거친다. 폐기는 PSY-05#s13을 따른다.

두 갈래를 계속 유지할지는 다음 지표로 판단한다.

- 동일 수정의 중복 적용 시간이 월 8시간 이상인지
- 원 자산 보안 수정 반영 지연이 5영업일을 초과했는지
- 차이 파일 수가 직전 점검 대비 계속 증가하는지
- 두 계열에서 동일 원인의 결함이 각각 발생했는지
- 포크 전담 책임자의 월 유지 공수를 확보했는지

위 항목 중 2개 이상이 충족되면 복귀 또는 별도 자산 전환 결정을 다시 승인받는다.

기한이 지난 포크는 자동으로 `만료` 상태가 되며 신규 프로젝트 사용과 기능 추가를 중단한다. 책임자는 만료 통지 후 5영업일 내 복귀, 승격 또는 폐기 계획을 제출해야 하며, 미제출 시 해당 포크는 폐기 검토 대상으로 이관한다.

## 폐기 절차
<!--meta: sec=s13; dept=AIAX|BE|DATA; level=시니어; ct_band=중; related=s3|s8-->
자산 소유자는 아래 사유가 확인되면 폐기 검토를 개시한다. 등급 변경 기준은 PSY-05#s3, 지원 종료와 버전 처리 기준은 PSY-05#s8을 따른다.

| 폐기 사유 | 판정 기준 | 필수 증적 |
|---|---|---|
| 사용처 소멸 | 사용 등록된 사업이 없고 최근 12개월간 신규 사용 문의가 없다 | 사용 대장 조회 결과, 문의 이력 |
| 더 나은 대체 자산 | 동일 문제를 해결하는 자산이 있으며 기능·호환성·운영 비용 비교에서 대체 자산이 우세하다 | 비교표, 전환 시험 결과 |
| 유지 비용 초과 | 최근 2개 분기의 수정·지원 공수가 같은 기간 재사용으로 절감한 추정 공수보다 크다 | 작업 기록, 절감 공수 산출표 |
| 보안 위험 | 수정할 수 없는 취약 구성요소, 배포 중단이 필요한 노출 또는 반복되는 보안 결함이 확인된다 | 점검 결과, 영향 범위, 완화 가능성 검토 |
| 소유자 부재 | 소유자와 부소유자를 모두 대체하지 못하고 소속팀이 10영업일 내 신규 담당자를 지정하지 못한다 | 인수 후보 확인 기록, 팀 검토 결과 |

폐기는 다음 순서로 진행한다.

1. 소유자는 사유와 증적을 첨부해 자산을 `폐기예정` 등급으로 변경 신청한다.
2. 자산 심사 담당자는 사용 대장과 저장소 참조 기록을 대조하여 현재 사용처를 조사한다.
3. 확인된 프로젝트 수행책임자에게 폐기 사유, 영향 버전과 지원 종료 예정일을 2영업일 내 통지한다.
4. 소유자는 대체 자산, 설정 전환, 기능 제거 중 적용 가능한 경로와 검증 절차를 제시한다.
5. 일반 폐기의 이동 기한은 통지일로부터 30영업일로 하며, 일정 연장이 필요한 프로젝트는 만료 5영업일 전까지 사유와 완료 예정일을 제출한다.
6. 모든 사용처의 이동 또는 예외 승인이 확인되면 자산 ID의 신규 사용을 차단하고 등록 목록에서 해제한다.
7. 마지막 배포본, 문서, 변경 이력, 폐기 결정서를 읽기 전용 보관소로 이동한다.

사용처가 남은 상태에서 폐기해야 하는 경우 소유자가 단독 결정하지 않는다. 영향을 받는 프로젝트 수행책임자와 자산 소속 부서장이 종료일을 승인하며, 보안 위험으로 즉시 중단이 필요한 경우에는 해당 부서장이 선중단 여부와 임시 대책을 결정한다.

코드와 문서는 장애 원인 확인, 과거 버전 재현과 전환 검증에 필요하므로 등록 해제와 동시에 삭제하지 않는다. 보관 기간은 등록 해제일로부터 3년으로 하며, 접근 권한은 소유 부서의 지정 인원으로 제한한다.

계약상 보관 조건, 고객 정보 삭제 조건 또는 보안 조치가 보관 원칙과 충돌하면 사안별 확인이 필요하다. 해당 조건에 따라 더 짧은 기간을 적용하거나 특정 파일만 분리 폐기할 수 있다.

폐기 결정서에는 자산 ID, 대상 버전, 사유, 증적, 영향 사용처, 대체 경로, 승인자, 이동 기한, 등록 해제일과 보관 종료일을 기록한다. 폐기 철회는 등록 해제 전에는 등급 복구로 처리하며, 등록 해제 후에는 기존 결정을 고쳐 쓰지 않고 재등록 심사를 거친 새 결정으로 남긴다.

## 측정 지표
<!--meta: sec=s14; dept=AIAX|BE|DATA|CNS; level=시니어; ct_band=중; related=s3|s10-->
운영 담당자는 분기 종료 후 10영업일 이내에 자산 대장, 사용 등록 기록과 지원 이력을 기준으로 지표를 산출한다. 등급 판정은 PSY-05#s3, 사용 기록의 원천은 PSY-05#s10을 따른다.

| 지표 | 산식 또는 집계 기준 | 함께 표시할 값 |
|---|---|---|
| 등록 자산 수 | 분기 말 유효 등록 자산을 등급별로 집계한다 | 신규 등록, 승격, 강등, 등록 해제 수 |
| 신규 사업의 표준 자산 채택률 | 표준 자산 적용 가능 신규 사업 중 1개 이상 채택한 사업 수 ÷ 적용 가능 신규 사업 수 × 100 | 적용 불가 판정 사유 |
| 자산당 사용 사업 수 | 유효 사용 등록 건수 ÷ 사용 중 자산 수 | 중앙값, 최댓값, 사용 사업이 없는 자산 수 |
| 사용 등록률 | 실제 사용이 확인된 사업 중 사용 등록을 완료한 사업 수 ÷ 실제 사용 사업 수 × 100 | 미등록 사업 목록 |
| 절감 공수 추정 | 미사용 사업의 착수 구간 평균 공수에서 사용 사업의 동등 구간 평균 공수를 차감한다 | 비교 표본 수, 평균과 중앙값, 비교 구간 |
| 소유자 응답 시한 준수율 | 정해진 시한 내 최초 유효 답변을 제공한 지원 건수 ÷ 전체 지원 건수 × 100 | 초과 건수, 평균 초과 시간 |
| 폐기예정 자산 이동 완료율 | 이동을 완료한 사용 사업 수 ÷ 이동 대상 사용 사업 수 × 100 | 기한 경과 사업 수 |
| 포크 수 | 분기 중 승인되어 존속한 포크를 중복 없이 집계한다 | 신규 생성, 원 자산 복귀, 폐기 수 |
| 포크 평균 존속 기간 | 종료된 포크별 생성일부터 복귀 또는 폐기일까지의 일수 합계 ÷ 종료 포크 수 | 진행 중 포크의 최장 존속 일수 |

표준 자산은 분기 시작 전에 운영대장에서 적용 대상으로 표시된 자산만 집계한다. 분기 도중 지정 상태를 바꾸어 채택률의 분모를 조정하지 않는다.

절감 공수는 요구 범위, 프로젝트 규모와 담당자 숙련도가 유사한 사업끼리 비교한다. 착수 구간은 환경 준비부터 최초 실행 또는 적용 검증 완료까지로 고정하고, 비교 중 구간 정의를 변경하지 않는다.

산출 결과를 자산 사용의 단일 효과로 단정하지 않는다. 자동화 도구, 인력 구성, 고객 준비 상태 등 함께 달라진 조건을 주석으로 남기며, 사용 사업과 미사용 사업의 표본 수를 각각 표시한다. 어느 한쪽 표본이 3건 미만이면 수치는 참고값으로 분류하고 증감 평가에 사용하지 않는다.

분기 점검에서는 다음 순서로 지표를 검토한다.

1. 사용 등록률을 확인하여 원천 데이터의 누락을 먼저 보정한다.
2. 응답 시한 준수율과 폐기예정 이동 완료율로 운영 병목을 찾는다.
3. 채택률과 자산당 사용 사업 수를 기준으로 검색성, 적용 난이도와 중복 자산을 점검한다.
4. 포크 수와 존속 기간이 증가하면 원 자산의 확장 지점과 기여 수용 지연을 확인한다.
5. 데이터 신뢰성이 확보된 뒤 절감 공수와 등록 자산 수를 함께 해석한다.

지표가 나쁘다는 이유만으로 신규 등록 목표를 늘리지 않는다. 먼저 미등록 사용처 정리, 기한 초과 지원 해소, 이동 장애 제거, 저사용 자산의 대체·폐기 판단 순으로 조치하며, 각 조치에는 담당자와 다음 분기 확인일을 지정한다.

## 인정과 평가 반영
<!--meta: sec=s15; dept=CNS|AIAX|BE|DATA; level=시니어; ct_band=중; related=s9-->
재사용 자산 관련 업무는 프로젝트 산출물과 별도로 활동 기록을 남긴다. 기록은 기여 사실과 운영 결과를 확인하기 위한 근거이며, 자산 개수만으로 개인 성과를 판단하는 자료로 사용하지 않는다.

| 기록 대상 | 기록 단위 | 필수 항목 | 인정 증적 |
|---|---|---|---|
| 등록 자산 | 심사를 통과한 자산 1건 | 자산 ID, 유형, 등급, 등록일, 작성자, 소유자 | 승인된 등록 결정 |
| 변경 기여 | 병합 또는 문서 반영 1건 | 기여자, 변경 목적, 영향 버전, 반영일 | 병합 기록 또는 승인 이력 |
| 지원 응답 | 사용 문의나 결함 지원 1건 | 요청 시각, 응답 시각, 처리자, 결과 | 지원 티켓 또는 결정 기록 |
| 폐기 정리 | 등록 해제된 자산 1건 | 조사한 사용처, 전환 지원, 해제일, 담당자 | 폐기 결정서와 이동 완료 기록 |

자산 소유자는 분기 종료 후 5영업일 이내에 활동 기록을 확인한다. 작성자와 기여자는 누락이 있으면 증적 링크를 첨부해 정정을 요청하며, 소유자는 요청 접수 후 3영업일 이내에 반영 여부와 사유를 답한다. 소유자 의무의 범위는 PSY-05#s9를 따른다.

활동 기록에는 투입 시간만 적지 않고 다음 결과를 함께 남긴다.

- 실제 사용한 사업 수와 해당 분기의 신규 사용 수
- 해결한 공통 문제와 영향을 받은 자산 버전
- 호환성 유지, 결함 제거 또는 사용 문서 개선 결과
- 지원 요청의 완료 여부와 미해결 사유
- 폐기 시 이동을 완료한 사용처 수와 남은 예외

등록 자산 수 자체를 목표로 삼지 않는다. 개수 중심의 집계는 작은 결과물의 분할 등록, 중복 자산 생성과 유지 책임 회피를 유발할 수 있다. 인정 자료에는 자산별 사용 사업 수를 반드시 병기하며, 사용 사업이 없는 자산은 등록 사실과 후속 사용 실적을 구분해 표시한다.

분기 보고에는 다음 항목을 포함한다.

1. 신규 등록·승격·폐기 자산과 각 담당자
2. 자산별 사용 사업 수와 신규 채택 사업 수
3. 반영된 기여와 반려된 기여의 건수 및 주요 사유
4. 지원 응답 완료 건수와 시한 초과 건수
5. 폐기 정리, 사용처 이동과 보관 처리 결과
6. 다음 분기에 확인할 유지보수 또는 인수 필요 항목

이 섹션은 평가와 보상에 활용할 수 있는 활동 근거를 남기는 범위까지만 규정한다. 인사평가의 가중치, 보상 금액, 승진 기준과 조직별 할당 방식은 이 문서에서 정하지 않는다.

## 제도 운영 책임과 정기 점검
<!--meta: sec=s16; dept=AIAX|BE|DATA|CNS; level=시니어; ct_band=중; related=s7|s13-->
제도 운영 책임자는 AIAX·BE·DATA·CNS 소속 시니어 중 1명을 지정하며, 소속 부서 부장이 임명한다. 임기는 1년으로 하고 후임자 지정 전까지 기존 책임자가 업무를 계속 수행한다.

운영 책임자는 등록부 정합성 유지, 심사 일정 배정, 심사자 풀 관리, 분기 점검 주관과 규칙 개정안 관리를 담당한다. 개별 자산의 기술적 합격 여부에는 개입하지 않으며 심사 운영 기준은 PSY-05#s7을 따른다.

심사자 풀은 AIAX·BE·DATA·CNS가 각 2명 이상 추천해 구성한다. 추천자는 해당 유형의 결과물을 검토할 수 있고 최근 6개월 내 심사 일정에 참여 가능한 시니어로 한정한다. 운영 책임자는 특정인에게 분기 심사의 40%를 초과해 배정하지 않는다.

| 분기 점검 작업 | 확인 범위 | 주 담당 | 결과물 |
|---|---|---|---|
| 등급 재판정 | 현 등급 유지 조건과 승격·강등 사유 | 심사자 풀 | 등급 검토표 |
| 소유자 확인 | 재직·역할 수행 가능 여부와 부재 상태 | 운영 책임자 | 담당자 갱신 목록 |
| 의존성 보안 점검 | 등록된 의존성의 취약점 경보와 미지원 버전 | 기술 심사자 | 조치 필요 목록 |
| 사용 등록 갱신 | 종료 사업, 버전 불일치와 미갱신 기록 | 운영 책임자·사용 측 담당자 | 정정된 사용 대장 |
| 폐기 후보 선정 | 중복, 미사용, 지원 불가 자산 | 운영 책임자·소유자 | 폐기 검토 후보표 |
| 지표 집계 | 해당 분기 측정 대상 전체 | 운영 책임자 | 분기 운영 보고서 |

폐기 후보의 후속 처리는 PSY-05#s13을 따른다. 분기 점검은 분기 종료 후 5영업일 이내에 시작하고 10영업일 이내에 종료한다.

1. 운영 책임자는 점검 시작 3영업일 전 대상 목록과 담당자를 확정한다.
2. 자산 소유자는 자산당 최대 30분을 투입해 상태와 증적 링크를 확인한다.
3. 기술 심사자는 배정 자산당 최대 60분을 사용하며, 재현 검증이 필요하면 별도 심사로 전환한다.
4. 운영 책임자는 분기당 최대 8시간 범위에서 대장 정리, 회의 진행과 결과 취합을 수행한다.
5. 전원이 모이는 점검 회의는 60분 1회로 제한하고 미해결 항목만 다룬다.

등록부 원본은 접근 기록과 변경 이력이 남는 사내 문서 저장소의 단일 경로에 보관한다. AIAX·BE·DATA·CNS 구성원에게 열람 권한을 부여하고, 편집 권한은 운영 책임자와 지정된 대체 담당자에게만 부여한다. 자산 소유자와 심사자는 변경 요청으로 정정을 신청하며 원본을 직접 수정하지 않는다.

제도 규칙 변경은 운영 책임자가 변경 사유, 영향 조항, 예상 이익, 등록 부담과 시행일을 포함한 개정안을 작성하는 방식으로 진행한다. 영향받는 부서별 시니어 1명이 5영업일 내 검토하고, 운영 책임자 소속 부서의 부장이 최종 승인한다. 다른 부서의 의무나 승인 권한을 추가하는 개정은 해당 부서 부장의 동의를 함께 받아야 한다.

다음 중 하나가 발생하면 등록 장벽 경계 신호로 판정한다.

- 두 분기 연속 신규 등록 신청이 0건이고 사전 문의 또는 재사용 후보 제보가 존재한다.
- 한 분기 신청 건의 50% 이상이 기술 결함이 아닌 제출 형식이나 증적 부담 때문에 철회된다.
- 신청자 3명 이상이 동일한 필수 항목을 실제 재사용 판단과 무관한 작업으로 지적한다.

경계 신호가 확인되면 운영 책임자는 10영업일 내 원인 항목, 삭제·통합 가능한 요구사항과 심사 품질에 미치는 영향을 정리해 개정 여부를 상정한다. 등록 건수를 늘리기 위해 비밀정보 제거, 라이선스 확인 또는 기술 검증 항목을 생략하는 변경은 허용하지 않는다.
