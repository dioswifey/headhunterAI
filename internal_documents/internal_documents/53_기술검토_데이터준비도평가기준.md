# 고객사 데이터 준비도 평가 기준
<!--meta: doc=DSC-03; doc_type=assessment_standard; tier=1; topic=DISCOVERY; disclosure=internal; status=active-->

## 평가 목적·범위·소요 기간
<!--meta: sec=s1; dept=CNS|DATA; level=주니어|시니어; ct_band=중; related=DSC-01#s5-->

데이터 준비도 평가는 고객사의 데이터 생태계를 구조적으로 점검해 데이터 전략과 AI 도입 전략을 맞추는 작업이다. 모델 개발 여부만 판단하지 않고 데이터 사일로, 불일치, 인프라 한계, 거버넌스 공백을 확인한다. 디스커버리에서 확인한 데이터 현황은 DSC-01#s5를 참고한다.

### 적용 범위

평가는 전사 전체가 아니라 사전에 합의한 유스케이스와 이에 직접 연결된 데이터셋을 대상으로 한다. 데이터셋 목록화, 품질 점수화, 격차 분석을 기본 범위로 한다. 평가 중 발견된 전사 공통 문제는 별도 관찰사항으로 기록하되 임의로 평가 범위를 확대하지 않는다.

| 구분 | 범위 기준 | 필수 확인 | 범위 확정 시점 | 기록 방식 |
|---|---|---|---|---|
| 유스케이스 경계 | 업무 목적 1~3개 | 입력·산출물·이용 부서 | 킥오프 전 | 범위 문장과 업무 흐름 ID |
| 대상 데이터 | 직접 입력 또는 정답으로 쓰는 데이터셋 | 원천·가공·참조 데이터 | 1주차 | 인벤토리 ID |
| 대상 시스템 | 수집·저장·가공·전달 시스템 | 운영·분석계 구분 | 1주차 | 시스템 역할과 담당 부서 |
| 포함 기간 | 대표 운영 주기와 예외가 나타나는 기간 | 계절성·정책 변경 시점 | 1주차 | 시작일·종료일 |
| 제외 항목 | 유스케이스와 직접 관련 없는 데이터 | 제외 근거와 영향 | 범위 확정 시 | 제외 사유 코드 |
| 완료 경계 | 증빙 확인과 격차 우선순위화 완료 | 미확인 항목 잔여 여부 | 종료 회의 전 | 완료·조건부 완료 구분 |

### 수행 기간과 게이트

표준 수행 기간은 착수일로부터 4~6주이며 고객 측 자료 제출과 접근 승인이 예정대로 이루어지는 것을 전제로 한다. 단일 유스케이스와 10개 이하 데이터셋은 4주를 기준으로 하고, 시스템 또는 데이터셋 수가 늘어나면 최대 6주로 계획한다. 기간 변경이 필요한 경우 지연 원인, 미완료 범위, 변경 종료일을 기록한다.

1. 1주차에는 유스케이스 경계, 대상 시스템, 데이터 소유 부서를 확정한다.
2. 1~2주차에는 데이터 인벤토리와 증빙 목록을 작성한다.
3. 2~3주차에는 샘플을 확보하고 품질 및 계보 현황을 확인한다.
4. 3~4주차에는 7개 차원별 증빙을 검토하고 격차를 분류한다.
5. 4~5주차에는 성숙도 기준점과 개선 과제 초안을 작성한다.
6. 5~6주차에는 사실확인, 이견 기록, 최종 로드맵 확정을 수행한다.

기간 적용 기준은 다음과 같다.

- 4주는 대상 데이터셋 10개 이하, 원천 시스템 3개 이하, 접근 승인 완료인 경우 적용한다.
- 5주는 대상 데이터셋 11~20개 또는 원천 시스템 4~6개인 경우 적용한다.
- 6주는 대상 데이터셋 21~30개, 복수 부서 인터뷰 또는 폐쇄망 내 검토가 필요한 경우 적용한다.
- 30개를 초과하는 데이터셋은 대표군을 선정하거나 후속 평가로 분리한다.
- 자료 제출이 5영업일 이상 지연되면 해당 기간을 평가 일정과 분리해 기록한다.
- 평가 중 유스케이스가 변경되면 기존 결과의 재사용 가능성을 확인한 뒤 범위를 다시 확정한다.

### 산출물과 판정 용도

- 성숙도 기준점에는 평가일, 대상 범위, 차원별 상태, 적용한 증빙을 기재한다.
- 데이터셋별 준비도 기록에는 확인 결과와 미확인 항목을 구분한다.
- 격차 목록에는 사일로, 불일치, 인프라 한계, 거버넌스 공백을 원인별로 기록한다.
- 개선 로드맵에는 조치 순서, 책임 부서, 선행 조건, 목표 완료 시점을 포함한다.
- 증빙 목록에는 문서명, 시스템 화면, 인터뷰 기록, 추출 파일의 위치를 남긴다.
- 미확인 사항은 추정값으로 대체하지 않고 확인 책임자와 확인 기한을 지정한다.
- 평가 결과는 데이터 준비 상태를 나타내며 모델 성능이나 업무 효과를 보장하지 않는다.

### 평가 투입 구성

- CNS는 유스케이스 경계, 업무 흐름, 고객 인터뷰와 이견 조정을 담당한다.
- DATA는 인벤토리, 샘플, 품질 현황, 데이터 특성 및 격차 분석을 담당한다.
- AIAX는 모델 입력 가능성, 프로그램적 공급 가능성, 계산 가능성을 검토한다.
- 고객 업무 책임자는 유스케이스 목적과 현행 업무 규칙을 확인한다.
- 고객 데이터 소유 부서는 데이터 정의, 보유 범위, 이용 조건을 확인한다.
- 고객 시스템 운영 담당자는 저장 위치, 파이프라인, 접근 절차와 중단 이력을 제공한다.
- 보안·개인정보 담당자는 필요한 경우 접근·반출·비식별 처리 조건을 검토한다.

### 고객 측 협조 기준

- 킥오프 후 3영업일 이내에 업무·데이터·시스템 담당자를 지정한다.
- 평가 기간 중 담당자별 인터뷰 1~2회와 사실확인 회의 1회를 확보한다.
- 데이터 사전, 테이블 명세, 계보 문서, 운영 절차서는 보유 범위 내에서 제출한다.
- 샘플은 승인된 저장 위치와 전달 방식으로 제공한다.
- 조회 계정은 최소 권한으로 발급하고 종료 후 회수 여부를 확인한다.
- 검토 결과의 사실확인은 초안 전달 후 3영업일 이내에 회신한다.
- 제공할 수 없는 자료는 미제공 사유와 대체 증빙 가능 여부를 기록한다.
- 개인정보가 포함될 가능성이 있으면 샘플 제공 전에 고객 내부 절차를 확인한다.

협조 지연으로 핵심 증빙을 확인하지 못한 경우 해당 항목은 확인불가로 판정한다. 확인불가 항목이 핵심 데이터셋의 판단을 바꾸는 경우 평가는 조건부 완료로 종료한다.

## 데이터 인벤토리 작성
<!--meta: sec=s2; dept=DATA|CNS; level=주니어|시니어; ct_band=중; related=none-->

데이터 인벤토리는 평가 대상 데이터셋의 위치, 형태, 규모, 책임과 접근 조건을 동일한 기준으로 기록한 목록이다. 파일명이나 테이블명만 나열하지 않고 유스케이스에서 맡는 역할을 함께 적는다. 실제 담당자가 확인하지 않은 정보는 추정으로 확정하지 않는다.

### 작성 단위와 필드

한 행은 독립적으로 접근·갱신·관리되는 데이터셋 1개를 기준으로 한다. 동일 테이블이라도 운영계와 분석계의 갱신 방식 또는 책임 부서가 다르면 별도 행으로 작성한다. 개인 이름 대신 부서, 직책 또는 역할 ID를 기록한다.

| 열 이름 | 작성 기준 | 입력 예시 형식 | 미확인 시 처리 |
|---|---|---|---|
| 원천 시스템 | 최초 생성 시스템과 중간 수집 시스템을 구분한다 | 시스템 역할 / 환경 구분 | 시스템 담당자 확인 요청 |
| 데이터 종류 | 정형·시계열·문서·이미지·음성·로그로 분류한다 | 정형 / 거래 이력 | 기타로 두지 않고 설명 추가 |
| 저장 형태 | DB·파일·오브젝트 저장소와 포맷을 적는다 | DB / 테이블, 파일 / JSON | 실제 조회 후 보완 |
| 보유량 | 행·건·파일 수와 저장 용량을 기준일과 함께 적는다 | 1,200만 행 / 48GB | 산출 방식과 추정 여부 표시 |
| 보유 기간 | 최초·최종 보유일과 삭제·보존 기준을 적는다 | 2023-01~현재 / 3년 | 확인 책임 부서 지정 |
| 갱신 주기 | 실시간·시간·일·주·월·수동을 구분한다 | 일 1회 / 02:00 | 최근 갱신일 병기 |
| 소유 부서 | 정의와 이용 승인 책임이 있는 부서를 적는다 | 업무부서 / 데이터 관리 역할 | 임시 책임 부서 표시 |
| 접근 권한 보유자 | 조회·추출·승인 권한을 역할 단위로 적는다 | 운영 관리자 / 조회 담당 | 권한 확인 필요로 표시 |
| 정합성 기준 문서 | 검증 규칙·데이터 사전·코드표 존재 여부를 적는다 | 있음 / 문서 ID / 개정일 | 없음과 미확인을 구분 |

### 작성 순서

1. 유스케이스 입력, 정답, 참조, 결과 저장 데이터로 후보군을 분류한다.
2. 업무 흐름을 따라 최초 생성 시스템부터 모델 공급 지점까지 연결한다.
3. 데이터 소유 부서와 시스템 운영 부서가 다른지 확인한다.
4. 보유량과 보유 기간은 동일한 기준일로 다시 확인한다.
5. 데이터 사전, 코드표, 검증 규칙의 문서 ID와 개정일을 연결한다.
6. 접근 권한 보유 역할과 승인 절차를 확인한 뒤 샘플 요청 대상을 정한다.
7. 중복 사본에는 원본 후보와 복제 목적을 기록한다.

### 샘플 확보 기준

샘플은 인벤토리의 존재 여부와 데이터 특성을 검증하기 위한 자료이며 전체 모집단을 대신하는 성능 평가 데이터가 아니다. 추출 조건, 기준 시점, 난수 또는 정렬 방식, 제외 조건을 함께 기록한다. 원본 직접 조회가 가능한 경우에도 평가용 쿼리와 결과 건수를 보존한다.

- 정형 데이터는 기본 1,000행을 확보하고 전체가 1,000행 미만이면 전량을 확인한다.
- 시계열 데이터는 최소 2개 업무 주기와 500시점 이상을 포함한다.
- 문서 데이터는 100건 또는 전체의 10% 중 작은 수를 기본으로 하되 최소 30건을 확보한다.
- 이미지·음성 데이터는 200건 또는 전체의 10% 중 작은 수를 기본으로 하되 최소 50건을 확보한다.
- 로그 데이터는 연속 7일과 10,000이벤트를 기본으로 하며 장애일이 있으면 해당 일자를 포함한다.
- 희소 사건은 정상 사례 외에 확인 가능한 희소 사례를 최대 50건까지 별도 표본으로 구성한다.
- 단일 샘플 파일은 1GB 이하를 원칙으로 하며 초과 시 분할 또는 원격 조회를 사용한다.

샘플 확보 절차는 다음 순서를 따른다.

1. DATA가 데이터셋 ID, 요청 필드, 기간, 건수와 추출 조건을 작성한다.
2. 고객 데이터 소유 부서가 제공 가능 범위와 제외 필드를 확인한다.
3. 고객 보안·개인정보 담당 절차가 필요한 경우 승인 완료 후 추출한다.
4. 수령자는 건수, 스키마, 기준일, 파일 해시 또는 조회 기록을 확인한다.
5. 평가 종료 시 보관 필요성, 반환·삭제 여부와 처리일을 기록한다.

### 발견 상황 기록

- 같은 데이터의 복수 사본은 각 사본을 별도 행으로 두고 원본 후보, 복제 시점, 차이 필드를 연결한다.
- 담당자만 아는 가공 규칙은 인터뷰 근거, 적용 순서, 예외 조건과 문서화 책임자를 기록한다.
- 중단된 파이프라인은 최종 정상 실행일, 중단 원인, 대체 공급 방식, 재개 계획을 기록한다.
- 소유 부서가 불명확한 데이터는 임시 확인 부서와 최종 책임 확정 기한을 지정한다.
- 문서 정의와 실제 값이 다른 경우 문서 버전, 불일치 필드, 실제 사용 규칙을 함께 적는다.
- 접근 권한이 없는 데이터는 미보유로 처리하지 않고 접근 제한과 대체 증빙을 기록한다.

기록은 발견 사실, 확인 근거, 유스케이스 영향, 후속 확인 책임을 분리한다. 동일 문제가 여러 데이터셋에서 반복되면 공통 격차 ID를 부여하고 각 인벤토리 행에 연결한다. 인터뷰 진술과 시스템 증빙이 충돌하면 시스템 상태와 이견을 모두 남긴다.

### 완료 기준

- 대상 데이터셋마다 9개 필드가 입력되었거나 미확인 사유가 기록되어야 한다.
- 핵심 데이터셋마다 샘플 또는 승인된 대체 증빙이 1건 이상 연결되어야 한다.
- 원천 시스템부터 모델 공급 후보 지점까지 데이터 흐름이 식별되어야 한다.
- 복수 사본과 중단 파이프라인에는 원본 후보 또는 대체 경로가 표시되어야 한다.
- 고객 데이터 소유 부서가 인벤토리의 사실관계를 확인해야 한다.

## 평가 7개 차원
<!--meta: sec=s3; dept=DATA|AIAX; level=시니어; ct_band=상; related=none-->

평가 7개 차원은 공공 연구 표준화 작업에서 제시된 AI 준비도 개념을 헤드헌터랩의 유스케이스 단위 점검 항목으로 번역한 것이다. 각 차원은 문서 존재 여부만으로 충족 처리하지 않고 실제 데이터와 운영 절차에 적용되는지를 확인한다. 차원별 결과는 데이터셋 단위 증빙과 공통 운영 증빙을 함께 사용한다.

### 차원별 정의와 확인 항목

평가자는 확인 질문에 대한 답변과 증빙이 일치하는지 검토한다. 증빙이 없거나 표본에서 반대 사례가 발견되면 인터뷰 진술만으로 충족 판정하지 않는다. 미충족 영향은 현재 유스케이스에서 발생할 수 있는 직접 영향을 기준으로 기록한다.

| 차원 | 헤드헌터랩 적용 정의 | 핵심 확인 질문 | 주요 증빙 | 미충족 시 영향 |
|---|---|---|---|---|
| FAIRness | 데이터를 찾고 접근하며 다른 시스템과 상호운용하고 재사용할 수 있는 상태 | 위치·접근 절차·공통 식별자·재사용 조건이 정의되어 있는가 | 카탈로그, 데이터 사전, 접근 절차, 코드표 | 탐색 지연, 결합 실패, 중복 추출, 재사용 제한 |
| Provenance | 데이터의 출처, 변경 이력, 가공 단계와 책임을 추적할 수 있는 상태 | 원천부터 현재 값까지 생성·변환 주체와 시점을 추적할 수 있는가 | 계보도, 파이프라인 로그, 변경 이력, 버전 기록 | 오류 원인과 책임 구간 식별 곤란 |
| Characterization | 분포, 결측, 범위, 하위 집단, 수집 조건과 한계를 기술한 상태 | 대표 기간과 집단별 특성 및 알려진 한계가 문서화되었는가 | 프로파일링 결과, 통계 요약, 수집 명세 | 학습 데이터 오해와 평가 기준 왜곡 |
| Ethics | 이용 목적, 민감 요소, 편향 가능성과 필요한 검토 절차를 식별한 상태 | 이용 목적 외 사용과 집단별 불이익 가능성을 검토했는가 | 검토 기록, 필드 분류, 편향 점검표, 승인 기록 | 부적절한 이용 또는 특정 집단 영향 미식별 |
| Pre-model Explainability | 모델 적용 전에 데이터 의미, 수집 맥락, 가공 규칙을 설명할 수 있는 상태 | 주요 필드와 변환이 업무 언어로 설명되고 결과에 미칠 영향이 알려져 있는가 | 용어집, 가공 명세, 규칙서, 인터뷰 기록 | 모델 결과 원인 설명과 오류 분석 제한 |
| Sustainability | 데이터 공급, 관리 책임, 품질 점검과 변경 대응을 지속할 수 있는 상태 | 담당자 변경이나 시스템 개편 후에도 공급과 관리가 유지되는가 | 운영 절차, 역할 지정서, 점검 일정, 변경 계획 | 일회성 추출 의존과 운영 중 데이터 단절 |
| Computability | 데이터가 기계 판독 가능한 형식과 안정된 인터페이스로 처리될 수 있는 상태 | 파이프라인이 모델에 데이터를 프로그램적으로 공급할 수 있는가 | API·배치 명세, 스키마, 실행 로그, 오류 기록 | 수작업 의존, 처리 지연, 재현 불가 |

### 공통 판정 규칙

- 충족은 핵심 질문에 긍정 답변이 있고 현재 유효한 증빙이 1건 이상 확인된 상태로 판정한다.
- 부분 충족은 절차가 있으나 일부 데이터셋·부서·기간에만 적용되는 상태로 판정한다.
- 미충족은 절차나 책임이 없거나 표본에서 반복적으로 반대 사례가 확인된 상태로 판정한다.
- 확인불가는 접근 제한 또는 증빙 미제공으로 사실을 판단할 수 없는 상태로 판정한다.
- 문서의 최종 개정일이 12개월을 초과하면 실제 적용 여부를 추가 확인한다.
- 인터뷰와 시스템 기록이 충돌하면 시스템 기록을 우선 증빙으로 두되 이견을 병기한다.

### 5개 평가 영역과 매핑

7개 차원은 데이터 품질, 거버넌스, 인프라, 역량, 전략 정합성의 5개 영역을 교차 점검한다. 하나의 차원은 여러 영역에 연결될 수 있으며 영역별 판정을 단순 합산하지 않는다. 핵심 데이터셋의 미충족이 유스케이스 전체에 미치는 영향을 별도로 판단한다.

- 데이터 품질은 FAIRness, Characterization, Provenance, Pre-model Explainability와 주로 연결한다.
- 거버넌스는 Provenance, Ethics, Sustainability, FAIRness와 주로 연결한다.
- 인프라는 Computability, FAIRness, Provenance, Sustainability와 주로 연결한다.
- 역량은 Characterization, Ethics, Pre-model Explainability, Sustainability와 주로 연결한다.
- 전략 정합성은 Ethics, Sustainability, FAIRness, Computability와 주로 연결한다.

### 영역별 필수 확인

1. 거버넌스에서는 데이터 관리 책임인 스튜어드십 역할이 공식 문서나 역할 체계에 지정되었는지 확인한다.
2. 거버넌스에서는 원천, 변환, 저장, 제공 단계의 데이터 계보를 추적할 수 있는지 확인한다.
3. 인프라에서는 파이프라인이 수동 파일 전달 없이 모델에 프로그램적으로 데이터를 공급할 수 있는지 확인한다.
4. 역량에서는 업무·데이터 담당자가 AI 산출물을 해석하고 편향이 발생할 조건을 식별할 수 있는지 확인한다.
5. 전략 정합성에서는 데이터 개선 과제가 유스케이스 목적과 조직의 데이터 전략에 연결되는지 확인한다.
6. 데이터 품질에서는 정의, 값, 갱신 시점의 불일치가 모델 입력에 미치는 영향을 확인한다.

### 차원 간 영향 해석

- FAIRness 미충족은 데이터 존재 여부와 무관하게 탐색·결합·재사용 시간을 증가시킨다.
- Provenance 미충족은 오류가 발견되어도 발생 지점과 영향 범위를 특정하기 어렵게 한다.
- Characterization 미충족은 대표성, 희소 사례, 기간별 변화를 판단하기 어렵게 한다.
- Ethics 미충족은 이용 목적과 편향 조건에 대한 조직적 검토를 누락시킬 수 있다.
- Pre-model Explainability 미충족은 모델 적용 전 데이터 의미와 가공 영향을 설명하기 어렵게 한다.
- Sustainability 미충족은 초기 구축 이후 데이터 공급과 품질 관리가 중단될 가능성을 높인다.
- Computability 미충족은 반복 실행과 재현 가능한 모델 입력 구성을 제한한다.

차원 점수는 증빙된 현재 상태를 기준으로 하며 예정된 개선을 선반영하지 않는다. 개선 계획은 현재 점수와 분리해 목표 상태와 완료 조건으로 기록한다. 법률·규제 관련 적정성은 고객의 담당 부서 또는 별도 검토 주체의 확인 결과를 근거로 기재한다.

### 기록 최소 단위

- 차원명과 연결된 데이터셋·시스템 ID를 기록한다.
- 적용한 확인 질문과 인터뷰 대상 역할을 기록한다.
- 충족·부분 충족·미충족·확인불가 중 하나를 선택한다.
- 증빙 명칭, 기준일, 보관 위치와 확인자를 기록한다.
- 미충족 또는 부분 충족의 직접 영향을 1문장으로 작성한다.
- 개선 책임 부서와 필요한 선행 조건을 기록한다.
- 목표 완료일은 날짜 또는 평가 종료 후 영업일 수로 적는다.
- 다른 차원과 공유하는 격차는 동일한 격차 ID로 연결한다.

## 품질 지표 산식과 허용선
<!--meta: sec=s4; dept=DATA; level=시니어; ct_band=상; related=none-->

품질 지표는 평가 대상 데이터셋별로 계산하고, 업무상 핵심 필드와 일반 필드를 구분한다. 허용선은 기본 기준이며 데이터 생성 방식, 표본 크기, 과제 민감도에 따라 강화할 수 있다. 기준 완화는 DATA 부장과 과제 담당 AIAX 부장의 공동 확인을 받는다.

### 지표별 산식과 기본 허용선

비율 지표의 분모가 100건 미만이면 비율과 원시 건수를 함께 기록한다. 이상치와 코드값 비표준 여부는 업무 규칙 또는 승인된 기준 사전을 적용하며, 통계적 탐지만으로 오류를 확정하지 않는다.

| 지표 | 산식 | 계산 단위 | 집계 기간 | 허용·경고선 | 초과 시 기본 처리 |
|---|---|---|---|---|---|
| 결측률 | 결측 셀 수 ÷ 검사 대상 셀 수 × 100 | 필드·데이터셋 | 최근 3개월 및 전체 | 허용 ≤1%, 경고 >1~5%, 초과 >5% | 핵심 필드 5% 초과 시 범위 축소 검토 |

### 계산 단위와 집계 원칙

- 행 단위 중복은 업무 키가 확정된 경우에만 판정하며 전체 열 일치를 대신 사용하지 않는다.
- 핵심 필드는 입력값, 목표값, 시간값, 식별 연결키 등 모델 학습과 평가에 직접 쓰이는 필드로 지정한다.
- 일별 변동이 있는 데이터는 일 단위 결과와 최근 30일 이동 집계를 함께 보관한다.
- 라벨 일치율은 동일 표본을 독립적으로 판정한 작업자 2명 이상의 결과로 계산한다.
- 코드값 검사는 고객이 승인한 코드 사전의 버전과 적용일을 기록한다.
- 시계열은 영업일, 휴일, 점검 시간 등 기대 시점 제외 규칙을 먼저 고정한다.

### 허용선 초과 처리

허용선 초과는 즉시 데이터 사용 불가를 뜻하지 않는다. 영향 범위, 수정 가능성, 모델 입력 여부를 확인한 뒤 정비, 범위 축소, 중단 권고 중 하나로 처리한다. 동일 원인으로 2개 이상의 핵심 지표가 초과하면 한 단계 높은 조치를 적용한다.

1. 초과 데이터가 전체의 10% 이하이고 10영업일 안에 수정 가능하면 정비 과제로 등록한다.
2. 특정 기간·조직·채널에 한정되고 제외 후 표본의 70% 이상이 남으면 범위 축소를 검토한다.
3. 핵심 라벨 일치율이 80% 미만이거나 참조 관계 복원이 불가능하면 해당 학습 범위 중단을 권고한다.
4. 수정 책임자와 완료일이 확정되지 않은 상태가 15영업일을 넘으면 일정 위험으로 전환한다.

- 정비 과제에는 원인, 대상 건수, 책임 조직, 완료 예정일, 재측정 방법을 기록한다.
- 범위 축소 시 제외 조건과 제외 전후 데이터 건수를 모두 남긴다.
- 중단 권고는 해당 데이터 범위에 한정하며 전체 AI 과제의 중단으로 확대 해석하지 않는다.
- 임계값 예외는 업무 근거와 모델 영향 분석을 첨부하고 구두 승인만으로 처리하지 않는다.

### 측정 불가 시 대체 확인

원천 조회 권한, 기준 사전 또는 이력 데이터가 없어 지표를 직접 계산하지 못하면 미측정으로 기록한다. 미측정을 0% 또는 적합으로 간주하지 않으며, 아래 대체 확인 중 2개 이상을 사용한다.

- 스키마 정의서와 필드 제약조건을 확인해 결측·형식 위반 가능 범위를 추정한다.
- 최근 1개월에서 무작위 200건 이상을 추출해 수기 또는 쿼리 기반 표본 검사를 수행한다.
- 적재 로그와 오류 로그의 최근 90일 건수를 이용해 형식·참조 오류 발생 추이를 확인한다.
- 업무 담당자 2명 이상에게 이상값, 예외 코드, 결손 기간의 실제 처리 방식을 교차 확인한다.
- 라벨 원문을 볼 수 없으면 라벨링 지침, 재검수 기록, 작업자 간 분쟁 기록을 확인한다.
- 참조 테이블 접근이 제한되면 조인 실패 로그와 원천 시스템의 무결성 검사 결과를 확인한다.

### 측정 기록 기준

- 산식의 분자·분모 정의와 제외 조건을 지표별로 기록한다.
- 허용선 판정에는 전체값과 핵심 필드값을 분리해 표시한다.
- 표본 검사는 난수 시드, 추출 시점, 모집단 건수와 표본 건수를 남긴다.
- 정제 후 결과만 제공된 경우 정제 전 품질을 확인할 수 없음을 명시한다.
- 재측정 시 동일 산식과 기준 사전 버전을 사용하고 변경 사항은 별도 기록한다.
- 모든 판정에는 쿼리 결과, 로그, 화면 확인 기록 중 1개 이상의 근거를 연결한다.

## 라벨·정답 데이터 확보 가능성 평가
<!--meta: sec=s5; dept=DATA|AIAX; level=시니어; ct_band=상; related=DSC-04#s4-->

라벨·정답 데이터 평가는 학습용 데이터와 평가용 데이터의 확보 가능성을 분리해 확인한다. 기존 라벨이 있어도 작성 기준과 재현성이 확인되지 않으면 미검증 라벨로 분류한다. 평가 데이터셋의 확정과 측정 절차는 DSC-04#s4를 함께 적용한다.

### 업무 유형별 골든셋 최소 기준

골든셋은 모델 개발자가 임의로 수정할 수 없는 평가용 표본으로 관리한다. 아래 수량은 초기 타당성 검토의 최소선이며 클래스 수, 오류 비용, 계절성에 따라 확대한다.

| 업무 유형 | 최소 규모 | 필수 구성 | 판정 참여 | 산정 근거 | 확대 조건 |
|---|---:|---|---|---|---|
| 분류 | 200건, 클래스별 30건 이상 | 주요·희소 클래스 포함 | 작업자 2명 | 클래스별 오류 확인 가능 표본 | 클래스 10개 초과 시 클래스당 20건 추가 |
| 회귀·수치 예측 | 150건 | 목표값 구간별 층화 | 검수자 1명 이상 | 오차 분포와 극단값 확인 | 상·하위 10% 표본이 각 20건 미만일 때 확대 |
| 시계열 예측 | 3개 계절 주기 또는 100시점 | 정상·성수기·이벤트 구간 | 업무 담당자 1명 이상 | 기간별 오차 변동 확인 | 구조 변화가 있으면 변화 전후 각 1주기 추가 |
| 검색·순위화 | 질의 100건, 질의당 후보 5건 이상 | 빈도·난도별 질의 | 판정자 2명 | 적합·부적합 후보 비교 | 고위험 질의군은 별도 30건 추가 |
| 추출·개체 인식 | 문서 200건 또는 항목 1,000개 | 문서 유형과 항목별 층화 | 작업자 2명 | 경계·누락 오류 확인 | 문서 양식별 30건 미만이면 확대 |
| 생성·요약 | 프롬프트 100건 | 정상·경계·거부 사례 포함 | 전문가 2명 | 다기준 수기 평가 필요 | 평가 기준이 5개 이상이면 50건 추가 |

### 기존 라벨 검증

- 라벨 작성 기준 문서의 승인일, 적용 대상, 예외 처리 규칙을 확인한다.
- 실제 작성자 수와 업무 자격을 확인하고 자동 생성 라벨은 별도로 표시한다.
- 전체 라벨 중 최소 10% 또는 200건 중 큰 수를 재검수 표본으로 지정한다.
- 작업자 2명 이상이 참여한 경우 작업자별 일치율과 불일치 집중 클래스를 계산한다.
- 기준 변경 이력에는 변경일, 변경 사유, 이전 라벨의 소급 수정 여부를 포함한다.
- 재검수 결과 오류율이 5%를 넘으면 동일 차수 전체의 추가 표본 검수를 수행한다.
- 라벨 원문과 기준 문서의 버전 연결이 불가능하면 평가용 골든셋으로 사용하지 않는다.

### 라벨이 없는 경우의 대응

라벨이 없으면 약한 라벨 생성, 전문가 직접 라벨링, 평가용 소표본 구축 순으로 선택지를 검토한다. 초기 단계에서는 전체 학습 데이터보다 골든셋을 먼저 만들어 과제 정의와 평가 가능성을 확인한다. 자동 생성 라벨은 전문가 정답과 구분해 보관한다.

1. 업무 규칙이 명시돼 있으면 규칙 기반 약한 라벨을 생성하고 무작위 200건을 검수한다.
2. 규칙 간 충돌률이 10%를 넘으면 약한 라벨만으로 학습 범위를 확정하지 않는다.
3. 전문가 라벨링은 건당 평균 처리시간을 30건 이상 측정해 전체 공수를 추정한다.
4. 평가용 소표본은 업무 유형별 최소 기준의 30%를 먼저 작성하되 50건 미만으로 두지 않는다.
5. 소표본 일치율이 80% 미만이면 기준 문서를 수정한 후 첫 차수부터 다시 판정한다.

- 라벨링 공수에는 판정, 이견 조정, 재검수, 개인정보 마스킹 시간을 포함한다.
- 단일 전문가만 가능한 경우 전체의 20% 이상을 지연 재판정해 자기 일치성을 확인한다.
- 희소 사건은 무작위 추출과 조건 추출을 병행하고 실제 발생 비율을 별도로 기록한다.
- 약한 라벨의 출처 규칙, 적용 순서, 신뢰 점수와 생성일을 보존한다.
- 생성형 과제는 단일 정답 대신 정확성, 충실성, 유해성 등 평가 기준별 판정을 허용한다.
- 골든셋은 학습·프롬프트 조정 과정에서 열람한 개발 표본과 물리적 또는 논리적으로 분리한다.

### 라벨링 책임 판단

- 법정·내부 권한이 필요한 업무 판정은 고객 업무 전문가가 라벨을 확정한다.
- 고객만 해석할 수 있는 약어, 예외 코드, 내부 정책이 포함되면 고객 수행을 우선한다.
- 기준이 명확하고 반복 작업 비중이 80% 이상이면 수행사 작업 후 고객 검수를 적용할 수 있다.
- 전용 도구 개발이나 대량 전처리가 필요한 경우 AIAX가 도구를 제공하고 DATA가 품질을 점검한다.
- 고객이 원문 제공을 제한하면 고객 환경에서 라벨링하고 수행사는 집계 결과만 확인한다.
- 공동 라벨링은 고객이 기준과 최종 이견을 확정하고 수행사가 작업 운영과 표본 검수를 담당한다.
- 책임 분담에는 작업량, 승인자, 이견 조정 기한, 결과물 보관 위치를 명시한다.

### 라벨 품질과 모델 품질 상한

라벨 오류는 모델이 학습하는 목표와 평가 결과를 동시에 왜곡하므로 모델 품질의 실질적 상한으로 취급한다. 작업자 일치율은 상한의 대리 지표이며 수학적으로 고정된 한계값으로 단정하지 않는다. 라벨 품질 개선 없이 모델 변경만 반복하는 방식은 허용하지 않는다.

- 골든셋 일치율이 90% 미만이면 모델 성능 목표의 확정 전 라벨 기준을 재검토한다.
- 클래스별 라벨 오류율이 전체 평균의 2배를 넘으면 해당 클래스 성능을 별도로 보고한다.
- 학습 라벨과 평가 라벨이 동일 규칙으로 자동 생성됐으면 독립 평가로 인정하지 않는다.
- 모델 오류 분석에서 라벨 오류가 20% 이상이면 재학습보다 라벨 정비를 우선한다.
- 기준 변경 후에는 영향받는 골든셋 전량을 재판정하고 이전 평가값과 직접 비교하지 않는다.

## 데이터 접근·반출 가능성 평가
<!--meta: sec=s6; dept=DATA|AIAX; level=시니어; ct_band=상; related=DSC-05#s3-->

데이터 품질이 적정해도 승인된 접근 경로가 없으면 준비 완료로 판단하지 않는다. 접근 평가는 실제 조회, 추출, 분석 결과 반입, 작업 로그 보관까지 이어지는 경로를 기준으로 한다. 망분리·폐쇄망의 기반 조건은 DSC-05#s3을 함께 확인한다.

### 접근 경로별 평가 기준

승인 소요 기간과 추가 공수는 초기 계획용 기준이며 고객 절차 확인 후 갱신한다. 작업 효율은 통제된 분석 환경에서 직접 접근하는 경우를 100으로 둔 상대 범위다.

| 접근 경로 | 전제 조건 | 예상 승인 기간 | 작업 효율 | 4주당 추가 공수 | 주요 확인 사항 |
|---|---|---:|---:|---:|---|
| 고객사 현장 작업 | 출입 승인, 지정 단말, 작업 좌석 | 5~10영업일 | 70~85% | 3~6인일 | 출입 가능 시간, 저장매체 금지, 결과 반출 절차 |
| 전용 회선·VPN | 계정, 다중인증, 접속원 IP 등록 | 10~20영업일 | 80~95% | 2~5인일 | 세션 제한, 쿼리 권한, 로그 수집, 계정 만료 |
| 가명처리 후 샘플 반출 | 처리 기준, 반출 심의, 암호화 전송 | 10~15영업일 | 85~100% | 3~7인일 | 표본 대표성, 재식별 키 분리, 파기 확인 |
| 폐쇄망 내 작업 | 폐쇄망 계정, 도구 반입, 내부 저장소 | 15~30영업일 | 50~75% | 6~12인일 | 패키지 반입, 계산 자원, 결과 검수, 반출 주기 |

### 경로 확정 전 확인 사항

- 데이터 저장 위치와 실제 조회 시스템이 동일한지 확인한다.
- 읽기 권한, 스키마 조회 권한, 임시 테이블 생성 권한을 분리해 기록한다.
- 원천 전체 접근과 승인된 뷰·샘플 접근을 구분한다.
- 접속 가능 요일과 시간, 세션 종료 시간, 동시 접속자 제한을 확인한다.
- 분석 코드, 라이브러리, 모델 파일의 반입 승인 단위를 확인한다.
- 집계표, 로그, 모델 산출물의 반출 가능 형식과 검수자를 확인한다.
- 계정 발급과 보안교육의 선후 관계 및 재발급 소요 기간을 확인한다.
- 작업 종료 후 계정 회수, 임시 파일 삭제, 저장매체 파기 절차를 기록한다.

### 가명처리·비식별 처리 합의

가명처리 또는 비식별 처리가 필요한지는 수행사가 단독으로 확정하지 않는다. 고객 보안·법무·개인정보 담당 부서가 적용 범위와 승인 절차를 확인하고, DATA와 AIAX는 모델 활용성과 데이터 손실 영향을 제시한다. 관련 표현은 고객이 승인한 용어와 처리 기준을 따른다.

- 성명, 연락처, 계정번호 등 직접 식별자의 삭제·대체 방식을 합의한다.
- 날짜, 위치, 직무, 희소 코드 등 간접 식별자의 범주화 수준을 정한다.
- 자유기술문, 상담문, 첨부파일에 포함된 식별정보 탐지 범위를 정한다.
- 음성·이미지 데이터는 화자, 얼굴, 화면 내 문자 처리 여부를 구분한다.
- 가명키와 원본 매핑표의 보관 주체, 접근자, 보관 기간을 명시한다.
- 표본 추출 전후의 클래스·기간·지역 분포 차이를 측정한다.
- 극소 집단과 희소 사건의 최소 집계 단위를 고객 기준으로 확정한다.
- 모델 출력과 오류 사례가 원문을 재현할 가능성에 대한 검수 절차를 정한다.

### 접근 승인 지연 위험 등록

1. 예정 착수일 10영업일 전까지 승인 신청이 접수되지 않으면 주의 위험으로 등록한다.
2. 예정 착수일 5영업일 전까지 계정·환경 담당자가 지정되지 않으면 경고 위험으로 상향한다.
3. 착수일에 조회 권한 또는 필수 도구가 없으면 데이터 평가 일정을 미착수로 기록한다.
4. 승인 예정일이 기준 계획보다 10영업일 이상 늦으면 범위 축소 또는 순서 변경을 검토한다.
5. 동일 승인 요청이 2회 반려되면 반려 사유와 보완 책임자를 확정한 후 일정을 재산정한다.

- 일정 위험에는 요청일, 승인 단계, 현재 담당자, 예상 완료일과 영향 작업을 기록한다.
- 부분 접근만 가능한 경우 사용 가능한 테이블과 불가능한 검증 항목을 구분한다.
- 승인 대기 중 합성 데이터로 수행한 결과는 실제 데이터 검증을 대체하지 않는다.
- 접근 불가가 20영업일을 넘으면 해당 범위의 중단 권고 여부를 검토한다.

### 보안·법무 확인 원칙

접근과 반출의 허용 여부는 수행사가 법률 결론으로 단정하지 않는다. 고객 보안·법무·개인정보 담당자의 서면 확인 또는 승인 시스템 기록을 근거로 처리한다. 확인되지 않은 상태는 허용이 아니라 미확정으로 표시한다.

- 적용 규정, 내부 보안지침, 개인정보 영향평가 대상 여부를 고객 담당자에게 질의한다.
- 승인 문서에는 데이터 범위, 이용 목적, 접근자, 장소, 기간과 파기 조건을 포함한다.
- 구두 허용만 있는 경우 데이터 원문 조회나 반출을 시작하지 않는다.
- 승인 범위를 벗어난 추가 필드가 필요하면 기존 승인을 확대 해석하지 않고 재확인한다.
- 수행 인력 변경 시 계정 공유를 금지하고 신규 접근자 승인을 다시 받는다.
- 승인 기록과 접속 로그는 고객 보관 기준에 따르며 수행사 보관본의 범위를 별도로 확인한다.

## 준비도 등급과 등급별 권고
<!--meta: sec=s7; dept=CNS|DATA; level=시니어; ct_band=상; related=DSC-02#s2-->

준비도 등급은 평가 시점의 데이터 상태와 해당 유스케이스의 착수 가능 범위를 나타낸다. 등급은 조직 전체의 역량을 단정하는 지표로 사용하지 않는다. 동일 고객사라도 유스케이스, 데이터셋, 배치 환경이 다르면 별도 등급을 부여한다.

| 등급 | 상태 기술 | 대표 징후 | 착수 가능 범위 | 권고 조치 |
|---|---|---|---|---|
| L0 미확인 | 평가에 필요한 자료와 접근 근거가 없어 상태를 판정할 수 없다 | 데이터셋 목록 부재, 표본 미제공, 담당자 미지정 | PoC 착수 불가 | 인벤토리 작성, 책임자 지정, 표본 접근 승인부터 수행한다 |
| L1 부족 | 핵심 데이터가 존재하나 접근성·품질·출처 중 복수 항목이 결정적으로 미달한다 | 수작업 추출 의존, 계보 불명, 결측·중복 규모 미확인 | 데이터 탐색과 정비 계획 수립만 가능 | 결정적 미달 해소 후 재평가한다 |
| L2 조건부 | 제한된 표본과 범위에서는 검증 가능하나 반복 공급과 운영 근거가 부족하다 | 일회성 추출 가능, 일부 품질 기준 충족, 책임 경계 불명확 | 제한형 PoC를 조건부로 허용한다 | 데이터 동결, 품질 보정, 접근 승인 조건을 선확정한다 |
| L3 준비 | 핵심 데이터의 접근·품질·계보가 확인되고 재현 가능한 공급 경로가 있다 | 정기 파이프라인, 품질 점검 기록, 데이터 책임자 존재 | 표준 PoC 착수 가능 | 운영 전환에 필요한 자동화·관측 항목을 보완한다 |
| L4 운영 준비 | 지속 공급, 변경 관리, 윤리 점검, 해석 역량까지 운영 수준으로 관리된다 | 계보 추적, 품질 경보, 편향 점검, 변경 승인 절차 운영 | PoC 및 운영 전환 검토 가능 | 지속 가능성과 재평가 주기를 유지한다 |

등급은 7개 차원의 0~4점 점수를 결합해 산정하되 단순 평균만으로 결정하지 않는다. 평균값은 기준 등급의 후보를 정하고, 최저점과 결정적 미달 조건은 상한을 정한다. 평가 근거가 없는 차원은 0점으로 간주하지 않고 미확인으로 표시하되 최종 등급은 L0을 상한으로 한다.

### 등급 산정 규칙

1. FAIRness, Provenance, Characterization, Ethics, Pre-model Explainability, Sustainability, Computability를 각각 0~4점으로 채점한다.
2. 7개 차원의 산술평균을 소수점 둘째 자리에서 반올림해 소수점 첫째 자리까지 기록한다.
3. 평균 0.0~0.9는 L0, 1.0~1.9는 L1, 2.0~2.9는 L2, 3.0~3.6은 L3, 3.7~4.0은 L4 후보로 둔다.
4. 어느 한 차원이라도 1점 이하이면 최종 등급은 L2를 초과할 수 없다.
5. 결정적 미달 조건이 있으면 평균과 관계없이 해당 상한을 적용한다.
6. 상한 적용 전 후보 등급과 적용 후 최종 등급을 모두 평가 기록에 남긴다.

결정적 미달은 해당 유스케이스의 데이터 사용 자체나 결과 검증을 막는 상태로 한정한다.

- 핵심 데이터에 합법적·내부 절차상 유효한 접근 근거가 확인되지 않으면 L0으로 판정한다.
- 핵심 데이터가 프로그램적으로 공급될 수 없고 대체 추출 절차도 없으면 L1을 상한으로 한다.
- 출처와 생성 이력이 확인되지 않아 정답·입력의 신뢰성을 검증할 수 없으면 L1을 상한으로 한다.
- 윤리 검토가 필요한 데이터인데 검토 책임자와 처리 기준이 없으면 L1을 상한으로 한다.
- 목표변수 또는 검증 기준이 필요한 과제에서 정답 데이터 확보 경로가 없으면 L1을 상한으로 한다.
- 일부 데이터셋만 미달한 경우 해당 데이터셋을 제외해 목표를 달성할 수 있는지 별도로 판정한다.

### PoC 착수 판정

- **L0:** PoC에 착수하지 않는다.
  - 데이터 인벤토리와 접근 가능성 확인을 별도 선행 활동으로 둔다.
- **L1:** 모델 학습·평가 PoC에 착수하지 않는다.
  - 스키마 탐색, 표본 프로파일링, 정비 난이도 확인까지만 허용한다.
- **L2:** 범위와 종료 조건을 제한한 PoC만 허용한다.
  - 사용 데이터셋, 추출 기준일, 보정 방식, 미확인 위험을 착수 전에 고정한다.
  - 데이터 조건이 해제되지 않으면 DSC-04의 종료 상태로 전환한다.
- **L3:** DSC-04의 설계 요건을 충족하면 표준 PoC에 착수할 수 있다.
  - 운영 전환 가능성은 별도 판정하며 PoC 성공만으로 운영 준비를 인정하지 않는다.
- **L4:** 표준 PoC와 운영 전환 준비를 병행 검토할 수 있다.
  - 실제 운영 환경의 인프라·보안 조건은 DSC-05에서 별도로 확인한다.

### 등급 상향 선행 기간

기간은 평가 완료 후 고객 승인과 담당자 투입이 즉시 가능하다는 전제로 산정한다. 개인정보 영향평가, 별도 보안 심사, 외부 데이터 구매가 필요하면 아래 기간에 포함하지 않고 별도 의존 일정으로 기록한다.

- L0→L1은 인벤토리 작성과 표본 확보에 최소 2주를 적용한다.
- L1→L2는 접근 승인, 품질 프로파일링, 핵심 결함 보정에 최소 3~6주를 적용한다.
- L2→L3은 반복 추출 또는 파이프라인 구성과 품질 기준 확정에 최소 4~8주를 적용한다.
- L3→L4는 계보·변경 관리·모니터링·책임 체계 운영 검증에 최소 8~12주를 적용한다.
- 둘 이상의 등급을 올릴 때는 기간을 단순 합산하지 않고 병렬 수행 가능성과 승인 선후관계를 반영한다.

기간 추정에는 다음 조건을 함께 기록한다.

1. 고객 담당자의 주당 가용 시간과 승인 소요 일수를 명시한다.
2. 데이터셋 수가 10개를 초과하면 추가 5개마다 프로파일링 3영업일을 가산한다.
3. 수작업 정제가 필요한 레코드 비율이 20%를 넘으면 자동화 가능성을 재검토한다.
4. 10영업일 이상 근거가 갱신되지 않으면 등급 상향 일정을 재산정한다.

등급 상향은 문서 작성 완료가 아니라 미달 근거가 해소되고 재검증 표본이 통과한 시점에 인정한다. 최종 착수 판단은 데이터 준비도만으로 확정하지 않으며 DSC-02#s2의 타당성 검토 결과와 함께 사용한다.

## 사전 정비 과제 산정과 책임 분리
<!--meta: sec=s8; dept=CNS|DATA; level=시니어; ct_band=상; related=none-->

사전 정비 과제는 현재 상태와 목표 등급 사이의 격차를 해소하는 작업으로 정의한다. 데이터 소유권, 시스템 변경 권한, 업무 의미 판단 권한을 가진 주체가 고객 과제를 담당한다. 헤드헌터랩은 평가·설계·검증·제한된 가공처럼 수행 범위와 완료 기준을 명확히 통제할 수 있는 과제를 담당한다.

| 분류 | 정비 과제 | 기본 책임 | 책임 구분 기준 | 완료 증적 |
|---|---|---|---|---|
| 데이터 소유 | 원천 데이터 사용 승인과 담당자 지정 | 고객 | 고객 내부 권한과 책임 지정이 필요하다 | 승인 기록, 담당자 목록 |
| 업무 정의 | 필드 의미, 제외 조건, 정답 기준 확정 | 고객 | 업무 규칙의 최종 판단 권한이 고객에게 있다 | 데이터 사전, 판단 기준서 |
| 원천 수정 | 누락 입력 보완, 코드 체계 정합화 | 고객 | 운영 시스템과 원천 기록의 변경이 필요하다 | 수정 내역, 재추출 표본 |
| 접근 환경 | 계정·망·반출·보안 절차 마련 | 고객 | 고객 인프라와 통제 절차에 속한다 | 접근 시험 결과, 승인 번호 |
| 진단 | 프로파일링, 결함 유형화, 영향 분석 | 수행사 | 제공된 범위에서 분석 방법을 통제할 수 있다 | 품질 점수표, 결함 목록 |
| 가공 설계 | 정제·변환·샘플링 규칙 설계 | 수행사 | 규칙을 제안하되 업무 의미는 고객 확인을 받는다 | 변환 명세, 검토 기록 |
| 검증 | 보정 결과 재측정과 등급 재판정 | 공동 | 수행사가 측정하고 고객이 업무 적합성을 확인한다 | 검증 결과, 확인 기록 |
| 파이프라인 | 반복 공급 경로의 구현 또는 변경 | 별도 확정 | 시스템 소유권과 운영 주체에 따라 달라진다 | 실행 기록, 운영 인계서 |

과제별 책임은 회의 참석 여부가 아니라 결과물을 작성·승인·유지할 권한으로 정한다. 공동 과제도 단일 책임자를 각각 지정하며 “상호 협의”만 기재하지 않는다. 개인정보, 보안, 보존 기간에 관한 판단이 필요한 경우 고객의 해당 책임 조직 확인을 선행 조건으로 둔다.

### 선행·후행 관계 기록

- 모든 과제에 선행 과제 ID, 입력물, 완료 조건, 책임자, 예정일을 부여한다.
- 원천 데이터 사용 승인은 표본 반출, 프로파일링, 가공 설계보다 먼저 완료한다.
- 필드 의미와 업무 규칙 확정은 라벨 보정 및 정답 데이터 구축보다 먼저 완료한다.
- 품질 프로파일링은 결함 보정 규모와 수행 공수를 확정하기 전에 수행한다.
- 결함 유형화 후 원천 수정과 일회성 가공 중 어느 경로를 택할지 결정한다.
- 원천 수정 결과는 동일 추출 조건으로 다시 측정한 뒤 완료로 인정한다.
- 반복 공급 검증은 최소 2회 실행 또는 10영업일 관찰 중 하나를 충족한다.
- 병렬 수행 과제는 공통 선행 조건과 결과 병합 시점을 함께 표시한다.

일정 영향은 과제 자체의 작업일과 대기일을 구분해 산정한다.

1. 고객 승인 대기는 작업 공수에 포함하지 않고 별도 경과일로 기록한다.
2. 핵심 경로의 과제 지연일은 PoC 데이터 동결일과 착수 가능일에 동일하게 반영한다.
3. 비핵심 데이터셋 과제는 제외 시 목표 달성 가능 여부를 확인한 후 병렬 처리한다.
4. 선행 과제가 5영업일 지연되면 담당자 간 일정 재확인을 실시한다.
5. 10영업일 지연되면 범위 축소, 대체 데이터, 착수 보류 중 하나를 재판정한다.
6. 20영업일 이상 지연되면 기존 등급 근거의 유효성을 검토하고 필요한 항목을 재평가한다.

### 고객 과제 지연 시 사전 합의

- 고객 과제별 자료 제공일, 승인일, 재제출 허용 횟수를 기록한다.
- 지연 기간에는 수행사 인력이 대기하는지 다른 과제로 전환되는지 구분한다.
- 데이터 동결일 이후 변경된 원천 데이터는 변경분과 재검증 범위를 별도로 기록한다.
- 대체 데이터 사용 시 원본과의 차이, 결과 해석 제한, 폐기 시점을 명시한다.
- 핵심 데이터 미제공 시 PoC를 자동 개시하지 않고 착수 보류 상태로 둔다.
- 일정·범위 변경이 제안·가격 판단에 영향을 주면 제안·가격 소관 문서 계열로 이관한다.

### 수행사 과잉 부담 방지

- 수행사가 고객의 원천 데이터 오류를 상시 수작업으로 보정하는 구조를 만들지 않는다.
- 업무 규칙이 미확정인 상태에서 수행사가 임의로 정답 라벨을 확정하지 않는다.
- 고객 시스템의 운영 권한 없이 반복 추출 성공을 보장하지 않는다.
- 평가 목적의 임시 스크립트를 운영 파이프라인 완료물로 간주하지 않는다.
- 데이터 정비 전량을 미정 범위로 받아들이지 않고 대상·건수·허용 오류율을 제한한다.
- 고객 책임 과제를 수행사 과제로 변경할 때는 권한, 접근, 검수 책임을 다시 지정한다.

### 제안 범위 이관 기재 규칙

1. 정비 과제 ID와 대상 데이터셋을 식별 정보 없이 기재한다.
2. 기준 레코드 수, 파일 수, 테이블 수와 산정 기준일을 함께 적는다.
3. 포함 작업, 제외 작업, 고객 제공물을 구분한다.
4. 완료 기준은 결측률·중복률·검증 건수 등 측정 가능한 조건으로 쓴다.
5. 미확인 항목은 가정으로 표시하고 확인 기한과 영향 범위를 연결한다.
6. 일정은 선행 승인 완료일을 기준으로 한 작업일 범위로 전달한다.
7. 가격·계약 조건은 작성하지 않고 제안·가격 소관 문서 계열에서 판단하도록 넘긴다.

정비 과제 산정표는 데이터 준비도 등급을 올리기 위한 근거이며 수행사의 무제한 정비 의무를 뜻하지 않는다. 책임 변경이나 데이터 규모 변동이 발생하면 기존 산정표를 덮어쓰지 않고 개정 이력을 남긴다.

## 평가 보고서 양식과 공유 범위

평가 보고서는 평가 범위, 확인 근거, 준비도 등급, 선행 과제를 한 문서에서 추적할 수 있도록 작성한다. 사실, 추정, 고객 확인 사항을 구분하고 확인하지 못한 항목을 정상 상태로 간주하지 않는다. 종합 기술 검토 보고서로 이관할 때는 DSC-06#s2의 목차 체계에 맞춰 요약한다.

| 장 | 제목 | 필수 기재 항목 | 고객 전달판 | 내부 보관판 |
|---|---|---|---|---|
| 1 | 평가 개요 | 목적, 유스케이스, 기준일, 기간, 참여 역할 | 포함 | 포함 |
| 2 | 범위와 제한 | 대상·제외 데이터셋, 표본 범위, 접근 제한 | 포함 | 제한 배경과 내부 판단 추가 |
| 3 | 데이터 인벤토리 | 데이터셋 ID, 소유 역할, 규모, 갱신 주기 | 합의된 항목만 포함 | 원본 위치와 접촉 기록 포함 |
| 4 | 차원별 평가 | 7개 차원 점수, 근거, 미확인 항목 | 포함 | 세부 관찰과 검토 메모 포함 |
| 5 | 품질 측정 | 지표, 산식, 표본 수, 결과, 허용선 | 집계값 중심 | 필드별 결과와 재현 정보 포함 |
| 6 | 준비도 판정 | 후보 등급, 상한 조건, 최종 등급 | 포함 | 반대 의견과 내부 판정 경위 포함 |
| 7 | 정비 로드맵 | 과제, 책임, 선후관계, 최소 기간 | 합의 과제 포함 | 공수 가정과 위험 신호 포함 |
| 8 | 부록 | 용어, 근거 목록, 변경 이력 | 공개 승인 자료만 포함 | 질의응답, 작업 로그, 내부 참조 포함 |

고객 전달판과 내부 보관판은 동일한 평가 기준과 최종 등급을 사용한다. 내부 보관판에만 존재하는 사실 때문에 고객 전달판의 결론이 달라져서는 안 된다. 접근 계정, 원본 경로, 개인 단위 표본, 내부 검토 의견은 고객 전달판에서 제외하거나 집계 형태로 바꾼다.

### 보고서 작성 필수 규칙

- 보고서 표지에 평가 기준일과 데이터 추출 기준일을 각각 표시한다.
- 데이터셋은 고객사명이나 시스템 실명 대신 평가용 ID로 연결한다.
- 표본 결과에는 전체 건수, 표본 건수, 추출 방법, 측정 도구 버전을 적는다.
- 점수마다 최소 1개의 확인 근거 또는 미확인 사유를 연결한다.
- 고객 진술만으로 확인한 항목은 “고객 확인”으로 표시한다.
- 추정치는 산식, 가정, 오차 가능성을 함께 기재한다.
- 재평가가 필요한 조건과 권고 유효기간을 명시한다.
- 고객 전달판의 부록에는 승인되지 않은 원본 자료를 첨부하지 않는다.

### 민감 항목 기술 방법

- 품질 문제의 원인을 특정 부서의 태도나 과실로 표현하지 않는다.
- “담당 부서가 관리하지 않음” 대신 “관리 책임 역할과 점검 기록이 확인되지 않음”으로 쓴다.
- “입력 오류가 많음” 대신 대상 필드, 표본 수, 오류율, 판정 기준을 기재한다.
- 개인의 발언은 직접 인용하지 않고 확인된 업무 절차와 증적으로 바꿔 기록한다.
- 원인이 확정되지 않은 경우 관찰 사실, 가능한 영향, 추가 확인 항목만 구분해 쓴다.
- 부서 간 책임이 불명확하면 책임 공백을 기술하고 임의로 귀책 주체를 정하지 않는다.
- 개인정보나 민감정보의 실제 값은 보고서에 싣지 않고 유형과 건수만 표시한다.
- 보안 취약 가능성은 일반 배포본에 상세 경로나 계정 정보를 포함하지 않는다.

### 검토·승인 절차

1. DATA 작성자는 점수, 산식, 표본 재현성을 1차 검토한다.
2. CNS 책임자는 범위, 업무 해석, 권고 조치의 정합성을 검토한다.
3. AIAX 또는 BE 검토자는 파이프라인·계산 가능성 관련 판단이 있을 때 참여한다.
4. 시니어 검토자는 결정적 미달과 최종 등급 적용을 승인한다.
5. 고객 전달판은 고객 담당자에게 사실관계 확인 기회를 최소 3영업일 제공한다.
6. 고객 이견은 점수 변경 여부와 관계없이 이견 내용과 처리 결과를 기록한다.
7. 최종본은 작성자와 승인자의 이름 대신 사내 역할·부서 코드·승인일로 식별한다.

### 보관과 재사용

- 내부 보관판은 최종 승인일부터 5년간 접근 통제 저장소에 보관한다.
- 원본 표본과 추출 파일은 고객 합의 보존 기간을 우선하며 보고서와 분리 보관한다.
- 고객 전달판의 발송 일시, 수신 역할, 문서 버전을 발송 기록에 남긴다.
- 개정본은 이전 버전을 삭제하지 않고 변경 사유와 변경 항목을 연결한다.
- 다른 고객 평가에 재사용할 때 고객사명, 시스템명, 부서명, 인명, 경로를 제거한다.
- 희소한 데이터 규모나 산업 조합으로 고객을 추정할 수 있으면 범주값으로 일반화한다.
- 표본 행과 원문 질의응답은 익명화 여부와 관계없이 재사용하지 않는다.
- 집계 지표는 최소 3개 평가 건을 결합한 경우에만 내부 기준 개선 자료로 사용할 수 있다.

외부 공유는 고객의 문서별 승인 범위 안에서만 수행하며 영업 참고자료라는 이유로 자동 허용하지 않는다. 익명화 후에도 고객을 합리적으로 재식별할 가능성이 있으면 재사용하지 않는다.
