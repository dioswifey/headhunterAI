# 인재상 부서별 적용과 온보딩 90일 장면

## 부서별로 달라지는 조건
<!--meta: sec=s1; dept=CNS|AIAX|BE|DATA|SALES; level=주니어|시니어; ct_band=상-->
같은 가치를 적용해도 부서별로 관찰되는 행동과 판단 시점은 다르다. 차이는 결과가 확인되는 시점, 잘못된 결정을 되돌릴 수 있는 정도, 고객과 접촉하는 관계의 밀도, 업무 불확실성이 발생하는 출처에서 생긴다. 평가자는 눈에 띄는 행동만 비교하지 않고 해당 행동이 놓인 네 조건을 함께 기록한다.

| 부서 | 결과가 확인되는 시점 | 되돌릴 수 있는 정도 | 관계의 밀도 | 주요 불확실성의 출처 |
|---|---|---|---|---|
| CNS | 인터뷰 직후 반응은 즉시 확인되지만 요구사항의 적합성은 설계·개발 착수 후 수주에서 수개월 뒤 확인된다 | 초안과 인터뷰 질문은 수정하기 쉽지만 고객 합의와 타 부서 전달 이후의 변경 비용은 높다 | 고객 실무자와 주 2~5회 접촉하고 내부 개발·데이터 담당자와 매일 해석을 조정한다 | 고객별 요구 표현, 이해관계자 간 우선순위, 결정권자의 승인 여부 |
| AIAX | 실험 지표는 수시간에서 수일 내 나오지만 운영 성과와 사용자 반응은 수주에서 수개월 뒤 확인된다 | 실험 설정은 되돌리기 쉽지만 모델 연동, 평가 기준 확정, 운영 배포 이후에는 영향 범위가 커진다 | 고객 접촉은 단계별로 집중되며 CNS·DATA·BE와의 내부 접촉 빈도가 높다 | 데이터 편향, 모델 변동성, 재현 조건, 기술 성숙도 |
| BE | 단위 기능은 당일 확인할 수 있지만 트래픽 증가와 연계 장애는 운영 이후 수주에 걸쳐 드러난다 | 로컬 코드 수정은 쉽지만 API 계약, 데이터 스키마, 마이그레이션 이후에는 복구 비용이 크다 | 고객과의 직접 접촉은 프로젝트에 따라 달라지고 내부 개발자 간 의존 관계는 상시 존재한다 | 외부 시스템 의존성, 동시성·부하, 예외 입력, 배포 환경 |
| DATA | 집계 결과는 당일 확인되지만 지표가 의사결정에 미친 효과는 다음 보고 주기 이후 확인된다 | 분석 쿼리는 수정하기 쉽지만 확정된 지표 정의가 보고서와 시스템에 확산되면 변경이 어렵다 | 고객 업무 담당자와 정의를 맞추는 접촉이 반복되며 CNS·AIAX에 데이터 해석을 제공한다 | 원천 데이터 품질, 지표 정의, 표본 구성, 누락과 시점 차이 |
| SALES | 고객 반응은 통화나 미팅에서 즉시 보이지만 수주 여부와 계약 이후 이행 가능성은 수주에서 수개월 뒤 확인된다 | 제안 초기의 메시지는 수정하기 쉽지만 견적·범위·납기 약속이 전달된 뒤에는 되돌리기 어렵다 | 잠재고객·기존고객과 접촉 빈도가 가장 높고 내부 수행부서와 사전 조율이 필요하다 | 고객 예산, 경쟁 상황, 구매 절차, 계약 시점, 수행 가능 범위 |

### 결과가 확인되는 시점
즉시 반응과 최종 결과를 같은 증거로 취급하지 않는다. CNS가 회의에서 고객의 긍정적 답변을 받은 장면은 회의 운영의 증거가 될 수 있지만, 요구사항이 정확했다는 판단은 AIAX·BE가 구현 단계에서 재질문한 횟수와 변경 기록까지 확인한 뒤 내린다.

AIAX의 실험 점수나 DATA의 분석 수치는 빠르게 확인되지만 현업 사용률과 업무시간 감소는 늦게 드러난다. 따라서 실험 종료일에 행동을 관찰하고, 운영 후 2주 또는 합의한 업무 주기 1회가 지난 시점에 결과를 추가 기록한다.

SALES는 미팅 직후 고객 반응이 분명하게 보이므로 단기 신호가 과대평가되기 쉽다. 수주 여부와 별개로 제안 단계에서 전달한 범위가 수행부서의 추정과 일치했는지 계약 검토 시점에 확인한다.

### 되돌릴 수 있는 정도
되돌리기 어려운 결정일수록 사전 확인의 범위와 기록 수준을 높인다. API 계약, 고객 합의 요구사항, 외부 전달 견적처럼 후속 작업을 발생시키는 결정은 담당자 개인의 빠른 판단보다 영향받는 부서의 확인 이력을 우선한다.

반대로 탐색용 분석, 비공개 실험, 인터뷰 질문 초안은 작은 범위에서 먼저 시도할 수 있다. 이때 시도 자체를 성과로 보지 않고 중단 기준, 비교 기준, 다음 판단 시점을 시작 전에 남겼는지 확인한다.

가역성이 낮은 업무에서 문제가 생기면 결과만으로 행동을 단정하지 않는다. 결정 당시 확보할 수 있었던 정보, 검토 요청 대상, 승인 이후 새로 발생한 조건을 분리해 기록한다.

### 관계의 밀도
고객 접촉이 잦은 CNS와 SALES에서는 회의 중 응답뿐 아니라 회의 후 내부 전달의 정확성이 중요한 관찰 대상이 된다. 고객에게는 긍정적으로 답했으나 수행부서에 제약을 누락한 경우 관계를 유지한 행동과 협업 행동을 별도로 판단한다.

AIAX·BE처럼 내부 의존 관계가 높은 부서는 코드나 모델을 혼자 완성한 장면보다 다른 부서가 사용할 수 있는 조건을 남긴 장면을 확인한다. 예를 들어 입력 형식, 실패 조건, 버전 변경 사항을 합의 시점 전에 공유했는지가 후속 판단의 근거가 된다.

DATA는 고객의 업무 용어와 내부 데이터 구조를 연결하는 접점에 놓인다. 동일한 명칭이 서로 다른 산식을 뜻하는 경우 질문 횟수가 많았다는 사실보다 최종 산식과 제외 조건을 양쪽이 같은 문장으로 확인했는지를 본다.

### 불확실성의 출처
요구 불확실성은 추가 인터뷰와 의사결정자 확인으로 줄이고, 데이터 불확실성은 분포·누락·계보 점검으로 줄인다. 기술 불확실성은 제한된 실험과 실패 조건 확인으로 다루며, 시장 불확실성은 고객 예산·구매 절차·경쟁 상황을 가정과 사실로 나누어 관리한다.

서로 다른 불확실성을 같은 방식으로 처리하지 않는다. 고객의 우선순위가 정해지지 않은 상황에서 기술 실험만 반복하거나, 데이터 결측 문제를 회의 횟수로 해결하려는 행동은 투입량과 무관하게 적합한 대응으로 보기 어렵다.

복합 프로젝트에서는 불확실성의 소유자를 한 명으로 고정하지 않는다. 주간 점검 시 요구·데이터·기술·시장 가운데 변동이 발생한 항목을 표시하고, 해당 변동으로 다음 10영업일 안에 영향을 받는 결정을 함께 기록한다.

### 부서 간 비교 시 판단 규칙
1. 결과 확인 시점이 다른 두 직원을 같은 주간 성과만으로 비교하지 않는다. 평가 기간 안에 결과가 나오지 않는 업무는 선행 증거와 사후 확인 일정을 함께 둔다.
2. 복구 비용이 큰 업무는 검토 단계의 행동을 결과와 함께 본다. 장애가 없었다는 사실만으로 사전 검증이 충분했다고 판단하지 않는다.
3. 고객 접촉 횟수는 관계의 밀도를 보여주는 참고치일 뿐 가치 행동의 점수가 아니다. 접촉 이후 약속, 제한조건, 담당자, 기한이 내부 기록과 일치하는지를 확인한다.
4. 불확실성이 큰 업무에서 최초 예상과 결과가 달라진 사실만으로 감점하지 않는다. 가정을 명시하고 확인 결과에 따라 범위나 접근을 조정했는지를 판단한다.

## 컨설팅팀(CNS)에서의 적용
<!--meta: sec=s2; dept=CNS; level=주니어|시니어; ct_band=상-->
CNS의 업무는 고객이 말한 내용을 정리하는 데서 끝나지 않는다. 서로 다른 표현과 권한 구조를 확인해 실행 가능한 판단 단위로 만들고, 그 결과가 AIAX·BE·DATA의 작업 입력으로 사용되는 지점까지 연결된다.

### 구조적 조건 3개
1. **요구가 사람마다 다르게 서술된다.** A사 현업 담당자는 “검색이 느리다”고 말하고, 운영 담당자는 “권한별 결과가 다르다”고 말하며, 임원은 “답변 신뢰도를 높여 달라”고 말할 수 있다. 세 발언을 하나의 요구로 합치기 전에 각각의 사용 장면, 측정 기준, 제외 범위를 확인해야 한다.
2. **결정권이 고객 조직에 분산된다.** 실무자는 화면 흐름을 정할 수 있어도 데이터 반출, 운영 배포, 예산 변경은 다른 책임자의 승인이 필요할 수 있다. 회의 참석자의 직급만 보고 최종 결정으로 처리하지 않고 안건별 승인권자와 회신 기한을 구분한다.
3. **산출물이 다음 부서의 입력이 된다.** CNS 문서의 모호한 표현 하나가 모델 평가, API 설계, 데이터 추출 범위를 동시에 흔들 수 있다. 전달 완료 여부는 문서 발송이 아니라 수신 부서가 동일한 조건으로 작업을 시작할 수 있는지로 확인한다.

### 상황 사례 1 — 주도성이 드러난 요구 충돌 정리
**상황:** B제조의 상담 자동화 착수 회의에서 고객 운영팀은 모든 문의에 자동 답변을 요구했고, 품질팀은 승인된 문서만 답변 근거로 사용해야 한다고 말했다. 회의 종료까지 20분이 남았지만 어느 참석자도 두 요구의 충돌을 안건으로 올리지 않았다.

**행동:** CNS 대리는 두 발언을 회의록의 일반 요구사항으로 병기하지 않고 답변 범위와 근거 제한의 충돌로 표시했다. 이어 “두 조건을 동시에 적용하면 승인 문서가 없는 문의는 자동 답변할 수 없습니다. 이 경우 상담원 연결로 처리해도 되는지 오늘 결정할 담당자를 확인하겠습니다”라고 말했다.

대리는 고객 측 운영책임자와 품질책임자를 결정자로 지정하고 다음 날 15시까지 회신받기로 합의했다. 회의 후 1시간 안에 AIAX와 BE에 미결정 항목을 알리고, 결정 전에는 전체 자동화율을 확정 수치로 사용하지 않도록 표시했다.

**결과:** 고객은 승인 문서가 없는 문의를 상담원에게 넘기는 조건을 채택했고 초기 범위에서 18개 문의 유형을 제외했다. AIAX는 평가 데이터에 거절·전환 유형을 별도로 넣었고, BE는 상담원 연결 상태값을 착수 시점부터 설계했다.

### 상황 사례 2 — 전문성이 드러난 원인 구분
**상황:** C금융의 업무 진단 중 고객은 월말 처리시간이 기존 6시간에서 9시간으로 늘었다며 시스템 교체를 요청했다. 인터뷰 자료에는 사용자 증가, 승인 단계 추가, 배치 지연이 섞여 있었고 시스템 로그는 아직 제공되지 않았다.

**행동:** CNS 과장은 해결안을 먼저 제시하지 않고 처리시간을 대기시간, 실제 작업시간, 시스템 응답시간으로 나누어 확인했다. 고객이 “현업에서는 전부 시스템 문제라고 봅니다”라고 말하자 “현재 자료로는 3시간 증가분의 위치가 확인되지 않습니다. 5영업일 동안 단계별 시각을 수집한 뒤 교체 범위를 판단하겠습니다”라고 답했다.

과장은 DATA와 함께 표본 30건의 시작·종료 시각을 확인하고, BE에는 배치 구간의 응답시간만 제한적으로 검토하도록 요청했다. 분석 전에 시스템 전면 교체, 프로세스 변경, 인력 추가를 대안으로 확정하지 않았다.

**결과:** 증가한 3시간 중 2시간 10분은 신규 승인 대기에서 발생했고 시스템 응답 증가분은 22분으로 확인됐다. 고객은 전면 교체 검토를 중단하고 승인 규칙 조정과 특정 배치 구간 개선을 우선 과제로 정했다.

### 상황 사례 3 — 협업이 드러난 전달 기준 조정
**상황:** A사의 예측 프로젝트에서 CNS 사원이 작성한 요구사항에는 “매일 오전 최신 예측값 제공”이라고 적혀 있었다. DATA는 원천 데이터가 매일 09시 30분에 적재된다고 이해했고, BE는 고객 화면이 09시에 열려야 한다고 전달받았다.

**행동:** 사원은 어느 해석이 맞는지 개별 부서에 추측하도록 두지 않고 30분 조정 회의를 요청했다. 회의에서 “최신이라는 표현을 기준 시각으로 바꾸겠습니다. 화면 공개와 데이터 적재 중 무엇이 우선인지 고객에게 다시 확인하겠습니다”라고 말했다.

확인 결과 고객은 전일 데이터를 기준으로 08시 50분 화면 공개를 원했고 당일 적재분은 다음 날 반영해도 된다고 답했다. 사원은 기준 데이터 시점, 화면 공개 시점, 실패 시 이전 값 표시 여부를 한 문단으로 수정하고 세 부서가 같은 날 17시까지 확인하도록 했다.

**결과:** DATA의 적재 완료 시각과 BE의 화면 공개 시각이 분리됐고, AIAX는 전일 마감 데이터만 평가 기준에 사용했다. 개발 착수 후 시점 정의를 다시 변경하는 일을 피했으며 후속 질의는 기존 7건에서 2건으로 줄었다.

### 상황 사례 4 — 고객중심이 드러난 요청 거절과 대안 제시
**상황:** B제조 담당자는 시연 이틀 전에 경영진 보고용 기능 세 가지를 추가해 달라고 요청했다. 요청을 모두 반영하면 기존 오류 점검 시간이 하루 미만으로 줄고, 한 기능은 확보되지 않은 설비 데이터를 필요로 했다.

**행동:** CNS 차장은 고객의 긴급성을 인정하면서도 즉시 수락하지 않았다. “세 기능을 모두 넣으면 현재 시연 범위의 검증을 완료할 수 없습니다. 경영진이 확인하려는 판단이 무엇인지 정하면 한 가지는 실제 기능으로, 두 가지는 화면 예시와 후속 일정으로 보여드리겠습니다”라고 제안했다.

차장은 SALES·AIAX와 2시간 안에 구현 가능 여부를 확인하고, 고객에게 실제 구현 1건과 비작동 화면 예시 2건을 구분해 표시했다. 확보되지 않은 설비 데이터는 임의 값으로 실제 결과처럼 제시하지 않고 예시 데이터라는 문구를 화면 상단에 넣었다.

**결과:** 시연은 기존 검증 범위를 유지한 채 진행됐고 고객 경영진은 추가 기능의 우선순위를 결정했다. 이후 계약 변경 시 실제 데이터 확보 책임과 추가 소요기간 15영업일이 명시됐다.

### 가치가 왜곡되기 쉬운 지점
- **문서 분량을 성과로 보는 경향:** 인터뷰 기록과 설명 페이지가 많아도 결정할 항목, 미확정 조건, 후속 담당자가 분리되지 않으면 다음 부서가 다시 해석해야 한다. 관리자는 문서 페이지 수가 아니라 개발 착수 후 10영업일 동안 발생한 정의 재질의, 승인 누락, 범위 재작업을 확인한다.
- **고객 발언을 결정으로 옮기는 경향:** 고객 참석자가 말한 희망사항을 승인된 범위로 기록하면 결정권 분산을 놓치게 된다. 회의록에는 발언자, 결정권자, 결정 상태, 회신 기한을 구분하고 승인되지 않은 항목에는 견적·일정 확정 표현을 사용하지 않는다.

### CNS 지원자 면접 질문
1. “한 프로젝트에서 고객 담당자 두 명이 서로 다른 요구를 말했던 실제 사례를 설명해 달라. 누구의 말이 맞는지 판단하기 전에 무엇을 확인했고, 최종 결정권자를 어떻게 찾았는가?” 답변에서는 지원자 본인이 만든 확인 절차, 회신 기한, 후속 작업의 변화를 추가로 묻는다.
2. “본인이 작성한 문서 때문에 개발자나 분석가가 다르게 이해했던 경험을 말해 달라. 상대방의 이해 부족으로 결론 내리지 않고 문서나 전달 방식을 어떻게 바꿨는가?” 수정 전후 표현과 재발 확인 방법이 구체적으로 나오는지 본다.
3. “고객이 일정상 수용하기 어려운 추가 요청을 했을 때 실제로 어떤 말을 했는가?” 당시 대화 문장을 요청하고, 거절 여부보다 고객이 달성하려던 목적을 확인해 대안을 제시했는지와 내부 수행 가능성을 먼저 확인했는지를 살핀다.

## AI/AX개발팀(AIAX)에서의 적용

AIAX의 결과물은 동일한 코드라도 모델 버전, 데이터 표본, 프롬프트, 추론 설정에 따라 다른 결과를 낼 수 있다. 실험 수치가 개선됐다는 사실과 고객 업무가 개선됐다는 사실 사이에는 평가 설계, 운영 조건, 사용자 행동이라는 추가 검증 단계가 존재한다.

### 구조적 조건 3개
1. **결과가 확률적이고 재현 조건에 민감하다.** 한 번의 좋은 응답이나 단일 실행의 점수만으로 품질을 판단할 수 없으며 모델 버전, 입력 데이터, 난수 조건, 평가 시각을 함께 남겨야 한다. 재현되지 않는 개선은 운영 기준으로 채택하지 않는다.
2. **평가 기준을 스스로 만들어야 한다.** 고객이 “정확하게 답해 달라”고 요청해도 정확성, 근거 일치, 답변 거절, 형식 준수 가운데 무엇을 우선할지는 자동으로 정해지지 않는다. 개발 전에 실패 유형과 허용 수준을 업무 담당자와 합의해야 한다.
3. **성능 개선의 한계 수익이 빠르게 줄어든다.** 초기 실험에서는 큰 폭의 개선이 가능하지만 일정 수준 이후에는 1~2%포인트를 높이기 위해 데이터 정제와 추론 비용이 크게 증가할 수 있다. 추가 실험은 기대 개선 폭, 운영비, 일정 영향을 함께 보고 계속 여부를 정한다.

### 상황 사례 1 — 주도성이 드러난 재현 실패 대응
**상황:** A사의 문서 질의응답 실험에서 AIAX 사원이 금요일 오후 정확도 84%를 기록했으나 월요일 재실행 결과는 76%였다. 시연은 4영업일 뒤였고 팀 공유 문서에는 높은 점수만 입력돼 있었다.

**행동:** 사원은 84%를 대표 결과로 유지하지 않고 두 실행의 모델 버전, 검색 인덱스 생성 시각, 평가 표본을 비교했다. “좋았던 실행을 기준으로 보고하기 전에 8%포인트 차이의 원인을 먼저 고정하겠습니다”라고 팀 리더에게 알렸다.

확인 결과 주말 동안 원문 43건이 교체됐지만 검색 인덱스는 갱신되지 않았고, 금요일과 월요일의 평가 질문 중 18건도 달랐다. 사원은 동일 질문 120건과 고정 인덱스로 세 차례 재실행하고 시연 자료에는 평균 78%, 최저 76%, 최고 80%를 함께 표시했다.

**결과:** 팀은 단일 최고점이 아니라 고정 조건의 분포를 기준선으로 채택했다. BE는 문서 갱신과 인덱스 생성 완료 상태를 연결했고, 시연 당일에는 사전에 검증한 버전이 사용됐다.

### 상황 사례 2 — 전문성이 드러난 평가 기준 설계
**상황:** C금융은 규정 안내 모델의 목표를 “정확도 90% 이상”으로 제시했지만 정답 데이터가 없었다. 일반 질문에는 긴 설명이 유리했으나 규정 근거가 없는 질문에는 답변을 생성하지 않는 편이 안전했다.

**행동:** AIAX 과장은 임의의 단일 정확도 산식을 만들지 않고 CNS와 고객 업무담당자에게 실패 사례 40건을 분류하도록 제안했다. 회의에서 “근거 없는 답을 유창하게 생성한 경우와 필요한 정보를 묻는 경우를 같은 오답으로 처리하면 운영 위험을 구분할 수 없습니다”라고 설명했다.

과장은 근거 조항 일치, 핵심 결론 일치, 답변 보류 적정성, 금지 표현 발생을 별도 항목으로 두고 각 항목의 판정 예시를 5건씩 만들었다. 고객 담당자 2명이 독립 판정한 뒤 불일치한 11건을 재논의해 기준 문구를 수정했다.

**결과:** 초기 모델은 핵심 결론 일치율이 높았지만 근거 없는 답변 비율이 14%로 확인됐다. 팀은 전체 평균을 높이는 실험보다 해당 비율을 5% 이하로 낮추는 검색·거절 조건 개선을 먼저 진행했다.

### 상황 사례 3 — 협업이 드러난 인터페이스 변경
**상황:** B제조 프로젝트에서 AIAX 대리는 응답 품질을 높이기 위해 모델 출력 형식을 자유 문장에서 근거 목록이 포함된 구조화 형식으로 바꾸려 했다. 변경하면 BE의 파싱 로직과 CNS의 시연 시나리오를 함께 수정해야 했고 배포 예정일은 6영업일 뒤였다.

**행동:** 대리는 성능이 좋아졌다는 이유로 출력 형식을 바로 병합하지 않고 기존 형식과 신규 형식의 예시, 실패 입력, 예상 수정 범위를 공유했다. BE 담당자가 “필드가 없을 때 빈 배열입니까, 오류입니까?”라고 묻자 “모델 판단에 맡기지 않고 빈 배열로 고정하고 스키마 검증 실패 시 기존 응답으로 전환하겠습니다”라고 답했다.

세 부서는 45분 검토 후 신규 형식을 별도 버전으로 제공하고 기존 버전을 배포 후 10영업일까지 유지하기로 했다. 대리는 변경 당일 테스트 입력 30건과 예상 출력을 전달하고 BE의 통합 테스트 실패 4건을 함께 수정했다.

**결과:** 배포 일정은 유지됐고 구버전 사용 호출은 전환 기간 동안 21%에서 0%로 감소했다. 신규 형식의 근거 누락은 오류가 아니라 명시된 빈 값으로 처리돼 화면 장애로 이어지지 않았다.

### 상황 사례 4 — 고객중심이 드러난 개선 중단 판단
**상황:** A사의 분류 모델은 3주간 실험을 거쳐 정확도가 91.2%에서 92.0%로 올랐지만 추론 비용은 건당 38% 증가했다. 오류 100건을 살펴보니 실제 업무에 큰 영향을 주는 유형은 7건이었고 나머지는 상담원이 최종 확인하는 항목이었다.

**행동:** AIAX 차장은 추가 학습을 계속하는 대신 오류 유형별 업무 영향을 CNS와 고객에게 확인했다. “0.8%포인트 상승은 확인됐지만 현재 방식은 월 추론비를 38% 늘립니다. 자동 처리되는 고위험 유형 7건을 별도 규칙으로 막는 편이 비용과 위험을 함께 낮춥니다”라고 제안했다.

차장은 전체 정확도 목표를 임의로 낮추지 않고 고객 승인 아래 고위험 오류 0건, 전체 정확도 91% 이상, 월 추론비 기존 대비 10% 이내 증가를 운영 조건으로 기록했다. 남은 실험 시간은 고위험 유형 탐지와 모니터링 알림에 배정했다.

**결과:** 최종 정확도는 91.5%였으나 검증 표본에서 고위험 오류가 발생하지 않았고 추론비 증가는 7%에 그쳤다. 고객은 최고 점수 모델이 아니라 합의한 운영 조건을 충족한 버전을 채택했다.

### 가치가 왜곡되기 쉬운 지점
- **지표 상승을 성과로 환산하는 경향:** 평가 표본이 바뀌었거나 고객 업무에 영향이 작은 유형에서 오른 수치는 그대로 성과로 확정하지 않는다. 관리자는 기준선과 동일한 조건인지, 개선된 오류가 실제 자동 처리 구간에 포함되는지, 비용·지연시간·실패율이 함께 변했는지를 확인한다.
- **신기술 도입을 전문성으로 환산하는 경향:** 새 모델이나 프레임워크를 적용한 사실만으로 판단하지 않는다. 기존 방식 대비 해결한 제약, 운영 환경에서의 지원 가능성, 장애 시 복구 방식, 팀 내 유지 가능성을 문서와 검증 결과로 제시해야 한다.

### AIAX 지원자 면접 질문
1. “실험에서 좋은 결과가 한 번 나왔지만 다시 재현되지 않았던 실제 경험을 설명해 달라. 최초 결과를 어떻게 보고했고 어떤 조건을 고정해 원인을 찾았는가?” 모델·데이터·평가 표본 가운데 지원자가 직접 비교한 항목과 최종 기준선이 어떻게 바뀌었는지 묻는다.
2. “고객이나 기획자가 모호한 품질 목표를 제시했을 때 평가 기준을 만든 사례를 말해 달라.” 정답을 임의로 정한 경험이 아니라 실패 유형, 판정자 간 불일치, 허용 수준을 조정한 장면이 있는지 확인한다.
3. “성능을 더 높일 수 있었지만 실험을 중단하거나 다른 접근으로 전환한 경험을 설명해 달라.” 중단 당시 개선 폭, 추가 비용, 일정, 업무 영향 중 무엇을 수치로 비교했으며 누구와 결정했는지를 추가로 질문한다.

## 백엔드팀(BE)에서의 적용
<!--meta: sec=s4; dept=BE; level=주니어|시니어; ct_band=상-->
BE의 행동은 코드 완성도뿐 아니라 변경 전후의 서비스 상태, 복구 가능성, 연동 부서에 남긴 정보로 판단한다. 정상 배포에서는 드러나지 않던 판단이 장애, 데이터 변경, 인터페이스 충돌에서 선명하게 나타나므로 관리자는 결과와 함께 의사결정 시점의 근거를 확인한다.

### 구조적 조건 3개

| 구조적 조건 | 실제로 발생하는 압력 | 행동 판단 시 확인할 증거 |
|---|---|---|
| 장애의 영향이 즉시 외부로 드러난다 | 오류율과 응답 지연이 고객 화면, 상담 접수, 거래 실패로 바로 이어진다 | 최초 인지 시각, 영향 범위 추정, 알림 대상, 임시 조치와 정상화 시각을 확인한다 |
| 되돌리기 비용이 높다 | 스키마 변경, 데이터 보정, 외부 연동 배포는 단순 코드 롤백으로 원상 복구되지 않을 수 있다 | 사전 백업, 호환 기간, 중단 기준, 복구 리허설, 데이터 정합성 확인 방법을 확인한다 |
| 다른 팀의 변경에 영향을 받는다 | AIAX의 추론 응답, DATA의 적재 구조, CNS의 업무 규칙 변경이 API와 배치 처리에 영향을 준다 | 변경 통지 시점, 계약 테스트 결과, 버전 정책, 담당자 간 승인 기록을 확인한다 |

같은 장애를 해결했더라도 혼자 장시간 버틴 경우와 필요한 인력을 조기에 호출해 영향 시간을 줄인 경우는 다르게 판단한다. 변경을 늦춘 사실보다 어떤 위험을 확인했고 어떤 조건에서 실행 가능하다고 보았는지를 본다. 시니어는 본인 작업의 안전성에 그치지 않고 이후 유사 변경에 적용할 통제 장치를 남겨야 한다.

### 상황 사례 1: 결제 상태 중복 반영을 먼저 드러낸 주도성

**상황:** B제조 주문 API 배포 20분 후 동일한 결제 완료 이벤트가 두 번 처리된 기록 14건이 발견됐다. 고객 화면에는 한 번만 표시됐지만 후속 정산 배치가 실행되면 중복 매출로 반영될 가능성이 있었다.

**행동:** BE 대리는 로그를 더 수집하느라 보고를 미루지 않고 배포 채널에 “현재 중복 수신 14건이며 정산 반영 전이다. 신규 이벤트 처리를 15분간 보류하고 직전 버전으로 전환하겠다”라고 알렸다. 이어 SALES와 CNS에는 고객 문의가 발생할 경우 사용할 사실관계만 전달하고, DATA에는 해당 이벤트가 집계 테이블에 유입됐는지 확인을 요청했다.

대리는 롤백 후 중복 키 기준으로 영향 데이터를 분리하고, 삭제 대신 정정 이력을 남기는 보정 쿼리를 작성했다. 차장은 운영 데이터 사본에서 쿼리 결과를 검토한 뒤 실행을 승인했으며, 대리는 정상화 후 이벤트 멱등성 검사를 배포 관문에 추가했다.

**결과:** 정산 배치 전에 14건을 모두 격리해 고객 금액 수정은 발생하지 않았다. 최초 인지부터 신규 처리 재개까지 43분이 걸렸고, 다음 두 차례 배포에서는 동일 조건을 자동 검사해 중복 반영이 발생하지 않았다.

### 상황 사례 2: 되돌릴 수 있는 데이터 변경으로 나타난 전문성

**상황:** C금융 회원 테이블의 상태 코드를 숫자형에서 문자열형으로 바꾸면 신규 규칙을 적용할 수 있었지만, 기존 배치 3개와 외부 조회 API 2개가 숫자 코드를 전제로 사용하고 있었다. 일괄 변환은 개발 시간이 짧지만 실패 시 이전 값 복원이 어려운 조건이었다.

**행동:** BE 과장은 즉시 컬럼을 교체하지 않고 신규 컬럼 추가, 이중 기록, 과거 데이터 변환, 조회 전환, 구 컬럼 제거의 다섯 단계로 변경안을 나눴다. “성공 경로만 보면 오늘 끝나지만, 외부 배치가 늦게 발견되면 원복할 기준값이 없습니다”라고 설명하고 단계별 중단 조건을 변경 기록에 남겼다.

과장은 운영 데이터의 5% 표본으로 변환 결과를 비교하고 불일치율 0%, 배치 처리시간 증가 3% 이내를 다음 단계 진입 조건으로 정했다. 구 컬럼 제거는 모든 연동 담당자가 2주간 신규 컬럼 조회 결과를 확인한 뒤 진행하도록 별도 작업으로 분리했다.

**결과:** 두 번째 단계에서 오래된 수기 업로드 파일이 숫자 코드를 사용한다는 사실을 발견해 제거 일정을 5영업일 늦췄다. 서비스 중단 없이 업로드 형식을 수정했고, 전환 완료 후에도 30일간 매핑 로그를 보관해 고객 감사 요청에 대응했다.

### 상황 사례 3: 연동 규격 충돌을 공동 검증한 협업

**상황:** AIAX가 추론 결과에 신뢰도 구간을 추가하면서 응답 객체의 일부 필드를 배열로 변경했다. 개발 환경에서는 정상 동작했지만 BE의 캐시 직렬화 모듈은 단일 값만 처리해 운영 반영 시 전체 응답이 실패할 수 있었다.

**행동:** BE 사원은 AIAX에 기존 형식을 유지하라고만 요청하지 않고 실패 요청과 정상 요청을 각각 재현해 공유했다. “배열 자체가 문제라기보다 현재 캐시 키 생성기가 첫 번째 값만 읽습니다. 2주간 구형과 신형을 함께 받을 수 있으면 모듈을 순차 전환하겠습니다”라고 제안했다.

AIAX는 응답 버전을 헤더로 구분하고 BE는 두 버전을 검증하는 계약 테스트를 공동 저장소에 추가했다. 양 팀은 운영 반영 1영업일 전 자동 테스트가 실패하면 배포를 중단하며, 버전 종료일은 BE 전환 확인 후 확정한다는 기준에 합의했다.

**결과:** 신형 응답은 예정일에 반영됐고 캐시 오류 없이 트래픽의 10%, 50%, 100% 순서로 전환됐다. 이후 연동 필드 변경 4건도 같은 계약 테스트를 거쳐 통합 환경에서 발견되는 오류 수가 월 6건에서 1건으로 줄었다.

### 상황 사례 4: 고객 업무 중단 시간을 기준으로 한 고객중심

**상황:** A사 야간 배치의 처리시간이 70분에서 118분으로 늘어 오전 상담 시작 시각과 겹치기 시작했다. 서버 증설은 즉시 가능했지만 월 운영비가 24% 증가하고, 병목 원인이 해소되지 않으면 처리량 증가 때 같은 문제가 반복될 상황이었다.

**행동:** BE 차장은 평균 처리시간만 줄이는 대신 고객에게 “오전 8시 30분까지 필요한 데이터와 이후에도 처리해도 되는 데이터를 구분해 달라”고 요청했다. 고객이 상담 대상 고객 목록을 우선 데이터로 지정하자 전체 배치를 두 단계로 분리하고 우선 구간의 완료 시각을 별도 모니터링했다.

차장은 인덱스 조정과 병렬 처리 수를 시험하면서 우선 구간 35분 이내, 전체 완료 100분 이내, 데이터 누락 0건을 승인 기준으로 설정했다. 서버 증설은 해당 기준을 두 차례 연속 충족하지 못할 때만 시행하도록 보류했다.

**결과:** 우선 데이터는 오전 8시 12분에 제공됐고 전체 처리는 94분에 끝났다. 월 운영비 증가는 4%에 그쳤으며 고객 상담 지연도 다음 영업일부터 발생하지 않았다.

### 가치가 왜곡되기 쉬운 지점

- **안정성을 이유로 변경을 모두 지연하는 경향:** 위험 항목을 특정하지 않은 채 “운영 영향이 있을 수 있다”는 이유로 배포를 반복 연기하지 않는다. 관리자는 발생 가능성, 영향 규모, 탐지 방법, 복구 소요시간이 적혀 있는지 확인하고 통제 가능한 위험이면 단계 배포나 제한된 트래픽으로 검증하게 한다.
- **야간 단독 복구를 영웅시하는 경향:** 한 사람이 새벽까지 모든 조치를 수행한 사실을 헌신으로만 평가하지 않는다. 호출 기준을 넘겼는데도 지원을 요청하지 않았거나 승인 없이 운영 데이터를 수정했다면 복구 성공과 별개로 개선 대상으로 기록하며, 다음 장애 전 당직 연락망과 이중 확인 절차를 보완한다.

### BE 지원자 면접 질문

1. “본인이 수행한 배포나 데이터 변경을 실제로 되돌려야 했던 경험을 설명해 달라. 되돌리기로 결정한 수치나 현상은 무엇이었고, 복구 후 데이터가 맞는지 어떻게 확인했는가?” 단순히 롤백 명령을 실행한 경험이 아니라 비가역 작업을 구분하고 검증한 장면을 확인한다.
2. “다른 개발팀의 변경 때문에 본인 서비스에 문제가 생길 가능성을 발견한 사례를 말해 달라. 상대 팀에 어떤 재현 자료를 제공했고 양쪽 일정이나 규격을 어떻게 조정했는가?” 책임 소재 주장보다 공동 검증 장치를 만든 행동이 있었는지 확인한다.
3. “운영 장애 중 혼자 해결할 수 있다고 판단했지만 다른 사람을 호출한 경험을 설명해 달라. 호출 시점, 전달한 정보, 본인이 계속 맡은 역할은 무엇이었는가?” 지원 요청을 역량 부족으로 보지 않고 영향 시간을 줄이기 위한 판단으로 사용했는지 묻는다.

## 데이터분석팀(DATA)에서의 적용
<!--meta: sec=s5; dept=DATA; level=주니어|시니어; ct_band=상-->
DATA의 산출물은 보고서가 제출된 시점보다 그 수치가 회의, 운영 정책, 고객 설명에 인용되는 순간에 더 큰 영향을 만든다. 분석자는 계산 과정의 정확성과 함께 지표의 의미, 사용할 수 있는 범위, 결론이 달라지는 조건을 명시해야 한다.

### 구조적 조건 3개

| 구조적 조건 | 실제로 발생하는 압력 | 행동 판단 시 확인할 증거 |
|---|---|---|
| 지표 정의가 조직마다 다르다 | 같은 ‘활성 고객’도 SALES는 계약 유지 고객, 고객 운영부서는 월 1회 이상 이용자, DATA는 이벤트 발생자로 계산할 수 있다 | 분모·분자, 제외 조건, 기준 시점, 중복 제거 단위, 정의 승인자를 확인한다 |
| 데이터 품질 문제가 분석 결론을 뒤집는다 | 누락, 중복, 시점 오류, 코드 변경이 통계적 차이보다 큰 변화를 만들 수 있다 | 원천 대비 건수, 결측률, 조인 증감률, 이상치 처리 전후, 수집 변경 이력을 확인한다 |
| 결과가 의사결정에 바로 인용된다 | 분석 문장의 조건이 빠진 채 투자, 기능 종료, 고객 평가의 근거로 사용될 수 있다 | 적용 대상, 관찰 기간, 불확실성, 대안 설명, 재검증 시점을 확인한다 |

분석 난도가 높더라도 의사결정에 사용할 수 없는 결과라면 완료로 보지 않는다. 반대로 단순 집계라도 정의 충돌을 해소하고 잘못된 결정을 막았다면 의미 있는 행동으로 판단한다. 시니어는 분석 결과뿐 아니라 조직이 수치를 오용하지 않도록 전달 형식을 설계해야 한다.

### 상황 사례 1: 회의 전에 지표 충돌을 드러낸 주도성

**상황:** 분기 고객 유지율 회의를 하루 앞두고 SALES 자료에는 92%, DATA 대시보드에는 84%가 표시됐다. SALES는 계약 갱신 여부를 기준으로 삼았고 대시보드는 최근 30일 접속 여부를 기준으로 계산하고 있었다.

**행동:** DATA 대리는 어느 한 수치를 정답으로 선택하지 않고 두 지표의 대상 고객 318곳을 대조했다. “계약은 유지됐지만 최근 30일간 접속이 없는 고객이 26곳입니다. 내일 회의에서 두 수치를 하나로 합치면 이탈 위험과 계약 상태가 섞입니다”라고 회의 주관자에게 알렸다.

대리는 회의 자료를 계약 유지율과 제품 이용 유지율로 분리하고, 두 조건이 모두 충족된 고객 비율 81%를 참고값으로 추가했다. 각 지표 아래에는 기준일, 휴면 판정 기간, 무료 계정 제외 여부를 한 줄로 표시했다.

**결과:** 회의에서는 92%를 영업 성과로, 84%를 사용 감소 점검 대상으로 각각 활용했다. 접속이 없는 계약 유지 고객 26곳은 CNS와 SALES의 후속 확인 대상으로 배정됐고, 이후 분기 자료에서 같은 명칭 충돌이 재발하지 않았다.

### 상황 사례 2: 데이터 결함으로 결론을 철회한 전문성

**상황:** B제조의 설비 알림 기능을 사용한 작업장에서 고장률이 18% 낮다는 중간 결과가 나왔다. 그러나 알림 기능은 최근 설치된 설비에 먼저 적용됐고, 구형 설비의 센서 로그는 일부 날짜에 수집되지 않았다.

**행동:** DATA 과장은 유의확률만 보고 효과를 확정하지 않고 설비 연식, 가동시간, 센서 누락률을 비교했다. “현재 차이는 기능 효과보다 신형 설비 비중으로 설명될 가능성이 큽니다. 누락률 12%인 구형군을 포함한 결론은 보류하겠습니다”라고 CNS에 전달했다.

과장은 설치 연식과 월 가동시간이 유사한 설비끼리 다시 비교하고, 센서 누락률 5% 이하인 기간만 주 분석에 포함했다. 제외된 데이터까지 포함한 민감도 분석을 별도로 제시해 어떤 조건에서 결과 방향이 바뀌는지 표시했다.

**결과:** 보정 후 고장률 차이는 18%에서 6%로 줄었고 통계적 불확실성 범위에 포함됐다. 고객은 전면 확대 결정을 유보하고 작업장 2곳에서 8주간 추가 검증하기로 했으며, 잘못된 절감액 산정도 방지했다.

### 상황 사례 3: 해석 차이를 의사결정 문장으로 조정한 협업

**상황:** CNS는 C금융 상담 자동분류의 재문의율이 낮아졌다는 결과를 고객 보고서에 넣으려 했다. DATA는 자동분류 적용군의 고객 유형이 달라 직접 비교가 어렵다는 이유로 해당 문장을 삭제해야 한다고 보았다.

**행동:** DATA 사원은 “비교 불가”라는 의견만 전달하지 않고 적용 전후 고객군의 차이를 연령, 문의 유형, 채널별로 정리했다. “전체 고객에서 개선됐다고 말할 수는 없지만, 채팅 채널의 계정 문의에서는 동일 조건 비교가 가능합니다”라고 CNS와 검토했다.

CNS는 보고서의 결론을 전체 재문의율 개선에서 특정 채널·문의 유형의 변화로 좁혔다. DATA는 동일 고객군 기준 4.2%포인트 감소, 관찰 기간 6주, 표본 1,240건을 본문에 넣고 다른 유형에는 적용하지 않는다는 주석을 추가했다.

**결과:** 고객은 제한된 적용 범위를 이해한 상태에서 채팅 채널의 자동분류 비율만 확대했다. 확대 후 4주 재측정에서도 3.8%포인트 감소가 확인돼 다음 범위 검토의 근거가 마련됐다.

### 상황 사례 4: 고객의 실행 시점에 맞춘 고객중심

**상황:** A사는 다음 주 월요일까지 이탈 가능 고객 목록을 요청했지만 완전한 예측모형을 새로 개발하려면 최소 4주가 필요했다. 고객 상담 인력은 월요일부터 200명에게 연락할 계획이어서 늦은 고정밀 결과보다 즉시 사용할 우선순위가 필요한 상황이었다.

**행동:** DATA 차장은 불완전한 모형을 완성본처럼 제공하지 않고 기존 이용 감소, 문의 증가, 결제 지연의 세 신호를 조합한 임시 선별 기준을 제안했다. “이 목록은 이탈 확률이 아니라 연락 우선순위입니다. 상위 200명 중 실제 위험 고객 비율을 확인한 뒤 기준을 조정하겠습니다”라고 구분했다.

차장은 최근 이탈 고객 500명으로 기준을 역검증하고 상위 200명에서 62%가 실제 이탈했던 결과와 38%의 오탐 가능성을 함께 제시했다. 상담 결과는 위험 여부, 연락 성공 여부, 주요 사유로 기록하게 해 2주 후 정식 분석에 사용할 수 있도록 했다.

**결과:** 고객은 월요일에 예정대로 연락을 시작했고 200명 중 117명의 위험 사유를 확인했다. DATA는 해당 기록으로 선별 기준을 수정해 두 번째 목록의 오탐 비율을 38%에서 24%로 낮췄다.

### 가치가 왜곡되기 쉬운 지점

- **분석 난이도를 가치로 환산하는 경향:** 복잡한 모형, 긴 쿼리, 고급 통계기법을 사용했다는 사실을 결과의 가치로 간주하지 않는다. 관리자는 해당 방법이 단순 비교보다 줄인 오류가 무엇인지, 사용자가 어떤 결정을 달리 할 수 있는지, 유지·재실행 비용이 적정한지를 확인한다.
- **결론의 적용 범위를 넓게 말하는 경향:** 특정 기간, 고객군, 채널에서 확인된 결과를 전체 고객이나 장기 효과로 확장해 표현하지 않는다. 적용 범위를 벗어난 문장이 보고 자료에 포함되면 분석자는 배포 전에 수정하고, 이미 인용됐다면 1영업일 내 제한 조건과 정정 수치를 전달한다.

### DATA 지원자 면접 질문

1. “분석 도중 데이터 품질 문제 때문에 처음의 결론을 바꾸거나 철회한 경험을 설명해 달라. 어떤 검사가 문제를 드러냈고 이해관계자에게 언제 알렸는가?” 결론을 지키기 위해 결함을 축소하지 않았는지 확인한다.
2. “같은 이름의 지표를 여러 조직이 다르게 사용했던 사례를 말해 달라. 분모·분자·기준 시점 중 무엇이 달랐으며 최종적으로 어떤 명칭이나 정의를 채택했는가?” 수치 계산보다 정의 합의를 이끈 행동을 묻는다.
3. “분석 결과가 실제 의사결정에 인용됐지만 적용 범위를 제한해야 했던 경험을 설명해 달라. 보고서에 어떤 조건을 표시했고 이후 재검증은 어떻게 했는가?” 불확실성을 숨기지 않으면서도 실행 가능한 선택지를 제시했는지 확인한다.

## 영업팀(SALES)에서의 적용
<!--meta: sec=s6; dept=SALES; level=주니어|시니어; ct_band=상-->
SALES의 말과 문서는 계약 전에는 기대를 만들고 계약 후에는 수행 기준으로 사용된다. 영업 현장에서 빠르게 답하는 능력보다 확인되지 않은 약속을 구분하고, 고객 요구와 내부 수행 조건을 같은 기록에 남기는 행동을 중점적으로 판단한다.

### 구조적 조건 3개

| 구조적 조건 | 실제로 발생하는 압력 | 행동 판단 시 확인할 증거 |
|---|---|---|
| 약속의 비용이 다른 부서에서 발생한다 | 납기 단축, 추가 기능, 무상 지원을 약속하면 CNS·AIAX·BE·DATA의 투입시간과 운영 부담이 늘어난다 | 사전 검토자, 가정한 업무 범위, 추가 투입량, 제외 항목, 고객 전달 문구를 확인한다 |
| 수주 시점과 수행 시점이 떨어져 있다 | 제안 당시 가능했던 인력과 기술 조건이 착수 시점에는 달라질 수 있다 | 유효기간, 착수 전 재확인 항목, 의존 일정, 대체안, 변경 승인 기록을 확인한다 |
| 고객 관계가 개인에게 귀속되기 쉽다 | 구두 논의와 의사결정 배경이 담당자 개인의 메신저와 기억에 남을 수 있다 | 접촉 기록, 의사결정자, 반대 의견, 미확정 요청, 후속 담당자가 이해할 수 있는 인계 내용을 확인한다 |

수주 금액이 크더라도 실행 조건을 숨겼거나 수행 조직이 감당할 수 없는 약속을 했다면 바람직한 결과로 보지 않는다. 반대로 당장 계약 규모를 줄였더라도 손실 가능성을 미리 드러내고 장기 거래의 기준을 세운 행동은 별도로 평가한다.

### 상황 사례 1: 고객의 확답 요구를 검토 과제로 전환한 주도성

**상황:** A사는 제안 발표 중 6주 안에 상담 자동화 기능을 전 지점에 적용할 수 있는지 즉답을 요구했다. SALES 대리는 유사 사업 경험은 있었지만 고객 데이터 연계 방식과 지점별 업무 차이를 확인하지 못한 상태였다.

**행동:** 대리는 경쟁사보다 늦어 보일 것을 우려해 가능하다고 답하지 않고 “6주 안에 가능한 범위와 전 지점 적용 조건을 오늘 구분하겠습니다. 데이터 연계와 지점별 예외를 내일 오전까지 확인하면 오후 3시에 확정 답변을 드리겠습니다”라고 말했다. 회의 직후 CNS와 AIAX에 질문을 넘기는 데 그치지 않고 고객의 시스템 담당자와 40분 확인 회의를 직접 잡았다.

대리는 6주 내 가능한 공통 업무 2개, 추가 검증이 필요한 지점별 업무 3개, 고객 선행 조치 4개를 정리했다. 내부 검토 결과를 받은 뒤 전면 적용 대신 2개 지점 우선 적용과 4주 후 확대 판단안을 제안했다.

**결과:** 최초 요구보다 범위는 줄었지만 고객은 선행 조건이 명확하다는 이유로 우선 적용안을 선택했다. 착수 후 미확인 연계로 인한 일정 변경은 발생하지 않았고, 4주 검증 뒤 나머지 지점의 적용 일정을 확정했다.

### 상황 사례 2: 제안 문구의 기술적 한계를 드러낸 전문성

**상황:** B제조 제안서 초안에는 “설비 이상을 실시간으로 정확히 예측한다”는 문구가 포함돼 있었다. 실제 제공 가능한 방식은 10분 주기의 데이터 수집과 위험 신호 탐지였으며, 고장 자체를 확정적으로 예측할 근거는 없었다.

**행동:** SALES 과장은 문구가 강해야 수주에 유리하다는 의견에 동의하지 않고 AIAX와 DATA에 측정 가능한 성능 기준을 요청했다. “실시간과 예측을 그대로 쓰면 고객은 고장 전에 확정 알림을 기대합니다. 현재 검증 가능한 것은 10분 주기 위험 탐지와 재현율 범위입니다”라고 제안 검토 회의에서 지적했다.

과장은 문구를 ‘10분 주기 위험 신호 탐지’로 고치고, 검증 데이터 기준 재현율 82~87%, 오탐 검토 절차, 센서 누락 시 제외 조건을 함께 표시했다. 고객 질의에는 목표치와 보장치를 구분해 답하고 실제 데이터 검증 후 확정한다는 조건을 회의록에 남겼다.

**결과:** 고객은 과장된 고장 예측보다 현장 점검 우선순위를 만드는 기능으로 기대를 조정했다. 검수 단계에서 제안 문구와 성능 기준의 충돌이 발생하지 않았고, 오탐 처리 업무도 별도 범위로 합의됐다.

### 상황 사례 3: 수주 이후 수행팀이 재해석하지 않게 한 협업

**상황:** C금융 계약 협상에서는 ‘관리자 대시보드’가 포함됐지만 화면 수, 사용자 권한, 갱신 주기가 정해지지 않았다. 계약 직후 SALES가 고객 설명만 넘기면 CNS와 BE가 서로 다른 범위를 가정할 가능성이 컸다.

**행동:** SALES 사원은 계약 체결 다음 날 수행팀에 자료만 전달하지 않고 고객 발언을 확정 사항, 선호 사항, 미결 사항으로 구분했다. “화면 3개는 예시로 언급됐을 뿐 확정되지 않았고, 권한 분리는 고객 보안 담당자의 확인이 남았습니다”라고 착수 인계에서 설명했다.

사원은 고객과 CNS가 함께 참여하는 60분 범위 확인 회의를 마련하고, BE가 요구한 갱신 주기와 동시 사용자 수를 의제로 추가했다. 회의 후 고객 승인 내용과 미결 항목의 결정 기한을 각각 기록하고, 구두로 논의된 추가 요청은 계약 범위에 자동 편입하지 않았다.

**결과:** 수행팀은 화면 수를 임의로 추정하지 않고 5영업일 안에 범위를 확정했다. 계약 당시 예상하지 못한 권한 관리 작업은 별도 변경 항목으로 처리돼 개발 일정에 무단으로 추가되지 않았다.

### 상황 사례 4: 관계 유지를 위해 불가능한 범위를 약속하지 않은 고객중심

**상황:** 장기 거래 중인 A사는 정식 검수 이틀 전 임원 시연용 기능 4개를 추가해 달라고 요청했다. SALES 차장은 거절하면 관계가 나빠질 수 있다는 압력을 받았지만, 전부 반영하면 기존 검수 항목의 회귀 테스트 시간이 절반 이하로 줄어드는 상황이었다.

**행동:** 차장은 “오래 거래한 고객이므로 해드리겠다”고 답하지 않고 네 기능의 시연 목적을 확인했다. 고객이 임원에게 자동화 흐름을 보여주는 것이 핵심이라고 하자 “운영 반영까지 약속하면 기존 검수 품질이 낮아집니다. 시연용 데이터로 핵심 흐름 1개를 구성하고 나머지는 다음 변경 일정으로 확정하겠습니다”라고 제안했다.

차장은 AIAX와 BE에 당일 2시간 내 가능한 시연 범위를 확인하고, 시연용 기능은 운영 데이터와 연결하지 않으며 검수 완료 후 제거한다는 조건을 고객에게 전달했다. 나머지 3개 요청은 예상 투입량과 의사결정 기한을 붙여 후속 범위로 등록했다.

**결과:** 임원 시연은 예정대로 진행됐고 기존 검수 일정도 유지됐다. 고객은 추가 기능이 무상 포함된 것으로 오해하지 않았으며, 후속 3개 중 우선순위가 낮은 1개는 검토 과정에서 제외했다.

### 가치가 왜곡되기 쉬운 지점

- **수주 금액만으로 성과를 판단하는 경향:** 계약 금액이 목표를 초과했더라도 수행 원가를 발생시키는 미확정 약속, 검수 불가능한 표현, 고객 선행 조건 누락이 있으면 별도로 기록한다. 수주 후 30일 안에 범위 충돌이나 무상 추가 요청이 확인되면 제안·협상 단계의 기록을 재검토한다.
- **관계 유지를 위한 범위 확대 경향:** 고객 요청을 즉시 받아들이는 것을 관계 관리로 보지 않는다. 추가 요청의 목적, 기존 일정 영향, 대체안, 유상 여부를 설명하지 않은 채 수행팀에 넘기면 고객 만족 여부와 별개로 개선이 필요한 행동으로 판단한다.

### SALES 지원자 면접 질문

1. “고객이 회의 중 즉답이나 확약을 요구했지만 확인 후 답변한 경험을 설명해 달라. 무엇을 확인해야 했고 고객에게 답변 기한을 어떻게 제시했는가?” 모호한 보류가 아니라 검토 항목과 회신 시점을 통제했는지 확인한다.
2. “수주 가능성을 낮출 수 있는데도 제안 범위나 표현을 수정한 사례를 말해 달라. 내부의 반대 의견과 고객 반응은 어떠했고 결과적으로 어떤 위험을 줄였는가?” 기술·일정 한계를 이해하고 거래 조건에 반영한 경험을 묻는다.
3. “기존 고객이 계약 범위를 넘는 요청을 했을 때 관계를 해치지 않고 조정한 경험을 설명해 달라. 요청 목적을 충족한 대안, 비용이나 일정 처리, 수행팀과의 합의 과정을 말해 달라.” 단순 거절이나 무조건 수용이 아닌 선택지 설계 여부를 확인한다.

## 부서 경계에서 생기는 장면

부서 경계의 충돌은 한쪽이 가치를 따르지 않아서만 발생하지 않는다. 같은 가치를 고객 언어 보존, 기술 검증, 운영 안정, 수치 엄밀성, 신속한 약속처럼 서로 다른 방식으로 해석할 때 발생한다. 관리자는 어느 해석이 우월한지를 정하기보다 최종 의사결정자가 확인할 수 있는 공통 기준으로 전환하게 한다.

### 경계 사례 1: CNS와 AIAX의 요구 전달

**상황:** C금융은 상담 요약 결과가 “숙련 상담사가 작성한 것처럼 자연스러워야 한다”고 요청했다. CNS는 고객 표현을 수정하지 않고 전달해야 신뢰를 지킨다고 보았고, AIAX는 해당 문장만으로는 모델 완료 여부를 판정할 수 없다고 보았다.

**같은 가치의 다른 해석:** CNS는 고객중심을 고객이 사용한 언어와 업무 맥락을 보존하는 것으로 해석했다. AIAX는 고객중심을 검수 시 분쟁이 없도록 실패 조건과 허용 수준을 먼저 정하는 것으로 해석했다.

**충돌 장면:** AIAX 과장이 “자연스러움은 시험할 수 없습니다”라고 말하자 CNS 대리는 “고객 표현을 기술 용어로 바꾸면 요구를 축소하는 것으로 받아들일 수 있습니다”라고 답했다. 양쪽 모두 고객 요구를 지키려 했지만 한쪽은 원문 보존, 다른 쪽은 판정 가능성을 우선했다.

**합의 방법:** 두 팀은 고객이 부자연스럽다고 판단한 기존 요약 30건을 함께 수집하고 오류를 문장 단절, 핵심 조치 누락, 금지 표현 사용, 사실 추가의 네 유형으로 분류했다. 고객 판정자 2명이 같은 결과를 평가해 불일치 사례를 조정한 뒤 핵심 조치 누락 0건, 사실 추가 0건, 나머지 오류율 10% 이하를 1차 승인 기준으로 삼았다.

**역할 확정:** CNS는 고객 사례와 판정자를 확보하고 AIAX는 평가 세트와 반복 측정 방식을 관리한다. 기준 변경은 어느 한 팀이 구두로 수용하지 않으며 고객 승인 기록과 영향 분석을 함께 남긴다.

**결과:** ‘자연스러운 요약’이라는 표현은 고객 문서에 유지됐지만 검수표에는 네 오류 유형과 표본 수가 연결됐다. 첫 검수에서 문장 단절 오류가 13%로 나타나 해당 항목만 재개선했고, 요구 전체를 충족하지 못했다는 불필요한 논쟁을 피했다.

### 경계 사례 2: AIAX와 BE의 운영 이관

**상황:** AIAX는 문서 분류 모델의 검증 정확도 93%를 달성해 운영 이관이 가능하다고 판단했다. BE는 최대 응답시간이 8초이고 모델 서버 재시작에 17분이 걸려 현재 운영 기준으로는 연결할 수 없다고 판단했다.

**같은 가치의 다른 해석:** AIAX는 전문성을 모델의 재현 가능한 품질과 오류 분석으로 해석했다. BE는 전문성을 장애 탐지, 용량 한계, 복구 절차까지 포함한 지속 운영 가능성으로 해석했다.

**충돌 장면:** AIAX 대리는 “정확도 기준은 이미 넘었으니 API 연결 후 최적화하자”고 제안했고 BE 과장은 “연결 이후 지연이 발생하면 고객 요청 전체가 대기하므로 현재 상태는 완료가 아니다”라고 답했다. 완료의 기준이 모델 산출물과 서비스 운영 상태로 갈렸다.

**합의 방법:** 양 팀은 정확도, 95백분위 응답시간, 초당 처리량, 재시작 시간, 실패 시 대체 응답의 다섯 항목을 이관 관문으로 정했다. 95백분위 3초 이내, 재시작 5분 이내, 모델 오류 시 수동 분류 대기열 전환을 필수 조건으로 두고 운영 트래픽의 10%에서 2영업일간 확인하기로 했다.

**역할 확정:** AIAX는 모델 로딩 최적화, 추론 오류 코드, 품질 저하 기준을 담당하고 BE는 자동 재시작, 요청 제한, 대체 경로, 모니터링 알림을 담당한다. 장애 발생 시 정확도 문제와 인프라 문제를 구분할 로그 필드는 공동으로 정의한다.

**결과:** 모델 경량화와 사전 로딩으로 95백분위 응답시간은 2.4초, 재시작은 4분으로 줄었다. 운영 이관 후 첫 달에 모델 서버 오류 2건이 있었지만 요청은 대기열로 전환돼 고객 화면의 실패 응답은 발생하지 않았다.

### 경계 사례 3: DATA와 CNS의 지표 해석

**상황:** A사의 자동 추천 기능 사용 고객이 미사용 고객보다 구매 전환율이 9%포인트 높다는 결과가 나왔다. CNS는 고객 경영진에게 기능 효과로 설명하려 했고, DATA는 원래 구매 의도가 높은 고객이 기능을 더 많이 사용했을 가능성을 지적했다.

**같은 가치의 다른 해석:** DATA는 전문성을 관찰된 차이와 원인 효과를 구분하는 것으로 해석했다. CNS는 전문성을 고객이 다음 행동을 선택할 수 있도록 복잡한 결과를 명확한 메시지로 정리하는 것으로 해석했다.

**충돌 장면:** DATA 과장이 “인과 효과라고 말할 수 없다”고 하자 CNS 차장은 “차이가 있다는 말만으로는 고객이 확대 여부를 결정할 수 없다”고 답했다. DATA는 과도한 결론을 막으려 했고 CNS는 결론 없는 보고를 피하려 했다.

**합의 방법:** 양 팀은 경영진 보고 문장을 ‘사용 고객에서 9%포인트 높은 전환율이 관찰됐으며 기능 효과를 분리하려면 추가 검증이 필요하다’로 정했다. 동시에 지역과 기존 구매 빈도가 유사한 고객군을 대상으로 6주 비교를 시행하고, 3%포인트 이상 차이가 유지되면 확대 검토를 시작한다는 후속 판단 기준을 제시했다.

**역할 확정:** DATA는 비교군 구성, 제외 조건, 불확실성 범위를 관리하고 CNS는 결과가 연결되는 고객 의사결정과 선택지를 작성한다. 발표 자료의 제목에는 관찰 결과와 검증 결과를 구분하며, 발표자가 구두로 적용 범위를 넓히지 않도록 예상 질문 답변을 함께 검토한다.

**결과:** 고객은 즉시 전면 확대하지 않고 두 지역에서 검증을 진행했다. 6주 후 차이는 4.1%포인트로 확인돼 단계 확대가 결정됐으며, 최초 9%포인트를 그대로 사업 효과로 사용해 투자 규모를 과대 산정하는 일을 막았다.

### 경계 사례 4: SALES와 전 부서의 약속 확정

**상황:** B제조는 계약 서명 조건으로 “두 달 안에 전 공장 적용” 문구를 요구했다. SALES는 서명 일정을 지켜야 고객중심과 주도성이 드러난다고 보았고, 수행 부서는 공장별 데이터 구조와 설비 연계 방식이 확인되지 않은 상태에서 확약할 수 없다고 보았다.

**같은 가치의 다른 해석:** SALES는 주도성을 고객의 결정 시점을 놓치지 않고 선택 가능한 제안을 확정하는 것으로 해석했다. CNS·AIAX·BE·DATA는 주도성을 미확인 조건을 드러내고 실행 가능한 범위를 먼저 구성하는 것으로 해석했다.

**충돌 장면:** SALES 부장이 “내부 검토가 길어지면 이번 분기 계약이 무산된다”고 말하자 BE 차장은 “연계 방식도 모른 채 날짜를 쓰면 계약 후 일정 실패가 확정된다”고 답했다. 일정 준수 책임과 수행 가능성 책임이 서로 다른 시점을 기준으로 충돌했다.

**합의 방법:** SALES는 고객에게 전 공장 적용을 단일 완료일로 약속하지 않고 10영업일 진단, 공통 기능 적용, 공장별 확대의 세 관문을 제시했다. 각 부서는 1영업일 안에 필수 확인 항목과 최악 조건의 추가 기간을 제출하고, 차장급 검토 회의에서 확정 범위·조건부 범위·제외 범위로 구분했다.

**약속 확정 기준:** 고객 문서에는 공장 수, 데이터 제공일, 설비 연계 담당자, 현장 검증 가능일을 고객 선행 조건으로 적었다. 선행 조건이 예정일보다 3영업일 이상 늦어지면 확대 일정도 재산정하며, SALES가 단독으로 원래 날짜를 유지하지 못하도록 변경 승인자를 CNS 부장과 해당 기술 부서 부장으로 지정했다.

**결과:** 계약은 최초 요청일보다 3영업일 늦게 체결됐지만 첫 공장의 공통 기능은 예정대로 적용됐다. 진단 과정에서 별도 연계가 필요한 공장 2곳을 발견해 확대 일정을 조정했고, 고객은 계약 위반이 아니라 사전에 합의한 조건부 일정으로 처리했다.

| 재검토를 시작하는 조건 | 운영 또는 분석 담당 부서 | 최초 합의 시 | 오류율, 지연일, 비용 증가율, 표본 수처럼 관찰 가능한 조건을 사용한다 |

부서 간 합의는 회의 참석 자체로 완료되지 않는다. 합의 이후 상대 부서가 재해석하지 않아도 실행할 수 있고, 고객에게 전달된 내용과 내부 수행 기준이 연결돼 있을 때 완료로 본다. 동일한 충돌이 두 차례 발생하면 개인 간 조율로 남기지 않고 계약 테스트, 검수표, 지표 사전, 제안 승인 항목 가운데 해당 경계에 맞는 반복 통제로 전환한다.

## 온보딩 1~2주 — 이해와 질문의 장면
<!--meta: sec=s8; dept=CNS|AIAX|BE|DATA|SALES; level=주니어; ct_band=중-->
입사 1~2주의 관찰 목적은 업무를 이미 능숙하게 수행하는지 확인하는 데 있지 않다. 설명을 들은 뒤 자신의 이해를 검증하고, 막힘이 생겼을 때 혼자 추측하지 않으며, 필요한 사람에게 접근하는 방식을 확인한다. 멘토는 질문 횟수보다 질문 전 확인한 자료, 질문한 시점, 답변을 다음 행동에 반영한 흔적을 기록한다.

### 잘 드러난 장면 1 — 들은 설명을 자기 말로 되돌려 확인한다

**상황:** CNS 입사자는 A사의 상담 자동화 프로젝트 설명을 들으며 ‘검증 완료’가 기술 검증과 고객 승인 중 무엇을 뜻하는지 불분명하다고 느꼈다. 설명자는 이전 프로젝트부터 참여한 과장으로, 내부에서 사용하는 용어를 별도 설명 없이 사용했다. 입사자는 회의 중 이해한 내용을 바로 확정하지 않고 설명이 끝난 뒤 2분간 확인 시간을 요청했다.

**행동:** 입사자는 “제가 이해한 기준은 AIAX가 응답 정확도를 확인하면 내부 검증이 끝나고, 고객 담당자가 시나리오별 결과를 승인해야 최종 완료가 된다는 뜻인데 맞습니까?”라고 물었다. 이어서 내부 검증 결과만으로 다음 작업을 시작할 수 있는지, 고객 승인이 늦어질 때 누가 일정을 조정하는지까지 확인했다. 답변을 받은 뒤 회의 메모에서 ‘내부 검증’과 ‘고객 승인’을 별도 항목으로 나누고 각 담당자를 표시했다.

**결과:** 멘토는 입사자가 들은 표현을 그대로 반복하지 않고 단계와 책임자로 바꿔 확인한 점을 관찰했다. 같은 회의에 참석한 AIAX 담당자도 고객 승인 전까지 수정 가능한 범위를 명확히 알게 됐다. 이후 입사자가 작성한 회의 기록에는 완료 상태가 한 단어로 뭉쳐 기록되지 않았다.

**판단:** 이 장면은 질문을 많이 했기 때문이 아니라 자신의 해석이 실제 업무 흐름과 일치하는지 확인했다는 점에서 의미가 있다. 되묻는 내용이 틀렸더라도 설명을 듣고 수정한 기록이 남아 있으면 학습 행동으로 판단한다. 반대로 고개를 끄덕인 횟수나 회의 중 발언량은 이해 여부의 근거로 사용하지 않는다.

### 잘 드러난 장면 2 — 접근 권한의 막힘을 반나절 안에 알린다

**상황:** BE 입사자는 오전 9시 30분에 개발 환경 안내를 받고 저장소와 이슈 관리 도구에 접속하려 했다. 저장소는 열렸지만 B제조 프로젝트의 이슈 보드는 권한 오류가 발생했고, 안내 문서에는 별도 신청 절차가 적혀 있지 않았다. 입사자는 개인 설정 문제인지 확인하기 위해 재로그인, 계정 선택, 공통 권한 페이지를 차례로 확인했다.

**행동:** 오전 11시 20분까지 해결되지 않자 입사자는 오류 화면, 시도한 조치 3개, 필요한 접근 범위를 정리해 멘토에게 알렸다. “제가 더 확인할 설정이 있으면 진행하고, 프로젝트별 승인이 필요한 권한이면 승인 담당자를 연결해 주십시오”라고 요청했다. 기다리는 동안 권한이 없어도 볼 수 있는 공통 개발 규칙을 읽고 질문 2개를 메모했다.

**결과:** 멘토는 프로젝트 관리자인 과장에게 승인을 요청했고 오후 1시 40분에 권한이 부여됐다. 입사자는 하루를 잃지 않았고, 동일한 오류가 발생한 다음 입사자를 위해 권한 신청 경로가 안내 문서에 추가됐다. 문제를 알린 행위와 대기 시간에 수행한 대체 행동을 함께 긍정적으로 기록한다.

**판단:** 반나절은 모든 장애의 일률적 보고 기한이 아니라 초기 온보딩에서 업무 진입 자체를 막는 권한 문제의 기준으로 사용한다. 오류 원인을 전부 밝히지 못했더라도 자신이 확인한 범위와 필요한 조치를 구분해 알리면 적절한 행동으로 본다. 권한 요청을 여러 사람에게 동시에 보내 책임자를 혼란스럽게 한 경우에는 보고 속도와 별개로 요청 경로를 교정한다.

### 어긋난 장면 — 모르는 용어를 메모만 하고 3일을 보낸다

**상황:** DATA 입사자는 C금융 분석 회의에서 ‘정상군’, ‘관찰 창’, ‘재산출’이라는 표현을 들었으나 뜻을 묻지 않고 메모만 남겼다. 입사자는 회의 후 문서 검색을 했지만 프로젝트별 의미가 다르다는 점을 확인하지 못했다. 3일째에 멘토가 메모를 검토하면서 입사자가 정상군을 오류가 없는 데이터 전체로 이해하고 있음을 발견했다.

**행동과 영향:** 입사자는 질문하면 기본 지식이 부족해 보일 수 있다고 판단해 용어를 추측했다. 아직 외부 산출물은 작성하지 않았으므로 직접적인 재작업은 발생하지 않았지만, 분석 기준을 잘못 이해한 상태로 다음 주 업무를 준비하고 있었다. 이 장면만으로 소극적이거나 전문성이 부족하다고 단정하지 않는다.

**필요했던 지원:** 멘토는 프로젝트 고유 용어와 일반 직무 용어를 나눠 표시한 1쪽짜리 용어 목록을 제공하고, 매일 오후 4시에 10분간 질문 시간을 1주일 동안 운영한다. 질문할 때는 ‘들은 문장’, ‘현재 이해’, ‘확인이 필요한 차이’를 적게 해 막연한 질문 부담을 낮춘다. 2영업일 뒤 같은 용어가 사용된 회의 기록을 입사자가 다시 읽고 의미와 적용 위치를 설명하게 한다.

### 이 구간에 멘토가 관찰할 항목

| 관찰 항목 | 관찰 장면 | 적절한 신호 | 추가 지원이 필요한 신호 |
|---|---|---|---|
| 이해 확인 방식 | 업무 설명 직후 또는 회의 종료 전 | 자신의 말로 업무 순서·담당자·완료 조건을 되돌려 확인한다 | 들은 표현을 그대로 반복하거나 확인 없이 임의로 확정한다 |

멘토는 첫 2주 동안 위 항목을 최소 3개 장면에서 확인하고, 한 번의 실수를 성향으로 기록하지 않는다. 관찰 기록에는 날짜, 업무 상황, 입사자가 실제로 한 말이나 행동, 멘토가 제공한 지원을 함께 남긴다. 지원 후 동일한 상황에서 행동이 달라졌는지를 다음 판단 근거로 사용한다.

### 관찰하지 말아야 할 항목

- 점심 모임 참석 횟수, 회식 반응, 사적인 대화량을 협업의 근거로 사용하지 않는다.
- 질문이 적다는 이유만으로 이해가 빠르다고 판단하지 않으며, 질문이 많다는 이유만으로 준비가 부족하다고 판단하지 않는다.
- 기존 임직원과 사용하는 도구의 단축키, 내부 약어 암기 속도, 사내 인맥 수를 전문성 판단에 포함하지 않는다.
- 출신 회사의 규모, 이전 직급, 학력, 말투의 유창함을 온보딩 행동보다 앞세우지 않는다.
- 야간 메시지 응답, 자발적 연장근무, 휴게시간 축소를 주도성의 증거로 인정하지 않는다.
- 첫 2주에 고객이나 시스템의 전체 구조를 설명하지 못한다는 이유로 향후 수행 가능성을 단정하지 않는다.

## 온보딩 3~4주 — 첫 산출물의 장면
<!--meta: sec=s9; dept=CNS|AIAX|BE|DATA|SALES; level=주니어; ct_band=중-->
입사 3~4주에는 처음 맡은 산출물을 통해 요구 해석, 중간 확인, 검토 반영 방식을 관찰한다. 산출물의 규모나 외관보다 누가 어떤 목적으로 사용할지 확인했는지, 확정되지 않은 내용을 표시했는지, 검토 가능한 시점에 공유했는지를 본다. 최초 결과물은 학습 자료이므로 기존 구성원과 같은 속도를 일률적으로 요구하지 않는다.

### 잘 드러난 장면 1 — 작성 전에 사용 장면을 확인한다

**상황:** SALES 입사자는 B제조 제안 준비를 위해 고객 미팅 요약본 작성을 요청받았다. 요청 문장은 “논의 내용을 두 쪽으로 정리해 달라”는 수준이었고, 요약본의 독자는 명시되지 않았다. 입사자는 회의 녹취와 기존 양식을 읽은 뒤 작성에 들어가기 전에 요청자에게 10분 확인을 제안했다.

**행동:** 입사자는 “이 문서는 고객에게 재확인받을 자료인지, 내부 제안 인계용인지에 따라 미확정 사항을 쓰는 방식이 달라집니다”라고 말했다. 요청자는 내부 제안 회의용이며 CNS와 AIAX가 고객 요구의 우선순위를 판단하는 데 사용한다고 답했다. 입사자는 고객 발언, 내부 해석, 추가 확인이 필요한 사항을 세 열로 분리한 초안을 당일 오후 3시에 공유했다.

**결과:** CNS는 고객이 확정한 요구와 SALES가 추정한 요구를 구분해 검토할 수 있었다. AIAX는 기술 확인이 필요한 항목 2개를 다음 고객 질의에 추가했고, 최종 요약본은 최초 요청 분량을 넘기지 않았다. 멘토는 문서 디자인보다 독자와 사용 목적을 먼저 확인한 행동을 기록했다.

### 잘 드러난 장면 2 — 완성 전 검토 가능한 단위를 보여준다

**상황:** AIAX 입사자는 A사의 문서 분류 기능에 사용할 테스트 시나리오 초안을 맡았다. 유사한 내부 자료가 있었지만 고객 문서의 분류 기준과 일치하지 않는 항목이 섞여 있었다. 입사자는 전체 시나리오를 완성한 뒤 검토받는 대신 대표 유형 5개를 먼저 작성했다.

**행동:** 입사자는 각 유형에 입력 예시, 기대 결과, 경계 사례, 판단이 필요한 질문을 붙여 다음 날 오전 리뷰를 요청했다. “제가 ‘기타’ 분류를 마지막 수단으로 두었는데, 고객 운영에서는 특정 부서로 보내는 것이 맞는지 확인이 필요합니다”라고 설명했다. 리뷰에서 기준이 바뀌자 나머지 유형에 적용할 작성 규칙을 수정하고 변경 이유를 문서 상단에 남겼다.

**결과:** 30개 유형을 모두 작성한 뒤 구조를 바꾸는 재작업을 피했다. 리뷰어는 표현 교정보다 분류 원칙에 시간을 사용할 수 있었고, 입사자는 변경된 기준을 나머지 항목에 일관되게 적용했다. 중간 공유가 단순 진행 보고가 아니라 손실을 줄이는 검토 요청으로 기능했다.

### 어긋난 장면 — 요구를 확인하지 않고 완성도 높은 산출물을 만든다

**상황:** CNS 입사자는 C금융 인터뷰 결과를 정리해 달라는 요청을 받고 3일 동안 25쪽의 발표 자료를 작성했다. 도표와 문장은 정교했지만 요청자가 필요로 한 것은 다음 인터뷰 질문을 조정하기 위한 1쪽짜리 쟁점 목록이었다. 입사자는 과거 회사에서 사용하던 보고서 형식을 기준으로 완성도를 높였다.

**행동과 영향:** 첫 리뷰에서 요청자는 “자료 자체는 잘 만들었지만 이번 주 인터뷰에 바로 쓸 수 있는 판단 항목이 보이지 않습니다”라고 피드백했다. 입사자는 25쪽을 다시 축약하면서 하루를 추가로 사용했고, 다음 인터뷰 질문 확정이 반나절 늦어졌다. 문서 작성 능력의 부족이 아니라 사용 목적을 확인하지 않은 업무 시작 방식이 재작업 원인으로 기록됐다.

**필요했던 지원:** 관리자는 산출물 요청 시 독자, 사용 시점, 최대 분량, 반드시 포함할 판단을 함께 전달했는지 먼저 점검한다. 입사자에게는 작업 예상 시간이 4시간을 넘는 경우 목차나 표본을 먼저 공유하도록 2주간 임시 기준을 둔다. 다음 과제에서는 시작 후 1시간 이내에 목적과 완료 기준을 입사자가 되묻게 하고, 관리자는 확인 여부를 관찰한다.

### 첫 리뷰에서 피드백을 다루는 모습의 차이

| 리뷰 장면 | 성장에 연결되는 모습 | 추가 개입이 필요한 모습 | 리뷰어의 후속 조치 |

피드백을 즉시 수용했다는 사실만으로 좋은 태도로 판단하지 않는다. 고객 사실관계나 기술 제약과 충돌하는 피드백이라면 근거를 제시하고 확인을 요청해야 한다. 다만 이견 제시 후 결정된 사항을 반영하지 않는 행동은 의견의 타당성과 별도로 관리한다.

### 이 구간 관찰 항목

1. 산출물 착수 전 독자, 사용 목적, 제출 시점, 완료 기준 가운데 누락된 항목을 확인하는지 본다.
2. 4시간 이상 걸리는 작업을 최종본까지 숨기지 않고 목차, 표본, 핵심 가정 중 하나로 중간 공유하는지 본다.
3. 사실, 해석, 제안, 미확정 사항을 문서에서 구분하는지 본다.
4. 리뷰 의견을 항목별로 기록하고 반영 여부를 확인할 수 있게 남기는지 본다.
5. 수정 과정에서 원래 요청 범위를 임의로 넓히거나 중요한 근거를 삭제하지 않는지 본다.
6. 품질을 높이기 위해 사용한 시간이 실제 사용 목적에 비례하는지 본다.
7. 첫 산출물의 오류가 안내 부족, 기준 불명확, 도구 미숙, 판단 누락 중 어디에서 발생했는지 구분하는지 본다.

멘토는 최초 산출물의 점수나 등급을 단독으로 남기지 않고 초안, 리뷰 내용, 수정본을 연결해 보관한다. 리뷰가 구두로 끝났다면 입사자가 이해한 수정 항목을 당일 안에 5줄 이내로 정리하게 한다. 다음 산출물에서 같은 기준을 독립적으로 적용했는지가 이 구간의 핵심 후속 관찰이 된다.

## 온보딩 2개월 — 협업과 경계의 장면

입사 2개월에는 개인에게 배정된 작업보다 다른 부서의 입력을 받고 결과를 넘기는 경계에서 행동이 드러난다. 요청 문장을 그대로 처리했는지가 아니라 상대 부서가 그 결과를 어디에 사용하는지 확인하고, 미결 사항을 숨기지 않으며, 일정 위험을 조기에 공유하는지를 본다. 관리자는 협업 상대의 만족도만 묻지 않고 요청·응답 기록과 실제 인계 결과를 함께 확인한다.

### 잘 드러난 장면 1 — 타 팀 요청의 배경을 질문한다

**상황:** DATA 입사자는 SALES로부터 “B제조 고객 데이터에서 이상치 비율을 오늘 안에 알려 달라”는 요청을 받았다. 요청에는 대상 기간, 이상치 기준, 수치의 사용처가 없었다. 입사자는 임의 기준으로 계산하면 빠르게 답할 수 있었지만 숫자가 제안서에 들어갈 가능성을 고려했다.

**행동:** 입사자는 “이 수치가 고객 현황 진단용인지, 제안 범위 산정용인지 확인하고 싶습니다. 대상 기간과 이상치 정의가 정해져 있지 않으면 두 수치가 크게 달라집니다”라고 답했다. SALES는 다음 날 고객 미팅에서 데이터 정제 범위를 설명하기 위한 자료라고 밝혔다. 입사자는 최근 3개월과 12개월을 나눠 계산하고, 결측·범위 초과·중복을 별도 비율로 제시했다.

**결과:** SALES는 하나의 합계 수치를 단정적으로 제시하지 않고 기준별 차이를 고객에게 설명했다. 고객은 중복 데이터가 특정 설비에서 집중된다는 사실을 확인해 표본 제공 범위를 조정했다. 입사자는 요청을 지연시키지 않으면서 숫자의 사용 목적에 맞는 조건을 확보했다.

### 잘 드러난 장면 2 — 인계받은 과제의 미결 항목을 목록으로 만든다

**상황:** BE 입사자는 다른 지점 개발자가 긴급 지원을 마치고 복귀하면서 A사 연계 과제를 인계받았다. 코드와 이슈 티켓은 있었지만 고객 테스트 계정, 재시도 정책, 오류 메시지 문구는 확정되지 않았다. 기존 담당자는 “대부분 됐고 나머지만 이어서 하면 된다”고 설명했다.

**행동:** 입사자는 완료된 항목과 미결 항목을 분리하고, 미결 항목마다 결정자·필요 자료·영향 기능·확인 기한을 적었다. 인계 회의에서 “재시도 횟수가 정해지지 않으면 부하 시험 조건도 확정할 수 없습니다. 이 항목은 AIAX가 아니라 고객 운영 담당자의 결정이 맞습니까?”라고 확인했다. 회의 당일 목록을 CNS와 기존 담당자에게 보내 이견이 있으면 다음 날 정오까지 표시하도록 요청했다.

**결과:** 고객 테스트 계정 발급이 지연되고 있다는 사실이 배포 직전에 발견되는 일을 피했다. 재시도 정책은 고객 운영 담당자에게 질의됐고, 답변 전까지 적용할 임시값과 변경 위치가 기록됐다. 후속 담당자는 인계받았다는 이유만으로 이전 판단을 확정된 사실로 취급하지 않았다.

### 어긋난 장면 — 도움 요청 시점을 놓쳐 일정이 밀린다

**상황:** AIAX 입사자는 C금융 문서 추출 결과의 오류 원인을 분석하는 과제를 받았다. 이틀째부터 특정 문서 형식에서만 오류가 반복됐지만 자신이 해결해야 실력을 인정받는다고 생각해 동료에게 알리지 않았다. 예정된 중간 확인 시간에는 “조금 더 보면 될 것 같습니다”라고만 보고했다.

**행동과 영향:** 제출 전날 입사자는 문서 변환 단계의 라이브러리 문제일 가능성을 알렸고, BE 담당자가 확인한 결과 해당 형식은 별도 전처리가 필요했다. 지원 요청이 늦어 테스트 일정이 1영업일 밀렸고, 고객 보고 자료의 표본 수를 줄여야 했다. 관리자는 해결하지 못한 사실보다 막힘의 범위와 일정 영향을 알고도 구체적으로 공유하지 않은 시점을 문제로 기록했다.

**필요했던 지원:** 관리자는 불확실한 원인 분석의 경우 4시간 동안 유의미한 가설이 추가되지 않거나 동일 오류가 3회 반복되면 동료 검토를 요청하도록 기준을 제시한다. 입사자와 함께 도움 요청 문장을 ‘현상, 이미 확인한 것, 남은 가설, 필요한 역할, 결정 기한’ 순서로 작성한다. 다음 2주 동안 주 2회 진행 점검에서 완료율 대신 막힌 시간과 외부 의존 항목을 먼저 확인한다.

### 시니어 입사자에게 달라지는 장면 1 — 요청 구조 자체를 조정한다

**상황:** CNS 시니어 입사자는 여러 프로젝트에서 AIAX에 기술 검토 요청이 몰리지만 요청서마다 필요한 정보가 달라 답변 시간이 길어지는 상황을 발견했다. 단건 요청을 대신 처리하는 것만으로는 지연이 반복될 것으로 판단했다. 다만 입사 2개월 시점에 전사 양식을 일방적으로 바꾸지 않고 최근 요청 6건을 표본으로 삼았다.

**행동:** 시니어 입사자는 AIAX 과장과 30분 검토를 진행해 답변에 반드시 필요한 고객 데이터, 사용 환경, 예상 사용자 수, 결정 기한을 추렸다. 이후 CNS 내부에서 2주간 임시 양식을 사용하고 누락률과 회신 시간을 비교하자고 제안했다. “양식을 채우는 일이 늘어나는 대신 되묻는 횟수가 줄어드는지 먼저 확인하겠습니다”라고 설명했다.

**결과:** 표본 기간의 추가 질의는 요청당 평균 3회에서 1회로 줄었고, 기존 양식 폐지 여부는 과장급 회의에서 별도로 결정했다. 시니어에게는 개인 요청을 잘 처리하는 것뿐 아니라 반복되는 경계 손실을 작은 실험으로 전환하는 행동을 기대한다. 권한을 넘어서 규칙을 확정하지 않고 관련 부서의 검증을 거쳤는지도 함께 본다.

### 시니어 입사자에게 달라지는 장면 2 — 이해관계가 다른 부서의 판단 기준을 연결한다

**상황:** SALES 시니어 입사자는 계약 일정 준수를 우선하는 영업 요청과 안정성 검토 시간을 확보하려는 BE 의견이 충돌하는 회의에 참여했다. 양측은 각각 “고객이 기다린다”와 “검증 없이 배포할 수 없다”는 말만 반복했다. 시니어 입사자는 어느 한쪽을 설득하기보다 결정에 필요한 조건을 표로 정리했다.

**행동:** 고객이 반드시 확인해야 하는 기능 2개, 배포 후 변경 가능한 항목 3개, 장애 시 복구 시간, 승인 기한을 분리했다. “전체 완료일을 놓고 다투지 말고 고객 확인에 필요한 최소 범위와 되돌릴 조건부터 합의하겠습니다”라고 제안했다. CNS가 고객 확인 범위를 조정하고 BE가 중단 조건을 제시하도록 역할을 나눴다.

**결과:** 고객 확인용 범위는 예정일에 제공하고 나머지 기능은 2영업일 뒤 배포하는 합의가 이뤄졌다. 시니어는 자신의 부서 요구를 관철한 것이 아니라 서로 다른 판단 기준을 하나의 결정 구조로 연결했다. 회의 후 결정 사항과 미결 사항을 분리해 남겼는지도 평가 근거로 사용한다.

| 부서 간 이견 | 상대 설명을 확인한 뒤 자신의 제약을 제시한다 | 양측 제약을 공통 결정 조건과 중단 조건으로 바꾼다 |
| 책임 범위 | 맡은 작업과 타 부서 대기 항목을 구분한다 | 공백이 생긴 경계의 임시 책임자와 종료 시점을 제안한다 |
| 기록 | 구두 합의 후 담당자와 기한을 남긴다 | 반복 충돌을 양식·검수·회의 구조 개선으로 연결한다 |

이 시기에는 협업 상대가 친절하다고 평가했는지를 단독 근거로 사용하지 않는다. 필요한 이견을 제시해 상대가 불편함을 느꼈더라도 근거, 표현, 결정 이후의 실행이 적절하면 협업 행동으로 인정한다. 반대로 관계가 원만해 보여도 미결 항목과 일정 위험을 숨긴 경우에는 별도 피드백을 실시한다.

## 온보딩 3개월 — 판단과 책임의 장면
<!--meta: sec=s11; dept=CNS|AIAX|BE|DATA|SALES; level=주니어|시니어; ct_band=상-->
입사 3개월에는 정답을 알고 있는지보다 불완전한 정보에서 전제를 확인하고, 선택의 영향을 설명하며, 자신의 오류를 처리하는 방식을 확인한다. 판단의 난도는 직급과 배정 기회에 따라 다르므로 동일한 고객 대응이나 기술 결정을 모든 입사자에게 요구하지 않는다. 관리자는 결과가 좋았다는 이유만으로 과정의 위험을 생략하지 않고, 결과가 나빴다는 이유만으로 판단 당시 확보할 수 없던 정보를 사후 기준으로 적용하지 않는다.

### 잘 드러난 장면 1 — 고객 요청의 전제를 확인해 범위를 되돌린다

**상황:** A사는 CNS 입사자에게 “다음 주까지 상담 이력 전체를 AI 학습에 반영해 달라”고 요청했다. 고객 담당자는 전체 이력을 사용하면 정확도가 즉시 높아질 것으로 기대했지만, 데이터의 기간과 상담 유형별 품질은 확인되지 않았다. 요청을 그대로 전달하면 DATA와 AIAX가 범위 산정부터 다시 해야 하는 상황이었다.

**행동:** 입사자는 “전체 이력이라는 표현이 보관된 모든 기간을 뜻하는지, 최근 운영 기준이 반영된 기간을 뜻하는지 먼저 확인해야 합니다”라고 답했다. 이어서 사용 목적, 대상 상담 유형, 제외해야 할 기록, 기대하는 개선 지표를 질문했다. 고객이 최근 6개월의 세 유형을 우선 대상으로 한다고 답하자 해당 범위로 1차 검토하고 나머지는 결과 확인 후 결정하는 안을 제시했다.

**결과:** 최초 요청보다 데이터 범위는 줄었지만 목표와 무관한 과거 양식의 정제 작업을 피했다. DATA는 표본 품질을 2영업일 안에 확인했고 AIAX는 적용 가능 시점을 근거와 함께 제시했다. 입사자는 고객 요구를 거절한 것이 아니라 요청에 숨어 있던 전제를 드러내 실행 가능한 범위로 되돌렸다.

**판단:** 고객의 첫 표현과 다른 범위를 제안했더라도 목적, 제약, 대안, 확인 절차가 연결돼 있으면 고객중심 행동으로 기록한다. 고객이 요구한 일정에 맞췄다는 사실만으로 적절한 판단으로 보지 않는다. 범위를 조정할 권한이 없는 입사자는 독자적으로 확정하지 않고 승인자를 연결해야 한다.

### 잘 드러난 장면 2 — 자기 실수를 영향 확인 즉시 보고한다

**상황:** DATA 입사자는 C금융 주간 지표를 갱신하면서 필터 조건 하나를 이전 주 값으로 유지했다. 검토 중 전체 건수와 세부 건수의 합계가 맞지 않아 오류를 발견했고, 해당 표가 40분 전에 CNS 내부 문서에 복사됐음을 확인했다. 아직 고객에게는 전달되지 않았지만 오후 회의 자료로 사용할 예정이었다.

**행동:** 입사자는 수정본을 완성할 때까지 기다리지 않고 발견 후 15분 안에 담당 과장에게 알렸다. “제가 필터 기간을 잘못 유지해 표 2개가 영향을 받았습니다. 고객 전달 전이며 CNS 문서 한 곳에 복사된 상태입니다. 30분 안에 재산출하고 복사 위치도 확인하겠습니다”라고 보고했다. 수정 후에는 영향받지 않은 표까지 다시 계산하지 않고 오류 조건과 연결된 항목만 검증한 뒤 변경 내역을 남겼다.

**결과:** CNS는 회의 전에 표를 교체했고 고객에게 잘못된 수치가 전달되지 않았다. 관리자는 오류 발생 자체, 발견 과정, 보고 시점, 영향 차단, 재발 방지 조치를 분리해 기록했다. 입사자는 이후 갱신 작업에 기준 기간을 자동 표시하는 확인 열을 추가했다.

**판단:** 보고 속도는 발견 시점과 영향 범위를 기준으로 판단하며, 완전한 원인 분석이 끝날 때까지 기다리게 하지 않는다. 오류를 스스로 발견했다는 이유로 영향 보고를 생략할 수 없고, 경미한 오탈자까지 모두 긴급 보고하도록 요구하지도 않는다. 고객 전달, 운영 반영, 다른 부서의 후속 판단에 영향을 주는지를 우선 확인한다.

### 어긋난 장면 — 판단을 볼 기회가 충분하지 않았다

**상황:** BE 입사자는 첫 90일 동안 공통 모듈 문서 정리와 이미 결정된 수정 작업을 주로 맡았다. 고객 질의, 장애 대응, 부서 간 범위 협의에는 참관만 했고 자신의 대안을 제시하거나 결정을 설명할 기회가 두 차례뿐이었다. 관리자는 일정 준수와 코드 품질은 확인했지만 불확실한 상황에서의 판단을 평가할 근거가 부족했다.

**처리:** 관찰 기회 부족을 입사자의 소극성이나 낮은 역량으로 환산하지 않는다. 관리자는 ‘미충족’이 아니라 ‘관찰 근거 부족’으로 표시하고, 90일 이후 30일 안에 작은 판단 과제를 배정한다. 과제는 운영 영향이 제한되고 되돌릴 수 있어야 하며, 예를 들어 오류 응답 방식 두 안의 장단점을 정리해 과장 승인 후 하나를 적용하는 수준으로 정한다.

**필요한 지원:** 판단 과제 전에 입사자에게 결정 가능한 범위, 반드시 협의할 대상, 중단 조건을 설명한다. 결과만 제출하게 하지 않고 선택하지 않은 대안과 예상 영향을 15분 리뷰에서 말하게 한다. 관리자는 이 추가 관찰을 수습 기간을 임의로 연장하는 수단으로 사용하지 않으며, 근로계약서와 취업규칙에 따른 절차를 별도로 준수한다.

### 90일 시점에 확인하는 것

| 확인 영역 | 확인할 근거 | 판단 질문 |
|---|---|---|
| 이해의 갱신 | 초기 메모와 최근 업무 기록 | 설명을 받은 뒤 잘못 이해한 부분을 수정하고 다음 업무에 반영했는가 |
| 산출물 사용성 | 초안·리뷰·수정본 | 독자와 사용 목적에 맞춰 정보의 깊이와 형식을 조정했는가 |
| 경계 관리 | 요청·인계·합의 기록 | 다른 부서의 입력과 자신의 책임 범위를 구분했는가 |
| 위험 공유 | 막힘 보고와 일정 변경 기록 | 영향이 커지기 전에 사실, 가설, 필요한 도움을 알렸는가 |
| 고객 판단 | 질의 목록과 범위 합의 | 고객 표현을 그대로 받지 않고 목적과 전제를 확인했는가 |
| 오류 책임 | 오류 보고와 후속 조치 | 실수를 숨기지 않고 영향 차단과 재발 방지까지 연결했는가 |
| 피드백 학습 | 첫 리뷰와 후속 산출물 | 같은 피드백을 다음 과제에서 독립적으로 적용했는가 |
| 역할 적정성 | 배정 과제와 관찰 횟수 | 직급에 맞는 판단 기회가 실제로 제공됐는가 |

90일 대화에는 입사자 본인이 선택한 장면 2개와 관리자가 선택한 장면 2개를 가져온다. 각 장면은 상황, 실제 행동, 발생한 영향, 다음에 바꿀 행동을 5분 이내로 설명한다. 양측의 해석이 다르면 인상으로 결론 내리지 않고 당시 메시지, 문서, 리뷰 기록을 확인한다.

### 90일 시점에 확인하지 않는 것

- 입사 전 회사의 방식과 헤드헌터랩 방식을 처음부터 동일하게 수행했는지는 확인하지 않는다.
- 야간·휴일 연락에 즉시 응답했는지, 휴가를 적게 사용했는지, 근무시간을 초과했는지는 가치 실천 근거로 사용하지 않는다.
- 특정 관리자와 성격이 잘 맞는지, 회의에서 말이 많은지, 사내 행사에 적극적인지는 판단 항목에 포함하지 않는다.
- 배정되지 않은 고객 발표, 장애 대응, 제안 작성 경험이 없다는 사실을 결함으로 처리하지 않는다.
- 90일 안에 매출, 대규모 비용 절감, 전사 제도 변경을 만들었는지를 공통 기대치로 두지 않는다.
- 한 번의 성공이나 실수를 네 가치 전체에 대한 판정으로 확대하지 않는다.

90일 시점의 결론은 확인된 행동, 아직 관찰하지 못한 행동, 조직이 제공하지 못한 조건, 다음 30~90일의 성장 과제를 구분해 작성한다. 시니어에게는 더 넓은 판단 범위를 기대할 수 있지만 권한과 정보가 제공되지 않은 결과까지 책임지게 하지 않는다. 주니어에게는 독립 결정의 크기보다 적절한 시점에 확인하고 승인받는 행동을 우선 본다.

**수습 평가와의 관계:** 이 문서의 장면 기록은 HR-06 수습 평가의 관찰 근거로만 사용하며, 본채용 여부와 절차는 HR-06의 사전 고지된 평가 기준과 서면 절차에 따른다.

## 온보딩 이후 — 가치가 자리 잡는 신호
<!--meta: sec=s12; dept=CNS|AIAX|BE|DATA|SALES; level=주니어|시니어; ct_band=상-->
90일 이후에는 개별 장면을 통과했는지가 아니라 유사한 상황에서 행동이 반복되고 다른 사람의 업무에도 도움이 되는지를 확인한다. 행동의 안정성은 어려운 업무를 맡았다는 사실보다 설명을 덜 받아도 적절한 확인과 공유가 이뤄지는지로 판단한다. 6개월과 1년 시점의 신호는 승진 요건이나 등급 기준이 아니라 성장 대화의 근거로 사용한다.

### 6개월 시점에 나타나는 신호 1 — 남긴 산출물이 다른 사람에게 재사용된다

입사자가 작성한 회의 기록, 테스트 기준, 분석 확인표, 고객 질의 목록 가운데 하나가 다른 구성원의 업무에 사용된다. 단순 복사 횟수보다 사용자가 추가 설명 없이 적용할 수 있는지가 중요하다. 재사용 과정에서 조건이 다른 부분을 표시하고 원 작성자에게 수정 제안이 돌아오면 산출물이 개인 작업을 넘어 팀 자산으로 기능한 것으로 본다.

확인할 때는 “문서를 잘 만들었다”는 평가 대신 누가 어떤 상황에서 사용했고, 재작성 시간을 얼마나 줄였으며, 잘못 적용될 위험은 없었는지 묻는다. 재사용이 없더라도 과제가 일회성이었다면 부정적 신호로 보지 않는다. 반복 업무인데 매번 같은 자료를 새로 만들고 있다면 보관 위치와 검색 방식부터 확인한다.

### 6개월 시점에 나타나는 신호 2 — 질문의 수준이 바뀐다

초기에는 용어와 절차를 묻던 입사자가 6개월에는 선택지별 영향, 우선순위, 예외 조건을 질문한다. 예를 들어 “이 지표는 무엇입니까?”에서 “이 지표를 월간 비교에 사용하면 계절 변동을 어떻게 분리합니까?”로 질문의 범위가 이동한다. 질문 수가 줄어드는 것이 아니라 답을 얻은 뒤 다음 판단에 필요한 조건까지 연결하는 변화가 나타난다.

멘토는 질문의 난도가 높아졌는지만 보지 않고 이전 답변과 자료를 활용했는지 확인한다. 동일한 기초 질문이 반복되면 기억력 문제로 단정하지 않고 문서 위치, 용어 일관성, 설명 방식에 결함이 있는지 점검한다. 질문을 하지 않는 상태는 독립 수행과 혼자 막혀 있는 경우를 구분해 확인한다.

### 6개월 시점에 나타나는 신호 3 — 거절과 대안 제시가 함께 가능해진다

입사자는 일정, 기술 제약, 데이터 품질 때문에 요청을 그대로 수용할 수 없을 때 불가능하다는 말로 끝내지 않는다. 수행 가능한 최소 범위, 필요한 추가 조건, 다시 판단할 시점을 제시한다. 고객이나 상위 직급자의 요청이라도 영향 근거를 설명하되 최종 승인 권한은 넘지 않는다.

예를 들어 AIAX 담당자는 “이번 주 전체 적용은 어렵습니다”에 그치지 않고 대표 시나리오 10개를 우선 검증하고 오류율이 기준 이내면 다음 범위로 확대하는 안을 제시한다. SALES 담당자는 고객 요청을 즉시 약속하지 않고 수행 부서 확인 기한을 먼저 전달한다. 관리자는 거절 횟수가 아니라 불필요한 충돌과 무리한 확약을 함께 줄였는지 본다.

### 6개월 시점에 나타나는 신호 4 — 자신의 작업이 다음 단계에 미치는 영향을 예측한다

입사자는 파일 제출이나 기능 완료를 자신의 업무 종료로 보지 않고 다음 사용자가 무엇을 확인해야 하는지 함께 전달한다. DATA는 표본 제외 조건을 CNS에 알리고, BE는 변경된 응답 형식을 AIAX와 공유하며, CNS는 고객 미확정 사항을 SALES의 확약 문장과 분리한다. 인계 뒤 반복 질의가 줄고 누락을 조기에 발견하면 영향 예측이 자리 잡는 신호로 본다.

이 신호는 모든 후속 업무를 대신 처리한다는 뜻이 아니다. 자신의 변경으로 영향을 받는 상대와 확인 시점을 식별하면 충분하다. 관련 없는 사람을 대량으로 참조하거나 책임 회피를 위해 모든 결정을 상위자에게 넘기는 행동은 구분한다.

### 1년 시점에 나타나는 신호 1 — 후임의 질문을 받게 된다

후임이나 다른 지점 구성원이 특정 업무의 맥락을 묻기 위해 해당 구성원을 찾기 시작한다. 질문을 받는 이유가 직급이나 근속기간이 아니라 실제 경험과 설명 가능성에 있는지 확인한다. 답을 독점하지 않고 원문서, 결정 배경, 예외 조건을 함께 알려 주면 전문성이 팀 안에서 전달되는 상태로 본다.

후임의 질문을 대신 처리해 주는 것만으로는 충분하지 않다. 질문자가 다음에는 스스로 확인할 수 있도록 자료 위치와 판단 순서를 알려 주는지가 중요하다. 같은 질문이 세 차례 이상 반복되면 개인 설명을 계속하기보다 안내 자료나 체크 항목을 보완한다.

### 1년 시점에 나타나는 신호 2 — 반복되는 마찰을 작업 방식의 개선으로 바꾼다

구성원은 개인 간 불편으로 보였던 문제가 요청 정보 누락, 승인 시점 불명확, 지표 정의 차이처럼 반복 구조에서 발생하는지 확인한다. 최근 사례 3건 이상을 근거로 작은 변경안을 제시하고, 2~4주 동안 효과를 측정한다. 변경 전후의 회신 횟수, 재작업 시간, 누락 건수 중 하나를 비교해 유지 여부를 결정한다.

개선안이 곧바로 전사 규칙이 될 필요는 없다. 영향받는 부서와 시험 범위를 합의하고 기존 방식으로 돌아갈 조건을 남기면 충분하다. 시니어는 개선을 주도할 수 있고 주니어는 반복 사례를 발견해 관리자에게 제안하는 방식으로 참여한다.

### 1년 시점에 나타나는 신호 3 — 고객의 표현 뒤에 있는 운영 조건을 먼저 본다

고객이 기능명이나 최신 기술을 지정해 요청하더라도 실제 사용자, 업무 빈도, 실패 시 영향, 운영 담당자를 확인한다. 제안이나 구축 범위가 줄어들 수 있어도 목적과 맞지 않는 작업을 그대로 확약하지 않는다. 고객의 요청을 바꾸는 경우에는 제외한 내용, 선택한 대안, 다시 검토할 조건을 기록한다.

고객과 친밀한 관계를 유지했다는 평가보다 고객이 의사결정에 필요한 정보를 받았는지를 본다. 고객이 처음에는 이견을 보였더라도 영향 설명 후 합의가 이뤄지고 내부 수행 기준과 연결됐다면 신뢰 형성 장면으로 기록한다. 고객 요구를 근거 없이 축소한 경우에는 동일한 행동으로 인정하지 않는다.

### 1년 시점에 나타나는 신호 4 — 자신의 판단 한계와 책임 범위를 설명한다

구성원은 자신이 결정할 수 있는 항목, 승인받아야 하는 항목, 추가 전문가가 필요한 항목을 구분한다. “제 담당이 아닙니다”라고 선을 긋는 대신 다음 책임자와 필요한 입력을 연결한다. 반대로 모든 문제를 떠맡지 않고 권한 없는 확약이나 검증되지 않은 결론을 중단한다.

판단 한계를 말하는 행동은 자신감 부족으로 해석하지 않는다. 불확실성을 구체화하고 확인 경로를 제시하면 책임 있는 행동으로 본다. 1년이 지나도 모든 판단을 상위자에게 넘기는 경우에는 권한 부여 수준과 실패 허용 범위를 먼저 점검한다.

### 가치가 자리 잡지 않을 때 나타나는 신호

| 관찰 신호 | 즉시 개인 문제로 단정하지 않는 이유 | 조직이 먼저 점검할 조건 |
|---|---|---|
| 같은 종류의 질문이 반복된다 | 기준 문서가 여러 위치에 있거나 설명자가 서로 다른 답을 줄 수 있다 | 최신 문서 위치, 용어 일치, 승인된 기준의 표시 여부를 확인한다 |
| 결과물을 마지막 순간에 공유한다 | 중간 공유를 요청했을 때 과도한 지적이나 책임 전가를 경험했을 수 있다 | 리뷰 일정, 초안 허용 여부, 수정 책임의 범위를 확인한다 |
| 도움 요청이 늦다 | 도움을 요청할 대상과 기준이 정해지지 않았을 수 있다 | 막힘 기준, 담당자 가용 시간, 긴급 연락 경로를 확인한다 |
| 고객 요구를 그대로 전달한다 | 범위를 조정할 권한이나 내부 검토 시간이 없을 수 있다 | 확약 권한, 기술 검토 기한, 고객 회신 전 승인 절차를 확인한다 |
| 타 부서 요청을 소극적으로 처리한다 | 요청의 우선순위와 본래 업무의 충돌을 조정할 관리자가 없을 수 있다 | 부서 간 우선순위 결정자와 일정 변경 권한을 확인한다 |
| 실수를 축소하거나 늦게 알린다 | 과거 보고 이후 공개 비난이나 불이익을 경험했을 수 있다 | 오류 보고 반응, 영향 확인 절차, 재발 방지 지원 방식을 확인한다 |
| 피드백 반영이 매번 다르다 | 리뷰어별 요구가 충돌하거나 최종 결정자가 불명확할 수 있다 | 승인자, 필수 기준, 선택 가능한 표현 범위를 확인한다 |
| 개선 제안이 나오지 않는다 | 제안이 검토되지 않거나 제안자가 실행 책임까지 모두 떠안을 수 있다 | 제안 검토 기한, 시험 범위, 지원 인력, 종료 조건을 확인한다 |

조직 조건을 점검한 뒤에도 같은 행동이 반복되면 관리자는 최근 4주 안의 구체적 장면 2~3개를 선택해 성장 대화를 진행한다. “주도성이 부족하다”처럼 가치명만 말하지 않고 요청 시점, 실제 행동, 발생한 영향, 다음에 사용할 기준을 제시한다. 개선 행동은 한 번에 두 개 이하로 정하고 확인일을 영업일 기준 10~20일 뒤로 잡는다.

### 이 문서를 성장 대화에 사용하는 방법

1. 대화 2영업일 전 구성원과 관리자가 각각 이 문서에서 현재 업무와 가까운 장면 1개를 선택한다.
2. 구성원은 선택한 장면과 비슷했던 실제 사례를 상황·행동·영향 순서로 10줄 이내에서 작성한다.
3. 관리자는 가치명에 대한 인상 대신 메시지, 문서, 회의 기록에서 확인한 행동을 준비한다.
4. 30분 대화 중 앞의 10분은 사실 확인, 다음 10분은 서로 다른 해석 확인, 마지막 10분은 후속 행동 합의에 사용한다.
5. 후속 행동은 “협업을 잘한다”가 아니라 “타 팀 요청을 받으면 사용 목적과 결정 기한을 확인한다”처럼 다음 장면에서 관찰할 수 있게 정한다.
6. 조직이 제공할 지원에는 권한 부여, 리뷰 시간, 담당자 연결, 표본 제공, 업무 우선순위 조정 중 최소 하나를 포함한다.
7. 확인일에는 결과의 성공 여부뿐 아니라 합의한 행동을 시도했는지, 예상하지 못한 제약이 무엇이었는지를 검토한다.
8. 동일 장면이 두 차례 안정적으로 관찰되면 해당 행동을 유지 과제로 남기지 않고 다음 난도의 장면을 선택한다.

이 문서는 모든 구성원을 같은 사례에 맞추는 체크리스트로 사용하지 않는다. 부서, 직급, 고객 접점, 배정 과제에 따라 관찰 가능한 장면이 달라질 수 있으므로 근거가 없는 항목은 공란으로 남긴다. 성장 대화 기록은 인사평가 문구를 미리 확정하는 데 사용하지 않고 실제 행동의 변화와 필요한 업무 조건을 추적하는 데 사용한다.
