# 릴리즈 노트 작성 및 내부 공유 규칙
<!--meta: doc=PSY-04; doc_type=release_rule; tier=1; topic=PROCESS; disclosure=internal; status=active-->

## 범위와 두 종류의 노트
<!--meta: sec=s1; dept=AIAX|BE|DATA|DEVOPS; level=주니어|시니어; ct_band=하; related=none-->
릴리즈 노트는 배포로 발생하는 변화를 독자별로 전달하는 기록이다. 하나의 배포에 대해 고객 전달용과 내부 공유용을 각각 작성하며, 동일한 변경이라도 공개 범위와 사용 목적에 맞게 내용을 분리한다.

| 구분 | 고객 전달용 | 내부 공유용 |
|---|---|---|
| 주요 독자 | 고객사 운영자, 관리자, 사용자 | AIAX·BE·DATA 및 배포 지원 인력 |
| 목적 | 사용 결과, 영향, 필요한 조치를 안내 | 구현 맥락, 운영 영향, 대응 정보를 인계 |
| 표현 기준 | 고객이 확인할 수 있는 동작과 조치 중심 | 기술 구성요소와 내부 추적 정보 포함 |
| 포함 범위 | 주요 변경, 호환성 영향, 업그레이드 안내 | 고객용 항목과 내부 진단·운영 항목 |
| 공개 수준 | 계약 및 보안 범위에서 전달 가능한 정보 | 사내 접근 권한이 있는 인원에게만 공유 |
| 분리 이유 | 내부 식별자나 취약 정보의 외부 노출 방지 | 장애 대응과 후속 개발에 필요한 정보 보존 |

두 노트는 원본 하나를 그대로 복사해 배포하지 않는다. 고객 전달용에서 제외한 기술 정보는 내부 공유용에 남겨 추적 가능하게 한다.

적용 대상은 다음과 같다.

1. 고객이 인수하거나 운영하는 시스템에 반영되는 애플리케이션, API, 모델, 데이터 처리 구성이다.
2. 둘 이상의 팀 또는 프로젝트가 사용하는 사내 공통 모듈이다.
3. 업무 수행자가 공동으로 사용하는 내부 운영 도구이다.
4. 기존 배포물을 교체하거나 설정·데이터·동작을 변경하는 배포 패키지이다.

| 작업 상태 | 작성 의무 | 판정 기준 |
|---|---:|---|
| 고객 환경 배포 | 의무 | 고객 운영 또는 사용 결과에 반영됨 |
| 다른 팀 사용 환경 배포 | 의무 | 배포팀 밖의 사용자가 존재함 |
| 사내 공통 모듈 배포 | 의무 | 다른 저장소나 서비스가 참조함 |
| 내부 운영 도구 배포 | 의무 | 공동 업무 절차에 영향을 줌 |
| 실험 브랜치 실행 | 제외 | 공유 환경에 병합·배포되지 않음 |
| 개인 로컬 작업 | 제외 | 타인의 실행 결과에 영향을 주지 않음 |

작성 의무는 변경 규모가 아니라 배포 도달 범위로 판단한다. 코드 수정이 작더라도 고객 환경이나 다른 팀이 사용하는 환경에 들어가면 작성한다.

실험 브랜치가 공용 검증 환경에 배포되어 다른 팀의 시험 기준으로 사용되면 제외 대상이 아니며 내부 공유용 노트를 작성한다. 개인 작업이 공통 모듈에 병합되는 시점에도 동일한 기준을 적용한다.

이 문서는 변경 승인 절차를 정하지 않으며 해당 절차는 PSY-02#s8 참조로 처리한다. 고객 요청의 수용·보류·거절 판정은 PSY-03 참조로 처리한다. 재사용 자산 자체의 버전 및 지원 정책은 PSY-05#s8 참조로 처리한다.

## 버전 체계와 증가 규칙
<!--meta: sec=s2; dept=BE|AIAX|DEVOPS; level=주니어|시니어; ct_band=중; related=s1|s3-->
정식 배포 버전은 유의적 버전 형식인 `MAJOR.MINOR.PATCH`를 사용한다. 각 자리는 음이 아닌 정수로 표기하며 앞자리가 증가하면 뒤의 자리는 0으로 초기화한다.

- `MAJOR`는 기존 사용 방식과 호환되지 않는 변경에 올린다.
- `MINOR`는 하위 호환성을 유지하는 신규 기능에 올린다.
- `PATCH`는 공개된 동작 계약을 유지하는 버그 수정에 올린다.

예를 들어 `2.4.7`에서 호환성 파괴 변경은 `3.0.0`, 하위 호환 신규 기능은 `2.5.0`, 버그 수정은 `2.4.8`로 정한다.

| 변경 사례 | 증가 자리 | 판정 조건 |
|---|---|---|
| 기존 인터페이스 제거·변경 | MAJOR | 기존 호출 또는 연동이 실패함 |
| 선택형 인터페이스 추가 | MINOR | 기존 호출을 수정하지 않아도 됨 |
| 설정 기본값 변경 | MAJOR | 설정을 생략한 기존 환경의 동작이 달라짐 |
| 선택형 설정 추가 | MINOR | 미설정 시 기존 동작이 유지됨 |
| 응답 형식의 필드 삭제·자료형 변경 | MAJOR | 기존 파서나 후속 처리가 깨질 수 있음 |
| 선택형 응답 필드 추가 | MINOR | 기존 소비자가 추가 필드를 무시할 수 있음 |
| 성능만 개선 | PATCH | 입력·출력·오류 조건이 유지됨 |
| 내부 리팩터링 | PATCH | 외부 관찰 동작과 운영 절차가 동일함 |
| 기존 명세에 맞춘 오류 수정 | PATCH | 문서화된 계약으로 복원함 |
| 새 기능 또는 새 API 추가 | MINOR | 기존 기능에 변경을 요구하지 않음 |
| 모델·프롬프트 교체 | MAJOR | 고객 또는 연동 시스템이 받는 출력이 달라짐 |
| 모델 구현만 교체 | PATCH | 동일 시험 기준에서 외부 출력 계약이 유지됨 |

모델이나 프롬프트의 교체로 분류, 생성 결과, 점수 의미, 임계값 판정 또는 응답 구조가 바뀌면 호환성 파괴로 본다. 호출 규격이 같다는 사유만으로 `PATCH`를 적용하지 않는다. 출력 변화가 없다고 판정하려면 배포 대상의 기존 수용 기준을 동일하게 통과한 근거가 있어야 한다.

한 배포에 여러 변경이 포함되면 가장 높은 증가 자리를 적용한다. `PATCH` 수정과 호환성 파괴 변경이 함께 있으면 `MAJOR`를 올린다.

사전 배포본은 정식 버전 뒤에 하이픈과 식별자를 붙인다.

| 단계 | 표기 예 | 용도 |
|---|---|---|
| 알파 검증 | `3.0.0-alpha.1` | 구현팀 내부 검증 |
| 베타 검증 | `3.0.0-beta.1` | 제한된 통합 검증 |
| 릴리즈 후보 | `3.0.0-rc.1` | 정식 배포 전 최종 검증 |

릴리즈 후보에서 수정이 발생하면 `rc` 번호를 올린다. 정식 배포가 확정되면 사전 배포 식별자를 제거하고 해당 정식 버전을 사용한다.

버전과 배포 식별자는 서로 다른 값을 관리한다. 버전은 사용자가 인식하는 변경 계약이고, 빌드 번호는 같은 소스 버전으로 생성된 개별 산출물을 식별하는 값이다. 재빌드만 수행한 경우 버전을 올리지 않고 빌드 번호를 변경한다.

고객 계약 문서에 특정 버전이 기재된 경우 배포 기록에 계약 기재 버전, 실제 유의적 버전, 빌드 번호를 함께 연결한다. 계약상 버전 명칭과 사내 버전 형식이 다르면 임의로 치환하지 않고 대응표를 유지한다.

| 계약 기재 항목 | 내부 기록 항목 |
|---|---|
| 계약상 버전 또는 납품 차수 | 변경하지 않은 원문 값 |
| 정식 배포 버전 | `MAJOR.MINOR.PATCH` |
| 배포 산출물 | 빌드 번호 또는 패키지 식별자 |
| 대응 근거 | 검수본, 배포 기록 또는 승인 내역 위치 |

## 호환성 파괴 변경의 정의와 표기
<!--meta: sec=s3; dept=BE|AIAX|DEVOPS; level=시니어; ct_band=상; related=s2-->
호환성 파괴 변경은 기존 사용자가 코드, 설정, 데이터, 인증 또는 운영 절차를 수정하지 않으면 이전과 같은 결과를 얻을 수 없는 변경이다. 실제 장애가 발생했는지가 아니라 기존 사용 방식이 그대로 유지되는지를 기준으로 판정한다.

다음 중 하나에 해당하면 호환성 파괴 후보로 등록한다.

1. 기존 API, 명령, 이벤트, 설정 또는 기능을 제거한다.
2. 설정 키, 필드, 명령 또는 엔드포인트의 이름을 바꾼다.
3. 생략 가능한 설정의 기본값을 변경한다.
4. 허용하던 입력값, 길이, 자료형 또는 형식을 더 좁게 제한한다.
5. 이전에 정상 처리하던 조건을 오류로 반환하도록 바꾼다.
6. 응답 필드를 삭제하거나 필드의 자료형·의미를 변경한다.
7. 인증 방식, 토큰 형식, 권한 범위 또는 자격 증명 전달 위치를 변경한다.
8. 데이터 저장 형식 변경으로 기존 데이터의 변환이 필요해진다.
9. 호출 순서나 필수 선행 절차를 추가한다.
10. 모델 출력의 의미, 구조 또는 판정 기준이 기존 소비 방식과 달라진다.

| 변경 유형 | 파괴 판정 예 | 파괴가 아닌 예 |
|---|---|---|
| 항목 제거 | 기존 옵션을 더 이상 인식하지 않음 | 사용 중단 예정 표시만 추가함 |
| 이름 변경 | 이전 설정 키를 거부함 | 이전 이름을 별칭으로 계속 지원함 |
| 기본값 변경 | 미설정 환경의 결과가 달라짐 | 명시 설정 환경의 동작만 수정함 |
| 입력 제한 | 허용 길이를 100자에서 50자로 축소함 | 허용 길이를 100자에서 200자로 확대함 |
| 오류 조건 | 기존 성공 입력에 오류를 반환함 | 오류 메시지의 설명만 보완함 |
| 응답 변경 | 기존 필드를 삭제함 | 선택형 필드를 새로 추가함 |
| 인증 변경 | 기존 인증 헤더를 사용할 수 없음 | 기존 방식과 새 방식을 병행 지원함 |

릴리즈 노트의 호환성 파괴 변경은 한 줄에 하나씩 적는다. 여러 수정 사항을 한 문장에 묶거나 “일부 사양 변경”처럼 포괄적으로 표현하지 않는다.

각 줄은 변경된 대상과 수정의 형태가 드러나게 작성한다.

- `[설정 이름 변경] retry_count를 max_retry로 변경한다.`
- `[옵션 제거] legacy_mode 옵션을 제거한다.`
- `[기본값 변경] request_timeout 기본값을 30초에서 10초로 변경한다.`
- `[응답 필드 삭제] result.detail 필드를 삭제한다.`
- `[인증 방식 변경] 쿼리 문자열의 토큰 전달을 중단하고 인증 헤더만 허용한다.`

파괴적 변경을 포함한 커밋은 Conventional Commits 방식으로 명시한다. 커밋 타입 뒤에 느낌표를 붙이거나 본문 꼬리말에 `BREAKING CHANGE:`를 사용한다.

| 표기 방식 | 예시 | 적용 상황 |
|---|---|---|
| 타입 뒤 느낌표 | `feat!: 인증 헤더 형식 변경` | 제목만으로 파괴 여부를 드러낼 때 |
| 범위 뒤 느낌표 | `fix(api)!: 응답 필드 자료형 변경` | 영향 구성요소를 함께 표시할 때 |
| 본문 꼬리말 | `BREAKING CHANGE: legacy_mode 옵션 제거` | 변경 내용과 전환 설명이 필요할 때 |

파괴적 변경 커밋에 일반 `feat` 또는 `fix`만 사용해서는 안 된다. 병합 검토자는 커밋 표기와 실제 변경의 파괴 여부가 일치하는지 확인한다.

릴리즈 노트의 각 파괴 항목에는 다음 세 정보를 연결한다.

1. 기존 사용자가 수행할 마이그레이션 경로가 있는지 적는다.
2. 이전 버전과 병행 사용 가능한 범위와 불가능한 범위를 설명한다.
3. 영향을 받는 서비스, 연동 시스템, 설정 보유자 또는 사용자 집단을 특정한다.

| 점검 질문 | 통과 기준 |
|---|---|
| 마이그레이션 경로가 있는가 | 대체 설정, 변환 절차 또는 수정 방법이 제시됨 |
| 호환성 설명이 있는가 | 이전 방식의 유지 여부와 종료 지점이 명시됨 |
| 영향받는 대상이 적혀 있는가 | 구성요소 또는 사용자 범위가 식별됨 |

호환성 파괴 변경을 `PATCH` 버전으로 내보내는 행위는 금지한다. 버그 수정 목적이더라도 기존에 공개된 사용 방식이 깨지면 `MAJOR`로 판정한다.

보안상 즉시 적용하지 않으면 피해 가능성이 커지는 긴급 수정은 사전 고지나 병행 지원 기간을 단축할 수 있다. 이 예외는 버전 증가 원칙을 면제하지 않으며, 파괴적 변경이면 긴급 배포도 `MAJOR`를 적용한다. 공개할 수 없는 취약점 세부 정보는 노트에서 제한하되 영향 대상, 필수 조치, 적용 기한은 식별 가능하게 남긴다.

## 릴리즈 노트 표준 구성
<!--meta: sec=s4; dept=AIAX|BE|DEVOPS; level=주니어|시니어; ct_band=중; related=s3-->
릴리즈 노트는 아래 여덟 개 절을 정해진 순서로 작성한다.  
작성자는 절을 합치거나 제목을 임의로 바꾸지 않는다.

| 순서 | 절 | 필수 기재 내용 | 분량 기준 |
|---:|---|---|---|
| 1 | 결과 헤드라인 | 배포 후 사용자가 얻는 결과 또는 필요한 조치 | 한 문장, 30자 내외 |
| 2 | 주요 변경 | 새 기능, 개선, 수정으로 달라지는 핵심 결과 | 최대 5개 항목 |
| 3 | 호환성 파괴 변경과 마이그레이션 | 변경점별 영향과 대응 절차의 연결 | 변경점당 한 항목 |
| 4 | 업그레이드 노트 | 명령, 플래그, 설정 변경, 데이터 마이그레이션 | 실행 단위별 한 항목 |
| 5 | 영향받는 대상 | 영향받는 사용자, 기능, 인터페이스 또는 실행 환경 | 최대 5개 항목 |
| 6 | 알려진 제한 | 배포 시점에 확인된 제약과 적용 조건 | 제한당 한 항목 |
| 7 | 되돌리기 방법 | 복구 시작 조건, 수행 방법, 확인 지점 | 한 절, 최대 7단계 |
| 8 | 관련 요청 ID | 변경 근거를 추적할 수 있는 요청 식별자 | 쉼표 없는 목록 |

결과 헤드라인은 기능명만 나열하지 않고 배포로 완성된 상태를 말한다.  
주요 변경에는 독자가 먼저 확인해야 할 내용을 영향이 큰 순서로 배치한다.  
단순 수정 내역을 모두 옮기지 않으며 같은 결과를 만드는 변경은 하나로 묶는다.

호환성 파괴 여부는 `PSY-04#s3 참조`로 판정한다.  
해당 절에서는 판정 근거를 재설명하지 않고 변경, 영향, 마이그레이션 항목을 서로 대응시킨다.  
상세 실행 절차는 `PSY-04#s6 참조`에 따라 작성한다.

업그레이드 노트에는 실제 적용자가 입력하거나 변경해야 하는 값만 둔다.  
명령과 설정 예시는 설명 문장과 분리해 복사 범위를 식별할 수 있게 한다.  
영향받는 대상은 “전체”처럼 넓게 쓰지 않고 식별 가능한 기능 또는 사용자 범위로 한정한다.

알려진 제한에는 우회 방법이 확인된 경우에만 그 방법을 함께 적는다.  
확인되지 않은 해결 시점이나 개선 예고는 넣지 않는다.  
되돌리기 방법이 없으면 그 사실과 되돌릴 수 없는 지점을 명시한다.

관련 요청 ID는 본문 문장에 삽입하지 않고 마지막 절에 모은다.  
하나의 변경에 여러 요청이 연결되면 중복을 제거하되 원래 식별자는 바꾸지 않는다.

절의 순서는 결과 확인, 영향 판단, 적용, 복구, 추적의 읽기 흐름을 유지하기 위해 고정한다.  
순서가 같아야 배포 검토자가 누락 항목을 동일한 위치에서 확인할 수 있다.  
분량 기준을 넘는 세부 설명은 별도 운영 문서로 분리하고 해당 링크만 남긴다.

변경 내용이 없는 절도 삭제하지 않는다.  
내용 칸에 `해당 없음`을 적으며 공란, 하이픈, 제목 생략으로 대신하지 않는다.

| 결과 헤드라인 | 주요 변경 | 호환성 파괴 변경과 마이그레이션 | 업그레이드 노트 | 영향받는 대상 | 알려진 제한 | 되돌리기 방법 | 관련 요청 ID |
|---|---|---|---|---|---|---|---|
| [사용 결과 한 문장] | [항목 목록 또는 해당 없음] | [변경·영향·절차 또는 해당 없음] | [명령·플래그·설정·데이터 작업 또는 해당 없음] | [대상 목록 또는 해당 없음] | [제한 목록 또는 해당 없음] | [복구 단계 또는 불가 지점] | [ID 목록 또는 해당 없음] |

## 항목 문장 작성 규칙
<!--meta: sec=s5; dept=AIAX|BE|DATA|DEVOPS; level=주니어|시니어; ct_band=중; related=s4-->
각 항목은 구현 행위가 아니라 배포 후 사용자에게 달라지는 결과를 중심으로 작성한다.  
“무엇을 개발했다”보다 “누가 무엇을 새로 할 수 있는가” 또는 “기존 동작이 어떻게 달라지는가”를 먼저 쓴다.

| 구분 | 나쁜 예 | 좋은 예 |
|---|---|---|
| 기능 추가 | 조회 API를 신규 개발했다 | 사용자는 조회 화면에서 기간별 결과를 확인할 수 있다 |
| 성능 변경 | 캐시 계층을 최적화했다 | 관리자는 동일 조건의 반복 조회 결과를 더 빨리 확인할 수 있다 |
| 오류 수정 | 예외 처리 로직을 수정했다 | 사용자가 빈 값을 입력해도 화면이 종료되지 않고 입력 안내가 표시된다 |
| 설정 변경 | 내부 설정 구조를 리팩터링했다 | 운영자는 설정 파일에서 기능별 사용 여부를 각각 지정할 수 있다 |
| 데이터 변경 | 변환 배치를 추가했다 | 기존 데이터의 날짜 값이 새 형식으로 자동 변환된다 |
| 권한 변경 | 인증 모듈을 변경했다 | 읽기 권한만 있는 사용자는 수정 기능을 실행할 수 없다 |
| 추적 정보 혼입 | 요청 ID-184에 따라 검색을 개선했다 | 사용자는 여러 검색 조건을 동시에 적용할 수 있다 |
| 불확정 예고 | 향후 검색 속도를 추가 개선할 예정이다 | 해당 문장을 삭제한다 |

한 항목에는 하나의 사용자 결과만 쓴다.  
서로 다른 기능이나 조치가 포함되면 문장을 분리한다.  
원인과 결과가 반드시 함께 필요할 때만 한 문장 안에서 연결한다.

문장의 주어는 사용자, 운영자, 관리자 또는 기능으로 둔다.  
“개발팀”, “서버”, “모듈”처럼 내부 구현 주체를 앞세우지 않는다.  
사용자 구분이 필요하지 않으면 기능을 주어로 삼아 동작을 직접 설명한다.

내부 클래스명, 함수명, 테이블명, 브랜치명 및 배포 파이프라인 단계명은 고객이 조치에 사용하지 않는 한 쓰지 않는다.  
불가피한 명령, 설정 키 및 인터페이스 이름은 원문 표기를 유지하고 기능 설명을 덧붙인다.  
약어는 처음 나올 때 풀어 쓰되 제품 또는 인터페이스의 고유 표기는 바꾸지 않는다.

티켓 번호와 관련 요청 ID는 문장 중간이나 제목에 넣지 않는다.  
식별자는 `PSY-04#s4`의 관련 요청 ID 칸에만 기록한다.  
식별자만 있고 사용자 결과가 없는 항목은 작성 완료로 보지 않는다.

수치가 포함된 문장은 측정 조건을 함께 제시할 수 있을 때만 사용한다.  
측정 조건에는 비교 기준, 측정 환경 또는 대상 범위, 측정 시점이 포함되어야 한다.  
수치 기재의 세부 원칙은 `PRP-01#s7 참조`로 처리한다.  
측정되지 않은 “대폭”, “획기적”, “최적”, “완벽” 등의 표현은 사용하지 않는다.

추측, 계획, 기대 효과를 완료된 변경처럼 쓰지 않는다.  
`향후 개선 예정`, `추가 지원 예정`, `성능이 좋아질 것으로 예상`과 같은 문장은 삭제한다.  
배포 시점에 확인되지 않은 일정은 릴리즈 노트에 포함하지 않는다.

번역본이 필요하면 한국어 원문을 먼저 확정한 뒤 번역한다.  
번역자는 기능명, 설정 키, 권한명 및 화면 용어를 기존 고객 문서와 대조한다.  
동일한 개념에는 문서 전체에서 하나의 번역어를 사용한다.  
직역으로 의미가 달라지는 경우 원문 용어를 괄호에 병기하며 임의의 새 명칭을 만들지 않는다.

## 업그레이드·마이그레이션 안내 작성
<!--meta: sec=s6; dept=BE|AIAX|DATA|DEVOPS; level=시니어; ct_band=상; related=s3|s4-->
업그레이드·마이그레이션 안내는 적용자가 문서만 보고 사전 확인, 실행, 검증, 복구를 완료할 수 있도록 작성한다.  
아래 순서를 바꾸거나 실행에 필요한 단계를 생략하지 않는다.

| 순서 | 필수 요소 | 기재 기준 |
|---:|---|---|
| 1 | 적용 전 확인 | 현재 버전, 목표 버전, 필요한 권한과 전제 조건 |
| 2 | 중단 여부 | 서비스 중단 필요 여부와 예상 중단 시간 |
| 3 | 백업 대상 | 데이터, 설정, 파일 등 복구에 필요한 대상과 확인 방법 |
| 4 | 실행 순서 | 명령, 플래그, 설정 변경, 데이터 변환을 시간순으로 제시 |
| 5 | 검증 방법 | 성공 판정에 사용할 조회, 응답, 로그 또는 기능 결과 |
| 6 | 실패 시 되돌리기 | 실패 판정 조건, 복구 순서, 복구 후 확인 방법 |
| 7 | 비가역 지점 | 실행 후 이전 상태로 되돌릴 수 없는 단계와 진입 조건 |

적용 전 확인에는 지원하는 시작 버전을 명시한다.  
현재 버전을 확인하는 방법과 목표 버전을 혼동하지 않도록 각각 별도 항목으로 쓴다.  
전제 조건에는 선행 배포, 필수 권한, 저장 공간, 외부 연동 상태 중 실제 필요한 항목만 적는다.

중단이 필요하지 않으면 `중단 없음`이라고 명시한다.  
중단이 필요하면 시작 조건, 예상 중단 시간 및 재개 확인 방법을 함께 적는다.  
예상 시간은 측정 또는 리허설 근거가 없으면 확정값으로 표현하지 않는다.

백업 단계에는 백업 대상과 완료 확인 기준을 함께 둔다.  
“백업 수행”만 적지 않고 복구에 사용할 파일 또는 데이터의 범위를 식별한다.  
백업 유효성을 확인하지 못한 상태에서는 비가역 단계로 진행하지 않는다.

실행 순서는 한 단계에 하나의 명령 또는 하나의 설정 변경만 배치한다.  
명령에는 실행 위치, 필요한 권한, 인자와 성공 시 확인할 결과를 적는다.  
플래그는 기본값과 이번 적용값을 구분한다.  
설정 변경은 이전 값과 변경 후 값을 함께 제시한다.

데이터 변환이 포함되면 다음 항목을 추가한다.

1. 대상 데이터의 범위와 예상 변환 소요 시간을 적는다.
2. 변환 중 읽기, 쓰기 및 조회 기능이 어떻게 동작하는지 적는다.
3. 중단 후 같은 작업을 재실행할 수 있는지 명시한다.
4. 재실행할 수 있다면 중복 처리 방지 조건과 시작 지점을 적는다.
5. 재실행할 수 없다면 복구 후 처음부터 수행해야 하는 범위를 적는다.

검증 방법은 “정상 여부 확인”처럼 판단을 남기지 않는다.  
확인할 기능, 입력 조건, 기대 결과 및 실패로 판정할 결과를 구분한다.  
여러 구성요소를 적용했다면 구성요소별 검증이 끝난 뒤 전체 동작을 확인한다.

되돌리기 절차는 적용 순서의 단순 역순으로 가정하지 않는다.  
복구 명령, 설정 복원, 데이터 복원 및 서비스 재개 순서를 실제 수행 기준으로 작성한다.  
되돌릴 수 없는 지점이 있으면 해당 단계 직전에 경고를 두고 승인 또는 백업 확인 조건을 기재한다.

작성자는 배포 전에 안내문만 사용해 전 과정을 한 번 직접 실행한다.  
실행 중 추가로 필요했던 명령, 권한 또는 판단 기준은 안내문에 반영한다.  
검증을 완료하지 않은 안내문으로는 배포를 진행하지 않는다.

고객 환경의 시작 버전이 서로 다르면 단일 경로로 통합해 표현하지 않는다.  
시작 버전별 필수 경유 버전과 적용 순서를 아래 형식으로 구분한다.

| 현재 버전 범위 | 필수 경유 버전 | 목표 버전 | 적용 경로 | 직접 업그레이드 가능 여부 |
|---|---|---|---|---|
| [시작 버전] | [경유 버전 또는 해당 없음] | [목표 버전] | [시작 → 경유 → 목표] | [가능/불가] |

표에 없는 시작 버전은 임의로 적용하지 않으며 작성자가 경로를 추가 검증한 뒤 안내를 갱신한다.

## 분류 라벨 체계
<!--meta: sec=s7; dept=AIAX|BE|DEVOPS; level=주니어; ct_band=하; related=s4-->
모든 변경 항목은 아래 라벨 중 하나 이상을 문장 맨 앞에 붙인다. 라벨을 판정하지 못한 항목은 릴리즈 노트에 올리지 않고 작성자에게 돌려보낸다.

| 라벨 | 판정 기준 | 고객용 노출 |
|---|---|---|
| 추가 | 이전 버전에 없던 기능·API·화면·옵션을 제공한다 | 노출한다 |
| 변경 | 기존 동작, 입력·출력, 사용 절차 또는 운영 방식이 달라진다 | 노출한다 |
| 수정 | 의도와 다르게 작동하던 동작을 원래 기준에 맞게 바로잡는다 | 노출한다 |
| 제거 | 기존 기능·옵션·인터페이스를 더 이상 제공하지 않는다 | 노출한다 |
| 보안 | 취약 가능성, 접근 통제, 인증·인가 또는 정보 노출 위험을 보완한다 | 공개 수위를 검토한 후 노출한다 |
| 성능 | 동일한 기능 결과를 유지하면서 처리 시간이나 자원 사용량을 개선한다 | 측정 근거가 있을 때 노출한다 |
| 호환성 파괴 | 기존 사용자가 코드·설정·데이터·운영 절차를 바꿔야 한다 | 반드시 노출한다 |
| 비활성화 예고 | 현재 사용할 수 있으나 향후 중단·제거할 대상을 알린다 | 반드시 노출한다 |

판정은 변경의 개발 목적이 아니라 배포 후 나타나는 결과를 기준으로 한다.

1. 성능 작업이 응답 형식, 정렬 순서, 제한값 또는 기본 동작을 바꾸면 `성능`이 아니라 `변경`으로 분류한다.
2. 오류 수정 과정에서 기존 사용 방식이 유지되지 않으면 `수정`과 `호환성 파괴`를 함께 붙인다.
3. 보안 보완으로 인증 절차나 권한 설정을 바꿔야 하면 `보안`과 `변경`을 함께 붙인다.
4. 즉시 제거되는 항목은 `제거`, 다음 버전 이후 제거될 항목은 `비활성화 예고`로 구분한다.
5. 신규 기능이 기존 인터페이스를 깨뜨리면 `추가`와 `호환성 파괴`를 함께 붙인다.

라벨은 각 항목의 첫 위치에 대괄호로 표기한다. 복수 라벨은 `호환성 파괴`, `보안`, `제거`, `비활성화 예고`, `변경`, `추가`, `수정`, `성능` 순으로 정렬한다.

- 표기 예: `[호환성 파괴][변경] 기본 인증 방식을 변경한다`
- 항목 정렬도 같은 우선순위를 적용하며, 동일 라벨 안에서는 사용자 영향이 큰 항목을 먼저 둔다.
- 고객용 노출 여부가 조건부인 항목은 PSY-04#s8 기준을 적용한다.

| 커밋 규약 타입·표시 | 대응 라벨 | 처리 기준 |
|---|---|---|
| `feat` | 추가 | 기존 동작 변경이 있으면 `변경`을 병기한다 |
| `fix` | 수정 | 보안 관련 수정이면 `보안`을 우선한다 |
| `perf` | 성능 | 동작 변화가 확인되면 `변경`으로 재분류한다 |
| `refactor` | 변경 | 외부 동작이나 운영 절차가 달라질 때만 노트에 올린다 |
| `revert` | 수정 또는 제거 | 되돌린 결과를 기준으로 판정한다 |
| 타입 뒤 `!` 또는 `BREAKING CHANGE` | 호환성 파괴 | 원래 타입의 라벨과 함께 표기한다 |
| `docs`, `test`, `build`, `ci`, `chore` | 직접 대응 없음 | 사용자·운영 영향이 있을 때만 별도 라벨을 판정한다 |

커밋 타입만으로 라벨을 확정하지 않는다. 배포 결과를 확인한 뒤 노트 작성자가 최종 라벨을 지정한다.

## 고객용 노트 금지 사항
<!--meta: sec=s8; dept=AIAX|BE|CNS|DEVOPS; level=시니어; ct_band=상; related=s4|s5-->
고객 전달용 노트에는 고객이 변경 영향을 판단하고 필요한 조치를 수행하는 데 필요한 정보만 남긴다. 내부 추적 정보, 제3자 식별 정보 또는 악용 가능한 세부 정보는 외부 전달 전에 제거한다.

| 금지 정보 | 제거 기준 | 허용되는 대체 표현 |
|---|---|---|
| 내부 티켓·브랜치·커밋 식별자 | 번호, 링크, 해시를 모두 삭제한다 | 변경 결과를 서술한다 |
| 담당자 이름 | 작성자·개발자·검토자 실명을 삭제한다 | 담당 부서 또는 고객 문의 창구를 적는다 |
| 다른 고객사 관련 변경 | 고객 식별자, 계약 맥락, 사용 사례를 삭제한다 | 공통 기능에 미치는 결과만 적는다 |
| 사내 모듈 구조·파일 경로 | 패키지명, 저장소 경로, 서버 내부 경로를 삭제한다 | 기능 영역 또는 설정 항목으로 표현한다 |
| 확정되지 않은 장애 원인 | 추정·가설·미검증 원인을 삭제한다 | 확인된 현상과 수정 결과만 적는다 |
| 보안 취약점 상세 재현 정보 | 공격 순서, 악용 조건, 요청값, 우회 절차를 삭제한다 | 수정 사실과 영향 범위를 적는다 |
| 측정 조건을 밝힐 수 없는 성능 수치 | 비교 환경·표본·측정 방식이 없는 수치를 삭제한다 | 정성 표현을 쓰거나 항목을 보류한다 |
| 경쟁 제품 언급 | 제품명과 우열 비교를 삭제한다 | 자사 배포 결과만 설명한다 |

보안 수정은 사실 자체를 숨기지 않되 공개 범위를 제한한다.

1. 수정된 기능 영역과 영향받을 수 있는 버전 범위를 알린다.
2. 고객이 수행해야 하는 업데이트·설정 확인 조치를 알린다.
3. 공격 재현 절차, 취약 지점의 상세 구조, 우회 가능 조건은 적지 않는다.
4. 공개 수준에 이견이 있으면 외부 배포를 보류하고 AIAX 또는 BE 배포 책임자의 확인을 받는다.
5. 공개 범위에 법률·계약상 판단이 필요한 경우 사안별 확인이 필요하다.

사고와 관련된 변경은 책임 추정이나 감정적 표현 없이 확인된 사실로 작성한다.

- “담당자의 실수로 장애가 발생했다”처럼 개인에게 원인을 귀속하지 않는다.
- “완전히 해결했다”, “재발 가능성이 없다”처럼 검증 범위를 넘는 단정을 쓰지 않는다.
- 발생 현상, 영향 범위, 이번 배포로 달라진 사항, 고객 조치만 기재한다.
- 원인 분석, 시간대별 대응, 조직별 판단, 후속 개선 과제는 장애 회고 문서에서 다룬다.
- 릴리즈 노트는 장애 회고 문서를 대신하지 않으며 회고 문서의 내부 링크도 고객용 노트에 넣지 않는다.

외부 전달 전에는 AIAX 또는 BE의 배포 책임자가 기술 정보와 보안 공개 수위를 확인하고, CNS의 고객 커뮤니케이션 담당자가 고객 식별 정보·표현·계약상 공개 범위를 확인한다. 두 확인 중 하나라도 완료되지 않으면 고객에게 전송하지 않는다.

## 내부용 노트 추가 항목
<!--meta: sec=s9; dept=AIAX|BE|DATA|DEVOPS; level=시니어; ct_band=상; related=s4-->
내부용 노트에는 고객 전달용 정보에 더해 배포 실행, 관측, 복구 및 후속 추적에 필요한 항목을 기록한다. 아래 항목은 해당 사항이 없을 때도 삭제하지 않고 `해당 없음`과 판단 근거를 남긴다.

| 추가 항목 | 필수 기재 내용 | 완료 판정 |
|---|---|---|
| 포함된 요청·부채 ID | 반영된 요청 번호와 기술 부채 등록 번호 | 원본 기록을 검색할 수 있다 |
| 변경 범위 | 영향받는 모듈·서비스·데이터 처리 영역 | 배포 대상을 구분할 수 있다 |
| 대상 환경과 순서 | 적용 환경과 환경별 실행 순서 | 선행·후행 관계가 드러난다 |
| 롤백 절차 | 실행 명령, 설정 복원, 데이터 처리, 검증 방법 | 담당자가 별도 설명 없이 수행할 수 있다 |
| 롤백 가능 시간 창 | 롤백 시작이 가능한 최종 시점과 제한 사유 | 데이터·스키마 제약이 명시된다 |
| 관측 지표와 임계값 | 지표명, 정상 범위, 경고·중단 기준 | 수치 또는 명시적 상태값이 있다 |
| 모니터링 담당과 기간 | 담당 부서 또는 역할, 관측 시작·종료 시점 | 인수 시점까지 지정된다 |
| 영향받는 다른 팀 | 영향 내용, 통지 대상, 통지 완료 여부 | 미통지 사유까지 확인된다 |
| 설정 변경 목록 | 키, 변경 전 값, 변경 후 값, 적용 환경 | 실제 적용값과 대조할 수 있다 |
| 마이그레이션 실행 책임자 | 실행자, 확인자, 실행 예정 시각 | 책임자가 수락한 상태이다 |

배포 후 관측 지표는 배포 전에 확정한다. 지표가 정해지지 않으면 이상을 사용자 신고나 후속 장애로 처음 인지하게 되므로 배포 승인 조건을 충족하지 못한 것으로 판정한다.

관측 항목에는 최소한 다음 정보를 포함한다.

1. 지표가 나타내는 사용자 또는 시스템 영향을 적는다.
2. 배포 전 기준값과 배포 후 허용 범위를 구분한다.
3. 임계값 초과 시 관찰 지속, 배포 중단, 롤백 중 어느 조치를 실행할지 지정한다.
4. 확인 주기와 관측 종료 조건을 적는다.
5. DATA 지표가 필요한 경우 집계 지연 시간과 데이터 확정 시점을 함께 적는다.

내부용 노트는 해당 프로젝트의 승인된 문서 저장소 내 릴리즈 노트 영역에 버전별로 보관한다. 파일명 또는 문서 제목에는 서비스 식별자, 버전, 배포일을 포함하고 다음 검색 필드를 등록한다.

- 배포 버전과 배포 일시
- 대상 환경
- 변경 모듈·서비스
- 요청·부채 ID
- 작성 부서와 배포 책임 역할
- `정상`, `롤백`, `부분 적용` 중 최종 배포 상태

채팅 메시지나 전자우편 본문만으로 보관을 대신하지 않는다. 공유 메시지에는 저장된 원본 노트의 위치를 연결하며, 접근 권한은 배포·운영 지원 인력이 확인할 수 있는 범위로 설정한다.

사내 공통 모듈을 변경한 경우에는 해당 모듈을 직접 의존하는 프로젝트 목록, 사용 중인 버전, 영향 확인 담당 부서, 적용 또는 미적용 결정을 추가한다. 의존 프로젝트를 확인하지 못한 상태는 `미확인`으로 표시하고 배포 책임자에게 판단을 요청한다.

## 사전 고지와 비활성화 정책
<!--meta: sec=s10; dept=BE|AIAX|CNS|DEVOPS; level=시니어; ct_band=상; related=s3-->
기능·인터페이스 제거는 `비활성화 예고 → 대체 수단 제공 → 유지 → 제거` 순서로 진행한다.  
비활성화는 현재 사용을 허용하되 향후 제거를 확정하고 신규 사용을 중단시키는 상태이다.

| 변경 유형 | 예고 최소 기간 | 응답 경고 적용 | 대체 수단 제공 시점 | 제거 가능 시점 |
|---|---:|---|---|---|
| 외부 API·이벤트·연동 인터페이스 | 90일 | 예고일부터 | 예고와 동시에 | 90일 경과 후 |
| 고객 운영용 설정·명령·관리 기능 | 60일 | 실행 또는 저장 시 | 예고 후 10영업일 이내 | 60일 경과 후 |
| 사용자 화면·업무 기능 | 30일 | 화면 진입 또는 기능 실행 시 | 예고와 동시에 | 30일 경과 후 |
| 내부 공용 모듈·공용 데이터 인터페이스 | 20영업일 | 호출·빌드·검증 시 | 예고 후 5영업일 이내 | 20영업일 경과 후 |
| 실험 기능으로 명시된 기능 | 10영업일 | 예고일부터 | 제공 가능 여부를 함께 고지 | 10영업일 경과 후 |

고객 계약이 적용되는 인터페이스에는 표의 기간과 계약상 통지·지원 기간 중 더 긴 기간을 적용한다.  
계약 기간 중 제공이 약정된 항목은 고객사의 서면 동의 없이 표의 최소 기간만으로 제거하지 않는다.  
계약 해석과 법적 의무는 사안별 확인이 필요하다.

예고 노트에는 다음 항목을 빠짐없이 적는다.

1. 비활성화 대상의 정확한 명칭과 현재 버전을 적는다.
2. 신규 사용 중단일과 최종 제거 예정일을 날짜로 적는다.
3. 대체 기능·API·설정과 전환 절차의 위치를 적는다.
4. 영향 여부를 확인할 조회 방법, 로그 조건 또는 점검 명령을 적는다.
5. 전환 문의 창구와 회신 기한을 적는다.

응답 경고는 정상 결과를 훼손하지 않으면서 대상이 비활성화 상태임을 식별할 수 있어야 한다.  
경고를 추가할 수 없는 화면이나 배치 작업에는 관리자 알림 또는 실행 로그를 사용한다.  
대체 수단은 기존 핵심 용도를 수행할 수 있어야 하며, 수행하지 못하는 차이는 노트에 명시한다.

예고 후에도 이동하지 않은 고객은 사용 현황과 미전환 사유를 확인한 뒤 처리한다.

- 기술 지원만으로 전환 가능한 경우 CNS가 전환 일정을 고객 담당자와 확정한다.
- 고객 작업이 남은 경우 제거일 전 10영업일까지 완료 예정일을 회신받는다.
- 30일 이내의 1회 연장은 담당 개발팀 부장이 승인한다.
- 30일을 넘는 연장 또는 계약 영향이 있는 유지는 담당 개발팀 부장과 CNS 부장이 공동 결정한다.
- 연장을 거부하면 영향 범위, 최종 지원일 및 제거 후 예상 동작을 서면으로 통지한다.

보안 취약점 악용 차단이나 준수해야 할 법적 요구로 유예가 불가능한 경우에는 예고 없이 제거할 수 있다.  
이 예외는 담당 개발팀 부장이 승인하며 법적 요구의 적용 여부는 사안별 확인한다.  
가능하면 제거 전에 CNS와 고객 담당자에게 알리고, 선통지가 불가능하면 제거 후 24시간 이내에 사유·영향·대체 방법을 통지한다.

모든 비활성화 대상은 하나의 비활성화 등록부에 모은다.  
등록부에는 대상, 소유팀, 예고일, 제거 예정일, 영향 고객, 대체 수단, 전환율, 예외 승인자를 기록한다.  
단일 등록부는 서로 다른 배포에서 같은 대상을 중복 예고하거나 고객별 제거일이 어긋나는 것을 방지하는 기준 원장이다.

## 작성 책임자와 검토 경로
<!--meta: sec=s11; dept=AIAX|BE|DATA|DEVOPS; level=주니어|시니어; ct_band=중; related=s4-->
릴리즈 노트 작성 책임자는 해당 배포의 배포 책임자이다.  
배포 범위와 실제 반영 결과를 확인할 권한이 없는 별도 작성자에게 책임을 넘기지 않는다.  
문안 초안 작성은 다른 구성원이 지원할 수 있으나 완성도와 사실 일치에 대한 책임은 배포 책임자가 진다.

노트는 배포 승인 요청 전에 작성한다.  
배포가 끝난 뒤 기억과 티켓을 모아 작성하는 방식은 허용하지 않는다.  
실제 배포 결과가 승인본과 다르면 배포 책임자가 즉시 차이를 반영한 뒤 공유한다.

| 검토 단계 | 검토자 | 소요 시간 목표 | 확인 대상 | 주요 반송 사유 |
|---|---|---:|---|---|
| 기술 정확성 검토 | 같은 팀 구성원 1명 | 4업무시간 이내 | 반영 범위, 동작, 버전, 알려진 제약 | 구현 결과와 설명 불일치, 검증 근거 누락 |
| 파괴적 변경·마이그레이션 검토 | 영향받는 팀 구성원 1명 | 1영업일 이내 | 연동 영향, 전환 단계, 복구 가능성 | 영향 대상 누락, 실행 불가능한 절차, 복구 경로 부재 |
| 고객 전달 문안 검토 | CNS 또는 SALES 구성원 1명 | 1영업일 이내 | 고객 이해 가능성, 공개 범위, 필요한 조치 | 내부 용어 노출, 조치 주체 불명확, 전달 범위 오류 |

파괴적 변경이 없으면 두 번째 검토 단계에는 `해당 없음`과 판정자를 남긴다.  
고객에게 전달하지 않는 배포이면 세 번째 단계에는 비전달 사유를 기록한다.  
한 사람이 여러 검토 자격을 갖더라도 기술 정확성 검토자와 작성자는 동일인이 될 수 없다.

검토는 다음 순서로 처리한다.

1. 배포 책임자가 초안과 검증 결과를 기술 정확성 검토자에게 보낸다.
2. 영향받는 팀이 있는 경우 기술 검토 통과본을 해당 팀에 전달한다.
3. 고객 전달본이 있는 경우 앞선 검토가 끝난 문안을 CNS 또는 SALES에 전달한다.
4. 배포 책임자가 반송 사항을 수정하고 각 검토자의 승인 표시를 받는다.
5. 모든 필수 승인이 확인된 뒤 배포 승인 요청에 노트 링크를 첨부한다.

검토 의견에는 수정 위치, 사실 근거와 완료 조건을 함께 적는다.  
단순한 선호 표현은 배포 차단 사유로 사용하지 않는다.  
버전, 영향 범위, 고객 조치 또는 복구 정보의 오류는 필수 반송 사유이다.

검토 없이 배포할 수 있는 예외는 고객이 사용하지 않는 내부 도구의 `PATCH`로 한정한다.  
이 예외는 공용 API, 데이터 스키마, 권한, 배포 경로 또는 다른 팀의 자동화에 영향을 주면 적용하지 않는다.  
예외 배포도 노트 작성과 배포 책임자의 자체 점검은 생략하지 않으며, 예외 사유를 내부용 노트에 남긴다.

필수 노트가 없거나 검토 상태를 확인할 수 없으면 배포를 차단한다.  
배포 일정 임박은 누락을 허용하는 사유가 아니다.  
차단 해제는 누락 문서 작성과 필수 검토 완료 후 배포 책임자가 요청한다.

## 공유 채널과 공유 시점
<!--meta: sec=s12; dept=AIAX|BE|CNS|SALES|DEVOPS; level=주니어|시니어; ct_band=하; related=s11-->
승인된 릴리즈 노트는 독자별 노트 종류와 전달 시점을 구분해 공유한다.  
링크만 전달할 때도 대상 버전과 배포 일시는 메시지 본문에 표시한다.

| 공유 대상 | 전달 노트 | 전달 수단 | 전달 시점 |
|---|---|---|---|
| 수행팀 내부 | 내부용 노트 | 프로젝트 문서 저장소와 승인된 협업 채널 | 배포 전 예고, 배포 직후 결과 공유 |
| 영향을 받는 다른 수행팀 | 내부용 노트 | 팀 간 협업 채널과 노트 링크 | 영향 작업 시작 전, 배포 직후 |
| SALES·CNS | 고객용 노트와 문의 대응용 내부 링크 | 영업·컨설팅 협업 채널 | 고객 고지 전, 주간 요약 |
| 고객 담당자 | 고객용 노트 | 합의된 이메일 또는 고객 협업 채널 | 필요한 경우 배포 전 예고, 배포 직후 |
| 고객 운영 조직 | 고객용 노트와 적용 안내 | 합의된 운영 전달 수단 | 운영 조치가 있으면 배포 전, 결과는 배포 직후 |

배포 전 예고는 고객 작업, 중단, 권한 변경 또는 사전 설정이 필요한 경우에 사용한다.  
배포 직후 공유에는 실제 배포 버전, 완료 시각, 적용 환경과 확인 결과를 포함한다.  
영향이 없는 다른 수행팀에는 개별 알림 대신 주간 요약으로 전달할 수 있다.

SALES와 CNS는 고객 문의의 1차 응답과 후속 요청의 범위 판정에 노트를 사용한다.  
따라서 고객 전달보다 늦게 노트를 받지 않도록 한다.  
고객의 신규 기능 요청 처리 기준은 PSY-03#s3 참조로 처리한다.

주간 요약본은 해당 주에 배포를 완료한 팀의 배포 책임자 중 1명이 취합한다.  
여러 팀이 배포했다면 각 배포 책임자가 자기 항목을 제출하고, 마지막 정기 배포의 책임자가 하나의 요약본으로 묶는다.  
요약본은 다음 항목으로 구성한다.

1. 버전, 배포일과 담당 팀을 적는다.
2. 고객에게 보이는 변경을 항목별 한 줄로 적는다.
3. 운영 조치가 필요한 대상과 기한을 적는다.
4. 진행 중인 비활성화와 다음 제거 예정일을 적는다.
5. 확인 중인 문제와 문의 창구를 적는다.

긴급 배포는 속도 때문에 공유 대상을 생략하지 않고 전달 순서만 단축한다.

1. 배포 책임자가 수행팀 내부에 배포 착수와 영향을 알린다.
2. 영향받는 다른 수행팀에 대응 필요 사항을 전달한다.
3. CNS와 SALES에 고객 설명 문안과 예상 문의를 전달한다.
4. 고객 담당자와 고객 운영 조직에 승인된 고객용 노트를 전달한다.
5. 배포 직후 같은 순서로 완료 여부와 검증 결과를 갱신한다.

모든 공유는 전달 기록을 남긴다.  
기록 항목은 버전, 노트 링크, 전달 대상, 전달 채널, 발송자, 발송 시각, 수신 확인 여부이다.  
고객 조치가 필요한 경우에는 조치 기한과 회신 상태도 추가한다.  
공유 기록은 누가 어떤 정보로 운영 판단을 했는지 확인하고 누락된 수신자를 재통지하는 근거로 사용한다.

## 커밋 규약과의 연계
<!--meta: sec=s13; dept=BE|AIAX|DEVOPS; level=시니어; ct_band=상; related=s3|s7-->
BE와 AIAX는 변경 이력을 기계적으로 분류할 수 있도록 커밋 제목을 `<type>[선택 범위]: 요약` 형식으로 작성한다. 호환성 파괴 여부는 타입 뒤 `!` 또는 본문의 `BREAKING CHANGE:` 꼬리말로 선언한다.

| 커밋 타입 | 적용 대상 | 노트 라벨 대응 | 버전 증가 후보 |
|---|---|---|---|
| `feat` | 하위 호환 신규 기능·옵션·인터페이스 | 추가 | MINOR |
| `fix` | 의도와 다르게 작동한 동작의 수정 | 수정 | PATCH |
| `perf` | 사용자가 체감하거나 측정할 수 있는 성능 개선 | 변경 | PATCH |
| `refactor` | 외부 동작을 유지하는 내부 구조 변경 | 고객용 미노출, 내부용 기록 | 없음 |
| `docs` | 사용·운영 문서만 변경 | 문서 | 없음 |
| `test` | 테스트 코드·데이터만 변경 | 내부용 기록 | 없음 |
| `build` | 빌드 도구·의존성·패키징 변경 | 영향이 있을 때 변경 | 없음 또는 PATCH |
| `ci` | 통합·배포 자동화 변경 | 내부용 기록 | 없음 |
| `chore` | 분류되지 않는 유지보수 작업 | 내부용 기록 | 없음 |
| `revert` | 이전 변경의 되돌림 | 되돌린 항목의 결과에 따라 판정 | 영향에 따라 재판정 |

`feat!`, `fix!`처럼 `!`가 붙거나 `BREAKING CHANGE:`가 있는 커밋은 타입과 관계없이 MAJOR 후보로 올린다. 최종 판정은 PSY-04#s3을 적용하며, 자동화 도구가 버전을 단독 확정하지 않는다.

커밋 규약과 유의적 버전을 함께 강제하면 타입, 변경 범위, 파괴적 변경 선언을 수집해 릴리즈 노트 초안을 자동 생성할 수 있다. 이 방식은 배포 책임자가 여러 티켓과 변경 이력을 다시 대조하는 인지 부담을 줄이고, 변경 항목 누락과 잘못된 버전 선택에 따른 운영 위험을 낮춘다.

자동 생성기는 다음 정보까지만 초안에 채운다.

- 커밋 타입에 대응하는 분류 라벨
- 제목에 기재된 변경 요약과 선택 범위
- 연관 요청 번호가 있는 경우 해당 식별자
- 파괴적 변경 선언 유무와 버전 증가 후보
- 릴리즈 기준점 사이의 커밋 목록과 작성 시각

배포 책임자는 생성된 초안을 그대로 외부에 내보내지 않고 다음 항목을 직접 고친다.

1. 구현 중심 제목을 고객이 얻는 결과 또는 수행할 조치 중심 문장으로 바꾼다.
2. 여러 커밋이 하나의 결과를 만든 경우 중복 항목을 합친다.
3. 실제 영향받는 사용자, 모듈, 연동 대상 및 운영 구간을 확인한다.
4. 파괴적 변경에는 실행 가능한 마이그레이션 안내를 연결한다.
5. 배포에서 제외되거나 되돌려진 커밋을 초안에서 제거한다.

고객 영향 기간, 데이터 변환 순서, 중단 시간, 복구 조건, 알려진 제약, 고객별 적용 여부는 커밋 정보만으로 채우지 않는다. 해당 내용은 배포 결과와 운영 확인 자료를 근거로 사람이 작성한다.

규약을 위반한 커밋은 병합 전에 자동 검사에서 실패 처리한다. 이미 병합된 경우 공유 브랜치 이력을 임의로 고쳐 쓰지 않고, 배포 책임자가 타입·라벨·버전 후보를 매핑 기록에 보완한다. 매핑되지 않은 커밋이 하나라도 남으면 릴리즈 노트 승인 요청을 올리지 않는다.

자동화 도입 전에는 배포 책임자가 배포 기준점 사이의 커밋을 전수 확인해 동일한 타입 표로 수동 분류한다. 분류 결과, 제외 사유, 파괴적 변경 판정자를 내부용 노트의 작성 근거에 남긴다.

## 긴급 수정 노트 규칙
<!--meta: sec=s14; dept=BE|AIAX|DEVOPS; level=시니어; ct_band=상; related=s4|s12-->
긴급 수정은 정규 배포 절차보다 짧은 시간에 적용하더라도 노트를 생략하지 않는다. 배포 책임자는 수정 배포가 완료된 당일 23시 59분까지 승인된 공유 채널에 긴급 수정 노트를 게시한다.

| 필수 항목 | 작성 기준 | 미확정 시 표기 |
|---|---|---|
| 깨져 있던 동작 | 정상 기대값과 실제 관측 결과를 대비해 적는다 | 관측된 현상만 적는다 |
| 영향 대상 | 영향받은 사용자군, 기능, 연동 또는 운영 작업을 구분한다 | 확인 중인 범위를 명시한다 |
| 수정 내용 | 복구된 동작과 적용된 변경을 결과 단위로 적는다 | 적용 사실까지만 적는다 |
| 영향 기간 | 최초 발생 시각부터 정상화 확인 시각까지 적는다 | 시작 또는 종료 시각을 `확인 중`으로 둔다 |
| 사용자 확인 사항 | 재시도, 재조회, 설정 확인 등 필요한 행동을 적는다 | 조치가 없으면 `사용자 조치 없음`으로 적는다 |
| 후속 조치 | 추가 검증, 원인 확정, 재발 방지 또는 잔여 작업의 예정일을 적는다 | 담당자와 다음 갱신 시각을 적는다 |

영향 대상이 없다고 판단한 경우에도 해당 항목을 삭제하지 않는다. 배포 책임자는 확인한 관측 지표와 확인 시각을 근거로 `외부 영향 확인되지 않음`이라고 기록한다.

원인 분석이 끝나지 않았을 때는 추정을 사실처럼 표현하지 않는다. 다음 표현 원칙을 적용한다.

- 확인된 증상과 시간 정보는 단정형으로 쓴다.
- 원인 후보는 `현재 확인 중이며 확정되지 않음`으로 구분한다.
- “원인은”, “완전히 해결”, “재발하지 않음”은 검증이 끝나기 전 사용하지 않는다.
- 임시 우회와 영구 수정이 다르면 각각의 적용 상태를 분리한다.

원인이 확정되면 배포 책임자는 확정 시점부터 1영업일 이내에 기존 노트에 보완 기록을 추가한다. 최초 게시 내용은 지우지 않고 갱신 일시, 확정 원인, 후속 조치 변경분을 덧붙인다.

긴급 수정 항목은 다음 정규 릴리즈 노트에도 다시 포함한다. 이때 제목 앞에 `긴급 수정 재수록`을 표시하고 긴급 노트 링크, 적용 버전, 적용 일시를 연결한다. 정규 노트에는 새 변경처럼 서술하지 않고 이미 적용된 수정임을 밝힌다.

같은 원인으로 두 번째 긴급 수정이 발생하면 배포 책임자는 다음 절차를 수행한다.

1. 두 번째 배포 완료 후 4시간 이내에 수행 책임자와 관련 BE·AIAX 책임자에게 반복 발생 사실을 보고한다.
2. 최초 건과 재발 건의 버전, 영향 기간, 수정 방식 및 검증 차이를 한 표로 비교한다.
3. 다음 영업일까지 기술 부채 등록부에 항목을 만들고 두 긴급 노트를 연결한다.
4. 상환 우선순위와 반복 주기 반영은 PSY-06#s4를 따른다.
5. 추가 수정 일정이 정해지지 않았으면 결정권자와 결정 예정일을 기록한다.

공유 대상과 채널 선택은 PSY-04#s12를 따르며, 긴급이라는 이유로 영향을 받는 대상에 대한 전달을 다음 정규 배포까지 미루지 않는다.

## 과거 노트 수정·정정 규칙
<!--meta: sec=s15; dept=AIAX|BE|DEVOPS; level=주니어|시니어; ct_band=중; related=s4-->
이미 공유한 릴리즈 노트의 본문을 조용히 덮어쓰지 않는다. 오탈자처럼 의미에 영향이 없는 수정도 변경 이력에 수정 일시와 항목을 남긴다.

| 정정 사유 | 처리 방식 | 추가 조치 |
|---|---|---|
| 버전·일시·영향 대상 등 사실 오류 | 원문을 유지하고 바로 아래에 올바른 사실을 추가한다 | 기존 공유 채널에 정정 사실을 알린다 |
| 호환성 파괴 변경 누락 | 노트 상단에 정정 경고를 추가하고 해당 변경을 본문에 보완한다 | 영향 대상에 별도 통지한다 |
| 잘못된 마이그레이션 절차 | 잘못된 단계를 즉시 사용 중지 표시하고 검증된 절차를 추가한다 | 긴급 통지와 적용 여부 확인을 수행한다 |
| 필요한 사용자 조치 누락 | 수행할 조치, 기한, 미수행 영향을 추가한다 | 조치 대상 목록으로 전달 상태를 추적한다 |

정정 블록은 다음 형식을 사용한다.

- `정정 일자`: 연월일과 시각
- `정정 내용`: 잘못된 내용과 올바른 내용을 한 쌍으로 표시
- `정정 사유`: 오류가 노트에 포함된 경위
- `원문`: 취소선 또는 인용 형식으로 보존
- `영향`: 정정 전 안내를 따른 경우 발생할 수 있는 결과
- `확인 담당`: 정정 내용을 검증한 부서와 역할

정정본은 새 파일로 갈아끼우지 않고 기존 노트의 동일 주소에서 조회되게 한다. 문서 저장소의 변경 이력에는 수정자, 수정 시각, 이전 판본 및 정정본을 보관한다.

각 노트에는 직전 버전과 다음 버전의 링크를 둔다. 정정이 여러 버전에 영향을 주면 영향받는 모든 노트에 상호 링크를 추가해 변경 흐름을 추적할 수 있게 한다.

잘못된 마이그레이션 절차가 배포된 경우 배포 책임자는 발견 후 1시간 이내에 다음 순서로 통지한다.

1. 문서 상단에 `절차 사용 중지` 경고와 발견 시각을 표시한다.
2. 배포 대상 목록, 버전 수집 정보, 전달 이력 및 적용 확인 기록으로 통지 대상을 식별한다.
3. 해당 절차를 받은 수행팀과 고객사 운영 담당자에게 정정 전용 메시지를 보낸다.
4. 실행 여부, 실행 단계, 백업 보유 여부 및 현재 상태를 회신 항목으로 요구한다.
5. 검증된 대체 절차가 준비되면 동일한 대상에게 재통지하고 수신 여부를 기록한다.

정정 사유는 `사실 검증 누락`, `파괴적 변경 판정 누락`, `절차 검증 실패`, `대상 식별 오류`, `기타`로 집계한다. 배포 책임자는 월말에 발생 건수를 검토하고 같은 사유가 2회 이상이면 작성 양식이나 검토 체크 항목의 수정안을 제출한다. 변경된 표준 구성은 PSY-04#s4에 반영한다.

## 품질 점검 체크리스트
<!--meta: sec=s16; dept=AIAX|BE|DATA|DEVOPS; level=주니어|시니어; ct_band=중; related=s4|s6-->
배포 책임자는 배포 승인 요청 직전에 아래 항목을 확인하고 각 항목에 `충족`, `해당 없음`, `미충족` 중 하나를 표시한다. `해당 없음`에는 판단 근거를 한 문장으로 남기며, 구두 확인은 증빙으로 인정하지 않는다.

1. 노트의 대상 버전이 실제 배포 산출물의 버전과 일치하는가.
2. `MAJOR`, `MINOR`, `PATCH` 증가 자리가 변경 성격과 일치하는가.
3. 배포 일시, 대상 환경 및 적용 범위가 승인 요청 내용과 일치하는가.
4. 필수 절과 순서가 빠짐없이 유지되어 있는가. 세부 기준은 PSY-04#s4 참조.
5. 실제 반영된 변경만 기재되고 배포에서 제외된 항목은 제거되었는가.
6. 호환성 파괴 변경이 누락 없이 한 줄에 하나씩 분리되어 있는가.
7. 각 호환성 파괴 변경에 영향받는 사용자, 연동, 설정 또는 데이터가 명시되어 있는가.
8. 각 호환성 파괴 변경에 실행 가능한 마이그레이션 경로가 연결되어 있는가.
9. 이름이 바뀐 설정, 제거된 옵션 및 변경된 기본값이 각각 식별되는가.
10. 업그레이드 절차를 배포 대상과 동등한 검증 환경에서 실제로 실행했는가.
11. 실행 결과와 예상 결과를 비교한 증빙 링크가 내부용 노트에 연결되어 있는가.
12. 되돌리기 절차가 명령, 순서 및 담당 부서 단위로 작성되어 있는가.
13. 데이터 변환 등 되돌릴 수 없는 지점과 진입 전 승인 조건이 표시되어 있는가.
14. 백업 대상, 복구 확인 방법 및 복구 완료 판정값이 있는가. 세부 기준은 PSY-04#s6 참조.
15. 배포 후 관측할 지표마다 정상 범위 또는 중단·복구를 판단할 임계값이 정해져 있는가.
16. 관측 시작 시점, 관측 종료 시점 및 확인 담당자가 지정되어 있는가.
17. 고객용 노트에 내부 티켓, 요청 ID, 커밋 해시, 브랜치명 또는 내부 링크가 남아 있지 않은가.
18. 내부용 노트에 관련 요청 ID와 원본 기록 링크가 연결되어 있는가.
19. 고객이 수행해야 할 조치에 주체, 완료 시한 및 완료 확인 방법이 포함되어 있는가.
20. 필수 검토자의 이름, 검토 일시 및 승인 서명이 기록되어 있는가.

| 판정 | 배포 처리 | 차단 해제 조건 |
|---|---|---|
| 전 항목 충족 | 승인 절차를 계속한다 | 추가 조치 없음 |
| 근거가 있는 해당 없음만 존재 | 승인 절차를 계속한다 | 검토자가 근거를 승인한다 |
| 1개 이상 미충족 | 배포를 차단한다 | 수정 후 해당 항목을 재검토한다 |
| 증빙 링크 접근 불가 또는 서명 누락 | 미충족으로 판정한다 | 접근 복구 또는 서명 완료 후 다시 확인한다 |

배포 책임자와 필수 검토자는 각각 배포 차단 권한을 가진다. 영향받는 AIAX·BE·DATA 영역의 검토자 중 한 명이라도 미충족을 선언하면 다수결로 해제하지 않으며, 해당 항목의 재검토 서명이 등록될 때까지 배포하지 않는다.
