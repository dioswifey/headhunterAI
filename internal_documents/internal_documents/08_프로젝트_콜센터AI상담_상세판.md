## 고객사 및 계약 정보
<!--meta: sec=s1; dept=AIAX|BE|SALES; level=시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
고객사는 중견 가전제조사 "대한전자"이며, 수도권 고객센터(상담사 80명 규모)에 2026년 3분기 도입했습니다. 계약 규모와 세부 조건은 영업팀 자료 참고.

본 프로젝트의 계약 범위는 상담 중 지식 검색 지원, 반복 문의 자동응답, 상담사 검토 화면, 관리자용 품질 모니터링, 기존 상담 시스템과의 연계, 운영 이관 및 초기 안정화 지원으로 구성했습니다. 고객센터의 전체 업무를 무인화하는 사업이 아니라, 상담사의 판단을 보조하고 정형화된 반복 문의를 선별적으로 자동 처리하는 상담 지원 체계 구축을 목표로 정의했습니다.

계약·견적·정산·검수 조건과 고객사 담당자 개인 연락처는 본 문서에 기록하지 않습니다. 해당 정보는 영업팀의 접근통제 자료를 기준으로 확인하며, 기술팀은 승인된 범위·일정·인수 기준만 전달받아 수행합니다. 범위 변경 요청은 구두 합의로 반영하지 않고 영업팀과 프로젝트 책임자의 확인을 거쳐 변경 요청 항목으로 관리했습니다.

프로젝트 수행에는 헤드헌터랩 AI/AX개발팀, 백엔드팀, 데이터분석팀, 영업팀이 참여했습니다. AI/AX개발팀은 상담 지식 검색과 응답 생성 정책을, 백엔드팀은 연계 API와 권한·로그·운영 기능을, 데이터분석팀은 평가셋과 성과지표를, 영업팀은 고객 커뮤니케이션과 계약 범위 관리를 담당했습니다.

## 프로젝트 목표와 비목표
<!--meta: sec=s2; dept=AIAX|BE|DATA|SALES; level=주니어|시니어; ct_band=하; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
프로젝트의 1차 목표는 상담사가 여러 PDF 매뉴얼을 직접 검색하는 시간을 줄이고, 반복 문의에 일관된 답변을 제공하며, 신입 상담사의 업무 숙련 기간을 단축하는 것이었습니다. 상담사가 AI 답변을 그대로 읽도록 강제하지 않고, 근거 문서와 주의 문구를 함께 확인한 뒤 최종 답변을 선택하도록 업무 흐름을 설계했습니다.

주요 목표는 다음과 같습니다.

- 상담 중 필요한 매뉴얼 근거를 짧은 시간 안에 제시
- 반복 문의를 식별해 자동응답 가능 여부를 분류
- 응답마다 참조한 문서명과 근거 구간을 표시
- 개인정보가 검색 인덱스와 모델 입력에 불필요하게 남지 않도록 통제
- 상담사 수정·채택·거절 이력을 품질 개선 데이터로 축적
- 운영자가 문서 반영 상태와 응답 품질을 확인할 수 있도록 지원
- 위험도가 높은 문의는 AI가 단독 처리하지 않고 상담사에게 이관

비목표에는 민원에 대한 법적 판단, 보상 금액의 임의 확정, 제품 결함 판정, 감정적으로 격앙된 고객에 대한 완전 자동응대, 고객 신원 확인의 대체, 기존 상담·녹취·고객관리 시스템의 전면 교체가 포함됩니다. 비목표를 명확히 둔 이유는 생성형 AI의 답변 범위를 제한하고 고객센터의 기존 책임 체계를 유지하기 위해서입니다.

## 사용자 및 업무 시나리오
<!--meta: sec=s3; dept=AIAX|BE|DATA; level=주니어; ct_band=하; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
주 사용자는 상담사, 상담 관리자, 지식 관리자, 시스템 운영자로 구분했습니다. 동일한 화면과 기능을 모든 사용자에게 제공하지 않고 역할별로 조회·수정·승인 권한을 분리했습니다.

상담사는 고객 문의를 입력하거나 상담 시스템에서 전달된 문의 요약을 확인한 뒤 AI 추천 답변과 근거 문서를 검토합니다. 추천 답변이 적절하면 채택하고, 표현만 수정해야 하면 수정 후 사용하며, 내용이 부정확하거나 현재 상황에 맞지 않으면 거절 사유를 선택합니다.

상담 관리자는 상담사별 사용률을 평가하기보다 문의 유형별 자동해결률, 답변 거절 사유, 근거 부족 비율, 상담사 이관 비율을 중심으로 확인합니다. AI 사용 횟수만으로 상담사 성과를 평가하지 않도록 운영 원칙을 합의했습니다.

지식 관리자는 신규 매뉴얼 등록, 기존 문서 교체, 적용 시작일 확인, 중복 문서 정리, 폐기 문서 비활성화를 수행합니다. 시스템 운영자는 연계 상태, 응답 지연, 인덱싱 실패, 마스킹 실패, 권한 오류를 점검합니다.

대표 시나리오는 제품 사용법, 설치 조건, 소모품 교체, 보증 범위 안내, 방문 서비스 절차와 같은 반복 문의입니다. 반면 고객이 강한 불만을 표현하거나 보상·법적 대응·안전사고 가능성을 언급하는 경우에는 자동응답을 중단하고 상담사 또는 관리자에게 이관합니다.

## 상담 흐름 및 처리 단계
<!--meta: sec=s4; dept=AIAX|BE; level=주니어|시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
상담 지원 요청은 다음 단계로 처리합니다.

1. 상담 시스템에서 문의 문장과 허용된 상담 맥락을 전달합니다.
2. 입력값에서 전화번호, 주소 등 개인정보 후보를 탐지하고 마스킹합니다.
3. 문의를 제품군, 문의 목적, 위험 표현, 자동응답 허용 여부 기준으로 분류합니다.
4. 자동응답이 허용된 요청은 상담 매뉴얼 검색 단계로 전달합니다.
5. 검색 결과의 관련성, 문서 유효 상태, 적용 시점, 권한 범위를 확인합니다.
6. 적합한 근거가 확보되면 근거 범위 안에서 답변 초안을 생성합니다.
7. 답변에는 참조 문서와 확인이 필요한 조건을 함께 표시합니다.
8. 위험 표현이 있거나 근거가 부족하면 답변을 확정하지 않고 상담사 확인 대상으로 전환합니다.
9. 상담사가 채택·수정·거절한 결과를 품질 로그에 기록합니다.
10. 관리 화면에서는 개별 고객의 불필요한 개인정보를 제거한 집계 결과만 우선 제공합니다.

문의 분류 결과는 최종 업무 판단이 아니라 라우팅을 위한 보조 정보입니다. 분류 모델이 일반 문의로 판단했더라도 상담사가 민원·안전·보상 관련 위험을 발견하면 즉시 상위 단계로 이관할 수 있습니다.

## 아키텍처 세부
<!--meta: sec=s5; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=UNIT-RAG-->
<!--forbid: 대한전자|PRJ-CC-->
RAG 검색 모듈은 고객사 상담 매뉴얼(PDF)을 임베딩해 벡터DB에 저장하고, 상담사 질의 시 유사도 상위 5건을 LLM 프롬프트에 포함합니다. 개인정보(고객 전화번호·주소)는 임베딩 전 마스킹 처리합니다.

전체 구성은 문서 수집 영역, 전처리·인덱싱 영역, 실시간 질의 영역, 생성·검증 영역, 상담 화면 연계 영역, 운영·관측 영역으로 구분했습니다. 문서 수집과 실시간 질의를 분리해 대량 문서 등록이 상담 응답 처리에 직접 영향을 주지 않도록 했습니다.

문서 수집 영역은 승인된 PDF만 받아 원본 식별자, 문서명, 제품군, 버전, 시행일, 폐기 여부를 기록합니다. 전처리·인덱싱 영역은 텍스트 추출, 표·목록 구조 보정, 개인정보 마스킹, 구간 분할, 임베딩 생성, 벡터DB 적재를 순서대로 수행합니다.

실시간 질의 영역은 문의 정규화, 위험 분류, 검색 조건 생성, 벡터 검색, 메타데이터 필터링, 후보 정렬을 수행합니다. 생성·검증 영역은 상위 5건의 검색 근거를 프롬프트에 포함하고 답변 초안, 출처, 확인 필요 여부를 생성합니다.

상담 화면에는 생성 답변만 단독으로 표시하지 않고 근거 문서 제목, 해당 구간, 문서 적용 상태, 상담사 확인 항목을 함께 표시합니다. 운영 영역에서는 지연 시간, 검색 실패, 생성 실패, 마스킹 결과, 문서 반영 상태를 추적합니다.

세부 함수·클래스·검색 점수 계산 방식은 RAG 검색 모듈 단위코드 문서에서 관리하며, 본 문서는 프로젝트 관점의 구성과 적용 원칙만 다룹니다.

## 상담 매뉴얼 수집 및 등록 기준
<!--meta: sec=s6; dept=AIAX|DATA; level=주니어; ct_band=중; related=UNIT-RAG-->
<!--forbid: 대한전자|PRJ-CC-->
검색 대상으로 등록할 문서는 고객사가 승인한 상담 매뉴얼 PDF로 제한했습니다. 개인이 작성한 메모, 검토되지 않은 이메일, 임시 안내문, 출처가 불분명한 파일은 기본 검색 대상에서 제외했습니다.

문서 등록 시 다음 항목을 확인합니다.

- 문서 제목과 제품군이 식별 가능한가
- 버전 또는 적용 시점이 확인되는가
- 동일 내용의 구버전이 함께 활성화되어 있지 않은가
- 스캔 품질이 텍스트 추출에 적합한가
- 표와 주의 문구가 본문과 분리되지 않았는가
- 전화번호·주소 등 개인정보가 포함되어 있는가
- 내부 전용 절차와 고객 안내 가능 문구가 구분되어 있는가
- 폐기·대체 관계를 시스템에서 표현할 수 있는가

등록 실패 문서는 원인을 `텍스트 추출 불가`, `메타데이터 누락`, `중복 의심`, `개인정보 검토 필요`, `승인 상태 불명`으로 분류합니다. 실패 문서를 임의로 재등록하지 않고 지식 관리자가 보완한 뒤 다시 승인하도록 했습니다.

PDF의 페이지 번호는 상담사가 원문을 찾을 때 중요한 단서이므로 가능한 경우 검색 구간 메타데이터에 유지합니다. 다만 표지·목차·본문의 페이지 표기가 서로 다르면 시스템 페이지와 문서 표기 페이지를 구분해 저장합니다.

## 문서 전처리와 지식 단위 설계
<!--meta: sec=s7; dept=AIAX|DATA; level=주니어|시니어; ct_band=상; related=UNIT-RAG-->
<!--forbid: 대한전자|PRJ-CC-->
문서 전처리의 목적은 PDF를 단순히 잘게 나누는 것이 아니라, 상담 질문에 답할 수 있는 의미 단위로 재구성하는 것입니다. 제목, 소제목, 단계 목록, 경고 문구, 조건문이 서로 분리되면 검색 결과가 문법적으로 맞더라도 업무적으로 잘못 해석될 수 있습니다.

지식 단위는 다음 원칙으로 구성했습니다.

- 상위 제목과 제품군 정보를 본문 구간에 상속
- 절차형 문장은 순서를 유지해 함께 배치
- 경고·예외·금지 조건은 대상 설명과 분리하지 않음
- 표의 행·열 머리글을 각 데이터와 연결
- 동일 문장이 여러 제품군에 반복될 경우 제품군 메타데이터로 구분
- 문서 개정 이력 자체는 답변 근거와 분리
- 지나치게 짧은 구간은 앞뒤 맥락과 병합
- 서로 다른 정책을 하나의 구간에 과도하게 결합하지 않음

전처리 결과는 원문 위치를 역추적할 수 있어야 합니다. 상담사가 근거 구간을 선택하면 원본 PDF의 해당 페이지를 확인할 수 있도록 원본 문서 식별자와 위치 정보를 유지했습니다.

광학문자인식 결과가 불확실한 스캔 문서는 숫자, 모델명, 단위가 왜곡될 가능성이 있으므로 별도 검토 대상으로 표시합니다. 특히 숫자 하나가 설치 조건이나 보증 범위를 바꿀 수 있는 문장은 자동 등록보다 수동 확인을 우선합니다.

## 개인정보 및 민감정보 처리
<!--meta: sec=s8; dept=AIAX|BE; level=주니어|시니어; ct_band=상; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC|전화번호|주소-->
개인정보(고객 전화번호·주소)는 임베딩 전 마스킹 처리합니다. 마스킹은 문서 적재 시점과 실시간 질의 시점에 각각 적용하며, 불필요한 원문이 벡터DB나 모델 입력에 포함되지 않도록 하는 것을 기본 원칙으로 삼았습니다.

대표 마스킹 대상은 전화번호, 주소, 이메일 형식, 고객 식별번호처럼 개인을 직접 또는 간접적으로 식별할 가능성이 있는 값입니다. 단순한 숫자를 모두 제거하면 제품 모델명과 오류 코드가 훼손될 수 있으므로 문맥과 형식을 함께 사용해 개인정보 후보를 판별합니다.

마스킹 후에는 다음 검사를 수행합니다.

- 전화번호 형식이 그대로 남아 있지 않은가
- 주소의 상세 번지·동·호 정보가 남아 있지 않은가
- 제품 모델명이나 오류 코드가 잘못 제거되지 않았는가
- 마스킹 토큰이 문장 의미를 지나치게 훼손하지 않았는가
- 로그에 마스킹 전 입력값이 기록되지 않는가
- 재처리 과정에서 원문이 임시 파일로 장기간 유지되지 않는가

운영 로그는 문제 분석에 필요한 요청 식별자, 처리 단계, 오류 코드, 소요 시간 중심으로 구성합니다. 개인정보 원문을 디버깅 편의 목적으로 상시 남기는 방식은 허용하지 않습니다. 예외적인 원문 확인이 필요한 경우에는 별도의 승인과 제한된 접근 절차를 사용합니다.

## 검색 및 답변 생성 정책
<!--meta: sec=s9; dept=AIAX; level=시니어; ct_band=상; related=UNIT-RAG|UNIT-SERVE-->
<!--forbid: 대한전자|PRJ-CC-->
검색 단계는 질의 의미와 문서 메타데이터를 함께 사용합니다. 제품군이 확인된 경우 해당 제품군을 우선 검색하고, 제품군이 불분명한 경우에는 답변을 단정하기보다 추가 확인이 필요하다는 상태를 표시합니다.

상담사 질의 시 유사도 상위 5건을 LLM 프롬프트에 포함하지만, 상위 5건이라는 개수 자체가 답변 가능성을 보장하지는 않습니다. 검색 결과가 모두 낮은 관련성을 보이거나 서로 상충하는 경우에는 생성 단계에서 임의로 결론을 합성하지 않도록 제한합니다.

답변 생성 정책은 다음과 같습니다.

- 제공된 검색 근거 범위에서만 답변
- 근거에 없는 비용, 기간, 보상, 확정 표현 생성 금지
- 제품군 또는 조건이 불명확하면 추가 확인 항목 표시
- 서로 다른 문서가 충돌하면 최신 승인 문서를 우선하되 충돌 상태 기록
- 근거가 부족하면 "확인 필요"로 표시
- 내부 절차 문구를 고객 안내 문장으로 그대로 노출하지 않음
- 상담사가 확인해야 할 예외 조건을 답변 하단에 분리 표시
- 출처 없는 상식 보완이나 추정 답변을 허용하지 않음

생성 답변은 최종 정책 문서가 아닙니다. 최종 응대 책임은 승인된 업무 절차와 상담사 판단 체계에 있으며, AI는 검색과 초안 작성을 지원하는 도구로 배치했습니다.

## 신뢰도와 근거 표시 방식
<!--meta: sec=s10; dept=AIAX|DATA|BE; level=주니어|시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
상담 화면에서 단일 백분율을 제시하면 사용자가 이를 정답 확률로 오해할 수 있으므로, 신뢰도는 `답변 가능`, `상담사 확인 필요`, `근거 부족`의 업무 상태 중심으로 표현했습니다. 내부 분석에서는 검색 점수와 후보 간 차이를 활용하지만, 이를 곧바로 정답률로 간주하지 않습니다.

근거 카드는 문서명, 제품군, 적용 상태, 원문 구간, 페이지 위치를 표시합니다. 상담사는 답변 문장과 근거 문장을 비교한 뒤 채택 여부를 선택할 수 있습니다. 근거 카드가 없거나 문서가 비활성 상태이면 답변 확정 버튼을 제한하는 방식을 적용했습니다.

상담사가 답변을 수정한 경우에는 수정 전·후 전체 문장을 무조건 장기 보관하기보다, 품질 개선에 필요한 범위와 개인정보 제거 여부를 확인해 저장합니다. 수정 사유는 `표현 보정`, `조건 누락`, `제품 불일치`, `정책 불일치`, `근거 부족`, `기타`로 분류해 분석 가능성을 높였습니다.

## 감정·민원·위험 문의 이관 정책
<!--meta: sec=s11; dept=AIAX|BE|SALES; level=주니어|시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
감정적으로 격앙된 고객 응대에는 챗봇을 개입시키지 않고 바로 상담사에게 넘기도록 설계했습니다. 욕설 유무만으로 감정 상태를 판단하지 않고 반복 항의, 즉시 책임자 연결 요구, 법적 조치 언급, 안전사고 가능성, 보상 요구 등 업무 위험 신호를 함께 확인합니다.

이관 대상의 대표 예시는 다음과 같습니다.

- 고객이 인명·화재·감전 등 안전 위험을 언급한 경우
- 제품 결함을 단정하거나 법적 책임을 요구하는 경우
- 보상 금액이나 교환·환불의 즉시 확정을 요구하는 경우
- 동일 문의가 반복되며 고객 불만이 지속되는 경우
- 상담사 또는 책임자와의 직접 통화를 명시적으로 요청한 경우
- AI가 제품군이나 정책 근거를 명확히 식별하지 못한 경우
- 검색 문서 간 내용이 상충하는 경우

이관 시에는 생성 답변을 고객에게 먼저 노출하지 않습니다. 상담사에게 문의 요약, 탐지된 위험 유형, 관련 가능성이 있는 근거 문서만 제공하고 최종 대응은 기존 상담 절차에 따르도록 했습니다.

오탐으로 인해 일반 문의가 상담사에게 이관되는 것은 일정 범위에서 허용하지만, 위험 문의가 자동응답으로 처리되는 누락은 더 높은 우선순위로 관리했습니다. 따라서 초기 운영에서는 자동화율보다 안전한 이관 정책을 우선했습니다.

## 상담사 화면 및 사용자 경험
<!--meta: sec=s12; dept=AIAX|BE; level=주니어; ct_band=하; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
상담사 화면은 통화 중 짧은 시간 안에 읽을 수 있도록 추천 답변, 근거, 확인 항목의 순서를 고정했습니다. 생성 과정의 기술 용어와 내부 점수는 노출하지 않고 업무에 필요한 상태만 표현했습니다.

화면의 주요 요소는 다음과 같습니다.

- 고객 문의 또는 상담사 입력 영역
- 제품군과 문의 유형 확인 영역
- AI 추천 답변 영역
- 근거 문서 카드
- 필수 확인 조건과 주의 문구
- 채택·수정·거절 버튼
- 상담사 이관 또는 관리자 확인 버튼
- 처리 지연·근거 부족 상태 안내

답변이 길어질 경우 핵심 안내와 조건을 구분해 표시합니다. 경고 문구는 접힌 영역 안에 숨기지 않고 기본 노출하며, 근거 원문은 필요할 때 확장해 확인할 수 있도록 구성했습니다.

상담사에게 AI 사용을 강제하지 않았습니다. 직접 매뉴얼 검색이 더 적합한 경우 기존 절차를 사용할 수 있으며, AI 답변을 거절했다는 사실만으로 불이익이 발생하지 않도록 사용자 교육에 포함했습니다.

## 백엔드 연계 및 권한 구조
<!--meta: sec=s13; dept=BE|AIAX; level=주니어|시니어; ct_band=상; related=JD-BE-->
<!--forbid: 대한전자|PRJ-CC-->
백엔드 연계는 상담 요청, 검색·생성 결과, 상담사 피드백, 문서 상태, 운영 지표를 서로 다른 책임 영역으로 분리했습니다. 상담 화면이 모델 서빙 영역을 직접 호출하지 않고 백엔드의 인증·권한·검증 계층을 통과하도록 구성했습니다.

요청에는 추적 가능한 요청 식별자를 부여하되 고객 개인정보를 식별자에 포함하지 않습니다. 같은 요청이 네트워크 재시도로 중복 제출될 수 있으므로 피드백 저장과 상태 변경은 중복 처리에 안전하도록 설계했습니다.

권한은 최소한 다음 역할로 분리했습니다.

- 상담사: 추천 답변과 허용된 근거 조회, 채택·수정·거절
- 상담 관리자: 집계 지표와 품질 검토 대상 조회
- 지식 관리자: 문서 등록·비활성화·재처리 요청
- 시스템 운영자: 연계 상태와 오류 로그 조회
- 프로젝트 관리자: 배포 승인 상태와 운영 보고 확인

권한이 없는 사용자는 원문 문서 다운로드, 문서 활성화, 전체 로그 조회를 수행할 수 없습니다. 관리자 권한도 하나의 공용 계정으로 공유하지 않고 사용자 단위로 부여하는 것을 원칙으로 했습니다.

## 운영 상태와 오류 처리
<!--meta: sec=s14; dept=BE|AIAX; level=주니어|시니어; ct_band=중; related=UNIT-SERVE-->
<!--forbid: 대한전자|PRJ-CC-->
실시간 요청은 정상 응답, 근거 부족, 생성 제한, 사용자 입력 오류, 외부 연계 오류, 내부 처리 오류로 구분했습니다. 모든 오류를 동일한 실패 문구로 처리하면 상담사가 재시도해야 하는지 직접 응대해야 하는지 판단하기 어렵기 때문입니다.

처리 원칙은 다음과 같습니다.

- 입력값이 부족하면 필요한 확인 항목을 표시
- 검색 근거가 부족하면 답변 생성 없이 상담사 확인으로 전환
- 생성 영역이 일시적으로 응답하지 않으면 제한된 횟수만 재시도
- 동일 요청이 반복 실패하면 기존 상담 절차로 전환
- 문서 상태가 불명확하면 비활성 문서를 답변 근거로 사용하지 않음
- 부분 성공을 전체 성공으로 기록하지 않음
- 사용자 화면에는 내부 스택 정보나 시스템 경로를 노출하지 않음

AI 기능이 사용 불가능하더라도 기존 상담 업무가 완전히 중단되지 않도록 수동 매뉴얼 조회 경로를 유지했습니다. AI 기능의 장애는 상담 지원 기능 저하로 처리하되, 고객센터의 핵심 상담 채널까지 연쇄적으로 중단시키지 않는 구조를 우선했습니다.

## 평가 데이터셋 구성
<!--meta: sec=s15; dept=DATA|AIAX; level=주니어|시니어; ct_band=상; related=JD-DATA-->
<!--forbid: 대한전자|PRJ-CC-->
평가 데이터셋은 반복 문의, 제품군이 명확한 문의, 조건 확인이 필요한 문의, 문서에 답이 없는 문의, 문서 간 충돌 가능성이 있는 문의, 감정·민원 이관 문의를 포함하도록 구성했습니다. 정답 문장 하나만 두기보다 기대 근거 문서, 필수 포함 조건, 금지 표현, 기대 처리 상태를 함께 정의했습니다.

평가 항목은 다음과 같습니다.

- 올바른 제품군의 문서를 검색했는가
- 답변이 근거 문서의 범위를 벗어나지 않았는가
- 필수 조건과 예외가 누락되지 않았는가
- 근거가 없을 때 "확인 필요"로 처리했는가
- 감정·민원·안전 문의를 상담사에게 이관했는가
- 비활성 문서나 구버전을 우선하지 않았는가
- 개인정보가 답변과 로그에 불필요하게 노출되지 않았는가
- 상담사가 이해할 수 있는 표현으로 작성되었는가

평가셋은 모델 성능만 측정하기 위한 자료가 아니라 문서 품질, 검색 설정, 생성 정책, 화면 표시 방식의 결함을 함께 찾기 위한 기준으로 사용했습니다. 실패 원인이 검색인지, 문서 자체의 모호성인지, 생성 단계의 과도한 추론인지 분리해 기록했습니다.

실제 상담 데이터를 평가에 활용할 때는 개인정보 제거와 사용 범위를 먼저 확인합니다. 특정 상담사의 표현 습관이나 고객의 상세 사연이 그대로 평가셋에 남지 않도록 정제했습니다.

## 테스트 전략과 승인 기준
<!--meta: sec=s16; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->

## 성과지표 정의 및 해석 기준

프로젝트 성과는 자동화율 하나로 판단하지 않았습니다. 높은 자동화율을 목표로 위험 문의까지 자동 처리하면 품질과 고객 신뢰가 악화될 수 있으므로 효율, 정확성, 안전성, 사용성을 함께 확인했습니다.

- 자동 해결률: 자동응답 허용 범위에서 상담사 개입 없이 완료된 비율
- 매뉴얼 오답률: 기준 답변 또는 필수 조건과 불일치한 응답 비율
- 근거 제시율: 답변에 유효한 출처 구간이 연결된 비율
- 근거 부족 전환율: 충분한 근거가 없어 상담사 확인으로 전환된 비율
- 상담사 수정률: 추천 답변이 수정 후 사용된 비율
- 상담사 거절률: 추천 답변이 사용되지 않은 비율
- 위험 문의 이관률: 위험 신호가 확인된 문의가 상담사에게 전달된 비율
- 구버전 참조 건수: 비활성 또는 대체된 문서가 후보에 포함된 건수
- 마스킹 검토 건수: 개인정보 후보 탐지 결과를 추가 검토한 건수

수정률이 높다고 항상 모델 품질이 낮은 것은 아닙니다. 상담사의 말투 조정과 정책 내용 수정은 구분해야 합니다. 마찬가지로 근거 부족 전환율이 일정 수준 존재하는 것은 안전장치가 작동했다는 의미일 수 있으므로, 무조건 낮추는 지표로 사용하지 않았습니다.

교육에서는 기능 사용법보다 AI 답변을 안전하게 검토하는 방법을 우선했습니다. 상담사가 자연스러운 문장을 정확한 답변으로 오해하지 않도록 근거 확인, 조건 확인, 이관 기준을 반복 안내했습니다.

교육 항목은 다음과 같습니다.

- 추천 답변과 확정 답변의 차이
- 근거 문서와 원문 위치 확인 방법
- "확인 필요" 상태의 의미
- 제품군이 불명확할 때 추가 질문하는 방법
- 감정·민원·안전 문의의 즉시 이관 기준
- 수정·거절 사유를 정확히 선택하는 방법
- 개인정보를 불필요하게 입력하지 않는 원칙
- AI 기능이 불가능할 때 기존 절차로 복귀하는 방법

운영자 교육에는 문서 상태 관리, 인덱싱 실패 확인, 권한 관리, 오류 분류, 품질 표본 검토가 포함됩니다. 지식 관리자에게는 구버전 비활성화와 시행일 검증을 별도로 안내했습니다.

운영 이관 시에는 시스템 구성도, 역할별 운영 절차, 문서 갱신 절차, 주요 지표 정의, 오류 유형, 비상 전환 절차, 알려진 제한사항을 전달했습니다. 교육 참석 여부만으로 이관을 완료하지 않고 운영자가 실제 문서 갱신과 오류 확인을 수행할 수 있는지 확인했습니다.

## 제약사항과 알려진 한계
<!--meta: sec=s25; dept=AIAX|BE|DATA; level=주니어|시니어; ct_band=중; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
본 시스템의 답변 품질은 등록된 매뉴얼의 정확성, 최신성, 구조 품질에 영향을 받습니다. 매뉴얼 자체에 조건이 누락되어 있거나 서로 다른 문서가 충돌하면 AI가 이를 독립적으로 해결할 수 없습니다.

주요 한계는 다음과 같습니다.

- 스캔 품질이 낮은 PDF는 숫자와 모델명이 잘못 추출될 수 있음
- 동일 제품의 유사 모델이 많으면 제품군 확인이 추가로 필요함
- 고객이 여러 문제를 한 문장에 섞어 질문하면 근거가 분산될 수 있음
- 신규 정책이 문서로 승인되기 전에는 검색에 반영할 수 없음
- 감정 상태와 민원 위험 분류에는 오탐과 누락 가능성이 존재함
- 생성 답변이 자연스럽더라도 근거가 없으면 사용할 수 없음
- 자동 해결률은 문의 구성과 적용 범위에 따라 달라질 수 있음
- 개인정보 마스킹이 제품 번호나 오류 코드와 충돌할 가능성이 있음

따라서 상담사 검토, 근거 표시, 위험 문의 이관, 문서 승인 체계는 선택 기능이 아니라 시스템의 필수 안전장치로 유지합니다.

## 향후 확장 계획
<!--meta: sec=s26; dept=AIAX|BE|DATA|SALES; level=시니어; ct_band=상; related=PRJ-CC-PUB-->
<!--forbid: 대한전자|PRJ-CC-->
향후 확장은 자동화 범위를 무조건 확대하기보다 현재 적용 영역의 품질과 운영 가능성을 확인한 뒤 단계적으로 검토합니다. 확장 후보는 기술 구현 가능성, 고객사 정책 승인, 개인정보 영향, 상담사 업무 효과를 함께 평가합니다.

검토 가능한 확장 방향은 다음과 같습니다.

- 제품군별 검색 필터와 동의어 사전 고도화
- 상담사 수정 사유를 활용한 지식 품질 개선
- 문서 개정 시 영향받는 대표 질문 자동 점검
- 표와 절차형 문서의 구조 인식 개선
- 근거 문서 간 충돌 탐지와 관리자 알림
- 상담 종료 후 후처리 요약 지원
- 다중 문의를 개별 질문으로 분리하는 기능
- 지식 만료일과 임시 정책 종료 알림
- 관리자용 품질 검토 대기열 개선
- 신규 상담사 교육용 근거 탐색 모드

음성 인식, 상담 요약, 자동 후처리와 같은 기능을 도입할 경우에는 기존 RAG 답변 기능과 별도로 정확도와 개인정보 영향을 평가해야 합니다. 특히 음성 원문은 텍스트 문의보다 더 많은 개인정보를 포함할 수 있으므로 현재 마스킹 정책을 그대로 적용할 수 있다고 가정하지 않습니다.

확장 기능은 운영 중인 상담 흐름을 복잡하게 만들지 않아야 하며, 상담사 화면에 추가되는 정보가 실제 판단 시간을 늘리는지 함께 검증합니다.

## 용어 및 상태 코드 설명
<!--meta: sec=s27; dept=AIAX|BE|DATA; level=주니어; ct_band=하; related=UNIT-RAG|UNIT-SERVE-->
<!--forbid: 대한전자|PRJ-CC-->
- **RAG**: 사용자 질문과 관련된 문서를 먼저 검색한 뒤 그 근거를 사용해 답변을 생성하는 방식입니다.
- **임베딩**: 문장이나 문서의 의미를 수치 벡터로 변환한 표현입니다.
- **벡터DB**: 의미가 유사한 문서 구간을 검색하기 위해 임베딩을 저장하는 데이터베이스입니다.
- **검색 근거**: 답변 생성에 사용된 승인 문서의 특정 구간입니다.
- **환각**: 모델이 제공된 근거에 없거나 사실과 다른 내용을 그럴듯하게 생성하는 현상입니다.
- **마스킹**: 전화번호·주소와 같은 값을 대체 토큰으로 변경해 직접 노출을 줄이는 처리입니다.
- **자동 해결**: 사전에 허용된 문의가 상담사 개입 없이 정해진 절차를 완료한 상태입니다.
- **상담사 확인 필요**: 근거는 있으나 조건 확인 또는 사람의 판단이 필요한 상태입니다.
- **근거 부족**: 유효한 문서 구간을 확보하지 못해 답변 확정을 제한한 상태입니다.
- **비활성 문서**: 이력 확인을 위해 보존되지만 현재 답변 근거로 사용할 수 없는 문서입니다.
- **이관**: AI 자동응답을 중단하고 상담사 또는 관리자 판단으로 전달하는 절차입니다.
- **회귀 테스트**: 시스템 변경 후 기존에 정상 동작하던 기능과 품질이 유지되는지 확인하는 테스트입니다.

상태 코드는 기술팀과 운영자가 동일한 의미로 사용해야 합니다. 사용자 화면의 문구와 내부 로그 코드가 다를 수 있으므로 운영 매뉴얼에서 대응 관계를 관리합니다.

프로젝트 완료는 기능 배포만으로 판단하지 않고 승인된 범위의 구현, 평가, 사용자 검증, 운영 이관, 문서 전달이 완료된 상태를 기준으로 했습니다.

주요 완료 산출물은 다음과 같습니다.

- 상담 지원 기능과 연계 API
- 승인 상담 매뉴얼의 검색 인덱스
- 개인정보 마스킹 및 입력 검증 정책
- 상담사·관리자 화면
- 평가 데이터셋과 테스트 결과
- 권한별 운영 절차
- 문서 등록·교체·비활성화 절차
- 상담사 및 운영자 교육 자료
- 운영 지표 정의서

- 배포·회귀 검증 기록

계약 규모와 세부 조건, 고객사 담당자 정보, 개별 승인 서명은 영업팀 및 승인된 관리 자료를 기준으로 합니다. 본 상세판은 기술·운영 관점의 프로젝트 기준 문서이며, 계약서나 장애회고 상세 문서를 대체하지 않습니다.
