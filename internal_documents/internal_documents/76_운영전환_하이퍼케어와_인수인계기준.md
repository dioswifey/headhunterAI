# 운영 전환 — 하이퍼케어와 인수인계 기준
<!--meta: doc=CSM-02; doc_type=playbook; tier=1; topic=CS; disclosure=internal; status=active-->

## 하이퍼케어의 정의와 기간
<!--meta: sec=s1; dept=CNS|BE; level=주니어|시니어; ct_band=중; related=s2|CSM-01#s1-->
하이퍼케어는 공식 오픈 직후 시스템과 사용자 정착 상태를 집중 관찰하고, 초기 결함과 운영 혼선을 단기간에 해소하는 지원 기간입니다. 구축 프로젝트에서는 오픈 안정화 구간으로 적용하며, 운영·유지보수 계약에서는 정상 SLA 운영으로 전환하기 전 별도 집중 지원 구간으로 적용합니다. `오픈(Go-Live)은 끝이 아니라 중간 지점이다.`

하이퍼케어 시작일과 종료일은 오픈 승인 전에 확정합니다. “안정화될 때까지”와 같이 종료일이 없는 표현은 사용할 수 없습니다. 기간을 못 박아야 프로젝트 투입 인력, 운영 당번, 고객 대응 가능 시간, 잔여 예산을 통제할 수 있습니다.

| 적용 규모 | 권장 기간 | 기간 산정 기준 | 예시 |
| --- | ---: | --- | --- |
| 제한 사용자·단일 기능 | 7~14일 | 사용자 50명 이하, 단일 연동 | 부서 단위 오픈 |
| 일반 구축 | 14~28일 | 복수 기능 또는 연동 2~5개 | 지점·사업부 오픈 |
| 복수 조직 롤아웃 | 4~8주 | 단계별 사용자 확대, 다수 배치 | 여러 조직 동시 적용 |
| 복잡한 전사 롤아웃 | 최대 90일 | 전사 적용, 다중 시스템 연동 | 단계별 전사 확산 |

기본 기간은 1~4주입니다. 4주를 초과하는 일정은 시스템 복잡도, 사용자 전환 단계, 연동 수, 배치 주기 등 객관적 사유가 있어야 합니다. 90일 적용은 전사 롤아웃처럼 장기간 집중 관찰이 필요한 경우에 한하며, 단순한 미완료 과제나 인력 부족을 사유로 설정하지 않습니다.

**기간 확정 절차**

1. CNS가 오픈일, 사용자 확대 일정, 고객 핵심 업무일을 확인합니다.
2. BE가 연동 수, 배치 수, 예상 트래픽과 장애 복구 난도를 산정합니다.
3. CNS와 BE가 시작일·종료일을 날짜 단위로 명시합니다.
4. 종료 기준은 s8, 에스컬레이션 경로는 s6 기준으로 연결합니다.
5. 종료일 이후의 지원 체계는 운영 담당 조직과 사전에 구분합니다.

끝나지 않는 하이퍼케어는 구축 인력이 운영 문의에 계속 묶이게 하여 신규 프로젝트 착수와 개발 일정에 손실을 만듭니다. 운영 조직이 책임을 인수하지 못하고 고객도 모든 요청을 긴급 건으로 인식하게 되므로, 우선순위와 SLA 측정이 왜곡됩니다.

기간이 고정되지 않으면 계약에 포함된 공수와 무상 지원 범위를 식별하기 어렵습니다. 추가 개발이 초기 안정화 작업으로 흡수되면서 변경 관리가 누락되고, 담당자 교대 없이 특정 개발자에게 지식과 연락이 집중되는 문제도 발생합니다.

온보딩 전체 흐름과 규모별 기간은 CSM-01을 참조합니다.

## 하이퍼케어 체제 구성과 당번 편성
<!--meta: sec=s2; dept=AIAX|BE|CNS; level=시니어; ct_band=상; related=s1|s3-->
하이퍼케어 체제는 고객 접점을 담당하는 1선과 기술 진단·조치를 수행하는 2선으로 구분합니다. 1선은 문의 접수, 정보 보완, 고객 안내와 상태 추적을 담당하고, 2선은 로그 분석, 데이터 검증, 코드·설정 조치를 담당합니다. 고객이 개발자 개인에게 직접 요청하는 방식은 허용하지 않습니다.

체제 책임자는 오픈 3영업일 전까지 실명 당번표를 확정합니다. 표에는 근무 시간, 주 담당, 백업 담당, 연락 수단과 교대 시각을 기록하며, 휴가·출장이 예정된 인원은 주 담당으로 편성하지 않습니다.

| 역할 | 기본 담당 | 주요 책임 | 백업 기준 |
| --- | --- | --- | --- |
| 하이퍼케어 리드 | CNS 과장 이상 | 상황 총괄, 고객 안내 승인, 우선순위 조정 | CNS 차장 이상 |
| 1선 당번 | CNS | 접수, 필수 정보 확인, 티켓 생성·갱신 | 동일 지점 CNS 1명 |
| 애플리케이션 2선 | AIAX | AI 기능·모델·애플리케이션 진단 | 동일 구성 이해자 1명 |
| 플랫폼 2선 | BE | API·인증·배치·인프라 진단 | 배포 권한 보유자 1명 |
| 데이터 지원 | DATA 또는 지정 분석자 | 데이터 적재·품질·집계 검증 | 쿼리 검토 가능자 1명 |
| 의사결정자 | 담당 부장 | 인력 증원, 고객 고위 담당자 조율 | 지점 부장 1명 |

**당번표 작성 규칙**

- 평일 기본 대응 시간은 `09:00~18:00`으로 설정하고, 교대 인계는 종료 30분 전에 실시합니다.
- 점심시간과 회의 시간에도 1선 연락 가능 인원 1명, 2선 호출 가능 인원 1명을 유지합니다.
- 야간·주말 지원은 계약 또는 오픈 계획서에 명시된 시간대만 편성합니다.
- 야간·주말 상시 대기는 자동 포함하지 않으며, 긴급 호출 대상과 원격 접속 가능 여부를 사전 확인합니다.
- 주 담당이 10분 내 응답할 수 없는 일정이면 백업 담당에게 당번을 이전합니다.
- 동일인이 1선과 2선을 겸임하더라도 티켓 접수와 기술 조치 기록은 분리합니다.

연락 수단 우선순위는 `공식 티켓 → 당번 전화 → 업무용 메신저 → 이메일`입니다. 긴급 상황은 당번 전화로 즉시 알리되, 10분 이내 공식 티켓을 생성합니다. 개인 메신저, 개인 이메일과 구두 전달만으로 작업을 시작해서는 안 됩니다.

필요 공수는 `예정 근무시간 × 역할별 인원 + 대기시간 환산 공수`로 계산합니다. 대기시간은 계약상 전용 대기이면 100%, 복수 업무 병행 호출 대기이면 내부 계획상 25~50%를 적용하며, 실제 작업시간은 별도로 집계합니다.

CNS는 계약서·제안서·작업범위서에서 평일 지원, 야간·주말 대기, 현장 상주, 추가 개발의 포함 여부를 확인합니다. 포함 여부가 불명확하면 영업 담당과 계약 책임자의 서면 확인 전까지 고객에게 무상 제공을 확약하지 않습니다. 계약·청구 영향은 s15를 참조합니다.

## 오픈 직후 집중 관찰 항목
<!--meta: sec=s3; dept=BE|AIAX|DATA; level=시니어; ct_band=상; related=s2|s4-->
오픈 직후 관찰은 시스템이 단순히 실행되는지보다 실제 업무량에서 기준 성능과 품질을 유지하는지를 확인하는 활동입니다. BE·AIAX·DATA는 오픈 전 부하 시험 또는 최근 5영업일 검증 결과의 중앙값을 기준선으로 등록합니다. 운영 이력이 없으면 제안 성능값이 아니라 승인된 성능 시험 결과를 사용합니다.

아래 정상 범위는 별도 계약 기준이 없을 때 적용하는 내부 기본값입니다. 고객 업무의 피크 시간, 일·주·월 배치 주기와 사용자 확대 계획을 반영해 오픈 전에 조정하며, 조정 근거 없이 오픈 후 임계값을 완화하지 않습니다.

| 관찰 항목 | 정상 범위 | 확인 주기 | 담당 |
| --- | --- | --- | --- |
| 처리량 | 시간대별 기준선의 80~120%, 대기열 지속 증가 없음 | 첫 3일 1시간마다, 이후 일 2회 | BE |
| 응답 시간 | p95가 기준선 대비 20% 이내 증가, 승인 상한 이하 | 첫 3일 1시간마다 | BE |
| 오류율 | 전체 요청의 1.0% 이하, 기준선 대비 증가 0.5%p 이하 | 30분마다 | BE |
| 연동 성공률 | 전체 호출의 99.0% 이상 | 1시간마다 | BE |
| 배치 완료 시각 | 승인 완료 시각 이내, 기준선 대비 지연 30분 이하 | 배치 종료 때마다 | DATA |
| AI 응답 품질 | 승인 평가표 통과율 95% 이상 | 일 2회, 회당 30건 표본 | AIAX |
| 로그인·활성 사용자 | 당일 계획 인원의 80% 이상 | 11시·16시·업무 종료 후 | CNS 협조, DATA 집계 |

처리량은 낮을수록 정상으로 판정하지 않습니다. 계획 대비 처리량이 80% 미만이면 사용자 미접속, 입력 데이터 누락, 연동 미호출 가능성을 확인합니다. 처리량이 120%를 초과하면 캠페인·일괄 작업 등 예정된 증가인지 확인하고, 예정되지 않은 반복 호출이나 재시도를 구분합니다.

응답 시간은 평균값만 보지 않고 p95를 사용합니다. 평균이 정상이더라도 일부 사용자의 지연이 누적될 수 있으며, 오류율은 HTTP 오류뿐 아니라 업무 처리 실패와 재시도 후 성공 건도 포함합니다. 연동 성공률은 송신 성공이 아니라 상대 시스템의 정상 수신 확인까지 계산합니다.

AI 응답 품질 표본은 시간대·업무 유형·사용자 그룹이 한쪽으로 치우치지 않게 추출합니다. 정확성, 근거 일치, 금지 응답, 형식 준수 항목을 승인 평가표로 판정하며, 동일 문장의 반복 입력은 표본 수에서 제외합니다.

사용자 로그인·활성 수는 계정 생성 수와 구분합니다. 활성 사용자는 해당일 핵심 업무 흐름을 1회 이상 완료한 사용자로 계산하며, 교육용·관리자·테스트 계정은 제외합니다. 계획 인원 자체가 변경된 경우 고객 책임자의 확인을 받아 분모를 수정합니다.

단일 임계값 초과만으로 원인을 단정하지 않습니다. 처리량 감소와 로그인 감소가 함께 발생했는지, 오류율 증가와 연동 성공률 하락이 연결되는지처럼 시간대가 겹치는 지표를 조합해 진단합니다. 관찰 기록 양식은 s17을 참조합니다.

## 장애·문의 접수 경로와 분류
<!--meta: sec=s4; dept=BE|CNS; level=주니어|시니어; ct_band=중; related=s3|s5-->
장애와 문의는 고객이 기억하기 쉬운 공식 창구 1개로 단일화합니다. 기본 창구는 프로젝트별 서비스 데스크 또는 지정 지원 이메일이며, 전화와 메신저는 긴급 통보 수단으로만 사용합니다. 모든 요청은 공식 티켓 번호가 생성되어야 접수 완료로 인정합니다.

1선 담당자는 접수 즉시 요청 유형을 분류하고, 제목·발생 시각·영향 사용자·대상 기능·재현 절차·화면 또는 로그·요청 결과를 확인합니다. 정보가 부족하더라도 접수를 거절하지 않고 티켓을 만든 뒤 `정보 보완 대기` 상태로 관리합니다.

| 접수 경로 | 사용 범위 | 처리 규칙 | 공식 기록 |
| --- | --- | --- | --- |
| 서비스 데스크 | 모든 장애·문의·요청 | 고객이 직접 등록하고 1선이 분류 | 생성 즉시 인정 |
| 지정 지원 이메일 | 서비스 데스크 접근이 어려운 경우 | 자동 또는 1선이 티켓으로 전환 | 티켓 번호 회신 |
| 당번 전화 | 업무 중단 등 긴급 통보 | 발생 시각과 연락자를 먼저 확인 | 10분 이내 티켓 생성 |
| 업무용 메신저 | 화면 공유·보충 설명 | 단독 접수로 인정하지 않음 | 핵심 내용을 티켓에 전사 |
| 정례회의·구두 전달 | 논의 중 발견된 요청 | 회의 종료 후 1선이 등록 | 회의록 링크와 티켓 연결 |

**요청 분류 기준**

| 분류 | 판정 기준 | 대표 처리 방향 | 잘못 분류했을 때의 문제 |
| --- | --- | --- | --- |
| 장애 | 합의된 기능이 작동하지 않거나 결과가 명백히 잘못됨 | 영향 확인 후 기술 담당 배정 | 일반 문의로 밀려 업무 중단이 장기화됨 |
| 사용 문의 | 기능은 정상이나 사용법·권한·절차 확인이 필요함 | 매뉴얼 안내 또는 사용 지원 | 장애로 집계되어 안정성 지표가 왜곡됨 |
| 데이터 요청 | 조회·추출·정정·재처리 등 데이터 작업이 필요함 | 대상·기간·권한 확인 | 승인 없이 고객 데이터가 처리될 수 있음 |
| 개선 요구 | 기존 기능의 편의성·성능·표현 변경을 요청함 | 요구사항 후보로 분리 | 결함 수정으로 처리되어 개발 범위가 확대됨 |
| 범위 외 요청 | 계약 범위에 없는 신규 기능·연동·업무를 요구함 | 범위 확인 후 별도 검토로 전환 | 무상 작업 약속과 일정 침해가 발생함 |

분류 기준은 고객이 사용한 표현이 아니라 현재 합의된 기능과 결과를 기준으로 적용합니다. 고객이 “오류”라고 표현해도 미교육에 따른 사용 문의일 수 있으며, 작은 문구 변경이라도 신규 로직이 필요하면 개선 요구 또는 범위 외 요청입니다.

동일 현상을 여러 사용자가 접수하면 최초 티켓을 대표 건으로 지정하고 나머지는 연결합니다. 서로 다른 발생 시각, 기능 또는 원인이 확인되면 별도 티켓으로 분리합니다. 중복 티켓을 단순 삭제하면 영향 사용자 수와 발생 빈도를 확인할 수 없으므로 삭제하지 않습니다.

최초 분류가 변경되면 기존 분류, 변경 분류, 변경 사유와 변경자를 남깁니다. 심각도 판정과 응답·복구 목표는 s5, 추가 요구의 검토 절차는 s16을 참조합니다.

## 심각도 등급과 응답·복구 목표
<!--meta: sec=s5; dept=BE|AIAX; level=시니어; ct_band=상; related=s4|s6-->
**판정 원칙**

심각도는 장애 원인이나 수정 난도가 아니라 `영향 범위 × 업무 긴급도`로 산정합니다. 접수 시점에 확인된 사실로 최초 등급을 부여하며, 영향 범위 확대·우회 수단 실패·마감 시각 임박이 확인되면 즉시 상향합니다.

응답은 담당자가 건을 인지하고 고객 또는 1선 담당자에게 접수 사실과 다음 확인 시각을 알린 상태를 의미합니다. 복구는 정상화 또는 고객이 승인한 우회 수단으로 핵심 업무를 재개한 상태이며, 근본 원인 제거 완료와 구분합니다.

**영향 범위 × 업무 긴급도 판정표**

| 영향 범위 | 긴급도 높음: 즉시 업무 필요 | 긴급도 중간: 당일 업무 필요 | 긴급도 낮음: 일정 조정 가능 |
| --- | --- | --- | --- |
| 전사·다수 사용자·핵심 연동 | P1 | P2 | P2 |
| 단일 부서·일부 사용자·주요 기능 | P2 | P2 | P3 |
| 단일 사용자·비핵심 기능 | P3 | P3 | P4 |

영향 범위는 사용자 수뿐 아니라 중단된 업무 흐름을 기준으로 판단합니다. 보안 사고, 데이터 무결성 훼손, 복구 불가능한 데이터 손실 가능성은 현재 사용자 수와 관계없이 P1로 지정합니다.

**P1~P4 등급 및 서비스 목표**

| 등급 | 정의·판정 예 | 최초 응답 목표 | 복구 목표 | 필수 통보 대상 |
| --- | --- | --- | --- | --- |
| P1 치명 | 다수 사용자 서비스 중단, 핵심 업무 전면 불가, 보안 사고, 데이터 손실 진행 | 15분 이내 | 2시간 목표, 최대 4시간 | BE·AIAX 당번, CNS 책임자, 프로젝트 부장, 고객 장애 책임자 |
| P2 높음 | 주요 기능 중단, 단일 부서 업무 불가, 성능 저하로 핵심 업무 지연, 제한적 우회 가능 | 30분 목표, 최대 60분 | 당일 복구 또는 영업 종료 전 승인된 우회 수단 제공 | 기술 리드, CNS 담당자, 고객 운영 책임자 |
| P3 보통 | 일부 기능 오류, 소수 사용자 영향, 핵심 업무를 우회해 계속 수행 가능 | 4시간 이내 | 3영업일 이내 또는 합의 배포일 | 담당 개발자, CNS 담당자, 고객 실무 담당자 |
| P4 낮음 | 사용 문의, 경미한 표시 오류, 개선 요청, 업무 영향 없음 | 익영업일 이내 | 5영업일 이내 처리계획 통보 또는 정기 배포 반영 | 담당자, 요청 고객 사용자 |

목표 시간은 회사가 지정한 접수 경로에 기록된 시각부터 계산합니다. 고객의 필수 정보 제공 대기 시간은 별도로 표시하되 임의로 차감하지 않으며, 중단 여부는 계약 또는 운영 합의 기준에 따릅니다.

**2선 인계 기준**

- P1은 1선 접수와 동시에 2선 기술 담당에게 인계하며, 2선은 인계 시각부터 15분 이내 픽업합니다.
- P2는 원인 확인에 코드·인프라·모델 분석이 필요하면 즉시 인계하며, 2선은 1시간 이내 픽업합니다.
- 픽업은 담당자 지정, 현상 확인, 다음 진단 행동 등록까지 완료된 상태로 판정합니다.
- P3·P4는 1선에서 재현 정보와 로그를 확보한 뒤 담당 백로그로 인계합니다.

최초 등급의 하향은 기술 리드와 CNS 책임자가 공동 승인합니다. 고객에게 이미 통보한 P1·P2는 우회 수단이 실제 운영에서 검증되기 전까지 하향하지 않습니다.

등급이 불명확한 최초 30분에는 더 높은 등급을 적용합니다. 동일 건에 여러 증상이 있으면 가장 높은 업무 영향 하나를 대표 등급으로 사용하고 나머지는 연관 증상으로 연결합니다.

## 에스컬레이션 경로와 경영진 보고 기준
<!--meta: sec=s6; dept=CNS|BE; level=시니어; ct_band=상; related=s5|s7-->
**기본 경로**

에스컬레이션은 담당자 비난이나 단순 참조 추가가 아니라 의사결정 권한과 복구 자원을 상위 단계로 이동하는 절차입니다. 단계가 올라가도 기존 담당자는 이탈하지 않으며, 기술 조치 책임자와 고객 커뮤니케이션 책임자를 분리해 지정합니다.

모든 에스컬레이션에는 발생 시각, 현재 영향, 시행한 조치, 필요한 결정, 다음 갱신 시각을 포함합니다. 사실이 확인되지 않은 원인은 추정으로 표시하며 고객 전달문에 확정 표현을 사용하지 않습니다.

**단계별 경로와 트리거**

| 단계 | 경로 | 진입 트리거 | 단계 책임 |
| --- | --- | --- | --- |
| E1 실무 대응 | 접수 담당 → BE·AIAX 당번 → CNS 담당 | P3·P4 접수 또는 목표 시간 내 해결 가능한 단일 건 | 담당자 지정, 재현·로그 확보, 다음 조치 기록 |
| E2 기술 리드 | 당번 → BE·AIAX 과장 이상 기술 리드 | P1·P2, 2선 분석 필요, 응답 목표의 50% 경과 후 담당 미지정 | 복구계획 확정, 인력 추가, 기술 의사결정 |
| E3 관리 책임 | 기술 리드 → CNS·BE 차장 이상 → 프로젝트 부장 | SLA 목표 초과 예상·발생, 고객 핵심 업무 직접 영향, 고객 에스컬레이션 요청 | 고객 연락, 우선순위 충돌 해소, 부서 간 자원 배정 |
| E4 경영 보고 | 프로젝트 부장 → 담당 임원급 의사결정자 | P1 발생, 동일 원인 반복, 고객 서면 항의, 중대한 보안·계약 위험 | 대외 메시지 승인, 복구·사업 연속성 결정 |

P1은 원인 확인을 기다리지 않고 E2와 E4를 동시에 시작합니다. P2는 복구 전망이 당일을 넘길 가능성이 생기거나 고객 마감 업무를 방해하면 E3로 상향합니다.

**경영진 보고 기준**

| 보고 사유 | 판정 기준 | 보고 기한 | 후속 갱신 |
| --- | --- | --- | --- |
| P1 발생 | 최초 P1 판정 또는 보안·데이터 사고 의심 | 즉시, 최초 인지 후 30분 이내 요약 | 복구 전 60분마다, 복구 후 최종 보고 |
| 동일 원인 반복 | 30일 안에 같은 원인 또는 같은 통제 실패가 3회 발생 | 3번째 건 확인 후 4시간 이내 | 재발방지안 승인 시 종료 |
| 고객 서면 항의 | 공문·이메일·협업도구에서 책임자 조치를 공식 요구 | 수신 후 2시간 이내 | 고객 회신과 시정계획 확정 시 갱신 |
| 중대한 일정·계약 영향 | 오픈·마감 일정 지연 또는 위약 위험이 현실화 | 확인 후 4시간 이내 | 영향 변경 시마다 갱신 |

고객은 SLA 목표를 초과했거나 장애가 핵심 업무에 직접 영향을 주는 경우 에스컬레이션을 요청할 수 있습니다. 이 요청은 내부 심각도와 무관하게 E3로 등록하며, 차장 이상 관리자는 요청 접수 후 24시간 이내 고객 책임자에게 직접 연락해야 합니다.

고객 연락에서는 현재 영향, 복구 진행, 다음 통보 시각, 고객 측 필요 조치만 확정합니다. 원인·배상·계약 책임은 승인 전 약속하지 않으며 관련 판단은 해당 계약 절차로 넘깁니다.

에스컬레이션 종료는 복구만으로 자동 처리하지 않습니다. 고객 통보 완료, 잔여 위험의 담당자 지정, 다음 업데이트 불필요에 대한 관리 책임자 확인까지 갖춰야 종료합니다.

## 일일 점검 회의 운영
<!--meta: sec=s7; dept=CNS|BE|AIAX; level=주니어|시니어; ct_band=중; related=s6|s8-->
**운영 원칙**

하이퍼케어 기간에는 영업일마다 15분 일일 점검 회의를 실시합니다. 기본 시각은 오전 9시 30분이며, 고객의 핵심 배치가 야간에 끝나는 경우 완료 후 60분 이내로 고정합니다.

회의는 장애 원인 분석이나 설계 토론을 수행하는 자리가 아닙니다. 15분 안에 우선순위와 담당자를 확정하고, 5분 이상 논의가 필요한 건은 별도 세션으로 분리합니다.

**15분 표준 아젠다**

| 순서 | 시간 | 확인 내용 | 산출 결과 |
| --- | --- | --- | --- |
| 1. 전일 발생 건 | 0~4분 | 신규 건수, P1~P4 등급, 복구 여부, 재발 여부 | 사실관계와 등급 확정 |
| 2. 미해결 건 | 4~8분 | 현재 상태, 차단 요인, 목표 시각, 지원 필요사항 | 건별 담당자·완료 예정 시각 |
| 3. 오늘 위험 | 8~11분 | 배포, 배치, 데이터 적재, 고객 주요 업무 일정 | 예방 조치와 감시 담당 |
| 4. 고객 전달 사항 | 11~14분 | 공지할 변경·제약·요청사항, 표현 승인 필요 여부 | 전달 담당자와 발송 시각 |
| 5. 액션 확인 | 14~15분 | 신규 액션의 담당·기한 낭독 | 누락 없는 액션 목록 |

필수 참석자는 CNS 회의 진행자, BE 운영 담당, AIAX 운영 담당입니다. 관련 건이 없더라도 각 팀에서 최소 1명이 참석하며, 의사결정이 필요한 날에는 과장 이상 기술 리드를 호출합니다.

진행자는 회의 시작 전에 현황판의 등급, 담당자, 목표 시각을 확인합니다. 참석자는 상태를 `완료·진행·차단` 중 하나로 말하고, 진행 상태만 설명한 채 완료 시각을 제시하지 않는 보고는 인정하지 않습니다.

**내부 회의와 고객 합석 회의의 차이**

| 구분 | 내부 일일 회의 | 고객 합석 회의 |
| --- | --- | --- |
| 참석 | CNS·BE·AIAX 필수 인원 | 내부 필수 인원과 고객 운영 책임자 |
| 정보 범위 | 원시 로그, 기술 가설, 인력·우선순위 충돌 | 확인된 영향, 복구 전망, 고객 행동 필요사항 |
| 표현 방식 | 가설과 대안을 자유롭게 검토 | 미확정 원인은 가설로 명시하고 책임 추정 금지 |
| 의사결정 | 담당·자원·기술 우선순위 결정 | 고객 일정, 우회 수단, 공지 범위 합의 |
| 권장 빈도 | 하이퍼케어 전 영업일 | 기본 주 2회, P1 발생 시 복구까지 매일 |

고객 합석일에도 내부 회의를 생략하지 않습니다. 내부 점검을 먼저 10분 진행한 뒤 고객 회의를 별도 15분으로 열어 미검증 정보와 내부 인력 논의를 제거합니다.

회의 종료 후 30분 이내에 액션 담당자와 기한을 공유합니다. 전일 액션이 기한을 넘기면 자동으로 다음 회의 첫 번째 미해결 건에 배치하며, P1·P2는 일일 회의를 기다리지 않고 즉시 처리합니다.

오픈(Go-Live)은 끝이 아니라 중간 지점입니다. 일일 회의의 종료 여부는 일정 경과가 아니라 운영 안정성과 인수인계 준비 상태로 판단합니다.

## 하이퍼케어 종료 기준
<!--meta: sec=s8; dept=CNS|BE; level=시니어; ct_band=상; related=s7|s9-->
**종료 판정 원칙**

하이퍼케어는 예정 종료일 도달만으로 끝나지 않습니다. 정량 기준, 운영 준비, 고객 확인을 모두 충족한 뒤 종료 심사 대상으로 올리며 하나라도 미충족이면 자동 종료하지 않습니다.

판정 범위는 실제 오픈된 기능과 연동만 포함합니다. 아직 오픈하지 않은 후속 범위는 별도 관리하되, 현재 운영 범위에 영향을 주는 공통 인프라·데이터 의존성은 제외할 수 없습니다.

**종료 기준 체크리스트**

| 구분 | 필수 기준 | 증빙 | 판정 |
| --- | --- | --- | --- |
| P1 안정성 | 최근 10일 연속 P1 무발생 | 장애 이력과 모니터링 기록 | 0건일 때 충족 |
| P2 안정성 | 최근 5영업일 연속 P2 무발생 | 문의·장애 관리대장 | 0건일 때 충족 |
| 미해결 건 | P3 최대 2건, P4 최대 5건, P1·P2 0건 | 건별 담당·기한·우회 수단 | 상한 이내이고 무담당 건 0건 |
| 운영지표 | 합의된 가용성·배치·처리 성공 기준을 5영업일 연속 충족 | 시스템 측정값 | 모든 필수 지표 충족 |
| 운영 문서 | 필수 운영 문서와 최신 구성정보 작성률 100% | 승인된 문서 링크 | 누락·임시본 0건 |
| 담당자 숙련도 | 장애 접수, 우회, 재기동, 연락망 시나리오 평가 80점 이상 | 교육 결과와 실습 기록 | 지정 담당자 전원 통과 |
| 지식 이전 | 운영 담당자가 감독 없이 실제 또는 모의 티켓 1건 처리 | 처리 기록 | 재작업 없이 완료 |
| 고객 확인 | 종료일, 잔여 과제, 정상 운영 전환을 서면 승인 | 이메일·공문·협업도구 승인 | 고객 책임자 승인 확보 |

P3 잔여 건은 핵심 업무에 직접 영향을 주지 않고 검증된 우회 수단이 있어야 합니다. P4 잔여 건도 담당자, 완료 예정일, 고객 통보 여부가 없으면 미해결 상한과 관계없이 종료할 수 없습니다.

운영 문서는 운영 절차서, 구성·연동 목록, 모니터링 기준, 백업·복구 절차, 연락망, 알려진 오류와 우회 방법을 포함합니다. 문서 구성과 승인본 기준은 이 문서의 s10을 적용합니다.

숙련도 평가는 문서 위치를 아는지만 묻지 않습니다. 운영 담당자가 경보 확인부터 등급 판정, 담당 호출, 고객 통보 초안 작성까지 정해진 순서로 수행해야 통과합니다.

**기준 미충족 시 선택지**

| 선택지 | 적용 가능 조건 | 필수 조치 |
| --- | --- | --- |
| 보완 후 재심사 | 2영업일 안에 문서·교육·경미한 결함 보완 가능 | 미충족 항목 수정 후 전체 체크리스트 재확인 |
| 하이퍼케어 연장 | 안정성 관찰기간 부족, P1·P2 잔존, 운영 역량 미확보 | 새 종료 예정일과 보완 책임자 지정 |
| 조건부 종료 | P4만 잔존하고 고객이 위험과 완료일을 서면 수용 | 예외 목록, 담당자, 기한을 종료 승인서에 명시 |
| 범위별 종료 | 독립 운영 가능한 일부 기능만 기준 충족 | 종료 범위와 잔류 범위의 경계·지원 경로 분리 |
| 제한 운영·복구 | P1·P2 재발 위험이 높거나 데이터 안전성 미확보 | 신규 사용 확대 중단과 안전 상태 복귀 결정 |

조건부 종료에는 P1·P2, 보안 취약점, 데이터 정합성 문제를 포함할 수 없습니다. 고객이 구두로 동의했더라도 서면 확인 전까지 하이퍼케어 상태를 유지합니다.

연장·종료에 따른 계약 및 청구 처리는 CSM-02 s15를 참조합니다. 추가 요구로 판정된 항목은 기존 결함과 섞지 않고 CSM-02 s16 절차로 넘깁니다.

## 종료 심사 회의와 승인
<!--meta: sec=s9; dept=CNS; level=시니어; ct_band=중; related=s8|s10-->
오픈(Go-Live)은 끝이 아니라 중간 지점입니다. 종료 심사는 집중 지원 체제를 해제하고 운영 담당 조직이 책임을 인수해도 되는지를 증거로 판정하는 의사결정 회의입니다.
회의는 목표 종료일 2영업일 전에 개최하며, 자료 기준 시점은 회의 전일 18시입니다. 미제출 자료가 하나라도 있으면 판정을 보류하지 않고 연장으로 처리합니다.
**소집과 참석자**
CNS PM이 회의를 소집하고 의사결정권자가 참석 가능한 45분을 확보합니다.
| 참석 구분 | 필수 참석자 | 회의 역할 |
| --- | --- | --- |
| 주관 | CNS PM 또는 차장 이상 대리자 | 자료 취합, 안건 진행, 판정안 제시 |
| 기술 | AIAX·BE 기술 리드 | 기술 안정성 확인, 잔여 기술 위험 승인 |
| 운영 | 내부 유지보수 책임자 또는 고객 운영 책임자 | 운영 수용성, 문서·지식 이전 완료 확인 |
| 고객 | 고객 프로젝트 책임자와 운영 담당자 각 1명 | 업무 영향과 운영 전환 가능 여부 확인 |
| 선택 | SALES 담당자 | 계약 범위 또는 상업적 쟁점이 있는 경우 사실 확인 |
고객 필수 참석자가 불참하면 내부 가판정만 기록하며, 고객 확인 전에는 종료 승인 효력이 발생하지 않습니다.
**심사 자료**
CNS PM은 자료별 작성자와 검수자의 확인 상태를 한 장의 심사 체크시트로 제출합니다.
| 심사 자료 | 필수 내용 | 제출 책임 |
| --- | --- | --- |
| 종료 기준 체크시트 | CSM-02 s8 항목별 충족 여부와 근거 링크 | CNS PM |
| 오픈 후 운영 실적 | 관찰 기간, 정상 처리 건수, 실패·재처리 내역 | BE·AIAX 기술 리드 |
| 장애·문의 현황 | 미종결 건, 재발 건, 고객 영향과 현재 상태 | CNS PM |
| 운영 인수인계 패키지 | 문서 목록, 버전, 운영 조직 수령 확인 | BE·AIAX 기술 리드 |
| 잔여 과제 목록 | 영향, 우회 방법, 담당, 기한, 해결 계획 | 과제 담당 부서 |
| 지식 이전 결과 | 교육 이력과 운영 담당자의 독립 처리 증거 | 운영 인계 책임자 |
자료의 상태값은 `충족·미충족·해당 없음`만 사용하며, 해당 없음에는 승인자와 사유를 남깁니다.
**판정과 승인**
판정은 다수결이 아니라 필수 증거와 운영 수용 여부를 기준으로 CNS PM이 제안하고 승인권자가 확정합니다.
| 판정 | 적용 기준 | 승인 후 후속 |
| --- | --- | --- |
| 종료 | 필수 기준 전부 충족, 인계 불가 이슈 0건 | 집중 지원 종료일 확정, 운영 조직에 책임 이전 |
| 조건부 종료 | 업무 중단 위험이 없는 보완 항목만 존재 | 5영업일 이내 보완 기한과 검증자를 지정하고 운영 전환 |
| 연장 | 필수 자료 누락, 운영 독립 처리 실패 또는 인계 불가 이슈 존재 | 기존 체제를 유지하고 CSM-02 s14에 따라 연장 결정 |
종료와 조건부 종료는 CNS 부장이 승인하며, 연장은 CNS 부장과 주 수행 부서인 BE 또는 AIAX 부장이 공동 승인합니다.
고객 확인은 회의록의 `판정·조건·책임 이전 시각`에 대한 이메일 회신 또는 전자결재 승인으로 받으며, 구두 동의는 인정하지 않습니다.
조건부 종료의 보완 항목이 기한 내 완료되지 않으면 다음 영업일부터 연장으로 전환하고 승인권자에게 재상신합니다.
이견은 회의록에 발언자·근거·최종 결정 사유를 기록하며, 승인본과 고객 확인 증적은 프로젝트 저장소에 함께 보관합니다.

## 운영 인수인계 문서 구성
<!--meta: sec=s10; dept=BE|AIAX|CNS; level=시니어; ct_band=상; related=s9|s11-->
운영 인수인계 문서는 운영 담당자가 구축 인력의 구두 설명 없이 시스템 상태를 확인하고 정규 작업과 1차 대응을 수행할 수 있도록 구성합니다.
패키지는 구축 프로젝트와 구축 후 운영·유지보수 계약 모두에 적용합니다. 유지보수 계약이 없는 단건 구축은 고객 운영 조직을 수령자로 지정하고, 내부 보관본의 책임 부서를 CNS로 지정합니다.
**패키지 구성 원칙**
최상위 인덱스 문서 한 개에서 모든 문서의 위치, 버전, 소유자와 열람 권한을 확인할 수 있어야 합니다.
| 문서 | 포함 내용 | 작성자 | 검수자 |
| --- | --- | --- | --- |
| 시스템 구성도 | 서비스·서버·네트워크·데이터 저장소·외부 연동 관계 | BE 또는 AIAX 대리 이상 | 해당 부서 과장 이상 |
| 운영 절차서 | 기동·중지·배포·점검·백업·복구의 실행 순서 | BE 운영 담당 | BE 기술 리드 |
| 장애 대응 절차 | 탐지 지점, 초기 진단, 격리·복구 순서, 증적 위치 | BE·AIAX 담당자 | CNS PM과 기술 리드 |
| 배치·스케줄 목록 | 작업명, 실행 주기, 선후행, 실패 알림, 재실행 조건 | BE·DATA 담당자 | BE 과장 이상 |
| 접근 권한 체계 | 역할별 권한, 신청·승인·회수 경로, 비상 접근 통제 | BE 담당자 | CNS PM과 고객 보안 담당 |
| 연락 체계 | 업무별 1차·2차 연락 역할, 가용 시간, 대체 담당 | CNS PM | 운영 책임자 |
| 알려진 제약 | 기능·성능·환경 제약, 영향 범위, 회피 조건 | AIAX·BE 기술 리드 | CNS PM |
| 모니터링 항목표 | 지표명, 정상 범위, 경보 조건, 확인 화면 | BE·AIAX 담당자 | 운영 책임자 |
| 변경 이력표 | 기준 버전, 배포일, 변경 요약, 승인 증적 링크 | 배포 담당자 | CNS PM |
각 문서는 개인명이 아니라 담당 역할을 소유자로 두고, 연락처 명부에서 현재 담당자를 연결합니다.
**기존 기술 문서 연결 규칙**
설계서, API 명세, 데이터 사전, 모델 카드와 배포 스크립트가 이미 존재하면 내용을 복사하지 않고 인덱스에서 원본을 참조합니다.
참조 항목에는 `문서 ID·저장 위치·기준 버전·최종 검수일·소유 부서`를 기록하며, 원본 변경 시 인수인계 문서가 자동으로 최신 상태를 가리키게 합니다.
운영에 필요한 일부 문단만 별도 복제하는 방식은 원본과의 불일치를 만들므로 금지합니다. 운영 관점의 설명이 필요하면 원본 문서에 해당 절을 추가합니다.
외부 링크와 저장소 경로는 운영 담당자 계정으로 직접 열어 보고, 권한 오류나 만료 링크가 있으면 패키지 검수를 통과시키지 않습니다.
**최소 품질 기준**
문서에는 실행자가 판단해야 할 조건과 실패 시 되돌리기 절차를 포함하며, 단순 화면 캡처만으로 절차를 대체하지 않습니다.
| 검수 항목 | 합격 기준 | 불합격 예시 |
| --- | --- | --- |
| 버전 식별 | 운영 반영 버전과 문서 기준 버전이 일치함 | 최신본 표시만 있고 버전 번호가 없음 |
| 적용 범위 | 운영·검증·개발 환경을 구분함 | 환경 구분 없이 공통 절차로 기재함 |
| 책임 소재 | 작업자·승인자·문의 역할이 지정됨 | 개인 이름만 있고 대체 역할이 없음 |
| 실행 증거 | 최근 30일 이내 검증 일시와 결과가 있음 | 작성자의 경험만으로 정상이라고 표시함 |
| 보안 통제 | 비밀값은 보안 저장소 위치만 안내함 | 암호·토큰·개인키가 문서에 평문 기재됨 |
단건 구축은 고객이 실제 사용하는 절차와 제약을 중심으로 구성하고, 내부 개발 과정의 임시 자료는 제외합니다.
운영·유지보수 계약은 반복 점검, 배치 실패 처리, 권한 회수와 변경 이력까지 운영 패키지에 포함합니다.
운영 책임자가 인덱스의 전체 링크를 열고 핵심 절차 2건을 재현한 결과를 남겨야 문서 인수를 완료합니다.

## 운영 담당 조직으로의 지식 이전
<!--meta: sec=s11; dept=BE|AIAX; level=시니어; ct_band=상; related=s10|s12-->
지식 이전은 문서 전달이 아니라 운영 담당자가 관찰, 실행, 복구와 보고를 독립적으로 수행하도록 만드는 실습 과정입니다. 대상은 내부 유지보수 조직과 고객 운영 조직이며 역할별로 교육 기록을 분리합니다.

잔여 과제는 운영 전환 시점까지 완료되지 않았지만 고객 업무를 안전하게 지속하면서 계획된 기한 안에 해소할 수 있는 항목만 인계합니다. 개발 편의를 위해 미완료 작업을 운영 조직에 넘기는 것은 허용하지 않습니다.
목록에는 결함, 설정 보완, 문서 보완과 기술 부채를 등록합니다. 계약 범위를 벗어난 추가 요구는 잔여 과제로 섞지 않고 CSM-02 s16에 따라 처리합니다.

이슈 하나당 한 행과 하나의 추적 번호를 사용하며, 여러 원인이나 해결 계획을 한 건으로 합치지 않습니다.

**우회 방법이 없는 이슈**
우회 방법이 없는 이슈는 심각도와 발생 빈도에 관계없이 운영 조직에 인계하지 않습니다.
해당 이슈는 하이퍼케어 안에서 해결·검증하거나 종료 판정을 연장으로 변경하며, 연장 절차는 CSM-02 s14를 적용합니다.
우회 방법은 운영 담당자가 30분 이내 시작할 수 있고, 추가 장애·보안 약화·데이터 불일치를 만들지 않아야 합니다.
서비스 재시작 반복, 검증되지 않은 데이터 수정, 개인 계정 공유와 고객의 수작업 상시 부담은 유효한 우회 방법으로 인정하지 않습니다.
**인계 후 관리**
승인된 잔여 과제는 운영 추적 도구에 등록하고 원래 추적 번호, 해결 기한, 검증 담당자를 유지합니다.
고객 확인은 알려진 이슈 목록의 버전과 영향·우회 방법을 명시한 이메일 회신 또는 전자결재로 받습니다.
기한 변경은 담당자 단독으로 처리하지 않으며 CNS PM과 운영 책임자의 승인 사유를 변경 이력에 남깁니다.
완료 처리는 수정 배포만으로 인정하지 않고, 운영 환경 검증 증거와 고객 영향 해소 확인이 모두 등록된 시점에 수행합니다.

## SLA 적용 시작 시점과 측정 기준
<!--meta: sec=s13; dept=BE|CNS; level=시니어; ct_band=상; related=s12|s14-->
SLA는 원칙적으로 하이퍼케어 종료 심사에서 종료가 승인된 날의 다음 영업일 00:00부터 적용합니다. 계약서가 오픈일, 검수일 또는 유지보수 개시일을 별도로 정한 경우에는 계약서의 기산일을 우선합니다. 승인 지연만으로 SLA 기산일을 소급 변경하지 않습니다.

하이퍼케어 기간의 응답·복구 실적은 운영 준비도 검증 자료로 집계하지만, 계약상 SLA 실적과 혼합하지 않습니다. 단, 계약서가 오픈 즉시 SLA 적용을 명시한 경우에는 하이퍼케어와 SLA를 병행 측정하며 보고서에서 두 구간을 분리합니다.

**적용 시작일 판정**

| 계약·전환 상태 | SLA 기산일 | 판정 책임 |
| --- | --- | --- |
| 종료 승인일이 계약상 유지보수 개시일보다 빠름 | 계약상 유지보수 개시일 | CNS |
| 종료 승인일이 계약상 개시일과 같거나 늦음 | 종료 승인 다음 영업일 | CNS·BE |
| 계약서에 오픈 즉시 적용이 명시됨 | 공식 오픈 시각 | CNS |

**측정 시계와 산식**

유효 응답은 자동 접수 알림이 아니라 담당자가 영향 범위, 심각도, 다음 안내 예정 시각을 전달한 경우로 한정합니다. 업무시간형 계약의 기본 측정창은 평일 09:00~18:00이며 토·일요일과 법정공휴일을 제외합니다. 24×7 측정은 계약서에 명시된 서비스와 심각도에만 적용합니다.

가용성은 `가용성(%) = (예정 서비스 분 - 귀책 중단 분) ÷ 예정 서비스 분 × 100`으로 계산합니다. 여러 장애가 중첩되면 동일 시간대를 한 번만 차감하며, 부분 기능 장애는 계약서에 정의된 기능별 가중치가 있을 때만 환산합니다.

**제외 시간 인정 기준**

- 계획 점검은 계약상 사전 통지기한을 지키고 승인된 점검창 안에서 수행한 시간만 제외합니다.

- 제3자 장애는 외부 서비스 상태 기록, 발생·복구 시각 및 영향 경로가 확보된 경우에만 제외합니다.
- 원인이 불명확하거나 공동 귀책인 시간은 임의 제외하지 않고 BE 부장과 CNS 부장이 판정합니다.

## 하이퍼케어 연장 조건
<!--meta: sec=s14; dept=CNS|BE; level=시니어; ct_band=중; related=s13|s15-->
하이퍼케어는 기간이 고정된 집중 지원 체제이므로 미결 항목이 있다는 이유만으로 자동 연장하지 않습니다. 연장은 안정화 판단에 필요한 관찰 기간이 부족하거나 종료 기준을 충족하지 못한 경우에만 사용하며, 종료 예정일 3영업일 전까지 결정합니다.

오픈(Go-Live)은 끝이 아니라 중간 지점입니다. 다만 이 원칙을 무기한 집중 지원의 근거로 사용해서는 안 되며, 연장안에는 미충족 기준, 추가 관찰 항목, 책임자와 새 종료일을 반드시 명시합니다.

| 중대 장애 안정성 미확보 | 최근 5영업일 내 P1 또는 동일 원인 P2 재발 | 해결된 단발성 P3·P4 |
| 핵심 업무 검증 부족 | 필수 배치·마감 주기를 1회도 정상 완료하지 못함 | 고객의 선택적 기능 미사용 |
| 성능 변동 지속 | 합의 임계값 초과가 2영업일 이상 반복됨 | 기준에 없던 성능 상향 요구 |
| 단계적 전사 롤아웃 | 다음 사용자군 전환이 기존 계획에 포함됨 | 신규 조직을 뒤늦게 범위에 추가 |
| 인수 조직 수용 불가 | 필수 운영권한·모니터링·당번 중 하나가 미완료됨 | 단순 문서 표현 수정 |

**연장 단위와 한도**

| 구분 | 1회 연장 단위 | 기본 최대 횟수 | 총기간 상한 |
| --- | --- | --- | --- |
| 일반 구축 | 7일 | 2회 | 최초 기간 포함 56일 |
| 다지점·다단계 오픈 | 14일 | 2회 | 최초 기간 포함 84일 |
| 전사 복합 롤아웃 | 14일 | 2회 | 최초 기간 포함 90일 |
| 운영·유지보수 변경 오픈 | 7일 | 1회 | 최초 기간 포함 28일 |

상한을 넘는 요청은 하이퍼케어 연장이 아니라 운영체제 재설계 대상으로 봅니다. 예외적으로 90일을 초과하려면 해당 지점 부장, CNS 부장, BE 부장 및 고객 책임자의 서면 승인이 모두 필요합니다.

**승인 주체**

| 의사결정 | 제안 | 내부 승인 | 고객 확인 |
| --- | --- | --- | --- |
| 1차 연장 | CNS PM | CNS 과장 이상·BE 과장 이상 | 고객 운영책임자 |
| 2차 연장 | CNS 차장 이상 | CNS 부장·BE 부장 | 고객 의사결정자 |
| 부분 종료 | CNS PM·BE 운영책임자 | 양 부서 차장 이상 | 대상 서비스 책임자 |
| 90일 초과 예외 | CNS 부장 | 해당 지점 부장 | 고객 의사결정자 |

연장 대신 서비스, 지점 또는 기능 단위의 부분 종료를 선택할 수 있습니다. 종료된 단위는 정상 운영으로 전환하고 미충족 단위에만 하이퍼케어 당번과 점검을 유지합니다.

범위 축소 종료는 비핵심 기능을 운영 대상에서 임시 제외하고 핵심 업무만 종료 승인하는 방식입니다. 제외 기능의 재개 조건과 목표일을 기록하지 못하면 범위 축소 종료를 승인하지 않습니다.

## 연장·종료가 계약·청구에 미치는 영향
<!--meta: sec=s15; dept=CNS|SALES; level=시니어; ct_band=중; related=s14|s16-->
연장 또는 종료의 계약·청구 영향은 하이퍼케어가 계약 범위, 무상 안정화 범위, 별도 유상 지원 중 어디에 정의되어 있는지에 따라 판정합니다. CNS는 투입을 먼저 약속하지 않고 계약서, 제안서, 작업범위서, 검수 조건의 문구를 동일한 기준일로 대조합니다.

하이퍼케어 종료는 구축 검수, 유지보수 개시 또는 청구 조건과 자동으로 동일하지 않습니다. 계약 문구가 서로 다른 사건을 기준으로 삼는 경우 SALES가 고객과 기준일을 확인하고, CNS는 승인 기록에 그 결과를 반영합니다.

**계약 유형별 처리 원칙**

| 계약 상태 | 연장 시 처리 | 종료 시 확인 |
| --- | --- | --- |
| 최초 하이퍼케어가 구축대금에 포함됨 | 포함 기간·인력 한도까지 기존 범위로 처리 | 검수·잔금 조건과 별도인지 확인 |
| 기간만 포함되고 투입 한도가 명시됨 | 한도 초과 예상 시 추가 승인 전 투입 금지 | 실제 투입량과 잔여 한도 확정 |
| 별도 유상 하이퍼케어 계약임 | 계약 단위에 따라 연장 여부 확인 | 종료일 기준 제공 실적 확정 |
| 계약에 하이퍼케어 문구가 없음 | 무상 제공으로 추정하지 않음 | SALES가 상업 조건 확인 |
| 공급자 귀책으로 종료 기준 미달 | 추가 청구를 선제 제안하지 않음 | 귀책 판정과 시정 완료 근거 확보 |
| 고객 요청으로 범위·기간 증가 | 기존 범위와 증가분을 분리 | 고객 요청 및 승인 시각 확인 |

추가 투입의 견적·승인 경로는 PRP-xx를 참조합니다. 청구 시점, 세금계산서, 매출 인식 및 정산 처리는 FIN-xx를 참조합니다.

**SALES 사전 확인 항목**

- 계약상 하이퍼케어 시작일, 종료일, 포함 일수와 지원시간을 확인합니다.
- 포함 인원, 역할, 원격·현장 구분 및 야간·휴일 지원 조건을 확인합니다.
- 연장 옵션, 단가표, 변경계약 필요 여부와 고객 승인권자를 확인합니다.
- 검수일, 유지보수 개시일, 잔금 또는 월 과금 개시일의 연동 여부를 확인합니다.
- 고객 귀책 지연, 제3자 지연, 공급자 귀책의 비용 처리 조항을 확인합니다.

**CNS 사전 확인 항목**

- 연장 사유가 기존 결함인지 신규 요구인지 티켓별로 구분합니다.
- 최초 계획 대비 추가 인력의 역할, 인일, 기간과 현장 방문 횟수를 산출합니다.
- 부분 종료 시 정상 운영 전환 범위와 하이퍼케어 잔류 범위를 분리합니다.
- 고객 요청, 내부 승인 및 종료 심사 결과가 문서로 남아 있는지 확인합니다.
- 승인 전 추가 작업이 시작되지 않도록 작업계획과 당번표의 적용일을 통제합니다.

무료 연장, 할인 또는 조기 종료에 따른 감액을 CNS가 구두로 확정해서는 안 됩니다. 고객에게는 기술적 필요 기간과 투입 가정만 제시하며 상업 조건은 SALES 확인 후 전달합니다.

종료일이 변경되면 SALES는 계약상 통지기한 안에 고객 확인을 확보합니다. 변경이 청구에 영향을 줄 가능성이 있으면 종료 승인서에 `청구 영향 검토 중`으로 표시하고, 상업 검토가 끝나기 전에는 영향 없음으로 단정하지 않습니다.

## 하이퍼케어 중 발견된 추가 요구 처리
<!--meta: sec=s16; dept=CNS; level=시니어; ct_band=상; related=s15|s17-->
하이퍼케어 중에는 사용자가 기대한 결과와 실제 결과의 차이를 모두 장애로 접수하는 경향이 있습니다. CNS는 접수 명칭이 아니라 합의된 요구사항, 정상 동작 기준, 재현 결과를 기준으로 결함과 개선 요구를 구분합니다.

초기 분류가 불명확하면 서비스 복구에 필요한 최소 조치만 수행하고 영구 변경은 보류합니다. 고객 업무를 살리는 임시 조치가 신규 기능의 무상 제공이나 범위 승인으로 해석되지 않도록 티켓에 목적과 종료 조건을 기록합니다.

**구분 질문**

1. 계약서·요구사항·인수 기준에 해당 동작이나 산출물이 명시되어 있습니까?
2. 동일 입력과 권한에서 합의된 결과가 재현되지 않습니까?
3. 오픈 전 승인된 설정을 변경하지 않아도 발생합니까?
4. 요청이 기존 기능의 복구입니까, 결과·절차·사용자 범위의 변경입니까?
5. 신규 데이터, 화면, API, 모델, 권한 또는 외부 시스템 연동이 필요합니까?
6. 요청을 반영하지 않으면 핵심 업무가 중단됩니까, 아니면 수작업 우회가 가능합니까?
7. 요청자가 현업 사용자인지 계약 범위 승인권자인지 확인했습니까?

**처리 경로 판정**

| 경로 | 필수 판정 기준 | 처리 한도 | 승인 |
| --- | --- | --- | --- |
| 즉시 처리 | 합의 사양 위반 또는 보안·데이터 무결성 위험 | 우회·복구를 우선하고 변경 이력 기록 | BE/CNS 당번 책임자 |
| 운영 변경 요청 | 기존 기능의 설정·임계값·스케줄 변경 | 2인일 이하, 구조 변경 없음 | 고객 운영책임자·CNS 과장 |
| 별도 과제화 | 신규 기능·사용자군·데이터·연동·모델 변경 | 2인일 초과 또는 설계 검토 필요 | CNS 차장 이상 |
| 정보 보완 후 재판정 | 재현 조건·기대 결과·승인 근거 부족 | 자료 수신 전 구현 금지 | CNS PM |

즉시 처리 경로에서도 요구사항 자체가 바뀌면 작업을 중단하고 재분류합니다. 장애 우회를 위해 추가한 임시 설정은 만료일을 두며, 만료일까지 정식 변경 승인이 없으면 원복합니다.

운영 변경 요청은 기존 운영 범위 안에서 되돌릴 수 있고 데이터 구조, 보안 경계, API 계약, 모델 학습 조건을 바꾸지 않는 경우에만 사용합니다. 이 조건 중 하나라도 충족하지 않으면 작업량과 무관하게 별도 과제로 분류합니다.

**조용한 범위 확대의 전형적 경로와 차단 장치**

| 발생 경로 | 위험 징후 | 차단 장치 |
| --- | --- | --- |
| 장애 해결 중 화면·보고서 항목 추가 | “같이 고쳐 달라”는 구두 요청 | 결함 수정과 추가 항목을 티켓 분리 |
| 임시 데이터 보정의 상시 업무화 | 같은 수작업을 2회 이상 요청 | 반복 작업 중지 후 운영 변경 심사 |
| 교육 질문이 신규 프로세스 설계로 확대 | 사용자 역할·승인 단계가 새로 등장 | 교육 기록 종료 후 별도 요구 등록 |
| 특정 부서 지원이 전사 적용으로 확대 | 미합의 사용자·지점이 접속 요청 | 승인된 사용자 목록으로 접근 통제 |
| 성능 조정이 인프라 증설로 확대 | 용량·동시접속 기준이 상향됨 | 기존 기준선과 추가 요구를 분리 산정 |

모든 추가 요구에는 요청자, 요청 시각, 업무 영향, 계약 근거, 예상 인일, 판정 경로를 기록합니다. 고객이 긴급성을 강조하더라도 승인되지 않은 신규 범위를 하이퍼케어 안정화 작업에 묶어 처리하지 않습니다.

## 기록·보고 양식
<!--meta: sec=s17; dept=CNS|BE; level=주니어; ct_band=중; related=s16|s18-->
하이퍼케어 기록은 일일 운영 사실과 종료 판단의 근거를 남기는 통제 자료입니다. CNS 담당자가 원본을 작성하고, 장애·성능·배포 관련 항목은 BE 또는 해당 기술 담당자가 사실 여부를 확인합니다.

고객 제출본과 내부본은 동일한 이슈 ID를 사용하되 공개 범위를 분리합니다. P1·P2 사건은 일일 보고 시각까지 기다리지 않고 CSM-02 s6의 경로로 즉시 보고합니다.

고객 제출 후 내용 오류를 발견하면 4시간 이내 정정본을 발행하고, 변경 위치·사유·승인자를 배포 메시지와 내부 이력에 함께 기록합니다.

| 기록 유형 | 기본 보관 기간 | 접근 범위 |

계약 또는 법정 보존기간이 더 길면 해당 기간을 우선하며, 지점이 달라도 업무상 필요가 없는 인원에게는 권한을 부여하지 않습니다.

## 회고와 플레이북 개선
<!--meta: sec=s18; dept=CNS|BE|AIAX; level=시니어; ct_band=중; related=s17-->
회고는 하이퍼케어 종료 승인일을 D0으로 하여 D+10영업일 이내 완료합니다. CNS가 진행하고 프로젝트 책임자, 운영 인수자, BE와 AIAX 기술 책임자가 참석하며 필요 시 DATA 담당자를 추가합니다.

회고는 책임자를 찾는 회의가 아니라 오픈 전에 탐지하거나 방지할 수 있었던 조건을 식별하는 회의입니다. 기억에 의존하지 않고 티켓 시각, 배포 이력, 테스트 결과, 교육 기록과 승인 기록을 근거로 판정합니다.

**운영 일정과 산출물**
`자료 동결 → 원인 검토 → 90분 회고 → 개선 과제 확정 → 플레이북 반영`
| 단계 | 기한 | 담당·완료 조건 |
| --- | --- | --- |
| 자료 동결 | D+5영업일 | CNS가 이슈 목록, 지표, 의사결정 이력과 잔여 과제를 하나의 회고 자료로 고정합니다. |
| 사전 검토 | D+7영업일 | BE·AIAX가 기술 사실과 탐지 가능 시점을 확인하고 이견을 주석으로 남깁니다. |
| 회고 회의 | D+10영업일 이내 | CNS가 90분간 진행하며 발견 사항별 근거, 원인, 통제 실패 지점을 합의합니다. |
| 과제 확정 | 회의 후 1영업일 | 소유자·기한·검증 방법이 없는 항목은 과제로 등록하지 않습니다. |

참석자는 회의 전 사실관계 수정 요청을 완료합니다. 회의 중 새로 제기되어 즉시 검증할 수 없는 주장은 `검증 필요`로 분리하고 3영업일 이내 확인 담당자를 지정합니다.

**필수 분석 범주**
| 범주 | 회고 질문 | 발견 판정 기준 |
| --- | --- | --- |
| 예측 가능했던 장애 | 오픈 전 테스트, 로그, 위험대장에 동일·유사 신호가 있었는가 | 신호가 있었으나 조치·승인·관찰 항목으로 연결되지 않았다면 개선 대상으로 판정합니다. |
| 문서 공백 | 담당자가 구두 문의 없이 복구·점검·인계할 수 있었는가 | 절차, 기준값, 권한, 롤백 또는 담당 중 하나라도 누락되면 공백으로 판정합니다. |
| 교육 공백 | 고객 및 운영 담당자가 핵심 업무와 오류 대응을 재현했는가 | 교육 미참석, 실습 미완료, 평가 미통과가 실제 문의·오조작과 연결되면 등록합니다. |
| 운영 통제 공백 | 알림, 당번, 승인 또는 인계가 정해진 시간에 작동했는가 | 담당 불명확, 중복 대응, 무응답 또는 수동 우회가 발생하면 통제 개선으로 분류합니다. |

원인은 `사람의 주의 부족`으로 종결하지 않습니다. 절차·도구·문서·교육·승인 구조 중 재현 가능한 조건까지 내려가며, 고객 책임을 추정하는 문구는 확인된 합의 기록이 없으면 사용하지 않습니다.

**개선 과제 등록과 기술 이관**
| 우선순위·유형 | 완료 기한 | 등록 및 이관 기준 |
| --- | --- | --- |
| 긴급 통제 개선 | 5영업일 | 동일 장애의 즉시 재발 가능성이 있으면 임시 통제와 영구 조치를 분리 등록합니다. |
| 주요 플레이북 개선 | 10영업일 | 두 프로젝트 이상에 적용 가능한 절차·체크리스트 변경은 CNS 소유 개선대장에 등록합니다. |
| 일반 개선 | 30일 | 영향이 제한적이지만 반복 가능하면 다음 적용 프로젝트와 검증 지표를 지정합니다. |
| 기술 과제 | 위험도별 기한 적용 | `회고 개선대장 → 기술 과제 트래커 → 담당 저장소의 기존 기술 문서 변경 절차`로 이관합니다. |

기술 과제는 BE 또는 AIAX 책임자가 수락해야 이관 완료로 보며, 원 회고 항목에는 기술 과제 ID와 문서 변경 링크를 역참조로 남깁니다.
CNS는 D+30일에 완료 여부가 아니라 재발률, 문의 건수, 복구시간 또는 교육 통과율 중 지정된 검증 지표의 변화를 확인합니다.
플레이북 개정본은 소유 부서 부장 승인 후 버전·시행일·변경 근거를 기록하며, 승인 전 초안은 표준 절차로 사용하지 않습니다.
