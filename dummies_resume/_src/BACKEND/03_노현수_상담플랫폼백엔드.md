## 노현수 | 상담·고객센터 플랫폼 백엔드 개발자

> 쇼핑몰 고객센터의 상담 티켓 플랫폼에서 API와 외부 연동을 담당했습니다. 상담 이력이 쌓여 느려진 목록 조회를 실행 계획부터 다시 보고 고쳤고, 고객사 쪽으로 보내는 웹훅이 중복 티켓을 만드는 문제를 멱등성 키와 재시도 구조로 정리했습니다.

### 경력

**로지브릿지 고객센터서비스팀 · 백엔드 개발자 (정규직)** · 2023.01–2026.10 · 3년 10개월
자사 쇼핑몰 2곳과 입점사 CS 조직이 함께 쓰는 상담 티켓 플랫폼을 백엔드 3명이 담당. 상담 저장 구조와 외부 연동이 제 담당이었습니다.

- **상담 티켓 API** · Python·FastAPI로 티켓 생성·배정·이력 조회 API를 담당. SQLAlchemy로 모델을 정의하고 Alembic으로 스키마를 단계별로 올렸으며, 기능마다 pytest로 정상·예외 케이스를 같이 작성.
- **비동기 처리 · 인증** · 첨부 파일 변환과 알림 발송은 Celery·Redis 큐로 분리, 입점사 담당자 로그인은 OAuth2 인증 서버 연동과 JWT 발급으로 처리. 서비스는 Docker 이미지로 배포하고 외부 요청은 Nginx가 받게 구성, 운영 지표는 Prometheus로 내보내 Grafana 대시보드에서 확인.

### 대표 프로젝트 ① 상담 이력 목록 API 응답 지연 개선

**현장 문제** · 상담 티켓이 누적되면서 상담원이 쓰는 **티켓 목록·검색 화면이 눈에 띄게 느려지고, 바쁜 시간대에는 타임아웃으로 빈 화면이 뜨는 일**이 생겼습니다. 서버를 늘려도 같은 증상이 남아 쿼리부터 확인했습니다.

- **본인 역할** · PostgreSQL `EXPLAIN ANALYZE`로 목록 쿼리를 확인해 ⓐ 담당자·상태 조합에 인덱스가 없어 전체 스캔이 나는 점 ⓑ 티켓마다 마지막 메시지를 따로 조회해 N+1이 생기는 점을 찾음. 조건 순서에 맞춘 복합 인덱스를 추가하고, 마지막 메시지는 한 번에 묶어 가져오도록 고치고, OFFSET 페이지네이션을 커서 방식으로 바꿈.
- **검증 방법** · 운영 데이터를 복제한 환경에서 **티켓 180만 건** 기준으로 변경 전후를 같은 쿼리·같은 조건으로 측정하고, Locust로 동시 사용자 100명 10분 부하를 따로 돌림. 캐시 때문에 두 번째 측정이 빨라지는 것을 막기 위해 측정마다 캐시를 비움.
- **성과** · ① 목록 API p95 응답 **1,840ms → 320ms**. ② 동시 100명 부하에서 오류율 **2.7% → 0.1%**. ③ 반대 지표: 인덱스를 늘리면서 티켓 생성 쓰기 시간이 **18ms → 21ms**로 늘었지만, 생성 호출량이 조회의 1/30이라 수용하고 증가치를 기록해 둠.

### 대표 프로젝트 ② 고객사 웹훅 연동의 중복 티켓 제거

**현장 문제** · 입점사 주문 시스템이 보내는 웹훅으로 티켓을 자동 생성했는데, **같은 문의가 2~3건으로 중복 생성돼 상담원 두 명이 같은 고객에게 각각 답하는 일**이 월 단위로 반복됐습니다.

- **본인 역할** · 원인을 ⓐ 고객사 쪽 응답 대기가 길어 타임아웃으로 떨어진 요청을 고객사가 다시 보내는 것 ⓑ 우리 쪽이 수신 기록을 남기기 전에 티켓을 만드는 순서 문제로 좁힘. 수신 요청의 멱등성 키를 Redis와 테이블에 함께 남겨 같은 키는 이미 만든 티켓 ID를 그대로 돌려주게 하고, 전송 실패 건은 지수 백오프로 5회까지 재시도한 뒤 데드레터 테이블로 보내 운영 화면에서 재처리할 수 있게 함.
- **현장 예외 처리** · 한 고객사의 SSO(SAML) 연동에서 식별자로 이메일이 아니라 사번이 와 계정 매핑이 실패하는 것을 발견. 고객사별 식별자 항목을 설정값으로 빼고 매핑 테이블을 둬, 코드 수정 없이 신규 고객사를 붙일 수 있게 함.
- **성과** · 8주 운영 기준 중복 티켓 **월 평균 47건 → 0건**, 실패 연동 수동 재처리 **주 3.5시간 → 0.4시간**, 웹훅 전달 성공률 **97.1% → 99.8%**.
