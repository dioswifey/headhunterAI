# 질문·꼬리질문 버그 수정과 A17 OpenAI 생성·룰 세팅 결과 리포트

대상은 지난 세션(2026-11-19~20, 커밋 `a491873`)에 한 질문·꼬리질문 수정, 사내문서 질문(A17) 생성의 OpenAI 전환, 질문 품질 룰 세팅이다. 이 리포트를 쓰면서 코드·데이터는 바꾸지 않았고 GPU·OpenAI도 부르지 않았다. 숫자는 이미 있는 측정 파일과 오늘(2026-11-20) 한 규칙 재검증(모델 호출 0회)에서 그대로 옮겼다. 측정하지 않은 것은 '미측정'으로 적었다.

## 1. 한 줄 결론

**규칙과 지시문은 만들어졌지만, 지원자가 실제로 받는 질문에는 대부분 아직 닿지 않았다.** 새 검사는 사내문서 질문을 *새로 만들 때*만 돈다. 이미 저장된 질문 풀은 새 룰로 다시 검증된 적이 없다(지금 기준으로 다시 돌리면 이 PC 풀 528개 중 216개, 41%가 탈락). 면접 중에도 질문을 다시 쓰거나 새로 만드는 경로 3개(질문 검수 A6의 재작성, 이력서 질문, 이력서 템플릿)가 새 룰을 거치지 않는다. 고쳐진 것은 공고·직무 관문, 꼬리질문 문장 검사 일부, 채점 루브릭(M과 L이 갈리게 됨)이다.

## 5. 오늘 재검증 결과 (2026-11-20, 모델 호출 0회)

현재 코드의 `validate()`와 규칙 함수를 저장된 질문 풀에 그대로 다시 돌렸다. 대상은 두 풀이다.

- **로컬 528** — 이 PC의 Chroma 사내문서 질문(인성 111·직무 170·기업 247). 전부 2026-11-17 생성분이고, 지금 이 PC에서 면접에 실제로 쓰이는 풀이다.
- **백업 592** — git의 `eval_runs/iq_backup_2026-11-19/internal_questions.jsonl`(인성 127·직무 196·기업 269). 11-17분 154개 + 11-19 재생성분 438개. PRD §10.20의 590개(인성 126·직무 195·기업 269)와 2개가 다르고, 그 차이에 대한 기록은 없다.

> 생성 모델 칸이 두 풀 모두 전부 `qwen3:4b`다. 그런데 코드가 이 칸에 **실제 제공자가 아니라 항상 `LLM_MODEL`**을 적기 때문에(아래 ⓒ), OpenAI로 만든 질문이 섞였는지는 판별할 수 없다. **OpenAI로 풀 전체를 다시 만들었다는 기록은 찾지 못했다.**

### 5-3. 피드백 항목별 — 지금 코드가 실제로 막는가

| 피드백 | 지금 상태 |

### 5-4. 면접 중에 새 룰을 거치지 않는 경로 3개

1. **질문 검수 A6가 면접 중에 사내문서 질문을 다시 쓴다** — `question_graph.evaluate_philosophy`(`question_graph.py:643`)는 인성만 건너뛰고(`:651`) 직무·기업 사내문서 질문을 로컬 4B로 고친다. 고친 문장은 길이·차단 목록·토큰만 보는 `_rule_ok`(`:670`)만 거치고, 비문·문장 틀 검사는 거치지 않는다. `qa_full_2026-11-19`에서 사내문서 직무 질문 9개 중 3개가 바뀌었고, 예 하나는 이렇게 나빠졌다:
   - 원문: "AI 모델 서빙 설정에서 '트래픽 가중치 합이 100이 아닌 경우 실패'라는 기준이 적용되는 상황이라면, 어떻게 해당 설정을 검증할지 설명해 주세요."
   - 면접 중 재작성: "헤드헌터랩_경기에서 비전 모델 서빙 환경에서 … 해당 설정을 검증하기 위해 **어떤 경험과 판단 과정을 거쳤는지** 설명해 주세요." (회사명 + 이 회사에서 일했다는 전제 + 두 개 묻기)

   PRD QST-14 ③ "면접 중에는 다시 쓰지 않는다"와 어긋나고, **OpenAI로 질문을 잘 만들어도 면접 중에 망가질 수 있다**.
2. **이력서 질문** — `questions.make_resume_question`(`questions.py:491`, 면접 중 로컬 4B)은 한 문장·차단 목록·근거(`grounded`)만 검사한다. 수치 결론형·두 개 묻기 검사가 없다. `qa_full_2026-11-19`에서 모델이 만든 이력서 질문 2개가 둘 다 금지 패턴이었다: "…1,200건의 질문을 기반으로 … 매주 자동 점검한 경험을 설명해 주세요.", "…90일 지난 대화 로그를 S3로 옮겨 DB 용량을 60% 줄인 경험을 설명해 주세요". 합성 지시문 규칙 4는 아직 "요구 과제는 1~2개"라서 QST-20 ①(하나만 묻기)과 맞지 않는다.
3. **이력서 템플릿** — 모델 생성이 실패하면 쓰는 고정 문장 3개(`questions.py:35-37`)가 그 자체로 룰을 어긴다. `qa_full_2026-11-19`에서 24문항 중 7개(29%)가 이 템플릿이었다.
   - "이력서에 적은 '{label}'에서 맡은 역할과 가장 어려웠던 문제를 어떻게 해결했는지 설명해 주세요." → 두 개 묻기
   - "이력서에 적은 '{label}'에서 사용한 기술을 선택한 이유와 그 결과를 설명해 주세요." → 개념 2개 + 지시어 '그 결과'
   - 세 문장 모두 라벨을 곧은 따옴표로 감싸 `quoted_internal_term` 패턴과 같다

### 5-5. 새로 찾은 결함

- **ⓐ 관문 2에서 일부만 살아남으면 질문 수가 모자란다** — `_filter_by_posting`이 살아남은 것만 돌려주고(`question_graph.py:338` `return kept or None`), `retrieve`는 모자란 만큼 백업 층에서 채우지 않는다(`:365`). `finalize`(`:816`)와 `questions.pregenerate`(`questions.py:609`)에도 문항 수 검사가 없다 → 직무 3개 중 1개가 탈락하면 기본 질문이 7개가 된다. PRD AC-107(기본 질문 8개 유지)과 어긋날 수 있다. 실제 발생 빈도는 미측정.
- **ⓑ 관문 2가 인성 질문에도 걸린다** — 근태·HR 문서에서 나온 인성 질문은 공고 본문과 유사도가 낮게 나오므로(TRD 표의 근태 0.236), 인성 문항이 백업 층(질문 은행·DB)으로 자주 내려갈 수 있다 → M-55가 떨어질 수 있다. 미측정.
- **ⓒ 생성 모델 기록이 틀린다** — `run_generate`가 생성 모델 칸에 항상 `config.LLM_MODEL`을 적는다(`internal_question_agent.py:428`). OpenAI로 만들었는지, OpenAI가 실패해 로컬로 대체됐는지 저장 뒤에 알 수 없다.
- **ⓓ 인성 질문이 사내 규정 퀴즈가 된다** — 백업 592의 인성 127개 중 52개(41%)가 HR·근태 문서(`doc_type` hr 42·attendance 10)에서 나왔다. 예: "반차와 반반차를 동시에 사용할 때, 연차 차감 규칙이 어떻게 적용되나요?", "휴직 유형별로 필요한 서류가 다르면, 이 회사에서 어떤 기준으로 서류를 선택하는지 설명해 주세요." 지원자가 답할 수 없는 회사 내부 규정을 묻는다. 지난 세션의 미결 과제(TAL-01 같은 추상 가치표 문서 처리)와 같은 뿌리다.
- **ⓔ 사내문서 질문에도 음성 조각 같은 문장이 있다** — "수요예: 예측 대시보드가…", "수요예측 대시보: 예측 결과를…" 등 로컬 4·백업 2건. 콜론 조각 검사는 꼬리질문(`readable()`)에만 있고 사내문서 질문 검증에는 없다.
- **ⓕ 새 룰을 확인하는 회귀 시험이 0건이다** — `backend/tools/`에 `sentence_shape`·`has_malformed_phrasing`·`readable`을 부르는 시험이 없다. 아래 ⓖ가 그대로 지나간 이유다.
- **ⓖ 문장 틀 검사 2종이 죽어 있다(확인)** — `ABSTRACT_HEAD`(`:309-312`)·`TWO_CONCEPTS`(`:314`) 끝에 백스페이스 문자(0x08) 1바이트씩, 2개가 들어 있다. 질문에 그 문자가 나올 일이 없으니 두 검사는 한 번도 걸리지 않는다. 고칠 때 주의할 것:
  - 추상 범주(`ABSTRACT_HEAD`)는 고치면 로컬 1·백업 2건을 잡는다. 전부 진짜 위반(사고 4 문장 포함)이다.
  - 개념 2개(`TWO_CONCEPTS`)는 0x08만 지우면 로컬 32·백업 33건을 잡지만 **약 절반이 잘못 잡은 것**이다. 예: "기안자와 팀장이"(사람 둘), "사실과 의견을 구분해"(둘을 가르는 한 과제), "피신고인과 신고인의 관계", "직속상사와 구성원이". 범위를 좁힌 뒤 켜야 한다.
- **ⓗ 사내 용어 검사에 곡선 따옴표가 빠져 있다** — `QUOTED_PHRASE`(`internal_question_agent.py:89`)는 곧은 따옴표(`'` `"`)와 「」『』만 본다. 같은 파일의 구체 앵커 검사(`:143`)에는 ‘’“”가 들어 있다. 지금 풀에는 곡선 따옴표 질문이 0건이지만, OpenAI는 곡선 따옴표를 쓸 수 있어 재생성 때 바로 빈틈이 된다. TRD §6.9.4(a)는 코드를 그대로 옮겨 같은 누락이 있다.
- **ⓘ '조건형 상황 없음' 검사가 '~(으)면' 조건을 인정하지 않는다** — "…30분 이상 차이가 나면, 어떻게 해결해 보시겠습니까?"처럼 분명한 조건문도 `no_situation`으로 떨어진다. `no_situation` 탈락 중 이런 것이 로컬 105건 중 25건·백업 30건 중 10건(잘못 잡은 후보)이다.

## 9. few-shot 검증 장치 (2026-11-20)

사용자가 직접 응시하며 준 피드백 문장이 질문 생성 지시문의 좋은 예/나쁜 예(few-shot)가 됐다(HANDOFF 28-5). 앞으로 예문이 더 늘어날 때를 대비해, few-shot의 위험을 미리 잡는 장치를 두 층으로 둔다. 리드 지시(LLM-as-evaluator)는 처음에 전달이 빠져 이 절에서 구현을 시작했다.

### 9-1. 위험 4가지

| 위험 | 예 | 잡는 곳 |
|---|---|---|
| 예문 베끼기 | 모든 인성 질문이 '회계팀 브리핑' 예문을 말만 바꿔 씀 | 1층 ② 내용어 Jaccard ≥ 0.5 · 임베딩 코사인 ≥ 0.90 |
| 예문 내용 새기 | 조각에 없는 '생산 라인'·'소비기한'이 질문에 들어감 | 1층 ③ 예문 고유어가 근거(조각·이력서·공고)에 없으면 **탈락**(A18·이력서 질문 검사에 연결) |

### 9-2. 1층 — 규칙·지표 (LLM 호출 0회) · 구현 완료

- **① 예문 등록부** — `backend/app/agents/fewshot_guard.py` `REGISTRY` 11개(사내문서 질문 지시문 8 · 이력서 합성 2 · 꼬리질문 1). 예문마다 id · 지시문 파일 · 좋은 예/나쁜 예 · 원문 · `key_terms`(다른 장면의 고유한 말, 근거에 없으면 탈락) · `style_terms`(일반 묘사어, 빈도만 봄). 시험이 **등록 예문이 실제 지시문에 있는지** 확인한다 — 예문을 바꾸고 등록부를 안 고치면 시험이 실패한다.
- **② 베끼기 탐지** — `copy_score()`(내용어 Jaccard) + 도구에서 예문 임베딩 코사인.

### 9-3. 2층 — LLM 판정 노드 (설계 · 실행은 GO 대기)

- **위치**: 오프라인 A18 검증 뒤, **표본만** 판정(면접 경로 아님 → 면접 속도 영향 없음).
- **판정 항목**: 표현만 바꾼 베끼기인가 · 조각의 핵심을 묻는가 · 같은 질문 묶음인가 · (추가 제안) 지원자가 답할 수 있는가 — 맡는 일이 구체적인가, 지원자가 모르는 것을 전제하는가, 면접관용 기준을 질문으로 뒤집었는가.
- **판정 모델 = 로컬 Qwen**. 외부 AI 예외(⑥)는 생성에만 있고 판정은 없다(생성·판정 분리 원칙).
- **먼저 일치도를 잰다**: 사용자가 준 피드백 문장(attempt 14 사고 문장 8개 + 오늘 지적한 '경험하지 않은 기술' 질문 + 사용자가 괜찮다고 본 질문)을 골든셋으로 써서 Cohen's kappa를 잰다. **kappa ≥ 0.6일 때만 결과를 반영**하고, 그 전에는 참고용이다.
- **근거 — 2026-11-19 실패 사례**: 같은 목적(질문 구체성)으로 로컬 4B 판정을 만들었더니 591개 중 100개 표본에서 **42%** 탈락, 예시를 넣어 다시 써도 **43%**. 사람이 직접 든 표본은 12개 중 2개(17%)였고, "RFC 소유자가 초안을 작성한 후 … 테크 리드와 같은 검토자에게 …" 같은 멀쩡한 질문까지 떨어뜨렸다(거짓양성). 그래서 2층은 **골든셋 일치도로 먼저 검증하고, 넘지 못하면 반영하지 않는다**(RAG_질문품질_QA.md ④ · PRD v0.16 QST-17 ③).

### 10-2. 원인

F4(주제 반복 금지)는 **이력서 질문**과 **다시 쓴 직무·기업 문장**에만 걸려 있었다. retrieve가 사내문서 질문(A17)을 카테고리별로 따로 뽑으면서, 앞 카테고리에서 이미 뽑은 질문과 출처가 같은지는 보지 않았다. 카테고리 안 중복 기준(`dup_group`)도 역량 이름이라서, 역량만 다르면 **같은 조각**에서 나온 질문 2개가 같이 나갔다(QA 실행에서 직무 Q6·Q7 둘 다 `MSK-15#s6`).

### 10-3. 조치 (`backend/app/agents/question_graph.py`)

- `_topic_key(b)`: 주제 열쇠는 프로젝트 묶음으로 잡는다. 같은 프로젝트의 상세판·공개판·장애 기록·단위코드 문서는 문서 ID가 달라도 한 주제로 본다(`_TOPIC_FAMILIES`: 콜센터 4문서, 수요예측·배치 서버 4문서). 묶음 밖 문서는 문서 ID로 가른다.

### 10-5. 남은 것

- **낱말 단위 겹침은 아직 남아 있다.** 예를 들어 공고 4에서는 사내문서 질문 "RAG 검색 결과 전달 방식"과 Redis 은행 질문 "RAG 답변 디버깅"이 함께 나간다. 지금 있는 단어 비교 함수 `QR.shared_topic`을 세트 전체에 돌려 보니 16세트 중 16세트가 걸렸다. 걸린 말은 대부분 `에서`(`{회사}에서` 조각), `고객`, `서비스`, `줄이기` 같은 흔한 말이었다. 오탐이 많아 이 함수로는 자를 수 없다. 이 단계를 하려면 질문끼리 임베딩 코사인을 비교하고 경계값을 정한 뒤 교체 후보를 둬야 한다. 경계값은 사용자 지적 쌍을 기준으로 실측한다.
- 기업 질문 후보가 모두 콜센터 프로젝트인 공고(4번 등)에서는 기업 문항이 일반 은행 문항("우리 회사에 지원한 이유…")으로 내려간다. 원인은 기업 관문 2(0.58)이며, 기업 관문 결정은 사용자 대기 중이다.
