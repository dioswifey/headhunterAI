# 사내문서 질문(A17) 구체성 품질 QA

이 문서는 일반 `QA.md`·`TEST.md`·`VERSIONS.md`(구현 품질·테스트 전반)와 **별개**다. 사내문서 질문 생성(A17, `app.agents.internal_question_agent`)의 RAG 능력 검증 지표로 사용자가 지정해 따로 보관한다. 대상 코드: `backend/app/agents/internal_question_agent.py`(`validate()`, `CONCRETE_*`, `has_concrete_anchor`) · `backend/app/prompts/generate/internal_question.md`(규칙1).

## ① 문제 정의

사용자가 personality/job/company 각 4개씩 12개를 직접 샘플 검토(2026-11-19) — 10/12는 구체적 상황+목표가 들어가 양호, **2/12는 "~상황이라면, 어떻게 하시겠습니까?" 형식만 있고 내용이 비어 있음**:

- "백엔드팀에서 의존 관계와 운영 위험을 조기에 드러내는 상황이라면, 어떻게 하시겠습니까?" (TAL-01#023#0)
- "다른 부서와 협업해 변경 내용을 문서화한 상황이라면, 어떻게 하시겠습니까?" (TAL-01#001#0)

두 문항 모두 같은 원본 문서 `TAL-01`(헤드헌터랩 인재상)에서 나왔다 — 이 문서가 "가치가 업무에서 어떻게 표현되는가"를 설명하는 추상적 원칙·표 형식 문서라, A17이 그 표현을 그대로 질문 틀에 옮기면 "상황"이 실은 평가하려는 가치·역량 설명 자체의 재진술이 되는 구조적 약점이 있다.

패턴 요약: ① 조건형 어미("~다면/~라면")는 붙어 있다 ② 그 안에 숫자·인용·고유명사·실제 사건이 전혀 없다 ③ 질문을 만든 재료(intent·competency·expected_keywords)만 다른 말로 되풀이한다.

## ② 1차 수정 (2026-11-18, SITUATION_MARKERS 어미 검사)

최초 설계는 조건형 어미(`SITUATION_MARKERS`: "다면·상황·경우·때" 등)가 **있는지만** 봤다. 이건 "조각 머리글·메타 설명만 베껴 조건형 어미조차 없는" 다른 문제(internal_question.md 규칙1 위반)를 잡기 위한 것이었고, 위 ①의 두 문항은 **어미가 있으므로 이 검사를 그대로 통과**한다.

1차 수정 검증(재생성 전 591개 중 무작위 20개 샘플, seed 고정): 80%(16/20)가 조건형 어미를 가지고 있었음 — 어미 유무 자체는 이미 널리 퍼져 있어 이 지표로는 ①의 2문항을 가려낼 수 없었다.

## ③ 1차 수정의 한계 발견 — 어미만 검사, 내용 공백 통과

사용자가 ①의 2문항을 지적하면서 원인이 드러남: `SITUATION_MARKERS`는 문법적 어미 유무만 보는 **형식 검사**이지 **내용 검사**가 아니다. 모델이 어미만 붙이고 알맹이(구체적 명사·숫자·행위·대상)를 비워도 통과한다.

## ④ 2차 수정 — 두 가지 시도

### 시도 A: 모델 보조 판단 (A6/A7과 같은 패턴) — 폐기

규칙(정규식·키워드 겹침)만으로는 구분이 안 된다는 걸 먼저 실측으로 확인했다(①의 두 문항이 조각 본문 단어로 만들어져서 "조각에서 왔는지" 겹침 검사로는 정상 문항 분포 한가운데 섞였다). A6(philosophy_fit)·A7(answerability)과 같은 패턴으로 로컬 Qwen(`llm.chat_json`, A6/A7과 동일 모델)에 "실제 업무 상황(사건·요청·숫자·구체 대상)을 묘사하는가, 평가 재료를 되풀이한 것뿐인가"를 묻는 체크(`concrete_situation_ok`, 프롬프트 `evaluate/situation_concreteness.md`, 폐기 후 파일 삭제)를 추가했다.

- 1차 프롬프트: 591개 중 100개 판정, **탈락 43개(43%)**
- few-shot 예시 4개를 추가해 재조정: 작은 테스트셋(9개)은 100% 정확했으나, **실제 591개에 다시 돌리니 100개 중 43개(43%)로 거의 그대로**
- 탈락 목록을 사람이 직접 재확인: 명백히 괜찮은 문항도 다수 탈락시킴(거짓양성) — 예:
  - "RFC 소유자가 초안을 작성한 후 검토 단계를 진행할 때, 영향받는 팀의 테크 리드와 같은 검토자에게 피드백을 전달하는 방식을 설명해 주세요." → 탈락 (RFC·테크 리드라는 구체 명사가 있는데도)
  - "프로젝트 철수 시, 현금 흐름과 고객 요청이 동시에 발생할 때 어떻게 처리하시겠습니까?" → 탈락 (구체적 충돌 상황인데도)
  - "출퇴근 누락이 반복적으로 발생할 때, 어떤 점검을 통해 원인을 파악하고 개선할까요?" → 탈락 (사건이 명시돼 있는데도)

**결론**: 로컬 4B 모델(qwen3:4b)이 few-shot을 줘도 "~상황이라면 어떻게" 표면 형태만 보고 내용을 다시 따지지 못하는 경향이 있고, 프롬프트를 두 번 조정해도 탈락률이 42%→43%로 거의 그대로였다(모델 역량 한계로 판단). 사람이 직접 든 원래 샘플(12개 중 2개, 17%)과 2.5배 이상 차이 나는 탈락률로 전체를 교체하면 **멀쩡한 문항을 대량으로 깎아내는 더 큰 사고**가 날 위험이 있어 폐기했다.

### 시도 B: 좁은 규칙(순수 토큰 검사, GPU 불필요) — 채택

사용자가 지정한 정확한 패턴만 규칙으로 옮겼다:

1. 문장이 "~다면/~라면, 어떻게 하시겠습니까?" 류의 일반적 종결로 끝난다
2. **그런데도** 문장 안에 구체 앵커가 **하나도** 없다 — 숫자, 인용부호(「」·""·''), 고유명사·문서명·이벤트명(영문 토큰 포함), 또는 추상명사(위험·문제·상황·의존 관계 같은 상위어)가 아닌 구체 행위·대상 명사가 전부 없는 경우만

구현(`internal_question_agent.py`):
- 숫자·인용부호·영문 토큰(2자 이상) 중 하나라도 있으면 즉시 통과
- 없으면 한글 2글자 이상 토큰에서 조사·어미(`CONCRETE_SUFFIXES`, 길이 긴 것부터 떼어냄)를 떼고, 남는 어근이 `CONCRETE_ABSTRACT`(가치·원칙·역할 설명에 쓰는 상위어 — 상황·경우·업무·과정·절차·기준·역량·가치·역할·책임·관계·의존·운영·위험·문제·협업·소통·조정·문서화·변경·내용·확인·처리·진행·수행·담당·설명·부서·회사·조기·드러내다 등)에 전혀 안 걸리는 토큰이 하나도 없으면 탈락
- 부서·팀 이름(접미 "팀"으로 끝나고 6자 이하, 예: "백엔드팀")은 **그 자체로는 구체 앵커로 치지 않는다** — "누가"일 뿐 "무슨 일"이 아니기 때문. 1차 구현에서 "백엔드팀"이 걸려 통과해 버리는 문제를 발견해 추가한 규칙.

검증: 사용자가 지적한 3문장(RFC·프로젝트 철수·출퇴근 누락)을 먼저 통과 여부로 테스트 → 전부 통과(True) 확인 후 591개 전체에 적용.

## ⑦ 잔여 리스크·다음에 측정할 것

- **TAL-01#023#0의 교체 결과는 완전히 새로운 상황이 아니다.** 재생성해도 원본 문서(TAL-01, 인재상 표)가 추상적이라 "백엔드팀에서 의존 관계와 운영 위험을 조기에 드러내는" 문구가 그대로 남았고, 질문 뒤쪽에 "그 위험을 예방하고 신속히 대응"이라는 구체 동사가 하나 더 붙어 규칙을 통과했을 뿐이다. 규칙은 통과했지만 **내용이 질적으로 크게 좋아졌다고 보기는 어렵다** — 솔직히 남겨 둔다.
- **근본 원인은 원본 문서의 추상성이다.** TAL-01처럼 "가치가 어떻게 표현되는가"를 설명하는 표/원칙 문서는 애초에 구체적 사건을 담고 있지 않아, 재시도를 더 해도 비슷한 패턴이 나올 가능성이 있다. 다음에 고려할 것: ① 이런 문서를 personality 카테고리 질문 생성 대상에서 빼거나 ② `internal_question.md`에 "원본이 추상적 가치표라면 지원자 본인의 과거 경험을 묻는 형태로 바꿔라" 같은 더 구체적인 지시 추가.
- **좁은 규칙은 "지금 보인 두 패턴"에 맞춘 것이라 커버리지 한계가 있다.** `CONCRETE_ABSTRACT` 목록에 없는 새로운 추상 어휘 조합으로 미래에 비슷한 공백형 질문이 생기면 이 규칙이 못 잡을 수 있다. 정기적으로(사내문서 질문을 재생성할 때마다) 사람이 샘플을 다시 봐야 한다.
- **로컬 4B 모델의 "표면 형태 vs 내용" 구분 실패는 이 체크에만 한정된 관찰이 아닐 수 있다.** A6(philosophy_fit)·A7(answerability)도 같은 모델·같은 패턴을 쓰므로, 비슷한 거짓양성이 거기서도 날 수 있다는 가능성은 이번에 측정하지 않았다(범위 밖).
- 591→590으로 줄어든 1개는 personality 카테고리 TAL-01#023#0의 두 번째 질문 슬롯 — 이후 사내문서 질문 수 집계 시 참고.

## ⑧ 질문·답변·평가 실측 (2026-11-19, 조정자 지시 — 그래프 1-A·1-B·2 전수 점검)

사용자 지시 원문: "너도 돌려서 qa excel 질문마다 따로 평가하고 답변 너가 만들어서 답변 평가 어떻게 됫는지 평가 기준 검증 다 체크해서 qa 파일 제대로 만들고 업데이트해". 기존 도구(`backend/tools/sim_applicants.py` gen·judge·evaluate — 제품 코드는 그대로 호출, 지원자 데이터는 전부 가상)를 그대로 재사용했다. 입출력 전체는 `documents/03_QA_doc/eval_runs/qa_full_2026-11-19/`에 있다.

**범위**: 가상 지원자 3명(P03 백엔드·P08 데이터사이언스·P20 AI/AX, 기존 2026-11-16 시뮬레이션 자원 재사용) × 8문항 × 60초 분량 H/M/L 답변 3벌 = 72개 답변. GPU는 user의 실제 응시와 경합하지 않게 순차·백그라운드 로그로 돌렸다(진행 중 api 컨테이너가 외부에서 한 번 재시작된 걸 발견해 조정자에게 확인 요청함 — 작업 자체에는 영향 없었음).

### 8-1. 질문 뽑기 — gen_method 분포

8문항 × 3명 = 24문항. 전부 `internal_q:`(사내문서, 2026-11-17 전환 이후 설계대로) 또는 `llm|internal:`/`template`(이력서 기반) — **Redis(`redis:`)·DB 은행(`db`) 출처는 0건**, 사내문서 풀이 충분히 채워진 뒤로는 백업 층이 거의 안 쓰인다는 걸 재확인했다.

| 범주 | 건수 | 비율 |
|---|---|---|
| internal_q(사내문서, 인성·직무·기업) | 15 | 62.5% |
| llm\|internal(이력서+사내문서 참고, 리바이저) | 2 | 8.3% |
| template(이력서, 참고 문항 못 찾아 원문 그대로) | 7 | 29.2% |
| redis / db | 0 | 0% |

P20(ai_ax)은 이력서 3문항(Q3·Q4·Q5)이 **전부** template으로 떨어졌다 — `resume_question_merger`가 이 사람의 프로젝트(통계·상담 품질 분석)와 맞는 참고 문항을 못 찾은 것으로 보인다. 결함은 아니고(모자르면 원문 템플릿으로 안전하게 떨어지는 설계대로 동작) 관찰 사항으로만 남긴다.

### 8-2. 질문 자체 평가 (24문항)

- **구체적 상황**: 24/24 — 전부 숫자·구체 사례·조건형 상황 중 하나 이상 포함(⑤의 `has_concrete_anchor` 규칙 기준으로도 전부 통과)
- **목표(평가 의도) 분명함**: 24/24 — 질문마다 무엇을 확인하려는지 모호하지 않음
- **사내문서 근거 실제 반영**: internal_q 15건 모두 `doc_refs`가 실제 조각 ID를 가리킴(그라운딩 확인, A18 통과분이라 당연하지만 재확인)
- **직무·이력서 부합**: 24/24 — 자리에 맞지 않는 질문 없음(P20의 비전 검사 역할에 통계·콜센터 경력을 연결한 질문 등 포함)
- **금지 항목(나이·가족·학벌 등)**: 0건
- **중복**: 같은 사람 안에서 중복 0건. 세 사람이 같은 조각(예: MSK-53#s1)에서 같은 문항을 공유하는 건 질문 풀을 같이 쓰는 설계라 정상(한 사람의 세트 안에서 중복되는 게 문제)

### 8-3. H/M/L 꼬리질문·평가 결과

꼬리질문(judge_detail, 그래프 1-B 그대로 호출) — 질문당 1개·전체 4개 상한:

| 레벨 | P03 | P08 | P20 | 비고 |
|---|---|---|---|---|
| H | 0 | 0 | 0 | 우수 답변에서는 꼬리질문이 전혀 안 생김(의도대로) |
| M | 2 | 3 | 4(상한) | |
| L | 3 | 2 | 4(상한) | |

그래프 2(evaluation_graph.evaluate_blocks→compute→summarize→decide, 실제 코드 경로) 점수:

| 레벨 | P03 | P08 | P20 | 판정 |
|---|---|---|---|---|
| H | 88.47 | 81.02 | 75.12 | 전부 pass |
| M | 28.28 | 22.13 | 20.25 | 전부 fail |
| L | 20.00 | 20.00 | 20.00 | 전부 fail(항목 5개 전부 정확히 1/5) |

**H > M > L 순서 역전: 0건**(3명 전부 순서 유지). 다만 **M과 L의 차이가 0.25~8.28점뿐**이라 사실상 거의 안 갈린다 — ⑧-4에서 자세히.

- **5개 항목(전문성·논리성·관련성·전달력·조직적합성)이 레벨을 구분하는가**: H는 항목별로 57.5~100까지 펴져 있어 변별력이 있다. M·L은 항목 간 차이가 거의 없이 전부 20점대 초반에 몰린다 — 아래 QA-32.
- **인용(quote)이 실제 답변 원문의 부분 문자열인가**: 전체 288개 항목-점수 중 **22건(7.6%)**이 `quote_ok` 검증에 실패해 **코드가 강제로 1점·verified=False로 확정**했다(H 9건·M 1건·L 12건). 설계대로 LLM이 점수를 못 우회하고 코드가 막는 걸 실측으로 확인했다.
- **합산·합불이 코드 규칙대로인가**: 전부 `evaluation.compute`의 가중합·`pass_score` 비교로만 결정됐다(LLM이 total/result를 만들지 않음). 확인됨.
- **꼬리질문이 L에서 나오고 H에서는 안 나오는가**: 맞음(위 표). 단 M도 상당수(2~4개) 나와 — M은 설계상 "맞지만 구체성 부족"이라 꼬리질문이 나오는 게 정상.

### 8-4. 평가 기준(루브릭) 자체에서 찾은 문제 — QA-32(결함관리 시트 동일 번호)

M(답은 맞지만 구체성 부족)과 L(일반론·주제이탈·STT잡음·되묻기)이 점수에서 거의 구분되지 않는다. L은 세 사람 모두 **5개 항목 전부 정확히 1/5(100점 환산 20.0)** — 질문마다 답변 유형이 다른데도(일반론/주제이탈/되묻기/STT잡음/이력서와 다름) 전부 똑같이 바닥을 찍었다. M도 20.3~28.3으로 L과 겹친다. 루브릭에 적힌 "3: 기본 요구를 충족함" 구간이 실측에서 전혀 안 쓰이고, 점수가 1점(최저) 아니면 4~5점(H)으로 양극화된다.

코드 쪽(인용 검증·가중합·판정 분기)은 전부 정상 동작을 확인했으므로 **버그가 아니라 `evaluation.py`의 `EVAL_SYSTEM`·`RUBRIC` 프롬프트가 모델에게 중간 점수(2~3점)를 줄 근거를 충분히 안 주는 것**으로 추정한다(확정 아님). 루브릭·프롬프트를 바꾸는 건 사용자 결정이라 **보고만 하고 고치지 않았다**. 재현 데이터·실제 LLM rationale 전문은 `eval_runs/qa_full_2026-11-19/eval_{H,M,L}.json`의 `scores_by_q`에 있다(예: M 답변에 "핵심이 빠지거나 오류가 있음(2점)"이 아니라 "최저 수준(1점)"으로 매긴 rationale 다수).

## ⑨ QA-32 조치 결과 (2026-11-19, 테스트케이스.xlsx 결함관리 동일 번호)

⑧-4에서 찾은 "M과 L이 점수로 안 갈린다"(QA-32)는 그래프 2 채점(`backend/app/evaluation.py`)을 다음과 같이 고쳐 조치했다.

**고친 것**
1. RUBRIC 1~5점을 전부 구체적으로 다시 썼다 — 3점을 "질문 의도를 정확히 이해했고 내용이 맞으며 주장–근거–결론이 통한다. 수치·사례가 적거나 없어도 판단 자체가 옳으면 이 점수를 준다"로 명확히 정의.
2. "수치·구체 사례·동작 원리·트레이드오프·두괄식 중 하나가 없다는 이유만으로 1~2점으로 깎지 않는다"는 규칙을 명시 — 이 요소들은 4~5점으로 올리는 가점 요소로만.
3. `ITEM_DEF["expertise"]`의 "AI/AX 개념" 하드코딩을 "지원 직무(백엔드·데이터·AI/AX 등)"로 수정 — 백엔드·데이터 지원자가 AI/AX 기준으로 채점되던 버그.
4. 사내문서 근거(모범 답변 요지·기대 키워드)를 채점 프롬프트에 새로 주입 — 기존에는 이력서 질문의 `resume_ref`만 참고했고, personality·job·company(전체의 60%+)는 참고 자료 없이 채점되고 있었다(QO-13류 재발).
5. 인용(quote) 검증을 완화 — `_norm()`에 구두점·따옴표 정규화 추가(쉼표 하나 차이로 탈락하던 문제), quote를 score보다 먼저 쓰게 스키마 순서 변경, 재시도 2→3회. **"원문 부분 문자열이어야 한다"는 핵심 규칙 자체는 그대로 유지**(느슨하게 안 풂).
6. `EVAL_SYSTEM`을 `evaluation.py` 안 문자열에서 `backend/app/prompts/evaluate/scoring.md`로 분리(다른 에이전트와 구조를 맞춤).

**재측정 결과**(같은 가상 지원자 3명 × H/M/L 72건, 재빌드 반영 후):

| 레벨 | 1차(수정 전) | 최종(수정 후) | 판정 |
|---|---|---|---|
| H | 75.1~88.5 | **80.4~89.9** | 3명 전부 pass |
| M | 20.3~28.3 | **25.9~41.3** | 전부 fail |
| L | 20.0 | 20.0 | 전부 fail |

H>M>L 순서 역전 0건. quote_ok 검증 실패율 9.4%→0%(H). M-L 최소 격차는 5.9점(목표 10점에는 못 미치지만 1차 0.3점 대비 대폭 개선). pass_score(70)·항목 가중치(w_*)는 변경하지 않았다(사용자 지시 — "70점이 저 루브릭 기준으로 넘어가게 만들어야 한다", 임계값을 내려 맞추는 건 지시를 거꾸로 수행하는 것).

**추가로 확인한 것 — 모델 역량 한계**: 같은 P03 H 답변 세트를 qwen3:4b → qwen3:8b로만 바꿔 채점하니 **75.6점 → 99.3점**으로 올랐다(항목별로도 4B는 4점대에 머물고 8B는 4~5점을 정상적으로 줌). 루브릭·가중치를 더 고쳐도 **로컬 4B가 5점을 잘 안 주는 성향** 자체는 못 없앨 가능성이 크다는 근거다. 운영 기준 모델이 원래 Qwen3-8B(CLAUDE.md)이므로, 개발 PC(4B)에서의 점수 양극화 잔존은 모델 교체 전까지 남는 **알려진 한계**로 남긴다.

**산출물**: `documents/03_QA_doc/headhunterAI_테스트케이스.xlsx` 결함관리 QA-32(조치완료) · AI평가 EV-64 · **`합격_시나리오`·`불합격_시나리오` 시트 신규**(P03 8문항, 열: 질문|답변|답변 채점 기준|합불 결과|출처|카테고리, 실제 evaluation_graph가 낸 점수·인용·rationale 그대로 — 지어내지 않음, 꼬리질문 3건도 행으로 포함). `headhunterAI_QA_테스트계획서.xlsx` M-64 갱신. 재현 데이터 `eval_runs/qa_full_2026-11-19/final_{H,M,L}.json`(최종본).

|---|---|---|
| H | 78.0 ~ 92.62 (전부 pass) | 79.6 ~ 98.62 (전부 pass) |
| M | 24.95 ~ 40.13 (전부 fail) | 38.65 ~ 43.05 (전부 fail) |
| L | 20.0 (전부 fail) | 20.25 ~ 21.5 (전부 fail) |

**결론(채점 작업 종료)**: 확정 요건 두 가지 — H가 85점 언저리로 pass, L은 fail 유지 — 둘 다 4B·8B 모두 충족. **M은 의도적으로 fail로 둔다.** "M도 합격권"은 사용자가 직접 지시한 목표가 아니라 "70점은 어렵지 않게 통과"에서 도출한 추정 목표였고, M을 pass 쪽으로 더 올리려 루브릭을 추가로 낮추면 L과의 간격이 좁아지거나 L이 같이 올라가는 위험이 실제로 있다(M 25~43 vs L 20~22, 4B·8B 둘 다 간격이 좁음) — **변별력이 합격률보다 우선**이라고 판단해 M은 더 손대지 않는다. M·L이 뚜렷이 분리된 상태를 유지하는 것으로 QA-32를 종결한다. pass_score(70)·w_* 가중치는 끝까지 변경하지 않았다.
